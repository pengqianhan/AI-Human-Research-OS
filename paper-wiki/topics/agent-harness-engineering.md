# Scope

This topic tracks work on the executable software layer around a foundation model: prompt construction, tool interfaces, state and memory, execution control, environment interaction, evaluation, and the representations and workflows needed to modify that layer safely.

# Papers

* [Harness Handbook](../papers/2607.13285.md) - behavior-centric repository representation and progressive-disclosure workflow for localizing distributed harness changes before editing.
* [MemoHarness](../papers/2607.14159.md) - six-dimensional harness search with a dual-layer experience bank and feedback-free per-case adaptation at test time.
* [AI Agents Do Not Fail Alone](../papers/2607.14275.md) - seven-criterion assessment of the context assembled by a harness, validated against corresponding downstream behaviors.
* [Self-Improvements in Modern Agentic Systems](../papers/2607.13104.md) - surveys prompt, memory, tool, and full-harness updates as the fast, explicit branch of persistent agent self-improvement.
* [Recursive Language Models](../papers/2512.24601.md) - a minimal fixed harness (externalized prompt, persistent REPL, sub-LM call, final-answer protocol) whose failures are harness-use failures rather than semantic ones.
* [SearchOS-V1](../papers/2607.15257.md) - middleware-governed search that externalizes state, grounds evidence, detects stalls, enforces budgets, and dispatches workers around explicit coverage gaps.
* [SkillOpt-Lite](../papers/2607.03451.md) - extends a file-native skill optimizer into HarnessOpt, where a coding agent patches execution scaffolding behind human bootstrapping, sandboxed validation, feature toggles, and rollback.
* [LongHorizon-Harness](../papers/2608.01964.md) - a Manage-Execute-Audit loop that externalizes task state outside the growing execution context and advances it only from an independent, read-only auditor's verified evidence, wrapping existing backends (Claude Code, Codex CLI, OpenClaw) through a role-preserving `AgentAdapter`.
* [OpenHands (f.k.a. OpenDevin)](../papers/2407.16741.md) - an event-stream interaction protocol, docker-sandboxed bash/IPython/browser runtime, extensible agent-skills library, and multi-agent delegation, with an inclusion rule that only adds a skill when an LLM cannot readily write the equivalent code itself.
* [HarnessEval-W](../papers/2608.16859.md) - brings the harness paradigm to the evaluator itself: a parent agent plus specialized sub-agents decompose a world-model evaluation question into an auditable evidence tree instead of applying a fixed rubric.
* [StateM](../papers/2608.15089.md) - an agent-native YAML+CLI runbook where phase-level states are simultaneously refreshed control contexts and checked, logged transition contracts, evaluated across a four-level transfer hierarchy (fixed-model lift, frozen cross-generation transfer, adapted cross-provider transfer, held-out task-family generalization) on Terminal-Bench 2.1 and BusinessBench.
* [LLM-as-a-Verifier](../papers/2607.05391.md) - ships TurboAgent, a Claude Code/Codex inference-time proxy that dispatches parallel candidates and reranks them via a Probabilistic Pivot Tournament without modifying the underlying model or agent loop.
* [UI-Mate](../papers/2608.15930.md) - a shared harness plus DemoCUA workflow-conditioning layer that converts multimodal demonstrations into subtask-level guidance the live observation can override, evaluated on a new controlled paired benchmark (OSWorkerBench) that isolates demonstration value from instruction-only capability.
* [EnvHarness](../papers/2608.19880.md) - applies the harness paradigm to the environment side of the policy-environment pair: composable plug-in components reshape a static environment's state, rules, and task composition through its own interface, with EnvRigger closing a diagnose-write-validate loop from the target policy's own trajectories.
* [Zetta](../papers/2608.16590.md) - a closed-loop embodied harness that evolves code-based runtime critics and recovery skills online through three timescale-separated loops (action-frequency, rollout-level, validation-gated) while the base VLA policy stays frozen.
* [AgentScope 1.0](../papers/2508.16279.md) - general-purpose harness infrastructure rather than a harness-modification technique: non-invasive pre/post hooks, automated nested state persistence, and dynamic tool provisioning that other papers in this topic could in principle be built on top of.
* [OpenRath](../papers/2606.19409.md) - proposes Session, a single first-class runtime value every agent, tool, and workflow transforms or annotates, as the programming-model answer to state fragmentation: branching, merging, persistence, and replay become operations on an ordinary program value rather than state reconstructed from controller logs, tool logs, and provider traces after the fact.
* [Graph Engineering](../papers/2608.21156.md) - a 35-author survey arguing that Harness and Loop Engineering, this topic's subject, structurally max out at a single agent's "Individual Intelligence" no matter how far they are pushed, and proposing Graph Engineering (explicit task, agent-coordination, and runtime-state graphs) as the next paradigm for multi-agent "System Intelligence" — it cites this topic's own [LongHorizon-Harness](../papers/2608.01964.md) by name among the harness-as-optimization-target lineage it argues has reached that ceiling.
* [Prime Agent](../papers/2608.23552.md) - a four-level (L0-L3) addressable-state framing for what a harness must expose beyond model weights and active context, implementing [Recursive Language Models](../papers/2512.24601.md)' persistent-REPL abstraction as its computation layer and extending it with non-blocking recursive subagent sessions, direct agent-to-agent communication over a daemon-managed session tree, and Continual Harness state the model itself can revise from trajectory evidence — plus a disclosed case where that revision loop persisted a discovered exploit as a reusable skill with no validation gate.
* [Recuris](../papers/2608.24876.md) - names its four-component patch space (skills, working-memory specification, invocation policy, checkers) "the memory-control layer of the agent harness" and shows that structured execution traces localize an injected fault at 64.8% accuracy versus 13.0% from the task outcome alone, giving this topic's diagnose-write-validate loop a finer-grained, component-typed target than a single undifferentiated harness object.
* [Apodex 1.1](../papers/2608.23283.md) - AgentOS externalizes multi-agent coordination state (a Task Board) outside the LLM's message history and periodically re-injects it so the plan survives context compaction, applying this topic's state-externalization pattern to team coordination rather than single-agent execution state.

# Synthesis

Harness Handbook asks where requested harness behavior lives in code so evolution can be localized and verified. MemoHarness searches six control surfaces and carries execution diagnoses forward as reusable adaptation evidence. SkillOpt-Lite's HarnessOpt instead lets a coding agent inspect raw trajectory files and patch harness code directly, with a human-approved round zero, constrained paths, smoke tests, validation, toggles, and rollback. AI Agents Do Not Fail Alone asks whether one major harness output—the context presented to the model—is clear, grounded, consistent, tool-aware, hardened, and efficient before behavior is tested. SearchOS demonstrates a concrete runtime harness that intercepts model and tool boundaries so evidence grounding, state updates, loop recovery, and budgets are not left to prompt compliance. LongHorizon-Harness targets a narrower, structural failure inside long-horizon execution itself: it splits state-holding, environment-changing, and state-verifying into three separate roles so that an agent's own completion claim can never directly become a persistent state record, and shows the resulting harness-layer change transfers across backbone models and interaction domains without any change to the wrapped backend's native loop. OpenHands sits earlier in this lineage as the foundational infrastructure layer itself — the event-stream protocol, sandboxed runtime, and skill-library discipline that later harness-modification papers in this topic take as their starting substrate, rather than a technique for evolving an existing harness. HarnessEval-W applies the harness paradigm to a different role entirely: not executing a task, but decomposing the *evaluation* of a task's output into sub-agent-verified evidence, extending "harness" from an execution-control concept to an evaluation-control one. StateM shares LongHorizon-Harness's concern with externalizing durable state outside a growing execution context, but generalizes it into a jointly agent-and-user-editable state machine and adds an explicit transfer-hierarchy study (which harness content survives a model swap, a provider swap, or a new task family) rather than a fixed role split. UI-Mate shows the same harness-scaling logic applied to GUI/computer-use agents specifically: a shared execution harness plus a workflow-conditioning layer (DemoCUA) that treats a demonstration as advisory prior rather than replayed script. Self-Improvements in Modern Agentic Systems generalizes these cases into prompt, memory, tool, and full-scaffold updates and argues that this explicit layer should host fast exploration before validated behavior is consolidated into slower model updates. EnvHarness moves the harness paradigm one layer further out again: instead of modifying the agent's own control surface, its EnvRigger designer diagnoses a frozen target policy's trajectories and writes wrapper components for the *environment* the policy trains or is evaluated in, while provably preserving that environment's original verifier — a diagnose-write-validate loop structurally close to MemoHarness's and SkillOpt-Lite's, applied one step outside the agent. Zetta pushes the same failure-diagnose-candidate-validate pattern down to action frequency in embodied control, explicitly separating three timescales (per-action runtime critics, rollout-level diagnosis, cross-rollout validation-gated promotion) so that a frozen VLA policy can be governed as physical execution unfolds rather than only reflected on afterward. AgentScope 1.0 sits underneath all of these as general-purpose infrastructure rather than a harness-modification technique: its non-invasive hook system, automated state persistence, and dynamic tool provisioning are the kind of substrate a harness-patching or environment-reshaping method could be implemented on top of, though the paper itself does not evaluate any such modification loop. OpenRath sits at a similar infrastructural altitude but answers a different, more foundational question than any harness-modification paper above: not how to diagnose and patch a harness, but what runtime object the harness's own state (transcripts, tool effects, memory events, branch lineage) should be represented as in the first place, so that later diagnosis, patching, and audit have something stable to operate on — its central architectural move (a Session value every component transforms rather than a private per-layer record) is a precondition this topic's diagnose-write-validate loops implicitly assume rather than a competing instance of one. Together they suggest a four-part loop: map behavior to authoritative implementation, modify the control layer using execution evidence, independently gate the candidate, then assess both the assembled context and downstream behavior — and the target of that loop can now be the agent's harness, its environment, or (in Zetta's case) an embodied control layer operating within a single rollout. The current evidence does not yet show that these representations and diagnostics remain accurate through long-running self-modification. Graph Engineering steps back from all of the single-agent diagnose-write-validate loops above and asks a different question: even a perfectly self-improving individual harness cannot schedule parallel interdependent subtasks, isolate specialized roles from confirmation bias, or maintain recoverable state across multiple agents, because those are structural limits of a single execution loop rather than harness-quality problems — its proposed answer (explicit task, coordination, and runtime-state graphs, with a "System Evolution" concept requiring validated, rollback-able persistent structural change rather than one-off adaptation) generalizes this topic's own harness-level diagnose-write-validate pattern up one level, from patching one agent's control surface to patching an entire multi-agent system's organization. Prime Agent names the state hierarchy this topic's papers have each been implicitly carving up: L0 (weights, changed by fine-tuning), L1 (active context, changed by compaction), L2 (persistent REPL and recursive subagent sessions, changed by the model's own create/retain/summarize/delete decisions), and L3 (disk-backed history and versioned harness state, changed by refinement) — Recuris's Skill Memory and StateM's runbook both live at L3 in this framing, while LongHorizon-Harness's externalized state and Zetta's runtime critics operate closer to L2. Recuris sharpens this topic's diagnose-write-validate loop into a measured claim rather than an assumed one: it shows a structured execution trace linking verified state, invoked skill, action, and outcome localizes an injected component fault far more accurately (64.8%) than the raw trajectory (37.0%) or the task outcome alone (13.0%, below a constant-answer floor) — direct evidence for why this topic's harness-patching papers need structured evidence, not just failure signal, to target a repair correctly. Apodex 1.1 shows the same externalized-state pattern this topic tracks for single-agent execution (LongHorizon-Harness's role split, StateM's runbook) applied to multi-agent coordination: its Task Board lives outside the LLM's message history and is periodically re-injected so the plan survives compaction, functioning as both external memory and a runtime finalization gate rather than a presentation-only checklist.

# Open Questions

* How should agent-visible behavior be mapped to code when runtime dispatch, generated code, or external services defeat static analysis?
* Which representations improve final patch correctness, not only localization and planning quality?
* How can a harness map remain synchronized through repeated edits without making stale prose an accidental source of truth?
* What evaluation gates are necessary before agents may modify their own harnesses?
* How should harness maintainability, regression risk, token cost, and task capability be optimized together?
* Can preflight context assessment predict harness regressions on unseen tasks without sharing the biases of the behavioral judge?
* Which parts of adaptive harness performance come from global search, case-level experience, distilled patterns, and test-time specialization?
* How should a harness reject stale, misleading, or adversarially similar experience before adapting a new case?
* Which scaffold updates are safe to automate, and which require an independent or human acceptance boundary?
* Which execution invariants should middleware enforce automatically, and which interventions risk suppressing productive but unusual agent behavior?
* Can repeated locally validated harness patches avoid long-term complexity growth, test overfitting, and erosion of the human approval boundary?
* When a harness role structure (e.g. manager/executor/auditor) improves reliability, how much of the token-cost increase is inherent to independent verification versus recoverable through cheaper audit strategies?
* OpenRath's own evidence is scoped to deterministic, locally-verifiable claims (lineage export, local sandbox execution, focused tests) with benchmark-superiority, memory-quality, and merge-quality claims explicitly deferred — does representing runtime state as one first-class Session value measurably improve this topic's harness-diagnosis and patch-correctness questions once that follow-on evaluation exists, or does it mainly help audit and review without changing what a diagnose-write-validate loop can discover?
* Graph Engineering argues (its own Section 6.1) that end-task success alone cannot distinguish genuine system-level organizational improvement from a stronger model or more compute — does the same critique apply to this topic's single-agent harness-optimization papers, several of which report gains without a controlled ablation isolating the harness change from a concurrent model or context-budget change?
* Prime Agent's own Factorio case study shows its Continual Harness refinement loop persisting a discovered specification-gaming exploit as a reusable skill with no validation gate stopping it — should this topic's held-out validation gates (SkillOpt, GenericAgent) be treated as a required part of any online L2/L3 state-revision mechanism, not just an optional strengthening, and would such a gate have caught this specific case?
* Recuris finds that which memory component is worth repairing is domain-dependent and not fixed at design time (write-review is critical on one τ²-Bench domain and inert on the other, with the pattern exactly reversing for a different mechanism) — do this topic's other harness-patching papers, which mostly report one dominant repair target per system, actually have a similarly domain-dependent critical component that a narrower evaluation has not yet surfaced?
