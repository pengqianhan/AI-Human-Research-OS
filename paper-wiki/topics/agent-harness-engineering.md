# Scope

This topic tracks work on the executable software layer around a foundation model: prompt construction, tool interfaces, state and memory, execution control, environment interaction, evaluation, and the representations and workflows needed to modify that layer safely.

# Papers

* [Harness Handbook](../papers/2607.13285.md) - behavior-centric repository representation and progressive-disclosure workflow for localizing distributed harness changes before editing.
* [MemoHarness](../papers/2607.14159.md) - six-dimensional harness search with a dual-layer experience bank and feedback-free per-case adaptation at test time.
* [AI Agents Do Not Fail Alone](../papers/2607.14275.md) - seven-criterion assessment of the context assembled by a harness, validated against corresponding downstream behaviors.
* [Self-Improvements in Modern Agentic Systems](../papers/2607.13104.md) - surveys prompt, memory, tool, and full-harness updates as the fast, explicit branch of persistent agent self-improvement.
* [Recursive Language Models](../papers/2512.24601.md) - a minimal fixed harness (externalized prompt, persistent REPL, sub-LM call, final-answer protocol) whose failures are harness-use failures rather than semantic ones.
* [SearchOS-V1](../papers/2607.15257.md) - middleware-governed search that externalizes state, grounds evidence, detects stalls, enforces budgets, and dispatches workers around explicit coverage gaps.
* [SkillOpt-Lite](../papers/2607.03451.md) - extends a file-native skill optimizer into HarnessOpt, where a coding agent patches execution scaffolding behind human bootstrapping, sandboxed validation, feature toggles, and rollback.
* [LongHorizon-Harness](../papers/2608.01964.md) - a Manage-Execute-Audit loop that externalizes task state outside the growing execution context and advances it only from an independent, read-only auditor's verified evidence, wrapping existing backends (Claude Code, Codex CLI, OpenClaw) through a role-preserving `AgentAdapter`.
* [OpenHands (f.k.a. OpenDevin)](../papers/2407.16741.md) - an event-stream interaction protocol, docker-sandboxed bash/IPython/browser runtime, extensible agent-skills library, and multi-agent delegation, with an inclusion rule that only adds a skill when an LLM cannot readily write the equivalent code itself.
* [HarnessEval-W](../papers/2608.16859.md) - brings the harness paradigm to the evaluator itself: a parent agent plus specialized sub-agents decompose a world-model evaluation question into an auditable evidence tree instead of applying a fixed rubric.
* [StateM](../papers/2608.15089.md) - an agent-native YAML+CLI runbook where phase-level states are simultaneously refreshed control contexts and checked, logged transition contracts, evaluated across a four-level transfer hierarchy (fixed-model lift, frozen cross-generation transfer, adapted cross-provider transfer, held-out task-family generalization) on Terminal-Bench 2.1 and BusinessBench.
* [LLM-as-a-Verifier](../papers/2607.05391.md) - ships TurboAgent, a Claude Code/Codex inference-time proxy that dispatches parallel candidates and reranks them via a Probabilistic Pivot Tournament without modifying the underlying model or agent loop.
* [UI-Mate](../papers/2608.15930.md) - a shared harness plus DemoCUA workflow-conditioning layer that converts multimodal demonstrations into subtask-level guidance the live observation can override, evaluated on a new controlled paired benchmark (OSWorkerBench) that isolates demonstration value from instruction-only capability.
* [EnvHarness](../papers/2608.19880.md) - applies the harness paradigm to the environment side of the policy-environment pair: composable plug-in components reshape a static environment's state, rules, and task composition through its own interface, with EnvRigger closing a diagnose-write-validate loop from the target policy's own trajectories.
* [Zetta](../papers/2608.16590.md) - a closed-loop embodied harness that evolves code-based runtime critics and recovery skills online through three timescale-separated loops (action-frequency, rollout-level, validation-gated) while the base VLA policy stays frozen.
* [AgentScope 1.0](../papers/2508.16279.md) - general-purpose harness infrastructure rather than a harness-modification technique: non-invasive pre/post hooks, automated nested state persistence, and dynamic tool provisioning that other papers in this topic could in principle be built on top of.
* [OpenRath](../papers/2606.19409.md) - proposes Session, a single first-class runtime value every agent, tool, and workflow transforms or annotates, as the programming-model answer to state fragmentation: branching, merging, persistence, and replay become operations on an ordinary program value rather than state reconstructed from controller logs, tool logs, and provider traces after the fact.
* [Graph Engineering](../papers/2608.21156.md) - a 35-author survey arguing that Harness and Loop Engineering, this topic's subject, structurally max out at a single agent's "Individual Intelligence" no matter how far they are pushed, and proposing Graph Engineering (explicit task, agent-coordination, and runtime-state graphs) as the next paradigm for multi-agent "System Intelligence" — it cites this topic's own [LongHorizon-Harness](../papers/2608.01964.md) by name among the harness-as-optimization-target lineage it argues has reached that ceiling.
* [Prime Agent](../papers/2608.23552.md) - a four-level (L0-L3) addressable-state framing for what a harness must expose beyond model weights and active context, implementing [Recursive Language Models](../papers/2512.24601.md)' persistent-REPL abstraction as its computation layer and extending it with non-blocking recursive subagent sessions, direct agent-to-agent communication over a daemon-managed session tree, and Continual Harness state the model itself can revise from trajectory evidence — plus a disclosed case where that revision loop persisted a discovered exploit as a reusable skill with no validation gate.
* [Recuris](../papers/2608.24876.md) - names its four-component patch space (skills, working-memory specification, invocation policy, checkers) "the memory-control layer of the agent harness" and shows that structured execution traces localize an injected fault at 64.8% accuracy versus 13.0% from the task outcome alone, giving this topic's diagnose-write-validate loop a finer-grained, component-typed target than a single undifferentiated harness object.
* [Apodex 1.1](../papers/2608.23283.md) - AgentOS externalizes multi-agent coordination state (a Task Board) outside the LLM's message history and periodically re-injects it so the plan survives context compaction, applying this topic's state-externalization pattern to team coordination rather than single-agent execution state.
* [ASI-Bench](../papers/2608.17271.md) - not a harness-modification technique but independent, benchmark-scale confirmation of this topic's model-vs-harness separation: the same backbone model's score shifts by several points from a harness swap alone (MiMo V2.5 Pro moves from 16.17 to 23.25, Kimi K2.7 from 19.72 to 27.34, both under identical Claude Code vs. their own default harness), while a third model (Kimi K3) barely changes — showing the effect is real but not uniform across models.
* [AutoSaddler](../papers/2608.23041.md) - formulates harness improvement explicitly as an offline learning problem: a Diagnosis-Patch Agent grounds repairs in both execution traces and harness source code, patches are typed by layer and by capability-vs-steering kind under a phased (capability-first) schedule, and an EvoDAG preserves multiple optimization lineages for later recombination rather than forcing linear continuation — reaching peak GAIA2 dev accuracy in ~147 traces versus a comparable baseline's 1,400.
* [AutoDev](../papers/2403.08299.md) - an earlier-generation (March 2024) entry in this topic's lineage: a hand-authored Tools Library, Docker-sandboxed Evaluation Environment, and YAML-configured per-agent, per-command permissions establish sandboxed, typed, permissioned execution as an architectural pattern well before this topic's later papers treat that same harness surface as something to be automatically diagnosed and patched.
* [JIT-Agent](../papers/2608.25593.md) - formalizes any agent harness as a fixed, composable four-module protocol `h = (M, P, A, F)` (memory, planning, action, orchestration), reimplements 13 named harness designs under it (HarnessFactory), and trains a dedicated model through a three-stage pipeline (supervised customization, bounded repair, archive-gated Evo-GDPO evolution) to synthesize task-adaptive harnesses on the fly for arbitrary frozen backbone LLMs, rather than patching one fixed harness in place.
* [Omni Interaction Agent (Gander)](../papers/2609.08977.md) - an agent orchestration runtime whose Gateway manages five persistent entities (Project, Task, Run, WorkerEvent, Delivery) behind a unified Worker Provider interface, with a lean mode (direct low-latency execution) and a coordinator mode (a separate control-plane model producing declarative execution directives the Gateway structurally validates, but never itself executes) — applying this topic's control-layer/execution-layer separation to realtime-to-agentic delegation specifically, where the harness's job is keeping a training-free backend agent (Codex, Claude Code) swappable behind a stable delegation protocol rather than diagnosing and patching that backend's own behavior.
* [Show-Harness](../papers/2609.10522.md) - an embodied harness that redefines the model-facing control interface itself rather than adding diagnosis or patching around an existing one: a nine-unit, view-relative discrete semantic action vocabulary lets a frozen VLM act on a real robot zero-shot, while a deterministic per-embodiment interpreter isolates all embodiment-specific detail outside the model, so adding a new robot requires only a new interpreter rather than retraining or re-harnessing — the same separation this topic tracks for [Zetta](../papers/2608.16590.md)'s runtime critics, but applied to the action interface itself rather than to critics layered around a fixed policy's outputs.
* [SoL-Pi](../papers/2609.20519.md) - narrows the optimization objective specifically to token/cost efficiency under a capability-preservation constraint, and elevates the search/held-out-validation separation this topic's other papers mostly assume implicitly into an explicit structural rule: capability tolerances and efficiency metrics are frozen and kept outside the optimizing agent's control before search, held-out EdgeBench results are structurally prevented from feeding back into search, and each of ~150 proposal directions runs as a disposable, isolated search lineage. Its Online Context Compact and ObservationPack mechanisms sit in the same externalize-and-gate-access-to-growing-context lineage this topic tracks through LongHorizon-Harness's state-role split and StateM's runbook, but operate one level lower (per-request token accounting and a retrievable-handle local archive rather than a redesigned state machine), while Evidence-Preserving Reducer's verified-receipt pattern (deterministic schema/hash/exit-status/quote checks, falling back to the untouched original on any verification failure) gives this topic's diagnose-write-validate lineage a concrete, auditable instance of delegated compression.
* [Harness VLA](../papers/2607.08448.md) - an embodied harness (like [Zetta](../papers/2608.16590.md) and [Show-Harness](../papers/2609.10522.md)) built around a frozen VLA, but structurally distinct from Zetta's online evolution: a one-time Exploratory Bootstrapping phase (single reference seed, `reset` enabled) produces a Task Specific Memory record that is then frozen and only re-grounded, not further updated, during a strict Deployment Evaluation phase — closer to a fixed planner-plus-primitives composition with a static per-task memory snapshot than to a continuously self-evolving harness. Against Show-Harness, the two papers freeze opposite halves of the same fixed-vocabulary pattern: Show-Harness freezes the model (a VLM acts zero-shot through a fixed action vocabulary) while Harness VLA freezes the policy (`vla_act`'s VLA backend) behind a swappable LLM planner. Its Task Specific Memory and Global Memory (named failure models: empty-grasp, false-success) apply [Recuris](../papers/2608.24876.md)'s structured-evidence-beats-bare-outcome principle at a narrower, single-task-recipe grain, without a comparable controlled ablation.
* [RRSI](../papers/2609.24972.md) - treats harness evolution as adaptive empirical optimization that overfits its evolve set, and regularizes the propose/select dynamics (annealed edit budget, full-history credit, pre-scoring leakage critic, noise-band floor, cost-per-gain rule, pruning) without restricting which components may change. In a same-budget comparison it is the only evolved harness to clear H₀ by more than a point out of distribution, at lower token cost.
* [ScienceBuddy](../papers/2609.17523.md) - restricts harness evolution to one bounded edit per proposal (one skill, instruction, or context setting) accepted only on strict paired-development improvement, then re-evaluates the inherited harness after each RL update of the task model, since a harness's value depends on the weights it runs with; +20 points validation accuracy at fixed weights on biomedical tasks.
* [Raven](../papers/2609.33439.md) - a "harness of harnesses": treats each model-harness pair, including Claude Code, Codex, Hermes Agent, and OpenClaw behind ACP or CLI adapters, as a unit that a host agent assigns through an admission-checked DAG, and evolves its own four specialist harnesses around a frozen model through Memory, Planning, Capability, and Action interfaces with gated screening (from HarnessBank); it reports same-backbone gains per specialist but no end-to-end test of the composed system.
* [Omni-IO Skills](../papers/2609.31847.md) - extends an unchanged host agent to any-to-any media production with a Skill layer, an MCP tool contract with swappable providers, dependency-checked wave-scheduled execution graphs, and an append-only asset registry; measured only against the bare agent (input support from about 40% to 100% on UniM-90).
* [Mid-Harness](../papers/2609.39982.md) - leaves the harness loop and the generator unchanged and adds compute in the model-call wrapper: each step samples several candidate actions and a verifier picks one before execution; with TMAX-9B on TerminalBench-Lite, pairwise self-verification lifts Pass@1 from 50.00% to 54.76%, a distilled verifier to 57.14%, and a GPT-5.6 Sol verifier to 68.03%.
* [ActiveSaddler](../papers/2610.00906.md) - keeps AutoSaddler's optimizer unchanged and adapts which training scenarios feed each update: LLM-induced failure-pattern arms, LLM learning-progress scores, and an LLM explore-or-repair controller; with gpt-5.5, +4.4 points on GAIA2 and +7.5 on Terminal-Bench 2.0 over a fixed scenario order, and +3.0 when wrapped around GEPA.
* [Context Language Models](../papers/2609.37725.md) - moves one harness responsibility, context management, out of the harness and into the model: the live context becomes a file the model edits with Bash, search tools are exposed as in-context skills rather than a fixed tool interface, and the paper reads existing harness compaction policies as "procedural memory" that can be steered by instruction, evolved as skills with a GEPA-style loop, or internalized with RL. Zero-shot it beats harness-defined and action-based compaction on BrowseComp-Plus and matches Codex-style summarization on Terminal-Bench 2.1 at lower compute; it also motivates a serving co-design (Suffix Cache Reuse) because in-the-middle context edits break prefix caching.
* [Recursive Self-Rewrite](../papers/2610.02826.md) - uses harnesses as discovery tools rather than optimization targets: one model under Terminus 2, StateM, and a verifier-outcome continuation variant solves 759 of 2,929 terminal tasks against 565 for the best single harness, and the same model then rewrites those successes into fresh Terminus 2 trajectories for SFT, so the trained model needs only the general harness at inference.
* [From Evidence to Action (SafeActBench)](../papers/2610.07753.md) - not a harness method but a controlled harness comparison on consequential tool use: five models each run in their family harness and in one shared Inspect ReAct harness on the same 570 cases, with case-paired intervals (DeepSeek +4.4 in its own harness, GLM −6.8 in ZCode, the rest indistinguishable from zero) and a failure decomposition showing a harness swap can trade early actions for no actions at a nearly unchanged failure rate.
* [Recursive Game Creator](../papers/2610.08621.md) - a task-specific harness for game development around a fixed model: Designer, Builder, a Player that writes and runs gameplay policies instead of acting from screenshots, and a Reviewer that keeps the better version on anonymized evidence; with GPT-6 Astra it passes 25 of 47 GameASG-Bench tasks against 9 for the same model under Codex CLI.
* [Learn2Play Bench](../papers/2610.08215.md) - a learning-from-experience benchmark with a same-backbone harness comparison: Claude Code lifts Claude Opus 5 from Max 74.5 to 81.8 and Codex lifts GPT-5.6-SOL from 57.0 to 74.3 over OpenCode, and OpenCode in turn beats six per-action self-evolving methods on the same backbone at lower token cost by batching actions and dropping repeated feedback.

# Synthesis

Harness Handbook asks where requested harness behavior lives in code so evolution can be localized and verified. MemoHarness searches six control surfaces and carries execution diagnoses forward as reusable adaptation evidence. SkillOpt-Lite's HarnessOpt instead lets a coding agent inspect raw trajectory files and patch harness code directly, with a human-approved round zero, constrained paths, smoke tests, validation, toggles, and rollback. AI Agents Do Not Fail Alone asks whether one major harness output—the context presented to the model—is clear, grounded, consistent, tool-aware, hardened, and efficient before behavior is tested. SearchOS demonstrates a concrete runtime harness that intercepts model and tool boundaries so evidence grounding, state updates, loop recovery, and budgets are not left to prompt compliance. LongHorizon-Harness targets a narrower, structural failure inside long-horizon execution itself: it splits state-holding, environment-changing, and state-verifying into three separate roles so that an agent's own completion claim can never directly become a persistent state record, and shows the resulting harness-layer change transfers across backbone models and interaction domains without any change to the wrapped backend's native loop. OpenHands sits earlier in this lineage as the foundational infrastructure layer itself — the event-stream protocol, sandboxed runtime, and skill-library discipline that later harness-modification papers in this topic take as their starting substrate, rather than a technique for evolving an existing harness. HarnessEval-W applies the harness paradigm to a different role entirely: not executing a task, but decomposing the *evaluation* of a task's output into sub-agent-verified evidence, extending "harness" from an execution-control concept to an evaluation-control one. StateM shares LongHorizon-Harness's concern with externalizing durable state outside a growing execution context, but generalizes it into a jointly agent-and-user-editable state machine and adds an explicit transfer-hierarchy study (which harness content survives a model swap, a provider swap, or a new task family) rather than a fixed role split. UI-Mate shows the same harness-scaling logic applied to GUI/computer-use agents specifically: a shared execution harness plus a workflow-conditioning layer (DemoCUA) that treats a demonstration as advisory prior rather than replayed script. Self-Improvements in Modern Agentic Systems generalizes these cases into prompt, memory, tool, and full-scaffold updates and argues that this explicit layer should host fast exploration before validated behavior is consolidated into slower model updates. EnvHarness moves the harness paradigm one layer further out again: instead of modifying the agent's own control surface, its EnvRigger designer diagnoses a frozen target policy's trajectories and writes wrapper components for the *environment* the policy trains or is evaluated in, while provably preserving that environment's original verifier — a diagnose-write-validate loop structurally close to MemoHarness's and SkillOpt-Lite's, applied one step outside the agent. Zetta pushes the same failure-diagnose-candidate-validate pattern down to action frequency in embodied control, explicitly separating three timescales (per-action runtime critics, rollout-level diagnosis, cross-rollout validation-gated promotion) so that a frozen VLA policy can be governed as physical execution unfolds rather than only reflected on afterward. AgentScope 1.0 sits underneath all of these as general-purpose infrastructure rather than a harness-modification technique: its non-invasive hook system, automated state persistence, and dynamic tool provisioning are the kind of substrate a harness-patching or environment-reshaping method could be implemented on top of, though the paper itself does not evaluate any such modification loop. OpenRath sits at a similar infrastructural altitude but answers a different, more foundational question than any harness-modification paper above: not how to diagnose and patch a harness, but what runtime object the harness's own state (transcripts, tool effects, memory events, branch lineage) should be represented as in the first place, so that later diagnosis, patching, and audit have something stable to operate on — its central architectural move (a Session value every component transforms rather than a private per-layer record) is a precondition this topic's diagnose-write-validate loops implicitly assume rather than a competing instance of one. Together they suggest a four-part loop: map behavior to authoritative implementation, modify the control layer using execution evidence, independently gate the candidate, then assess both the assembled context and downstream behavior — and the target of that loop can now be the agent's harness, its environment, or (in Zetta's case) an embodied control layer operating within a single rollout. The current evidence does not yet show that these representations and diagnostics remain accurate through long-running self-modification. Graph Engineering steps back from all of the single-agent diagnose-write-validate loops above and asks a different question: even a perfectly self-improving individual harness cannot schedule parallel interdependent subtasks, isolate specialized roles from confirmation bias, or maintain recoverable state across multiple agents, because those are structural limits of a single execution loop rather than harness-quality problems — its proposed answer (explicit task, coordination, and runtime-state graphs, with a "System Evolution" concept requiring validated, rollback-able persistent structural change rather than one-off adaptation) generalizes this topic's own harness-level diagnose-write-validate pattern up one level, from patching one agent's control surface to patching an entire multi-agent system's organization. Prime Agent names the state hierarchy this topic's papers have each been implicitly carving up: L0 (weights, changed by fine-tuning), L1 (active context, changed by compaction), L2 (persistent REPL and recursive subagent sessions, changed by the model's own create/retain/summarize/delete decisions), and L3 (disk-backed history and versioned harness state, changed by refinement) — Recuris's Skill Memory and StateM's runbook both live at L3 in this framing, while LongHorizon-Harness's externalized state and Zetta's runtime critics operate closer to L2. Recuris sharpens this topic's diagnose-write-validate loop into a measured claim rather than an assumed one: it shows a structured execution trace linking verified state, invoked skill, action, and outcome localizes an injected component fault far more accurately (64.8%) than the raw trajectory (37.0%) or the task outcome alone (13.0%, below a constant-answer floor) — direct evidence for why this topic's harness-patching papers need structured evidence, not just failure signal, to target a repair correctly. Apodex 1.1 shows the same externalized-state pattern this topic tracks for single-agent execution (LongHorizon-Harness's role split, StateM's runbook) applied to multi-agent coordination: its Task Board lives outside the LLM's message history and is periodically re-injected so the plan survives compaction, functioning as both external memory and a runtime finalization gate rather than a presentation-only checklist. ASI-Bench sits outside this topic's diagnose-write-validate lineage entirely — it evaluates rather than modifies a harness — but its own "Harnesses Shape Model's Capability" result is independent, cross-domain evidence for exactly the premise the rest of this topic assumes: that a fixed backbone model's demonstrated capability is not solely a property of the model, since the same model scored under two different harnesses on the same 60 scientific-research tasks can differ by several points, though the effect size itself varies by model rather than holding uniformly. AutoSaddler sharpens this topic's diagnose-write-validate loop with a controlled ablation the loop itself usually lacks: removing structured, typed patches collapses 91.5% of proposals to textual Steering edits (versus only 4% capability-changing types under the full method), even though capability patches have higher acceptance rates and far fewer regressions once proposed — direct evidence that a patch taxonomy changes *what kind* of fix gets proposed, not only how it is validated afterward; its EvoDAG also generalizes MemoHarness's and SkillOpt's single-lineage adaptation into an explicitly branching optimization history that later runs can recombine from. AutoDev sits chronologically before every other paper in this topic (March 2024, roughly four months ahead of OpenHands) and is best read as this lineage's common ancestor rather than a peer instance of the diagnose-write-validate loop: its Tools Library, Docker sandbox, and YAML permission model are the fixed, hand-authored version of the same sandboxed-typed-permissioned-execution pattern that AutoSaddler, EnvHarness, and Zetta each later treat as an automatically patchable surface rather than a one-time design decision. JIT-Agent shifts this topic's unit of intervention once more: rather than diagnosing and patching one running harness in place (AutoSaddler, Recuris, SkillOpt-Lite) or exposing more addressable state within one persistent harness for the model to revise (Prime Agent), it trains a separate, transferable model whose job is harness *construction* itself — formalizing the harness as a fixed four-module protocol so 13 existing named designs become interchangeable points in one space (HarnessFactory), then learning to synthesize, repair, and archive-gate-evolve new instances of that protocol per task for arbitrary frozen backbones, most clearly answering this topic's own open question about how harness-design skill can be made trainable and transferable rather than remaining a one-off engineering artifact. Omni Interaction Agent (Gander) applies this topic's externalized-coordination-state pattern (LongHorizon-Harness's role split, StateM's runbook, Apodex 1.1's Task Board) to a boundary none of those papers cross: the harness sits between a realtime, latency-bound interaction model and a completely separate, training-free backend agent, so its lean-vs-coordinator control-plane split is doing double duty as both a latency lever (skip the extra model call when routing is unambiguous) and a harness-modification boundary (the coordinator can only emit a declarative plan the Gateway validates, never execute directly) — a two-tier harness design this topic's single-agent diagnose-write-validate papers have not needed, since none of them couples a sub-second interaction budget to a long-horizon delegated execution tier. Show-Harness sits apart from every diagnose-write-validate paper above in a different way: it does not modify, patch, or evolve an existing harness or control surface at all, but designs the interface a harness exposes to the model from scratch, and its own ablation (Sec. 5.4.4 of that paper) is direct evidence for why this topic's other harnesses bother externalizing state, typing tool calls, and constraining action vocabularies in the first place — an unconstrained action space with no explicit grounding conventions succeeds in only 1/20 episodes even for a frontier VLM, while adding explicit conventions (with or without semantically meaningful names) restores most of the lost performance, suggesting the "harness" layer's value is partly just making the action interface legible enough for a model to reason over reliably, independent of any diagnosis or patching mechanism.

Raven and Omni-IO Skills move the unit of harness engineering in two directions. Raven moves it up a level: whole model-harness pairs, its own specialists and third-party agents behind adapters, become components that a host composes through typed graphs. This is the wrapping move LongHorizon-Harness makes for one long task, applied instead to dividing work across specialists. Omni-IO Skills moves it outward: the host agent is untouched, and the harness adds output modalities through Skills, a provider-agnostic tool contract, and a persistent asset registry. Both keep the model fixed, and neither isolates its own components: Raven's composed system is never compared end to end with a strong single agent, and Omni-IO is compared only with the bare agent.

Mid-Harness marks a boundary case for this topic. Most papers here change the harness itself (tools, state, control flow) or search over harness code; Mid-Harness changes nothing in the harness loop and inserts its intervention into the model-call wrapper, where candidate actions are sampled and compared before the harness executes one. That makes it compatible with any of the harnesses above, and its transfer runs across two harnesses (Vanillux2 and Terminus-2). Its finding that the verifier, not the number of candidates, sets the gain parallels this topic's results that the same model can score very differently depending on the layer around it.

ActiveSaddler adds an axis the diagnose-write-validate loops above leave fixed: which training scenarios produce the evidence for the next patch. Most optimizers here (AutoSaddler, Meta-Harness, GEPA) fix their mini-batches before optimization begins. ActiveSaddler induces failure-pattern arms from diagnosed failures and spends rollouts on weaknesses that are still active. Its ablations show category-level and scenario-level arms both do worse, which matches Recuris's finding that a typed, component-level failure description is a better repair target than an outcome. Its own list of discovered arms also shows a risk this topic has not measured: on GAIA2 many arms describe matching the grader's output format, so an optimizer that targets persistent failures may also learn the evaluator's conventions.

Recursive Self-Rewrite takes the opposite direction from Context Language Models' proposal to absorb harness policies into the model step by step: it keeps several fixed harnesses, uses each to find solutions the others miss, and moves the *results* into weights by re-executing them under one general harness. Its base-model table is independent evidence for this topic's premise that capability depends on the harness: on Terminal-Bench Hard the same Qwen-3.8-27B scores 33.0% under Terminus 2, 46.0% under StateM, and 66.0% under the continuation variant. The trained model under Terminus 2 does not reach the best harness on that benchmark (63% pass@3), so internalization recovered part of the harness gain, not all of it.

SafeActBench adds the most careful measurement of harness effects in this topic so far, and a caution about reading them. Pairing each model's family harness with one shared ReAct harness on identical cases, with three reruns (standard deviations 0.2-0.7 points) and bootstrap intervals, it finds only two of five effects distinguishable from zero, and in opposite directions. Its failure decomposition shows why aggregate scores mislead: GLM under Inspect instead of ZCode cuts early actions on single-action tasks from 0.66 to 0.29 but raises no-action failures from 0.01 to 0.37, leaving the failure rate nearly unchanged. Its supplementary runtime (SCGR) also tests a harness-level fix for the failures it finds, a persistent evidence ledger plus structural checks before submission, and the result is mixed (+11.6 points for Qwen, −9.1 for Claude), so adding evidence structure in the harness does not reliably help across models.

Recursive Game Creator is another large same-model harness effect: GPT-6 Astra (high) goes from 9 to 25 of 47 GameASG-Bench tasks when wrapped in its four-role loop instead of Codex CLI. Unlike SafeActBench's comparison, this one is not budget-matched (three design-build-play-review rounds against one pass), the baseline rows are copied from the benchmark paper, and no ablation removes a component, so the gain cannot yet be attributed to the harness design rather than extra rounds. Its distinctive move is moving testing into code the agent writes: the Player builds reusable gameplay policies that run without a model call per action, which turns playtesting from an expensive step into a cheap, repeatable one, a separation of policy construction from execution that the paper traces to Code as Policies and Voyager.

Learn2Play Bench measures the harness effect on *learning across episodes*, not only on single-task success, and finds it in both directions SafeActBench separates: vendor harnesses raise every metric for their own model (Learning Gain +21.3 to +27.1 for Opus 5 under Claude Code, +14.5 to +22.2 for GPT-5.6-SOL under Codex), and the general OpenCode harness beats research self-evolving methods on the same backbone. Its cost table points to a concrete mechanism for the second effect: OpenCode makes about 8 model calls per episode for Kimi K3 against 27 for the raw-history Memory method, because it executes several actions per response and strips repeated feedback, and it scores higher at roughly half the estimated cost. The first effect is attributed to model-harness co-training on the authority of vendor statements; like Recursive Game Creator's, it is not isolated by an ablation, and it rests on three trials per configuration.

# Open Questions

* How should agent-visible behavior be mapped to code when runtime dispatch, generated code, or external services defeat static analysis?
* Which representations improve final patch correctness, not only localization and planning quality?
* How can a harness map remain synchronized through repeated edits without making stale prose an accidental source of truth?
* What evaluation gates are necessary before agents may modify their own harnesses?
* How should harness maintainability, regression risk, token cost, and task capability be optimized together?
* Can preflight context assessment predict harness regressions on unseen tasks without sharing the biases of the behavioral judge?
* Which parts of adaptive harness performance come from global search, case-level experience, distilled patterns, and test-time specialization?
* How should a harness reject stale, misleading, or adversarially similar experience before adapting a new case?
* Which scaffold updates are safe to automate, and which require an independent or human acceptance boundary?
* Which execution invariants should middleware enforce automatically, and which interventions risk suppressing productive but unusual agent behavior?
* Can repeated locally validated harness patches avoid long-term complexity growth, test overfitting, and erosion of the human approval boundary?
* When a harness role structure (e.g. manager/executor/auditor) improves reliability, how much of the token-cost increase is inherent to independent verification versus recoverable through cheaper audit strategies?
* OpenRath's own evidence is scoped to deterministic, locally-verifiable claims (lineage export, local sandbox execution, focused tests) with benchmark-superiority, memory-quality, and merge-quality claims explicitly deferred — does representing runtime state as one first-class Session value measurably improve this topic's harness-diagnosis and patch-correctness questions once that follow-on evaluation exists, or does it mainly help audit and review without changing what a diagnose-write-validate loop can discover?
* Graph Engineering argues (its own Section 6.1) that end-task success alone cannot distinguish genuine system-level organizational improvement from a stronger model or more compute — does the same critique apply to this topic's single-agent harness-optimization papers, several of which report gains without a controlled ablation isolating the harness change from a concurrent model or context-budget change?
* Prime Agent's own Factorio case study shows its Continual Harness refinement loop persisting a discovered specification-gaming exploit as a reusable skill with no validation gate stopping it — should this topic's held-out validation gates (SkillOpt, GenericAgent) be treated as a required part of any online L2/L3 state-revision mechanism, not just an optional strengthening, and would such a gate have caught this specific case?
* Recuris finds that which memory component is worth repairing is domain-dependent and not fixed at design time (write-review is critical on one τ²-Bench domain and inert on the other, with the pattern exactly reversing for a different mechanism) — do this topic's other harness-patching papers, which mostly report one dominant repair target per system, actually have a similarly domain-dependent critical component that a narrower evaluation has not yet surfaced?
* RRSI shows that four same-budget harness-evolution methods lose most of their evolve-set gain out of distribution, and two fall below the starting harness. Which of its regularizers — leakage critic, noise-band floor, cost-per-gain rule, pruning — carries that transfer, and does a critic from a different model family than the proposer reject fewer genuine improvements?
* Raven's theory says composing harnesses adds coverage only when every individual agent falls below the reliability target while planning and per-node errors stay small. Can those error terms be measured on real harnesses, and would one agent given the union of all specialists' tools close most of the gap, as the paper's own parity example concedes it could?
* Mid-Harness adds verification at the model-call boundary without touching the harness, and its gains differ by task domain (+20.5 points on software-engineering tasks but −10.0 on scientific computing at 27B). Would a harness that exposes action reversibility or environment state to the verifier close the gap on the state-dependent later steps where its verifier is weakest?
* ActiveSaddler's curriculum steers optimization toward whatever keeps failing, and several of its GAIA2 arms are grader-format conventions. How should a harness optimizer tell task-behavior weaknesses from evaluator-specific ones, and how much of the reported held-out gain survives when patches from format-only arms are removed?
* Context Language Models propose distilling harness context policies into model behavior and eventually into weights, framing harnesses as procedural memory the model can absorb. Which of this topic's harness components (compaction, state externalization, skill routing, verification) are context transformations a model could take over, which depend on side effects or isolation the model should not control, and does moving a policy into the model make it harder to audit than the same policy in harness code?
* Recursive Self-Rewrite shows harnesses solve partly disjoint task sets for one model. Is that complementarity stable enough to plan around (route tasks to harnesses by domain), or does it mostly reflect sampling noise that more rollouts under one harness would also cover?
* SafeActBench finds that single-action execution is nearly always correct once the required evidence has been read, and that most failures are premature actions or early stops. Would a harness gate that blocks a consequential call until the case's required reads are present remove most premature actions, and why did offering the model an evidence ledger and checks (SCGR-Select) help one model family and hurt another?
* Recursive Game Creator's Player tests games through code-written policies rather than per-action model calls. When an agent can write its own test drivers against a programmatic interface, how much of a task-specific harness's gain comes from that cheaper verification, and does it carry over to domains (web apps, data pipelines) where the interface exposes less of the state a user sees?
* Learn2Play finds vendor harnesses beat a general harness on their own model's learning across episodes. How much of that comes from model-harness co-training and how much from transferable features (context handling, action batching, tool-assisted calculation) that could be added to an open harness?
