# Scope

This topic tracks papers about AI systems used to plan, run, and revise scientific experiments over repeated cycles.

# Papers

* [AutoScientists](../papers/2605.28655.md) - self-organizing agent teams for long-running computational scientific experimentation.
* [Arbor](../papers/2606.11926.md) - hypothesis-tree refinement for autonomous optimization of research artifacts.
* [EurekAgent](../papers/2606.13662.md) - environment engineering for metric-driven autonomous scientific discovery.
* [SkillFoundry](../papers/2604.03964.md) - mines scientific resources into validated agent skills and designs task-specific skills on demand for genomics workflows (cell type annotation, scDRS).
* [SWE-bench Science](../papers/2608.19799.md) - a 119-task, 98-repository benchmark for repairing scientific software repositories under domain contracts (units, invariants, formats); even the best coding agent scores under 50% pass@1, with a paired ablation showing scientific guidance is not uniformly helpful.
* [ASI-Bench](../papers/2608.17271.md) - a 60-task benchmark spanning 11 scientific domains (mathematics, physics, chemistry, biology, astronomy, materials science, earth science, medicine/biostatistics, computer science, robotics, electrical engineering) that measures autonomous scientific research capability directly by progressively withdrawing human methodological guidance within the same matched project, rather than proposing a discovery system itself.
* [EvoScientist](../papers/2603.08127.md) - a three-agent (Researcher/Engineer/Evolution-Manager) end-to-end AI-scientist framework that distills each task's outcomes into two persistent memories (ideation, experimentation) rather than adapting only within a single run; beats 7 open-source and commercial baselines on idea quality, lifts execution success rate 34.39%→44.56%, and had all six of its autonomously generated end-to-end manuscripts accepted at a real peer-reviewed venue (ICAIS 2025), including a Best Paper Award.
* [Lean Pool](../papers/2609.25199.md) - agents maintain scientific *infrastructure* rather than run experiments: scheduled jobs discover and import Lean formalizations, repair projects after each Lean/Mathlib upgrade (95 of 97 repair jobs succeeded on the stable-Lean migration), shorten proofs, and review statements, keeping 211 projects in one continuously building archive intended as a formal counterpart to arXiv.
* [ScienceBuddy](../papers/2609.17523.md) - a released biomedical research workspace (224 tools) whose researcher collaborations are packaged as executable Harbor tasks with task-specific rubrics, which then drive both harness edits and RL of the deployed agent.
* [Self-Evolving Coding Agents (HexaAnything)](../papers/2609.35432.md) - PhyBench, a simulated Isaac Sim laboratory where an embodied coding agent must design and physically run an experiment (spring constant, g from three pendulums, coupled-oscillator normal modes) and submit an estimate backed by recorded measurements; three frontier models keep mean relative error below 5% on every task, while Qwen3.8-Max produces valid results in at most half its runs.
* [AutoSciBench](../papers/2610.05140.md) - generates and refines data-analysis tasks for scientific agents in computational biology, materials science, and clinical imaging (question, data files, exact-match answer), revising each task's plan until solver trajectories show no shortcut and all trials fail; ten solvers that score 92.7-97.7% on the MatTools seed spread from 21.3% to 90.0% on the Opus-4.8-generated set.

# Synthesis

AutoScientists emphasizes decentralized team organization for sustained experimentation, Arbor emphasizes persistent hypothesis management and held-out admission, while EurekAgent emphasizes the surrounding execution environment: hidden evaluators, durable artifacts, budget controls, and supervision interfaces. All three treat scientific discovery as iterative agent work, but they put the main design pressure on different layers. SWE-bench Science shifts the topic's object from *conducting* science to *maintaining the software science depends on*: rather than an agent proposing or running experiments, the agent repairs existing scientific-computing repositories while preserving domain contracts (units, coordinate systems, numerical invariants) that no general-purpose coding benchmark exposes — a complementary failure mode to the discovery-oriented papers above, since a repair that silently breaks a scientific contract could corrupt the evidence an AutoScientists- or EurekAgent-style discovery loop would later rely on. ASI-Bench occupies a fifth, evaluation-only role distinct from all four system papers above: rather than proposing a discovery architecture, it cross-domain-tests whatever architecture an Agent×Model pairing uses, and its finding that current systems' average score collapses from 50.91 to 26.62 as guidance is withdrawn — with the collapse concentrated in turning a named method into a working procedure, not in choosing the method — gives this topic's system-building papers a concrete, externally validated failure point (operationalization, not method selection) that none of AutoScientists, Arbor, or EurekAgent currently reports isolating in their own evaluations. EvoScientist returns this topic to system-building but answers the "how does the system improve" question differently from AutoScientists (team organization), Arbor (hypothesis-tree management), or EnvHarness/Zetta-style environment evolution elsewhere in this wiki: it adds a dedicated Evolution Manager Agent whose sole job is converting each task's ideation and execution outcomes into two typed, cross-task-retrievable memories, so the researcher and engineer roles improve not by a richer within-run search (as Arbor's held-out admission or AutoScientists' team reorganization do) but by starting each new task with distilled evidence about which directions already failed and which execution strategies already worked. Its ablation isolates this contribution cleanly — removing all idea evolution costs 45.83 average points on novelty/feasibility pairwise comparisons while leaving relevance/clarity comparatively untouched — giving this topic a concrete data point on how much of an AI-scientist system's benefit is attributable to cross-task memory specifically, as opposed to within-run search machinery (tree search, tournament ranking) that EvoScientist also uses but does not ablate as a group. Unlike ASI-Bench's cross-domain evaluation-only stance, EvoScientist's end-to-end validation is domain-narrow (computational, code-executable research only, six papers) but carries genuine external stakes — real peer review, real acceptance decisions — that neither AutoScientists, Arbor, nor EurekAgent's own evaluations report.

HexaAnything's PhyBench moves this topic from computational experiments to *physical* ones, still in simulation. The agent must operate apparatus with a robot arm, read instruments from camera images, record each measurement with the condition that produced it, and fit a model in code, so a manipulation slip becomes a measurement error rather than a failed step. Its tasks have known reference values hidden from the agent, which makes accuracy checkable in a way open-ended discovery systems cannot offer, but the experiments are textbook physics with prescribed apparatus rather than open research questions.

AutoSciBench takes the evaluation role ASI-Bench and SWE-bench Science play, but automates building the evaluation. Its tasks share PhyBench's hidden-reference design (an exact answer the agent must recover from data), and its target failure is interpretation rather than ASI-Bench's operationalization: refinement rewrites the data so that a direct reading of one intermediate output no longer gives the answer, for example by adding sequencing errors to UMI barcodes, so the agent must check intermediate results against the raw data. Its weak point is the one this topic's discovery systems also face, trust in the reference itself: answers are computed by the generating model, often on simulated data, and no domain expert checks them.

# Open Questions

* How should failed experiments be captured so future agents avoid repeating them?
* Which parts of scientific experimentation map onto long-running literature review workflows?
* How should compute budgets shape agent critique and proposal acceptance?
* Which environment boundaries are necessary before autonomous discovery results should be trusted?
* How should hypothesis trees connect to project memory, paper skeletons, and durable experiment logs?
* How should autonomous-discovery agents (AutoScientists, Arbor, EurekAgent) verify that the scientific software they depend on has not silently violated a domain contract SWE-bench Science-style failure modes would catch?
* ASI-Bench's main results explicitly exclude external tool access — would AutoScientists', Arbor's, or EurekAgent's own designs (each of which grants agents tool and environment access as a core mechanism) close a meaningful share of the B1→B2 operationalization gap ASI-Bench measures, or does that gap persist even with tools?
* AutoSciBench generates scientific-analysis tasks whose reference answers come from the generating model's own code. Could the discovery systems in this topic (AutoScientists, Arbor, EurekAgent) be evaluated on such generated tasks without inheriting the generator's errors, and what independent check (expert review, a second analysis pipeline, real rather than simulated data) would a generated scientific task need before its answer counts as ground truth?
* EvoScientist's evolution memory is driven entirely by outcome-level comparisons (win/lose judgments, execution success/failure) rather than any mechanism for abstracting *why* a direction succeeded or failed into a generalizable claim — would grounding its ideation- and experimentation-memory updates in ASI-Bench-style progressive-guidance-withdrawal probes, or in Arbor's held-out hypothesis admission criteria, produce more transferable distilled knowledge than EvoScientist's own LLM-judged feasibility summaries?
