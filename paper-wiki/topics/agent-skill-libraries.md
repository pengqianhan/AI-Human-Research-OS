# Scope

This topic tracks papers that treat agent capabilities as reusable, validated skill packages and that build or maintain libraries of such skills — including how skills are mined from external resources, represented (scope, inputs/outputs, steps, environment, provenance, tests), validated, and kept novel and non-redundant as the library grows.

# Papers

* [SkillFoundry](../papers/2604.03964.md) - mines heterogeneous scientific resources into validated, executable skill packages and grows the library through closed-loop expand/repair/merge/prune.
* [OpenSkill](../papers/2606.06741.md) - builds transferable skills and self-built verification anchors from open-world resources without target-task supervision.
* [ResearchStudio-Idea](../papers/2607.04439.md) - packages literature search, claim-level prior-art checking, and outcome-grounded idea generation as interoperable research-agent skills.
* [SkillOpt-Lite](../papers/2607.03451.md) - optimizes existing skill files from execution trajectories using cross-task consensus, minimal patches, and a disjoint validation gate.
* [COLLEAGUE.SKILL](../papers/2605.31264.md) - distills heterogeneous human traces (not agent trajectories) into versioned, correctable, capability/behavior-split skill packages via a colleague/celebrity/relationship preset pipeline.
* [SkillOpt](../papers/2605.23904.md) - a deep-learning-style text-space optimizer (rollout/reflection batches, bounded textual learning rate, held-out validation gate, rejected-edit buffer, epoch-wise slow/meta update) that trains one compact skill document per domain, best-or-tied on 52 of 52 evaluated (model, benchmark, harness) cells.
* [Repo-To-Skill (DisCo)](../papers/2609.02749.md) - formalizes "operational knowledge" as a third component alongside model and harness, then distills it from 1,000 ML repositories and 153 papers into the 5,000+-skill AREX-Skill Library, improving a fixed GPT-5.5 Codex agent by 134.3% on MLE-bench, 34.4% on PaperBench, 9.2% on FrontierCS, and 14.0% on PassNet under matched with/without-skills ablations.
* [Code2Skill](../papers/2609.05571.md) - mines atomic/composite/recurring-pattern skill records from 19,769 GitHub repositories, verifying each through source-body-blind LLM reconstruction and source-aware comparison rather than test-based checks, producing the 1,006,822-record CodeSkillBank; improves 57 of 72 protocol-matched agent evaluations by 11.7% macro-average and outperforms trajectory-derived skill banks (Trace2Skill, ExpeL, SkillRL-Bank) on all seven shared benchmarks under one common retrieval interface.
* [Raven](../papers/2609.33439.md) - Skill Forge routes each task over a curated catalog (SkillCorpus, built from a crawl of about 821,000 skill files), local skills, and memory-derived skills, injecting at most two; in the reused SkillCorpus experiments retrieved skills help in all 12 cell-benchmark comparisons, and with identical selections Raven's harness gains more than OpenClaw's.
* [Omni-IO Skills](../papers/2609.31847.md) - a 27-Skill library organized by granularity rather than modality (19 atomic operations, 2 expert deliverable workflows, 6 application scenarios), each Skill declaring applicability, inputs, procedure, outputs, and expansion links so a scenario request expands recursively into an executable graph.
* [RASO](../papers/2609.38024.md) - treats the public GitSkills corpus as a prior for optimizing one skill: section-level BM25 retrieval plus Cross-Harness Adaptation rewrites retrieved procedure into the target harness's vocabulary, both to initialize a skill with zero rollouts and to repair diagnosed failures during updates; unadapted retrieval (SkillRouter) is often worse than no skill, and RASO beats TextGrad, GEPA, SkillOpt, and WikiSkill on four benchmarks with two models.
* [X-Tree](../papers/2609.32993.md) - the topic's counter-position: reusable sub-procedures are mined from trajectories by counting (recurrence, length, success), never written by an LLM, and consumed by training (offline RL instances, an RLVR bonus, an OPSD privileged context) rather than retrieved at inference; the same tree also beats four LLM-written in-context skill banks on MiniWoB++.
* [EviSkill](../papers/2610.05030.md) - improves one skill document per environment with edits that each carry replayable evidence (the exact trajectory step ranges that justify them), re-executes those ranges under the edited skill to accept, repair, or reject each edit, and keeps replay-supported edits from validation-rejected revisions in a provisional ledger; best in 14 of 18 settings against Trace2Skill, EvoSkill, SkillGrad, and SkillOpt on ALFWorld, AppWorld, and ScienceWorld.

# Synthesis

These papers treat skills as durable, reusable artifacts rather than one-off prompts. SkillFoundry emphasizes mining and maintaining a domain-scoped *library* from heterogeneous scientific artifacts with executability and novelty checks. OpenSkill emphasizes constructing skills and their verifiers from scratch under a no-supervision constraint. ResearchStudio-Idea emphasizes composing specialized skills into an evidence-gated research workflow whose pattern cards support both generation and audit. SkillOpt-Lite addresses a different lifecycle stage: improving an existing skill from raw task trajectories while resisting one-example fixes through consensus and independent validation. COLLEAGUE.SKILL applies the same "durable, versioned, correctable package" framing to a different input class entirely — human traces about a person or role, rather than an agent's own execution history — and adds an explicit correction-and-rollback lifecycle over natural-language feedback. SkillOpt pushes the "improve an existing skill" stage furthest toward a literal training loop: it names its edit budget a textual learning rate with schedules, its validation split a held-out gate, its failed proposals a negative-feedback buffer, and its cross-epoch consolidation a slow/meta update — and demonstrates the resulting artifact transfers across models, harnesses, and nearby benchmarks. Repo-To-Skill (DisCo) targets a different lifecycle stage again, and at a different scale: rather than improving one existing skill document (SkillOpt, SkillOpt-Lite) or mining a domain-scoped set from scientific artifacts (SkillFoundry), it anchors a single four-stage distillation pipeline (scope/ground/construct/verify) on 1,000 versioned software repositories plus 153 papers, producing 5,000+ skills organized by an LLM-induced taxonomy, and is the first paper in this topic to isolate skill contribution via a matched with/without-skills ablation across four independent, pre-existing third-party benchmarks rather than a custom in-house one. Code2Skill mines the same general substrate as Repo-To-Skill (GitHub repositories) but at nearly 20x the repository count (19,769 vs. 1,000) and without the paper corpus, and answers this topic's provenance/trustworthiness question with a distinct verification mechanism: rather than a scope/ground/construct/verify pipeline, it uses source-body-blind reconstruction — an LLM regenerates the implementation from the skill record alone, and a judge compares the reconstruction against the real source — as a scalable substitute for test-based verification when executable tests are unavailable. It is also the first paper in this topic to run a direct, shared-interface comparison against trajectory-derived skill banks (Trace2Skill, ExpeL, SkillRL-Bank) rather than only against a no-skill baseline, giving the topic's open question about mining vs. training a skill source its first controlled substrate-vs-substrate data point: under an identical retrieval interface, Code2Skill beats even an oracle that takes each trajectory-derived baseline's best per-benchmark result by 9.5 points on average. Together they foreground explicit contracts, provenance, verification, abstention, and maintenance as properties of trustworthy skill systems.

Raven and Omni-IO Skills add evidence on two later lifecycle stages, selection and composition. Raven's evidence, reused from SkillCorpus, concerns selection: curation and a trained retriever each matter (replacing either drops SkillsBench Pass@1 from 22.6% to 13.8-14.9%), gains grow with how well the catalog covers a task, and the same skills help one harness more than another, so a skill's value depends on the harness that executes it. Omni-IO Skills concerns composition: each skill declares how it expands into lower-level skills, so a scenario request becomes an execution graph rather than one large prompt, a concrete answer to this topic's question of when narrow skills should be composed into a workflow.
RASO and X-Tree pull the topic in opposite directions on where a skill should live. RASO is the first paper here to treat a public skill corpus as the *input* to skill optimization rather than its output, and its SkillRouter result sharpens Raven's selection evidence: retrieval without adaptation can fall below no skill, and the adaptation step (strip domain nouns, drop procedures without a counterpart in the target harness, keep tool claims only when the harness description corroborates them) is what makes a foreign skill usable. That is a concrete answer to this topic's portability question, though it works per target harness rather than by making the package itself portable. X-Tree questions the premise shared by every other paper here, that skills are text an LLM writes and an agent reads: it recovers the hierarchy from the trajectories themselves with no LLM calls and trains it into the weights, and reports that LLM-written banks from small models can hurt in context while the counted tree does not. The two are complementary in evidence as well: RASO's gains are largest for a frontier backbone on document and spreadsheet tasks, X-Tree's for small open models on web and text-game environments.

EviSkill adds provenance at the level of a single edit, which this topic has so far tracked for whole skills (SkillFoundry's validated packages, Code2Skill's reconstruction check). Each line it adds to a skill keeps a pointer to the trajectory steps that motivated it, and the line is kept only if re-running those steps under the edited skill changes the behavior as intended. Its results also put a number on a risk the "improve an existing skill" papers mostly report as a footnote: on ScienceWorld with GPT-5.5, three of four evolution baselines end below the unevolved initial skill (54.50-67.30 against 76.78). Its own margins on AppWorld are within one or two test tasks, and its optimizer is GPT-5.5 even for 4B and 9B action models, so how much of the gain comes from replay rather than a stronger editor is not yet isolated.

# Open Questions

* What metadata makes a skill package portable across agents, models, and environments?
* How should a skill library detect and prune redundant or stale skills as it grows?
* How well do internal or self-built validation signals predict real downstream task success?
* How should mined skill libraries connect to a research OS's own skills hub and its skill contract?
* When should several narrow skills be composed into a gated workflow instead of merged into one large skill?
* How should a library retain failed optimization attempts for audit without letting a growing rejected-edit buffer distort future updates?
* Does a deep-learning training analogy (learning rate, schedule, validation gate, momentum) generalize to optimizing skill *libraries*, not just a single skill document?
* Repo-To-Skill distills skills ahead of time from declarative sources (repos, papers) while SkillOpt trains one skill document from execution trajectories after the fact — would seeding a SkillOpt-style optimization loop from an AREX-Skill-constructed starting skill compose the two approaches' gains, or does either method already capture most of what the other would add?
* Code2Skill's reconstruction-based verification is explicitly framed as a substitute for test-based verification, not validated against it on a shared sample — how often would reconstruction-based acceptance agree or disagree with an executable-test oracle on the same code units, and would combining the two (Code2Skill's scale with SkillFoundry- or DisCo-style executable verification where tests exist) change which records get accepted?
* With identical skill selections, Raven gains more than OpenClaw; on tasks Raven solves and OpenClaw fails, OpenClaw often stops after reasoning, leaves generated scripts unexecuted, or never runs the verifier. Should a skill package declare the execution behaviors it assumes (run, verify, fix) so a library can predict which harnesses will benefit from it?
* RASO adapts a retrieved skill to one target harness at optimization time, while this topic's portability question asks what metadata would let one package serve many harnesses. Could the adaptation rules (domain-noun removal, harness-corroborated tool claims) be run once per harness and stored as variants inside the skill package, and would a package carrying its own harness description make Cross-Harness Adaptation unnecessary?
* X-Tree's counted hierarchy beats LLM-written skill banks as in-context advice on MiniWoB++ and matches them as OPSD context, at zero LLM cost. For which skill types does an LLM author still add value over counting: procedures that recur rarely, that need explanation to be followed, or that span tools whose actions cannot be canonicalized to a shared alphabet?
* EviSkill stores, with each skill edit, the trajectory step ranges that justified it. Should a skill package carry that per-line provenance after optimization ends, so a maintainer can re-run the motivating case before deleting or rewriting a line, and does replay acceptance on those motivating steps predict whether the line helps on tasks that did not produce it?
