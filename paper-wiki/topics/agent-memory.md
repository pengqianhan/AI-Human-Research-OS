# Scope

This topic tracks papers about persistent memory systems for LLM agents: how salient information is extracted from ongoing interaction, consolidated against existing memory (added, updated, or invalidated), structured (flat text vs. relational graph), and retrieved at query time, and the accuracy/cost trade-offs that follow from those design choices.

# Papers

* [Zep](../papers/2501.13956.md) - Graphiti, a bi-temporal (event-time plus transaction-time) dynamic knowledge graph with episode/semantic-entity/community subgraphs and a three-method search-rerank-construct retrieval pipeline; reports state-of-the-art DMR accuracy over MemGPT and up to 18.5% accuracy gains with ~90% lower latency on LongMemEval.
* [Mem0](../papers/2504.19413.md) - an incremental extraction/update pipeline where an LLM tool-call decides ADD/UPDATE/DELETE/NOOP per candidate fact against top-k similar memories, plus a graph-structured variant (Mem0^g) for relational and temporal queries; beats a six-category baseline sweep (including Zep) on LOCOMO's LLM-as-judge metric while cutting p95 latency by 91% versus full-context.
* [MemOS](../papers/2507.03724.md) - an OS-inspired architecture that unifies plaintext, activation, and parameter memory into a schedulable MemCube unit with lifecycle states and governance metadata, outperforming Mem0, Zep, MIRIX, Memobase, MemU, and Supermemory across LoCoMo, LongMemEval, PreFEval, and PersonaMem on a shared GPT-4o-mini backbone.
* [EverMemOS](../papers/2601.02163.md) - an engram-inspired three-phase lifecycle (episodic trace formation, semantic consolidation into MemScenes, sufficiency-checked reconstructive retrieval) built around a MemCell primitive with time-bounded Foresight, beating Zep on LoCoMo (+7.0-9.2% relative) and MemOS on LongMemEval (+6.7% relative).
* [Recuris](../papers/2608.24876.md) - couples experiential skill memory with a checker-verified working state that gates *when* and *which* skill is invoked, then uses the resulting structured trace to localize cross-task memory failures to one of four components (skills, working-memory spec, invocation policy, checkers) and apply validation-gated, component-scoped patches; improves 35 of 37 model-benchmark pairs across ten models and four long-horizon benchmarks.
* [VoiceMem](../papers/2608.26005.md) - a streaming "dual-brain" memory for real-time voice agents: a schema/entity-indexed left brain for facts sits above an interchangeable backend (Mem0, Zep, or LangMem), a right brain of independent/cross-entity nodes maintains persona and affect as its own structure rather than a retrieval re-weighting, and a four-stage pipeline hides the entire retrieval (134ms) inside a standard VAD's turn-taking window at a top-5 budget.

# Synthesis

Zep is the earliest system in this topic (January 2025) and the one all three later papers benchmark against. It answers "what is the unit of memory management" with a knowledge-graph edge carrying two independent timelines — a real-world validity interval and a transactional record-keeping interval — so a fact can be superseded without deleting its history, and pairs this with a three-method (lexical + semantic + graph-traversal) retrieval pipeline and a menu of rerankers rather than a single extraction/update policy. Mem0 and MemOS both externalize memory outside the context window, but differ in what they treat as the unit of memory management. Mem0 keeps a single memory type (extracted natural-language facts, optionally graph-structured) and focuses the design on the extraction/update decision itself — an LLM tool-call choosing ADD/UPDATE/DELETE/NOOP per candidate fact against its nearest neighbors; it benchmarks against Zep as one of six baseline categories. MemOS instead treats plaintext, activation (KV-cache/hidden-state), and parameter (weight-level) memory as three interchangeable substrates inside one scheduled unit (MemCube), adding OS-style lifecycle states, access governance, and explicit cross-type transformation (e.g., distilling stable plaintext into a parameter module) that neither Zep nor Mem0 attempts; it directly reimplements Zep on a shared backbone and reports beating it. MemOS reports beating Mem0 on the same LoCoMo/LongMemEval/PreFEval/PersonaMem suite under a matched backbone, but the comparison is architecture-vs-architecture at each system's own best configuration, not an ablation isolating which of MemOS's added mechanisms (cross-type scheduling vs. governance metadata vs. lifecycle tracking) drives the gain. EverMemOS answers the same question with a third structure: rather than a single extraction pipeline (Mem0), a cross-substrate schedulable resource (MemOS), or a bi-temporal graph (Zep), it externalizes an explicit *lifecycle* — raw interaction is first distilled into MemCells (episode, atomic facts, time-bounded Foresight), then consolidated online into thematic MemScenes and a user profile, and only then retrieved through a sufficiency-checked, query-rewriting reconstruction step rather than flat top-k matching or Zep's multi-method search-and-rerank. Its reported gains concentrate on multi-hop and temporal/knowledge-update questions specifically, which is consistent with the paper's own framing that consolidation (not retrieval accuracy alone) is what lets a system integrate evidence dispersed across separate episodes. Notably, Zep's own paper independently arrives at a similar caution about benchmark weakness that this topic's later entries implicitly act on: it argues DMR is a poor differentiator for memory systems specifically because its conversations are short enough to fit a full context window, which is part of why Mem0, MemOS, and EverMemOS all lean more heavily on LongMemEval/LoCoMo-style benchmarks with longer, more temporally complex conversations. Recuris answers a different question than any of the four consolidation-focused systems above: not how a fact is stored, updated, or retrieved by similarity, but how memory *use* is gated during an active task. None of Zep, Mem0, MemOS, or EverMemOS couples retrieval to a checker-verified record of what the agent has actually confirmed it has accomplished — they retrieve based on similarity to the current query or context, which is exactly the "raw observation matched by similarity" pattern Recuris's own related-work section distinguishes itself from. Recuris's within-task loop (working state gates skill invocation; a checker commits only observation-supported state changes) is closer to this topic's question about auditable memory state (see Open Questions below) than to any one of the four systems' extraction/consolidation pipelines, while its cross-task evolution loop — localizing a failure to one of four typed memory components from a structured trace, then a validation-gated patch — is a distinct mechanism from all four systems' per-fact add/update/delete at ingestion time. VoiceMem answers a question none of the text-only systems above face: what happens when the retrieval budget is not "however many tokens the model can afford" but a hard ~400ms wall-clock window before a voice model must reply. Its response is architectural on two axes at once — a schema/entity index that narrows the candidate pool *before* any backend ranks it (VoiceMem's own ablations show removing this index costs more than removing any other single mechanism, on every dataset tested), and a persona/affect graph maintained as a fully separate structure from the factual store rather than a re-weighting term folded into one retrieval score, which is what Emotional RAG and KEEM do instead. Rather than proposing a fourth alternative to Zep's bi-temporal graph, Mem0's extraction pipeline, or MemOS's cross-substrate scheduling, VoiceMem treats those systems' backends as interchangeable and adds its index as a layer *above* them — reporting that the same index improves Mem0, Zep, and LangMem's own LoCoMo accuracy by 15.8-29.5 points without retuning any threshold, which is direct evidence that this topic's "unit of memory management" question and the streaming-latency question are separable design axes rather than a single combined choice.

# Open Questions

* How do accuracy and cost change under a stronger backbone than GPT-4o-mini for both the extraction/update pipeline and the LLM-judge?
* How should NOOP/DELETE decisions be audited or made reversible when an LLM tool-call misjudges whether new information contradicts an existing memory?
* When does graph-structured (relational) memory pay for its extra token and latency cost, versus when does dense natural-language memory alone suffice?
* How does per-agent or per-session long-term memory interact with the per-agent and shared-context memory designs this wiki already tracks under [Multi-agent systems](multi-agent-systems.md) (e.g. decentralized dual-pool memory) when a system needs both cross-session personalization and multi-agent coordination?
* How should a memory system's own state (which facts were kept, updated, or discarded, and why) be made externally auditable, similar to how [Agent harness engineering](agent-harness-engineering.md) tracks externally verified task state for execution?
* Which of MemOS's added mechanisms over a simpler extraction/update pipeline (cross-type plaintext/activation/parameter scheduling, governance metadata, lifecycle states) actually drives its reported accuracy and latency gains, and which add complexity without proportionate benefit?
* How sensitive is EverMemOS's incremental-clustering consolidation to its similarity threshold, and does its semantic-segmentation win over ground-truth session boundaries hold on noisier, less-curated interaction streams than existing benchmarks provide?
* Zep's bi-temporal edge invalidation always prioritizes the most recently ingested information when two facts conflict — does this transactional-recency priority hold up against Mem0's LLM-judged ADD/UPDATE/DELETE/NOOP decision and MemOS's governance metadata when the *older* fact is actually still correct (e.g., a later message misremembers or contradicts an earlier, accurate one)?
* Recuris shows that coupling memory to a verified working state, rather than the query or context alone, roughly doubles fault-localization accuracy for *why* a memory-augmented run failed (64.8% vs. 37.0% from the raw trajectory) — would adding a comparable checker-verified state layer to Zep's, Mem0's, or MemOS's own consolidation pipelines improve their reported add/update/delete decision quality, or is Recuris's gain specific to gating *invocation* rather than gating *ingestion*?
* VoiceMem's index improves Mem0, Zep, and LangMem's LoCoMo accuracy by 15.8-29.5 points as a layer bolted on top, without changing any of those systems' own extraction, consolidation, or graph-construction logic — does a comparable pre-ranking narrowing step (schema/entity routing before backend search) transfer gains to MemOS's or EverMemOS's more elaborate lifecycle-based consolidation, or does their existing structure already capture what VoiceMem's index adds, making the two approaches redundant rather than additive?
