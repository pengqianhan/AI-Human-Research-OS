# Scope

This topic tracks agents that act directly on graphical interfaces — desktops, native applications, and browsers — by perceiving screenshots and emitting GUI-level actions (clicks, keystrokes, drags), as distinct from agents that act through text-only tool calls or APIs. It covers training data/pipelines for such agents, mechanisms for conditioning execution on demonstrations or other in-context guidance, and benchmarks that evaluate long-horizon or cross-application GUI workflows.

# Papers

* [UI-Mate](../papers/2608.15930.md) - an open-weight foundation GUI agent combining a closed-loop environment-grounded training pipeline with DemoCUA, which converts multimodal demonstrations into adaptive subtask-level workflows rather than rigid replay; introduces OSWorkerBench, a 100-task long-horizon office benchmark with a controlled paired protocol for isolating demonstration value from instruction-only capability.
* [MAI-UI](../papers/2512.22047.md) - a 2B-235B foundation GUI agent family adding native agent-user-interaction (`ask_user`) and MCP-tool-use (`mcp_call`) actions, a device-cloud collaboration system with a trajectory monitor and privacy gate, and large-scale online RL (up to 512 parallel environments); new SOTA on five grounding benchmarks and AndroidWorld (76.7%).
* [RecreationWorld](../papers/2609.22000.md) - a five-platform (Ubuntu, macOS, Windows, Android, Web) framework built around application recreation: given a running reference and no prescribed workflow, an agent must interleave GUI exploration, coding, and execution-grounded self-verification to build a faithful implementation, scored by reference-validated hidden programmatic and visual test suites; training on 35,000 rejection-sampled recreation trajectories transfers to five out-of-distribution benchmarks (up to +17.9 points), while on the released 250-task RecreationBench the strongest model passes all programmatic tests on only 2.8% of tasks.
* [GameHorizon Suite](../papers/2609.25001.md) - evaluates models on AAA video games in the same raw keyboard-mouse action space as desktop computer use; both GUI agents tested (GELab-Zero-4B-Preview, UI-TARS-1.5-7B) fall into its lowest tier, and UI-TARS-1.5-7B scores 3.7 points below its own general-purpose base (Qwen2.5-VL-7B), suggesting GUI post-training can reduce transfer to other screen-and-control domains.
* [AutoGUIWorld](../papers/2610.01215.md) - synthesizes GUI trajectories without deploying software: a planner scripts actions and their visual effects, gpt-image-2 edits each screenshot into the next, a grounding model labels clicks, and a VLM filters inconsistent transitions; 79,266 samples lift Qwen3.5-35B-A3B on OSWorld (33.0 → 40.8), Windows Agent Arena, macOSWorld, ScienceBoard (14.0 → 32.2), and ScreenSpot-Pro (31.7 → 57.1).
* [nanoMuse](../papers/2610.08699.md) - puts screen control inside an open personal agent: on Android and desktops, operating the screen is the last rung of a ladder below skills, MCP servers, logged-in page fetches, and the browser, run as a one-action-per-screenshot loop in which the model must state each step in a sentence that a rule-based gate checks for committing words before the gesture runs; no success rates are reported.
* [SoftwareGym](../papers/2610.12611.md) - trains on software that did not exist before: 182 agent-written desktop applications supply the trajectories, and Qwen3.5-9B fine-tuned only on them goes from 41.39% to 56.97% Pass@3 on 244 OSWorld tasks (28.40% to 46.77% single-run average), within about 1.3 points of matched-size training on OSWorld applications by single-run average.
* [ExpActivator](../papers/2609.33304.md) - training-free personalization for mobile GUI agents: at every step the current screenshot is matched to the user's recorded screens in the frozen backbone's own visual features and the one best-matching past action is supplied as a reference; on AndroidIntent (82 users) it raises within-trajectory step success by 2.4-8.2 points across four 8-9B backbones with about one-fifth the history tokens, in offline evaluation against recorded actions.
* [SwitchMem](../papers/2610.17928.md) - at every step a router on the frozen actor's hidden state decides whether a retrieved demonstration step is shown as a text description or a screenshot; with Qwen3.5-9B it beats the best fixed form by 2.1 points on AITW and 0.7 on LearnGUI (significant, offline step-level scoring) and by 2 of 92 tasks on online MobileMiniWoB++ (not significant), and showing both forms at once is worst on LearnGUI.
* [OpenGCUA](../papers/2610.22200.md) - defines a generalist computer-use agent by three per-step model decisions (what to observe, how to act, how to organize) over GUI, accessibility, shell, and API interfaces; code execution plus model-chosen screenshots and a todo ledger lift eight frozen models from 45.3 to 64.9 mean partial score on the 82-task offline OSWorld-v2 set, and a preliminary macOS harness addresses shared control, background windows, and existing user state.
* [MAI-Gym](../papers/2610.20939.md) - an open platform that runs evaluation, data collection, and online RL through one harness over mobile, computer, and web (ten benchmarks, 20,000 parallel environments), synthesizes resettable app clones, invented apps, cross-app worlds, and execution-tested verifiers, and trains MAI-Gym-9B to 78.4% on MobileWorld and 76.2% on OSWorld-Verified in one joint GRPO run; RL in a ticketing-app clone lifts the real app on a physical phone from 28.8% to 48.1%.
* [CarryOn](../papers/2610.18784.md) - a context runtime evaluated on the full OSWorld 2.0 set (500 steps) with Claude Opus 4.7's native computer-use interface: partial score 43.9% to 49.7%, binary 15.7% to 19.4%, input context held near 65K tokens where the baseline passes 200K, and cost per task down 35.9%.

# Synthesis

UI-Mate and MAI-UI both target the gap between static-trajectory training and real-world deployment robustness, but through different levers: UI-Mate injects procedural structure at inference time via demonstrations, while MAI-UI extends the action space itself (clarification, tool calls) and pairs that with a deployment-time architecture (device-cloud routing) rather than a demonstration mechanism. Both introduce their own realistic benchmark (OSWorkerBench, MobileWorld) specifically because existing GUI benchmarks under-test the capability each paper adds. RecreationWorld answers a different question than either: not how to make a GUI agent robust to deployment variation, but whether an agent can autonomously fuse GUI operation with code authorship into one coordinated loop when the specification itself must be discovered by operating a reference rather than read from an instruction. Where UI-Mate's demonstrations and MAI-UI's `ask_user`/`mcp_call` actions both still start from a given task instruction, RecreationWorld's recreation task removes the instruction's specificity entirely — the agent must reverse-engineer *what* to build before it can decide *how* — making its own benchmark (RecreationBench) a test of specification-recovery-plus-implementation-plus-verification jointly, rather than execution robustness against a known goal. Its own trajectory analysis gives this topic's first evidence that even the strongest model (GPT-6 Astra, 58.1% overall) reproduces an interface's static structure far more reliably than its interactions and computed outputs, and that GUI activity does not fall off as implementation activity rises — a hybrid-workflow signature neither UI-Mate's nor MAI-UI's own analyses directly measure.

AutoGUIWorld attacks the coverage problem that UI-Mate's closed-loop pipeline, MAI-UI's online RL, and RecreationWorld's VM pool all solve by running more real software: it does not run the software at all. An image generator renders each next screen from a planner's description of the intended change, which makes specialized applications (CAD, scientific, audio) far cheaper to cover. Its measured costs are specific: 2-3% of transitions contradict their action, concentrated in text entry, drag, and scroll; the data contains almost no failures or recoveries; and Chrome, its largest domain, gets worse on two benchmarks. Its 80k synthetic samples beat 350k AgentNet human-demonstration samples on four benchmarks, though under different inference settings, and no ablation separates what the generated transitions add from the click labels a separate grounding model supplies.

nanoMuse treats screen operation as a deployment question rather than a capability one. Every other paper here asks how to make a GUI agent succeed more often; nanoMuse asks when a personal agent should use the screen at all (only when no skill, MCP server, logged-in fetch, or browser route works, echoing MAI-UI's added MCP-call action) and how to govern a step once it does. Its answer is that a policy cannot judge a screenshot but can judge the model's own description of the step, so each gesture is preceded by a sentence the gate reads for committing words, plus the Android accessibility text under the finger. This makes the agent's stated intent part of the safety boundary, and it has not been evaluated: the paper reports no success rate and no test of whether descriptions and gestures can diverge.

SoftwareGym and AutoGUIWorld answer the same question, how to get GUI training data without wrapping more real applications, from opposite ends. AutoGUIWorld deploys nothing and has an image generator draw each next screenshot, so it has no environment state and no verifier; SoftwareGym has coding agents write complete applications that run, persist state, and can be checked programmatically, at about $70 per application. SoftwareGym's 9B model gains on every OSWorld domain it evaluates, whereas AutoGUIWorld's larger model gained on multi-application tasks and lost on Chrome. The two use different base models, task subsets, and metrics (Pass@3 over three rollouts against mean task score), so this is a comparison of patterns, not of numbers.

ExpActivator and UI-Mate both condition a GUI policy on prior experience at inference time, at different grains. UI-Mate turns demonstrations into subtask-level workflows; ExpActivator supplies one recorded action, chosen again at each screen, and its controls show the grain matters: a whole retrieved trajectory in the prompt performs like no history after the first step, while one action selected from that same trajectory adds 5.4 points. Its setting is one user's own history rather than general demonstrations, and its evaluation is correspondingly narrow: step-level agreement with what that user did, with the true action prefix supplied, on one dataset. It does not measure live task completion, which the OSWorld-style evaluations elsewhere in this topic do.

SwitchMem and ExpActivator both make a memory decision at every step of a mobile GUI task from the frozen backbone's own representations, and both are evaluated mostly offline against recorded actions. ExpActivator chooses which recorded action to show; SwitchMem keeps a per-step retrieved demonstration and chooses whether its screen appears as text or as a screenshot. Its finding that both forms together score 10.5 points below the screenshot alone on LearnGUI bears on the richer context other papers here add (UI-Mate's workflows, MAI-UI's tool outputs): for a 9B actor, more evidence in the prompt did not mean better actions (reader inference from one benchmark). Its effects are small, 0.7 to 2.1 points offline and two tasks of 92 online, and the online result is not significant, so this topic's open question about live execution applies to it as well.

OpenGCUA widens this topic from GUI-level action to generalist computer use, where the model picks among GUI, accessibility, shell, and API interfaces each step and writes the step as a program. Against batched GUI-only execution on eight frozen models it adds 19.6 OSWorld-v2 points and halves steps, and against batched GUI+CLI with the same interfaces it still adds 4.4 to 9.1 points. In its formalization the hybrid designs this topic tracks, such as MAI-UI's added tool-use actions and RecreationWorld's interleaved GUI and coding trajectories, differ in which of three decisions the model makes rather than in which interfaces exist (reader mapping). Its real-device section names conditions the offline benchmarks here do not test: a user sharing the pointer and focus, background windows that a desktop screenshot does not show, and tasks that start among existing files and sessions. Its four-task study already shows models differing more in reasoning cost (19.4 times between GPT-6 Astra and Qwen3.8-Max) than in completion under one harness, with dollar cost ranking them the other way.

MAI-Gym is the training-side companion to OpenGCUA from the same team, and the two pull in different directions on action format. OpenGCUA finds that programs over GUI and shell beat batched GUI+CLI actions for frozen frontier models. MAI-Gym trains a 9B policy on batched GUI+CLI actions and reaches 76.2% on OSWorld-Verified, but stays low in computer environments it never trained in (3.7/11.3 on OSWorld 2.0, 15.2 on MyPCBench), so whether code as action would help a small trained policy is open (reader connection). It also gives this topic its first sim-to-real numbers for GUI training. Clone-only RL in a 12306 replica raises the real app from 28.8% to 48.1% on 52 tasks, while the clone-to-real gap widens from 7.7 to 25.0 points, and RL on invented apps with no demonstrations raises held-out success from 25.8% to 45.2%. Its gain split echoes SoftwareGym's SFT-only result in direction: most of MAI-Gym-9B's improvement comes from the SFT warm-up (Task-OOD average 29.9 to 66.4) and RL adds a smaller step (cross-domain average 44.1 to 50.5), though the two papers' splits and metrics differ (reader connection).

CarryOn brings context management into this topic's long-horizon desktop setting, where finished edits already live in documents, slides, and forms the agent can reopen. Instead of summarizing the screenshots and actions that produced them, it keeps references to those objects and checks them read-only (file exists, hash changed, valid document container), while the agent's native filter still keeps the ten most recent screenshots. On OSWorld 2.0 this holds input context near 65K tokens and makes runs cheaper from about turn 200 onward. Its 49.7% partial score is within half a point of the published GPT-5.5 and Claude Opus 4.8 results, which come from other runs and, for GPT-5.5, batched actions, so the like-for-like evidence is the gain over the same Claude Opus 4.7 agent (reader observation).

# Open Questions

* How should a demonstration-guided GUI agent transfer procedural structure across related-but-non-identical tasks (the variant-demo problem), rather than only replaying guidance from the same task?
* Can demonstrations be acquired at scale from passive sources (documentation, instructional video) rather than per-task recording, without losing the grounding that makes a recorded demonstration useful?
* How should training-data pipelines detect and rebalance systematic coverage gaps (long-horizon, cross-application, error-recovery tasks) that are expensive to generate relative to short single-application tasks?
* What is the right balance between deterministic milestone verification and learned judges for progress-based reward credit in long-horizon GUI tasks?
* How should a GUI agent's action space and context representation avoid invalidating KV-cache reuse as task state (e.g. a demonstration workflow pointer) updates mid-episode?
* How should a device-cloud collaboration system's deviation-detection threshold trade off false handoffs (cost/latency) against missed handoffs (task failure), and does that tradeoff transfer across the demonstration-guided and native-action-space approaches to real-world robustness in this topic?
* RecreationWorld finds recreated applications are typically far smaller and more structurally concentrated than their references (median 16.9% of reference LOC) yet the highest-scoring model has the *lowest* median code volume — what implementation choices, beyond raw code volume, actually explain higher behavioral fidelity, and would UI-Mate's demonstration-guided procedural structure or MAI-UI's expanded action space change that relationship if applied to recreation-style tasks?
* AutoGUIWorld's generated trajectories almost never contain a failed step. Can an image-generator world model also produce realistic errors and their visible consequences, so synthetic data teaches recovery, and does training on such data narrow the gap on long multi-app tasks that stays large even after its gains?
* nanoMuse gates each screen action on the operator's own sentence describing it. How often does that description disagree with the gesture actually executed, especially when on-screen content tries to mislead the operator, and does adding the accessibility text under the target close the gap on desktops where many controls are unlabeled icons?
* SoftwareGym builds eight of its twelve categories to mirror OSWorld's application domains. How much of the transfer to real applications survives when the synthesized categories share no function set with the test applications?
* ExpActivator's gains are measured as agreement with a user's recorded next action under teacher forcing. Does step-level reference selection still help in live execution, where following a slightly wrong reference changes the next screen, and on tasks the user has rarely done before?
* SwitchMem chooses between two forms of one retrieved step. Would the same router learn when to show no memory, or both forms, given that on MobileMiniWoB++ the actor without memory beats fixed text and fixed image memory?
* OpenGCUA's real-device harness prefers accessibility actions and background delivery so the agent does not disturb its user. How often does that order fail on desktop applications with poor accessibility support, and do the training pipelines here (SoftwareGym, RecreationWorld) produce agents that choose interfaces well or only agents that use the GUI well?
* MAI-Gym's clone-only RL widens the clone-to-real gap from 7.7 to 25.0 points even as real-app success rises. Which clone differences (layout, latency, pop-ups, login state) cause the widening, and would a few real-device rollouts mixed into training close it more cheaply than better clones?
* CarryOn's Grounder can verify that a document exists and changed but not that it shows the right content. Could the screenshot-based verifiers GUI agents already use serve as stronger Grounder checks, and would that close the binary-score gap in its carrier ablation, where hiding the carriers scored higher on binary success (25.00% against 22.50%)?
