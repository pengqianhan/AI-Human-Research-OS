# Q1 Problem Definition

* **Input (X):** a base agent harness (system prompts, tool definitions, and middleware/control logic) wrapping a frozen foundation model (Claude Opus 4.6 by default), a training split of tasks from one benchmark family, and mini-batches of execution traces — both successes and failures — sampled from that harness running on the training split.
* **Output (Y):** an updated harness (same frozen model, revised prompts/tools/middleware) with higher Pass@1 on a held-out test split, plus an EvoDAG recording the full optimization lineage (patches, lessons, and performance signal at each node).
* **Core problem:** long-horizon LLM-agent reliability degrades because small local failures compound, and external harnesses can substantially improve robustness, but hand-designing a harness is expensive, requiring manual search over prompt variations, tool configurations, and control logic. Can this search be automated as an offline learning problem — the harness treated as the trainable object, mini-batch failure signals as the training signal — the way weight-space training is driven by gradients?
* **Scope:** the prompt, tool, and middleware layers of a harness for a frozen model; the paper explicitly excludes memory or skill curation for stateless single-episode tasks from its current scope.

# Q2 Problem Novelty

Automatic harness/prompt optimization is not new — the paper positions itself directly against two contemporaneous automated baselines it benchmarks against: GEPA (prompt-centric evolutionary optimization driven by shallow reflection) and Meta-Harness (a minimal end-to-end harness-optimization system built on the Claude Agent SDK). AutoSaddler's claimed novelty is not a new optimization target but a specific combination of three ingredients the paper argues prior automatic approaches under-specify: (1) evidence-grounded diagnosis that actively explores both the execution trace and the harness's own source code rather than a single shallow-reflection call; (2) patches constrained to a typed taxonomy (by harness layer and by capability-vs-steering kind) with an explicit two-phase schedule, rather than unconstrained free-text edits; (3) acceptance gated on validated, generalization-aware evidence (mini-batch plus optional held-out dev-set check) rather than fixing whatever a single failed trajectory suggests. The paper's own framing is that prior automatic methods explore "complementary aspects" of this space rather than combining all three.

# Q3 Scientific Hypothesis

If harness optimization performs (a) evidence-grounded, code-level diagnosis instead of shallow reflection, (b) constrained, code-structured, phase-scheduled patches instead of unconstrained free-text edits, and (c) mini-batch-plus-dev-set validation gating instead of trajectory-specific repair, then the resulting automated loop will outperform existing automatic harness-optimization baselines on held-out test accuracy *and* reach a given accuracy level using substantially fewer execution traces than those baselines. The paper's three ablations (RQ1-RQ3, one per ingredient) are each designed to isolate whether that specific ingredient — not just the overall system — is load-bearing for these two claims.

# Q4 Related Work and Key People

* **GEPA** — prompt-centric evolutionary optimization via shallow reflection; a baseline compared on GAIA2 and SWE-Bench Pro.
* **Meta-Harness** — a minimal system built on the Claude Agent SDK for end-to-end harness optimization; a baseline compared on GAIA2 and Terminal-Bench 2.0, and the reference point for AutoSaddler's efficiency claim (10x fewer traces to reach peak dev accuracy).
* **Terminus KIRA** — a manually, expert-tuned harness for Terminal-Bench 2.0 that AutoSaddler's automated result (50.0%) exceeds (47.5%), used as evidence that the automated loop is not merely catching up to hand engineering but surpassing it on this benchmark.

# Q5 Key Solution Idea

1. **Failure-trace diagnosis via a Diagnosis-Patch Agent.** Rather than a single shallow-reflection call over a trajectory summary, the agent actively explores both the raw execution trace and the harness's own source code, using structured guidance for progressive retrieval that mitigates the context-length pressure of long agent trajectories — "deep debugging rather than shallow reflection."
2. **Structured, typed patch generation.** Patches are constrained to a taxonomy crossing harness layer (Prompt: system-prompt rule add/modify; Tool: new tool, argument fix, implementation correction, description update; Middleware: hook, infrastructure, or agent-loop-logic change) with patch kind (Capability: executable code/orchestration change; Steering: textual-only edit) — "targeted modifications rather than unconstrained editing."
3. **Phased Patch Scheduling.** Optimization begins with capability patches before shifting to steering patches later in the run, an explicit analogy to a learning-rate schedule in conventional weight-space training.
4. **Validation-based update selection.** A candidate patch must first improve mini-batch performance to be provisionally accepted, then optionally passes a held-out development-set check for generalization before being retained — "generalization-aware selection rather than trajectory-specific repair."
5. **EvoDAG.** The optimization history is kept as a directed acyclic graph rather than a single linear chain, recording lessons and performance signal at each node so that successful patch components from different optimization lineages can be recombined instead of only extending the single most recent harness state.

# Q6 Experiment Design

Three benchmarks, three distinct base harnesses and task domains, with the underlying LLM held fixed at Claude Opus 4.6 (so only the harness, not the model, is being optimized):

* **GAIA2** — general-assistant tasks in a simulated smartphone environment, evaluated across three test "universes" of 107-112 tasks each; base harness is a default ReAct-based agent.
* **SWE-Bench Pro** — enterprise software engineering across three repositories (96 Ansible, 85 Flipt, 56 Element-web tasks); base harness is the SWE-agent framework.
* **Terminal-Bench 2.0** — system-administration, ML, and cybersecurity tasks (40 test tasks); base harness is Terminus 2.

Tasks are partitioned into disjoint train/dev/test groups by distinct task group (not a random split), so held-out results measure cross-domain generalization rather than in-distribution memorization. The headline metric is test-set Pass@1 against the corresponding base harness and against GEPA and Meta-Harness where reported. A separate optimization-efficiency comparison on GAIA2 tracks dev-set accuracy against the number of task executions/rollouts consumed. Three ablations isolate the three method components (RQ1: replace in-depth diagnosis with a single shallow-reflection call; RQ2: remove the patch taxonomy and phased scheduling; RQ3: remove the reflection/dev-set generalization filter), each measured on GAIA2. A cross-model transfer probe applies an Opus-optimized harness unchanged to Haiku 4.5.

# Q8 Evidence Quality

The headline test-set gains are specific, self-consistent across three unrelated task domains, and computed here directly from the paper's own reported point values rather than from a secondary summary: GAIA2 default agent 53.0% → AutoSaddler 62.0% (+9.0 pp), also beating GEPA (54.6%) and Meta-Harness (53.2%) on the same split; SWE-Bench Pro SWE-agent baseline 37.3% → AutoSaddler 46.9% (+9.6 pp), also beating GEPA (42.5%) and Meta-Harness (35.3%); Terminal-Bench 2.0 Terminus 2 baseline 40.0% → AutoSaddler 50.0% (+10.0 pp), beating GEPA (42.5%), Meta-Harness (43.3%), and — notably — the manually expert-tuned Terminus KIRA harness (47.5%). These three deltas match the paper's own abstract statement of "9.0, 9.6, and 10.0 percentage points" respectively. The efficiency claim is a second, independent line of evidence rather than a restatement of the accuracy gain: on GAIA2, AutoSaddler reaches 72.3% dev accuracy in ~1,000 total task executions, while GEPA and Meta-Harness saturate lower (64.6% and 61.5%) despite consuming roughly 2,800 executions, and AutoSaddler reaches its own peak dev score after 147 traces versus Meta-Harness's 1,400 (~10x fewer). The ablations are reasonably diagnostic about *why* each component matters rather than only *that* removing it hurts: without structured, typed patches, 91.5% of generated patches collapse to textual Steering edits and only 4% are capability-changing (New Tool, Loop Change, Infra Change) patch types, even though those capability types have higher acceptance rates (67-83%) and, when they are proposed, comparable fix rates to steering patches (55% vs. 58%) with far fewer regressions (8% vs. 17%) — evidence that the taxonomy is not merely bookkeeping but changes what kind of fix the system is willing to propose. Removing the reflection/dev-set filter (RQ3) produces the largest single drop (62.0% → 50.6%) and a qualitatively different regression trend across iterations (AutoSaddler trending -0.24 pp/iteration versus the ablation's +0.16 pp/iteration), consistent with the filter specifically preventing accumulation of narrow, poorly-generalizing patches over the run rather than just improving a single-shot score. Caveats for this note: the numeric evidence above was reconstructed from an automated re-fetch of the paper's HTML rendering (cross-checked across three independent extraction passes for internal arithmetic consistency) rather than a hand-read PDF, so table entries carrying uncertain "±" qualifiers were deliberately omitted rather than reported with a guessed interpretation; the paper is very recent (submitted 2026-08-24) and has not yet accumulated independent replication or peer review at the time of this note; and cross-model transfer evidence is a single data point (Opus→Haiku, +5.6 pp over the Haiku base harness) rather than a systematic transfer study.

# Q9 Contributions

1. Frames automatic harness optimization explicitly as an offline learning problem over mini-batch failure signals, with the harness itself as the trainable artifact.
2. Introduces a Diagnosis-Patch Agent that grounds patch proposals in both execution traces and harness source code rather than trajectory-only shallow reflection.
3. Introduces a typed patch taxonomy (layer x capability/steering) with Phased Patch Scheduling (capability patches before steering patches), and shows via ablation that this structure — not just having *some* constraint — changes which patch types get proposed and accepted.
4. Introduces validation-based, generalization-aware update selection (mini-batch plus optional dev-set check) and an EvoDAG that preserves multiple optimization lineages for later recombination rather than forcing strictly linear continuation.
5. Empirical demonstration across three unrelated benchmarks (GAIA2, SWE-Bench Pro, Terminal-Bench 2.0) and three base harnesses, with consistent 9-10 point Pass@1 gains, an order-of-magnitude reduction in traces needed relative to a comparable baseline (Meta-Harness), and a same-benchmark win over a manually expert-tuned harness (Terminus KIRA on Terminal-Bench 2.0).

# Q10 Next Steps

* The paper's own stated limitations: current scope covers prompt, tool, and middleware layers but explicitly excludes memory or skill curation for stateless single-episode tasks; the authors suggest "specialized LLM-driven evolutionary algorithms" as a direction beyond the current Claude-Agent-SDK-based diagnosis/patch loop; cross-model transferability (Opus-optimized harness applied to Haiku, +5.6 pp) is reported as promising but is a single probe rather than a systematic study.
* **Research-OS fit:** AutoSaddler's diagnose-write-validate loop is structurally close to this wiki's existing harness-optimization lineage — compare directly against [MemoHarness](2607.14159.md) (six-dimensional harness search plus dual-layer experience bank), [SkillOpt-Lite](2607.03451.md) (file-native trajectory exploration with independent validation), and [EnvHarness](2608.19880.md) (the same diagnose-write-validate pattern applied to the environment rather than the agent side). AutoSaddler's specific contribution to that comparison is its typed patch taxonomy plus phased scheduling and its EvoDAG-based lineage recombination, worth comparing against those papers' own patch-representation and validation-gate choices the next time this repository evaluates a harness-optimization method for its own agent tooling.
* Worth revisiting once independent replication exists, given the paper's very recent submission date and this note's reliance on an automated re-fetch of the HTML source rather than a full manual read.
