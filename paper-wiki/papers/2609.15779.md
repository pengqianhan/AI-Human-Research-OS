# Q1 Problem Definition

* **Input (X):** a training workload of natural-language tasks over heterogeneous data sources (tables, files, databases), the raw sources themselves, and historical agent-interaction trajectories accumulated during deployment. At evolution round *t*, the ontology state ℒ_t = (𝒮_t, Γ_t, ℛ_t) — a Content Layer, Schema Layer, and Tool Layer — is also an input to the next round's refinement.
* **Output (Y):** a versioned ontology state exposed as an MCP server with two tools (`browse` for top-*n* semantic matches, `resolve` for records and linked objects) plus a compact session manifest; downstream, this is the interface a ReAct-style data agent queries at runtime instead of exploring raw schemas.
* **Core problem:** data agents must fulfill instructions over heterogeneous data that "resides outside the agent" — reachable only through generic tools (SQL interfaces, file readers) — creating an "agent-data gap" in which the agent must blindly probe structure and content it cannot see in advance. Existing raw-querying agents re-explore this gap on every task; existing semantic layers are manually authored, static prompt injections that scale poorly to large sources and cannot adapt to different agents' behavior.
* **Scope:** three data-agent benchmarks (DDR-Bench 10-K scenario, InsightBench, BIRD text-to-SQL under Oracle Knowledge), six LLM backbones (GPT-5.5, GPT-5.6-sol, Claude-Sonnet-5, Claude-Opus-4.8, DeepSeek-V4-Flash, Qwen3.5-Flash), and a fixed ReAct scaffold with identical tools, decoding, and interaction budget across conditions. Evolution is offline/training-time (a reciprocal two-fold split-and-swap protocol), not continuous online adaptation during held-out evaluation; the ontology is frozen before testing on the held-out fold.

# Q2 Problem Novelty

The paper does not claim to originate ontologies, semantic layers, or LLM tool use in general — it cites OWL ontologies and dbt's metric layer as long-standing static representations, and situates raw-querying data agents (DIN-SQL, MAC-SQL, CHESS, text-to-SQL pipelines) and prompt-injected semantic layers (RSL-SQL, E-SQL, PET-SQL) as the two existing families. Its stated novelty is twofold: (1) making the intermediate layer *interactive* rather than static — encapsulated as an MCP server the agent actively queries at runtime rather than a fixed block prepended to every prompt, so only the terms and mappings relevant to the current step are retrieved instead of competing with the rest of the context; and (2) making it *self-evolving from agent behavior* rather than fixed after construction — a builder agent grounds an initial ontology in executable probes against the training workload without gold answers, and a separate evolution agent then diagnoses failures from historical trajectories, attributes each to one of three editable levels (Content, Tool, Schema), and admits only edits that pass a backbone-conditional paired validation gate. This differs from prior LLM-induced schema/metric descriptions (which are generated once) and from generic prompt-optimization work (Zhou et al. 2022; Yang et al. 2024) by evolving a structured, typed, evidence-grounded knowledge graph rather than free-text instructions.

# Q3 Scientific Hypothesis

If the agent-data intermediate layer is (a) built from evidence-grounded probes over the raw data rather than manual specification, (b) exposed through queryable MCP tools rather than injected as static context, and (c) continuously refined from agent-specific interaction trajectories via attribution-tagged, single-level, validation-gated edits, then it should more effectively bridge the agent-data gap than either raw exploration or a static semantic layer — and the refinement should compound over rounds rather than saturate after one construction pass. The paper's own evidence: on DDR-Bench, EvoOntology improves Trajectory-Wise accuracy on all six backbones by an average of +17.8 points (Table 1), while the static-prompt Baseline+SL baseline is inconsistent and drops by up to −15.0 points on Claude-Sonnet-5; the initial (pre-evolution) ontology alone already improves over the no-ontology baseline, and a further self-evolution stage extends the gain on all three benchmarks (Sec. "Effect of Ontology Layer").

# Q4 Related Work and Key People

* **Data agents on heterogeneous data.** Raw-querying agents (text-to-SQL: DIN-SQL, MAC-SQL, CHESS, RSL-SQL; table-QA: TabFact; code-executing analysts: InsightBench's DS-agent lineage) equip LLMs with schema-reading and query tools but discard grounding discovered in one trajectory rather than retaining it for later tasks — the gap EvoOntology's persistent ontology is built to close.
* **Semantic layers.** OWL ontologies (Hitzler 2021) and dbt's metric layer (dbt Labs 2023) are cited as the long-standing static-layer lineage; LLM-oriented prompt-time metadata (Feng et al. 2024; Chang and Fosler-Lussier 2023) and LLM-induced schema/metric descriptions (Zhang et al. 2023b; Nan et al. 2023) are the closer prior-work family, distinguished from EvoOntology by being detached from downstream usage trajectories and injected wholesale rather than selectively retrieved.
* **Memory-based persistence.** ReAct+Memory baselines (Reflexion/Shinn et al. 2023; Voyager/Wang et al. 2023; Self-Refine/Madaan et al. 2023), which store past trajectories as retrievable episodes, are directly benchmarked (Table 2): they lift DDR-Bench Trajectory-Wise from 69.5 to 75.8 but remain 13.7 points below EvoOntology's 89.5, because episodic memory only replays what has been done rather than exposing typed, composable structure.
* **Key people.** Corresponding author Shaolei Zhang (Renmin University of China, RUC-DataLab); co-authors Meiduo Chong, Ju Fan, Xiaoyong Du. Submitted 14 Sep 2026 (arXiv v1); code at github.com/ruc-datalab/EvoOntology (278 stars at fetch time per `hf papers info`).

# Q5 Key Solution Idea

1. **Three-layer ontology state, encapsulated as an MCP server (Sec. "Agent-First Ontology-Layer Architecture").** The Content Layer 𝒮 is a typed semantic graph with four node families (Terms, Mappings, Constraints, Evidence) and two edge families (Semantic Relations, Structural References); the Schema Layer Γ defines the fields and admissible relation/reference types for those families; the Tool Layer ℛ exposes `browse(q,k,n)` and `resolve(ℐ,c)` plus a compact session manifest — the only ontology content placed directly in the prompt, with detailed records retrieved on demand.
2. **Evidence-grounded initialization (builder agent).** From a training workload and raw sources, a builder agent proposes candidate concepts from recurrent entities, metrics, operations, and conditions, then issues executable probe queries against the raw data for each candidate; only candidates whose probe results pass a type/filter/value-distribution `verify(·)` check are committed to the initial Content Layer, with their supporting records retained as Evidence (Eq. 1).
3. **Trajectory-grounded evolution loop (evolution agent), four steps: diagnose → attribute → patch → gate.** The evolution agent extracts recurrent failure signatures from historical trajectories, assigns each to exactly one editable level (Content/Tool/Schema) with a stated expected behavioral effect, proposes a single-level patch, and admits it only if its paired-evaluation score against the current ontology on a held-out validation set improves by at least margin τ under the same backbone m (Eq. 2); rejected candidates are logged (not deployed) to avoid repeating ineffective updates, and all six backbones evolve independently from the same initial state.
4. **Reciprocal two-fold evaluation protocol.** Each benchmark is split into folds A and B; 70% of a fold builds and evolves the ontology and 30% is the paired-validation held-out set, the frozen ontology is then tested on the other fold, folds are swapped, and the two directions' scores are averaged — the held-out test fold's answers and feedback are never used during construction or evolution.

# Q6 Experiment Design

**Main comparison (Tables 1, 3, 4).** Three conditions — Baseline (ReAct, no ontology), Baseline+SL (the builder agent's semantic layer prepended as a static prompt fragment, matching prior prompt-injection work), and EvoOntology — are compared under the identical ReAct scaffold, tools, decoding, and interaction budget on DDR-Bench 10-K (Message-Wise/Trajectory-Wise), InsightBench (Insight/Summary), and BIRD under Oracle Knowledge (EX/VES), across all six backbones. A ReAct+Memory condition (Table 2) is compared separately on DDR-Bench, averaged across four backbones.

**Decomposition ablations (Sec. "Analyses").** (a) *Effect of Ontology Layer* isolates the builder-constructed Initial ontology from the further Evolved gain via a three-way Baseline/Initial/Evolved comparison. (b) *Effect of Iterative Evolution* plots the deployed score across accepted evolution rounds on DDR-Bench to check the gain is not a single fortunate patch. (c) *Ablation on the Evolution Loop* disables each of the four steps in turn (w/o Diagnose: propose from a random trace sample; w/o Attribution: no level tag; w/o Patch: free-form rewrite instead of a typed, hypothesis-conditioned edit; w/o Gate: accept every candidate) and compares final DDR-Bench Evolved score. (d) *Three-Level Evolution* restricts the loop to Content-only, Tool-only, or Schema-only edits versus the full three-level loop. (e) *Ablation on Ontology Structure* masks each removable Content-Layer object family (Mappings, Evidence, Constraints, Relations) from the final Evolved ontology. (f) *Divergence across Backbones* compares pairwise Jaccard overlap of accepted Term identifiers and cross-backbone transfer (each backbone's evolved store served to every other backbone).

**Design strength for the hypothesis.** The reciprocal two-fold protocol and the held-out validation split give the main comparison a genuine train/test separation. The four-step and three-level ablations (Tables 5–6) are the strongest evidence for the specific architectural claims (gate and attribution are load-bearing; all three editable levels are complementary), since they isolate one mechanism at a time on a fixed benchmark/backbone-average setup rather than comparing whole systems. The cross-backbone transfer analysis (Figure 5b) is a genuine held-out test of a different kind — whether one backbone's evolved ontology generalizes to another — and finds it does not (every off-diagonal cell drops ≥6.6 points from the same-backbone diagonal), directly supporting the paper's design choice to evolve each backbone's ontology independently rather than share one store.

# Q9 Contributions

1. EvoOntology, the first (per the paper's own claim) autonomous, interactive ontology layer for data agents, encapsulated as an MCP server with a typed content graph, schema, and queryable tool interface, replacing static prompt-injected semantic layers.
2. A builder-and-evolver framework: an evidence-grounded builder agent constructs an initial ontology from probe queries with no gold-answer supervision (Eq. 1), and a four-step (diagnose/attribute/patch/gate) evolution loop refines it from historical agent trajectories through backbone-conditional paired validation (Eq. 2), shown by ablation to require both the gate (−11.2 points if removed) and the attribution step (−6.3 points if removed) to reach full performance.
3. Consistent empirical gains across three heterogeneous data-agent benchmarks and six LLM backbones: average Trajectory-Wise gain of +17.8 on DDR-Bench, average EX/VES gains of +7.4/+8.6 on BIRD, and improved Overall on every backbone on InsightBench (mean +1.9), while the static semantic-layer baseline is inconsistent (e.g., −15.0 on Claude-Sonnet-5 DDR-Bench Overall).
4. Evidence that the ontology's three editable levels (Content, Tool, Schema) are complementary rather than substitutable (no single-level-only variant recovers more than 13.2 of the full loop's +20.0 DDR-Bench gain), and that evolved ontologies are backbone-specific — cross-backbone transfer drops by at least 6.6 points off the same-backbone diagonal — justifying independent per-backbone evolution over one shared store.

# Q10 Next Steps

The retrieved Conclusion does not enumerate a dedicated Limitations section (none of the section headings list one separately from the Conclusion), so no paper-stated limitations list is available to summarize here beyond what the experiments and appendices themselves flag: Appendix B's own cost accounting shows the Evolved ontology adds a larger per-turn input-token cost than Baseline (4.6K vs. 3.2K tokens/turn) even though total cost per task falls (42.0K vs. 52.6K) because trajectories shorten — a genuine cost/latency trade-off the paper reports but does not discuss as a limitation.

Beyond the paper's own text, three points are worth flagging for a reader assessing this note's evidence. First, all six backbones evolve independently from the same initial ontology, and the paper shows this is necessary (cross-backbone transfer degrades) — but this means deploying EvoOntology for *n* backbones requires *n* separate evolution runs against the training workload, a scaling cost the paper does not quantify in wall-clock or compute terms beyond the per-task token accounting in Appendix B. Second, the paired-validation gate's margin τ is never given a concrete value in the retrieved text, so a reader cannot assess how conservative or permissive the acceptance threshold actually is, only that removing the gate entirely costs 11.2 points. Third, the reciprocal two-fold protocol evaluates generalization *within* a fixed benchmark (fold A→B and B→A), not across genuinely different data sources or task distributions from where the ontology was built — so this note's "bridges the agent-data gap" framing should be read as demonstrated within-benchmark, not as evidence the ontology transfers to unrelated heterogeneous-data workloads never seen during construction or evolution.
