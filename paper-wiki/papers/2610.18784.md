# Q1 Problem Definition

* **Input (X):** a long-horizon agent's running interaction history (actions, observations, screenshots, reasoning summaries) together with the environment it acts on, where finished work already sits in files, documents, or application state.
* **Output (Y):** at each fold, a replacement for the covered history: a context view V_t = (A_k, E_k, L_t), where A_k is the set of continuation-carrier records, E_k the execution context, and L_t the live tail of interactions since the last fold.
* **Goal:** keep the agent able to continue (same or better task score) while it stops re-reading accounts of how progress that is already stored in the environment was produced, so active context and cost stop growing with trajectory length.
* **Constraints:** a fold may only commit carrier edits supported by the evidence bound to them; the original interactions stay in an append-only log; and the runtime's checks guard consistency, not task correctness, as the paper states.

# Q2 Problem Novelty

The paper groups prior work into two families. Compression and selection methods shorten or retrieve past interactions: prompt compression (LLMLingua, LongLLMLingua), trajectory reduction, periodic summaries (ReSum, ACON, AgentFold, HiAgent), branch returns (context folding), external histories (MemGPT, ACM), and compaction validated against later execution (Slipstream). State-externalization methods keep progress as explicit records: an internal state merged with new observations (MEM1, Context as a Tool), execution-state trees, persistent variables, or task records (*Memory as execution state management*, AgentProg, StructAgent, [LongHorizon-Harness](2608.01964.md)), and persistent workspaces with reconstructed views (InfiAgent, *Context as an environment*, FS-Researcher). The paper's claim is that both families still continue from an account of progress, compressed or reconstructed, that can drift from the state the agent actually inspects. CarryOn makes the reusable task objects themselves the unit of continuation and keeps in text only what those objects do not carry.

# Q3 Scientific Hypothesis

If long-horizon context is organized around reusable task objects, with each carrier stating what progress an object holds and when it can be reused, and the execution context keeps only the goals, constraints, and open work the objects do not capture, then the agent can drop covered history without losing what it needs to continue. It should then score at least as well as with the full history while processing far fewer tokens. The paper also expects the structure, not only shortness, to matter: a generic summary or a sliding window of similar length should do worse, and maintaining records across folds should beat rewriting a complete summary at each fold.

# Q4 Related Work and Key People

* **Compression and selection.** LLMLingua and LongLLMLingua; trajectory reduction (Xiao et al.); ReSum, ACON (whose FIFO-truncation and summarization baselines the paper reuses), AgentFold, and HiAgent; context folding via branch returns; MemGPT and ACM for histories kept outside the prompt; Memory OS and A-MEM among retrieval-style memories; PACE for predictive extraction; Slipstream for validating compaction against later execution.
* **State externalization.** MEM1 and Context as a Tool (an internal state merged with new observations); Agent Workflow Memory among methods that turn histories into explicit progress records; execution-state and task-record approaches (*Memory as execution state management*, AgentProg, StructAgent, LongHorizon-Harness); persistent workspaces (InfiAgent, *Context as an environment*, FS-Researcher).
* **Benchmarks.** OSWorld 2.0 (the main evaluation, v2026.08.08), BrowseComp-Plus, and OSWorld as the earlier desktop benchmark.
* **Key people.** Yuchen Lu, Julian McAuley, and Lei Zhang (corresponding author), all at UC San Diego. Likely critics: the ACON and AgentFold authors, whose learned or proactive compression is not among the baselines, and the LongHorizon-Harness and *Context as an environment* authors, who also externalize state but keep it as maintained records rather than object references.

# Q5 Key Solution Idea

**Three kinds of carrier.** An *external object* is a work product that exists independently and can be reopened (a code file, a document, a spreadsheet); its record references the object and says what progress it holds. An *information product* is a finding obtained through interaction (synthesized information, a troubleshooting conclusion) that is not saved anywhere, so its record stores the finding directly as claims with source references. *Situated state* is progress that lives only inside an application, session, or workflow (a checkout at the payment step, an unsaved workbook); its record names the environment anchor, the established state, and the scope within which it stays reusable. Every carrier has a stable identity, and a revision creates a successor version under it.

**Execution context and live tail.** The execution context holds the current focus, open obligations, active constraints, and immediate next steps not captured by any carrier, each with source attribution. The live tail keeps the raw interactions since the last fold.

**A four-stage fold.** (1) A Tracker reads recent interactions and maintains candidates, potential new carriers or updates, and requests compilation once one can support continuation. (2) The runtime binds each request to its evidence: source excerpts for information products, and for objects a Grounder runs scoped read-only checks (file exists, content hash differs from the initial snapshot, file non-empty, valid docx/pptx/xlsx container, document text differences, presence of text copied from the task instruction), each condition returning supported, contradicted, or unknown. Only fully supported object requests proceed. (3) A Compiler proposes carrier edits for the selected candidates only, grounded in their bound evidence, and revises the execution context against the whole live tail so that nothing outside the candidates is lost. (4) The runtime checks identity, references, source authorization, and that the input records are still current. A fold must change at least one carrier; it then commits atomically and retires the entire live tail, otherwise nothing changes. Unaffected carriers keep their records, so most progress is carried forward rather than reconstructed.

# Q6 Experiment Design

* **Benchmarks.** The full OSWorld 2.0 set (500-step budget per task; partial and binary scores under the official protocol) and a random 100-question subset of BrowseComp-Plus (BM25 retrieval, five results of 512-token snippets per call, 60 turns; answers graded by Qwen3-32B with the official prompt).
* **Models.** Claude Opus 4.7 as host agent, Tracker, and Compiler, without training; maximum adaptive thinking for the OSWorld agent. The baseline is the same agent with its native context handling, reproduced by the authors; published OSWorld 2.0 results for other models are listed for reference.
* **Triggers.** On OSWorld 2.0 the Tracker runs once roughly 6,000 tokens of interaction text (characters divided by four) have accumulated since the last scan or fold; on BrowseComp-Plus after 120,000 tokens of prompt growth, with thresholds doubling after scans that produce no fold.
* **Accounting.** Total tokens sum uncached input, cache reads, cache writes, and output across agent and runtime calls; costs use nominal Claude Opus 4.7 prices (USD 5 per million uncached input, 0.50 cache read, 25 output).
* **Comparisons and ablations.** On a shared 40-task OSWorld 2.0 subset: baseline, Sliding Window, Generic Summary (GS), CarryOn-Guided Summary (CGS, the same organizing principles written into one replacement summary each fold), and CarryOn, with the same host model, trigger, and step budget; plus hiding either the carriers or the execution context from the agent. Carrier persistence is measured over 494 committed folds.

# Q7 Datasets and Code

No new dataset. The paper lists the exact 40 OSWorld 2.0 task IDs and 100 BrowseComp-Plus question IDs it used, and reproduces the Tracker, Compiler, GS, and CGS prompts (GS in full, the others in excerpt). # Q8 Evidence Quality

* **Supported.**
  * *Higher score at lower cost on OSWorld 2.0.* Partial score rises from 43.9% to 49.7% and binary from 15.7% to 19.4% with the same host model. Total tokens fall from 40.10M to 19.30M per task (−51.9%) and cost from USD 36.83 to 23.62 (−35.9%), including USD 3.11 of runtime calls.
  * *Context stops growing.* The baseline's input context passes 200K tokens on long trajectories, while CarryOn's settles near 65K. Cumulative cost curves cross before turn 200, and by turn 500 CarryOn is 34.1% cheaper including overhead.
  * *Structure beats shortness.* On the 40-task subset, Sliding Window (12.08K characters retained) and Generic Summary (17.60K) both fall below the baseline (partial 37.41% and 44.94% against 50.32%). CGS recovers to 50.93%, and full CarryOn reaches 55.93% with 21.54K characters, about 10% less text than CGS, while matching the baseline's 22.50% binary score.
  * *Both parts of the view carry information.* Hiding the execution context drops partial score to 44.00% with little change in agent calls. Hiding the carriers drops it to 44.62% and raises agent calls by 23.8% and cost by 22.3%; a trajectory shows the masked agent re-extracting a PDF price list it had already used.
  * *Records persist.* Of 813 carrier observations over 494 folds, 278 are retained and 372 updated (79.95%), and 163 are new.
* **Weaker or narrower than the headline.**
  * *Single runs, small subsets.* Every configuration runs once and no intervals are reported. On the 40-task subset one task is 2.5 binary points; on BrowseComp-Plus the 7-point gain is 7 questions (reader arithmetic).
  * *An ablation the paper does not discuss.* Hiding the carriers gives a higher binary score (25.00%) than full CarryOn (22.50%) on the same subset, so the carriers' benefit shows in partial score and cost but not in fully completed tasks (reader observation from Table 5).
  * *"Exceeds other frontier models" is narrow and cross-setting.* CarryOn's 49.7% partial score is 0.2 to 0.4 points above the published GPT-5.5 (49.5%) and Claude Opus 4.8 (49.3%) results, which come from the benchmark's own runs, with GPT-5.5 executing actions in batches. The like-for-like claim is the gain over the reproduced Claude Opus 4.7 baseline.
  * *One host model.* Tracker, Compiler, and agent are all Claude Opus 4.7, so whether a smaller or different model can run the Tracker and Compiler, or benefits as a host, is untested.
  * *Baselines are prompt-based.* The compression comparisons are a sliding window and a generic summary in the style of ACON's baselines, not ACON's optimized compressor, AgentFold, LongHorizon-Harness, or another externalized-state method, so the gain over the strongest prior method is unmeasured.
  * *Cost depends on caching.* Costs use nominal prices with cache reads at a tenth of uncached input, so the 35.9% cost saving is smaller than the 51.9% token saving and would shift under other price schedules; on BrowseComp-Plus the cost saving is 7.1%.

# Q9 Contributions

* An object-oriented framing of long-horizon context in which progress already stored in the environment is referenced with conditions of reuse instead of being summarized, and text carries only what the objects do not.
* A fold protocol with candidate tracking, evidence binding, read-only environment checks, joint compilation of carriers and execution context, and atomic, versioned commits that leave unaffected records untouched.
* Evidence on OSWorld 2.0 and BrowseComp-Plus that this reduces tokens and cost while raising score for one frontier host model, and a controlled comparison against sliding-window, generic-summary, and same-principle summary baselines.
* Ablations showing that carriers and execution context hold different information, and a persistence analysis showing that most carrier records are maintained across folds.

# Q10 Next Steps

* **From the paper's analysis.** The authors suggest that maintaining records as objects evolve, rather than rewriting a summary, may explain the gain over CGS; testing that directly would separate the effect of persistence from that of the structured format.
* **Repeat with variance and more hosts (reader suggestion).** Run the 40-task comparisons several times and with an open-weight host and a smaller Tracker/Compiler, to show whether the 5-point gain over CGS exceeds run-to-run noise and survives a weaker runtime model.
* **Compare against externalized-state harnesses (reader suggestion).** [LongHorizon-Harness](2608.01964.md) and [PoS](2610.01415.md) also replace history with maintained state, an audited task state and a validated belief respectively, and PoS already compares several such methods on shared benchmarks. Adding CarryOn to that comparison would show whether object references beat maintained records.
* **Stronger Grounder checks (reader suggestion).** The OSWorld integration checks file existence, hashes, containers, and text differences, not whether content is correct. Checks that compare a document against the requirement it is meant to satisfy could let carriers carry verified rather than merely present progress, and might explain the binary-score gap in the carrier ablation.
