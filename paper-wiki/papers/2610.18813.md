# TL;DR

Many agent systems now improve by rewriting the software around a fixed model (its prompts, memory, tools, and control code) instead of retraining the model. This paper gives that practice a definition, a map of what such systems change, and a statistical rule for when a change should be kept: only when it beats the current version on fresh tasks the search never saw, by a margin large enough to rule out luck. It is for people building or evaluating self-improving agent harnesses, and for anyone deciding whether such a system can be trusted with persistent changes.

# Overview

**Scope.** A *harness* H is the software and configuration that governs a model M's execution in a task environment E. Running produces a rollout τ ~ Run(M, H, E), scored by a final assessment y = J(τ); candidates may revise critics or provisional checks inside H but cannot modify J. Table 1 lists seven runtime functions a harness performs (an implementation may combine them): agent loop and execution control; tool and skill orchestration; context construction; memory and state management; context compaction; scheduling and coordination (subagents, background work); and execution infrastructure (sandboxes, permissions, approvals, logs, replay).

**Harness self-evolution.** At round k the incumbent H_{k-1} produces a batch of b rollouts, and an update operator (diagnosis, proposal, assessment, admission) returns H_k; if nothing is admitted, H_k = H_{k-1}. Two requirements make this a lifecycle rather than a one-off edit: *operational feedback and update continuity* (the system builds or selects revisions algorithmically from its own executions and keeps the mechanism for further updates; people and automated assessors may supply feedback and admission may need human approval) and *persistence across runs* (accepted revisions are stored and loaded later). One observed update suffices to demonstrate the capability if both hold. Appending logs or compacting context under fixed rules does not revise the harness; learning reusable procedures or changing memory policies does; revising the update mechanism adds another level of recursion.

**Terminology.** *Self-evolution* names the update process and *self-improvement* a gain established by comparison. "Harness RSI" names the research area without assuming each revision helps. Weight-only adaptation and scaffolds without an update mechanism are out of scope; when a system also trains weights, its harness updates are examined with the task model held fixed.

**Why the harness rather than weights.** Three reasons are given: the harness directly shapes a fixed model's behavior and can keep task constraints and lessons from failures; revisions reuse a deployed model, including proprietary APIs without weight access, and avoid retraining and extra checkpoints; and instructions, memory, and code can be inspected, diffed, and tracked, whereas attributing behavior differences between checkpoints needs controlled experiments.

**What was read.** The arXiv v1 is a ten-page main text plus an appendix listing the contents of a companion technical report ("Harness Self-Evolution: Theory, Algorithms, Evaluation, Applications, and Impact", hosted on OpenReview), which carries the broader literature, the evaluation chapter (four claims behind a task score, current practices, longitudinal evaluation), and the societal-economic chapter. The abstract's "66-page discussion" refers to that report and the GitHub materials, which this note did not read.

# Framework

The paper separates three things a method must specify: the *update target* (what state later runs inherit), the *proposal* mechanism, and the *admission* mechanism. Its taxonomy classifies only the first.

| Branch | What is mutated | Examples the paper attributes |
|---|---|---|
| Interpreted-state updates | Instructions and prompts, stored experience, task-level coordination over predefined capabilities (workflows routing among fixed operators, including code that only composes them) | GEPA, Promptbreeder, ExpeL, Agent Workflow Memory, AFlow |
| Executable: tools and code patches (3.1) | Callable procedures or designated modules, with surrounding orchestration outside the editable surface | Voyager and PolySkill skill libraries; Self-Harness, HarnessCompass, and Agentic Harness Engineering patch selected components; MemEvolve edits memory-management functions; HarnessBank keeps candidate archives |
| Executable: repository and runtime logic (3.2) | Context construction, orchestration loops, execution hooks, recovery, termination: control over how components interact, not the number of files edited | ADAS, Meta-Harness, the self-improving coding agent (SICA), Darwin Gödel Machine, DarwinX, Huxley-Gödel Machine; RRSI and MOSS add edit constraints and transfer-oriented admission; VERSE makes the optimizer's own prompts, hooks, and tools evolvable |
| Executable: everything is a plugin (3.3) | Component implementations or the *bindings* that decide which implementation supplies a runtime service (memory storage, tool dispatch, the agent loop) | DeepSeek's harness and a spatiotemporal-composability paradigm as kernel substrates; HarnessX, Argus, Autogenesis, ModularRSI revise typed primitives or scoped modules; Everything Is a Plugin (EIP) extends this to capabilities generated, validated, and mounted during operation |

Two rules govern the boundaries. The interpreted/executable line concerns the edited artifact's *role*, not its language: a workflow written as code stays interpreted while it only sequences fixed operators, and becomes executable once operator implementations or the coordination runtime change. Plugin composition describes binding rather than scope, so one revision can belong to several executable categories. Classifying the target says nothing about whether a method meets the feedback, continuity, and persistence requirements; an exported program counts only if its deployment keeps an update mechanism, and archive membership is not adoption until the selected program is promoted into the runtime later tasks use.

# Key Techniques

**Evolutionary reading of harness search (Section 4.1, Figure 2).** An update has four aspects: the representation of mutable state, the variation that generates edits (traces and critiques can guide it), the assessment of fitness, and the selection of state to retain. Figure 2 maps methods to eight structures, each with the stated limits of the analogy:

* *Elitist (1+1)*: compare one candidate with the incumbent (SICA, MCE as a history-informed (1+1)-ES, SkillOpt, SkillOpt-Lite, SkillClaw).
* *Elitist (1+λ)*: several edits from one parent (Self-Harness; its later merging differs from the canonical single-survivor rule).
* *Archive-based search*: keep program lineages for parent selection and code mutation (DGM, DarwinX, HGM; the analogy does not imply tree-based genetic-programming operators).
* *Recombination*: combine material from earlier candidates (DarwinX, HarnessCompass, Self-Harness, MCE's agentic crossover; Trace2Skill's consolidation alone is not an evolutionary loop).
* *Quality-diversity*: semantic archive cells with local elites (HarnessBank, which modifies MAP-Elites parent selection and adds verification gates).
* *Cooperative coevolution*: optimize components separately, then combine (HarnessCompass, without independently evolving subpopulations).
* *Pareto selection*: cost-performance frontiers or several acceptance criteria (Meta-Harness, Self-Harness, SkillMOO; not a full multi-objective EA such as NSGA-II).
* *Bandit-guided evolution*: Thompson sampling over search budget (HGM, covering lineage expansion and candidate evaluation).

Because all of these select on empirical fitness, accepted revisions can overfit or forget, which motivates the next part.

**Three conditional guarantees (Section 4.2).** The evolution state X_k (harness, skills, archive, feedback memory) is updated from n_k tasks drawn independently from an exogenous distribution, with the model and evaluator fixed and loss in [0, 1].

1. *Expected generalization from stability.* Replace one task with a fresh draw, rerun every downstream update (feedback, archives, selection) under coupled randomness, and let β_{s,k} be the average loss change. Then the expected gap between true and empirical risk is at most β_{s,k}. The bound is on the expected gap, not on any single run, and small code edits do not by themselves make the full update process stable.
2. *Retention under regression budgets.* Define forgetting on round-s tasks as the risk change since H_s. If every later transition is assumed to raise round-s risk by at most a budget ε_{s,u}, telescoping gives E R_s(H_k) ≤ E R̂_s(H_s) + β_{s,s} + Σ_{u>s} ε_{s,u}. The budgets are assumptions rather than consequences of stability, their allowances add up, and checking them needs groupwise uncertainty control for the deployed composition, including merged edits and shared routers.
3. *Admission on fresh validation.* Over T rounds with at most K candidates per round, draw a fresh set of m independent tasks from the uniform historical mixture, independent of how the candidates were built. With paired loss differences in [−1, 1], conditional Hoeffding bounds and a union bound over KT comparisons give, with probability at least 1 − δ, Δ_k(H′) ≤ Δ̂_k(H′) + √(2 ln(KT/δ)/m). Accept a candidate only if this upper bound is negative. If evaluator and target risk can differ by up to η per harness, the sufficient condition becomes Δ̂ + √(2 ln(KT/δ)/m) + 2η < 0, and η itself needs evidence from executable checks or independent human assessment.

The scope notes are part of the result: the sample size is the number of independent tasks (extra rollouts reduce execution noise but add no tasks); correlated sessions need grouping; non-additive metrics need their own concentration arguments; and the certificate covers the historical mixture, not arbitrary future distributions. Edits or merges informed by the validation set need fresh validation again. The paper names two search-time checks that lack the assumed independence: HarnessBank reuses training tasks for screening before a separate final test, and Self-Harness reuses a held-out regression split. Keeping the split secret or correcting for the number of comparisons does not remove adaptive dependence; fresh samples or adaptive-data-analysis methods (Dwork et al.) are needed.

**A reader calculation of what the admission rule asks for.** The margin √(2 ln(KT/δ)/m) is not small at the validation sizes common in this wiki. With K = 5 candidates, T = 10 rounds, and δ = 0.05, ln(KT/δ) = ln 1000 ≈ 6.9, so the margin is about 0.37 at m = 100 tasks, 0.17 at m = 500, and 0.12 at m = 1,000. On a [0, 1] loss, a candidate would need to beat the incumbent by roughly 37 points on 100 fresh tasks to be certified. The rule is a worst-case bound; it shows how far current small-split acceptance gates are from a certificate, not a recommended protocol (reader-constructed example, not in the paper).

# Case Studies

### Exemplar Systems

* **HarnessOpt on SpreadsheetBench (Section 3.2, Table 2).** Converted from proportions in SkillOpt-Lite's Table 3. HarnessOpt extends SkillOpt-Lite from skill editing to runtime revision: better spreadsheet previews, output checks, and recovery after tool failures. Accuracy (%) for initial, SkillOpt, SkillOpt-Lite, HarnessOpt only, and HarnessOpt plus skill:

  | Model | Initial | SkillOpt | SkillOpt-Lite | HO only | HO + skill |
  |---|---|---|---|---|---|
  | GPT-5.4-nano | 29.89 | 51.60 | 66.19 | 76.51 | 77.58 |
  | GPT-5.4-mini | 28.21 | 47.50 | 73.31 | 81.14 | 82.56 |
  | GPT-5.4 | 39.86 | 61.50 | 79.36 | 83.63 | 85.05 |
  | GPT-5.5 | 37.37 | 76.20 | 79.72 | 83.63 | 85.77 |

  GPT-5.4-nano with HarnessOpt and skill (77.58) exceeds GPT-5.5 with SkillOpt (76.20), and HarnessOpt plus skill beats SkillOpt-Lite by 5.69 to 11.39 points across the four models. The paper reads this as model–harness pairing and states it does not establish superiority at matched cost. The figures agree with this wiki's [SkillOpt-Lite](2607.03451.md) note (0.7758 against 0.7620).
* **Everything Is a Plugin through DSH Everything (Section 3.3, Tables 3-4).** A Codex plugin lets the agent generate tools during execution and keep them for later tasks. On a simulated office workload (spreadsheets from different company regions with shared calculations), Codex creates batch-lookup and summarization tools: on the first task, tool calls fall from 13 to 3 while tokens rise from 41,119 to 47,572 (+15.7%) and wall time from 15.49 s to 24.00 s (+54.9%). A separately reported cumulative series shows savings from the second task, reaching 110,351 tokens and 22.97 s after five tasks. The paper flags its own inconsistency: the first-task totals imply +6,453 tokens and +8.51 s, while cumulative row 1 reports +4,895 and +6.74, so the two cannot be read as one cost trajectory. The same source reports LiveBrowseComp 51.39 for "XYZ + dsh-everything" against 48.7 for XYZ-Aquila-mini, first of six entries under 40B and second of eleven overall (XYZ-Aquila-pro 53.7), in an unspecified unit. The paper states that repeated runs, matched budgets, and matched task quality are needed before calling these plugin gains causal.

### Application Domains

Section 5 asks what persistent revisions do in five settings and what software rollback cannot undo.

* *Personal workspaces* (Claude Code memory, GitHub Copilot Memory, agent skills): temporary workarounds become standing rules, injected instructions persist across tasks, and successful executions can still yield skills that generalize harmfully; recovery must cover derived skills, memory, and caches, not only tracked code.
* *Enterprise automation*: a local workaround spreads to teams with different permission or data assumptions, and a shared faulty procedure produces correlated errors (algorithmic monoculture extended to harness artifacts); version-linked deployment records and staged rollout support containment.
* *Scientific discovery*: evolving protocols that exploit provisional checks can reinforce procedures that fail independent measurement, and the cost (instrument time, reagents) is spent before detection; J must stay outside the editable surface, with independent replication.
* *Robotics*: EMHO and RoboRSI revise planning and skills around frozen models; accepted action code can cause excessive force or unsafe recovery that rollback cannot reverse. Emergency stops, force and speed limits, and authorization checks should stay outside the editable surface.
* *Public services and clinical systems*: qualified professionals must authorize consequential revisions; each decision should record its rule version, evidence, and admission history, with review and appeal.

# Evidence Boundaries

* **What the paper itself establishes.** A definition with two checkable requirements, a classification rule for update targets, a mapping of methods to EA structures, and three bounds derived from standard results (replace-one stability after Shalev-Shwartz et al., Hoeffding with a union bound). The bounds are correct consequences of their assumptions; none is checked against a running system.
* **The assumptions exclude most current practice, as the paper says.** Independent task draws from a fixed distribution, a fixed evaluator, fresh validation independent of candidate construction, and assumed regression budgets. It names HarnessBank and Self-Harness as violating independence; the reader calculation above suggests that typical small validation splits could not satisfy the admission rule even if independent.
* **No new experiments.** Tables 2-4 and Figure 3 are converted or adapted from other sources. Table 2 comes from SkillOpt-Lite (Shen, Li, and Zhang), whose first author shares the name of this paper's corresponding author, Yifei Shen. The EIP figures come from a Zhihu answer by Runqi Pan and from the DSH Everything repository listed under Yifei Shen (owner `yshenaw`). Neither EIP source is peer reviewed, the paper itself notes a numerical inconsistency between the two reported series, and LiveBrowseComp's "XYZ" models are not identified. Figure 3's latency curves come from a 2023 edge-AI paper (Shen et al.) on a fixed deployment, cited to motivate studying component placement rather than harness evolution.
* **The taxonomy and EA mapping are qualitative.** Figure 2 states that categories overlap and that a correspondence is not equivalence to the canonical algorithm. Method attributions are the authors' readings, and several cited systems (Self-Harness, HarnessCompass, DarwinX, HarnessBank, VERSE) are not ingested in this wiki, so their placement was not checked here.
* **Unread material.** The companion report's evaluation chapter (including "four claims behind a task score") and the literature review were not read; any claim in this note about evaluation practice comes from the short paper's Sections 4.2 and 6.4.

# Takeaways

Reader notes on what to carry into one's own work:

1. **Ask the two lifecycle questions of any "self-evolving" claim.** Does the system build its revision from its own execution feedback and keep the ability to revise again, and does the accepted revision load in a later run? A one-off optimizer that exports a fixed harness fails the first; an in-session lesson that is never stored fails the second.
2. **Classify the change by role, not by file type.** A workflow script that only routes among fixed tools is interpreted state; touching the tool implementations or the loop that runs them is an executable revision with wider regression risk.
3. **Count independent tasks, not rollouts.** Repeating runs on the same tasks lowers execution noise but does not add evidence that a change generalizes.
4. **Keep the judge and the brakes outside the editable surface.** Final assessment, permissions, spending limits, and physical safety limits should never be something a candidate can modify, and creating a capability should not grant authority to use it.
5. **Project fit.** This repository's own self-updating layers (the cognition cache, project memory, installed skills) meet both lifecycle requirements in the paper's sense: they are revised from session feedback and loaded by later sessions. Their admission today is human review and `verify.sh`, which checks structure, not whether a revision helps; the paper's framing suggests recording, per revision, what evidence admitted it.

# Open Questions

* How large must a fresh, independent validation set be for the admission rule to accept realistic improvements, and can sequential or adaptive-data-analysis methods certify smaller gains with fewer tasks? (reader question from Section 4.2)
* How should effort be split between model selection, skill optimization, runtime revision, and weight updates at matched adaptation and execution cost, and do frozen, transferred, or re-evolved harnesses keep their gains across model checkpoints? (authors, 6.1)
* After how many related tasks does a generated plugin repay its generation and validation cost at matched quality, and when should a retained tool be revalidated, regenerated, or retired? (authors, 6.3)
* How can the evaluator-target discrepancy η be bounded after an evaluator changes (judge bias, drift), and how should budgets be divided among calibration, admission, and regression checks? (authors, 6.4)
* How can composed behavior be validated and permissions revoked as dependencies change, so that a locally valid plugin cannot alter shared state or other components unseen? (authors, 6.3 and 6.5)
