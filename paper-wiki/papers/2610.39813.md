# Q1 Problem Definition

* **Input (X):** a sequence of evolution tasks, from one benchmark or a shuffled mix of several; a global pool of agents; and execution traces with native evaluation results.
* **Output (Y):** a frozen set of persistent knowledge: a team library (each team a description of supported collaboration requirements plus a candidate roster), one interaction-rule set per team, and per-agent guidance (prompt patches and reusable skills). This is scored on disjoint held-out tasks.
* **Core problem:** how can a multi-agent system keep improving its collaboration across tasks that need different divisions of work, without earlier coordination experience harming later tasks?
* **Constraints:** LLM weights stay fixed, and all methods share tools, per-case budgets, and splits.

# Q2 Problem Novelty

Partly new. Experience-driven improvement of individual agents has a long line (Reflexion, ExpeL, Voyager, ReCreate), and recent work evolves collaboration itself: Meta-Team, [Self-Evolving MAS via Decentralized Memory](2605.22721.md), SkillMAS, Skill-MAS, and EMAS. The paper's new focus is continued evolution across heterogeneous tasks. Its preliminary study reports that Meta-Team scores lower on target tasks after inheriting evolution from another benchmark, or even from another task category with a compatible team template, than after target-only evolution. The authors name two causes: reorganization constrained to one shared team, and interaction rules reused across incompatible contexts.

# Q3 Scientific Hypothesis

If reusable team structures are kept separate from one another, interaction rules are scoped to the team they were learned in, and individual skills stay shared across teams, then a system evolving over mixed tasks should not lose performance relative to evolving on one benchmark. Learned rules should add value beyond team selection alone, team selection should add value without rules, and the evolved artifacts should remain useful under a different evaluation model.

# Q5 Key Solution Idea

**Decouple capability from organization.** A global agent pool holds the agents. A team T = ⟨d_T, C_T⟩ is a description of the collaboration it supports plus a candidate roster drawn from the pool. An LLM Team Selector checks whether any team fits the query's collaboration requirements and functional roles; topic similarity alone is not enough. If none fits, a Composer builds a provisional team. Teams are organized by collaboration requirements, not by benchmark, so holdout tasks from LoCoBench, LOCA-Bench, and BeyondSWE reuse one analyst-implementer-verifier team in a case study.

**Recruit and plan per task.** A Chairman recruits an execution team from the roster, decomposes the query into subtasks, assigns them, and can reassign within the team when progress stalls. The same team can therefore activate different members on different tasks.

**Scope the rules.** Only the selected team's rule set is injected into agents' contexts, as soft guidance. For each handoff, the sending agent judges applicability from the sender-recipient pair, the rule's trigger, and current needs; if no rule applies, it communicates directly. A rule specifies what information and evidence a handoff must carry, not a whole workflow.

**Reflect at three levels.** The system records individual traces and a handoff trace. A Team Reflector revises the roster and description, and decides whether a provisional team is admitted (its roster must support the division of work and be reusable). A Rule Reflector adds, revises, or removes rules using handoff events and payloads. An Agent Reflector updates that agent's skills from its local trace. Rules stay with their team, while skills stay with the agent and travel across teams. Everything is frozen before held-out evaluation.

**The contrast the paper draws.** In a LOCA-Bench case, Meta-Team's reflection replaced 45, 43, and 31 accumulated profile notes with one note each, shared by teammate name without any benchmark condition. EvoTeam's update added one family-scoped rule while keeping the others. The authors note that the overwrite followed evaluation and so does not explain that task's score difference, and that EvoTeam's recruitment profiles also remain shared.

# Q6 Experiment Design

* **Benchmarks and splits (evolution / held out).** GAIA validation subset (20 / 100), LoCoBench Python Feature Implementation and Cross-File Refactoring (20 / 80 each), [LOCA-Bench](../concepts/loca-bench.md) (16 at 96K with two seeds / 240 at other lengths and seeds), and BeyondSWE CrossRepo (20 / 180) and DepMigrate (20 / 158). Subsets and splits follow Meta-Team.
* **Two evolution settings.** Individual: each benchmark or track alone. Mixed: 116 tasks interleaved in one fixed shuffle (seed 20260828), evolving one system that is evaluated on all 838 held-out cases.
* **Baselines.** ReAct single agent, unevolved MAS with EvoTeam's collaboration structure, OWL, AgentSquare, ReCreate, Meta-Team, and Skill-MAS, using official implementations where available, all under the same model, tools, and budgets.
* **Model and metrics.** GPT-5.6-Luna (temperature 0.2), with DeepSeek-V4.1-Flash for cross-backbone runs on GAIA and LoCoBench. Metrics are GAIA answer accuracy, LOCA-Bench final-state success, BeyondSWE resolution (all F2P and P2P tests), and LoCoBench's weighted LCBS. The paper states avg@3 over three rollouts per test instance.
* **Ablation and cost.** Removing rules, and removing both teams and rules, on all six metrics; per-task cost against score from figures.

# Q8 Evidence Quality

* **Supported.**
  * *Mixed-stream lead.* First on all six metrics: GAIA 77.00 against Meta-Team's 67.00, LOCA-Bench 67.08 against 58.33, LoCoBench 65.55 and 65.65 against 64.90 and 64.52, DepMigrate 40.51 against 37.97, CrossRepo 41.67 against 40.56.
  * *Robust to mixing.* Its average moves from 58.85 (individual) to 59.58 (mixed), while Meta-Team's falls from 58.30 to 55.55.
  * *Rules and teams each add on several tasks.* Rules add 10.00 on GAIA and 8.75 on LOCA-Bench; teams add 6.00 and 2.50 without rules.
  * *Artifacts transfer between models.* Cross-backbone results stay within 4.00 of same-backbone results on all six comparisons and beat unevolved MAS, for example GAIA 76.00 against 58.00 on DeepSeek-V4.1-Flash.
* **Weaker or narrower than the headline.**
  * *Per-benchmark evolution is nearly a tie.* The average lead is 0.55, and Meta-Team wins LOCA-Bench clearly (69.58 against 63.75) and CrossRepo narrowly (41.67 against 41.11). The GAIA margin of 5 points is 5 of 100 questions.
  * *The mixed lead is concentrated (reader calculation).* GAIA and LOCA-Bench supply 18.75 of the 24.18 points summed over six metrics. Removing rules gives exactly Meta-Team's scores on those two (67.00, 58.33), so on them the lead comes entirely from the rules.
  * *Evolved knowledge can hurt.* The appendix reports that removing rules improves LoCoBench Refactoring (66.40 against 65.65), and that removing both components beats removing rules alone on DepMigrate (37.97 against 36.71); the main-text figure shows four tasks without these two. By the paper's stated differences, the variant with skill evolution only scores 61.00 on GAIA, below the unevolved MAS at 72.00 (reader calculation), so skill accumulation over the mixed stream can lose ground before rules and teams recover it.
  * *No skill ablation.* Skills are shared across teams, so interference at that level remains possible, and no variant removes or scopes them (reader observation).
  * *One stream order.* The text describes one fixed shuffle of 116 tasks, roughly 20 per source, and no repeated evolution runs, so the effect of order and of the stochastic reflectors is unmeasured (reader observation).
  * *Rollout count unclear (reader inference).* The paper states avg@3, yet every LOCA-Bench and BeyondSWE score in Table 1 is a whole number of held-out cases (for example 161 of 240, 64 of 158), which averaging three binary rollouts would rarely give. Those scores may come from one pass per case.
  * *Library size is not reported.* The text does not say how many teams or rules result, so how selective the reuse scope is cannot be judged from the numbers (reader observation).
  * *Cost and the preliminary study are figure evidence.* This note read those figures only through captions and the surrounding text.

# Q9 Contributions

* A collaboration-centric architecture with three separately scoped kinds of persistent knowledge: reusable teams, team-specific rules, and cross-team agent skills.
* Evidence that a shared system can evolve over a mixed task stream without losing average performance relative to per-benchmark evolution, on one stream order.
* A role and rule-level account of why experience reuse can fail across tasks, with an ablation showing where rules help and where they do not.
* A cross-backbone test of evolved team artifacts in both directions.

# Q10 Next Steps

* **Multimodal settings (from the paper).** The evaluation does not cover visual interactive environments, where agents must share visual evidence and coordinate as the scene changes.
* **Combine with model adaptation (from the paper).** Experience is stored explicitly with fixed weights, so its value depends on the model interpreting it; training could internalize frequently useful coordination.
* **Library maintenance (reader question).** Algorithm 1 revises or adds teams and gives no merge or retirement step. How large does the library grow over a long stream, and does selection accuracy hold?
* **Gate updates on evidence (reader suggestion).** Updates are accepted by reflection without a paired check. Comparing this with validation against the current system, as the paper describes for EMAS, could address the cases where rules lower scores.
* **Repeat and vary the stream (reader suggestion).** Several stream orders and evolution repeats, with library size and rule counts reported, would show how stable the mixed-stream lead is.
* **Scope skills too (reader suggestion).** Testing family-conditioned skills against global ones would address the drop that skill-only evolution shows on GAIA.
