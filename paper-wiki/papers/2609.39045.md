# Q1 Problem Definition

* **Input (X):** a natural-language game specification x, a frozen initial game project P₀ sampled from a generator policy (source code, visual and textual assets, configuration files, plus replayable demonstration traces), a target game engine (Godot or Phaser), and a per-round tool budget (up to 26 tool calls per round, up to 30 development rounds).
* **Output (Y):** an improved project P_T whose replayed demonstration traces score higher against a hidden task-specific rubric Q = BUILD × (0.15·Mechanics + 0.35·Depth + 0.15·Visuals + 0.35·Art), where BUILD ∈ {0, 1} zeroes non-playable games. A second output is a fine-tuned generator (Qwen3.8-27B SFT) whose one-shot games start higher.
* **Core problem:** iterative "test, diagnose, revise" loops over a generated game tend to overfit the few test cases they happen to exercise, so they converge to fragile builds with untested bugs, missing behaviors, and unhandled corner cases, and they can plateau or regress as more rounds are added (Figure 3). The paper asks how to make long-horizon autonomous development *reliably* convert extra rounds into higher game quality.
* **Scope:** compact 2D games expressible within practical agent budgets; quality measured only on the four GameCraft-Bench dimensions (Appendix B names originality, narrative, long-term engagement, and enjoyment as outside the evaluation); improvement agents are GLM-5.3-Flash in the main runs, the explorer/test agent and the benchmark judge are Qwen3.8-27B.

# Q2 Problem Novelty

Not a new problem. Iterative agentic game development already exists: Play2Code alternates gameplay and code revision from interaction feedback, VibeGame runs an eight-role agent team with verification and optimization roles, and OpenGame accumulates reusable skills across projects. The benchmarks the paper builds on (OpenGame-Bench, GameCraft-Bench, GameDevBench) score a single submitted build. The paper's own framing of what is new (Sec. 6, Appendix F.1) is narrow and explicit: "This paper does not claim that an agent can improve a game it generated — several systems do that. It claims that doing so reliably needs a controller: something that decides where the headroom is, keeps the best version, and stops." The sibling paper [RSIAgent](2609.15364.md) from the same group had already shown a 40-task GameCraft-Bench generalization check against Play2Code; RSIGame makes game development the primary setting, scales to all 140 tasks and two engines, and adds the training-based internalization step. The problem matters because game projects are a stress test of multimodal, multi-file, runtime-behavior-dependent engineering where compile-only checks miss most failures (Table 2b: build-only checking detects 0% of behavioral failures).

# Q3 Scientific Hypothesis

Two coupled hypotheses:

1. **Controller hypothesis.** If the development loop (a) explores the executable game broadly rather than re-testing the same cases, (b) grounds each edit in observed evidence and verifies it by replay, (c) accumulates issues and guidance in a persistent checklist, and (d) is governed by a global monitor that keeps the best checkpoint and stops at saturation, then additional development rounds should yield monotone-in-expectation quality gains where naive iteration plateaus or regresses. Tests: Table 1 (matched-budget comparison to Play2Code), Figure 3 (development-time scaling), Figure 4a-b (best-checkpoint retention and saturation stopping), Figure 5 (adaptive versus round-robin direction choice), Table 2 (verification audit).
2. **Internalization hypothesis.** If the generator is fine-tuned on verified planning, generation, and improvement trajectories rather than on final artifacts alone, then one-shot generation quality should rise across all four quality dimensions and the loop should need fewer tokens to reach a given quality. Tests: the Qwen3.8-27B (SFT) rows of Table 1, Figure 4c, and the nested training-data ablation of Table 18.

# Q5 Key Solution Idea

The differentiator is a two-level control structure around an otherwise standard edit loop, plus feeding the loop's verified traces back into the generator.

* **Local loop (explore-diagnose-improve), four agents over one shared checklist 𝒞_t.** A *controller* reads the spec, current project, checklist, and optional stage guidance γ_s and picks a development direction d_t. An *explorer* plays the executable game along that direction and returns a trajectory τ_t of concrete behavioral evidence. An *editor* turns evidence into a project edit Δ_t. A *verifier* replays the edited game to decide whether the targeted issue is fixed without regressions, and writes the outcome back. The checklist update 𝒞_{t+1} = U(𝒞_t, d_t, τ_t, Δ_t, v_t) is what carries evidence across rounds, so each round starts from verified state rather than from scratch.
* **Global loop (quality monitor and convergence control).** A game quality monitor compares the newest build against the retained champion P*_s and keeps the better one. It reads a separate proxy rubric and never the benchmark's hidden rubric, scores, or feedback, and its pixel-reading comparator is isolated from the stage that decides direction and stopping (Appendix C.2). Persistent failure to beat the champion is treated as convergence: the run returns P*_s, or optionally opens a new stage under sparse high-level guidance from a human or stronger model (a "brief" of strategic direction, not edit instructions).
* **Adaptive direction rather than round-robin.** The controller shifts effort to the current bottleneck (toward repair after build failures, toward art when visuals lag); blind pairwise judging prefers adaptive runs 59% to 37%.
* **Training-based internalization.** 2,213 generation traces (GPT-5.5 in Godot and Phaser), 2,108 planning traces, and 2,013 verified improvement rounds (from 4,003 candidates, run with GLM-5.3-Flash) are serialized as long documents and used for LoRA SFT over 4-bit quantized Qwen3.8-27B. Benchmark task IDs are excluded at corpus build time and re-scanned afterward (zero overlaps across 2,511 task IDs).

What is deliberately *not* new: iteration, LLM judges, or multi-agent roles. Appendix F.1 argues from the VibeGame comparison that "the presence of verification and optimisation roles in a pipeline is not what produces sustained improvement."

# Q6 Experiment Design

* **Benchmark and engines.** All 140 GameCraft-Bench tasks (15 game families) instantiated in both Godot and Phaser with the same specs, rubrics, and protocol, so Phaser is a cross-engine robustness check.
* **Arms.** Frozen P₀, Play2Code, and RSIGame, each from an identical clone of P₀ with the same improvement backbone and per-round tool budget (26 tool calls per round, 30 rounds). Five generator settings on Godot (Codex + GPT-5.5, Codex + Kimi-K2.6, Codex + GLM-5.3-Flash, Codex + Qwen3.8-27B, Codex + Qwen3.8-27B SFT) and three on Phaser (OpenGame + GPT-5.5, OpenGame + Qwen3.8-27B, OpenGame + Qwen3.8-27B SFT).
* **Scoring.** Qwen3.8-27B judge, mean of three independent replay-and-score runs; RSIGame rows score the checkpoint the monitor holds when saturation stops the run, Play2Code rows the version after 30 rounds.
* **Analyses that target specific claims.** Development-time scaling curves on 40 tasks (Figure 3); oracle-best versus retained checkpoint and saturation stopping (Figure 4a-b); adaptive versus round-robin by blind pairwise judging (Figure 5, Appendix D.6); a verification audit of 40 sessions and 48 adjudicated rounds with Claude Opus 5 as independent auditor (Table 2, Appendix D.7); a nested S1 ⊂ S2 ⊂ S3 training-data ablation (Table 18); a VibeGame comparison on shared tasks (Appendix F.1).
* **Reliability controls.** 20,000-resample paired task bootstrap and Wilcoxon signed-rank tests (Table 14); replay stability over 529 thrice-scored Godot artifacts (median range 0.73 points, 225 of 529 identical across runs); cross-judge re-scoring of 40 tasks with GPT-5.5 giving the same method ordering (Table 12); a free-play evaluation on 20 tasks where blind agents play independently chosen trajectories (RSIGame preferred over base on 17 of 20 and over Play2Code on 18 of 20; 45 of 59 decided comparisons agree with the benchmark ordering).
* **Not designed in.** No ablation removes the checklist or the verifier individually from the main table; no per-component attribution of the gain between the local loop and the monitor beyond Figure 3's "local loop alone" curve; only one iterative baseline (Play2Code) is run at full scale; the single-engine Kimi and GLM generators are not evaluated on Phaser.

# Q7 Datasets and Code

No new benchmark. Uses GameCraft-Bench (140 tasks) in Godot and Phaser. Released: the implementation, prompts and output contracts, the scoring harness, six playable evolved games on the project page, and a Hugging Face dataset of 51,644 scoring files with per-task scores, judge outputs, and replay reports (`RSIGame/RSIGame-TableArtifacts`). # Q8 Evidence Quality

* **Well supported.**
  * The matched-budget gain over Play2Code is large and consistent on Godot: +7.2 to +13.8 Overall points across five generators, with task-bootstrap intervals above zero and Wilcoxon significance for both Godot generators tested in Table 14. Play2Code adds under 1 point on the strong GPT-5.5 base (50.26 → 50.74) where RSIGame adds 14 (→ 64.53) at lower cost ($0.88 versus $1.06 per task).
  * The internalization claim holds on its own terms: one-shot Qwen3.8-27B rises 37.07 → 48.22 with the nested-corpus ablation attributing gains to planning and improvement traces beyond generation traces (Mechanics +14.9, Depth +14.1), and tokens fall 6.41M → 0.57M.
  * Replay noise is small relative to task variation, cross-judge ordering is stable, and the free-play check addresses the obvious worry that gains are confined to the development-time replay scripts.
* **Weaker than the headline.**
  * The abstract's "exceeding GPT-5.5 one-shot scores" compares a *30-round developed* Qwen SFT game (61.38) against a *one-shot* GPT-5.5 game (50.26); GPT-5.5 plus RSIGame reaches 64.53, so the frontier model still wins like for like. On Phaser the Qwen SFT + RSIGame score (58.53) does edge GPT-5.5 + RSIGame (58.21), but the Qwen3.8-27B Phaser comparison against Play2Code is not significant (+1.55, p = 0.394).
  * The judge, the explorer/test agent, and the SFT student are all Qwen3.8-27B. Cross-judge re-scoring with GPT-5.5 on 40 tasks mitigates but does not eliminate the concern that a Qwen-family judge favors Qwen-family outputs, especially for the SFT rows.
  * Baseline rows report the Qwen3.8-27B one-shot generation at 6.41M billable tokens against 0.26M for GPT-5.5, which suggests the open model's base games cost far more to produce; the paper does not discuss why.
  * The VibeGame comparison is one trial per task with role models set by the authors; the paper itself says it makes "no claim about VibeGame under other models or a larger budget."
  * Multi-stage guidance from a human or stronger model is evaluated only on a limited set of cases (Appendix B), so the "optional guidance" mechanism is largely untested.
* **Reader observation.** The monitor's isolation from the benchmark rubric is well documented, but the monitor's proxy rubric and the benchmark rubric both target the same four dimensions, so some of the gain may come from optimizing a close proxy of the metric rather than from general game quality. The free-play study is the paper's answer, and it is on 20 tasks.

# Q9 Contributions

* A concrete control architecture for long-horizon autonomous development: adaptive direction choice, evidence-grounded editing, replay-based verification, a persistent checklist, best-checkpoint retention, and saturation-aware stopping, with an argument and evidence that the controller rather than the roles or the iteration is what makes rounds convert into quality.
* The first full-benchmark (140-task, two-engine, five-generator) comparison of iterative game-development methods at matched budgets, with unusually complete reliability reporting (paired bootstrap, replay stability, cross-judge, free-play).
* A verification audit quantifying what agentic verification adds: grounded precision 58.6% → 72.3% before editing, 76.2% failure recall after editing where build-only checks detect none.
* Evidence that internalizing planning and verified improvement traces into a 27B model lifts one-shot quality across all four dimensions and cuts generation tokens by about eleven times, with contamination screening documented.
* Released code, prompts, playable games, and 51,644 scoring artifacts.

# Q10 Next Steps

* **Judge independence.** Re-score all 140 tasks, not 40, with a non-Qwen judge, and report the SFT rows separately, since those are where judge-student family overlap matters most.
* **Component attribution.** Ablate the checklist, the verifier, and adaptive direction individually in the main table; Table 2 audits verification quality but does not show its effect on final scores.
* **Stronger iterative baselines.** Run OpenGame's skill accumulation and a tuned VibeGame at the same budget, and add a "Play2Code + best-checkpoint retention" arm to separate the monitor's contribution from the local loop's.
* **Continual RSI.** The paper gestures at repeatedly internalizing new experience; a second SFT round on RSIGame-with-SFT traces would test whether the loop keeps paying or saturates.
* **Larger projects.** Appendix B names larger games with richer assets and cross-system dependencies as open; the checklist's growth and the monitor's cost at that scale are unmeasured.
* **Project fit (reader note).** The best-checkpoint-plus-saturation-stop pattern, with the monitor isolated from the acceptance metric, is directly applicable to any self-improving loop in this repository (skills, harness edits, memory policies) and complements [RRSI](2609.24972.md)'s noise-band acceptance floor.
