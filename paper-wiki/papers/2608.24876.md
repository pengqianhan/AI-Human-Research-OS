# Q1 Problem Definition

* **Input (X):** a frozen LLM policy π_θ, a tool set T, and long-horizon tasks where the agent maintains an interaction history h_t and a working state w_t at each step; a Skill Memory M_k = (E_k, W_k, ρ_k, C_k) — experiential memory of reusable skills, a working-memory specification (state schema and update-proposal logic), an invocation policy (when and which skills reach the model), and a checker set (which observations support a proposed state change).
* **Output (Y):** Recuris, a recursive Experiential-Working Memory architecture. Within a task, a checker-verified working state grounds when and which skill is invoked from experiential memory, and state only advances on observation-confirmed evidence rather than the model's own claim. Across tasks, a fixed Meta-Agent reads the resulting structured execution trace, attributes each diagnosed failure to one of the four memory components, proposes a scoped patch, and a fixed validation gate admits or rejects it against a held-out development split.
* **Core problem:** recursive self-improvement (RSI) is hard in long-horizon tasks because growing histories obscure task state and misalign skill invocation. Existing experiential-memory methods retrieve from the initial instruction (missing needs that emerge later) or search the full interaction history (mixing outdated information, completed steps, and execution noise), and final-outcome-only learning signals give no guidance about *which* memory mechanism — a stored skill, the tracked state, the invocation trigger, or the progress verifier — should be repaired when a run fails.
* **Scope:** the base LLM, tools, Meta-Agent, localization and patching procedures, validation gate, and harness mechanisms outside the memory-control layer M_k are all held fixed throughout every experiment; recursion is confined to that externalized memory-control layer, not the model or the outer improvement procedure.

# Q2 Problem Novelty

Experiential memory and agent skills (Voyager, AWM, ExpeL, Buffer of Thoughts, Dynamic Cheatsheet, Anthropic's Agent Skills format, SkillOpt, SkillComposer) and explicit working-memory state tracking (StateAct, ReflAct, Magentic-One's ledgers, StateFlow, StructAgent) are each active areas the paper builds on rather than originates. Its stated novelty is coupling the two: prior experiential-memory work focuses on *what* to store, with skills either injected as a fixed block or left to the model to invoke on its own — a cited benchmark shows agents often fail to select the right skill unassisted, and injecting an inaccurate skill can actively hurt completion. Prior working-memory work maintains explicit state, but that state is not necessarily *trustworthy*: it is either governed by hand-written rules that generalize poorly off the designed flow, or self-reported by the model itself and vulnerable to omission and hallucination. Two cited systems (AutoGuide, SGDR) do condition retrieval on execution context, but their signal is the raw observation matched by similarity — what the environment currently looks like — rather than a verified record of what the agent has confirmed it has achieved. Recuris separates state *proposal* from state *commitment* via an explicit checker layer, then treats the resulting verified coupling as structured diagnostic evidence for cross-task memory evolution, converting "which of four components should be patched" from an outcome-only guess into an observable, measurable question.

# Q3 Scientific Hypothesis

If (a) a compact, checker-verified working state — not raw dialogue or the model's self-reported progress — grounds *when* and *which* skill is invoked from experiential memory at defined execution events, and (b) the resulting structured trace linking states, invoked skills, actions, and checker-verified outcomes lets a fixed Meta-Agent localize each diagnosed failure to one of four memory components (skills, working-memory specification, invocation policy, checkers) and apply a scoped, validation-gated patch to only that component, then within-task execution should improve — especially on completing tracked required actions rather than merely retrieving relevant knowledge — the resulting evolved memory should transfer to held-out tasks and to models never involved in evolving it, and the advantage should scale with interaction horizon rather than decay, all while the underlying frozen model and outer improvement procedure never change.

# Q4 Related Work and Key People

* **Experiential memory and agent skills.** Voyager stores executable code skills, AWM induces natural-language workflows, ExpeL extracts insights from successes and failures, Buffer of Thoughts and ReasonFlux maintain distilled thought templates, and Dynamic Cheatsheet curates test-time notes; Anthropic's Agent Skills format supplies the standardized representation E_k uses. SkillOpt (already in this wiki) treats skill files as trainable parameters optimized from feedback; SkillComposer learns to create, improve, and merge skills.
* **Working memory for LLM agents.** StateAct and ReflAct have the model write and reflect on structured state; Magentic-One maintains task and progress ledgers; StateFlow constrains execution with a hand-written state machine. StructAgent is the closest prior system — a verifier-backed progress transition — but its verified state feeds only the agent's own next action, with no procedural memory retrieved from it, which is exactly the gap Recuris's EM-WM coupling closes.
* **Recursive self-improvement of LLM agents.** Traces the lineage from the Gödel machine (Schmidhuber, 2003) through scaffold self-application (Zelikman et al.; Fernando et al.), then classifies recent systems by which layer they rewrite — runtime or codebase, workflow graph, tool set, or model weights — positioning Recuris at the narrowest layer, the memory itself, alongside add/update/delete memory systems this wiki's [Agent memory](../topics/agent-memory.md) topic already tracks, Memento (a frozen base model adapting only a case bank), and EvolveMem (evolving memory architecture, gated by aggregate benchmark improvement). Critiques the field's dominant admission signal — the model's own judgment of usefulness, or improvement in one aggregate number — as unable to say *which part* of the agent produced a failing run, citing a failure-attribution benchmark reaching only 53.5% (responsible agent) and 14.2% (decisive step) accuracy over unstructured logs.

# Q5 Key Solution Idea

1. **Skill Memory architecture.** M_k = (E_k, W_k, ρ_k, C_k): experiential memory of reusable skills in Agent Skills format; a working-memory specification defining the state schema and update-proposal logic; an invocation policy deciding at which execution events which skills reach the model; a checker set testing whether an observation supports a proposed state change. A candidate patch revises exactly the components a diagnosis implicates and copies the rest unchanged — scoping is enforced per edit, not per round.
2. **Within-task, state-grounded skill invocation.** A structured working state tracks each goal's content, status (pending, done, or blocked), supporting evidence, and an optional blocker. Invocation fires at defined execution events rather than once from the initial instruction or via full-history search: call-time invocation fires when the agent drafts a state-changing tool call (the draft is intercepted and replaced with a synthetic not-executed result, so the retrieved skill reaches the model before the real action is issued, matched by the tool the call names); boundary invocation fires on a working-state predicate at a turn boundary (e.g., first_turn).
3. **Evidence-grounded state update.** A proposed next state is checked against the actual returned observation via a component-specific completion predicate, and a fixed commit kernel advances the state only on a positive checker verdict — a goal moves from pending to done never on the model's own claim that an action succeeded, only on a matching checker-confirmed observation.
4. **Trace-based cross-task failure localization.** A structured trace Γ_k records the working state, invoked skills, action, and observation at every step, plus the proposed and committed state and checker decisions. A fixed Meta-Agent attributes each diagnosed failure to one of {E, W, ρ, C} — a missing/flawed skill, an omitted goal or bad update proposal, a missed/late/irrelevant invocation, or a false accept/reject — then a fixed patching stage proposes one edit per implicated component, applied together as a single candidate.
5. **Validation-gated admission and bounded recursion.** A fixed gate compares the candidate against the current memory on the failed source task plus a held-out development set of anchor tasks the current memory already solves, admitting only if the candidate repairs the target failure without regressing the anchors; test tasks, trajectories, and scores never enter localization, patching, or admission. Two operating modes follow from this loop: cross-task evolution builds one memory per benchmark, once, from a mid-sized "deployment model"'s own failures, then ships it frozen to other models; test-time adaptation instead rebuilds memory for a single isolated task from that task's own failed trajectory and a hidden verifier's pass/fail bit, retrying under the updated memory until the first success. The paper reports task structure — shared tools, policies, and task families versus isolated tasks — decides which regime applies: on Terminal-Bench 2.1, cross-task evolution admitted no patch across thirteen runs, so only test-time adaptation is evaluated there.

# Q6 Experiment Design

Four long-horizon benchmarks: τ²-Bench Retail (114 tasks) and Airline (50 tasks), dual-control tool-use dialogue scored by an environment verifier requiring full reward, with read-action and required-write recall reported separately; SkillFlow (166 tasks across 20 families sharing an execution flow, binary programmatic verifier) for lifelong skill discovery; and Terminal-Bench 2.1 (test-time-adaptation-only, via the Terminus-2 agent). Ten models — five open-weight (Granite-4.1-3B, Qwen3.5-4B/9B, GPT-OSS-20B, Qwen3.6-27B/35B), three frontier reached through a single proxy (Gemini 3.7 Flash, GPT-5.6 Sol, Claude Opus 5), plus the deployment model doubao-seed-2-0-pro — each run at temperature 0, k=4 independent attempts, with a 200-step and 10-consecutive-tool-error cap. For each benchmark, one Skill Memory is built once, on the deployment model alone, using a fixed Meta-Agent built on Claude Code that only sees failures from the benchmark's own unmodified reference agent — a deliberate single-source design rather than a memory tuned per target model. Three configurations are compared throughout: the base reference agent; Recuris with M₀, a neutral starting memory (isolates what the layer contributes before anything is learned, reported as indistinguishable from zero on four target models in an appendix ablation); and Recuris with the evolved memory. Statistical protocol: paired task-clustered bootstrap 95% confidence intervals, and McNemar's exact test for paired binary contrasts.

# Q7 Datasets and Code

No new benchmark is introduced; the paper reuses τ²-Bench (Retail/Airline), SkillFlow, and Terminal-Bench 2.1 (already tracked in this wiki's [Terminal-Bench](../concepts/terminal-bench.md) concept page) with their own reference agents and verifiers as the evaluation base. Code is released at github.com/Gen-Verse/Recuris (20 GitHub stars per HF metadata at the time of this note, reflecting a same-day arXiv release). Evolve, gating, and held-out splits (16 evolution-visible, 12 gate-screening, 86 fully held-out tasks for the main τ²-Retail line) are fixed before any evolution run and detailed in an appendix this note has not independently read in full.

# Q8 Evidence Quality

This note is built from the full arXiv HTML text of the Introduction, Method (§2, all subsections), Experiments (§3, all subsections 3.1-3.5), Related Work (§4), and Conclusion, fetched directly from arxiv.org/html since `hf papers read` returned only a placeholder page-icon description for this very recent (25 Aug 2026) submission. It has not read Appendices A-E (Statistical Protocol, Harness Ablation, Benchmarks and Splits, Compute and Context, Case Studies) beyond what the main text cites from them, so numeric detail specific to those appendices is not independently verified here. The paper is unusually careful about statistical honesty throughout: it explicitly separates settled gains (confidence intervals excluding zero, marked †) from directional-only results (every τ²-Airline EM-WM-coupling-ablation interval includes zero, which the paper itself reads as "a direction and not an established effect"); reports null results plainly (removing the checkers changes the τ²-Retail pass rate by exactly zero, attributed to "decode noise rather than caused failures"; one evolution run's round-4 candidate is shown to never be invoked on any held-out task, which the paper explicitly distinguishes from a genuine diminishing return); and reproduces its central Meta-Agent result on a second, independently re-implemented agent stack (DeepSeek Harness versus the original Claude Code implementation) specifically to rule out implementation-specific artifacts, finding the two "statistically interchangeable" and mechanistically convergent on the same repair. Headline numbers (35 of 37 model-benchmark pairs improved; +17.8/+15.6 points for GPT-5.6 Sol/Claude Opus 5 on τ²-Retail; 64.8% versus 13.0% fault-localization accuracy) are stated consistently between the abstract and body.

# Q9 Contributions

1. Establishes state-grounded memory use — a checker-verified working state gating skill invocation, rather than retrieval from the initial instruction or the raw interaction history — as a requirement for recursive self-improvement in long-horizon agent harnesses.
2. Recuris, a recursive Experiential-Working Memory architecture coupling persistent skill experience with a dynamically maintained, evidence-grounded task state, enabling execution-event-triggered skill invocation instead of a fixed context block or model-decided retrieval.
3. Shows EM-WM coupling turns harness execution into structured diagnostic evidence: a fixed judge localizes an injected component fault at 64.8% accuracy from the structured trace, versus 37.0% from the raw trajectory and 13.0% (below a 33.3% constant-answer floor) from the outcome alone, enabling component-scoped rather than whole-memory repair.
4. Empirical results across four benchmarks and ten models: task success improves in 35 of 37 completed model-benchmark pairs; the advantage widens rather than decays with interaction horizon (up to +32.2 points on the longest quartile); a memory evolved once, on a mid-sized model, transfers to frontier models never involved in evolving it (+17.8/+15.6 points for GPT-5.6 Sol/Claude Opus 5 on τ²-Retail); and gated updates preserve prior capability (4 of 42 anchor-task regressions versus 25.9% for an unchanged package re-run under identical noise, p=0.013).

# Q10 Next Steps

The paper's own reported open threads: which memory component is critical is domain-dependent and cannot be fixed at design time — on τ²-Airline write-review is critical and the status board is inert, while on τ²-Retail the pattern exactly reverses (a "double dissociation") — which the paper argues is precisely why a fixed, unconditional allocation of repair effort would be wrong somewhere, motivating reading the repair target off the trace instead of committing to it up front. The evolved memory only grows across the reported lineage (51 skills added, 2 revised, 0 deprecated, with 17 near-duplicate pairs surviving into admitted versions), and the paper states a pruning operator is "a natural addition to the update set" it has not yet implemented. On Terminal-Bench 2.1, the paper's own decomposition shows the attempt-budget/retry effect (+26.4 points) dominates the learning effect from test-time adaptation itself (+2.3 points, interval including zero, though seven tasks are solved only under adaptation and by no other configuration); the paper is explicit that its per-attempt reliability numbers still contain zero in every interval at the tested sample size — a direction rather than an established effect there.

This note adds one connection beyond the paper's own framing: the domain-dependent "critical component" finding above is a within-agent instance of the same problem [Graph Engineering](2608.21156.md) raises at the multi-agent-system level — that no fixed, design-time allocation of structure (there, task/team/state-graph topology; here, which of four memory components to trust) survives contact with which failure mode actually occurs, and both papers respond by making the allocation a runtime, evidence-driven decision rather than a static design choice.
