# Q1 Problem Definition

* **Input (X):** for the search phase, execution trajectories produced by a separate agent running the base harness (Pi) over two disjoint families of executable environments — 495 repository-derived tasks (GitHub issue + pre-fix repository state + hidden regression test, kept only when that test fails before the accepted patch and passes after) and 40 verifier-driven synthetic tasks (an executable success verifier built first, allowing multiple valid solution paths, in a Terminal-Bench-2-style interface) — 535 environments total. For held-out evaluation, the input is a frozen harness plus four separate benchmark surfaces: EdgeBench's 51 publicly released tasks (of 134 total), 63 CPU-only Terminal-Bench 4 tasks, 6 IMO 2026 problems requiring Lean 4-verified proofs, and a kernel-optimization "take-home" benchmark run as a 20-worker agent swarm.
* **Output (Y):** SoL-Pi, a fixed set of four mechanisms (Action Fusion, Online Context Compact, ObservationPack, Evidence-Preserving Reducer) implemented as extensions to the open-source Pi harness; per-task recorded token traffic broken into input/cache-read/cache-write/output/total (in billions of tokens), API cost in USD at a fixed August 17, 2026 price snapshot, average task score, and a derived token-efficiency metric (API cost per unit of aggregate task score).
* **Core problem:** as coding agents run unattended over long, tool-mediated trajectories rather than single-turn completions, token cost scales with trajectory length, and existing efficiency work (faster attention kernels, quantization, cheaper models) operates below the harness layer. Harness-level changes are a plausible efficiency lever, but harness components (tool use, context management, verification, delegation, recovery, termination) are tightly coupled, so a locally beneficial change can shift cost downstream or break capability; manually finding such changes does not scale, and a cited prior study (Wang et al. [20], "Rethinking the evaluation of harness evolution for agents," arXiv:2607.12227) found that automatically evolved harnesses can overfit the tasks used during search and yield only marginal held-out gains. The problem SoL-Pi addresses is therefore how to run automated harness discovery at scale that both reduces token/cost and demonstrably transfers to held-out tasks and an unseen model backend, rather than overfitting to search-time signal.
* **Scope:** harness-level changes only — model weights are fixed throughout; all four mechanisms are built as extensions to one specific open-source harness (Pi / pi-mono, Earendil Works); development and search were run on one backend (GPT-5.6 Sol), with cross-backend transfer tested against exactly one other backend (Claude Opus 5) and no third model family; held-out evaluation covers EdgeBench's public 51/134 tasks, 63 (GPU-excluded) Terminal-Bench-4 tasks, 6 IMO 2026 problems, and one kernel-optimization swarm experiment — not a broad multi-benchmark or multi-backend sweep, and the paper itself states its search-scale numbers ("∼150 proposed directions and ∼500 executable environments... more than 3,000 runs") "do not establish a scaling law."

# Q2 Problem Novelty

The paper does not claim to originate automated harness search, RSI-inspired agent design, or held-out-generalization concerns for harness evolution. It explicitly builds on Meta-Harness (Lee et al., arXiv:2603.28052 — searches executable harness programs and evaluates transfer to held-out datasets/models via a Pareto frontier over task performance and context cost) and Recursive Harness Self-Improvement / RHI (Lee et al., arXiv:2607.15524 — iteratively refines prompt-level specifications of the agent loop for individual tasks); it also cites AutoHarness (Lou et al., arXiv:2603.03329 — synthesizes environment-specific code guards or complete code policies), Agentic Harness Engineering / AHE (Lin et al., arXiv:2604.25850 — evolves modular coding-harness components from trajectory evidence and evaluates cross-task/cross-model transfer), and MemoHarness (Huang et al., arXiv:2607.14159, already in this wiki as [MemoHarness](2607.14159.md) — stores execution experience and adapts harness configuration to individual test cases at inference time). Its stated novelty is a direct response to Wang et al.'s [20] overfitting finding: rather than another search algorithm over harness code, SoL-Pi's contribution is architectural — a broad-to-deep funnel (breadth: ~150 outer-loop proposal directions across ~500 environments; depth: a per-candidate propose-implement-review-revise loop) built around a structural rule that held-out results never feed back into search (a failed EdgeBench validation simply rejects the candidate rather than triggering further tuning), plus scalable orchestration through disposable, isolated search lineages (each a throwaway copy of a shared minimal-research-loop skill template, discarded after the run except for the retained candidate and evidence). This differs from MemoHarness's per-case, feedback-free test-time adaptation and from this wiki's other harness-engineering papers (e.g., SkillOpt-Lite's human-gated patch-and-rollback loop) by making the search/validation separation itself the object under test, and by targeting token efficiency specifically as a first-class, gated optimization objective rather than task success alone.

# Q3 Scientific Hypothesis

If harness-level auto-research is scaled across a broad, diverse pool of proposal directions and executable environments, with (a) capability and efficiency metrics and tolerances fixed and kept outside the optimizing agent's control before search begins, (b) a strict two-gate acceptance rule (capability within a predeclared tolerance, and improvement on at least one declared efficiency metric), and (c) held-out evaluation results structurally prevented from feeding back into search, then the resulting harness mechanisms should reduce token traffic and cost substantially while preserving task capability within a small tolerance, and — critically — should transfer to a benchmark and model backend never used during search, rather than overfitting the way Wang et al. [20] document for other harness-evolution methods. The paper's own evidence: on EdgeBench, the frozen four-mechanism SoL-Pi (called SoL-Pi [Efficiency]) cuts total recorded token traffic by 49.0% and API cost by 33.2% while retaining 93.7% of Pi's average score on its GPT-5.6 Sol search backend, and — applied to Opus 5 with no further search or adaptation — cuts token traffic by 44.7% and cost by 33.5% while retaining 94.3% of Pi's average score on that unseen backend (Sec. 3.1, Tables 1–2).

# Q5 Key Solution Idea

1. **Broad-to-deep search funnel with hard search/validation separation (Sec. 2.1–2.2).** Capability metrics, tolerances, and efficiency metrics are fixed before search and kept isolated from the optimizing agent's control to prevent gaming. Candidate selection applies two sequential gates — every capability metric must stay within its predeclared tolerance, and the candidate must improve at least one declared efficiency metric — and among gate-passing candidates the pipeline retains the nondominated (Pareto) results. EdgeBench is reserved entirely for final validation: the harness and acceptance rule are frozen before evaluation, and a failed held-out validation simply rejects the candidate without triggering further optimization.
2. **Six proposal families seeding 152 outer-loop directions**, preceded by an "Oracle Analysis" pass over existing development trajectories to surface concrete, avoidable sources of overhead in the base harness: context, progress, tools, delegation, prompt and policy, and improvement and evaluation. The families classify hypotheses by origin, not by where the eventual change lands — e.g., ObservationPack originated from two context-family hypotheses but ultimately modifies the observation boundary. Each direction runs an autoresearch cycle (propose → implement → run a fixed experiment → inspect → retain/revise/discard, credited to Karpathy's "Autoresearch: the experiment loop"), extended with an iterative implementation loop based on Anthropic's "Ralph Wiggum" Ralph Loop pattern: an implementer refines the candidate against an explicit completion criterion, an independent reviewer checks it, and failed reviews trigger revision. Independent trajectory analyzers (one per exploration trajectory, checking for repeated actions, context growth, large observations, or sparse diagnostic signals) feed a reducer that synthesizes a candidate-level summary guiding the next proposal round.
3. **Disposable, isolated search lineages.** Each independent search runs as a throwaway instance of a shared skill template containing a minimal research loop and operating instructions; each experiment copies the template, sets its parameters, runs to completion, and retains the candidate and its evidence while discarding the modified orchestration code — the "scalable orchestration" principle that lets breadth scale by running more isolated loops without coupling failures across candidates.
4. **Two disjoint search-environment families, kept separate from the 51-task EdgeBench held-out set** (Sec. 2.3): 495 repository-derived environments (GitHub issue + pre-fix repository state + offline dependencies, using the accepted patch/history as a reference trajectory, with the PR and regression test hidden from the agent and retained only when that test fails before the patch and passes after) and 40 verifier-driven synthetic environments (an executable success verifier is authored first, then a task environment is built around it, permitting multiple valid solution paths under a Terminal-Bench-2-style interface). Of EdgeBench's 51 tasks, 11 are used only for one-way acceptance of already-frozen candidates and 40 are reserved purely for final generalization evaluation.
5. **The four retained mechanisms, each targeting a different stage of the agent-environment loop (Sec. 2.4–2.5):**
   * *Action Fusion* — Base Pi often edits a file, then issues a separate command to test, build, or run it; Action Fusion adds an optional follow-up-command field to file-mutation tools so both actions are issued as one request and their outcomes returned in a single observation, cutting the round trip from 3 API calls to 2. Commands that require inspecting the mutation's result first remain separate.
   * *Online Context Compact* — Reconsiders compaction at each plan-step completion (tracked via the agent's own `update_plan` calls) rather than only at a fixed context-fill threshold. At each boundary the harness estimates remaining model requests from observed requests-per-completed-step and the count of unfinished steps, caps that estimate by the requests that would fill the context window at the observed growth rate, and compares projected input-token savings against the estimated cost of rewriting the prompt cache; later compactions require a larger margin to account for unrecovered rewrite cost from earlier compactions. Pi's native compaction is invoked when this cost gate passes, or when context usage nears the window limit and compaction would still shorten it.
   * *ObservationPack* — Archives tool outputs over 10 KiB locally and sends them in full for the next two provider requests; from the third request onward it substitutes a stable retrieval handle, the original size, and a short excerpt of complete head/tail lines, with exact content retrievable on demand. Smaller outputs are untouched.
   * *Evidence-Preserving Reducer* — For build/test logs of at least 4 KiB from a predefined command set (file reads and search results bypass it entirely), archives the exact output and has a separate low-cost model (GPT-5.6 Luna at "high" effort) extract a compact "receipt." A deterministic verifier checks the receipt's schema, source hash, exit status, exact quotes, and size before use, falling back to the untouched original if verification fails, credentials are suspected, or the receipt yields no size reduction. The reducer runs before ObservationPack, which recognizes the reducer's receipt marker and skips those results so verified evidence is not doubly compressed; the auxiliary model only extracts evidence, while the main agent retains responsibility for diagnosis and action selection.

# Q6 Experiment Design

**EdgeBench (Sec. 3.1, Tables 1–2).** EdgeBench publicly releases 51 of its 134 total tasks; evaluation uses this public subset. Table 1 compares eight configurations under GPT-5.6 Sol: an unranked EdgeBench-official GPT-5.5 reference row, native Codex, four third-party harnesses (OpenSquilla, Oh-My-Pi, OpenCode, Oh-My-Opencode), Pi, SoL-Pi [Efficiency] (the fixed complete four-mechanism stack), and SoL-Pi [Performance] (the single-mechanism configuration with the highest average score for that backend, selected from the Table 4 ablation — ObservationPack under GPT-5.6 Sol). Table 2 repeats the comparison for cross-model transfer: the GPT-5.6-Sol-developed SoL-Pi [Efficiency] is applied to Claude Opus 5 unmodified (no further search or adaptation), against native Claude Code and Pi on that backend; SoL-Pi [Performance] on Opus 5 corresponds to Action Fusion instead of ObservationPack.

**Terminal-Bench 4 and IMO 2026 (Sec. 3.2, Table 3).** Codex, Pi, and SoL-Pi are compared on 63 CPU-only Terminal-Bench 4 tasks (GPU-dependent tasks excluded for infrastructure reasons), reporting solved-task count, total API cost, and cost per solved task. The same three harnesses are compared on the 6 IMO 2026 problems using GPT-5.6 Sol at "xhigh," with each solution required to be formalized and verified in Lean 4 (via AxiomMath/IMO2026's formal statements and Humanfia's verification setup), capped at 150 minutes per problem.

**Kernel-optimization agent swarm (Sec. 3.3, Fig. 5).** A multi-agent experiment on Anthropic's "original performance takehome" kernel-optimization benchmark, scored in simulated machine cycles (lower is better). Three configurations, one two-hour run each, all starting from the same frozen 147,734-cycle starter with fresh sessions and no carried-over notes: a single Codex agent; a Codex coordinator with 20 Pi-baseline workers; and a Codex coordinator with 20 SoL-Pi workers (all four mechanisms). Coordinators and the single agent use GPT-5.6 Sol at "xhigh"; workers use GPT-5.6 Luna at "xhigh." Workers form five groups of four with independent workspaces and a shared per-group evidence board; the coordinator relays findings across groups, and the shared best result updates only when the coordinator submits an immutable candidate snapshot that independent verification confirms as a strict improvement.

**Ablation and activation analysis (Sec. 3.4, Table 4, Figs. 6–7).** An add-one evaluation isolates each mechanism's standalone contribution (Pi baseline + one mechanism, vs. the complete stack) under both backends, plus a trigger-rate (fraction of tasks where a mechanism activates) and trigger-intensity (mean activations per triggered task) analysis, and a standalone-vs.-full-stack comparison of each mechanism's own token-efficiency gain on its own triggered-task subset (explicitly caveated by the paper as descriptive, not an isolated interaction-effect measurement).

**Case study (Sec. 3.5, Fig. 8).** The 27-iteration development lineage of Action Fusion is traced across four stages (oracle analysis, baseline construction, prompt/tool-schema optimization spanning 18 explorations, final held-out validation), including the agent's own introduction of "trigger rate" as an intermediate acceptance metric alongside task score.

**Design strength for the hypothesis.** The EdgeBench cross-backend transfer test (Table 2) and the Terminal-Bench-4/IMO-2026/kernel-swarm evaluations are the paper's most genuine generalization tests, since the harness, metrics, and acceptance rule were frozen before all of them. A real asymmetry worth flagging for hypothesis coverage: on Terminal-Bench 4, SoL-Pi actually solves fewer tasks (15/63) than both Codex and Pi (18/63 each), so its cost win there ($211.12 vs. Pi's $286.45 total, $14.07 vs. $15.91 per solved task) comes alongside a real capability shortfall, not just a within-tolerance trade-off as on EdgeBench. On IMO 2026, Codex actually passes more problems (5/6) than either Pi or SoL-Pi (3/6 each); SoL-Pi's win there ($20.90 vs. Codex's $22.89 per passed problem) is a cost advantage over an equally-capable-on-this-metric peer (Pi), not a capability-plus-cost win over Codex.

# Q9 Contributions

1. SoL-Pi, a fixed four-mechanism extension of the Pi coding-agent harness (Action Fusion, Online Context Compact, ObservationPack, Evidence-Preserving Reducer), discovered through a broad-to-deep, search/validation-separated auto-research loop, cutting EdgeBench recorded token traffic by 44.7–49.0% and API cost by about one third while retaining 93.7–94.3% of Pi's average task score across two model backends (GPT-5.6 Sol, the search backend, and Opus 5, held out entirely from search).
2. A structural answer to Wang et al.'s [20] generalization critique of automated harness evolution: held-out EdgeBench results are architecturally prevented from feeding back into search, the harness and acceptance rule are frozen before evaluation, and search runs as disposable, isolated lineages — demonstrated to transfer both to an unseen model backend (Opus 5, no further search or adaptation) and to different task distributions entirely (Terminal-Bench 4, IMO 2026, a kernel-optimization agent swarm), though with real capability trade-offs on two of those three transfer benchmarks (Q6, Q8).
3. Evidence that independently search-discovered mechanisms remain net-beneficial when merged: every one of the four mechanisms reduces total token count under both backends standalone, and the merged stack has the lowest total token count and cost in both backend blocks (Table 4); a documented case (Action Fusion, Sec. 3.5) of the auto-research process itself inventing an intermediate acceptance metric ("trigger rate") not specified in advance.
4. A worked demonstration that harness-level efficiency gains compound at the multi-agent level: a 20-worker SoL-Pi swarm on a kernel-optimization task reduces API cost by 26.8% relative to an equivalent 20-worker Pi swarm under the same two-hour budget, while passing all 8 of 8 speed thresholds the Pi swarm narrowly misses one of (7/8) — though the single Codex agent alone remained the cheapest of the three configurations overall.

# Q10 Next Steps

The paper's own stated limitations (Sec. 5.1): **Pre-Training the Harness** — generalizing harness artifacts discovered via RSI-style search "remains a persistent challenge"; the authors frame scaling both executable environments and idea diversity as a hypothesis they plan to keep testing, drawing an explicit analogy to model pretraining, not a settled result. **Multi-Backend Training** — the harness was updated only from GPT-5.6 Sol trajectories, and on Opus 5 the mechanisms trigger less often and less intensely (Fig. 6), though still net-beneficial when triggered; the authors propose training and validating across multiple backends jointly as future work to improve robustness. **Recursive Efficient Improvement** — the idea that a cheaper harness could fund a larger next research cycle (lower per-run cost letting a fixed budget cover more environments, trajectories, and ideas) is explicitly named as "a long-term research vision rather than a compounding effect demonstrated by the present study"; the authors state they plan to use SoL-Pi itself as the starting harness for their next research cycle. **Search Coverage and Cost** — running complete auto-research loops is computationally expensive, which the authors say makes controlled breadth-vs-depth-under-fixed-budget comparisons "particularly challenging," and they explicitly leave scaling-law-style investigation of search breadth and depth to future work.

Beyond the paper's own list, three points are worth flagging for a reader assessing this note's evidence. First, the Terminal-Bench-4 capability shortfall (15/63 solved vs. 18/63 for both Codex and Pi) is reported transparently in Table 3 but not discussed as a limitation in the prose — a reader relying only on the abstract's "performance comparable to Pi" framing should weight this real regression on a non-EdgeBench benchmark. Second, the cross-backend transfer claim rests on a single backend pair (GPT-5.6 Sol → Opus 5); no third model family (e.g., an open-weight model, or a model from a different lab than either search or held-out backend) is tested, so "transfers to an unseen backend" should be read narrowly. Third, the kernel-optimization swarm result (Sec. 3.3) is a single two-hour run per configuration with no repeated-trial variance reported, so the 26.8% cost reduction and the 7/8-vs-8/8 threshold outcome could plausibly be sensitive to run-to-run variance the paper does not quantify — a natural follow-up would be to repeat that specific experiment across multiple seeds before treating its magnitude as precise.
