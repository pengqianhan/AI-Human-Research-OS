# Q1 Problem Definition

The paper asks how an agent system can complete long-horizon, open-domain information-seeking tasks without losing track of what has been found, what remains missing, which claims have evidence, and which search paths have already failed. The input is a natural-language request that may require discovering an unknown set of entities and attributes across sources; the output is a structured report whose individual values are linked to source URLs and anchored excerpts.

The motivating failure is not merely weak web search. In single-agent systems, plans, progress, evidence, and failures remain buried in a growing interaction history. Adding parallel workers does not fix this by itself: workers can duplicate searches, disagree about target fields, or leave execution capacity idle behind a slow task. SearchOS therefore treats search progress as system-maintained state rather than something each model must repeatedly reconstruct from conversation.

# Q2 Problem Novelty

Structured search and table completion are not new, and orchestrator–worker multi-agent systems already decompose work. The paper's stronger move is to combine relational schema completion with fine-grained citation grounding, dependency-aware frontier tasks, an evidence graph, an explicit coverage map, failure memory, continuous slot refilling, and middleware-enforced execution controls.

This matters because ordinary table completion exposes missing cells but does not by itself represent task dependencies, conflicts, provenance, failed attempts, or whether the discovered row set is exhaustive. SearchOS makes these intermediate objects durable and shared, so completeness and recovery can be inspected and scheduled instead of inferred from prose history.

# Q3 Scientific Hypothesis

The central hypothesis is that if open-domain search is represented as grounded relational schema completion and its evolving state is externalized into shared, role-specific views, then multiple agents can reduce omissions and repeated work while producing more complete cited answers.

The paper also tests two narrower mechanism hypotheses: continuously refilling released execution slots should reduce batch-straggler idle time, and hierarchical search skills plus middleware interventions should redirect unproductive trajectories while reducing exploratory tool use. These mechanisms are evaluated separately, although the full SOCM state design is not decomposed into a component-by-component ablation.

# Q4 Related Work and Key People

The paper connects four lines of work:

* **Agentic information seeking:** WebGPT, ReAct, search-policy optimization, deep-research agents, and structured broad-search systems.
* **Structured information collection:** WideSearch, GISA, WebShaper, A-MapReduce, Web2BigTable, and Table-as-Search, which make broad retrieval measurable through tables or structured outputs.
* **Multi-agent orchestration and memory:** AutoGen, MetaGPT, ChatDev, task-graph execution, reflection memory, MemGPT, and proactive context management.
* **Agent harness engineering:** middleware, operating-system abstractions, runtime constraints, tool interception, context preparation, and execution observability around the model.

The fourteen authors are affiliated with the Gaoling School of Artificial Intelligence at Renmin University of China and Ant Group. Ji-Rong Wen and Zhicheng Dou anchor the information-retrieval lineage; researchers working on broad information seeking, table-oriented search, agent memory, runtime governance, and harness engineering are the most direct audience. The strongest likely critiques concern Max@3 reporting, incomplete causal separation of system components, and whether schema coverage faithfully measures open-set completeness.

# Q5 Key Solution Idea

SearchOS models a request as a set of relational tables with attributes, primary keys, and foreign-key relations. It must discover entity rows, fill a value matrix, and maintain a same-shaped citation matrix that binds each value to a URL and excerpt.

Search-Oriented Context Management (SOCM) keeps four durable shared structures:

1. **Frontier Task** stores task type, status, priority, dependencies, target cells, assignment, and retry count; active target-cell overlap is rejected.
2. **Evidence Graph** stores atomic values, sources, excerpts, schema bindings, confidence, provenance tiers, and support/conflict/refinement relations.
3. **Coverage Map** materializes each known cell as missing, filled, uncertain, or unreachable and preserves conflicts rather than overwriting them.
4. **Failure Memory** records repeated or uninformative queries, inaccessible sources, failed skills, rejected claims, and corrective guidance.

An orchestrator plans and reprioritizes schema gaps; explore agents identify rows and sources; search agents gather scoped evidence; an optional writer produces the cited report from a structured outline. Agents receive role-specific projections of the current state rather than the entire workspace. Continuous dispatch refills an execution slot as soon as a worker finishes. A Search Tool Middleware Harness injects state, extracts and anchors evidence, detects loops and budget exhaustion, and updates SOCM through locked read–modify–write operations. Hierarchical skills separate global orchestration playbooks, source-independent search strategies, and source-specific access procedures.

# Q6 Experiment Design

The evaluation uses two open-domain benchmarks:

* **WideSearch:** 200 manually curated English and Chinese questions across more than 15 domains, each requiring a large table of verifiable atomic facts.
* **GISA:** 373 human-written queries in item, set, list, and table formats, combining multi-hop reasoning with cross-source aggregation.

SearchOS uses GLM-5 for agent roles and Qwen3.5-35B-A3B for evidence extraction. Each case is run three times and reported as the best run (`Max@3`). Default limits are 50 orchestrator iterations, eight concurrent sub-agents, 20 searches per sub-agent, and 1,800 seconds. Baselines include ReAct and Plan-and-Solve as single agents and A-MapReduce, Web2BigTable, and Table-as-Search as multi-agent systems.

The paper reports item- and row-level precision, recall, and F1, plus exact match and GISA format-specific F1. Additional studies compare autonomous schema planning with matched fixed schemas on 40 questions, continuous scheduling with batch barriers over 30 trajectories per policy, three illustrative middleware-intervention traces, and the full hierarchical skill stack against a no-skills setting.

# Q7 Datasets and Code

The paper does not introduce a new benchmark dataset. It evaluates on WideSearch and GISA and uses their deterministic structured-output scoring protocols.

The implementation is open source at [antins-labs/SearchOS](https://github.com/antins-labs/SearchOS). The paper also supplies role-specific tool interfaces, an executable access-skill example, SOCM state examples, and selected trajectory case studies. These materials improve inspectability, but the sources used for this note do not establish that every benchmark run, raw score, and environment snapshot needed to reproduce all tables is packaged in a versioned release.

# Q8 Evidence Quality

SearchOS leads all six headline F1 metrics reported across the two benchmarks. On WideSearch it reaches 80.3 item F1 versus 76.0 for the strongest baseline and 56.5 row F1, two points above the next-best system. On GISA it reaches 76.5 set F1 versus 63.1, 76.9 table item F1, 59.7 table row F1, and 68.1 list F1.

The mechanism studies align with the design claims. Autonomous schema planning exceeds an oracle that selects the better of fixed single- and multi-table schemas by 8.2 item-F1 and 7.7 row-F1 points on the 40-case subset. Continuous scheduling reduces mean end-to-end time by 24.3% across 30 trajectories per policy. Enabling all skill layers raises item F1 by 2.0 and row F1 by 3.4 while reducing session time by 36.6%, search calls by 39.1%, and page calls by 42.7%.

The evidence boundary is important. Main results are `Max@3`, so they measure best-of-three capability rather than expected single-run reliability. The skill study disables all layers together and cannot attribute gains to one layer. The middleware analysis shows three selected trajectories recovering after intervention, which is mechanism-level illustration rather than an aggregate causal estimate. Coverage applies to materialized known rows; the paper explicitly requires row-set audits because 100% known-cell coverage can still miss entities. Finally, the evidence-extraction model is a shared component whose independent error rate is not isolated.

# Q9 Contributions

1. Formalizes open-domain information seeking as relational schema completion with a citation matrix for independently verifiable values.
2. Introduces SOCM as durable shared task, evidence, coverage, and failure state with role-specific projections.
3. Applies continuous pipeline-style dispatch to heterogeneous agent tasks, avoiding synchronized batch barriers.
4. Moves evidence extraction, state injection, loop detection, and budget enforcement into a middleware harness rather than relying on agent memory.
5. Organizes reusable search knowledge into orchestration, strategy, and source-access skills, including typed executable access tools.
6. Demonstrates strong completeness-sensitive results on WideSearch and GISA while reporting efficiency-oriented scheduling and skill ablations.

# Q10 Next Steps

The paper names broader domains, multimodal search, and better adaptation across agents, sources, and tasks as future directions. The sharpest research questions are more structural:

* How can an open-set system estimate missing rows rather than only missing cells in already discovered rows?
* Which SOCM component contributes which quality, latency, and recovery gain under matched budgets?
* How robust is evidence extraction to entity ambiguity, temporal qualifiers, unit normalization, and conflicting authoritative sources?
* When does relational schema completion become a harmful inductive bias for explanatory, theoretical, or genuinely exploratory questions?
* How should a shared state store scale beyond locked file updates without weakening provenance or recoverability?
* Can learned or cross-run skills transfer without importing stale, task-specific, or source-specific failure patterns?
