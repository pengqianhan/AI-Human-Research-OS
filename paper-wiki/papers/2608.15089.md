# Q1 Problem Definition

* **Input (X):** a long-horizon CLI-agent task, a frozen foundation model (GPT-5.5, GPT-5.6 variants, or DeepSeek-V4-Flash) operating through an existing agent harness (Codex), and a versioned YAML runbook defining states, transitions, hooks, and checks for the target task family.
* **Output (Y):** a completed or terminally-recorded task run, produced by the same model but executed through StateM's control layer, plus (across experiments) an evolved runbook that encodes selected postmortem lessons as persistent, executable preconditions and practices.
* **Core problem:** long-horizon agents fail even when the underlying model can solve each constituent step — they lose track of mutable state, fail to reactivate lessons from earlier executions, skip known procedures, or stop prematurely. Can improving the surrounding execution system (the "harness") — rather than the model — recover much of this apparent capability gap, and how far does the resulting control profile transfer across model generations, providers, and task families?
* **Scope:** single-agent control flows for long-running CLI agents (Codex, Claude Code); the runtime requires no model fine-tuning or access to internals; role-isolated multi-agent runtimes are explicitly left to future work.

# Q2 Problem Novelty

Stateful/graph-based orchestration (StateFlow, LangGraph) and harness-adaptation methods (Agentic Harness Engineering, Life-Harness, Self-Harness, "Better Harnesses, Smaller Models") both already exist. StateM's novelty is combining them differently: rather than making the developer-authored graph the primary control artifact (with the agent invoked inside its nodes), StateM keeps a general-purpose CLI agent as the primary executive and exposes state, transitions, hooks, and checks as a shared, agent-and-user-editable runbook operated through the agent's own ordinary CLI action space. The paper frames its contribution as three properties not usually combined in one system: state boundaries as both refreshed context and enforceable transition contracts; the agent (not decomposed node-local calls) remains the primary executive; and the runbook is a jointly inspectable, auditable, machine-operable artifact for both agent and user.

# Q3 Scientific Hypothesis

If a control layer externalizes mutable execution state as phase-level states with checked, logged (but not fully transactional) transitions, refreshes phase-local context on entry, and accumulates selected postmortem lessons as versioned practices in a shared, agent-and-user-editable runbook, then (1) holding model weights fixed, this harness scaling recovers a model-generation-sized capability gap on long-horizon tasks; (2) the resulting control profile transfers with zero modification across nearby model generations within a provider family; (3) across a provider boundary, exact-profile transfer fails but the runtime, runbook structure, and development methodology remain reusable, making cheap re-adaptation possible; and (4) task-side generalization to a new task family depends on matching the control profile to that family's actual execution-boundary structure, not on adding more procedure. The paper tests all four claims on Terminal-Bench 2.1 and BusinessBench but explicitly does not isolate the state-machine runtime's contribution from the evolved, benchmark-adapted control profile's content (Section 4), nor test role-isolated multi-agent runtimes.

# Q4 Related Work and Key People

* **Stateful/graph-based orchestration:** StateFlow (state-driven task solving), LangGraph (persistent state, conditional edges, checkpointing, human-in-the-loop). StateM differs in default execution abstraction: the control artifact stays inside the executing agent's normal tool environment rather than externalizing the agent into controller-owned graph nodes.
* **CLI agents and soft control:** Codex, Claude Code — provide plans/checklists/hooks but these remain soft, natural-language, or lifecycle-event-attached rather than one authoritative, transition-aware execution state.
* **Longitudinal agent reliability:** AgingBench (compression/interference/revision/maintenance aging over many sessions) — complementary rather than overlapping: AgingBench diagnoses reliability degradation across an operational lifespan, while StateM controls procedural state within and across individual long-running executions.
* **Harness adaptation/self-improvement:** Agentic Harness Engineering, Life-Harness, Self-Harness, "Better Harnesses, Smaller Models" (Yang et al. 2026, whose BusinessBench StateM also evaluates on). StateM's distinguishing artifact is an explicit state-machine runbook (states, transition conditions, hooks, repair paths, history) directly operable by the executing agent, serving simultaneously as runtime control, an audit surface, and a failure-driven-optimization search space.
* **Authors:** Ziheng Qin, Yaxin Lu (equally-first, core contributors), Zhangyang "Atlas" Wang, Kai Wang — independent/personal-time project, not attributed to any institution in the paper (explicit disclaimer that the work does not reflect any affiliated organization's views).

# Q5 Key Solution Idea

1. **States as context-and-contract boundaries.** A runbook `Σ = (S, s_0, T, τ, δ)` defines phase-level states (not single model calls). Entering a state runs an `in_hook` (setup, context loading, progress refresh); the agent works freely inside the state; leaving requires `before_transfer` checks to pass, then an `out_hook` persists progress. Checks range in evidentiary strength from host-evaluated command/predicate checks to manual/checklist/message self-attestation to `llm_review` semantic judgment — the framework explicitly does not treat a structured field as proof merely because it exists.
2. **Checked, logged, recoverable (not transactional) transitions.** `goto TARGET` runs an ordered protocol: verify the edge exists → evaluate `before_transfer` checks → run persistence/`out_hook` → evaluate edge guards/transfer hooks → commit and log only if all pre-commit steps succeed → run the target state's `in_hook`. A failed check keeps the run in the source state, visible and repairable, rather than silently propagating.
3. **Per-run recovery record.** Each execution has its own mutable state (run id, current state, transition history, hook/check outcomes, evidence references) separate from the reusable runbook, giving a restarted or compacted agent an explicit phase and obligation set to resume from — without ACID-style rollback of arbitrary external side effects.
4. **Shared, jointly-editable control surface with bounded self-modification.** The agent can register additional run-local dynamic checks when the runbook permits it, but weakening or deleting existing invariants/permissions requires a privileged policy decision; base runbooks are frozen before cross-model evaluation so runbook evolution isn't conflated with evaluation-time adaptation. Stop-hook integration for Codex/Claude Code returns unmet obligations to the agent instead of allowing premature termination.
5. **Failure-driven harness optimization as selective procedural memory.** Failures are attributed to one of three gaps — epistemic (missing knowledge, addressed by `in_hook` context refresh), procedural-compliance (an active procedure not completed, addressed by checked transitions), or procedural-memory (a lesson from a prior run not retained, addressed by versioned practices). The paper stresses that experience must be filtered before becoming memory: BusinessBench iterations show generic/excessive procedure can *hurt* a family (RefactorBench, WooCommerce) until the control is narrowed to the actual invariant boundary, and Attendance-Payroll shows abstaining from any StateM workflow can be the correct decision.

# Q6 Experiment Design

**Terminal-Bench 2.1** (89 tasks, 5 trials/task = 445 trials/run): profile developed with GPT-5.5 xhigh under Codex, then *frozen* (no target-model-outcome-driven changes) before evaluating GPT-5.6 Sol xhigh, GPT-5.6 Luna, and DeepSeek-V4-Flash — testing fixed-model lift, frozen within-family transfer, and adapted cross-provider transfer as three progressively stronger empirical regimes. The DeepSeek run additionally undergoes an explicit adaptation phase (<$38) after first measuring frozen-transfer failure. Cost accounting separates realized API charges (final-evaluation and adaptation) from the pipeline's API-equivalent model-cost estimate. **BusinessBench** (Yang et al. 2026, run with Codex + GPT-5.6 Luna): one profile per treated task family (6 of 7 families; Attendance-Payroll abstained), developed on a development split and frozen before the *first* held-out evaluation (macro/micro averages); later refinements are reported separately as post-evaluation diagnostic validation, not blended into the untouched one-shot numbers. An operational-endurance case study reports one 22-hour continuous profile-development run to test whether the durable StateM record survives context refresh/compaction/stop-hook continuation.

# Q8 Evidence Quality

The headline numbers are strong and specific: GPT-5.5 xhigh + StateM reaches 92.1% vs. an 83.1% reference (+9.0 pts, closing to within range of the *next-generation* 91.9% Sol Ultra reference); the frozen runbook applied unmodified to GPT-5.6 Sol xhigh records 95.28% raw (424/445, "95.3%" at one decimal) vs. an 84.9% reference (+10.4 pts). The paper is unusually transparent about the fragility of this top number: it is a pre-adjudication, unmerged public submission (PR #142, open as of writing), and the authors themselves disclose that scoring 4 identified reward-hacking-adjacent trajectories as zero drops it to 94.38%, and scoring all 9 flagged trajectories as zero drops it to 93.26% — they explicitly report 95.28% "only as a raw public submission score," a rare and creditable level of self-flagged adjudication sensitivity. The cross-provider transfer result is honestly negative-then-positive: the frozen GPT profile applied directly to DeepSeek-V4-Flash *drops* accuracy (82.7%→82.0%), and only the explicit, costed adaptation phase (<$38) recovers gains (→88.09% full-suite, 89.09% common-core), which is the paper's actual evidence for "runtime and methodology transfer, exact practices don't." The BusinessbBench results are the most epistemically careful part: the paper reports negative transfer for two families (RefactorBench −2.78, WooCommerce −3.70) alongside the positive ones, and explicitly separates "frozen one-shot" evidence from "post-evaluation diagnostic validation" that uses aggregate feedback — a boundary that matters because the latter is not held-out in the same sense. Caveats: results measure the *combined* runtime + evolved, benchmark-adapted control profile, not the state-machine abstraction in isolation (explicitly acknowledged); BusinessBench per-instance results are one stochastic trajectory per arm, so family-level and instance-level averages answer different questions and neither has repeated-trial error bars; the paper is an independent/personal-time project without institutional peer review at the time of this note.

# Q9 Contributions

1. Formulates harness scaling as a capability axis complementary to model scaling, and distinguishes four progressively stronger empirical tests: within-model improvement, frozen cross-generation transfer, adapted cross-provider transfer, and held-out task-family generalization.
2. Introduces StateM, an agent-native runtime (YAML runbook + CLI) in which durable states are simultaneously refreshed control contexts and explicit, checked transition contracts, while preserving the executing agent's unified reasoning loop rather than decomposing it into controller-owned nodes.
3. Operationalizes three distinct execution-failure sources — epistemic gaps, procedural-compliance gaps, procedural-memory gaps — with a corresponding control mechanism for each (state-local context, checked transitions, versioned practices).
4. A failure-driven optimization loop that converts selected postmortem findings into versioned runbook changes, letting procedural knowledge accumulate outside model weights.
5. Empirical demonstration across GPT-5.5, two GPT-5.6 variants, DeepSeek-V4-Flash, Terminal-Bench 2.1, and BusinessBench, with explicit reporting of raw-score adjudication sensitivity, frozen vs. adapted transfer, task-level regressions, and realized API cost (~$15 final-evidence cost vs. $574.68 for the matched GPT reference, ≈38.9× cheaper).

# Q10 Next Steps

* The paper's own limitations/outlook: exact profiles transfer across nearby models within a provider but not across providers without adaptation; more remembered procedure is not better memory — RefactorBench and WooCommerce improve only when generic procedure is replaced by the actual cross-system invariants, and Attendance-Payroll shows the correct policy can be to not intervene at all; the framework provides control points, not a correctness oracle — semantic self-review and agent-authored receipts remain fallible even when structured; role-isolated multi-agent runtimes (separate context views, read/write permission boundaries per agent role) are named as a distinct set of coordination questions left to future work.
* **Research-OS fit:** directly comparable to this repository's own memory-layer conventions (merge-before-append, evidence thresholds, decay in `human-cognition-cache`) and to `HANDOFF.md`'s Active-Work/Decisions pattern — StateM's state-local `in_hook`/`out_hook` and checked-transition discipline is a more formalized version of the same "durable record survives context loss" problem this repository's session-startup contract already tries to solve informally.
* Worth comparing StateM's three-gap taxonomy (epistemic / procedural-compliance / procedural-memory) against this repository's own failure-mode vocabulary the next time a long-horizon agent task in this OS needs a persistent-state design, since the taxonomy maps cleanly onto "missing context," "known procedure skipped," and "lesson not reactivated."
