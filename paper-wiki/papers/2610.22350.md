# Q1 Problem Definition

* **Input (X):** one customer engagement. The agent's workspace holds the sponsor's task instruction, a copy of the customer's production system, documents and historical data, and a staff directory. Stakeholders can be messaged through a workspace command and may also start contact themselves. The runtime offers Python and SQLite only: no package installs and no general network, except a metered company LLM gateway that the delivered system may call.
* **Output (Y):** the contents of `system/` when the agent submits, or when it reaches the limit of 200 turns, 150 minutes, or USD 8 of model usage. These contents are deployed to production unmodified. Production keeps calling the original entry points, so new functionality only counts if it is wired into them.
* **What is measured:** the change in the customer's own business metric (for example, net financial benefit for an after-sales agent, or downtime hours correctly attributed to a contractor for a drilling coder) on held-out production data, normalized against a do-nothing baseline and an expert reference solution, minus a charge for stakeholder contact. A predefined operational incident, such as an unauthorized action, removes any positive credit.
* **Constraints:** the agent is not told that contact is charged, that some people should not be contacted, or that the sponsor's request may target the wrong problem. Clues sit in the staff directory, documents, and data, which may be outdated or contradict one another.

# Q2 Problem Novelty

The paper's claim is that existing benchmarks each measure one stage of delivery with the problem already fixed. Issue-and-test benchmarks (SWE-bench, Terminal-Bench, SWE-Lancer), specification-based deployment (FDE-Bench), predefined enterprise tasks (TheAgentCompany, CRMArena-Pro), and clarification benchmarks (Ambig-SWE, LHAW) all assume a correctly specified task, even when information is withheld from it. Three recent benchmarks come closer: ττ-bench (agents build and deploy customer-service agents), Trains but Doesn't Learn (agents as forward-deployed engineers for post-training), and XYEval (misleading user requests). The paper says each covers one part of delivery. FDE-Gym's new combination is a sponsor request that may be misdirected, constraints that must be found by questioning stakeholders at a cost, and credit only for moving the customer's metric. A solution to the wrong problem therefore earns nothing, and a harmful one scores below zero.

# Q3 Scientific Hypothesis

The stated initial hypothesis was that problem definition would be the bottleneck: an agent given a symptom or a wrong solution would build the wrong system. The experiment design isolates this by keeping the environment, stakeholders, and grader fixed and varying only how much the task instruction reveals (L0 to L3), so any score difference is attributable to the withheld information. The results contradict the hypothesis for leading models: the largest drop is from withholding constraints (L0 to L1), not from a vague or misdirected request (L1 to L3). The paper's revised claim is that the gap to real delivery lies in surfacing unstated constraints, turning known facts into a working system, and spending stakeholder time carefully.

# Q4 Related Work and Key People

* **Implementation benchmarks.** SWE-bench, SWE-Bench Pro, Terminal-Bench, SWE-Lancer: code that passes hidden tests. FDE-Gym asks whether the code was the right thing to write.
* **Framing and clarification.** Ambig-SWE, LHAW, SWE-RPG, UserBench, ReqElicitGym, XYEval; UnderSpecBench and Implicit Intelligence on unstated constraints. # Q5 Key Solution Idea

**A business-metric score with a cost for asking.** The normalized business uplift is U = (KPI_delivered − KPI_baseline) / (KPI_reference − KPI_baseline), all on the same held-out data, so U = 0 is no improvement, U = 1 matches the reference, and U < 0 is worse than the unchanged system. If a predefined incident occurs, U_adj = min(U, 0). Stakeholder contact cost C sums per-contact charges in the same units. Each stakeholder has a hidden per-message rate that rises when the agent exceeds their patience or breaks a contact restriction; unanswered messages are free, and in scenarios with a trial environment or a calendar each trial run and each day of waiting is charged too. The score is S = U_adj − C, and a task is *resolved* when S ≥ 0.8 with no incident. For averaging, U_adj is floored at −1 before subtracting C, so one disastrous delivery cannot dominate.

**Four instruction levels over one fixed world.** L0 states the underlying problem, its rules and constraints, and how it is scored; L1 states only the problem; L2 gives a vague but directionally correct request; L3 gives the sponsor's original request, which may target the wrong problem. L3 is the main setting. The drilling example shows why: a vice president asks for a daily summary email and an "Ask your wells" chat box and puts the downtime-coding script out of scope. The metric only moves if the agent revisits that script, finds the contractual rule, confirms it with the cost engineer, and gets approval from an approver who is away that week.

**Admission anchors against gaming.** A task enters the benchmark only if: the reference scores at least 0.95; doing nothing scores 0; the *literal* solution (exactly what the instruction asks, no further inquiry) scores at most 0.2; and shortcut strategies score at most 0.8. Shortcuts include overfitting to historical data, guessing round-number thresholds, and deferring every uncertain decision to humans. The one exception to the literal cap is a task whose request is both correct and complete; there the literal solution is the reference and must reach 0.95, so distrusting the sponsor is never a universally rewarded strategy. Bypassing customer controls or manipulating the grader caps the score near zero, and the graders were tested against more than 270 shortcut and bypass strategies (see [Reward hacking](../concepts/reward-hacking.md)).

**Variants and scripted stakeholders.** Each scenario has an original task plus two to seven expert-written variants that change key facts: which rule is outdated, who holds the critical information, and whether the request addresses the real problem. No single problem pattern covers more than a third of the set, so a solution that worked once may fail on a sibling task. More than 130 stakeholders are scripted rather than played by an LLM. A small model maps each question to a topic, and each stakeholder's knowledge, misconceptions, disclosure conditions, patience, evidence demands, unavailability, and contact restrictions are fixed in advance. Agents that solve a task from documents and data alone are scored the same as those that ask.

# Q6 Experiment Design

* **Models.** 13 configurations from seven providers (12 models; Claude Haiku 4.5 with and without extended thinking): Claude Opus 5.5, Claude Sonnet 5.5, GPT-6 Astra, GPT-6.1 Sol, GLM-5.3 Flash, DeepSeek V4.1 Flash, Gemini 3.8 Flash, Qwen 3.8 Flash, GPT-5.5, GPT-6 Luna, Mistral Small 4, and Claude Haiku 4.5. All run in one minimal framework with five tools (execute commands, read, write, edit, and list files) and no model-specific tuning.
* **Protocol.** L3 on all 95 tasks (20 originals and 75 variants); L0 to L2 on the 20 originals only, with three scenarios whose L2 and L3 instructions coincide reusing the L3 run. That is 152 task-level combinations per model and 1,976 in all, each run three times and averaged. 95% confidence intervals come from bootstrapping over tasks for the full L3 evaluation.
* **Diagnostics.** The grader records which key facts the agent obtained from stakeholders, separating discovery from building. The paper also reports uplift before contact cost, questions per task, score bands (including below the do-nothing baseline), per-scenario means and within-scenario spread, turns, minutes, submission rates, and model cost per run.
* **External comparison.** Success rates on Terminal-Bench 2.1, Vibe Code Bench, and Finance Agent from Vals AI (accessed 6 October 2026), shown beside FDE-Gym scores ×100, with the caveat that a success rate and a normalized uplift are different quantities.
* **Not included.** A human baseline, which is being collected on the online platform and deferred to a later version; any framework other than the minimal one; L0 to L2 on the 75 variants.

# Q7 Datasets and Code

The harness (workspace creation, stakeholder simulation, grading) and the experiment runner are open source at [deeplethe/fde-gym](https://github.com/deeplethe/fde-gym) (version 1.1.0; 98 stars per `hf papers info`). The 20 original tasks and their graders are available on request through the Hugging Face dataset DeepLethe/FDE-Gym, with three tasks public as examples. The 75 variants and all reference solutions are held out. The online platform at fde-gym.com runs the same workspaces, stakeholders, and graders for human participants. The scenarios come from delivery projects in China, Singapore, and the United States since 2024, with companies and people de-identified or fictional; expert work on the benchmark exceeded 10,000 hours. The repository and dataset were not opened for this note.

# Q8 Evidence Quality

* **Supported.**
  * *Leading models fall well short of the reference.* At L3, Claude Opus 5.5 averages 0.56 (95% CI 0.50 to 0.62) and resolves 14 of 95 tasks; Claude Sonnet 5.5 scores 0.49 (15 resolved), GPT-6 Astra 0.38 (9), and GPT-6.1 Sol 0.37 (7). Five configurations resolve none. Taking the best configuration per task still gives only 0.70 with 30 resolved, and on 16 tasks no configuration reaches 0.5 (Table 3). The scale's top is reachable: every reference scores at least 0.95, and with the rules given (L0) the leading three reach 0.73 to 0.82.
  * *Withheld constraints cost the most.* On the 20 originals, the leading three drop from 0.73-0.82 at L0 (11-13 of 20 resolved) to 0.39-0.62 at L1 (1-7 resolved). Averaged over the three models with paired tasks, the drop is 0.28 (CI 0.17 to 0.39), against a further 0.04 (CI −0.03 to 0.14) from L1 to L3. Questions per task rise from 3.9-7.0 to 11.3-13.0 and contact cost from 0.07-0.10 to 0.18-0.24, while delivered systems fall from 0.81-0.90 to 0.63-0.80 of the reference uplift. Weaker models keep losing beyond L1 (GPT-5.5: 0.51, 0.15, 0.04, 0.06).
  * *Knowing the facts is not delivering.* At L3 the leading three ask 10.0 to 12.3 questions per task, obtain 72-85% of the key facts, and deliver 0.60-0.70 of the reference uplift. In the 73 task-model cases where one of them had every key fact, uplift averages 0.66 and reaches 0.8 in only 27 (37%). Contact cost then turns near-successes into failures: GPT-6 Astra's systems reach 0.8 on 36 tasks, but only 9 stay resolved after cost (Claude Opus 5.5: 40 and 14).
  * *Weak agents do harm.* Claude Haiku 4.5 scores below zero on 79 tasks and GPT-6 Luna on 63, against 5 for Claude Opus 5.5. Before any contact cost, Mistral Small 4's systems fall below the baseline on 51 tasks and Claude Haiku 4.5 (thinking) on 55, against 1 to 4 for the leading three; on 23 tasks Mistral Small 4 caused more harm than the reference's benefit. Extended thinking does not help (−0.33 without, −0.35 with).
  * *Spending does not buy score.* GPT-6.1 Sol uses USD 0.24 and 25 turns per run for 0.37, while Gemini 3.8 Flash uses USD 1.54 and 121 turns for 0.19. Qwen 3.8 Flash averages 169 turns and 110 minutes and submits within limits on only 11 of its 152 combinations.
* **Weaker or narrower than the headline.**
  * *The level analysis rests on 20 tasks.* The authors claim only that no large drop beyond L1 is visible; the CI allows up to 0.14 more, and up to 0.25 for an individual model. GPT-6.1 Sol even scores higher at L3 (0.43) than at L1 (0.33) on the originals (reader observation from Table 3), which fits small-sample noise.
  * *Scripted people and expert-set prices.* Stakeholders cannot change their minds or misunderstand a question. Contact charges are a model of stakeholder time set by the scenario authors, not a measurement, yet they decide many resolutions (36 versus 9 for GPT-6 Astra). Rankings could shift under different pricing (reader inference).
  * *One minimal framework.* Scores describe models in a five-tool loop that was never told asking costs anything, not the products built around them. A framework that budgets questions could change both scores and ranking, as the authors note.
  * *Limited independent audit and a stake in the leaderboard.* The 75 variants and all reference solutions are held out, so the admission anchors (reference ≥ 0.95, literal ≤ 0.2, shortcuts ≤ 0.8) can be checked by outsiders only on three public tasks. DeepLethe also operates the platform and its leaderboard, which the paper discloses; none of the evaluated models comes from an affiliated organization.
  * *The external comparison is not like for like.* Terminal-Bench 2.1, Vibe Code Bench, and Finance Agent success rates (up to 88%, 90%, and 61%) sit beside FDE-Gym scores of 0.19 to 0.56. The closest matching quantity, the resolved share, is 15% for the leading model.
  * *Coverage and contamination.* The scenarios lean toward agents and workflows in regulated operations, and because they come from real deliveries the authors cannot rule out related material in training data.

# Q9 Contributions

* A delivery benchmark that chains problem framing, constraint discovery, building, and deployment into one causal outcome on the customer's own metric, with a do-nothing zero that a delivery can fall below.
* A construction method for reproducible enterprise scenarios: expert-adapted real projects, fact-changing variants, scripted stakeholders with hidden prices and disclosure rules, and four admission anchors validated against more than 270 shortcut and bypass strategies.
* An instruction-level ladder (L0-L3) over a fixed environment that separates engineering, constraint discovery, and problem clarification, and a grader that records which key facts were obtained.
* A 13-configuration evaluation whose findings (constraint discovery as the main drop, a fact-to-system gap, harm from weak models, little link between spending and score) give concrete targets for delivery agents.
* An online platform where people practice the same tasks under the same graders, setting up a direct human-agent comparison.

# Q10 Next Steps

* **From the authors.** A human baseline from industry experts on L3 tasks; stakeholders closer to real people; stronger per-run isolation (one container per run); more sectors and kinds of deliverable.
* **Price-aware agents (reader suggestion).** Tell the agent that contact is charged, or give it a question budget, and measure whether leading models keep their fact coverage at lower cost. GPT-6 Astra losing 27 of 36 near-resolutions to contact cost suggests this is where cheap gains are.
* **Sensitivity to the pricing model (reader suggestion).** Report rankings under several contact-cost schedules, or report U and C separately, which Table 3 already does, as co-primary results.
* **Framework comparison (reader suggestion).** Run the same models inside production coding agents and requirement-elicitation scaffolds. If a structured discovery phase closed the L0-to-L1 drop, that would locate the gap in the agent loop rather than the model.
* **Link to agent-building benchmarks (reader connection).** [AgentSWE](2610.13361.md) also freezes a delivered artifact and runs it on held-out cases, and finds overfitting to visible cases and false completion claims. Testing one builder on both would show whether the failures that hurt agent-building commissions also hurt customer deliveries.
