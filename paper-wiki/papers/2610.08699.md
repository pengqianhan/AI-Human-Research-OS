# Q1 Problem Definition

* **Input (X):** one person with several devices (an Android phone, possibly an iPhone, a desktop or laptop, a browser), their accounts and files, and a model provider or local model of their choosing.
* **Output (Y):** one agent that acts for that person on those accounts, devices, and files; works for weeks, partly while the person is away; remembers them; speaks first when it is worth it; and answers afterwards for what it did through a log, a ledger, and a list of the permissions it holds (the paper's definition in Sec. 1).
* **Core problem:** in September 2026 the personal agent arrived as a product category (Meta's Muse on September 8, then Today, Manus Cue, and OpenAI's dots within three weeks), but every version runs in the vendor's cloud with thin clients on the person's devices and a vendor-trained model. The paper argues that software holding a person's life should be inspectable, run on hardware the person owns where possible, and share only one piece (the meeting point of devices) as code anyone can run, and that no complete open counterpart existed. A second, technical gap motivates the design: cloud computers reach only what has an API or a web page, while many everyday phone apps (banking, government services) have neither.

# Q2 Problem Novelty

The category is new; its parts are not. Open personal agents already existed without screens (Hermes Agent, Jul 2025; OpenClaw, Nov 2025, both on a computer or server of the person's own and reached through chat apps) or on one phone without a server (OpenMinis, Jun 2026, an Android agent nanoMuse is built from). CopilotKit's OpenMuse (Sep 15, 2026) is open and Muse-shaped but runs on a server with a browser and Linux workspace, with graphical desktops listed as future work. In the paper's Table 1, nanoMuse is the only listed system that operates both a phone screen (Android only) and a computer screen and is fully open. Muse itself does not operate the phone's screen: its browser sub-agent sees accessibility-tree snapshots, so it cannot drive an interface without one (a native phone app, a kiosk, a game). The paper presents operating the person's own screens on their own devices as what nanoMuse adds.

# Q3 Scientific Hypothesis

This is a system report and position paper, not a hypothesis test; its implicit claims are design claims that the paper does not measure:

1. **Muse's value is its shape, not its model.** Muse "did not win on a benchmark; it won on a shape": legibility (one named agent, one long conversation, a chip per tool call, memory as editable files, an adjustable bar for speaking first) plus safety mechanisms placed outside the agent's reach. The authors claim this transfers to an open system, while Muse's per-person VM and in-house model do not.
2. **A deterministic policy can govern screen actions through the model's own words.** If the screen operator must state, in a sentence, what it is about to press, a rule-based gate can judge that sentence (committing words such as "confirm payment", "send", "delete") even though it cannot judge a picture.
3. **Peer devices cannot lend permissions.** If each device runs its own agent behind its own Sentinel and a job handed to another device runs under that device's Sentinel, a compromised or persuaded device cannot use permissions it does not hold.

# Q4 Related Work and Key People

* **Assistants to task agents.** Siri, Alexa, Google Assistant; AutoGPT and Open Interpreter as early unattended and local-execution agents.
* **Screen-operating agents and benchmarks.** CogAgent, AppAgent, Mobile-Agent, Anthropic's computer use, AutoGLM, and MCP as the tool standard; open screen models OS-Atlas, Aguvis, UI-TARS, OpenCUA, GUI-Owl (Mobile-Agent-v3); benchmarks Mind2Web, WebArena, OSWorld, AndroidWorld; MAS-Bench for hybrid shortcut-plus-screen phone agents.
* **Hosted agents.** Operator, ChatGPT agent, Manus: each acts for a task, none belongs to a person.
* **Personal agents of September 2026.** Muse (Meta), Today, OpenMuse (CopilotKit), Manus Cue, OpenAI dots, and Meta's Apache-2.0 Muse Gadget SDK (Oct 2); Simon Willison's "lethal trifecta" (private data, untrusted content, external communication) is cited for Muse's injection defenses.
* **Key people.** All three authors are listed at Zhejiang University; Guangyi Liu is the first-listed author of several works the system builds on (a phone-GUI-agent survey, LearnAct, MemGUI-Agent, MemGUI-Bench, MobileForge, and second author of MAS-Bench). Likely critics: Muse's safety engineers (the paper relies on their public essay), maintainers of OpenClaw, Hermes Agent, and OpenMinis, and GUI-agent safety researchers (OS-Harm), since the hands' safety rests on untested policy rules.

# Q5 Key Solution Idea

* **A definition and a normative frame.** Five questions about a personal agent, each answered at three horizons (what exists in 2026, what the open counterpart should add next, an agent meant to last years): *what it knows* (memory as plain files the person can read, edit, delete, and export, with provenance per line: model, date, confidence; lines the person wrote outrank model-written lines), *where it acts* (one agent, many "hands"), *whom it answers to* (approvals as "the grammar of trust": scoped, listed, revocable grants; payment approvals and passwords never remembered), *how it learns* (an interrupt bar the person can see and move; an open hands model trained on traces people chose to share), and *how it is paid for and governed* (small enough to run at home; ultimately a commons).
* **A source-tagged reading of Muse.** Every statement is marked *documented* (Meta's announcement, safety essay, design essay, privacy page), *prompt* (a copy of Muse's production system prompt from October 2026, not reproduced), *observed* (the shipped clients), or *inferred*. Highlights: a dedicated Linux VM per person in Meta's cloud, with the agent in a seccomp-filtered container; a Sentinel that is "the sole permission authority" for connector actions and network egress; surrogate tokens swapped for real credentials at the network boundary; kernel-level taint tracking per tool process; scoped capability grants; two memory layers and background jobs the agent cannot schedule itself; and a prompt instructing the agent to search memory rather than trust its recollection.
* **nanoMuse's construction (v0.1.40, first release Sep 25, 2026, GPL-3.0).** An Android app (a modified OpenMinis: a whole agent in the app with sandboxed Alpine Linux, shell, browser, MCP servers, skills, and scheduled tasks), an iOS app (TestFlight; everything but screen control, since iOS lets no app operate another), a desktop Electron app wrapping the DeepSeek harness with a nanoMuse plugin and bundled Python runtime, a web app served from the person's own computer, and an optional relay (nanoMuse Cloud).
* **Sentinel.** The agent never executes a tool directly. Each call passes a fixed decision order: denied tools; the person's own rules; always-allow and always-ask lists; taint (once a conversation has read private data, any call sending data outside the allow-list becomes an ask, never the reverse); tool risk against the mode the person set; and last, warnings no mode or list can wave through (a destructive shell command, a piped download executed on the spot, a committing word in a label). Approvals are scoped grants (once; this conversation; always for a named recipient, site, folder, device, or application) listed under Permissions with a revoke button; a call carrying a warning can be granted only once; every decision is logged.
* **Hands as the last rung of a ladder.** To reach an app the agent takes the lowest rung that works: a skill, CLI tool, or MCP server; a page fetched with the person's login; the browser; and last, the device's screen ("Hands", off by default). Hands is a one-action-per-screenshot loop in the dialect of MemGUI-Bench's phone operator, with the computer side ported from UI-TARS-desktop. The model sees one screenshot, the goal, a one-sentence history per step, and accessibility elements when available, and answers with a thought, a sentence in the person's language describing the step, and one gesture. That sentence is what the Sentinel judges: committing words make a step sensitive and approved every time, a type-and-submit step is sensitive, a step without a label gets a warning; on Android the accessibility text where the finger will land is also read and the stricter reading wins. The operator prompt forbids typing passwords, PINs, card numbers, and one-time codes. Runs show a capsule with a red Stop on the phone and a screen-edge glow plus a step-by-step trajectory on the computer.
* **Memory as files.** On the phone, Markdown files (`SOUL.md`, `USER.md`, `GLOBAL.md`, a dated diary, `HEARTBEAT.md`) that both the person and the agent's shell can open; on the computer, a line-level store with a change log and undo, recalled by rare words or embeddings, with a tidy-up pass that never drops lines the person wrote.
* **Peer devices over a relay.** Each device runs its own agent; the others appear as tools ("find the order number on my phone, then put it in the spreadsheet on my Mac" is one conversation). The device that would act must grant the request, and the job runs under that device's own Sentinel.
* **Model choice and what the relay keeps.** A catalogue of eighteen providers shared by the apps and the relay, an API key of the person's own (then nothing but model calls leaves a single device), a ChatGPT plan through OpenAI's Codex sign-in flow, or a local model server. The relay stores a hashed account identifier, issued keys, a model-call ledger without content, the agent profile, hub presence, and the text of conversations the person chose to sync; never files, images, or tool results. A "Help improve nanoMuse's AI models" switch is on by default for new community-relay accounts.

# Q6 Experiment Design

There are no experiments. The paper's only quantitative evidence is Table 2, sizes measured on the release files and one Linux installation plus cost estimates from documentation and price lists. The authors state they have no success rate or count of human take-overs for the hands and "would rather say so than estimate it". Claims about Muse rest on four public Meta documents, the shipped clients, and the prompt copy.

# Q7 Datasets and Code

No dataset. Code is GPL-3.0 at [nano-muse/nanoMuse](https://github.com/nano-muse/nanoMuse) (229 stars on Hugging Face's paper page at fetch time), with a project site at [nanomuse.cn](https://nanomuse.cn), a web demo, and repository documents on using one's own key, privacy, and self-hosting that the paper cites as its sources for provider lists, relay storage, and server sizing. The paper describes version 0.1.40 and notes later versions will differ.

# Q8 Evidence Quality

* **Supported by the paper's own measurements or documents.**
  * *It is small.* The Android app is a 38 MB download (arm64); the desktop app is 256 MB (Linux) to 498 MB (macOS) to download, 266 MB on Windows, 928 MB installed on Linux, and about 0.5 GB of memory idle; the relay is one Python process and one SQLite file using about 85 MB idle with a fresh database, sized for 1 vCPU and 1 GB.
  * *It is cheap to self-host (estimates).* A relay of one's own costs on the order of ¥30-¥60 a month inside mainland China or US$4-6 outside for the smallest server tier, plus model usage; Bailian's October 2026 list prices are ¥2 in and ¥8 out per million tokens for the chat model in busy hours and ¥3 and ¥12 for the hands model, "a day of chat is a few fen".
  * *The design is concrete and inspectable.* The Sentinel order, grant scopes, relay contents, and memory layout are specified precisely enough to audit against the open code.
* **Not established.**
  * *Capability.* There is no evaluation of the hands on any benchmark or real task, no human take-over count, and no comparison with Muse, OpenClaw, or OpenMinis. Linux hands work only in X11 sessions.
  * *Safety.* The Sentinel has not been red-teamed or tested against prompt injection. The authors stress that on one device it is a policy boundary in the agent's own trust domain, not a privilege boundary like Muse's per-person VM with credentials held outside the agent's reach: "a compromise of the device is a compromise of the agent."
  * *Judging gestures by their descriptions (reader inference).* The hands gate assumes the model's sentence matches its gesture. A model misled by content on the screen could describe a benign step while tapping a committing control; the Android accessibility check narrows this, but an unlabeled icon on a desktop only produces a warning, and the authors note that finding icons on dense professional screens is itself unsolved (citing ScreenSpot-Pro).
  * *The account of Muse.* Statements marked "prompt" rest on a copy of the production system prompt whose provenance the authors cannot verify beyond its consistency with Meta's documents, and which may change with every deployment; the paper does not say how the copy was obtained. Cost and size figures are estimates or single-installation measurements.
  * *Memory provenance.* The paper's own normative requirement (each memory line records the writing model, date, and confidence, with a reconciliation rule) is not implemented: the store records change history and undo only.

# Q9 Contributions

* A working definition of the personal agent and a short history from 2011 assistants to the September 2026 agents (Table 1 places each by where its loop runs, which screens it operates, and its license).
* A source-tagged reading of Muse's architecture that separates documented, prompt-derived, observed, and inferred statements, and identifies placing safety mechanisms outside the agent's reach and designing for legibility as its transferable core.
* A five-question, three-horizon statement of what a personal agent should be, usable as a checklist for other systems.
* nanoMuse: an open, multi-device personal agent with screen control on Android and desktops, a Sentinel with a fixed decision order and scoped grants, memory as files, peer devices that cannot lend permissions, and a relay that stores no tool results or files.
* A roadmap and an explicit list of what the authors would not yet trust the system with.

# Q10 Next Steps

* **From the authors.** Near term: memory that surfaces at the right moment, proactivity between schedules, hands that fail less, one-command self-hosting. Next: an evaluation suite built from failed runs, run beside AndroidWorld, OSWorld, MemGUI-Bench, and OS-Harm, then a small open hands model trained on traces people chose to contribute, as MobileForge adapts an open model from runs it collected. Later: cameras, appliances, and robot arms as further devices under the same approvals and log; memory and identity that survive models, devices, and vendors.
* **Test the sentence gate adversarially (reader suggestion).** Measure how often the operator's description disagrees with its gesture, with and without injected on-screen text, and whether the stricter-of-two rule on Android catches the mismatches the desktop cannot.
* **Implement memory provenance.** The proposed per-line model, date, and confidence fields with a re-check rule would let a stronger model discount what a weaker one guessed; this is testable on long-running memory benchmarks.
* **Peers versus a central VM.** Compare failure, latency, and permission errors of cross-device tasks run as peer jobs with per-device Sentinels against a single cloud agent with thin clients.
* **Project fit (reader note).** This repository already keeps agent memory as plain, human-editable files; nanoMuse's rule that a line the person wrote outranks any model-written line, and its proposal to record which model wrote each line, are directly applicable to the cognition cache and memory layers here.
