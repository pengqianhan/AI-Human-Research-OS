# Q1 Problem Definition

* **Input (X):** a real-world task with its context (inputs, environment, constraints, acceptance criteria) and a library of reusable units: tools, repository components, proof methods, source documents, multi-agent patterns, files, or harness control operations.
* **Output (Y):** a task-specific harness, built as a graph of activated primitives, that produces the task's artifact (a tool-call sequence, a repository, a Lean proof, an answer, a completed live action) and passes the task's own acceptance check, plus validated additions to the library for later tasks.
* **Constraints:** a fixed budget of revision rounds; a failed build or test cannot be overruled by a model's judgment; a library built ahead of time does not change during a task, and anything produced inside a task enters the library only through a separate validation path.

# Q2 Problem Novelty

Partly new. Tool learning, retrieval and memory, skill and code libraries, multi-agent frameworks, workflow search, and harness optimizers all make resources easier to reach. The paper's claim is that each leaves the *competence to apply* a resource with the caller (or a monolithic agent), so every harness rebuilds it. Its answer, putting a resident LLM inside each resource, generalizes ideas from reusable components, temporally extended options, and design by contract. The eight families are not new in this paper: each is a companion study by the same group (Tool Primitives arXiv:2609.01736, Code Primitives arXiv:2610.09079, Math Primitives arXiv:2610.09401, Knowledge Primitives arXiv:2610.02150, Agent Primitives arXiv:2602.03695, Dev-Primitives arXiv:2610.07832, Navigation Primitives arXiv:2609.33326, Harness Primitives arXiv:2609.38912). What is new is the single definition that unifies them, the restated theory, cross-family analyses, and the heelo.dev evaluation.

# Q3 Scientific Hypothesis

If each reusable resource carries its own LLM that applies it in context, validates its own step, and sends requirements to the primitives that depend on it, and a harness activates only the primitives a task needs and revises only those a failure implicates, then agents will complete more real-world tasks than frontier harnesses that apply resources themselves, at a cost that grows with the task's demand rather than with the library's size.

# Q5 Key Solution Idea

**Agent-native primitive.** A primitive is a resource *a* plus a resident LLM and an interface *d* through which a harness finds it. Called with a natural-language request in context, the LLM applies the resource and returns a result and messages to other primitives (requirements the result places on them, or information they need). One base model can be the resident LLM of every primitive. A primitive can also assess its own relevance and propose how it would be used, and it runs any validation its resource carries (tests, a schema) before returning. Where the domain has an exact procedure, code replaces the LLM.

**HEELO's three mechanisms.** (1) *Library selection and composition*: find candidates by retrieval or by reading every interface, read their relevance assessments, and build a graph of the few activated primitives with the edges along which results and messages flow. (2) *Evidence-based execution and improvement*: run the graph in rounds, execute what can run (builds, tests, compilers), verify the result, name the primitives the failure implicates, and revise only those, within *B* rounds. (3) *Validation and publishing*: between tasks, admit new or improved primitives (mined, harvested from verified runs, or proposed from failures) only after domain validation.

**Eight families.** Tool Primitives (one per tool in a 25,519-tool catalogue, 16,464 wrapping live APIs; framework HEART), Code Primitives (1,424 tested components; LEGO), Math Primitives (82 Lean-compiled method contracts from Putnam 2000-2014; self-advertised selection), Knowledge Primitives (a source model per authoritative source; SourceLearn), Agent Primitives (Review, Voting and Selection, Planning and Execution as latent operators sharing KV caches on one LLM), Dev-Primitives (one per repository file, sending directed messages; HERMES), Navigation Primitives (territory workers routed by unresolved needs; ANTMAN), and Harness Primitives (validated control operations composed into a harness before the actor starts; STITCH).

**Theory, restated from companion studies.** Activation is bounded by the task's demand when each primitive is activated only to resolve one unresolved need, however large the library. Under an additive model, per-task composition beats the best fixed harness if and only if its selection loss is below a computable gap. Any reranker of a similarity-retrieved shortlist is capped by that shortlist's recall, which assessing the whole library avoids.

# Q6 Experiment Design

* **Per-family benchmarks, more than twenty in all.** ToolBench, NESTFUL, τ²-bench, ACEBench, BFCLv4, and 50 curated real-world tool tasks; LEGO-REPO (522 repository-reconstruction tasks built by the authors) plus RepoZero, RepoGenesis, and RepoCraft; 120 Putnam 2015-2025 and 60 IMO ProofBench problems in Lean 4; MultiDoc2Dial, NarrativeQA, SWE-QA, APIBench, and [AppWorld](../concepts/appworld.md); eight math, code, and QA benchmarks for multi-agent systems; SWE-bench Verified, Terminal-Bench 4.0 (66 tasks), DevOps-Gym, and SWE Refactor Bench; HotpotQA, 2WikiMultiHopQA, MuSiQue, RepoProbe-Python, SWE-QA-Pro, [GAIA](../concepts/gaia.md)-Text-103, and controlled 32K-512K-token spaces; and samples of 100 SWE-bench Verified and 45 Terminal-Bench 2.0 tasks for Harness Primitives.
* **Baselines.** Each family's companion-study baselines on matched backbones, including Codex, Claude Code, OpenHands, [mini-SWE-agent](../concepts/mini-swe-agent.md), SWE-agent, Aider, DFSDT, RAPTOR, HippoRAG 2, LatentMAS, MAS-GPT, LongAgent, Chain of Agents, MemoHarness, and Meta-Harness, plus controls that remove or replace the primitives.
* **Cross-family analyses (Section 5).** Budget-matched controls, primitive-field ablations, communication ablations (KV-cache re-indexing, Dev-Primitive messages), activation and revision ablations, and model-placement sweeps, each drawn from a companion study.
* **heelo.dev (Section 6).** 46 tasks covering 26 capabilities in four live loops (distribution, acquisition, a personal assistant, and market validation); Claude Opus 5.5 with Claude Code and GPT-6.1 Sol with Codex, both at medium effort, each alone and connected to HEELO through an [MCP](../concepts/model-context-protocol.md) server; most tasks run three times; distribution and assistant answers graded blind by Claude Sonnet 5.5 with a person reviewing its grades.

# Q8 Evidence Quality

* **Supported.**
  * *Large gains over Codex on Terminal-Bench 4.0.* Over five runs of 66 tasks, HERMES with GPT-5.6 Sol resolves 55.5% against 37.3% for Codex at max effort and 51.8% against 33.0% at medium; GPT-5.6 Terra gains about 26 points.
  * *Per-task harness composition helps.* With a GPT-5.6 Luna actor, STITCH raises Pass@1 over the mini-SWE-agent seed from 73.0% to 80.5% on 100 SWE-bench Verified tasks and from 60.0% to 72.2% on 45 Terminal-Bench 2.0 tasks, above the best single primitive applied to all tasks (76.0%) and a random composer (73.3%), at 2.7% to 4.3% of one actor attempt.
  * *The gain sits in applying, not accessing, the resource.* A budget-matched control that self-refines arguments over raw schemas reaches 34.2% ToolBench pass rate against 75.1% for Tool Primitives; showing the caller the same retrieved components as read-only context gives 0.3544 repository delivery against 0.5134 for Code Primitives.
  * *Channels and revision matter.* Without RoPE re-indexing of shared KV caches the composed multi-agent system on R1/Llama-70B falls from 85.3% to 31.1% on HumanEval+; removing diagnosis feedback lowers HERMES on Terminal-Bench 4.0 from 51.8% to 41.2%.
  * *Activation tracks demand.* Active Navigation Primitives grow 1.23× when distractors grow the space 16×, against about 15× for LongAgent and Chain of Agents.
* **Weaker or narrower than the headline.**
  * *HEELO as one system is not evaluated on the research benchmarks.* Each family is a separate system (HEART, LEGO, HERMES, STITCH, ANTMAN, and others) evaluated in its own study; Appendix E only specifies a protocol for cross-family composition, with no results. The unified framework is a description shared by eight systems, and the restated propositions hold under each study's assumptions, such as an additive gain model (reader reading of Appendix E and Section 3.5).
  * *The headline comparison picks the weaker frontier harness.* Against Claude Code with Claude Opus 5, the strongest baseline, HERMES gains only 1.2 points at max effort (51.8% to 53.0%) and 1.5 at medium; the 18.2-point figure is against Codex. HERMES also uses about twice the tokens and cost of Codex on Terminal-Bench 4.0 (for example $2.5k to $4.7k per evaluation at max effort), with Claude Sonnet 5 as the noted exception.
  * *Several baselines are narrow.* Tool Primitives' 75.1% on ToolBench is 19.3 points above DFSDT on the same Qwen3-8B backbone but only 1.7 above Claude-4.6-Sonnet with DFSDT. Code Primitives' 0.5134 is measured on the authors' own LEGO-REPO benchmark against execution feedback (0.3180). SWE-bench Verified is near its ceiling (HERMES with Sol 97.0% against 96.2% for mini-SWE-agent).
  * *Small samples for the harness study.* STITCH's 1.5-point lead over Codex on SWE-bench Verified is 3 of 200 attempts (reader arithmetic), and primitives were developed on disjoint but same-benchmark development tasks.
  * *heelo.dev is built to favor the connected arm.* Standalone agents get no credentials and cannot act on any account, so the assistant loop scores 0% for both by construction and many of the 12 zero-score capabilities are acting on accounts. When a run exposed a defect in a primitive, the primitive was fixed and the task rerun, and only post-fix runs are reported. The tasks come from the authors' own product, one author is affiliated with it, and grading is by an LLM with human review. Time and cost "per completed task" divide totals by completions, which rewards the arm that completes more; per run, connected agents usually read more tokens (median assistant run 160,701 against 19,456) (reader observations from Section 6.3-6.4).

# Q9 Contributions

* A single definition (resource + resident LLM + interface + messages) that ties together eight families of reusable, self-applying units.
* HEELO's description of per-task composition, evidence-driven revision of implicated primitives, and validation-gated library growth.
* Cross-family analyses that locate gains in applying resources inside primitives, in inter-primitive channels, and in demand-driven activation and evidence-driven revision.
* heelo.dev, a live platform exposing real-world actions as primitives through MCP, with a 46-task end-to-end evaluation.

# Q10 Next Steps

* **Run the Appendix E protocol (from the paper).** Tasks that need two or more families, comparators with matched assets and budgets, and false-pass rates of each family's verifier under the composed distribution would test HEELO as one system.
* **Fair live comparisons (reader suggestion).** Give standalone agents the same credentials and API access, with primitives frozen before the evaluation, so heelo.dev results measure application competence rather than account access.
* **Against the strongest harness (reader suggestion).** Report each family's gain over the strongest same-backbone harness (Claude Code with Opus 5 on Terminal-Bench 4.0), with compute-matched variants.
* **Library maintenance under drift.** The paper lists API-schema, documentation, and dependency drift as stress tests; how often validated primitives go stale, and what revalidation costs, decides whether a 25,519-tool library stays usable.
* **Role-level model allocation.** The finding that a strong model helps most in diagnosis while small models can run inside primitives connects to turn-level handoffs such as AgentBaton's (reader connection).
