# Q1 Problem Definition

* **Input (X):** a user request whose source material and deliverables may mix seven artifact types (text, image, audio, video, documents, 3D assets, and code), plus assets registered in earlier turns. It is handled by an existing general-purpose host agent; the paper uses GPT-5.6 Sol and Claude Sonnet 5.
* **Output (Y):** the requested deliverables, from an analysis to a coordinated package such as a poster, a promotional video with sound effects, and a landing page, each registered as an asset that later turns can revise or reuse.
* **Core problem:** coding and knowledge-work agents already plan and execute well, but their production surface stops at software and text. Adding modalities to a foundation model ties capability growth to costly retraining. Wiring in specialist models and tools leaves open how procedures, dependencies, intermediate assets, and cross-turn revisions are coordinated.
* **Constraint:** the host agent's reasoning core stays unchanged; everything is added as a loadable harness.

# Q2 Problem Novelty

Partly new. Omni foundation models (Unified-IO 2, AnyGPT, Chameleon, NExT-GPT, Transfusion, the Qwen-Omni series) put multimodality inside one model. Model-coordination agents (MM-ReAct, Agent-Omni, OmniGAIA) delegate to modality specialists, but the authors note they are mostly evaluated on understanding and question answering. Agent Skills work ([SkillsBench](../concepts/skillsbench.md), CUA-Skill, MMSkills) packages procedures but not multi-asset media production. The paper places itself at their intersection: any-to-any production workflows with dependency-aware execution and persistent asset state across turns.

# Q3 Scientific Hypothesis

If an existing agent is given hierarchical Skills, a standardized multimodal execution interface, dependency-aware graph execution, and a persistent asset registry, then it should accept every input modality in the test set and produce better-structured, higher-quality multimodal outputs, with no change to the model.

# Q4 Related Work and Key People

* **Omni foundation models:** unified autoregressive models (Unified-IO 2, AnyGPT, Chameleon) and hybrid discrete-continuous ones (NExT-GPT, Transfusion, JanusFlow, Qwen2.5-Omni and Qwen3-Omni), plus streaming systems such as Moshi and Ming-Omni.
* **Harnesses and multimodal agents:** ReAct, the [Model Context Protocol](../concepts/model-context-protocol.md), work on harness engineering, MM-ReAct, Agent-Omni, and OmniGAIA.
* **Skills:** SkillsBench, CUA-Skill (computer-use procedures as parameterized graphs), and MMSkills (textual procedures with state cards and visual keyframes).
* **Key people:** National University of Singapore, with the University of Oxford also listed. Hao Fei is corresponding author and project lead; Mong-Li Lee and Wynne Hsu are senior authors. The evaluation benchmark, UniM (CVPR 2026), comes from the same group with the same first author, and Shengqiong Wu and Hao Fei also wrote NExT-GPT. Likely critics: omni-model builders, who would ask how the harness compares with a native omni model, and agent-evaluation researchers, who would ask for other harness baselines and ablations.

# Q5 Key Solution Idea

* **Four layers between the agent and the tools.** A Skill Entry layer selects and expands Skills. An MCP Tool Service layer exposes understanding, generation, and utility tools through one contract (task type, self-contained prompt, parameters, and dependency-resolved asset inputs). A Provider and Configuration layer binds each task type to a tool, provider, model, credential reference, defaults, and fallback policy, so providers can be swapped without editing Skills. An Asset Registry records every output.
* **Skills by granularity, not by modality.** Each Skill is declared as applicability conditions, inputs, procedure, outputs, and links to lower-level Skills. There are 19 Atomic Skills (one operation, such as image understanding, video generation, speech synthesis, 3D generation, PPT generation, or web search), 2 Expert Skills (Poster Design and Complex Video Production, each covering one finished deliverable from planning through inspection, with local regeneration of only the failed parts), and 6 Scenario Skills (social-media post, office documents, job application, education sharing, event material, game asset) that choose which deliverables a request needs. Higher-level Skills expand recursively until every step can run.
* **Declare Execution Graphs (DEGs).** Terminal tasks become graph nodes (id, type, prompt, parameters, dependencies). Before execution the graph is checked for unresolved references and cycles, and a failing graph is rebuilt rather than submitted. Nodes whose predecessors are all complete form a "Wave" and run concurrently. When a node fails, its descendants are cancelled, independent branches continue, and finished outputs are not rolled back.
* **Assets instead of paths.** An asset record carries an id, type and subtype, path, description, effective parameters, turn id, and source-asset id for provenance. The registry is append-only JSON with atomic, file-locked writes. A later turn refers to an old asset by reference, which becomes an already-completed source node in the new graph, so a revision such as restyling a landing page reruns only the affected nodes.

# Q6 Experiment Design

* **Benchmark:** UniM-90, a fixed 90-instance subset of UniM covering all seven modalities and their interleaved combinations. The authors say the subset was chosen independently of any agent's native abilities; the selection protocol is referenced to an appendix that the retrieved text does not contain.
* **Conditions:** GPT-5.6 Sol and Claude Sonnet 5, each run as a Base Agent (default environment and built-in Skills and tools, no third-party extensions) and with Omni-IO Skills loaded and everything else unchanged. The authors compare only within each agent, not across agents.
* **Metrics (UniM Evaluation Suite):** input-support rate τ (the share of instances whose inputs the agent can fully receive), the Semantic-Quality Coupled Score (SQCS: semantic correctness plus generation quality), the Interleaved Coherence Score (ICS), and the Strict and Lenient Structure Scores (StS, LeS). Absolute scores cover only supported instances; relative scores multiply by τ to cover the whole set. Instances whose required outputs cannot be produced still count as failures.
* **Qualitative:** two case studies, an 11-image art tutorial built from a video and its narration, and the product-promotion package.

# Q8 Evidence Quality

* **Supported (Table 3):**
  * *Full input coverage.* τ rises from 40.00% (GPT-5.6 Sol) and 38.89% (Claude Sonnet 5) to 100% for both.
  * *Large relative gains, mostly from coverage.* Relative SQCS rises from 26.99 to 74.94 and from 27.82 to 77.78 (+47.95 and +49.96 points). Relative ICS rises from 34.61 to 93.98 and from 32.00 to 83.28.
  * *Smaller but real gains on supported instances.* Absolute SQCS rises from 67.49 to 74.94 and from 71.53 to 77.78, although the base agent's absolute score covers only the 35-36 instances it could accept (τ × 90), while the harnessed score covers all 90.
  * *Output structure.* StS reaches 100.00 and 99.78 (from 47.84 and 52.21 absolute), and LeS 100.00 for both.
* **Weaker or bounded:**
  * *The comparison is harness versus nothing.* The baseline is the bare agent with its default tools, so most of the relative gain comes from the agent being able to accept inputs and call generators at all. No other multimodal harness or omni agent (such as Agent-Omni or OmniGAIA) is compared, and no native omni model is run on the same instances.
  * *No ablation.* The hierarchy, DEG scheduling, and Asset Registry are the paper's main design claims, but none is removed to measure its share of the gain. Cross-turn reuse, a headline feature, is shown only in the worked example and is not measured.
  * *Small, self-built evaluation.* 90 instances, one run per condition, no variance or significance reported, and a benchmark and evaluation suite from the same group. How SQCS and ICS are computed (for instance, whether a model judges them) is inherited from UniM and not restated in the retrieved text.
  * *Costs are not reported.* Tokens, latency, money, and failure rates of the external generation services are absent, and the backend models are not named, so the quality numbers cannot be attributed to the harness rather than to the chosen providers.
  * *Case studies are illustrative.* The two cases show complete outputs from both hosts but carry no human rating.

# Q9 Contributions

* A formulation of an omni-modal agent harness that extends a general-purpose agent to any-to-any production without retraining it.
* A concrete four-layer design: declarative, three-level Skills; an MCP tool contract with provider binding; dependency-checked, wave-scheduled execution graphs that isolate failures; and an append-only asset registry with provenance for cross-turn revision.
* An application-facing catalog of 27 Skills covering 38 representative tasks across seven artifact types and four capability families (understanding, generation, reasoning, retrieval).
* A first measurement on UniM-90 showing the same harness closes most of the modality gap for two different host agents.

# Q10 Next Steps

* **Ablate the design (reader note):** remove the Scenario and Expert layers (flat Atomic Skills only), replace DEG waves with sequential calls, and drop the registry, then measure quality, wall-clock time, and revision cost on multi-turn tasks.
* **Compare against native and coordinated omni systems (reader note):** run a native omni model and an Agent-Omni-style coordinator on UniM-90 to separate the harness's contribution from simply having generators available.
* **Report provider identity and cost (reader note):** with providers swappable by design, a provider-swap experiment would test the paper's own claim that Skills and graphs stay unchanged while backends evolve.
* **Asset registries elsewhere (reader note):** [Raven](2609.33439.md) routes all multi-agent handoffs through recorded file artifacts that later graphs can reuse by reference, which is the same move at the level of agents rather than tool calls. Omni-IO's append-only asset record with `source_asset_id` provenance is a small, reusable pattern for any agent that produces files across turns.
