# Q1 Problem Definition

* **Input (X):** a task on a real desktop (Linux, macOS, or Windows), a general agent with its own code, shell, and file tools, and application accessibility trees and screenshots of the current state.
* **Output (Y):** the task carried out through whichever channels the model chooses, with evidence returned after each action.
* **Constraints:** no model training, planner, or subagents, and the same interface must attach to different harnesses. All channels act on one desktop, so an action in one channel can invalidate evidence held from another. AX coverage depends on what applications expose.

# Q2 Problem Novelty

Partly new. Agents that combine GUI and code are established (CoAct-1, StateAct, ALE's GUI-as-Tool, the WeaveBench plugin), and semantic access exists in UFO2, Tactile, and [CUA Driver](../concepts/cua-driver.md), the baseline, which also has all three channels but favors best-effort background input. The new parts are how the AX channel is organized for sustained work (references bound before a compact view is drawn, batches with wait steps, diffs returned with the action), guards that work across channels, and a tool-call analysis of how models divide channels when free to choose. [OpenGCUA](2610.22200.md), not cited here, shares the premise of model-chosen interfaces but writes each step as a Python program, so the two designs differ in how actions are composed (reader comparison).

# Q3 Scientific Hypothesis

If an agent can choose among programmatic, semantic, and visual channels, and the AX channel lets it read compactly, act in batches, and see effects without a new observation, then task success and efficiency should both improve over a screenshot-centered or less composable interface, and models should use the channels in different ways.

# Q5 Key Solution Idea

**One loop, three channels.** The model picks a channel for each observation or action. Programmatic tools stay in the harness. HCU adds two MCP tools, AX and GUI, and a screenshot can inform a later AX action. Because there is no planner, the same interface attaches to Codex, Claude Code, Gemini CLI, and Grok Build.

**Compact views with stable references.** HCU keeps the acquired AX records and binds references (rN) to elements before projecting a shorter view that drops wrappers and summarizes repeats. Shortening the view does not change what a reference means, and omitted elements stay reachable with `find`.

**Batches with verification inside.** An `act` call runs up to 32 ordered steps in the evaluated version and 64 in the released one, within one window, and can include wait steps that send no input and hold until a state appears (postconditions and `assert_ax` in the evaluated version). It stops at the first failure and reports where.

**Feedback with the action.** By default a call returns per-target effects and an AX diff against the last eligible observation. HCU separates known non-delivery from an unknown effect, so input delivery is not presented as a confirmed result.

**Guards before input.** The AX target guard re-resolves each reference against live elements and rejects missing, ambiguous, or replaced targets rather than redirecting to a similar name. The GUI layout guard compares desktop bounds, visible windows, stacking order, active window, and target-point layout against the last screenshot, and on a mismatch blocks input and returns a fresh screenshot.

**A usage skill.** Distilled from mistakes in development trajectories, it covers what each channel can do, how to batch and continue from feedback, and how to verify and recover. It contains no task-specific solutions.

# Q6 Experiment Design

* **Main.** OSWorld 2.0 full set (108 tasks, 0808 release) with a 500-step limit: HCU with GPT-6 Astra (Codex, Code Mode) and Claude Opus 5 (Claude Code) at highest effort, matched CUA Driver with GPT-6 Astra, and reported results from the leaderboard, StateAct, and vendors.
* **Ablations.** OSWorld 1.0 (361 tasks), GPT-5.4 at xhigh, three runs per arm, 100 steps and 1,800 seconds: removing GUI, AX, or the skill, and CUA Driver.
* **Cross-model.** HCU against CUA Driver with GPT-5.4 (xhigh), Claude Opus 5.5 (low), Gemini 3.8 Flash (high), and Grok 4.7 (xhigh), each in its own harness, with web search, memory, subagents, and planning modes disabled and foreground input on.
* **Released version.** OSWorld 1.0, WeaveBench (114 tasks, medium effort), a 28-task UI-dependent subset of MacAgentBench, and 111 Windows Agent Arena tasks, all with GPT-5.4.

# Q8 Evidence Quality

* **Supported.**
  * *Top of the full-set results it compares.* 72.37 Partial and 32.40 Binary with GPT-6 Astra at $10.03 per task, and 72.06 and 35.19 with Claude Opus 5 at $22.67. The official Opus 5 result is 68.31 and 31.43 at $28.43, and CUA Driver with GPT-6 Astra is 68.82 and 31.5 at $10.05.
  * *More efficient than the matched baseline.* With GPT-6 Astra it uses 29.81% fewer tool calls and 21.00% less mean time. On OSWorld 1.0 with GPT-5.4 it scores 3.29 points higher with 29.80% fewer steps, 56.85% fewer input tokens, and 55.36% lower cost.
  * *Every model gains on OSWorld 1.0.* Scores rise 62.30 to 65.59 (GPT-5.4), 68.68 to 71.62 (Opus 5.5), 54.67 to 67.57 (Gemini 3.8 Flash), and 67.90 to 74.71 (Grok 4.7), with 18-57% fewer input tokens and 8-55% lower cost. Nearly all the score gain comes from tasks where HCU uses a desktop tool.
  * *AX matters more than GUI on GPT-5.4.* Removing AX costs 2.79 points, and HCU leads that arm in every run. Removing GUI leaves score within run-to-run variation (66.08 ± 1.66 against 65.59 ± 0.61) and adds 12.45% more steps.
  * *The skill fixes calling errors.* Malformed-argument rejections fall from 17.37% to 1.36%, and task-runs with repeated rejections from 44.69% to 0.37%, across 2,166 traces. The score effect is smaller, 1.59 points.
  * *Models split the channels differently.* AX is 80% of desktop calls for GPT-5.4, 68% for Grok, 51% for Gemini, and 6% for Claude, which also batches more (58% of acting calls against 11-21%). After an error, Claude rarely switches channel (1 of 55), and the others do in 25-37% of events.
  * *Other platforms.* WeaveBench 53.25 against 46.37, MacAgentBench 25 against 24 of 28 tasks, and Windows Agent Arena 80.86 against 71.89, at 46-51% lower cost.
* **Weaker or narrower than the headline.**
  * *The matched Binary gain looks like one task.* 32.40 and 31.5 fit 35 and 34 of 108 tasks, and the appendix mentions multiple runs only for the OSWorld 1.0 ablations and Opus 5.5 (reader inference). MacAgentBench likewise differs by one task. Partial and efficiency differences are the stronger evidence here.
  * *Claude's OSWorld 2.0 gain is unmatched.* Opus 5 is compared with its official loop result, not with CUA Driver under the same harness settings. OpenAI's GPT-6 Astra result (72.60, offline subset) is above HCU but is treated as unranked, and StateAct, Gemini, and Kimi rows come from other releases.
  * *70.13 is a later version on the same tasks.* The introduction's GPT-5.4 score comes from the released version, refined after the main experiments and rerun on OSWorld 1.0, against 65.59 for the evaluated version. Some of the +4.36 could be tuning on that benchmark, and the skill's "development trajectories" are not identified (reader inference).
  * *Gemini's gain is largely the step limit.* CUA Driver reaches the 100-step limit on 148 tasks against 93 for HCU, and Gemini gains 30.5 points on long tasks against 7.7 elsewhere. Part of the largest score gain is efficiency passing through a cap, which the authors show themselves.
  * *Ablations use one model.* The claim that AX contributes most rests on GPT-5.4, while Claude Opus 5.5 hardly uses AX. Channel share also does not order the scores: Grok leads at 68% AX, and Claude is second at 6%, though Claude runs at low effort and the others higher, so these scores are not directly comparable (reader observation).
  * *The guards are not ablated.* No arm removes them, or batching, wait steps, or diffs separately. Their value is shown by design argument and recorded examples, and stale-category errors are only compared between with and without the skill (107 of 14,160 against 88 of 10,783 calls). Attribution inside the AX design is therefore open (reader observation).
  * *The bitter-lesson reading goes further than the data.* AX is itself built for people using assistive technology, so it is not free of a human prior, and the comparison is between interface designs on one benchmark family rather than a test of the general claim (reader observation).
  * *Foreground only, restricted harnesses.* Foreground input on all calls and disabled harness features make the comparison clean, but CUA Driver's design goal is background use, and the user-shared desktop that [OpenGCUA](2610.22200.md) discusses is not tested.

# Q9 Contributions

* A model-directed interface that exposes programmatic, semantic, and visual channels to a general agent with no added planner.
* An AX design with stable references, batches with wait steps, and diffs returned with the action, plus cross-channel guards.
* Evidence across OSWorld 2.0, OSWorld 1.0, and three further benchmarks on Linux, macOS, and Windows that interface design alone changes score and cost.
* A tool-call analysis of how four models divide the same channels, including GUI vocabulary effects (Claude Opus 5.5 +0.82 with Claude-style actions, GPT-5.4 −2.03).

# Q10 Next Steps

* **Desktop as a programmable environment (from the paper).** AX states could enter code execution and programmatic tool calling, with batches and wait steps as the substrate.
* **Component ablations (reader suggestion).** Removing guards, wait steps, and diffs one at a time, on more than one model, would show which part of the AX design drives the gain.
* **HCU against code-as-action (reader suggestion).** Running HCU and OpenGCUA on the same tasks and models would compare structured AX batches with programs over GUI and shell.
* **Poor-accessibility applications (reader question).** Scores could be split by how much of each application AX exposes. Net step savings already concentrate in LibreOffice and Thunderbird tasks, but the paper does not measure AX coverage per application.
* **Training on the interface (reader question).** Frozen models learn the channels only from a skill. Would training on these channels change Claude-style GUI preference or reduce calling errors further?
