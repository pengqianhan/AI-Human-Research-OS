# Q1 Problem Definition

* **Input (X):** an LLM-based system's ongoing stream of user interaction, task context, and accumulated knowledge — spanning parametric weights, transient inference-time state (KV-cache, hidden states), and externally retrieved or user-supplied text.
* **Output (Y):** for a given query, a scheduled combination of plaintext, activation, and parameter memory injected into the model's reasoning, plus the system-level lifecycle state (created/activated/merged/archived/expired) of every memory unit involved.
* **Core problem:** LLMs have no unified way to manage memory as a controllable resource. Parametric memory is expensive to update and opaque; RAG is a stateless "retrieve-and-compose" patch with no lifecycle tracking, versioning, or permission model; and neither treats memory as schedulable across users, tasks, and platforms — so systems cannot sustain long-context coherence, absorb evolving knowledge, personalize durably, or migrate memory across deployments.
* **Scope:** proposes a system architecture (three layers, four core modules) plus MemCube, a unified memory-unit abstraction, and evaluates the resulting implementation (MemOS-1031) end-to-end against memory-system baselines; it does not modify the underlying LLM's pretraining.

# Q2 Problem Novelty

Explicit memory management for LLMs is an active area (RAG variants, knowledge editing, KV-cache optimization, agent memory tools such as Mem0 and Zep), but the paper argues these efforts operate at the tool or mechanism level — insert/update/delete operations layered onto an otherwise implicit memory substrate — without a system-level resource model. The paper frames this as a fourth stage in the field's progression (memory definition and exploration → human-like memory → tool-based memory management → systematic memory governance), positioning MemOS as the first to bring OS-style resource abstraction (scheduling, lifecycle, permissions, migration) uniformly across all three memory types rather than treating each type as a separate mechanism.

# Q3 Scientific Hypothesis

If plaintext, activation, and parameter memory are encapsulated in a common schedulable unit (MemCube) with shared metadata for identity, governance, and behavioral usage, and a three-layer system (interface, operation, infrastructure) manages that unit's full lifecycle and cross-type transformation, then the resulting system will sustain long-context coherence, personalization, and knowledge consistency better than RAG-style or single-mechanism memory tools, while remaining efficient and robust enough for production deployment.

# Q4 Related Work and Key People

* Extends the authors' own prior work, Memory 3 (cited as [1] throughout), which first proposed an explicit memory layer between parameter storage and external retrieval and encoded external knowledge as sparse KV pairs injected into attention; MemOS generalizes that idea into a full three-type (plaintext/activation/parameter), OS-managed system.
* Directly benchmarked against MIRIX (six specialized memory components), Mem0 (slot-based extraction/update memory — see [Mem0](2504.19413.md)), Zep (time-aware knowledge-graph memory), Memobase, Supermemory (dynamic knowledge graph), and MemU (multi-modal summarization into memory files) — all reimplemented on the same GPT-4o-mini backbone for parity.
* Draws its OS analogy from classical operating-system resource management (schedulers, file systems, ACLs) and from vLLM's PagedAttention, which the paper cites as an existing instance of OS-inspired KV-cache management.
* Related to knowledge-editing lines of work (ROME, MEMIT, LoRA-based adapters) that the paper categorizes as parameter-memory mechanisms MemOS can schedule alongside plaintext and activation memory rather than compete with directly.
* Authors: a 39-author team led by Zhiyu Li and Feiyu Xiong, credited to MemTensor (Shanghai) Technology Co., Ltd. and nine academic co-affiliations (Tongji, Zhejiang University, USTC, Peking University, Renmin University, Beihang, Shanghai Jiao Tong, and the Institute for Advanced Algorithms Research, Shanghai); originally submitted 2025-07-04, with a substantially expanded v4 as of 2025-12-03 (the version retrieved for this note).

# Q5 Key Solution Idea

**Three memory types, one unit.** MemOS distinguishes Plaintext Memory (externally retrieved/injected text, structured graphs, prompt templates — editable and traceable), Activation Memory (inference-time KV-cache, hidden states, attention weights — short-term and implicitly activated), and Parameter Memory (knowledge baked into model weights, modularly extensible via LoRA/adapters). Every unit of any type is wrapped in a MemCube: a Memory Payload (the semantic content) plus Metadata split into Descriptive Identifiers (timestamp, origin signature, semantic type), Governance Attributes (access control, TTL/decay, priority, compliance tags), and Behavioral Usage Indicators (access frequency/recency, a Contextual Fingerprint, a Version Chain). The behavioral indicators drive Policy-Aware Scheduling and three defined cross-type transformations: frequently used plaintext can be pre-compiled into activation vectors; stable plaintext/activation content can be distilled into parameter modules ("capability plugins"); and cold or outdated parameters can be offloaded back into plaintext.

**Three-layer architecture.** The Interface Layer's MemReader parses natural-language requests into a structured MemoryCall (task intent, time scope, memory type, access intent), exposed through a Memory API (Provenance, Update, LogQuery) and a pipeline mechanism for chaining operations (retrieve → augment → update → archive). The Operation Layer is the control center: MemOperator builds tag/graph/hierarchical indexes for retrieval, MemScheduler selects and orders which memory types to invoke based on task intent and context, and MemLifecycle tracks each unit through five states (Generated, Activated, Merged, Archived, Expired). The Infrastructure Layer handles storage and governance: MemGovernance enforces access control and audit logging, MemVault manages multiple repositories, MemLoader/MemDumper handle import/export and cross-platform sync, and MemStore provides publish-subscribe sharing across agents (e.g., a domain expert publishing a paid "memory plugin"). The paper draws an explicit component-by-component mapping from classical OS concepts (scheduler → MemScheduler, file system → MemVault, system call → Memory API, device driver → MemLoader/Dumper, package manager → MemStore, ACLs → MemGovernance) to argue the design generalizes OS resource-management discipline to memory.

# Q6 Experiment Design

All end-to-end comparisons use the same GPT-4o-mini backbone across every baseline (MIRIX, Mem0, Zep, Memobase, Supermemory, MemU, and MemOS-1031) on an 80GB H800 GPU, with each method's configuration tuned to its own best validation performance — controlling for backbone choice while allowing each system its optimal operating point.

* **Long-context/multi-session (LoCoMo, LongMemEval):** measures LLM-judge scores across task categories (single-hop, multi-hop, temporal reasoning, open-domain) plus F1 and context-token cost.
* **Personalization (PreFEval, PersonaMem):** PreFEval tests personalized-response rate under 0 and 10 injected irrelevant conversation turns, tracking error types (preference-unaware, hallucination, inconsistency, unhelpful); PersonaMem reports one-in-four precision on inferred user profile/preference.
* **Component ablations:** chunk-size/Top-K sweep on LoCoMo; retrieval-robustness under load (10/40/100 QPS) measuring P99/P90/mean latency and success rate for add/search operations; a separate controlled study of KV-based activation-memory acceleration (not detailed with numbers in the retrieved sections).

This design directly tests the paper's hypothesis by holding the backbone constant so that quality/latency/token-cost differences are attributable to the memory architecture rather than the underlying LLM.

# Q7 Datasets and Code

Benchmarks used: LoCoMo, LongMemEval, PreFEval, PersonaMem (all third-party, cited but not introduced by this paper). Code is open-sourced at [github.com/MemTensor/MemOS](https://github.com/MemTensor/MemOS), which links back to this arXiv paper and a companion short paper (arXiv:2505.22101); the released system is branded MemOS-1031 in the evaluation tables.

# Q8 Evidence Quality

MemOS-1031 reports the best or near-best score on essentially every reported metric across four benchmarks and six to seven baselines: LoCoMo overall LLM-judge 75.80 (next-best Memobase 72.01) with overall F1 45.27; LongMemEval overall 77.8 (next-best Memobase 72.4); PreFEval Personalized Response 77.2 with 0 turns and 71.9 with 10 irrelevant turns (next-best Mem0 at 65.9/63.7), plus the lowest Preference-Unaware error rate; PersonaMem precision 61.2 (next-best Memobase 58.9). Retrieval-robustness numbers show MemOS-1031 sustaining 100% success at up to 100 QPS while several baselines (MemU, Memobase, Zep) degrade sharply in success rate or latency under 40 QPS. These are consistent, large margins across independent benchmarks, which is stronger evidence than a single-benchmark win. However, several gaps limit how far the evidence generalizes: all comparisons use one backbone (GPT-4o-mini) and one hardware configuration, so it is unconfirmed whether the ranking holds under a stronger or differently-sized model; the ablation studies (chunk size/Top-K, KV-acceleration) are described qualitatively in the retrieved text without the specific numeric tables; and — as is generally true of architecture papers introducing both the system and its own named checkpoint (MemOS-1031) — the retrieved material does not report who tuned each baseline's configuration or whether tuning effort was matched across systems.

# Q9 Contributions

1. MemCube: a unified encapsulation (Memory Payload + three-part Metadata) that lets plaintext, activation, and parameter memory be scheduled, versioned, and transformed into one another through one interface, rather than as three separate mechanisms.
2. A three-layer OS-inspired system architecture (Interface/Operation/Infrastructure) with named modules (MemReader, MemScheduler, MemLifecycle, MemOperator, MemGovernance, MemVault, MemStore, MemLoader/Dumper) that operationalizes controllability, plasticity, and evolvability as explicit design pillars rather than emergent properties.
3. An empirical demonstration (MemOS-1031) that this architecture outperforms six memory-system baselines across four benchmarks spanning long-context QA, personalization, and preference understanding, while also sustaining lower latency and higher success rates under concurrent load.

# Q10 Next Steps

* The paper's own stated directions: a Memory Interchange Protocol (MIP) for cross-LLM/cross-app memory sharing with trust and compatibility rules; self-evolving MemBlocks that optimize and reconstruct themselves from usage feedback without manual maintenance; and a decentralized "memory marketplace" for asset-level memory transactions.
* Open questions the retrieved material leaves unresolved: how MemOS's advantage changes with backbone model strength or size; what governs conflict resolution when Plaintext→Parameter distillation encounters memory that later needs to be reverted (Parameter→Plaintext); and how MemStore's proposed monetized/access-controlled memory sharing would be audited or secured against leakage across the multi-user, multi-agent boundaries the paper motivates in its four application scenarios.
* **Research-OS fit:** MemOS's MemCube (lifecycle state + provenance + version chain per memory unit) is a concrete instance of the "auditable state" concern this wiki tracks under [Agent memory](../topics/agent-memory.md) — worth comparing against Mem0's simpler ADD/UPDATE/DELETE/NOOP tool-call design and Zep's temporal-graph approach for what the added governance machinery buys empirically versus its complexity cost.
