# Q1 Problem Definition

* **Input (X):** a candidate public Python repository (package metadata, a nonempty local test suite, at least five implementation files, under 40,000 lines; no external services, network, GUI, or special hardware), excluding repositories used by established coding benchmarks.
* **Output (Y):** a training environment e = (I, W, V, O): a language specification I, an isolated workspace and runtime W, a verifier V built from the repository's tests, and the original code kept hidden as oracle O. An agent receives (I, W) and must rebuild the project; V scores it in [0, 1].
* **Constraints:** the oracle must score 1 and the empty workspace 0; revisions are judged without running a solving agent or training a model; the loop has a fixed budget of up to 12 rounds.

# Q2 Problem Novelty

Repository-level environment pipelines such as DeNovoSWE and MindForge are linear: they fix documentation or builds around a fixed reference implementation and discard repositories that still fail. ProgramGym uses execution diagnostics and coverage to repair builds and strengthen tests, which improves reliability but not how much work a task demands. BenchEvolver, SETA, and DataMaster use learner rollouts or downstream training as feedback, which is slow and costly for long-horizon tasks. RepoFactory jointly revises the oracle implementation, specification, and tests, and steers them with cheap proxies for training value (call-graph coupling and code size plus dependency breadth) instead of model feedback; the paper claims to be the first to evolve full-repository generation environments this way.

# Q3 Scientific Hypothesis

Static properties of the oracle code, how interdependent its functions are and how much code and how many dependencies it involves, are usable proxies for an environment's training value. Optimizing them, together with a validity check, both recovers repositories a linear pipeline would discard and produces environments whose trajectories train better long-horizon coding agents.

# Q5 Key Solution Idea

1. **Objective Q = A · C · S.** Validity A is 1 only if the oracle gets full reward and the untouched workspace zero. Structural coupling C = R / N², the share of ordered function pairs (including self-pairs) reachable in the oracle's static internal call graph. Implementation scope S = log10(LOC) + log10(1 + D) − 2, with D the number of direct runtime dependencies.
2. **Construction pipeline.** Search and filter repositories; build a Docker image and keep the repository only if all tests pass offline in a fresh container; extract public classes, functions, signatures, and test-imported symbols with an AST scanner; a synthesis agent writes the specification and an API manifest, which are checked against symbols the tests import.
3. **Environment Evolution Loop.** Repair validity first from the validation report. Then, if S < 0.5 or C < 0.01, prioritize that term; otherwise the agent chooses which to raise. Each revision of oracle, specification, and tests is re-validated, and kept only if the targeted score strictly increases; up to 12 rounds. All construction agents use Qwen3.8-Max.
4. **Training data.** Qwen3.8-Max runs five times per environment; trajectories with reward above 0.5 that pass deterministic and LLM-judge quality checks are kept: 10,947 samples from 5,577 environments, used for supervised fine-tuning (three epochs, peak learning rate 1e-6).

# Q6 Experiment Design

* **Model.** Qwen3.5-35B-A3B fine-tuned on the trajectories (RepoHorizen-35B-A3B); a variant trained without environment evolution.
* **Benchmarks.** NL2Repo-Bench (build a repository from a natural-language description), SWE-bench Verified, SWE-bench Pro, SWE-bench Multilingual, Terminal-Bench 2.1; Claude Code 2.1.140 harness, 262,144-token context with compaction at 80%, temperature 1.0.
* **Data-source comparison.** Six open SWE datasets (OpenSWE, R2E, ScaleSWE, SWE-smith, SWE-rebench, SWE-rebench-v2), trajectories collected and cleaned the same way, 11,000 each, fine-tuning the same base; prior published results listed separately.
* **Scaling.** NL2Repo accuracy against the number of training environments, and across 9B, 27B, and 35B-A3B bases.
* **Objective ablations.** Recovery: 500 sampled repositories with up to three repair steps versus none. Training value: two evolution runs from the same 1,000 environments, one optimizing S and one C; environments after rounds 3, 6, 9, 12 become Levels 1 to 4, each supplying 2,000 trajectories for fine-tuning.

# Q8 Evidence Quality

**Main results (Table 1, Claude Code harness).**

| Model | NL2Repo | Verified | Pro | Multilingual | TB2.1 | Avg. |
|---|---|---|---|---|---|---|
| Qwen3.5-35B-A3B (base) | 23.8 | 65.8 | 42.4 | 59.7 | 33.7 | 45.1 |
| RepoHorizen-35B-A3B | 46.4 | 72.2 | 47.6 | 61.0 | 40.5 | 53.5 |
| w/o environment evolution | 41.3 | 70.9 | 45.1 | 60.8 | 39.3 | 51.5 |
| Qwen3.5-122B-A10B | 27.7 | 73.4 | 49.5 | 67.2 | 44.9 | 52.5 |
| Ornith-1.0-35B | 34.6 | 75.6 | 50.4 | 69.3 | 62.8 | 58.5 |
| Qwen3.8-Max (teacher) | 55.9 | 85.6 | 67.7 | - | 86.6 | 74.0 |

On NL2Repo RepoHorizen passes GPT-5.5 (45.1), Gemini-3.1 Pro (33.4), DeepSeek-V4-Pro (38.5), and MiniMax-M3 (42.1). Evolution adds 5.1 NL2Repo points and 2.1 average points over the no-evolution variant.

**Data sources (Table 2).** RepoFactory leads all six controlled baselines on all five benchmarks; on NL2Repo 46.4 against 25.2 for the best (OpenSWE). The best prior published NL2Repo figure (varying harnesses) is 28.9.

**Scaling.** NL2Repo rises from 23.8 with no RepoFactory data to 36.5 at 3,000 environments and 46.4 at 5,577, without visible saturation. Gains across the 9B, 27B, and 35B-A3B bases range from 12.2 to 22.6 points; the 35B-A3B gains most.

**Objective ablations.** Repair raises validated environments from 169 to 347 of 500 (33.8% to 69.4%), mostly from the first repair. Optimizing S lifts NL2Repo from 30.2 (Level 1) to 32.9 (Level 4) with longer trajectories; optimizing C reaches 32.5 with shorter interactions and slightly fewer supervised tokens. Teacher success falls from 23.0% in the lowest-scope fifth of environments to 13.4% in the highest.

**Data statistics.** Median oracle 4.2k lines and 26 source files; 2.09M statically identified test definitions; median trajectory 64 assistant turns; largest domain 12.5% of environments.

**Limits on the evidence.**

* Single training run per configuration, no variance reported; the S and C level ablations differ by 2 to 3 points on fixed 2,000-trajectory sets (reader observation).
* The gains come from supervised distillation of a much stronger teacher (Qwen3.8-Max scores 55.9 on NL2Repo); Table 2 holds the teacher fixed across data sources, as the paper notes, but the six baselines are issue-resolution data, so part of the NL2Repo margin plausibly reflects matching the benchmark's task format rather than general training value (reader inference). Gains on the four other benchmarks are 1.3 to 6.8 points.
* The retrieved text does not state how many environments or trajectories the no-evolution variant was trained on, so the 5.1-point evolution effect cannot be checked for matched data size.
* The Avg. column averages over different benchmark sets when a cell is missing (Kimi-K2.6's 70.7 is the mean of four scores without NL2Repo; Qwen3.8-Max, GPT-5.6-sol, and MiniMax-M3 lack Multilingual), so frontier averages are not comparable with each other or with RepoHorizen's (reader arithmetic). The headline +8.5 is the mean of per-benchmark gains; the Avg. columns differ by 8.4.
* Python only (stated); the proxies describe structure, not which capabilities a task exercises (stated).

# Q9 Contributions

1. RepoFactory, a pipeline from real repositories to 10,159 verifiable full-repository generation environments across 17 domains.
2. The Environment Evolution Loop: a validity-gated objective over call-graph coupling and implementation scope that guides joint revision of oracle, specification, and tests without solver rollouts.
3. RepoHorizen-35B-A3B and controlled comparisons with six SWE data sources, scaling curves, and per-term ablations.

# Q10 Next Steps

* **Stated by the paper.** Other programming languages; proxies that capture the capabilities a task requires.
* **RL on the environments.** The environments come with verifiers, yet only SFT on teacher trajectories is reported; reinforcement learning from the verifier would test whether the environments add value beyond the teacher (reader suggestion).
* **Proxy validation.** Correlate C and S with per-environment learning gain, not only teacher success, to check that coupling is a training-value signal rather than a difficulty signal.
* **Data-matched evolution ablation.** Train the no-evolution variant on the same number of environments and trajectories.
