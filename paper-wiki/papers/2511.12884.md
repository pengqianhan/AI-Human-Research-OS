# Q1 Problem Definition

* **Input (X):** a corpus of *agent context files* — project-root Markdown files such as `CLAUDE.md`, `AGENTS.md`, and `copilot-instructions.md` that agentic coding tools (Claude Code, OpenAI Codex, GitHub Copilot) load as persistent, project-level instructions — plus, for a maintenance analysis, the git commit history of each such file.
* **Output (Y):** an empirical characterization of these files along four axes: (RQ1) structural characteristics (size, readability, header-depth hierarchy), (RQ2) maintenance cadence (commit frequency, inter-commit interval, added/deleted lines), (RQ3) a 16-category instruction-content taxonomy with per-category prevalence, and (RQ4) whether that taxonomy can be assigned automatically by an LLM classifier.
* **Core problem:** agentic coding tools depend on these files to learn a project's architecture, conventions, and constraints, but official tool documentation only offers high-level guidance (e.g. "describe architecture and workflows"), so developers currently design these files by trial and error with no empirical basis for what content, structure, or maintenance practice actually works — a gap the paper calls out as the origin of a persistent, real software artifact operating entirely outside the empirical software-engineering literature on documentation.
* **Scope:** purely observational and root-directory-scoped — files are collected only from the root of each repository via exact filename match (`CLAUDE.md`, `AGENTS.md`, `copilot-instructions.md`, case-insensitive), from 1,925 repositories drawn from the AIDev dataset (Li et al., 2025b) after filtering to repositories with at least 5 GitHub stars; no causal claim is made about whether any file property affects agent task performance.

# Q2 Problem Novelty

This is an extension, not a first attempt: the same author group's prior PROFES'25 paper (Chatlatanagulchai et al., 2025) studied 253 Claude Code files only. This paper scales that corpus roughly 9x (2,303 files) and adds two more tools (OpenAI Codex's `AGENTS.md`, GitHub Copilot's `copilot-instructions.md`), letting every finding be reported as a per-tool comparison rather than a single-tool description, and adds two new content categories (Maintenance, Debugging) that the enlarged, multi-tool corpus surfaced. Positioned against this repository's [Context engineering](../topics/context-engineering.md) topic, every other entry there studies *runtime* context assembly, compression, or state-externalization mechanisms operating during an agent's execution; this paper instead treats the *static, version-controlled instruction file itself* — the artifact that seeds that runtime context before a session starts — as the unit of empirical study, and is the first paper in this topic to do so. The paper's own Related Work draws the same boundary against the broader agentic-software-engineering literature: prior work studies agents' internal architecture and coordination (planning, tool use, multi-agent collaboration) or transient, task-level prompts (chain-of-thought, in-the-moment instructions), while agent context files are persistent, project-level, and externally authored by developers rather than the agent — a class of artifact the paper argues has not been examined at scale in either the agentic-coding or the classical software-documentation literature (README/API-doc studies) it also reviews.

# Q3 Scientific Hypothesis

If agent context files are mined and coded at scale across multiple agentic coding tools, they will show measurable regularities that trial-and-error authorship alone would not predict: (a) these files behave as actively-maintained, incrementally-evolving configuration artifacts rather than write-once documentation, in contrast to traditional READMEs; (b) their instructional content is systematically skewed toward functional/operational categories (build, architecture, implementation) at the expense of non-functional requirements (security, performance); and (c) this skew is not an artifact of manual coding noise, because an LLM classifier trained on the same category definitions can recover the same categories with useful accuracy, making ecosystem-scale automated monitoring feasible.

# Q5 Key Solution Idea

* **Corpus construction:** identify repositories using agentic coding tools via the AIDev dataset (Li et al., 2025b), filter to repositories with >=5 GitHub stars (8,370 candidates) to exclude toy projects, then use the GitHub REST API to case-insensitively match `CLAUDE.md`, `AGENTS.md`, and `copilot-instructions.md` in each repository's root directory, yielding 922 Claude Code, 694 OpenAI Codex, and 687 GitHub Copilot files across 1,925 repositories.
* **RQ1 (characteristics):** word count via `\w+` regex, readability via Flesch Reading Ease, and Markdown header-level counts (H1-H6) per file; cross-tool differences tested with Mann-Whitney U and Cliff's delta effect size.
* **RQ2 (maintenance):** mine each repository's git history for every commit that adds/deletes/modifies the context file, recording timestamp and lines added/deleted per commit (5,655 Claude Code, 2,767 OpenAI Codex, 2,237 GitHub Copilot commits total), then compare commit-count, inter-commit-interval, and added/deleted-line distributions across tools with the same statistical tests.
* **RQ3 (content taxonomy):** two-phase manual coding. Phase 1 (label creation): extract all H1/H2 titles from Claude Code files, prompt three LLMs (Claude Opus 4.1, Gemini 2.5 Pro, GPT-5) for candidate category labels, have one author curate and two authors review, converging on 16 categories (adding Maintenance and Debugging beyond the prior 14-category scheme). Phase 2 (label assignment): two inspectors independently multi-label 332 Claude Code files against the 16 categories (2,227 total assignments, 80.3% raw agreement, 438 disagreements), with a third inspector resolving conflicts to a final 2,069 label assignments.
* **RQ4 (automatability):** frame the same 16-category scheme as multi-label binary classification; prompt GPT-5 with the full file content plus a description and representative examples per category, score against the RQ3 human-coded ground truth with per-category precision/recall/F1 and a support-weighted micro average.

# Q6 Experiment Design

Purely observational/descriptive — there is no intervention or ablation, only cross-tool statistical comparison (Mann-Whitney U, alpha=0.05, with Cliff's delta effect-size thresholds from Romano et al., 2006) and classifier-vs-human-ground-truth evaluation:

* **RQ1:** Claude Code (median 485 words) and GitHub Copilot (535 words) files are statistically indistinguishable in length from each other but both significantly longer than OpenAI Codex (335.5 words, small effect, d~0.21-0.22). Readability: Claude Code is hardest to read (median FRE 16.6, "very difficult" — comparable to dense legal/academic text), GitHub Copilot next (26.6, small effect vs. Claude Code, d=0.24), OpenAI Codex easiest (39.6, "difficult"; medium effect vs. Claude Code, small vs. Copilot). Structure: median exactly 1 H1 across all tools, 6-7 H2 headings; Copilot (median H3=12.0) and Claude Code (11.0) are more granular than Codex (9.0, small effect); H5+ headers are essentially absent (H5 appears in only 6 Claude Code files; H6 never).
* **RQ2:** 67.4% of Claude Code files receive multiple commits (vs. 59.7% Copilot, 59.2% Codex); Claude Code gets significantly more commits than both other tools (medium effect vs. Copilot, d=0.35; small vs. Codex, d=0.15). Median inter-commit interval: 70.7 hours (Copilot, ~3 days) vs. 24.1 hours (Claude Code) vs. 22.0 hours (Codex, ~1 day each), all pairwise differences significant (p<0.001, up to medium effect d=0.37 for Copilot vs. Claude Code). Deletions are consistently negligible (median <15 words); additions are larger and more variable, with Claude Code's median addition (57 words/commit) the largest though with only a negligible effect size.
* **RQ3 (Table 3, on the 332-file Claude Code subset):** most prevalent categories are Testing (75.0%), Implementation Details (69.9%), Architecture (67.7%), Development Process (63.3%), and Build and Run (62.3%); least prevalent are Project Management (5.4%), UI/UX (8.7%), Performance (14.5%), and Security (14.5%).
* **RQ4 (Table 4, GPT-5 vs. human labels, 2,069 assignments):** micro-average precision 0.73, recall 0.86, F1 0.79. Strongest categories: Testing (F1 0.94), Implementation Architecture (0.93), Build & Run (0.92), Implementation Details (0.89), System Overview (0.89). Weakest: Project Management (0.42, only 18 supporting instances), AI Integration (0.48), Documentation (0.57), Quality/Maintenance (0.56), UI/UX (0.56).

# Q8 Evidence Quality

Internal validity is handled reasonably: RQ3 labeling used two independent inspectors with a third resolving conflicts, and the paper reports the raw 80.3% agreement rate transparently rather than only a post-hoc-adjudicated number. The authors' own Construct Validity section flags a real limitation directly relevant to interpreting Table 3: category assignment was binary presence/absence, so a file mentioning code style in one line counts identically to one with an extensive style guide — the reported percentages measure topic *prevalence*, not depth or quality of coverage. External validity is also self-acknowledged as limited: only three tools and only root-directory files are scanned (nested or subdirectory-scoped context files, which some tools support, are excluded by construction), and the >=5-star filter selects toward more mature/visible open-source repositories rather than a representative sample of all agentic-coding usage (e.g., private/enterprise repos are entirely absent). The RQ4 evaluation is methodologically clean in one respect worth flagging explicitly: although three LLMs (including GPT-5) were used to help *generate candidate category labels* in Phase 1, the ground-truth *label assignments* used to score RQ4's GPT-5 classifier came entirely from the two-human-plus-arbiter Phase 2 process, so the RQ4 evaluation is not circularly validating GPT-5 against its own earlier-stage outputs. The RQ4 error pattern (high F1 on concrete/frequent categories, low F1 on abstract or rare ones, notably Project Management at only 18 supporting instances) is internally consistent with what a support-limited multi-label classifier would be expected to do, which is a soft check that the reported numbers are not overfit reporting.

# Q9 Contributions

1. The first large-scale, multi-tool (Claude Code, OpenAI Codex, GitHub Copilot) empirical study of agent context files, mining 2,303 files across 1,925 repositories — a 9x scale-up and 2x tool-coverage increase over the same authors' prior single-tool study.
2. Establishes that agent context files are long and "very difficult" to read by standard readability metrics (median FRE from 16.6 to 39.6 depending on tool), organized in a consistently shallow single-H1 hierarchy, and — unlike traditional README documentation, which the cited literature shows is largely write-once — are actively and incrementally maintained (67.4% of Claude Code files touched by multiple commits, median 1-3 day inter-commit intervals, growth via small additions rather than deletions).
3. Constructs and validates a 16-category instruction taxonomy from real file content, quantifying a specific, actionable content gap: functional categories (Build and Run, Implementation Details, Architecture, Testing) dominate at 62-75% prevalence while non-functional requirement categories (Security, Performance, UI/UX) each appear in under 15% of files.
4. Demonstrates that this 16-category taxonomy is automatable with useful accuracy (GPT-5, 0.79 micro-F1), enabling future ecosystem-scale, longitudinal monitoring of agent-context-file practices without exhaustive manual coding — while also showing where automation currently fails (abstract, low-frequency categories like Project Management).

# Q10 Next Steps

* The authors propose defining and measuring "context debt" as a new category of technical debt specific to agent-facing configuration, and building CI-integrated linters or divergence detectors that check whether a file's stated Build-and-Run commands (62.3% prevalence) still match the actual `package.json`/`Makefile` — an automated co-evolution check the paper motivates but does not build.
* They call for new benchmarks or evaluation frameworks that explicitly test an agent's adherence to non-functional requirements declared in its context file (current benchmarks like SWE-bench reward functional correctness only, so the Security/Performance blind spot this paper documents has no benchmark pressure against it).
* For tool builders, they suggest template scaffolds pre-populated with the 16 identified categories (with explicit NFR placeholders) and semantic, category-aware context retrieval (route a debugging task to the Debugging/Testing sections rather than naive full-file chunking).
* **Research-OS fit:** this paper is directly self-referential for a repository whose own root instruction chain (`INSTRUCTION.md`/`CLAUDE.md`) is exactly the artifact class studied here. Its 16-category taxonomy offers a concrete, evidence-based checklist against which this repository's own context files could be audited (e.g., whether Security/Performance guidance is present at all, matching the paper's documented blind spot), and its finding that healthy context files evolve via small, frequent additions rather than large rewrites matches this repository's own iterative instruction-maintenance practice. This is currently the wiki's only entry studying the static content of agent context files as such (as opposed to runtime context-management mechanisms), so it sits in [Context engineering](../topics/context-engineering.md) as a new, complementary angle within that topic rather than alongside a direct sibling.
