# TL;DR

Self-improving agents turn their own experience into persistent changes: either slow updates to model weights or faster changes to prompts, memory, tools, and control logic. The survey provides a common map for deciding where an agent should adapt and how that adaptation should be evaluated; it is most useful to researchers and engineers building adaptive agents, harnesses, memory or tool systems, and evaluation gates.

# Overview

The survey connects the historical roots, formal definitions, mechanism taxonomy, application domains, evaluation protocols, and open problems of foundation-model-based self-improving agents. Its scope is narrower than all adaptation: an execution must produce a signal that is committed as a durable change to the model or its operational scaffold and remains available after the immediate task boundary. A longer context, an in-session retry, or a temporary plan affects current behavior but is not self-improvement unless some result persists.

The paper models an agent at iteration `t` as `A_t = (θ_t, Σ_t)`. Here, `θ_t` is the foundation model's parameters and `Σ_t = (p_t, m_t, T_t, g_t)` is the scaffold: reusable prompts, memory, tools, and control/routing/safety logic. Transient working state `X_t`, including the current dialogue or plan, affects behavior but is not itself self-improvement unless some result is consolidated into `θ` or `Σ`.

This distinction yields two complementary timescales. **Foundation-model improvement** changes `θ`: it is slow, costly, difficult to attribute or reverse, but can amortize a capability across tasks. **Scaffold improvement** changes `Σ`: it is usually faster, explicit, inspectable, and reversible, but more context-dependent and prone to memory, tool, prompt, or workflow drift. The paper's most useful deployment principle follows from this asymmetry: explore in the scaffold, validate there, and consolidate into weights only after the behavior proves stable and transferable.

# Framework

The survey defines self-improvement through a self-induced update operator. The current agent executes a procedure in a task or deployment context, producing trajectories, critiques, verifier results, preferences, proposed edits, or other learning signals. An update operator then commits a persistent change. The agent can be self-referential in two senses:

1. **Indirect, distribution-level self-reference:** the agent generates demonstrations, judgments, or trajectories that an optimizer later uses to update model parameters.
2. **Direct, action-level self-reference:** the agent edits its own prompts, memories, tool interfaces, routing logic, or scaffold source code.

The taxonomy first separates the **update target** and then the **signal form**:

| Update target | Persistent substrate | Main signal families | Characteristic trade-off |
|---|---|---|---|
| Foundation model | Model parameters `θ` | Synthetic demonstrations; self-evaluation; environment-grounded experience | Broad consolidation, but expensive and difficult to audit or roll back |
| Prompt | Reusable instructions `p` | Scalar scores; critiques; population fitness; textual gradients | Cheap and interpretable, but vulnerable to template and benchmark overfitting |
| Memory | Memory objects and structures `m` | Salience, utility, retrieval failure, contradiction, capacity pressure | Cumulative experience, but susceptible to poisoning, staleness, and retrieval noise |
| Tools | Tool set and interfaces `T` | Routing outcomes, execution errors, verifier feedback, capability gaps | Expands executable capability, but increases integration and permission risk |
| Full scaffold | Control logic and source `Σ` | Tests, task outcomes, critiques, cost and safety signals | Deep architectural search, but the improver and evaluation boundary become critical attack surfaces |

The paper also defines a **skill** as a named, reusable serialization of an update operator. A skill may live in a prompt, memory entry, tool, control routine, or model weights; its identity is the reusable update it encodes, not its storage substrate. Object-level skills act on the task world, whereas meta-level skills modify the agent itself. A skill library is therefore a store plus retrieval policy over retained updates.

**Reader-constructed example.** Suppose a coding agent repeatedly fails to configure a repository, then discovers a sequence that passes the environment checks. Retrying that sequence within the same issue changes only transient execution state. Saving it as a verified reusable routine changes the tool or memory scaffold; later distilling the routine into model weights changes the foundation model. The example makes the survey's persistence boundary and fast-scaffold/slow-model distinction concrete; it is explanatory synthesis, not a worked example reported by the paper.

# Key Techniques

## Foundation-model improvement

The model-update branch is organized by the dominant source of supervision:

* **Intrinsic generative demonstrations:** the agent creates instruction–response pairs, reasoning traces, execution logs, problem curricula, or multimodal examples, optionally filtered by confidence, tests, formal verifiers, or diversity criteria before fine-tuning. This lowers annotation cost but can create model collapse, knowledge bubbles, confident-error amplification, and catastrophic forgetting.
* **Intrinsic evaluative feedback:** an internal or auxiliary evaluator emits scores, preferences, confidence estimates, critiques, or revised answers that train the model. Rubric-based, consistency-based, and corrective feedback are flexible but couple the improver to a critic that may share its blind spots. Recommended safeguards include heterogeneous evaluators, external anchors, disagreement-as-uncertainty, and periodic review of the rubric and reward model.
* **Extrinsic exploratory experience:** the agent learns from grounded task trajectories or learned proxy environments. Programmatic verifiers such as unit tests provide the clearest signal; learned reward models cover less formal tasks; self-generated tasks can drive curricula while the environment still decides success. World models reduce interaction cost but introduce exploitable, plausibly wrong dynamics.

## Prompt improvement

Prompt improvement ranges from derivative-free search on scalar scores to qualitative critique, population-based evolution, and structured textual gradients. The important target boundary is between changing a reusable system policy and assembling dynamic per-case context. Both are scaffold adaptations, but only the former directly alters the stable behavioral prior; context selection changes how that prior is conditioned on one execution.

## Memory improvement

The paper separates memory into **objects**, **structures**, and **processing**. Objects may be compressed lessons and routines, curated raw evidence, or hybrid records. Structures may be chronological, hierarchical, graph-based, or vector-indexed. Processing becomes an adaptive CRUD loop: selectively create memories, retrieve by task utility rather than similarity alone, revise conflicting or stale entries, and delete low-value content without erasing rare but important evidence. This makes memory a governed lifecycle rather than an append-only log.

## Tool governance

Tool improvement is framed as governance metacognition with three functions. **Dynamic routing** chooses and sequences tools as the pool grows; **iterative refinement** turns error-prone programs or documentation into verified reusable skills; **autonomous creation** synthesizes and registers tools when current capabilities are insufficient. The survey stresses that creation is incomplete without validation, documentation, permission control, standardized integration, and a policy for deciding what enters the active tool pool.

## Full-scaffold improvement

The deepest branch treats the agent's executable harness as mutable code. The current scaffold proposes a patch to itself, while tests, regression suites, safety checks, or other verifiers decide whether the candidate replaces the active version. Systems such as ADAS, Self-Taught Optimizer, Darwin Gödel Machine, Huxley–Gödel Machine, and Live-SWE-agent instantiate bounded versions of this loop. The practical advance is not unrestricted recursive improvement; it is versioned, verifier-gated search over an explicit program substrate.

# Case Studies

## Application Domains

The survey maps these mechanisms to domains according to the feedback environment available:

* **Software engineering** supplies compilers, tests, linters, and CI, making it a strong setting for both scaffold self-modification and parameter learning from executable rewards. The main risks are verifier overfitting, flaky or incomplete tests, and benchmark-specific harness tuning.
* **Web automation** combines sparse delayed feedback, changing interfaces, and prompt-injection exposure. Cross-session memory and grounding can adapt quickly, but robust evaluation must test layout and site drift rather than fixed snapshots.
* **Games and strategic reasoning** provide resettable environments and self-play, but fixed opponent pools can hide cycling, non-transitivity, brittle conventions, persuasion, or deception.
* **Scientific discovery** uses executable workflows, simulators, domain tools, and critique, but experiments can be expensive, noisy, and only partially verifiable. Progress should be attached to reproducible artifacts and provenance rather than narrative quality alone.
* **Embodied AI and computer control** add sim-to-real shift, safety constraints, costly rollouts, fragile interfaces, and long-horizon state tracking. These domains make permission boundaries and recovery behavior part of the improvement target.

## Exemplar Systems

| System | Survey branch | Concrete role in the landscape |
|---|---|---|
| WebRL | Foundation-model improvement from grounded experience | Learns a web-navigation policy from interaction trajectories and outcome-supervised rewards. |
| VOYAGER | Tool and memory improvement | Refines executable Minecraft skills through environment feedback and retains them for later routing and reuse. |
| Darwin Gödel Machine | Full-scaffold improvement | Rewrites coding-agent scaffolds and preserves diverse verified descendants in an open-ended archive. |
| AlphaEvolve | Full-scaffold improvement in scientific and technical optimization | Evolves programs against one or more evaluators, illustrating bounded self-modification with executable feedback. |

# Evidence Boundaries

The paper is a broad taxonomy and design synthesis, not an empirical demonstration of one self-improving system. Its evidence consists mainly of formalization, historical reconstruction, qualitative comparison, and results reported by a large and rapidly changing literature.

* The `θ`/`Σ` split, signal taxonomy, and definition of persistent self-improvement are the survey authors' organizing framework.
* Performance claims for individual systems come from different papers with different models, tasks, budgets, supervision, and evaluators; the survey does not establish their relative superiority through a common benchmark or meta-analysis.
* The memory-object scorecard is explicitly a qualitative, literature-grounded assessment rather than a standardized empirical comparison.
* The fast-scaffold/slow-model deployment principle is argued from the survey's systems discussion. Its application to a particular agent still requires domain-specific transfer, regression, cost, and safety evidence.

The survey's strongest contribution is therefore conceptual integration: a vocabulary and evaluation checklist for designing self-improvement loops. Its mechanism rankings, maturity judgments, and safety implications should not be read as experimentally settled across domains.

# Takeaways

1. **Persistence is the boundary between adaptation and self-improvement.** In-context retries, longer histories, or temporary plans do not count unless their result changes a retained component of the agent.
2. **The scaffold is the natural experimental layer.** Prompt, memory, tool, and control changes are observable and rollback-friendly; parameter updates should follow evidence of stable transfer, not precede it.
3. **The critic is governed infrastructure.** If the same system proposes and accepts updates, it can create a self-confirming loop. Final evaluation should be independent of the improvement signal, and evolving critics should have constrained, auditable update paths.
4. **Evaluation must be longitudinal.** Report learning curves under fixed compute, token, time, tool, and human-supervision budgets; held-out transfer; regression on previously solved tasks; safety violations; variance; and total improvement cost, rather than only a best final score.
5. **Full self-modification should be treated as untrusted code.** Persistent prompt injection, poisoned memory, or hijacked tool logic can become architectural vulnerabilities. Candidate updates need layered functional, permission, regression, perturbation, and safety gates.

# Open Questions

* How can a system attribute a failure to the correct substrate—model weights, prompt, context assembly, memory, tool interface, or control logic—before choosing an update?
* What promotion rule should move a successful scaffold behavior into parametric consolidation without losing rare recovery strategies or invalidating prior safety bounds?
* How can critics evolve without falling under the unconstrained control of the agents they evaluate?
* Which memory update policies preserve provenance, resolve contradictions, resist poisoning, and support deliberate forgetting at the same time?
* How should improvement efficiency be measured when methods trade task success against tokens, wall time, tool calls, model training, human review, and regression risk?
* Can version-controlled multi-agent co-evolution share tests, patches, tools, and skills without propagating corrupted rewards or creating a single shared failure point?
* What non-stationary benchmarks can distinguish genuine continual adaptation from repeated optimization against static interfaces and hidden test sets?
