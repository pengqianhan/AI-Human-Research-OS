# Q1 Problem Definition

* **Input (X):** one RGB photograph of an indoor scene, which may be synthetic or real and cluttered.
* **Output (Y):** a compositional 3D scene: room geometry (walls, floor, ceiling, openings) plus a set of separately meshed, textured objects, each with position, uniform scale, yaw, and PBR material parameters. It also recovers emissive lights and a calibrated camera whose render should match the input view.
* **Core problem:** single-view scene reconstruction is ill-posed: there is heavy occlusion, and a photo gives no explicit metric scale or inter-object relations. The paper frames the field as split between geometry-driven pipelines (segment, reconstruct, and align objects to estimated depth or point clouds), which get poses and small or occluded objects wrong, and VLM-driven pipelines, which capture relations like "against the wall" or "on top of" but cannot reason about precise numbers, so renders drift from the input.
* **Constraints:** no component is trained or fine-tuned; the method composes off-the-shelf foundation models. There is no per-scene manual intervention.

# Q2 Problem Novelty

Not a new problem. Single-image compositional scene reconstruction has been tackled by Gen3DSR, CAST, 3D-RE-GEN, ZeroScene, MIDI, SceneGen, and VLM-agent methods (Holodeck, SAGE, VIGA, and text-conditioned SceneSmith). The contribution is a new *combination*: a VLM plans and places objects in an explicit hierarchical order, and every placement is then corrected against dense geometric evidence (silhouette and point cloud), with a VLM check after each stage. The authors argue this matters because neither approach alone achieves both semantic correctness (orientation, pairing, support) and pixel- and metric-level alignment.

# Q3 Scientific Hypothesis

If a VLM first fixes a metric room frame and camera, then places objects in an order where each new object is unoccluded by what is already placed (walls first, then furniture outward from the deepest corner, then decorations on their hosts), and each placement is corrected by silhouette and depth evidence and re-checked by rendering against the input, then the reconstructed scene should beat both geometry-only and VLM-only pipelines on semantic similarity (N-CLIP), pixel error, and 3D geometry. Removing any one of these steps should hurt.

# Q4 Related Work and Key People

* **Image-to-3D object generation:** 3DShape2VecSet, CLAY, TRELLIS/TRELLIS.2, Hunyuan3D 2 (used here), TripoSG, Direct3D-S2, SAM 3D.
* **Geometry-grounded scene reconstruction:** Gen3DSR (divide-and-conquer with SDS), ZeroScene (joint 2D/3D pose losses), CAST (GPT scene parser plus SDF physical correction), 3D-RE-GEN (4-DoF differentiable ground-plane alignment), and feed-forward scene models (Coherent 3D Scene Diffusion, MIDI, SceneGen); VGGT for point clouds.
* **Agentic 3D scene generation:** SceneSmith (text-conditioned hierarchical placement order, from which HARMONY borrows the wall → furniture → decoration hierarchy), Holodeck/Holodeck 2.0 (VLM constraints plus a layout solver), SAGE, VIGA (a Blender agent that renders and compares), and Spatially-Contextualized VLMs (VLM plus Fast3R point clouds).
* **Key people:** Lingjie Liu's group at the University of Pennsylvania (Shufan Sun and Chen Wang are equal first authors), with Jiatao Gu; the acknowledgements thank Apple for support. Likely critics: VIGA and CAST authors, and 3D-vision groups who would ask for pose-level metrics rather than render similarity.

# Q5 Key Solution Idea

* **Metric room and camera first.** The VLM guesses room dimensions (for example 3×4×3 m for a bedroom), picks the deepest visible corner as an anchor, and labels which walls are visible. VGGT's point cloud gives a Manhattan frame (SVD clustering of normals) and the matching corner. A closed-form similarity transform (rotation from the Manhattan axes, scale from the VLM room height divided by the VGGT corner edge length, translation pinning the floor corner) places the VGGT camera in the canonical room.
* **Per-object assets.** For each level, the VLM lists objects and counts. An open-vocabulary detector and a segmenter give masks. An image editor amodally completes occluded objects from VLM descriptions, and the VLM checks the completions. Hunyuan3D-2 builds each mesh, which is canonicalized by PCA, and the VLM labels its front from multi-view renders.
* **Hierarchical, depth-first placement.** Placement goes wall-mounted → furniture/ceiling → decorations. Furniture is placed outward from the anchor corner, so every placed object lies behind the next one from the camera's view and each new object is seen unoccluded. The VLM writes relational prompts ("sofa back against the left wall", "chair facing the coffee table"), sets yaw from the canonical front, and makes small visual rotation fixes. A bounding-box overlap check fixes decorations attached to the wrong one of two similar hosts.
* **Geometric refinement.** The horizontal silhouette offset gives the lateral shift. Silhouette width gives the scale-to-depth ratio s/Z. A robust (median/MAD) comparison of front-surface depth between the VGGT and rendered point clouds gives Z, which fixes metric scale. Collisions are resolved by the smaller of the two separating moves, escalating to a VLM re-ordering if they persist.
* **Reflective loop and lighting.** After each stage the scene is rendered and the VLM compares it with the photo: scale, orientation, misplaced or missing items, and consistent sizes for matched groups such as chair pairs. A final count fills missing instances. The VLM also assigns PBR materials and estimates emitters, refined by comparing Blender Cycles renders with the input.

# Q6 Experiment Design

* **Data:** Front100, which is 100 3D-FRONT renders with ground-truth meshes, and HARMONY30, 30 real copyright-free photos. The full pipeline was also run on HARMONY300.
* **Metrics:** N-CLIP (1 − CLIP-ViT-B/32 cosine), photometric MSE (PL), and LPIPS on renders from the input view; Chamfer distance and F-score at 0.1/0.01/0.001 on Front100. A user study had 16 volunteers rank six methods on 20 scenes (mean rank, Top-1, Top-2).
* **Baselines:** Gen3DSR (stock), 3D-RE-GEN (with gpt-image-2 inpainting), CAST (unofficial implementation), SAM3D* (given HARMONY's own masks), VIGA (with SAM3D and GPT-5.5), and GPT-6 Astra as a qualitative and quantitative reference. CAST and SAM3D get HARMONY's background for perceptual metrics.
* **Ablation:** eight variants removing VGGT refinement, depth-first traversal, VLM placement reasoning, placement refinement, the feedback loop, placement order, and camera calibration.
* **Failure analysis:** rare object types where VLM and detector vocabularies disagree; objects very close to the camera and heavily clipped.

# Q7 Datasets and Code

Released: HARMONY300 (100 easy 3D-FRONT scenes, 100 medium real photos, 100 complicated real photos). Each scene has the reference photo, reconstructed scene, lit render, calibrated camera, a segmentation colormap, and per-object JSON with stage, type, size, position, wall affinity, and relations (facing, in-front-of, on-top-of, grouped-with). Licence CC-BY-NC-4.0; sources are Pexels, Unsplash, 3D-FRONT, and 3D-FUTURE. Code is at [ShufanSun/harmony-release](https://github.com/ShufanSun/harmony-release). Foundation models listed in the paper's Table 4 include gpt-5.5 as the VLM, a Gemini image model for editing, VGGT, and Hunyuan3D-2. Runtime is 20-90 minutes per scene on L40 GPUs, averaging 3.4 VLM calls per placed object.

# Q8 Evidence Quality

* **Supported:**
  * *Front100 (Table 1):* HARMONY is best on every metric: N-CLIP 0.092, PL 0.041, CD 0.049, F@0.1/0.01/0.001 89.82 / 19.47 / 0.130. The strongest baselines per metric are CAST (CD 0.052, F@0.1 85.70) and SAM3D* (F@0.01 14.44). GPT-6 Astra is close on N-CLIP (0.095) but worse on geometry (CD 0.061, F@0.1 77.44).
  * *Real photos (Table 2):* HARMONY N-CLIP 0.112, PL 0.045, against Astra's 0.127 / 0.047 and 3D-ReGen's 0.154 N-CLIP. In the user study it has mean rank 1.54 ± 0.93, 67.0% Top-1, and 86.0% Top-2; the next best, SAM3D*, has mean rank 3.26.
  * *Ablation (Table 3):* removing camera calibration hurts most (N-CLIP 0.1034 → 0.1381, PL 0.0462 → 0.0596), then the feedback loop (N-CLIP 0.1184). Every removal is worse than the full system on both metrics.
* **Weaker than it looks:**
  * *Small ablation effects.* Apart from calibration and the feedback loop, removals change N-CLIP by only 0.001-0.005 (for example, without depth-first traversal 0.1045 vs. 0.1034), with no variance or seeds reported. The ablation's full-system N-CLIP (0.1034) matches neither Table 1 (0.092) nor Table 2 (0.112), and the retrieved text does not say which scenes the ablation uses.
  * *Baseline set-up favors HARMONY on some rows.* SAM3D* gets HARMONY's own masks, CAST and SAM3D get HARMONY's background for perceptual metrics, CAST is an unofficial re-implementation, and VIGA and 3D-RE-GEN run with changed models.
  * *Render-similarity metrics* (N-CLIP, PL from the input view) reward matching the one visible view, and the method optimizes exactly that view through its render-and-compare loop. Only Front100 checks 3D geometry.
  * *User study scale:* 16 uncompensated volunteers and 20 scenes, restricted to scenes where every method rendered successfully.
  * *The "agentic" part is a fixed pipeline.* The VLM makes decisions and critiques inside a hand-designed stage order; there is no open-ended tool choice or learned policy. That is a design choice, not a flaw, but it limits what the results say about agents in general.

# Q9 Contributions

* A closed-form, VLM-anchored camera and room calibration that fixes metric scale from one photo.
* A hierarchical placement order with depth-first furniture traversal that keeps each new object unoccluded for the VLM, plus a stage-wise render-and-compare reflective check.
* A concrete split of work between the VLM (relations, orientation, support, counts) and geometry (lateral position from silhouette, depth from the point cloud, and scale from both).
* HARMONY300, a 300-scene dataset of reconstructed scenes with per-object relation annotations.

# Q10 Next Steps

* **Multi-view input and articulated objects** are the authors' stated future work.
* **Pose-level evaluation:** report per-object position and orientation error and relation accuracy on 3D-FRONT, not just render similarity and Chamfer distance.
* **Stronger ablations** with variance over seeds or scenes, on the same evaluation split as the main tables.
* **Cost:** 3.4 VLM calls per object and up to 90 minutes per scene. Which stages could a smaller or fine-tuned VLM handle?
* **Physics validity (reader note):** unlike [SceneMosaic](2609.05594.md) and [Code as Worlds](2608.27549.md), HARMONY's only physical check is collision resolution, with no simulation. Adding a settle-in-simulator check would test whether scenes that match the render are also physically stable.
* **Training signal (reader note):** HARMONY300's per-object relation JSON could serve as supervision or verifier targets for trained scene agents such as [VibeWorlding](2608.15265.md), which currently scores worlds with an MLLM rubric.
