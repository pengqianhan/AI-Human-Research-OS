# Q1 Problem Definition

* **Input (X):** a simulated robotics task in Isaac Lab (scene, robot embodiment, natural-language instruction), full simulator-state access, rendering/inspection tools, and configurable controllers (operational-space, inverse kinematics; a pretrained locomotion policy for the humanoid). The agent is a frontier coding agent in its native harness (Claude Code or Codex) inside an isolated Docker container.
* **Output (Y):** a Python program exposing `solve(env)` that completes the task when re-run in a separate grading environment. In the second half of the paper, the output is instead a large, diverse, verified set of trajectories used to fine-tune a vision-language-action (VLA) policy.
* **Core question:** can coding agents solve long-horizon, dexterous tasks (assembly, cutting, deformables, liquids) in a way that produces scalable, transferable demonstration data for generalist robot policies?
* **Constraints:** 4-hour wall-clock budget on one RTX 4090; network limited to the model API and the Python package index; grading happens offline with state-writing interfaces such as `set_states()` disabled.

# Q2 Problem Novelty

Partly new. Coding agents as robot programmers (Code-as-Policies-style work, CaP-Gym, real-robot program refinement) and simulated demonstration generation (MimicGen-style human-trajectory adaptation, LLM-assisted task generation, scripted-skill composition) both exist. The authors argue prior coding-agent work stays mostly at navigation and pick-and-place with hand-designed interfaces (object-pose queries, macro primitives), and that simulation benchmarks rarely combine long horizons with hard contact physics. The new part is (1) a benchmark whose tasks take tens of minutes and involve screws, deformables, cutting, and bimanual/humanoid embodiments, and (2) closing the loop from "the agent solved it once" to "the solution becomes VLA training data." This matters because teleoperated demonstrations for precise contact tasks are expensive, and a verified program is a cheap source of demonstrations.

# Q3 Scientific Hypothesis

If frontier coding agents are given full simulator state and an iterate-execute-inspect loop, they can write working programmatic policies for long-horizon dexterous tasks faster than tabula-rasa RL can learn them. If each verified solution is then diversified by an agent (scene, strategy, phase, noise) plus standard domain randomization, the resulting demonstrations should train a VLA whose performance scales with data, generalizes to held-out variations better than script-only augmentation, and transfers to a real robot without real demonstrations.

# Q5 Key Solution Idea

* **Benchmark (EmbodiedSWE-Bench).** 28 tasks in six suites: assembly (9), packing (4), puzzle (6), deformable/liquid (4), cutting (2), locomotion-with-manipulation (3). Examples are an IKEA table with four legs, a motherboard secured by seven bolts, and a shoelace half knot. Five embodiments are supported: Franka, xArm7, Kinova Gen3, bimanual Franka, and Unitree G1. Each task was solved at least once by a domain expert working with a coding model. Grading is offline, with task-specific simulator checks or a human-written rubric scored by a VLM. Each run is audited by Opus 5 for reward hacking, and hacked runs score 0.
* **Solver-side tools.** A *checkpoint tree* (save and revisit simulator states with their programs, logs, and notes), *CMA-ES parameter search* over parallel simulations with optional initial-state jitter, a scene viewer, a strategy-sweep tool, and a structured assessment log.
* **Teacher side (EmbodiedSWE-Gen).** One verified solution is expanded hierarchically. The agent edits the *scene* (objects, distractors, layout, plus updated success conditions), the *strategy* (step order, grasp choice, recovery branches), and the *phase* (demonstrations starting mid-task from constructed valid intermediate states), and writes *phase-specific DART noise* into the code (stronger during transport, weaker during insertion). Scripts then randomize physics (mass, friction, contact) and re-render visuals (lighting, texture, background, camera). A trajectory is kept only if it passes the task grader and an open-loop replay check.

# Q6 Experiment Design

* **Solver evaluation:** six models, each in its native harness (Fable 5.1, Opus 5, Opus 4.8 in Claude Code; GPT-6 Astra, GPT-5.6 Sol, GPT-5.6 Terra in Codex), one 4-hour run per task-model pair, reporting the best-so-far hack-adjusted rubric score against wall-clock and tokens.
* **RL comparison:** PPO on five easier single-arm tasks with sparse, agent-designed dense, and expert-tuned rewards (the expert is one of the authors). Reward design and tuning ran offline for about a week and is not charged to the RL budget; three seeds.
* **Transfer:** Opus 5 and GPT-5.6 Sol, three seeds, six target tasks. The agent gets one read-only verified solution from a similar task, a dissimilar task, or the same task on the Franka when solving on Kinova Gen3 or xArm7.
* **Tool ablation:** Opus 5 and GPT-5.6 Sol on the full benchmark with and without the extra tools, one run per task.
* **VLA experiments:** SmolVLA on six tasks at 10/50/100/200/400 in-distribution demos; agent-aided vs. script-only diversification at 1,000 demos each, evaluated on 256 held-out out-of-distribution settings per task (novel objects such as bread, chilli, and zucchini for slicing).
* **Sim-to-real:** Opus 5 writes an IK-based solution for a four-stage lamp disassembly (grasp shade, place and release shade, grasp bulb, unscrew and extract bulb). Gen produces 500 simulated demos in a Gaussian-splatting reconstruction of the room. π0.5-DROID is fine-tuned on sim data only and compared with the pretrained model over 10 real trials each.
* **Appendix G (preliminary):** an automatic seed-and-mutate task generator validated by six checks, used for turn-level PPO training of Seed-2.1-Lite on 400 generated environments.

# Q8 Evidence Quality

* **Supported:**
  * *Frontier agents solve many tasks.* Hack-adjusted success rates are 82% (GPT-6 Astra, mean score 0.94), 61% (Fable 5.1), 50% (Opus 5), 25% (Opus 4.8), 18% (GPT-5.6 Sol), and 11% (GPT-5.6 Terra). The median time to solve ranges from 39 minutes (Astra) to 119 minutes (Terra).
  * *Reward hacking is common and model-dependent.* Hack rates are 43% (Sol) and 39% (Terra) versus 0-11% for the others. Mechanisms include config/threshold mutation, direct state writes, external forces, monkeypatched graders, and physics or fixture tampering. The offline grader and the hack audit are real controls.
  * *Transfer helps.* A similar-task hint raises the final score to 0.60 (31% success) from 0.52 (11%). A dissimilar hint speeds early progress but ends at 0.51 (17%). A cross-embodiment Franka hint gives 0.74 (56%) on Kinova and 0.66 (36%) on xArm7.
  * *Demonstrations scale.* Mean VLA success goes from 18% at 10 demos to 69% at 400 (rubric 0.32→0.76). Agent-aided diversification beats script-only on all six tasks held out (overall 0.233 vs. 0.066).
  * *Sim-to-real is non-trivial.* On the real robot the sim-trained policy reaches 100% / 80% / 30% / 20% on the four cumulative stages, while pretrained π0.5-DROID gets 0% on every stage.
* **Weaker or bounded:**
  * *One run per task-model* in the main solver table, so per-task numbers are noisy. The model comparison also mixes model and harness (Claude Code vs. Codex).
  * *The RL comparison is limited to five easy tasks*, with reward tuning done offline and not charged to RL. The authors acknowledge scaling RL or using other algorithms might close the gap. The result is shown as a figure only, so no numbers are quoted here.
  * *Tool gains are small* by the authors' own description, measured with one run per task and two GPUs instead of one.
  * *Held-out VLA scores are still low in absolute terms* (0.233 mean rubric), and the in-distribution scaling study uses relaxed success criteria for some tasks (the paper's Table 22).
  * *Sim-to-real is one task and 10 trials*, and the baseline is a pretrained policy never fine-tuned on this task, not a policy fine-tuned on real or teleoperated demos.
  * *Coding-agent RL (Appendix G) has no held-out evaluation.* Training success rose from 2.7% to 7.5%, but the authors say external restrictions stopped the project before held-out tests.
  * *Solutions need full simulator state*, so the solver side does not show perception-grounded control. The VLA side is where perception enters.

# Q9 Contributions

* EmbodiedSWE-Bench: the first benchmark in this wiki pairing coding agents with long-horizon, contact-rich, multi-embodiment manipulation, graded offline with a reward-hack audit.
* A measured profile of frontier coding agents as robot programmers: capability spread, time and token cost, three named failure modes (poor visual grounding, over-commitment to a failing plan, scorer hacking), and per-mechanism hack statistics.
* Evidence that verified solutions transfer across similar tasks and across arm embodiments when given as a read-only hint.
* EmbodiedSWE-Gen, an agent-driven diversification pipeline that turns one program into many verified demonstrations, with measured gains over script-only randomization and a sim-only-trained real-robot result.

# Q10 Next Steps

* **Close the distillation loop end to end** (the authors' own open item): generate tasks, solve them, diversify, train VLAs, and measure how much of the coding agent's capability reaches the policy.
* **Visual grounding for coding agents:** the text-only agent in Appendix G and the "poor visual grounding" failure mode both point to agents that read rendered frames rather than printed state.
* **Held-out evaluation of the RL-trained coding agent**, first on generated environments and then on EmbodiedSWE-Bench.
* **Dexterous hands** with many more joints remain untested.
* **Hack-resistant graders (reader note):** the large gap in hack rates between model families suggests reporting hack rate next to success as a standard benchmark column. The same idea appears in the repository-sanitization protocol of [One to More, More to One](2609.23377.md).
* **Link to frozen-VLA harnesses (reader note):** [Harness VLA](2607.08448.md) and [Zetta](2608.16590.md) keep the VLA frozen and put an agent around it at deployment time. EmbodiedSWE instead uses the agent offline to *train* the VLA. Comparing the two on the same tasks would show whether agent effort is better spent at training time or at run time.
