# Q1 Problem Definition

* **Input (X):** a user goal that may span several domains and a long horizon (the running example asks for a survey of AI-for-AI research, a reproduction of the leading algorithms, and a web page reporting the results), a roster of executable agents, and one shared resource budget. Each agent is a model-harness pair: the four native specialists Raven-Research, Raven-Code, Raven-Design, and Raven-Oncall, a general Raven agent, and third-party agents (Claude Code, Codex, OpenCode, Hermes Agent, OpenClaw) connected through execution adapters.
* **Output (Y):** a directed acyclic graph (DAG) of agent calls with explicit artifact dependencies, its execution with every handoff recorded as an artifact, and a synthesized final deliverable. Across tasks, the system also produces improved harnesses, stored memory, and revised skills.
* **Core problem:** an agent's practical capability depends on its harness (tools, context management, skills, execution policy, recovery) as well as its model. More tools and conditions make harnesses hard to design by hand, and a harness tuned to one domain does not carry over to others. The authors therefore ask how to build specialized harnesses automatically, improve them from experience, and compose them across domains.
* **Constraint:** capability is defined as *reliable task coverage under a common budget*: the probability that a verifier accepts the delivered record while total cost (planning, workers, handoffs, verification, retries) stays within budget. An agent or judge declaring completion is not the same as objective correctness.

# Q2 Problem Novelty

Partly new. Multi-agent frameworks such as AutoGen and MetaGPT already coordinate role-prompted agents, but inside one shared framework and control loop. Raven instead composes *heterogeneous* harnesses that keep their own tools, context handling, and control policies, joined through adapters and typed artifact handoffs. Most components extend the authors' own earlier work: harness evolution comes from HarnessBank (arXiv:2607.13683), the skill catalog and retrieval stack from SkillCorpus (arXiv:2607.15557), and the memory lifecycle from [EverMemOS](2601.02163.md) through the EverOS memory layer. The new parts are the integration into one host-orchestrated ecosystem, a formal account of when composition can beat every available individual agent, and the Multi-Agent Orchestration Benchmark (MAOB).

# Q3 Scientific Hypothesis

Suppose the plan is an explicit typed graph, each node is assigned to an agent that can meet its contract, and handoffs are compatible. Suppose further that planning and per-node errors are bounded. Then the composed system should reliably solve tasks that none of the available agents can reliably solve alone under the same total budget. Empirically, the authors expect explicit graph orchestration to plan better than the native orchestration of existing agent systems, and harnesses specialized per domain to outperform general harnesses on the same backbone at comparable cost.

# Q5 Key Solution Idea

* **A heterogeneous agent registry.** Each entry binds a name and capability description to one of four backends: the in-process Raven loop, a command-line process, an Agent Client Protocol (ACP) connection, or an OpenAI-compatible API. Three flags constrain planning: whether the agent is stateful, can read local files, and reports progress. The Host Agent picks agents from these descriptions with its own model, without a trained router.
* **Admitted graphs, not free-form messages.** The host carries only a short summary of the orchestration guide and loads the full guide when a request needs several agents. It builds the graph backward from the deliverable and submits a typed DAG, which the runtime checks with five groups of admission checks before any worker starts. A rejected graph returns its first error together with a pointer to the guide. Execution then schedules nodes as their dependencies settle, has a completion judge adjudicate each node, and routes exceptions and clarification requests back to the host. Every handoff goes through a file-backed artifact that later graphs can reuse by reference.
* **Shared group memory.** After each round, the host writes a round summary and per-agent assessments ("verdicts": one at close, one after the next user turn) into owner-partitioned EverOS libraries. These are prefetched before later planning and dispatch. The user's personal memory is excluded.
* **Harness self-evolution (from HarnessBank).** The harness around a frozen model is split into Memory, Planning, Capability, and Action interfaces, and an immutable kernel protects evaluation and bookkeeping. An Evolver diagnoses failure traces and proposes prompt, knowledge, runtime, or configuration edits. A semantic gene bank keeps one harness per edit-category and pathology cell, in the style of MAP-Elites. Candidates pass validity, activation, and paired-gain screening, and the chosen harness is frozen before held-out testing.
* **Memory and skills.** EverOS runs episodic trace formation, semantic consolidation, and reconstructive retrieval, with separate user and agent tracks. Skill Forge fuses the curated SkillHub catalog (built on SkillCorpus) with local and memory-derived skills, lets an LLM select a bounded set, and revises experience-derived skills through intent clustering and explicit update operations.
* **Theory.** Theorem 1 bounds a valid plan's success probability below by one minus the sum of per-node and per-edge error allowances, with no independence assumption. Proposition 1 adds the host's chance of producing a valid plan. Corollary 1 states the condition for *new* coverage: the system's bound must exceed 1−δ while every individual agent's success probability stays below it. A constructive example has two agents that can each read only one of two hidden bits: composed, they return the parity exactly, while each alone is correct at most half the time. The authors note that a single agent given both read interfaces could also solve it.

# Q6 Experiment Design

* **Planning (MAOB, new).** 140 requests from 137 occupations, patterned on GDPval and JobBench without reusing their text. Each request has a reference DAG over four specialist domains (research, coding, content, oncall), and all 11 multi-domain subsets are covered. Reference graphs were written first with Claude Opus 5, requests were generated backward from them with GLM-5.2, a lexical filter rejected requests that list steps or name domains, and experts reviewed each sample. Graphs average 2.72 nodes and 1.84 edges; 98 are purely serial and 42 contain parallel branches. After folding invocations to domain level, the metrics are Node F1, Edge F1 on transitive reductions, Partial Order Accuracy (POA), and Exact Match. Raven, Claude Code, and Hermes Agent plan with Qwen3.8-27B and with DeepSeek-V4-Flash-0731, receive identical request text and delegation instructions, and submit graphs that are scored without running any worker.
* **Harness evolution.** The paper summarizes HarnessBank's published results rather than running new ones: seven benchmarks (Terminal-Bench-2, five EvoAgentBench domains, and AppWorld), a frozen Qwen3.6-27B, and held-out Pass@1 averaged over three attempts.
* **Raven-Research.** DeepResearch Mixed pools BrowseComp, FRAMES, text-only exact-match Humanity's Last Exam, and xBench-DeepSearch, with answers graded by an LLM judge. It is compared with MiroFlow and DeepSeek-Harness on three shared backbones with the same search tools, one attempt per question, with three commercial services as references.
* **Raven-Code.** SWE-bench Pro (731 tasks), SWE-bench Verified (500), the WorkBuddy code subset (80), and SWE-Refactor (20 whole-repository migrations), run in the authors' internal AgentEval containers with official graders. Some comparison points are public leaderboard values. DataAgentBench (54 questions over 12 datasets, five trials) is added for database analysis.
* **Raven-Design.** PresentBench (238 slide tasks, official evaluator), plus ArtifactsBench SVG and dashboard tasks and GDPval deliverables scored by an internal grader with GPT-5.6 Luna as judge, and seven selected showcase runs.
* **Raven-Oncall.** An AI4AI task (autoresearch, a single-GPU derivative of nanochat with a model of about 50M parameters: 300-second training runs within a 5 GPU-hour campaign on two A800s, scored by validation bits per byte) with one campaign per system, and AI4S, an internal set of 17 solver, training, and simulation tasks judged manually against withheld reference values.
* **Skill reuse.** The paper summarizes SkillCorpus's published results: SkillsBench (87 tasks), GDPval (220), and QwenClawBench (100), with Raven and OpenClaw each paired with Qwen3.5-27B and Qwen3.5-397B-A17B. Both harnesses receive identical precomputed selections of at most two skill bodies, and every configuration is averaged over three runs.

# Q8 Evidence Quality

* **Supported:**
  * *Better planning graphs on MAOB.* Raven leads Claude Code and Hermes Agent on all four metrics under both backbones. With Qwen3.8-27B: Node F1 0.923 against 0.776 for the strongest baseline, POA 0.950, and Exact Match 0.711 against 0.607 (+10.4 points). With DeepSeek-V4-Flash-0731: Node F1 0.963 against 0.854, Edge F1 0.897 against 0.813, and Exact Match 0.867 against 0.762 (+10.5 points). Edge F1 stays below Node F1 for every system, so dependency prediction is the harder part.
  * *Research harness.* Raven-Research has the highest pooled accuracy on all three shared backbones: 56.3% against 49.7% for the strongest baseline (Qwen3.6-35B-A3B), 59.3% against 56.0% (Qwen3.5-397B-A17B), and 76.5% against 68.9% (DeepSeek-V4-Flash). With DeepSeek-V4-Flash it costs $0.0242 per question, between MiroFlow ($0.0374) and DeepSeek-Harness ($0.0211). Exact McNemar tests give p < 0.02 in five of six same-backbone comparisons; the sixth (against DeepSeek-Harness on Qwen3.5-397B-A17B) has p = 0.21. The margin comes mostly from BrowseComp (69.3%) and Humanity's Last Exam (60.0%), where the other harnesses reach at most 62.4% and 43.3%; DeepSeek-Harness leads by 3.4 points on xBench-DeepSearch.
  * *Coding harness.* Raven-Code is top in six of eight settings, with the largest margins on SWE-Refactor (+9.5 points with DeepSeek-V4-Flash and +3.0 with GPT-5.6 Luna over leaderboard entries). On SWE-bench Pro it resolves 15 more of 731 tasks than Claude Code on the same Qwen3.8-27B backbone. On SWE-bench Verified the leads are 0.6 and 1.2 points (3 and 6 of 500 tasks). With Claude Opus 5 it reaches DataAgentBench Pass@1 0.8762, the highest among leaderboard entries on 24 August 2026.
  * *Design and run-and-watch harnesses.* PresentBench scores are 80.2 (Claude Opus 5) and 72.9 (GPT-5.6 Luna), against 78.3 and 52.4 for Claude Code. Under Claude Opus 5, Raven-Oncall reaches 1.038 bits per byte from a 1.108 start, against Claude Code's 1.053, in similar wall-clock time (4.90 h vs. 4.99 h) with lower reported tokens and cost. It solves 14 of 17 AI4S tasks against Claude Code's 11.
  * *Skills help, and help Raven more (SkillCorpus results).* All 12 cell-benchmark comparisons improve. Pooled gains are +7.5±2.3 points on SkillsBench, +1.51±0.49 on GDPval, and +2.79±0.70 on QwenClawBench. From identical skill selections, Raven gains 6.5 and 13.4 points on SkillsBench against OpenClaw's 4.2 and 5.8, and 3.9 and 4.4 on QwenClawBench against 1.5 and 1.3. In a single-run ablation, an off-the-shelf retriever drops Raven's best SkillsBench score from 22.6% to 13.8%, and the uncurated crawl of about 821,000 skill files drops it to 14.9% (no skills: 9.2%).
  * *Harness evolution (HarnessBank results).* With Qwen3.6-27B frozen, held-out Pass@1 rises on all seven benchmarks, for example AppWorld 41.3→56.7, BrowseComp+ 16.9→30.8, LiveCodeBench 58.1→71.8, and Terminal-Bench-2 36.1→45.4. Six pass the source's paired-gain criterion; SWE-bench Verified (+5.1 on a 26-task test split) does not.
* **Weaker or bounded:**
  * *The composed system is never tested end to end.* The paper's own theory (Sections 2.5-2.6) says that establishing new-task coverage requires matched comparisons against strong individual agents with comparable models, tools, information, and total cost. No such experiment is reported. MAOB scores only the plan before any worker runs, and the specialist results measure each harness alone. The title claim of "composable agentic intelligence" therefore rests on the theory and the planning benchmark, not on measured composed outcomes.
  * *Graph agreement is not task success.* MAOB's references were written by one LLM and its requests generated by another, from the authors' own construction pipeline, and scoring folds invocations to four domains. Raven's orchestration guide was written for this kind of graph submission, while Claude Code and Hermes Agent plan through their native interfaces. Whether a higher Exact Match predicts better executed results is not tested (reader note). Per-baseline MAOB values appear only in a figure; the text gives the strongest-baseline numbers quoted above.
  * *Two of the component results are reused, not new.* The harness-evolution and skill-reuse evidence reproduces the authors' earlier papers; it does not come from the integrated Raven system described here. The skill ablations are single runs.
  * *Uneven comparison protocols.* Several figures mix locally run systems with public leaderboard values; the SWE-bench Verified runs allow network access. In the AI4AI task, Claude Code received a separately written task statement and each system ran one campaign. In AI4S, Claude Code's statements included machine addresses and job commands that Raven-Oncall selects itself, and success is judged manually. The visual-design scores come from an internal grader with a GPT-5.6 Luna judge (margins of 0.3-2.8 points over the strongest alternative), and PresentBench means cover only successfully graded decks.
  * *Theory gives sufficient conditions only.* The per-node error allowances and the host's planning failure rate are never measured, so the bounds are not instantiated for any reported task. The parity example shows only that composition can beat agents that each lack an interface, not that it beats a single agent given all of them, as the authors state.

# Q9 Contributions

* An open ecosystem that treats model-harness pairs, including third-party agents behind ACP and CLI adapters, as composable units, with admission-checked DAG plans, artifact-based handoffs, completion adjudication, and host-level group memory.
* A formal definition of capability as reliable coverage under a shared budget, with composition-reliability bounds and a stated condition for new-task coverage beyond every individual agent, including planning and coordination cost.
* MAOB, a planning benchmark that scores specialist selection and dependency structure before execution, covering all multi-domain subsets of a fixed four-specialist roster.
* Four specialist harnesses (research, code, design, run-and-watch) with same-backbone comparisons that report cost next to quality, and one integration of the authors' harness-evolution, memory, and skill-retrieval work.

# Q10 Next Steps

* **The authors' plan:** one Raven instance per device or environment, coordinated over agent-to-agent (A2A) protocols into an "All-Domain Collaboration Network", with memory, task context, and execution progress synchronized across devices.
* **The missing end-to-end test (reader note):** run executed MAOB-style cross-domain tasks with the composed system and with the strongest single agent given the union of tools and the same budget. Measure the host's planning failure rate and per-node error to see whether Corollary 1's condition ever holds in practice.
* **Does plan agreement predict outcomes? (reader note):** execute the MAOB graphs and correlate Exact Match or Edge F1 with deliverable quality, since the benchmark admits that valid alternative plans can differ from the reference.
* **Adapter-level wrapping compared (reader note):** [LongHorizon-Harness](2608.01964.md) also wraps Claude Code, Codex, OpenClaw, and Hermes Agent, but to run one long task under a manager-executor-auditor split, while Raven wraps them to divide a task across specialists. The two answer different questions about the same backends, and could be combined.
* **Relevance to this repository (reader note):** the Research OS's `project-dispatch` skill hands work to per-project Claude Code or Codex sessions through `os-harness`. Raven's admission checks on a submitted graph and its artifact-only handoffs are concrete candidates for that dispatch layer. Separately, Raven-Oncall's AI4AI task tunes a nanochat-derived pretraining recipe scored in bits per byte, the same substrate family as the [nanochat_cpu](../../projects-folder/nanochat_cpu/index.md) project.
