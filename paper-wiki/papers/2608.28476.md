# Q1 Problem Definition

* **Input (X):** a long-horizon agentic task modeled as ReAct-style interaction — a user query `q` forms the initial context `c0`; at each step the agent generates a (thought, tool call) pair from the current context, and the resulting (thought, tool call, observation) is appended, so the context grows monotonically as the interaction proceeds.
* **Output (Y):** at each step, an action drawn from an action space that includes ordinary task actions and context-management actions `A_cm ⊆ A` (a subset of which, "context editing actions" `A_ce ⊆ A_cm`, directly rewrite the interaction history through a context transition function); the agent is trained via SFT then RL to use these tools so it completes long-context QA or deep-search tasks while keeping its working context compact.
* **Core problem:** recent "proactive context management" methods let a model edit its own working context via tools, but the paper identifies three limitations: (1) toolsets are typically restricted to search, deletion, and summarization, with no support for global planning, long-term memory, or adaptive compression; (2) training explores all context-management actions uniformly even though a pilot study (Fig. 2: branching from each tool and measuring the standard deviation of continuation success rates) shows tools differ substantially in how much they affect final outcomes; (3) training assigns the single sparse trajectory-level reward to every intermediate context-editing action, even though a case study (Fig. 3) shows final task correctness and context-management quality can be misaligned — a correct trajectory can rely on repeated, inefficient retrieval, while an incorrect one can still manage context reasonably.
* **Scope:** two task families only — long-context QA and deep search, both text-only tool-augmented agentic settings. The paper explicitly does not address agentic coding or GUI agents (named as future work).

# Q2 Problem Novelty

Proactive context management itself is not new — letting a model decide when and how to edit its own context, as opposed to passive rule-based truncation or summarization, is an active line (MemGPT, StateLM/"Pensieve," Sculptor, MemAct, AgentFold, surveyed in Sec. 2.2). ContextPilot's stated novelty is identifying and jointly addressing three specific, previously separate limitations of that line — toolset breadth, exploration allocation across tools, and credit-assignment granularity — each motivated by direct empirical evidence from the paper's own pilot study rather than by assumption: Fig. 2 shows some tools' branch outcomes vary far more than others (e.g., `readChunk` and `deleteContext` show the highest outcome-variance among the tools plotted, `buildIndex` and `finish` the least), and Fig. 3's paired case study shows a correct-answer trajectory using comparatively weak context management alongside a wrong-answer trajectory using comparatively strong context management.

# Q3 Scientific Hypothesis

If (a) the context-management toolset is extended beyond search, deletion, and summarization to include explicit planning, structured long-term memory (entity/timestamp/event extraction with cross-chunk relational edges), and soft, recoverable context offloading, and (b) RL training uses context-and-entropy-variation-based partial rollout to allocate extra exploration budget specifically to the context-editing actions shown to have high downstream sensitivity, and (c) credit for each intermediate trajectory snapshot is estimated from the average reward of *all* terminal trajectories that pass through it rather than the single trajectory-level reward broadcast uniformly, then the resulting agent will maintain a more compact working context while achieving higher task accuracy than both rule-based passive context management and prior RL-trained proactive context-management agents (e.g., StateLM), consistently across multiple base models and both long-context-QA and deep-search task families.

# Q4 Related Work and Key People

Section 2 splits prior work into **Passive Context Management** (rule-based truncation or summarization once a length threshold is crossed, or RL-trained context-folding that resumes reasoning from a compressed state — in both cases the model remains a passive recipient of externally managed context) and **Agentic Proactive Context Management** (MemGPT's virtual-memory tool-call framing; memory-editing-tool training without an external controller; Sculptor, StateLM ("the Pensieve paradigm"), and MemAct providing fragmentation/search/summarization/deletion tools with fine-tuning; AgentFold's SFT-learned multi-scale folding). ContextPilot builds directly on StateLM's base toolset and its trajectory-snapshot-plus-token-level-loss-masking training scheme (Sec. 3.1), extending both the tool design and the RL training recipe on top of it. # Q5 Key Solution Idea

1. **Extended context-management toolset** (Table 1, building on StateLM's base tools): a new "Perception & Planning" category adds `plan` (propose a concise plan) alongside `analyzeText`/`checkBudget`. Long-term memory adds `memorize` (extracts structured entities, timestamps, and event episodes, and builds edges among related memory items), `updateMemory`, and `readMemory` (retrieves a target memory together with its graph neighbors). Soft context offloading adds `summarizeContext`, `compressContext` (via a lightweight compression model, LLMLingua-2), and `foldHistory` (discards historical messages into a searchable index, recoverable later via `searchContext` keyword queries) — as gentler alternatives to StateLM's harder `deleteContext` (replace a message with a placeholder). Tools that modify interaction history (offloading, memory-writing, memory-updating) are treated as context-editing actions and are exactly the points where a trajectory is segmented into independent training snapshots.
2. **Context-aware partial rollout.** For each context-management action, the method computes a context-variation score (relative change in context length across the action) and an entropy-variation score (average next-token entropy over `k` generated tokens after the observation, compared against the *trajectory's initial* entropy rather than the immediately preceding step — deliberately, to capture uncertainty shift relative to the original query rather than local step-to-step noise). These combine into a sensitivity score `S = α·ΔC + β·ΔH`. Given a fixed per-query snapshot budget `N`, the method first performs ordinary trajectory-level rollouts, segmented into `M ≤ N` snapshots; if `M < N`, it ranks all context-management actions by `S` in descending order and spends the remaining `N − M` budget branching additional sub-trajectories from the highest-sensitivity actions, directing extra exploration to the decisions Fig. 2 shows have outsized downstream impact.
3. **Fine-grained, snapshot-level credit assignment.** Rather than broadcasting a single terminal trajectory's reward (an outcome term, a format term, and a penalty term for invalid tool invocations or context-length violations) to every intermediate snapshot — the convention in StateLM/Sculptor — ContextPilot estimates an intermediate snapshot's reward as the mean reward over *all* terminal trajectories that have it as a prefix, made possible by partial rollout supplying multiple continuations per sensitive snapshot. Snapshot-level advantages are then computed by group-normalizing (mean/std) all snapshots sampled for the same query and optimized with GRPO, treating each snapshot as an independent training sample. Appendix A proves this snapshot-averaged estimator is unbiased — it targets the same conditional expectation as trajectory-level assignment — with strictly lower variance whenever a branch point has more than one sampled continuation, giving a formal reason why partial rollout's extra continuations directly improve credit-assignment quality rather than only exploration coverage.
4. **Two-stage training.** SFT first, using Qwen3.5-397B-A17B (thinking mode) as teacher inside a scaffolded harness that dynamically reveals only tools whose preconditions are currently met (e.g., `readChunk` withheld until `searchContext` has been called) and retries recoverable tool-argument errors, with the scaffolding hints themselves excluded from final training trajectories; SFT data comes from the NovelQA PublicDomain split and the NarrativeQA training split. RL then follows with GRPO on LongBench-v2 for long-context QA; for deep search, RL is applied directly (skipping SFT, since the WebSailor/WebExplorer backbones already have search skills) on 1,000 sampled OpenSeeker questions.

# Q6 Experiment Design

**Long-context QA:** base models Qwen3-8B, Qwen3-14B, and Gemma4-E4B-it, each compared without tools (128K context), with tools but untrained ("w/ tools," a prompt-only 32K baseline), ContextPilot-{size} (SFT only, 32K), and ContextPilot-{size}-RL (SFT+RL, 32K) — plus published numbers for RL-MemoryAgent-7B/14B, ReadAgent-8B/14B, and StateLM-8B/14B-RL (marked in the paper as taken from the StateLM paper). Evaluated on NovelQA (Copyright split), ∞Bench (En.MC split), LongMemEval-S, and BrowseComp+ (built on a fixed corpus, not live web search) via exact-match for multiple-choice benchmarks and LLM-as-a-Judge otherwise. Headline result (Table 2): ContextPilot-8B-RL beats StateLM-8B-RL by 3.55 average points across the four benchmarks; RL over SFT-only ContextPilot yields an average +3.62 points, with a much larger +5.34-point gain specifically on the longer, harder BrowseComp+ (average input ~552K tokens) than on NovelQA (average input ~119K tokens, where SFT data already overlaps), which the authors read as RL's benefit growing with task difficulty. **Deep search:** backbones WebSailor-7B and WebExplorer-8B, evaluated on BrowseComp (pass@3), BrowseComp-ZH (pass@3), the text-only GAIA subset (103 examples, pass@1), and xBench-DeepSearch (pass@1) via LLM-as-a-Judge, against ReAct, ReAct-with-truncation (28K-token threshold), ReSum (inference-time summarization), SUPO (jointly RL-trained summarization plus agentic ability), and OpenSeeker (RL on the same 1K samples but without context-management tools). The paper reports ContextPilot surpassing SUPO by 1.51 average points across both backbones (Table 3); the WebExplorer-8B block of that table has a row-alignment ambiguity in this note's PDF-to-text extraction (see Q8), so only this paper-stated aggregate claim is reported rather than every individual cell. **Further analysis:** token-efficiency (Fig. 4) shows WebExplorer-8B's per-turn input tokens on BrowseComp growing to ~30K by turn 15, while ContextPilot-8B stabilizes at roughly 8K-10K tokens/turn; tool-use dynamics during RL training (Figs. 5-6) show information-retrieval tool share dropping from ~50% early in training as planning/memory/offloading tool share rises, with tool-invocation failure rates for memory and offloading tools falling as task success rate rises alongside them.

# Q7 Datasets and Code

No new benchmark is introduced; the paper reuses NovelQA, NarrativeQA, and LongBench-v2 for long-context QA, and OpenSeeker, BrowseComp, BrowseComp-ZH, GAIA, and xBench-DeepSearch for deep search, plus BrowseComp+ and LongMemEval-S as additional long-context-QA evaluation sets. Training-data statistics (Appendix B, Table 6): SFT retains 2,987 of 3,096 NovelQA questions and 81 of 100 NarrativeQA questions as trajectories, segmented into 51,469 total trajectory snapshots (50,691 from NovelQA, 778 from NarrativeQA); RL uses 488 LongBench-v2 questions (long-context QA) and 1,000 sampled OpenSeeker-v1 questions (deep search). Training uses the `verl` RL library, a per-query rollout budget of `N = 128` snapshots with at most 8 snapshots per trajectory, and 30K/2K maximum input/generation tokens at inference. Code, a project page, and a Hugging Face model collection are linked in the paper header: `github.com/Tencent/ContextPilot`, `tencent.github.io/ContextPilot`, `huggingface.co/collections/panzs19/contextpilot`.

# Q9 Contributions

1. Identifies and empirically motivates, via a pilot study measuring per-tool outcome variance and a correctness/context-quality-misalignment case study, three specific limitations of prior proactive context-management agents: narrow toolsets, uniform exploration across context-management actions, and coarse trajectory-level credit assignment.
2. An extended context-management toolset adding planning (`plan`), structured long-term memory (`memorize`/`updateMemory`/`readMemory` with entity, event, and relational-edge extraction), and soft, recoverable context offloading (`summarizeContext`, `compressContext` via LLMLingua-2, `foldHistory` plus `searchContext`) on top of StateLM's base tools.
3. Context-aware partial rollout, which combines context-length variation and entropy variation (measured against the trajectory's initial entropy) to identify high-sensitivity context-editing actions and allocate extra branch-sampling budget to them.
4. Fine-grained, snapshot-level credit assignment that estimates an intermediate context-editing action's value from the mean reward of all its sampled continuations rather than a single realized trajectory's reward, proven (Appendix A) to be an unbiased, lower-variance estimator of the same target credit whenever more than one continuation is sampled.
5. Reported consistent gains over rule-based and prior RL-trained baselines (StateLM, SUPO, ReadAgent, MemAgent, ReSum, OpenSeeker) across three base-model families and two task families, with a more compact working context (stabilizing at roughly 8-10K tokens/turn versus a baseline's near-linear growth to ~30K).

# Q10 Next Steps

* **Toolset coverage** (Limitations): the extended toolset may still not cover all forms of context-editing demand; the authors name richer organizing, compressing, and retrieving operations as open.
* **Hyperparameter search** (Limitations): due to compute constraints, the authors did not extensively search training hyperparameters, especially for partial rollout and credit assignment, so reported gains may not reflect each mechanism's full potential.
* **Task-family scope** (Limitations): evaluation is confined to long-context QA and deep search; extending proactive context management to agentic coding and GUI agents is explicitly named as future work.
* **Unexplained entropy instability:** the ablation (Table 5) shows entropy-based partial rollout alone was unstable — it decreased BrowseComp+ accuracy by 1.32 points on Qwen3-8B — and only became a reliable gain once combined with context-length variation. The paper does not explain why entropy alone misfires for a context-editing (rather than reasoning) action, which is an open question this note surfaces rather than one the paper poses directly.
* **Research-OS fit:** this wiki's [Context engineering](../topics/context-engineering.md) topic already asks how retrieved execution experience should be validated and what can be compressed without losing resumability. ContextPilot's fine-grained credit-assignment result (the Appendix A variance proof) suggests a general answer specifically for *training* a context-editing policy — average the reward over branched continuations at any decision point with genuine downstream uncertainty — which may extend to that topic's other harness-level and memory-level context decisions if they can similarly be branch-sampled during training.
