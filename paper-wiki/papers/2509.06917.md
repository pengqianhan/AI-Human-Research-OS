# Q1 Problem Definition

* **Input (X):** a research paper's text plus its associated public code repository (source code, tutorials/notebooks, example datasets, supplementary materials).
* **Output (Y):** a deployed, tested Model Context Protocol (MCP) server for that paper — exposing its methodological contributions as callable **Tools**, static **Resources** (manuscript text, codebase, data, figures), and multi-step **Prompts** (encoded workflows) — which any MCP-compatible chat agent ("paper agent") can invoke through natural language.
* **Core problem:** research papers are passive artifacts. Reusing a paper's method requires a reader to locate the code repository, install dependencies, configure environments, and learn API/parameter semantics — concretely illustrated with AlphaGenome, where using the method in code requires installing an environment, importing multiple modules, creating client objects with API keys, and constructing chromosome/variant input objects. Paper2Agent automates the paper-to-agent conversion to remove this barrier, turning the paper into a standing, queryable, and (the paper argues) more reliable interface to its own methods.
* **Scope:** demonstrated on three methodological papers — AlphaGenome (genomic variant-effect prediction), TISSUE (uncertainty-aware spatial transcriptomics), and Scanpy (restricted to its preprocessing/clustering workflow) — plus one cross-paper "method + data" case study connecting an AlphaGenome MCP to an ADHD GWAS discovery-paper MCP. No general-purpose benchmark across a random or large paper sample is reported; all evidence is case-study-based. The construction pipeline is implemented specifically in Claude Code, and Claude Code (`claude-sonnet-4-20250514`) is also used as the downstream chat agent in every reported evaluation, though the authors state paper MCPs "can be flexibly integrated with different chat agents."

# Q2 Problem Novelty

The paper does not claim to originate automatic code generation from papers (it cites Paper2Code [Seo et al.] and "From articles to code" [Movassaghi, Momenzadeh, Meyer] as the closest prior work) or general-purpose scientific AI agents (Virtual Lab, Google's AI co-scientist, Sakana AI Scientist, FutureHouse's Robin, CellVoyager, Biomni). Its stated novelty is narrower and more specific: rather than generating code from a paper's text, or building an open-ended discovery agent, Paper2Agent converts one specific paper into a standing, protocol-standardized (MCP), validated, and reusable tool — with an explicit reliability mechanism (validate-then-lock each tool against the reference codebase's own reported outputs) aimed at the "code hallucination" risk that ordinary LLM code generation carries.

It also positions itself as the next step in the "executable paper" lineage — Elsevier's Executable Paper Grand Challenge, Jupyter-notebook-backed publications, and the Papers with Code initiative — which the paper argues increased reproducibility and discoverability but still required the reader's own technical engagement to actually run the code. Paper2Agent's argued novelty is shifting the output of that lineage from a runnable artifact to an interactive, natural-language-queryable, autonomously-executing entity. The paper motivates this as more than incremental by proposing that a future "agent availability" section could join "data availability" and "code availability" as a standard part of how papers are published.

# Q3 Scientific Hypothesis

If a paper's methodological contributions are (a) mined from its own codebase's tutorials rather than freely generated from the paper's prose, (b) wrapped as single-purpose, parameterized tools that are tested and validated against the tutorial's own reported numerical and visual outputs before being "locked," and (c) exposed through a standardized protocol (MCP) to an LLM chat agent, then the resulting paper agent should reproduce the paper's own results with high fidelity, generalize correctly to novel queries outside the tutorial's exact examples, and do so more reliably and efficiently than a general-purpose coding agent given raw repository access or a general biomedical agent.

The paper's central evidence for this is the AlphaGenome benchmark: the AlphaGenome agent reaches 100% (15/15) accuracy on both tutorial-derived queries and held-out novel queries, versus 60%/80% for "Claude + Repo" (Claude Code given the raw AlphaGenome repository) and 40%/60% for Biomni, with 1.8x–4.6x lower median runtime. The TISSUE and Scanpy agents are reported to reproduce human-expert pipeline outputs on datasets outside their own codebase's examples (three external 10x Genomics PBMC datasets for Scanpy; a Zenodo mouse-cortex spatial dataset for TISSUE, checked against a human researcher running the same pipeline). This supports the hypothesis for the three demonstrated papers but is not tested at scale, across a random or larger paper sample, or outside genomics/single-cell biology.

# Q4 Related Work and Key People

# Q5 Key Solution Idea

1. **Two-layer architecture.** *Paper2MCP* extracts information from a paper and its codebase to build a remote MCP server; an *agent layer* wraps that MCP server as a context provider so a downstream chat agent (e.g., Claude Code) becomes a paper-specific conversational agent. Because MCP servers are modular, several paper MCPs can be attached to the same chat agent at once — exercised directly in the AlphaGenome + ADHD-GWAS cross-paper case study.
2. **Three MCP component types per server.** *Tools* are executable functions wrapping a methodological contribution (e.g., `score_variant_effect()`, `visualize_variant_effects()` for AlphaGenome); *Resources* are static assets — manuscript text, codebase, datasets, tables, figures — stored in standardized, agent-queryable formats; *Prompts* encode multi-step workflow instructions inferred directly from the paper/codebase (e.g., the correct order of Scanpy's QC → normalization → feature selection → dimensionality reduction → graph construction → clustering → annotation pipeline), removing the burden on the user to know or specify that order.
3. **Construction is itself a multi-agent pipeline, built in Claude Code.** An orchestrator agent coordinates four specialized sub-agents across six steps (Extended Methods):
   - *environment-manager* — provisions a clean, isolated, reproducible workspace and installs/pins dependencies so the codebase runs consistently.
   - *tutorial-scanner* — systematically scans the repository to distinguish genuine tutorials from other files and reports which are worth converting.
   - *tutorial-tool-extractor-implementor* — converts selected tutorials into clean, single-purpose functions: it parameterizes hardcoded values, enforces file-based inputs, saves artifacts/figures, and returns a standardized results summary, aiming to generalize beyond the tutorial's own example data while still reproducing it exactly.
   - *test-verifier-improver* — generates tests from the tutorial's own examples (for full coverage and faithful reproduction of both numerical and visualization outputs), runs them, diagnoses failures, and applies fixes in a loop; a function that keeps failing has its MCP decorator stripped and is dropped from the final server rather than shipped unvalidated.
   The six pipeline steps are: (1) locate and download the paper's official codebase; (2) environment setup; (3) tutorial discovery; (4) tutorial execution and audit (run tutorials end-to-end on their own example data, capturing inputs, outputs, figures, runtime constraints, and implicit assumptions); (5) tool extraction and implementation; (6) MCP server assembly (tools + resources + prompts, with a manifest, versioning, and basic security defaults).
4. **Reliability mechanism.** Every tool is validated against the reference codebase's own reported results and figures on example data, then "locked" — an explicit design choice against LLM "code hallucination" and a way to minimize randomness in code generation. Every tool also embeds a traceable link back to the original GitHub source, so provenance to the paper's own code is preserved end to end.
5. **Remote deployment.** The finished MCP server is hosted remotely (e.g., on Hugging Face Spaces), removing local dependency/setup friction for end users; any MCP-compatible agent can then connect to it without local installation.
6. **Extension to data/discovery papers via a "data agent."** For the ADHD-GWAS case study, the same framework's data-oriented path parses a data paper's supplementary Excel tables, cleans them, and converts them into standardized MCP Resources with consolidated metadata — letting a method-paper agent (AlphaGenome) and a data-paper agent (ADHD GWAS) be composed under one downstream co-scientist rather than requiring one paper to contain both a method and its own data.

# Q6 Experiment Design

**AlphaGenome benchmark (the paper's most quantitative evaluation).** 22 MCP tools were generated in about 3 hours on a personal laptop without human intervention. The agent was evaluated on 15 queries manually curated directly from the AlphaGenome tutorial (e.g., "Score variant chr3:58394738:A>T using ATAC-seq predictions for motor neuron cells...") and 15 novel queries constructed to be outside both the paper and codebase (new variant positions, substitutions, and tissue/cell-type combinations), to probe generalization rather than tutorial memorization. Two baselines were run on the same queries: "Claude + Repo" (Claude Code given local access to the raw AlphaGenome repository, explicitly instructed to write and execute Python code rather than answer from documentation) and Biomni (its API-based general biomedical agent). All three used `claude-sonnet-4-20250514` as the underlying LLM where applicable, run non-interactively (`claude --model ... --print --output-format json`) on a MacBook Air (M2). The evaluation procedure: (1) generate ground truth via manually curated and executed code; (2) capture each agent's response plus runtime/cost; (3) manually review and grade the response against ground truth; (4) summarize accuracy and runtime across the query set. Both the ground truth and the grading were produced by the same team that built the evaluated AlphaGenome agent (see Q8).

**GWAS interpretation case study (AlphaGenome agent, single illustrative run).** The agent was asked to interpret why variant chr1:109274968:G>T associates with LDL cholesterol — the same locus discussed in AlphaGenome's own paper. The agent built and executed a multi-step plan (score variants across modalities, filter for trait-relevant tissues, generate modality-specific visualizations, assemble a report) using tools such as `score_variant()` and `visualize_tf_binding()`, refining its plan through iterative observation and feedback.

**TISSUE agent.** 6 tools were generated covering spatial gene-expression prediction, prediction-interval construction, and uncertainty-aware downstream analysis (hypothesis testing, prediction, dimensionality reduction). Reproducibility was assessed qualitatively by comparing the agent's prediction-interval output for gene *Acta2* on mouse somatosensory cortex spatial-transcriptomics data (Zenodo record 8259942) against a human researcher manually running the same TISSUE pipeline from its GitHub tutorial; the paper states the outputs "match" without reporting a quantitative similarity metric in the retrieved text.

**Scanpy agent.** 7 tools were generated in about 45 minutes, scoped deliberately to the preprocessing-and-clustering subset of Scanpy's functionality rather than the whole package. An MCP Prompt encoding the correct pipeline order was elicited by prompting Paper2Agent itself: "Based on the tools you have, construct an MCP prompt to replicate the tutorial in the correct order. Always inspect the data first, and only deviate from the default settings if adhering to them would yield incorrect results." The agent was then run on three public 10x Genomics PBMC datasets not present in the Scanpy codebase, and its outputs (gene filtering, normalization, PCA, neighborhood graph, clustering) are reported to match human-researcher-run results, again without a stated quantitative match threshold.

**Cross-paper AI co-scientist case study.** With AlphaGenome and ADHD-GWAS (van der Laan et al., 2025, *Nature Genetics*) MCPs both connected to Claude Code, the system was prompted to propose 10 scored, structured research questions (rubric: novelty, feasibility, impact, validation clarity, resource fit, each 0–5) combining the two MCPs, with explicit constraints against fabricated citations/outputs. Users then steered the system to pursue one hypothesis (AlphaGenome prioritizes causal variants within ADHD fine-mapping credible sets), which the agent executed by prioritizing a single variant among 209 fine-mapping candidates, then scaled the same workflow autonomously across all 39 GWAS loci in under two hours, producing a per-locus markdown report (Supplementary Table 1). This is a single demonstrated run, not a repeated-trial or benchmarked evaluation.

# Q9 Contributions

1. Paper2Agent: a working orchestrator-plus-four-sub-agent pipeline (environment-manager, tutorial-scanner, tutorial-tool-extractor-implementor, test-verifier-improver) that converts a paper and its codebase into a tested MCP server (Tools/Resources/Prompts) with minimal human input, implemented on top of Claude Code.
2. A concrete reliability mechanism for LLM-agent scientific tool use — validate each generated tool against the reference codebase's own reported outputs, then lock it, while embedding a traceable link to the original source — explicitly framed as mitigating "code hallucination" rather than only maximizing capability.
3. Three demonstrated paper agents (AlphaGenome: 22 tools, ~3 hours; TISSUE: 6 tools; Scanpy: 7 tools, ~45 minutes, scoped to preprocessing/clustering) with evidence that the AlphaGenome agent outperforms a general coding agent given raw repo access (Claude + Repo) and a general biomedical agent (Biomni) on both tutorial-derived and novel queries (100% vs. 60–80% vs. 40–60%), while running 1.8x–4.6x faster.
4. A demonstrated cross-paper composition pattern — connecting a method-paper MCP (AlphaGenome) and a data-paper MCP (ADHD GWAS) to one downstream chat agent as an "AI co-scientist" — that autonomously generated and partially executed a specific, mechanistically detailed genomic hypothesis (rs1626703/MPHOSPH9 splicing in glutamatergic neurons) and then scaled the same analytical workflow across 39 GWAS loci in under two hours.
5. A reframing argument, offered as a discussion point rather than a validated finding: that ease of paper-to-agent conversion could serve as a practical proxy for codebase reproducibility and rigor, paired with a call for papers to eventually include an "agent availability" section alongside data/code availability.

# Q10 Next Steps

The paper's own stated limitations and future directions (Discussion): (a) the initial focus is restricted to methodological papers with clear code/tutorial structure — data-resource and discovery papers are named as future work, where the agent's role would shift from computation toward interpretation, curation, or explanation; (b) not every paper can become a robust agent — an incomplete, poorly documented, or buggy codebase blocks reliable conversion, which the authors reframe as a rigor signal rather than purely a limitation of Paper2Agent; (c) the benchmarking approach depends on expert knowledge and manual implementation/grading, which the authors propose to scale via LLM-as-judge evaluation in future work; (d) the paper may be the wrong unit of agentification when an idea spans a sequence of related publications, motivating a planned extension where one MCP encapsulates multiple related papers rather than exactly one.

Beyond the paper's own list, three points are worth flagging for a reader relying on this note. First, the AlphaGenome benchmark's ground truth, grading, and the evaluated agent itself were all produced by the same team, and the benchmark is small (15+15 queries) — an independent replication with blinded grading would strengthen the reliability claim considerably. Second, the TISSUE and Scanpy "matches human researcher results" claims are qualitative in the retrieved text; a reader who needs a quantitative reproducibility bound (e.g., a correlation or error threshold) cannot get it from this paper alone. Third, because two of the three case-study tools are Zou-lab publications and the third (Scanpy) is a widely-used, unusually well-documented general-purpose package, the paper's implicit claim that Paper2Agent generalizes across "research papers" broadly is asserted rather than evaluated on a more heterogeneous or adversarially chosen set of papers (e.g., papers in fields further from computational biology, or papers with less mature or less tutorial-rich codebases) — the paper itself flags this class of failure ("incomplete, poorly documented, or unresolved errors") as expected but does not quantify how common it would be outside its own selected examples.

# Related

* [LLM agents](../topics/llm-agents.md) - a genuinely different angle from this topic's other agent-construction/platform papers (OpenHands, AutoDev, Apodex 1.1): those build agent execution infrastructure that a user or downstream task operates directly, whereas Paper2Agent's orchestrator-plus-four-sub-agent pipeline (environment-manager, tutorial-scanner, tutorial-tool-extractor-implementor, test-verifier-improver) builds the interface itself — automatically converting one static research paper and its codebase into a tested, versioned MCP server, so the "agent" being constructed is a standing interactive proxy for a specific paper's methods rather than a general-purpose coding or task-execution platform.
* [Model Context Protocol (MCP)](../concepts/model-context-protocol.md) - MCP is not one feature among several here but the paper's central technique: Paper2Agent's entire contribution is systematically constructing an MCP server (Tools/Resources/Prompts) from a paper and its codebase, validating each tool against the reference implementation's own reported results before locking it, then deploying the server for any MCP-compatible chat agent — a more direct, load-bearing use of the protocol than this concept's current entries (AgentScope's MCP client support, MAI-UI's `mcp_call` action, VibeWorlding's asset-operation tools), each of which treats MCP as one integration surface within a larger agent rather than as the artifact the paper is actually about building.
