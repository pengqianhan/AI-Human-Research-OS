# Q1 Problem Definition

* **Input (X):** a visual question (one or more images plus text) whose answer may need evidence the model cannot infer from the input: exact counts or boxes in crowded scenes, facts about long-tail entities on the web, or metric quantities such as depth and 3D distance.
* **Output (Y):** the answer (an integer, boxes, a choice, or free text), produced by an MLLM orchestrator that calls tools over up to 15 iterations.
* **Goal:** give a general-purpose MLLM consistent access to heterogeneous perception, search, and computation tools, present their outputs in a form it can inspect, and keep the underlying artifacts reusable across steps, without fine-tuning the model.
* **Constraints:** the same harness, tools, prompts, and scoring serve every backbone and all 22 benchmarks; model weights stay fixed, including during domain specialization.

# Q2 Problem Novelty

Visual tool use is not new. The paper groups prior work into three lines: program-synthesis systems that compile a question into a fixed tool pipeline (ViperGPT, Visual Programming), multi-turn frameworks trained into a specific tool protocol (DeepEyesV2, PixelReasoner, AdaReasoner, OpenThinkIMG, and domain systems such as MMSearch-R1, DeepMMSearch-R1, and WebWatcher), and training-free harnesses with hand-designed tool interfaces (Visual Sketchpad, OctoTools). Its claimed gap is narrower: heterogeneous tools return masks, depth maps, and webpages that the model cannot read directly, and later steps need the raw artifacts rather than a description of them. The paper motivates the problem with its own reasoning-effort study: moving GPT-6 Luna from xhigh to max effort multiplies its model-token cost by 2.7 but raises its 22-benchmark average by 0.7 points.

# Q3 Scientific Hypothesis

If tool outputs are rendered into observations the model can inspect (an annotated overlay with counts and normalized boxes instead of an RLE mask), and the underlying artifacts stay addressable by handle so later tools and generated code can reuse them, then a general MLLM will gain more from acquiring and composing evidence than from reasoning longer over its input. The paper expects the gains to hold across model families and sizes, to exceed existing training-free and training-based visual tool harnesses, to come from both mechanisms (each adding on top of raw tool access), and to complement rather than replace higher reasoning effort.

# Q4 Related Work and Key People

* **Visual tool use.** ViperGPT and Visual Programming (fixed programs); DeepEyesV2, PixelReasoner, AdaReasoner, and OpenThinkIMG (trained multi-turn tool use); MMSearch-R1, DeepMMSearch-R1, WebWatcher, and Vision-DeepResearch (multimodal search agents); Visual Sketchpad and OctoTools (training-free harnesses, the main baselines).
* **Working memory for tool-using agents.** MemGPT and gist-memory reading agents separate a compact visible state from detailed external content; ReWOO references tool evidence through variables; CodeAct keeps intermediate results as interpreter variables; HuggingGPT and LLMCompiler resolve symbolic references to earlier outputs. OpenVLHarness extends this to a typed registry spanning images, structured data, and web references.
* **Backends.** SAM 3 (grounding), PaddleOCR-VL (OCR), Depth Anything 3 and VGGT (depth and camera trajectory), and the Serper API (search), with Grounding DINO, DeepSeek-OCR, and Gemini with Google Search as alternatives.
* **Benchmarks.** 22 datasets in four domains: grounded perception (CountQA, FSC-147, OdinW-13-All, FSCD-147, FSCD-LVIS), visual search and deep research (FVQA, MMSearch, MMSearch-Plus, HLE-VL, BrowseComp-VL, RealX-Bench), general VQA and hallucination (RealWorldQA, SimpleVQA, HallusionBench, FREAK-VQA, FREAK-MCQ, V*), and spatial reasoning (MMSI-Bench, ERQA, EmbSpatial-Bench, SparBench, MindCube).
* **Key people.** Yu Zhou, Cheng-Fu Yang, Rui Sun, Di Wu, Sibo Peng, Mingyang Zhang, Nanyun Peng, and Kai-Wei Chang (UCLA), with Zhen Yang, Ruiyi Zhang, and Zhe Gan (Apple). Likely critics: the Visual Sketchpad and OctoTools authors, whose harnesses are compared on Qwen3-VL and GPT-6 Luna, and the DeepEyesV2 and PixelReasoner authors, whose trained models are compared only on the older Qwen2.5-VL-7B base.

# Q5 Key Solution Idea

**Capability layer.** Each capability is defined by its operation, typed inputs, and the evidence and reusable data it exposes, independent of the backend. Nine capabilities are included: five for perception (zoom-in, visual grounding, OCR, depth estimation, camera trajectory), three for information seeking (text search, image search, webpage visit), and a Python coding agent. Each has an output processor that turns raw results into a model-facing observation combining a visual attachment, a short description, and compact structure: grounding returns a labeled mask overlay with the object count and boxes on a 0-1000 grid; search returns a summary of the top 10 results with inline citations, written by a Qwen3-VL-8B summarizer.

**Persistent multimodal memory.** For each query the harness keeps a registry that separates an artifact's payload from its handle. It holds image artifacts (input, tool-generated, and retrieved images, such as `input_image_3` or `tool_generated_image_6`, deduplicated by content), structured data bindings (boxes, scores, masks, depth arrays, camera parameters, OCR results, each with a field-and-shape descriptor), and web references (`webpage_url_1`). After each tool turn an Environment Update lists the available handles without repeating payloads, and a later call names a handle that the harness resolves into the input the receiving tool needs.

**Memory-grounded computation.** The orchestrator states a computational goal in language ("compute the average depth within each detected region"); a fresh context of the same backbone writes a program that runs with the actual binding values as named variables, and its outputs are registered for reuse. This lets the agent combine grounding masks with a depth array, or reconcile masks from two grounding queries to fix an undercount, without serializing arrays into its own context.

**Specialization without training.** For a new domain, failures on the user's data choose between two Codex-driven workflows (with GPT-5.5): harness search edits the system prompt, tool descriptions, and output templates; tool generation writes new tools composed from existing capabilities and accepts one only if it recovers failures on a held-out half of its examples.

# Q6 Experiment Design

* **Backbones.** Four open models (Qwen2.5-VL-7B, Qwen3-VL-8B, Qwen3-VL-32B, Kimi K3) and four proprietary ones (GPT-5 and GPT-6 Luna, Sol, and Astra at medium effort). Qwen3-VL results average three runs; proprietary results are single runs because of API cost.
* **Baselines.** The same backbone without tools; Visual Sketchpad and OctoTools on both Qwen3-VL sizes; Visual Sketchpad and Codex (the Codex CLI, web search disabled, read-only sandbox) on GPT-6 Luna; AdaReasoner, PixelReasoner, and DeepEyesV2 checkpoints against OpenVLHarness on their common base, Qwen2.5-VL-7B.
* **Scoring.** Exact match for counts, COCO box AP for grounding, option match for multiple choice, a GPT-4o judge (asking whether the report contains the correct answer) for the six search benchmarks, and a Qwen3-VL-8B judge for other open-ended answers.
* **Reasoning effort versus harness.** Base, Codex, Visual Sketchpad, and OpenVLHarness with GPT-6 Luna at five effort settings on the full splits of all 22 benchmarks (26,229 questions per setting, 524,580 in total), with model-token cost at standard-tier prices.
* **Ablation.** A ladder on Qwen3-VL-8B and 32B (datasets subsampled to at most 500 items, three runs): no tools, raw tools (minimal schema, raw payloads, no memory), plus the capability layer, plus textual memory (bindings, URL handles, Environment Updates, but tool images replaced by text descriptions), and the full harness with image handles.
* **Failure analysis and specialization.** Kimi K3 critiques 9,893 failed Qwen3-VL-8B trajectories (92% agreement with human labels on 100 samples) and proposes remedies; harness search and tool generation then run on four datasets chosen for contrasting remedy profiles, on splits disjoint from the evaluation data.

# Q8 Evidence Quality

* **Supported.**
  * *Consistent gains across backbones.* The 22-benchmark average rises from 34.2 to 45.4 on Qwen3-VL-8B, 38.3 to 50.9 on Qwen3-VL-32B, 45.8 to 56.5 on GPT-6 Luna, 60.3 to 70.2 on GPT-6 Astra, 44.4 to 55.7 on GPT-5, 52.7 to 64.3 on GPT-6 Sol, and 56.4 to 66.1 on Kimi K3, which spans the abstract's 9.7-12.6 range; Astra and Sol improve on all 22 benchmarks. The eighth backbone, Qwen2.5-VL-7B, appears only in the training-based comparison, and its no-tool score was not found in the sections read.
  * *Better than prior training-free harnesses.* On Qwen3-VL-8B, OctoTools (31.8) and Visual Sketchpad (30.5) both average below the bare model (34.2); with GPT-6 Luna, Codex (43.8) also falls below the bare model (45.8), while OpenVLHarness reaches 56.5.
  * *Better than trained tool-use models on their own base.* On Qwen2.5-VL-7B it averages 33.45 against PixelReasoner's 28.02, AdaReasoner's 25.29, and DeepEyesV2's 25.02, with the largest margins on grounding and search; the trained models lead on a few in-distribution sets such as RealWorldQA and V*.
  * *More effort does not replace the harness.* From low to max effort, Base goes from 44.3 to 48.0, Visual Sketchpad from 44.7 to 48.8, and Codex from 36.9 to 48.6, while OpenVLHarness goes from 49.9 to 60.1; at medium effort (USD 0.92 per 1,000 questions) it beats every other method at every effort, including Visual Sketchpad at max (48.84, USD 5.15).
  * *Each mechanism adds.* Overall on 8B / 32B: no tools 37.06 / 41.29, raw tools 40.84 / 45.61, capability layer 44.23 / 48.80, textual memory 44.93 / 49.12, full harness 47.14 / 52.51. Image handles add most on visual search and deep research (+6.2 / +3.5).
  * *Remedy profiles predict which specialization works.* Harness search lifts ERQA and RealWorldQA by 4.1 and 3.7 points (tool generation 0.2 and 0.1); tool generation lifts SparBench and FREAK-VQA by 8.2 and 4.5 (harness search −0.5 and −1.0).
* **Weaker or narrower than the headline.**
  * *Search access confounds the harness comparison on search benchmarks.* The bare model and Codex (web search disabled to stop it finding gold answers) cannot search the web, so on the six search benchmarks part of the gap measures having Serper search at all rather than how the harness presents it (reader observation). The paper's "no retrieval shortcut" check reports that search never surfaced a gold answer verbatim, without describing how this was checked.
  * *Cost counts model tokens only.* The 37% figure excludes tool execution (SAM 3, OCR, depth, and search APIs) and the Qwen3-VL-8B summarizer inside the search tools, which the paper states, so the harness's full cost advantage is unmeasured.
  * *The ablation's bottom rungs are built weak.* The raw-tools rung cuts each schema to a minimal signature and dumps raw payloads, so the capability-layer gain combines restoring full tool descriptions with output rendering; the paper says the comparison does not separate them. The ladder is also not monotone per domain: on 8B grounded perception the full harness (45.46) scores below textual memory (47.27) (reader observation from Table 3).
  * *Proprietary results are single runs.* GPT-5, GPT-6, and the whole effort study are one run per cell, and the paper notes that GPT models' refusals on identity questions lower some search scores.
  * *Lenient search judging.* The GPT-4o judge marks an answer correct if the report contains the correct answer anywhere, which favors long reports over short answers (reader observation).
  * *Specialization evidence is four datasets on one backbone*, chosen for contrasting profiles, with gains of 3.7-8.2 points.

# Q9 Contributions

* A capability abstraction that separates what a tool does from which backend serves it, with per-tool renderers that turn raw outputs into evidence an MLLM can inspect.
* A per-query multimodal artifact registry (images, typed data bindings, URLs) with handles that later tools and model-written code resolve, extending variable-passing ideas from text agents to images and arrays.
* A 22-benchmark, eight-backbone evaluation showing that the harness helps open and proprietary models alike, beats earlier training-free and trained visual tool systems, and is not matched by spending more reasoning tokens within the tested budgets.
* A diagnose-then-specialize recipe that uses failure critiques to choose between editing harness text and generating new composed tools, and an open-source release of the harness, tools, protocols, and workflows.

# Q10 Next Steps

* **Tool-matched baselines (reader suggestion).** Give the bare model and Codex the same Serper search and SAM 3 tools through a minimal interface, so the search-benchmark gains separate tool access from rendering and memory.
* **Full cost accounting (reader suggestion).** Report latency and the cost of tool backends and the search summarizer alongside model tokens, since the harness moves work from the orchestrator into tools.
* **Dense perception (from the paper).** Grounded perception still fails in crowded images with more than 25 objects, where 75% of failures are incorrect tool outputs, so stronger grounding backends or tiled detection matter more there than harness changes.
* **Long-term memory (reader suggestion).** The registry lives for one query. Keeping verified artifacts or generated tools across queries, as the self-evolving harness work in [Agent harness engineering](../topics/agent-harness-engineering.md) keeps edits, would turn per-query memory into reusable capability; the paper's accepted generated tools already form a bank.
* **Multilingual multimodal search (reader suggestion).** [HyperBrowseComp](2610.03574.md) asks BrowseComp-style questions whose evidence sits in videos, scans, maps, and 13 languages; it would test whether the image and web handles help where text-only search agents struggle.
