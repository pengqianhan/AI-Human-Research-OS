# Q1 Problem Definition

* **Input (X):** the interaction history a deployed routing harness naturally accumulates while serving a heterogeneous model pool — execution trajectories (user requests, model reasoning, tool calls, environment observations, terminal outcomes) plus, for every user turn, the router's predicted capability demand, the policy-adjusted service-tier decision, and the tier actually served.
* **Output (Y):** NeoHorse-1, a family of agent-native models (4B and 9B, built on Qwen3.5 bases) produced by converting that harness data into a routing-guided training curriculum, plus a described operational loop — capability-guided data allocation from evaluation feedback into the next training mixture — through which post-trained checkpoints return to the harness and feed the following iteration.
* **Core problem:** recursive self-improvement (RSI) needs a concrete mechanism by which a system observes its own capabilities and converts that evidence into the next round of learning. The paper's claim is that this mechanism does not need to be built from scratch: a harness already serving real traffic through a router already produces execution trajectories (task experience) and routing predictions/outcomes (evidence of what the model can and cannot yet do) as a byproduct of normal operation.
* **Scope:** two model scales (4B, 9B) evaluated on ten benchmarks spanning harness-based end-to-end agents, tool use, coding, and instruction following. The report frames itself explicitly as "an initial model-training prototype on this path towards RSI," not a completed RSI system — a single pass of the evaluation-selection-update loop, not a demonstrated multi-generation compounding process.

# Q2 Problem Novelty

The report does not claim to originate agentic post-training, LLM routing, curriculum learning, or on-policy distillation (OPD) — it cites FireAct, AgentTuning, Agent-FLAN, and AgentBank for trajectory SFT; Llama 3 for synthetic tool-use SFT plus iterative SFT/rejection-sampling/DPO; FrugalGPT and RouteLLM for cost-aware LLM routing; and Agarwal et al.'s OPD paper as the distillation mechanism it reuses. Its stated novelty is treating a *routing harness over a heterogeneous model pool* — rather than a fixed model's own generations, or externally curated difficulty labels — as the source of both training experience and curriculum-ordering signal. Two specific moves follow from this framing: (1) using the harness router's *predicted* capability demand, not the identity of the model actually served, as the curriculum-ordering proxy, because the served model also reflects user overrides, service availability, and deployment policy rather than task difficulty alone; and (2) closing a capability-guided allocation loop in which a checkpoint's own deficiency profile (from a decontaminated, stratified evaluation suite) reshapes the next training mixture, so what the system learns to do shapes what it learns from next. The report is explicit that this is a direct methodological extension of "Agentic Routing: the harness-native data flywheel" [33] — a separate paper this note has not read — by a substantially overlapping author team (TokenRhythm Technologies, with several named authors shared between the two papers' credited contributor lists).

# Q3 Scientific Hypothesis

If harness-recorded execution trajectories are converted into user-turn training examples that preserve interleaved reasoning, tool calls, and harness context; if the harness router's re-estimated capability-demand signal (not the served-model identity) is used to schedule both a three-stage SFT curriculum and an extension of the same staged progression to on-policy distillation, where a fixed teacher supervises the student's own generated response prefixes; and if a capability-guided allocation step feeds each checkpoint's evaluation deficiencies back into the next training mixture — then the resulting agent-native models should show consistent, broad-based gains over their un-post-trained bases on harness-based agent execution, tool use, coding, and instruction-following benchmarks, at both a 4B and a 9B scale, with the larger model retaining an advantage specifically on tasks requiring iterative debugging, recovery from execution failures, and strategy adaptation under environmental constraints. The paper treats this as a first, single-iteration test of whether the loop can close operationally at all, not a claim that the resulting gains compound indefinitely across future iterations.

# Q5 Key Solution Idea

1. **Three-granularity data organization.** A *trajectory* is a full harness-executed interaction; a *user turn* (request plus the assistant responses/tool interactions up to the next request) is the basic serialized training unit; a *subscene* groups adjacent user turns sharing a local goal and is the unit for semantic characterization — preserving provenance from raw interaction down to training example.
2. **Structural validation, then six-dimension semantic evaluation.** A rule-based gate reconstructs each trajectory's turns, tool calls, and observations, verifying causal event order and tool-call/result closure; outcomes are complete / partially recoverable / quarantined. Structurally usable trajectories are then scored on six independent dimensions — goal attainment, instruction adherence, tool use, evidence consistency, error recovery, termination — as PASS/WARN/FAIL/NOT_EVALUATED, using deterministic rules for high-certainty failures and an evidence-grounded semantic judge (restricted to trajectory-internal evidence) for cases needing task-level interpretation; missing evidence is never converted into a positive verdict.
3. **Three-axis subscene characterization (Scene / Goal / Outcome).** Each subscene is tagged with what the user is doing (Scene), what success means (Goal, decomposed into acceptance criteria and cross-turn relation to prior goals), and the verifiable result (Outcome) — with each attribute's derivation method and confidence retained separately so a semantic judge cannot silently overwrite a structurally established fact.
4. **Prediction-action-outcome separated routing signals.** The harness router assigns each turn to one of four tiers (C0 bounded/low-risk, C1 general-purpose, C2 multi-step reasoning/execution, C3 maximum capability), but the corpus retains the router's *raw* prediction, the *policy-adjusted* decision, and the tier *actually served* as three separate fields — so curriculum ordering (Section on training below) uses the raw predicted-demand estimate rather than conflating it with deployment-policy effects on which model happened to serve the request.
5. **Capability-guided data allocation.** At each iteration, the current checkpoint is evaluated on a stratified suite kept disjoint from training (via the same dedup/decontamination screen used on training data); results aggregated across attributes, quality dimensions, and routing tiers produce a per-checkpoint deficiency profile that reweights — not replaces — the next training mixture, while new harness trajectories continue arriving under the same pipeline, closing the evaluation-selection-update loop.
6. **Masked user-turn SFT.** Each training sequence is the current user turn (with retained reasoning, tool calls, and responses) plus historical context (earlier turns' visible responses/tool results, but not earlier reasoning); a binary token-level loss mask restricts prediction loss to the current turn's assistant target spans (Eq. 1), normalized by supervised-token count across the batch, following the Qwen3.5 chat/tool-call template.
7. **Routing-guided three-stage curriculum.** Each SFT example is re-scored for capability demand (hard: assigned tier index; soft: score-weighted mean tier, Eq. 2) from the request and pre-response history — not from which model the harness actually served. Training proceeds in three roughly equal-sized stages that progressively introduce higher-scored examples while deliberately reserving some lower-scored examples for later stages, without resetting the optimizer or learning-rate schedule between stages.
8. **Routing-guided on-policy distillation (OPD).** The same three-stage capability-demand scheduling selects recorded pre-response contexts as generation starting points (Eq. 4); at each stage the current student generates a response batch from these contexts, a fixed teacher supplies a next-token distribution over the student's own top-K candidate tokens plus one aggregated overflow bin, and the student minimizes a response-length-normalized reverse-KL divergence to the teacher (Eq. 3) — with the rollout checkpoint periodically refreshed so later-stage contexts receive teacher supervision on more recent student behavior, while only the student's parameters are updated.

# Q6 Experiment Design

Two scales (4B, 9B), both initialized from Qwen3.5 bases, evaluated on ten benchmarks across three categories: **agentic** — end-to-end harness-based execution (QwenClawBench, WorkBuddy Bench, PinchBench, VitaBench) and tool use/interactive completion (BFCL V4, τ²-Bench across Airline/Retail/Telecom); **coding** (HumanEval, LiveCodeBench v6); **instruction following** (IFEval, IFBench). The 4B track compares against Qwen3.5-4B, Spark-X2.5-4B, Gemma-4-E4B-it, Nanbeige-4.2-3B, and Agents-A1-4B; the 9B track against Qwen3.5-9B, Granite-4.2-8B, Ornith-1.5-9B, Gemma-4-12B-it, and the substantially larger Muse-Glimmer-30B as a contextual reference. Each benchmark uses a fixed harness/tool interface/context budget across all compared models within that benchmark, with each model's own official chat template; table entries marked with an asterisk are taken from another model's official blog or report rather than measured under the paper's own pipeline. QwenClawBench and PinchBench run through OpenSquilla as the agent harness; WorkBuddy Bench and VitaBench use their own official harnesses (VitaBench substituting DeepSeek-V4-Flash as user-simulator and judge because its originally recommended models were unavailable); BFCL V4 uses native function-calling mode; τ²-Bench uses its official framework. QwenClawBench, WorkBuddy Bench, and τ²-Bench are each averaged over three independent runs; PinchBench and VitaBench use a single run; the remaining benchmarks follow their own official protocols.

**Main results.** NeoHorse-1-4B lifts the macro-average from 58.94 (Qwen3.5-4B) to 64.87, outperforming Qwen3.5-4B on every benchmark where both have available results, ahead of the next-best 4B-track model Nanbeige-4.2-3B (62.31 avg) and Spark-X2.5-4B (62.22 avg). NeoHorse-1-9B lifts the macro-average from 65.60 (Qwen3.5-9B) to 69.04, the highest average in its own comparison table — ahead of the much larger Muse-Glimmer-30B (67.86) and Gemma-4-12B-it (63.51) — though instruction-following gains at 9B are small (one metric shows a minor decrease). NeoHorse-1-9B outperforms NeoHorse-1-4B on every benchmark with both available, with the largest scale-driven gains concentrated on harness-based agent tasks, function calling, and challenging coding, and comparatively small gains on instruction following; the paper reports NeoHorse-1-4B already matching or exceeding Qwen3.5-9B on several benchmarks.

**Trace analysis (main text).** Three representative trajectories illustrate the benchmark pattern qualitatively: a QwenClawBench project-scheduling case where NeoHorse-1-4B (unlike Qwen3.5-4B) retrieves an overlooked email with an updated dependency constraint and saves the corrected artifact to the required path; a WorkBuddy code-repair case where NeoHorse-1-9B (unlike NeoHorse-1-4B, which stops after one attempt) completes a full edit-test-inspect-repair cycle; and a PinchBench data-analysis case where, after discovering `pandas` is unavailable, NeoHorse-1-9B abandons repeated failed dependency-install attempts and switches to Python's standard library, completing the task with roughly 70.8% / 76.7% / 83.6% fewer requests, execution time, and tokens respectively than the 4B trajectory on the same task.

**Appendix case studies (A-C).** Three additional worked examples compare NeoHorse-1-9B against Qwen3.5-9B: a daily-ticket-reporting task under temporal/audit constraints, where NeoHorse-1-9B's reported 50 eligible records / 19 tickets matches independent recomputation while Qwen3.5-9B's final report carries internally contradictory totals (20 vs. 26 vs. 31) and assigns a next-day update's state to an in-window record; a repository time-leakage-auditor implementation task, where NeoHorse-1-9B reads the README and applies its documented five-minute tolerance while preserving the required output schema, and Qwen3.5-9B never reads the README, hardcodes a two-second tolerance, rejects a valid sample, and breaks the output schema; and an HTML Gomoku game, where a scripted 26-click replay renders 26 correctly tracked stones for NeoHorse-1-9B but produces zero placed stones for Qwen3.5-9B due to a DOM-property indexing bug in its click handler.

**Data ablations (held on the 4B model, 5-benchmark subset: LiveCodeBench, HumanEval, IFBench, BFCL V4, τ²-Bench).** Under matched initialization, curriculum schedule, optimizer, seed, and training budget, routing-harness-sourced trajectories beat a public synthetic tool-agent dataset (Toucan) on all five benchmarks by an unweighted average of +6.26 points (70.57 vs. 64.32), with the largest gains on HumanEval (+8.54) and τ²-Bench (+11.31). A second ablation scales unique routing-harness supervision over strictly nested subsets (fixed initialization, optimization, and pass count): the five-benchmark average rises from 69.31 at the base model to 71.45 at the largest data scale tested, on a logarithmic token-scale axis, without an observed saturation point within the tested range.

# Q7 Datasets and Code

No new pretraining corpus is released as a standalone artifact; the primary training corpus is an internal harness-generated set of roughly 10⁵-10⁶ trajectories, broadened with public instruction, reasoning, tool-use/code, and preference data (OASST2, the Aya dataset, ToolACE, APIGen, OpenThoughts3-1.2M, OpenR1-Math-220K, HelpSteer2, Nemotron-SFT-SWE-v3, UltraFeedback-binarized-cleaned). All evaluation benchmarks used (QwenClawBench, WorkBuddy Bench, PinchBench, VitaBench, BFCL V4, τ²-Bench, HumanEval, LiveCodeBench v6, IFEval, IFBench) are pre-existing public benchmarks, not new releases of this paper. # Q9 Contributions

1. Reframes the RSI data problem: argues a deployed routing harness over a heterogeneous model pool already emits the three signals RSI needs — execution trajectories, routing signals separating predicted from actually-served capability demand, and outcome feedback — without a separate RSI-specific instrumentation layer.
2. A trajectory-to-training-example pipeline at three linked granularities (trajectory / user turn / subscene) combining rule-based structural validation, six-dimension semantic evaluation (deterministic plus evidence-grounded judge, PASS/WARN/FAIL/NOT_EVALUATED), and three-axis (Scene/Goal/Outcome) subscene characterization that keeps structural facts protected from semantic-judge override.
3. A routing-guided three-stage curriculum for SFT — ordered by re-estimated capability demand rather than served-model identity — extended to routing-guided on-policy distillation with a compact top-K-plus-one-bin reverse-KL objective and a periodically refreshed rollout checkpoint.
4. Capability-guided data allocation that closes an evaluation-selection-update loop, reweighting the next training mixture from each checkpoint's own deficiency profile on a decontaminated, stratified suite.
5. Reported macro-average gains of 58.94→64.87 (4B) and 65.60→69.04 (9B) across the ten evaluated benchmarks (see Q8 for the ten-vs-eleven abstract discrepancy), with NeoHorse-1-4B beating Qwen3.5-4B on every directly comparable benchmark and NeoHorse-1-9B posting the highest average in its own comparison table, ahead of the much larger Muse-Glimmer-30B.
6. Ablation evidence that routing-harness-sourced trajectories transfer more effectively than a matched public synthetic agent dataset (Toucan) under identical training configuration (+6.26 unweighted average across five benchmarks), and that scaling unique routing-harness supervision continues improving results (69.31→71.45) over the tested data range without an observed saturation point.

# Q10 Next Steps

The paper is explicit that its own evidence covers only a single pass of the evaluation-selection-update loop: whether gains realized from returning a post-trained checkpoint to the harness continue to compound across successive generations "remains to be tested," not something this report demonstrates. It names three concrete extensions: iterating the feedback loop across successive model generations; extending experience collection, capability-guided allocation, and curriculum design to the harness's full range of tasks, execution environments, and models (validation here covers only agentic, coding, tool-use, and instruction-following capability); and sharpening the routing signal itself into calibrated difficulty/deficiency estimates — including training the router, which the paper states as a direct future step rather than something already built.

Two points beyond the paper's own framing are worth flagging for a reader assessing this note's evidence. First, this report is presented as a direct methodological extension of a separate paper, "Agentic Routing: the harness-native data flywheel" [33], by a substantially overlapping author team at the same primary affiliation (TokenRhythm Technologies); this note has not read that paper, so it cannot independently verify the underlying C0-C3 router's own predictive accuracy — only that NeoHorse-1 treats the router's raw predictions as a curriculum-ordering signal. Second, the paper reports no held-out human evaluation of its own six-dimension semantic-evaluation judge — the same judge that gates which trajectories are admitted as training data in the first place — leaving open whether errors in that judge could bias the training distribution in ways the reported benchmark gains would not surface; this is a data-quality-evaluator-reliability gap structurally adjacent to the evaluator-reliability questions this wiki's [Post-training feedback](../topics/post-training-feedback.md) topic already tracks for judge-derived training signals, though NeoHorse-1's judge gates *data admission* rather than directly shaping a scalar reward.
