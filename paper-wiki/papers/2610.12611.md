# Q1 Problem Definition

* **Input (X):** a software type (for example "spreadsheet" or "mail client") plus supporting resources; nothing else is hand-written per application.
* **Output (Y):** (a) a library of runnable desktop applications, each with a functional specification, a distinct interface, and GUI-tested behavior; (b) natural-language GUI tasks grounded in the functions that passed testing; (c) trajectories from those tasks used to fine-tune a computer-use agent (CUA).
* **Constraints the paper sets for itself:** *diversity* of interfaces and interaction patterns, *functional reliability* of every specified function through complete GUI workflows, and *scalability* with little human engineering.
* **Core problem:** CUA training data comes either from a fixed pool of real applications, which are costly to wrap as reproducible environments and invite application-specific overfitting, or from browser-hosted mock software, whose shared HTML/DOM substrate limits interaction depth and persistent workflows.

# Q2 Problem Novelty

Not a new problem. Synthesizing environments for GUI agents is an active line the paper cites: InfiniteWeb and AutoWebWorld generate websites and state-machine web worlds, GUI-GENESIS and ScaleWoB synthesize software as backend-free webpages, and CUA-Universe and Gym-Anything wrap existing software. The claimed difference is the artifact: standalone desktop applications (Avalonia, compiled and run in Ubuntu virtual machines) with persistence and file workflows rather than webpages, produced with explicit structural-diversity gates and a GUI-level test-and-repair loop.

# Q3 Scientific Hypothesis

1. **Structure must be forced apart.** If style variants are required to differ on at least two layout dimensions and pass a tree-edit-distance gate, generated interfaces for one software category will not collapse to the same layout, which unconstrained generation does.
2. **GUI evidence is needed for repair.** If repair is driven by failures observed while operating the running application, reliability rises; repair from source inspection alone does not.
3. **Synthesized software transfers.** If an agent is fine-tuned only on trajectories from synthesized applications, it improves on real applications it never saw (OSWorld), which would show it learned general GUI interaction rather than application-specific procedures.

# Q4 Related Work and Key People

* **Data synthesis inside existing software.** OSWorld, Windows Agent Arena, and AndroidWorld made real applications reproducible for evaluation; OS-Genesis, AgentSynth, ProCUA-SFT, and EvoCUA synthesize tasks and trajectories within them; CUA-Universe and Gym-Anything configure existing software as agent environments; UI-TARS, OpenCUA, and FedMABench refine online traces, collect human demonstrations, or train on decentralized data.
* **Browser-hosted synthesized environments.** InfiniteWeb, AutoWebWorld, GUI-GENESIS, ScaleWoB.
* **Key people.** Shanghai Jiao Tong University (Siheng Chen, corresponding author) with Zhejiang University; Haoting Shi, Wenhao Wang, Tian Jin, and Siheng Chen are also authors of CUA-Universe, which this paper cites. Likely critics: groups that train CUAs on real applications (OpenCUA, EvoCUA, UI-TARS), who would ask how a synthesized application's behavior compares with the real one, and authors of web-environment synthesis, who would ask for a matched comparison with browser-hosted data.

# Q5 Key Solution Idea

Three stages run by Codex CLI agents with GPT-5.5, plus a separate GUI agent as tester.

* **Design.**
  * *FunctionDesigner* expands the software type into a specification in four steps: baseline functions of a mature product, domain-specific professional functions (multi-condition retrieval, batch operations, history, validation), complete workflows across modules including failure handling, and finally a per-function contract (user entry, action, expected state update, visible response, acceptance checkpoint).
  * *StyleDesigner* writes several style specifications over the same functions, each following a layout archetype; every pair must differ on at least two of four layout dimensions (navigation, spatial organization, object browsing, action placement). Independent *SubStyleDesigners* turn each into Avalonia XAML, which is compiled to check validity.
  * Each blueprint becomes a normalized layout tree (windows, regions, panels, controls; text and colors removed). If the minimum pairwise normalized tree-edit distance is below 0.60, the least distinct blueprint is regenerated.
  * *IconDesigner* and *SubIconDesigner* produce per-style SVG icon sets that must differ structurally, not only in color.
* **Implementation.** *Coder* builds the full application and writes a functional manual with an acceptance check per function; *DevCoder* audits bindings, logic, persistence, startup, and file interfaces against the manual and repairs gaps.
* **GUI evaluation and repair.** *EvalTaskGenerateAgent* writes test cases from the manual once, after the first implementation; the suite is then fixed. A GUI agent (Seed 2.1 Pro, mouse and keyboard, up to 50 steps per case) runs them and records traces, checkpoint evidence, failure location, and a repair suggestion, which go back to the coders. Up to three versions per application, stopping early if all cases pass. A design-token fidelity score (weighted overlap of colors, corner radii, primary color, font, and resource binding; threshold 0.80) guards against repairs that drift from the blueprint; the paper notes this is not a perceptual image-similarity measure.
* **Task synthesis.** A function tree is built from the manual and the evaluation report; a capability counts as supported only if it cites a passed case, checkpoint, or interaction step. Tasks are planned at three difficulty levels (one goal; related operations with a dependency; multi-stage workflow where each stage sets up the next) in file-based and blank-state forms, then written as natural requests with an internal specification of initial state, outcome criteria, process criteria, and expected final state.

# Q6 Experiment Design

* **Synthesis.** Twelve categories (browser, chat, code editor, forum, mail, PDF, rich-text editor, image editor, slides, spreadsheet, music player, video player); applications run in isolated Ubuntu 22.04.3 virtual machines.
* **Training.** Full-parameter supervised fine-tuning (SFT) of the language model of Qwen3.5-9B (vision encoder and merger frozen), one epoch, learning rate 5e-6, sequence length 16,384, on 16 A800 GPUs. Candidate trajectories are scored by two GPT-5.5 judges, one for outcome (final messages and screenshots) and one for process (all messages, up to ten sampled screenshots); an attempt is kept only if both scores are at least 0.8. The SoftwareGym set has 3,715 trajectories and 55,263 serialized examples before length filtering, 49,445 after.
* **Evaluation.** OSWorld (244 tasks from eight application domains) and SoftwareGym-Bench (one application from each category, ten manually verified tasks each, 120 tasks, with reproducible initializers, programmatic evaluators, and distractor and protected objects). OSWorld's native context and tool protocol, temperature 1, 100 steps, three independent rollouts per task. The headline metric is Pass@3, task-level success across the three rollouts; per-run averages are in Appendix D.
* **Baselines.** Eight API models (GPT-5.5, GPT-5.4, Gemini 3.1 Pro, Gemini 3 Flash, Seed 2.1 Pro, Seed 2.0 Pro, Qwen3.8-Flash, Qwen3.7-Plus), six open-weight models of 32B or more, and compact 7-9B agents (EvoCUA-8B, DART-GUI-7B, OpenCUA-7B, UI-TARS-1.5-7B, the Qwen3.5-9B base).
* **Ablations.** Full design against a "simple" design told only that ten layouts should differ (ten blueprints per category, 240 total); GUI-guided against source-only repair on 36 applications (three per category) from a shared first version; and training on SoftwareGym, OSWorld-application, or combined trajectories at matched size.

# Q8 Evidence Quality

* **Supported.**
  * *Structured style design produces structural diversity.* Macro-average diversity (mean pairwise normalized tree-edit distance, 0-100) is 83.6 for the full design against 4.9 for the simple one, higher in all twelve categories; none of the twelve simple sets passes the 0.60 gate, and each contains at least one pair with an identical layout tree.
  * *GUI feedback is what makes repair work.* From a shared 50.4% pass rate, GUI-guided repair reaches 70.5% and then 83.1%; source-only repair reaches 50.5% and then 48.8%. The 34.3-point final gap has a 95% hierarchical-bootstrap interval of 28.2-41.0, and GUI-guided repair wins on all 36 applications.
  * *The library is reliable by the pipeline's own test.* Mean GUI pass rate over the 182 applications rises from 54.9% (first version) to 81.1% and 91.5%.
  * *Transfer to real applications is large on both metrics.* On OSWorld, Pass@3 goes from 41.39% to 56.97% and the single-run average from 28.40% to 46.77%, with all eight domains improving on Pass@3 (Chrome 28.26 to 58.70, VS Code 30.43 to 60.87, Calc only 27.66 to 31.91). The fine-tuned 9B model is level with EvoCUA-8B (56.56%) and below EvoCUA-32B (67.62%) and every API model (67.62-79.51%).
  * *Cost.* On a sample of 20 applications: 237.3 minutes, 14.8 million tokens, 1,718 model calls, and an estimated $70.76 per application.
* **Weaker or narrower than the headline.**
  * *Pass@3 is a best-of-three number.* The abstract's 56.97% counts a task as solved across three rollouts; a single run of the fine-tuned model averages 46.77%. The gain over the base model holds on both, but absolute numbers should be compared with other papers' single-run scores only through the Avg@3 rows.
  * *"Strictly out-of-domain" means unseen applications, not unseen kinds of software.* Eight of the twelve synthesized categories are chosen to match OSWorld's application domains (121 of the 182 applications), and the paper measures how much of the corresponding real applications' functionality they reproduce (all 49 major modules, 78.8% of concrete functions). No OSWorld application, task, or trajectory is in training, but the training distribution was built to resemble the test applications' functions (reader observation).
  * *Synthesized data does not beat native data on OSWorld, and adding it does not help there.* At matched size, training on OSWorld-application trajectories gives 61.48% Pass@3 on OSWorld, SoftwareGym-only 56.97%, and both together 58.61%. Single-run averages are 48.06%, 46.77%, and 47.10%, so the three are within about 1.3 points. The "complementary" claim rests on SoftwareGym-Bench (33.3%, 40.0%, 47.5%). The text read does not say whether the OSWorld-application training tasks overlap the 244 evaluation tasks; if they do, that row is an in-domain reference rather than a like-for-like competitor.
  * *SoftwareGym-Bench is in-distribution for the fine-tuned model.* Its twelve applications come from the same library; the sections read do not say whether those applications, or sibling variants sharing their functional specification, were held out of training. With ten tasks per application, per-category scores move in 10-point steps.
  * *The 91.5% reliability figure is model-judged.* Test cases are generated from the implementation's own functional manual and executed and assessed by a GUI agent, so a pass is checkpoint evidence recorded by a model and a failure may be the tester's rather than the application's. Applications enter the library with some failing cases; task synthesis then uses only functions with passing evidence.
  * *One training run, no variance.* Evaluation uses three rollouts, but each model is trained once.
  * *No comparison with browser-hosted synthesis.* The motivating claim that webpages limit interaction depth is not tested against a model trained on web-synthesized data of the same size.

# Q9 Contributions

* A multi-agent pipeline that turns a software type into multiple structurally distinct, GUI-tested desktop applications, with quantified diversity and fidelity gates.
* A measured result that GUI-level failure evidence, not source-level self-review, is what makes agent-written applications reliable.
* A released library of 182 applications in twelve categories and a 120-task benchmark with programmatic evaluators.
* Evidence that SFT on trajectories from synthesized desktop software alone transfers to real OSWorld applications, close to matched-size training on the real applications when measured by single-run average.

# Q10 Next Steps

The paper's conclusion states no limitations or future work; the items below are reader suggestions.

* **Hold out categories.** Train without the eight OSWorld-aligned categories (or with only the other four) to measure how much of the transfer comes from functional similarity to the test applications.
* **Scale curve.** Report OSWorld score against the number of applications and of variants per category, to show whether diversity or volume drives the gain; the structural-diversity score makes this directly measurable.
* **Check the tester.** Have people or programmatic checks audit a sample of the GUI agent's pass and fail verdicts, since the whole reliability claim and the task-evidence gate rest on them.
* **Match against web synthesis and against a stronger base.** Compare with ScaleWoB- or GUI-GENESIS-style data at equal size, and repeat on a larger model, where [AutoGUIWorld](2610.01215.md) saw gains concentrate in multi-application tasks while Chrome tasks got worse.
* **Project fit (reader note).** The repair ablation is a clean statement of a rule this repository's agents already follow: verification has to exercise the running artifact, because source-only review left pass rates flat and slightly lower.
