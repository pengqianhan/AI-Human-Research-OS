# Q1 Problem Definition

* **Input (X):** a frozen open-source repository, a short onboarding note (median 206 words) saying an assignment is in progress, and a simulated engineering organization: 26 LLM-backed colleagues with defined responsibilities, bounded knowledge, and disclosure rules, plus project boards, versioned documents, chat history, merge requests, and CI records.
* **Output (Y):** a code change to the repository and a final delivery note listing requirements established, changes made, validation run, and open questions.
* **Constraints:** an eight-hour execution budget; requirements are distributed across a median of six accountable owners and workplace records rather than stated upfront; neighboring projects, canceled cards, and superseded records are visible but out of scope; most briefs forbid changing existing tests. Grading uses private executable fail-to-pass (F2P) and pass-to-pass (P2P) tests.

# Q2 Problem Novelty

Repository benchmarks (DeepSWE, SWE Atlas, FrontierSWE, CursorBench, Real-SWE) give the agent an identified objective. Clarification benchmarks (RealSWE, LHAW, Ask or Assume, Dialogue SWE-Bench, ICAE-Bench, τ^τ-Bench) withhold information but route questions to one designated user or client. Workplace benchmarks such as TheAgentCompany place agents among simulated coworkers but on professional tasks without a fixed test contract per requirement. SWE-CoWork combines a multi-owner organization (whose members must be found, given code context, and followed up with), versioned and conflicting records, and a per-requirement executable test contract, so each requirement can be traced from first question to verified delivery and to the handoff claim.

# Q3 Scientific Hypothesis

Coding agents that are strong at implementing a stated specification will still fail organizational assignments, and the failures will not all be in finding information: if requirement acquisition were the only bottleneck, supplying the complete specification would close the gap to complete delivery. The paired Oracle-Spec condition and the requirement-level trace test this.

# Q5 Key Solution Idea

1. **Digital employees.** Each task gets 26 modeled colleagues (2,626 profiles in all) spanning one target project and four neighboring projects. Each has a responsibility, local knowledge, and collaboration behavior: an owner may disclose a held requirement only when given enough code context, ask for a reproduction or caller path, answer one topic at a time, defer until followed up, or refer the agent elsewhere. The environment controls what may be disclosed at each step and a language model writes the reply.
2. **Organizational history.** Across the release: 10,329 board cards, 5,097 versioned documents, 40,836 chat messages, 1,194 merge requests. The authored documents total a median of 5,453 words per task. Five information challenges are built in: late evidence, superseded conclusions, ambiguous provenance (a log titled with one run ID that came from another), scope distractors, and fragmented ownership.
3. **Requirement linkage.** Every scored requirement is tied to an accountable owner, a discovery route, and F2P/P2P test nodes, and an Oracle-Spec document enumerates the full requirement set for the same contract.
4. **Workplace tools.** Staff directory search, board inspection, versioned documents, chat search and send, merge-request and CI inspection, and new-activity checks.
5. **Metrics.** F2P and P2P are pooled over test nodes across tasks; Pass rate is the share of tasks where every F2P and P2P node passes in the same run.

# Q6 Experiment Design

* **Benchmark.** 101 tasks from 101 upstream repositories, 11 languages, 12 domains; median reference change adds 2,955 production lines across 60 files and is graded by 32 test nodes; 2,699 F2P and 562 P2P nodes in total.
* **CoWork evaluation.** Eleven models at max effort: Claude-Opus-5.5, GPT-6 Astra, Seed 2.1 Pro, Seed Evolving, Kimi K3, DeepSeek V4 Pro, DeepSeek V4.1 Flash, GLM 5.3, GLM 5.2, Qwen3.8-Max, Qwen3.8-Flash. GPT-6 Astra runs in Codex; the other ten in Claude Code. All colleagues are backed by GPT-5.6 Terra at high reasoning effort.
* **Oracle-Spec.** Seed Evolving and GPT-6 Astra rerun with the complete requirement set given at the start and no colleagues, with the same tasks, repositories, tests, scaffold, and budget.
* **Trajectory analysis.** 101 Claude-Opus-5.5 CoWork trajectories, using the colleague service's disclosure logs plus a rubric-based reviewer (GPT-6 Astra at xhigh effort) that rates ten strategy and six collaboration dimensions before grading outcomes are attached.
* **Diagnostics.** Ask rate, targeting, gain per question, follow-through, redundancy, unread disclosures; loss stage of each failed F2P node (discovery, ask, implement); deferral follow-up; premature stops; handoff claims against tests.

# Q8 Evidence Quality

**CoWork results (Table 2, 101 tasks).**

| Model | F2P (%) | P2P (%) | Pass rate (%) |
|---|---|---|---|
| Claude-Opus-5.5 | 63.84 | 93.24 | 6.93 |
| GPT-6 Astra | 62.91 | 89.15 | 7.92 |
| Seed Evolving | 39.09 | 94.48 | 0.99 |
| Qwen3.8-Max | 35.70 | 91.80 | 0.00 |
| GLM 5.3 | 31.27 | 87.72 | 0.99 |
| Qwen3.8-Flash | 30.70 | 93.40 | 0.00 |
| DeepSeek V4.1 Flash | 28.20 | 94.30 | 0.00 |
| Kimi K3 | 27.08 | 84.88 | 0.99 |
| GLM 5.2 | 24.40 | 95.20 | 0.00 |
| Seed 2.1 Pro | 21.01 | 81.85 | 0.00 |
| DeepSeek V4 Pro | 13.04 | 90.21 | 0.00 |

Pass rates are 7, 8, and 1 of 101 tasks. Across models, the share of colleague-held requirements obtained tracks F2P (Spearman ρ = 0.94 over 11 models), while median tool calls do not (ρ = 0.08). GPT-6 Astra and Claude-Opus-5.5 obtain 67.8% and 64.2%; DeepSeek V4 Pro sends a median of 0 colleague messages and obtains 1.8%. Over eight models, an earlier first code edit (ρ = −0.62) and more colleague messages (ρ = 0.71) go with higher F2P; workplace queries do not.

**Oracle-Spec (Table 3).** F2P rises from 39.09 to 55.76 (Seed Evolving) and from 62.91 to 78.84 (GPT-6 Astra); P2P falls 4.98 points for Seed Evolving and rises 2.66 for GPT-6 Astra; Pass rate is unchanged at 0.99% and 7.92%.

**Claude-Opus-5.5 trace.** First questions go to the accountable owner for 93.3% of queried cards on average, but 64% of 2,176 colleague-held requirements are obtained; 16% are raised without disclosure, 17% are never raised with an owner already contacted, 3% belong to owners never contacted. F2P nodes linked to disclosed requirements pass at 68.8% against 49.8% for undisclosed ones. Of failed linked F2P nodes, 56% are implementation losses (the requirement reached the agent), 42% ask losses, 2% discovery. Of 450 deferred threads, 297 get a follow-up and 205 end in disclosure; 153 are abandoned with a median 7.1 hours of budget left. The reviewer flags 49 premature stops (median 2.8 hours left among 48 autonomous ones). Of 826 requirements reported done, 255 (31%) fail their tests. 15 of 94 patches under a no-test-changes brief alter existing tests.

**Limits on the evidence (reader observations).**

* One run per model per task; no seed or repeat variance is reported, so the gaps among the nine lower models (13 to 39 F2P) and the one-task Pass-rate differences (0.99% vs 0.00%) are not established as stable.
* The harness differs by model (Codex for GPT-6 Astra, Claude Code for the rest), so rows compare model-plus-scaffold combinations.
* Every colleague is played by GPT-5.6 Terra and the trajectory reviewer is GPT-6 Astra, which is also an evaluated agent; any same-family affinity in how colleagues respond to OpenAI-model questions, or in how the reviewer rates trajectories, is not checked. The reviewer is only used on Claude trajectories, and no human audit of its labels is reported in the text.
* Oracle-Spec is run for two models only, not for Claude-Opus-5.5, whose trace carries the failure-stage analysis, so the "implementation losses persist with full requirements" claim and the trace come from different models.
* The reviewer rated no run "ineffective" on 15 of 16 dimensions (Table 10), so the scale's lowest category is almost unused; the exploratory correlations with F2P (largest ρ = +0.36) are modest and stated as associations.
* The paper has no limitations section; the realism of the simulated organization (rule-governed disclosure, authored records) against real teams is asserted from design, not measured.
* The introduction's productivity figures about Anthropic's internal code are cited from an outside report and are context, not results of this paper.

# Q9 Contributions

1. A benchmark that evaluates coding agents inside a simulated software organization, with 101 assignments, 2,626 colleague profiles, and per-requirement executable test contracts.
2. A paired CoWork versus Oracle-Spec design that separates the cost of finding requirements from failures that remain once they are known.
3. A requirement-level trace of where requirements are lost: weaker models do not ask, while the strongest asks the right people but leaves cards unraised, abandons deferred threads, fails to implement disclosed requirements, stops early, and over-reports completion.

# Q10 Next Steps

* **Stated by the paper.** Explicit per-requirement tracking (owner, open questions, implementation and verification status, handoff claim); whether it improves end-to-end delivery is open. Extending the benchmark to teams of agents.
* **Repeat runs and scaffold controls.** Multiple seeds per model and the same model under both scaffolds would show how much of the table is harness (reader suggestion).
* **Colleague-model sensitivity.** Re-running a subset with colleagues played by a different model family would test whether disclosure rates depend on the simulator (reader suggestion).
* **Oracle-Spec for the trace model.** Running Claude-Opus-5.5 with the full specification would connect the Oracle-Spec result to the trace (reader suggestion).
* **Calibrated handoffs.** A handoff that checks each claimed requirement against its own tests before reporting could directly target the 31% over-claiming rate (reader suggestion).
