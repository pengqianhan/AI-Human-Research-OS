# Q1 Problem Definition

* **Input (X):** a natural-language query describing one undesirable agent behavior (for example "retries an unchanged tool call after it fails"), a collection of recorded deployment traces (instructions, messages, tool calls, tool results, other events), and a target benchmark size range (default 5 to 50 instances). Queries may add behavior parameters, domain restrictions, trace constraints such as "context longer than 100,000 tokens," or combine two behaviors with AND/OR.
* **Output (Y):** a benchmark of context inputs, each the recorded trace prefix just before a confirmed occurrence of the behavior, plus a behavior-specific rubric scored 0-5. If no valid benchmark can be built, the system returns a rejection with a reason.
* **How a model is tested:** the evaluated LLM sees the prefix and produces exactly one next assistant turn (text, tool calls, or both). A judge panel grades only that turn. Nothing is executed, the trace is not continued, and there is no reference answer: the deployed agent's original turn is evidence of the bad behavior, not a target.
* **Constraints:** the behavior must leave observable signals that code can search for (tool errors, call arguments, event order, keywords). Behaviors that would need an LLM or a human to read every session are out of scope because that cost is too high at deployment scale.

# Q2 Problem Novelty

Partly new. Outcome benchmarks such as Terminal-Bench, RE-Bench, MLE-bench, and PaperBench check whether a task is completed. Safety and process-level suites (for example AgentHarm) check behavior during execution, but their cases and target behaviors are fixed. Trace-auditing tools find failures and patterns in recorded sessions, but they do not turn those records into benchmarks for testing other LLMs. Continuing an LLM from recorded histories or saved states has precedents, and OpenAI regenerates candidate models' responses on deployment conversations before release. The authors' claim is narrower: TraceDance is the first system to build benchmarks *on demand* for a user-specified undesirable behavior from deployment traces. The motivation is that agent behavior problems change as agents and deployments change, and many traces come from private repositories, internal tools, or MCP servers that cannot be replayed.

# Q3 Scientific Hypothesis

The authors' intuition is that a context in which a deployed agent actually showed an undesirable behavior is likely to lead other LLMs into the same behavior. If traces are cut just before that behavior and each LLM's next turn is graded against a behavior-specific rubric, the result should be (1) valid, in that humans agree the instances test the requested behavior, (2) gradable by an LLM judge panel about as reliably as by humans, and (3) informative, exposing weaknesses that outcome-based benchmarks miss. A second, engineering hypothesis is that cheap programmable retrieval on CPUs followed by LLM confirmation of only the retrieved candidates makes this affordable over hundreds of thousands of sessions.

# Q4 Related Work and Key People

* **Outcome-level agent evaluation:** Terminal-Bench (final container state), RE-Bench and MLE-bench (performance metrics), PaperBench (rubric-based LLM judging).
* **Safety and process-level evaluation:** AgentHarm and similar fixed suites, and LLMs judging proposed actions or recorded traces.
* **Continuation-based evaluation:** continuing from interaction histories, from synthesized snapshots of risk-triggering decision points, or from saved execution states; Prefix-GRPO uses teacher prefixes for training; OpenAI's pre-release regeneration on deployment conversations.
* **Agent auditing and automatic benchmark construction:** trace-auditing tools that summarize behavior or locate user-specified violations; BenchTrace, which conditions agents on annotated failures in fixed environments; generated behavioral or safety scenarios (including Bloom, an open-source tool for automated behavioral evaluations); REAP and SWE-Together, which rebuild executable tasks from recorded sessions; WildToolBench, which seeds synthetic dialogues from real logs. Session domains are clustered in the style of Clio.
* **Key people:** Dehai Min (contact, University of Illinois at Chicago) and Philip S. Yu (UIC), with ByteDance co-authors; the deployment traces come from ByteDance-operated agents running mainly on Doubao Seed models. Likely critics: builders of environment-replay benchmarks, who would point out that a single graded turn cannot show the outcome, and LLM-judge skeptics.

# Q5 Key Solution Idea

* **Decision-point continuation with three frames.** The *action* frame cuts before the target action ("what should the LLM do here?"). The *failure* frame keeps the observed failure but drops the response ("how should the LLM respond?"). The *claim* frame keeps the recorded work and results but drops the claim ("what, if anything, should the LLM claim?"). An instance is kept only if the held-out turn really shows the behavior, the context contains what is needed to decide, and the decision has not already been made.
* **Behavior specification with four parts:** an executable anchor that finds candidate positions, a confirmation criterion, a frame-specific cut rule, and a rubric.
* **Anchor-and-Confirm.** The anchor scans traces on CPUs with no LLM calls. A cheap "Flash" model (DeepSeek-V4-Flash) then confirms only the retrieved candidates. GPT-5.6-Sol is the Strong Model that selects and writes specifications, and Claude Opus 4.8 is the Reviewer that audits custom specifications and their anchor code.
* **Catalog plus synthesis.** A manually reviewed catalog of 28 behavior families (13 action, 10 failure, 5 claim) was mined from 10,000 reserved sessions per setting. Catalog reuse requires two of three independent family selections to agree, then all three equivalence checks to pass. Otherwise the *Anchor Synthesis Loop* writes a new specification, runs safety checks and a code review, executes the anchor, and revises it from retrieval statistics. The limits are at most 5 rounds, at least 8 sessions checked, a confirmation rate of at least 25%, and at least 8 confirmed examples, with 3 needed to begin acceptance review. In one example, a dependency-manifest anchor was rewritten to check the state at the decision point instead of requiring a later manifest edit, and matched sessions rose from 3 to 32.
* **Faithful prefixes.** Each instance keeps system instructions, tool definitions, user and harness-injected input (system reminders, skill instructions), assistant messages, and tool results. Only the source model's reasoning blocks are removed. Cuts at harness-forced turns (such as compaction-summary requests) are excluded.
* **Grading.** A three-judge panel (GPT-5.6-Sol, Gemini-3.5-Flash, Claude Opus 4.8) scores each response on the 0-5 rubric, and a response passes if the mean is at least 4.

# Q6 Experiment Design

* **Traces:** 252,557 de-identified sessions collected over six weeks from Claude Code (75,076; coding) and OpenClaw (177,481; general tool use), mainly driven by Doubao Seed 2.0 models. 10,000 sessions per setting are reserved for behavior discovery and excluded from construction.
* **Queries:** 139 test queries. 107 should be built (98 predefined, 9 custom), and 32 should be rejected (27 adversarial, 5 missing a required numeric parameter). The queries were drafted with LLMs and reviewed by the authors.
* **Evaluated models:** Claude Opus 4.8, GPT-5.6-Sol, GLM-5.2, DeepSeek-V4-Flash, DeepSeek-V4-Pro, Qwen3.7-Max, MiniMax-M3, Doubao-Seed-2.1-Pro, and Kimi-K3. Each gets the recorded system prompt and tool definitions unchanged through its provider's tool-calling API, with high reasoning effort and a 32,768-token output limit.
* **Human validation:** eight annotators, two per item, on 100 queries and 100 instances stratified by behavior family. Annotators do not see judge scores or model identity.
* **Robustness checks:** judge self-preference, 5,000 bootstrap resamples of the 107 benchmarks for rank intervals, alternative passing thresholds, and a comparison of Doubao-sourced and other-sourced instances.

# Q7 Datasets and Code

Built: the TraceDance pipeline, a 28-family behavior catalog, and 107 benchmarks with 4,125 instances. Code is at [ZhishanQ/TraceDance](https://github.com/ZhishanQ/TraceDance) with a [project page](https://zhishanq.github.io/TraceDance/). The deployment traces are not released, so the authors state the exact benchmarks cannot be rebuilt from public data; the pipeline can be applied to other trace collections. The appendix gives condensed prompts and one worked example from construction to grading.

# Q8 Evidence Quality

* **Supported:**
  * *Construction works at scale.* It built benchmarks for 102 of 107 build-target queries (95.3%) and rejected all 32 rejection-target queries. Per successful query, anchors scanned 128,297 sessions on average, 706 candidates went to the Flash model, 40.4 instances were kept, and 552 LLM calls were used (1.3 for a rejected adversarial query).
  * *Queries are mostly understood.* Annotators rated 78% of the system's interpretations accurate and 17% partly correct, and agreed with each other on whether clarification was needed for 96 of 100 queries.
  * *Instances and rubrics are mostly valid.* Both annotators confirmed the behavior in 84 of 100 sampled instances. Both rated rubric quality at least 4/5 in 90% of instances (mean 4.75). The most common complaint was unclear boundaries between adjacent score levels (21 mentions).
  * *The judge panel matches humans about as well as humans match each other.* Pass/fail agreement with humans is 81.0% on 84 instances (single judges 65.5-79.8%), with Cohen's κ = 0.40 against 0.31 between the two annotators.
  * *Frontier LLMs mostly fail these decision points.* Overall pass rates range from 22.9% (Qwen3.7-Max) to 33.5% (Claude Opus 4.8), mean 26.7%. The claim frame is hardest (mean 20.3%), and OpenClaw is harder than Claude Code (22.9% vs. 28.3%). Opus ranks first in 99.9% of bootstrap resamples, 4.2 points ahead of second (95% CI 1.7-6.6). The nine models fall into three groups; differences within a group are not significant.
  * *Checks before acting are the weakest skill.* Mean pass rates are 67.9% for issuing a valid tool call, 33.5% for handling failures, 28.9% for honest claims, and 8.1% for performing a required check first. Individual families go as low as 6.9% (secret protection), 0.9% (commit hygiene), and 0.6% (failure-log inspection). With a pass threshold of 3 instead of 4, check-first rises to 26.8%, but the group order and Opus's first place hold under every threshold tested.
  * *Overall rank hides per-behavior strengths.* On error-guided correction, Kimi-K3 passes 57.8% against Opus's 27.8%. GPT-5.6-Sol ranks fifth overall but leads 8 of the 28 families, including test-claim grounding (60.2% vs. at most 39.5%). GPT-5.6-Sol has higher reported SWE-bench Pro and Terminal-Bench 2.1 scores than DeepSeek-V4-Pro and GLM-5.2 but does not beat either here.
  * *Two confounds are checked.* GPT-5.6-Sol as judge shows a small self-preference (0.22 points on the 0-5 scale, CI excluding zero), with no clear effect for Opus, and removing each model's own judge leaves its rank unchanged. Doubao-Seed-2.1-Pro shows no family-specific disadvantage on Doubao-sourced instances (−0.9 points overall; −1.2, CI −3.3 to +0.9, when restricted to Seed 2.0 sources). The authors say the intervals rule out a disadvantage larger than about 3 points, but not smaller ones.
* **Weaker or bounded:**
  * *One graded turn cannot show outcomes.* A response that plans or gathers information first may behave well later, and a passing response may still fail when executed; the authors say this complements rather than replaces task-level evaluation. Responses that start with TodoWrite pass 4.6% vs. 30.8% for other first actions on the same instances (for all nine models), but the authors present this as association, not cause. That penalty may partly come from the single-turn design itself (reader inference).
  * *Pass rates are conditional.* Every instance comes from a context where the behavior already happened, so pass rates do not estimate how often the behavior occurs in deployment. The rubric also credits only the most appropriate response.
  * *The judge panel is lenient.* All three judges score higher than humans (means 2.02-2.90 vs. 1.68; 0-scores 11.9% vs. 39.3%). Because humans pass only 16.7% of responses, raw agreement is inflated: labeling everything as failing would agree 83.3% of the time. κ = 0.40 is moderate, and the validation sample is 100 instances.
  * *16% of sampled instances were not confirmed by both annotators*, so a share of each benchmark may not test the requested behavior.
  * *Not reproducible from public data.* Traces are private, and the non-Doubao source models are confidential.
  * *Construction-side models are also evaluated.* GPT-5.6-Sol, DeepSeek-V4-Flash, and Opus 4.8 build specifications or confirm candidates and are also among the nine evaluated LLMs. The paper analyzes judge self-preference and source-model family, but I did not find an analysis of construction-role bias in the retrieved text (reader note).
  * *The recursive self-improvement framing is untested.* The authors leave evaluating TraceDance inside an RSI loop to future work.

# Q9 Contributions

* Decision-point continuation: a way to evaluate agent behavior on real deployment contexts without environment replay, including traces from private tools and MCP servers.
* Anchor-and-Confirm plus the Anchor Synthesis Loop: an affordable pipeline from a natural-language behavior query to a validated benchmark, with explicit acceptance and rejection rules.
* A 28-family catalog of deployment-grounded undesirable behaviors across coding and general tool use, and 107 benchmarks with human validation of instances, rubrics, and grading.
* A measured profile of nine frontier LLMs at agent decision points: required checks, secret handling, and honest claims are far weaker than tool-call formatting, and overall rankings hide large per-behavior reversals.

# Q10 Next Steps

* **Close the loop** (the authors' stated future work): use TraceDance benchmarks inside a model-improvement cycle and test whether later revisions fix the targeted behaviors without regressions.
* **Multi-turn continuation:** grading a few turns, or executing the next turn in a sandbox where possible, would separate "plans first, acts well later" from real failure, the main ambiguity in the TodoWrite result.
* **Construction-bias controls (reader note):** rebuild a subset of benchmarks with different Strong and Flash models and check whether evaluated-model rankings change.
* **Base rates (reader note):** the pipeline measures behavior given a known-bad context. Pairing it with frequency estimates from the same traces would show which weaknesses matter most in deployment.
* **Links to this wiki (reader notes):** [RRSI](2609.24972.md) argues that harness self-improvement needs held-out, noise-aware gates; TraceDance benchmarks are one candidate source of such gates. [AI Agents Do Not Fail Alone](2607.14275.md) scores the context before execution, while TraceDance scores the model's decision given a fixed context; together they could separate context faults from model faults. [EmbodiedSWE](2609.27308.md) audits reward hacking in whole runs, a process-level check that TraceDance's claim frame covers at single decision points.
