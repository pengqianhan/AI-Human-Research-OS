# Q1 Problem Definition

* **Input (X):** a real scientific-software GitHub repository at a fixed baseline commit (source code, public fixtures, dependencies, compilers/tools), plus a task specification in one of three paradigms (Issue-driven, Expert-exploratory, Engineering-integration), given to a coding agent.
* **Output (Y):** a code patch to the repository that a coding agent believes resolves the task, evaluated by rebuilding the project in a clean environment and running held-out tests via a per-task Docker verifier image; success is a binary pass@1 per task.
* **Core problem:** scientific software increasingly functions as part of the scientific instrument itself, so a repair failure can compromise not just program behavior but the evidence underlying a scientific conclusion — yet existing coding-agent benchmarks measure aggregate task success and give little insight into *why* agents fail specifically when the software encodes domain-specific scientific contracts (units, coordinate systems, numerical invariants, file-format semantics, physical assumptions, workflow conventions) that ordinary code benchmarks never expose.
* **Scope:** 119 release tasks across 98 GitHub repositories spanning 20 scientific domains (96 tasks under unrestricted licenses in the default selection, 23 additional restricted-license tasks available via explicit opt-in); repository-level repair with programmatic verification, not isolated-function synthesis.

# Q2 Problem Novelty

Per the abstract, existing evaluations of coding agents largely emphasize aggregate task success and provide limited insight into failure causes when repairing scientific software specifically. SWE-bench Science's novelty is narrowing the SWE-bench-style repository-repair paradigm to a domain (scientific computing) where correctness depends on contracts — units, coordinate systems, numerical invariants, physical assumptions — that are rarely exposed by ordinary code benchmarks, and pairing that benchmark with an explicit taxonomy of *why* agents fail (four recurring failure mechanisms) plus a controlled ablation isolating the causal effect of scientific guidance on repair quality, rather than reporting pass@1 alone.

# Q3 Scientific Hypothesis

If coding agents are evaluated on repository-level repair tasks drawn from real scientific-software repositories under paradigms (Issue-driven, Expert-exploratory, Engineering-integration) that require preserving domain-specific scientific contracts, then even the strongest current agents will show substantially lower pass@1 than on general-purpose software-engineering benchmarks, their failures will cluster into identifiable mechanisms tied to scientific-knowledge gaps rather than generic coding errors, and providing explicit scientific guidance will help or hurt repair success depending on whether that guidance is well-grounded or poorly aligned with the task — i.e., scientific knowledge is not uniformly beneficial to agent repair.

# Q5 Key Solution Idea

1. **Three task paradigms.** Tasks are organized as Issue-driven (resolving a stated bug/feature request, closest to classic SWE-bench), Expert-exploratory (requiring the agent to discover the fix target without an explicit issue), and Engineering-integration (integrating or extending scientific-computing functionality into an existing system) — a taxonomy meant to separate different failure regimes rather than treat all repository repair as one task type.
2. **Repository-level, contract-preserving evaluation.** Each of the 119 tasks ships with baseline source, public fixtures, dependencies/compilers/tools, held-out tests, and two published Docker images (environment + verifier); the workflow applies an agent's patch to the clean baseline, rebuilds the project, and scores it against held-out tests, so correctness is checked against the same reproducible infrastructure used to build the benchmark rather than against the agent's own claims.
3. **Four-mechanism failure taxonomy.** Analyzing agent failures, the paper identifies four recurring mechanisms: deficits in scientific knowledge or abstraction, misguided exploration or surface-level repair, incomplete repair coverage or system integration, and failure to generalize scientific knowledge beyond observed cases — giving a vocabulary for *why* an agent failed rather than only whether it failed.
4. **Paired scientific-guidance ablation.** A controlled ablation removes explicit scientific guidance from the task while preserving the repository and executable engineering context, isolating the causal contribution of that guidance. The result is asymmetric: well-grounded scientific information can constrain the search space and improve both average performance and token efficiency, while poorly aligned guidance can induce anchoring effects that do not reliably improve — and can even harm — exact repair success.
5. **Reproducible distribution pipeline.** Tasks are distributed via Hugging Face (task table, selections, runtime tools), Docker Hub (immutable per-task environment/verifier images), and GitHub (documentation, tooling, audit records); a `materialize.py` tool produces an explicit `selection.json` recording exact task IDs and a selection hash, and `run_batch.py` drives agent execution against a configured harness (e.g., Codex) with credentials kept outside the checkout.

# Q6 Experiment Design

The headline result (from the abstract and corroborated by the project page's leaderboard) is that the best-performing evaluated agent, **Claude Code with Opus-5 (max)**, achieves pass@1 below 50% — the project page's own leaderboard (as of 2026-08-16) lists it at 47.90%, followed by GPT-5.6-sol (max) at 46.22%, DeepSeek-V4-Pro (max) at 42.02%, Kimi-K3 (max) at 35.29%, and GLM-5.2 (max) at 31.93%, across nine total evaluated (model, configuration) pairs. Beyond the leaderboard, the paper's core experimental contribution is the paired ablation (scientific guidance present vs. removed, repository/engineering context held fixed) used to attribute the four-mechanism failure taxonomy to specific causes rather than to report a single aggregate number.

# Q9 Contributions

1. **SWE-bench Science**, a 119-task, 98-repository, 20-domain benchmark extending the SWE-bench repository-repair paradigm to scientific software, organized into three task paradigms (Issue-driven, Expert-exploratory, Engineering-integration) and evaluated via reproducible Docker-based environment/verifier images.
2. An empirical finding that even the best current coding agent (Claude Code with Opus-5, max) resolves fewer than half of these tasks (47.90% pass@1 per the project leaderboard), establishing scientific software repair as substantially harder than general-purpose repository repair for today's agents.
3. A **four-mechanism failure taxonomy** (scientific-knowledge/abstraction deficits, misguided exploration/surface-level repair, incomplete coverage/integration, failure to generalize) giving future work a shared vocabulary for diagnosing *why* an agent failed on a scientific-software task.
4. A **paired ablation** isolating the causal effect of explicit scientific guidance on repair, showing the effect is guidance-quality-dependent rather than uniformly positive — well-grounded guidance helps average performance and token efficiency, poorly aligned guidance can anchor the agent and does not reliably help exact repair.

# Q10 Next Steps

Open questions this note cannot resolve without the full paper text: the precise operational definitions distinguishing the three task paradigms (what makes a task "Expert-exploratory" rather than "Issue-driven" in borderline cases); the quantitative breakdown of failures across the four mechanisms per paradigm or per scientific domain; and how "well-grounded" versus "poorly aligned" scientific guidance was operationalized or selected for the ablation, which matters for judging how actionable the guidance-quality finding is for harness designers. **Research-OS fit:** relevant to any project evaluating coding agents on scientific-computing repositories, or designing scientific-guidance prompts/skills for such agents — the guidance-quality ablation is a direct empirical caution against assuming more domain context is always better, worth revisiting once the full paper is retrievable (retry `hf papers read` once the paper has had more time to index, or fetch the PDF/TeX source directly).
