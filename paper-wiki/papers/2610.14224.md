# Q1 Problem Definition

* **Input (X):** a stream of tasks q₁, …, q_N that arrive one at a time with no answers, verifiers, or scores; a frozen executor model; a common starting harness H₀ made of K = 8 editable files (system prompt, guardrails, memory, tool guidance, skills, scripts, subagents, and a middleware plugin that runs inside the tool loop); and a budget for re-running the current task.
* **Output (Y):** for each task, one deliverable produced under an adapted harness, plus an updated *improvement harness* (a library of adopted harnesses and lessons) carried to the next task.
* **Constraints:** completed tasks are never replayed; every task restarts from H₀ rather than inheriting the last task's harness; the editor never sees a grader verdict, rubric, or score; the model's weights and the improvement procedure stay fixed.

# Q2 Problem Novelty

Partly new. Offline harness search (Meta-Harness, AHE, and others in the paper's comparison table of 27 methods) optimizes against training tasks before deployment; test-time methods refine a harness per task (Recursive Harness Self-Improvement, Harness Scaling) or carry one forward across unlabeled batches (TTHE), sometimes with proxy or delayed labels. The paper's claim is the combination: label-free, task-by-task refinement of both the execution harness and the procedure that refines it, together with a test-time scaling study. It argues this matters because deployed tasks have no verifiers, and because carrying a highly tailored harness to the next task adds noise when the task distribution shifts, while the experience of how a weakness was diagnosed and fixed is reusable.

# Q3 Scientific Hypothesis

1. Running a proposed edit on the same task and comparing its trajectory and deliverable with an unedited reference gives enough evidence to choose harness changes without any correctness label.
2. Spending more test-time budget on this (more candidates composed in parallel, or more chained steps) keeps improving the deliverable.
3. Lessons extracted from that process, stored with the harnesses they produced, make later refinements better, including on a different benchmark.

# Q4 Related Work and Key People

* **Recursive self-improvement.** Self-rewarding models, STOP, the Darwin Gödel Machine, Hyperagents (editable meta-level procedure), MetaSkill-Evolve and MCE (co-evolving artifacts and the skills that build them).
* **Harness optimization.** Prompts and workflows (DSPy, GEPA, ADAS, AFlow); memories and skills (ReasoningBank, Evo-Harness, HyperSkill); whole harnesses offline ([Meta-Harness](../concepts/meta-harness.md), AHE, AI4AI, DarwinX, HarnessX, HSI), offline-plus-test-time (MemoHarness, Harness-R1, [JIT-Agent](2608.25593.md), Recuris), and online (RHI, Harness Scaling, TTHE, Adaptive Auto-Harness, Continual Harness, HCL). Parallel recursion borrows its aggregation principle from RSA, and sequential recursion is Self-Refine applied to the harness.
* **Key people.** Google Cloud AI Research (Tomas Pfister, Chen-Yu Lee, Rujun Han, Yanfei Chen) with first author Ruiyao Xu (Northwestern). The group also wrote ReasoningBank, one of the baselines, and six of the authors are on [RRSI](2609.24972.md), which evaluates offline harness evolution on two of the same benchmarks. Likely critics: Meta-Harness and AHE authors, who would ask for compute-matched comparisons, and the authors of "Rethinking the evaluation of harness evolution" (the Harness Scaling baseline).

# Q5 Key Solution Idea

**A contrastive step: Propose, Probe, Compose.** The current harness is run once on the task as a reference; the reference shows how the harness behaves, not whether its output is right. An editor then writes two candidate harnesses by editing component files: an *invariant* candidate aimed at deficiencies that recur across domains (planning, tool use, context management, delegation) and a *domain-specific* candidate aimed at the knowledge, procedures, and constraints of this task's domain. Each candidate is run on the same task under the same model and environment, and the difference from the reference is the evidence. A composer reads the reference, both candidates, their diffs, and all runs, then merges supported changes, revises conflicting ones, adopts one candidate, or keeps the current harness, tying each decision to an observation. The composed harness is run to produce the deliverable.

**Two ways to spend more.** With budget k, *parallel recursion* collects k references, drafts k candidates of each scope, and runs k independent composition sessions over the whole pool (one population update, so k sets width, not depth). *Sequential recursion* chains k steps, each starting from the previous harness and all evidence so far. For k > 1 an agentic selector compares anonymized deliverables against the request and source files and returns one, without seeing which harness made it.

**Learning to harness.** After the task, a reflector reviews the whole record and keeps lessons only where an execution contrast supports them; the adopted harness tree and an `EXPERIENCE.md` (situation, lessons, evidence) become a library entry with an index. The next task starts again from H₀, but its proposals, probes, and composition can read and adapt library entries. Executable components are kept as files, not summarized as prose.

# Q6 Experiment Design

* **Benchmarks.** [WorkBuddy-Bench](../concepts/workbuddy-bench.md) Code, Web, and Office (test halves of 40, 35, and 25 tasks; composite verifier of hidden tests, file checks, and LLM or VLM judge items with Gemini 3.5 Flash as judge). [JobBench](../concepts/jobbench.md) (34 test tasks; weighted rubric judged by Claude Opus 4.8). [Harvey LAB](../concepts/harvey-lab.md) (100 test tasks from a published harness-optimization split; per-criterion pass rate, "Partial", judged by Claude Sonnet 4.6). Each method processes the test tasks as one stream; means and standard deviations over three streams in shuffled order.
* **Configurations.** Executors Gemini 3.5 Flash and GLM-5 inside OpenCode or Codex (four pairs per benchmark); 200 turns and 3,600 seconds per rollout. Editor, composer, reflector, and selector are Claude Opus 4.8 under OpenCode at high reasoning effort; a guard refuses any working directory that holds a verdict, rubric, or score. Main tables use one step (k = 1); "+ Recursion" is parallel recursion at k = 5.
* **Baselines.** Base harness; ReasoningBank (fixed harness plus retrieved memory distilled under an answer-free self-judge); Meta-Harness (offline search on the WorkBuddy-Bench and JobBench training halves, or LAB's 24-task dev set, then deployed unchanged); Harness Scaling (per-task, verifier-blind revision with no carried state). All use Opus 4.8 for revision and reflection.
* **Analyses.** Budget curves for parallel and sequential recursion on WorkBuddy-Bench Code and Office; total tokens against performance; ablations of the library, the two scoped editors, and composition (k = 1); library effects (direct refinement without evidence, libraries built at k = 1 and k = 5, transfer from JobBench to WorkBuddy-Bench, leave-one-out re-runs); the same model as executor and editor (five models, k = 2); component removal, library provenance, cross-model transfer, tool-error rates, comparison with production harnesses, and a failure analysis in the appendix.

# Q8 Evidence Quality

* **Supported.**
  * *One step helps in every configuration.* WorkBuddy-Bench averages rise from 72.4, 74.5, 64.2, and 64.4 to 77.5, 77.5, 75.7, and 75.3 (Gemini/OpenCode, Gemini/Codex, GLM-5/OpenCode, GLM-5/Codex); JobBench by 1.2 to 4.5 points; LAB Partial by 2.0 to 11.8. It is above every baseline on WorkBuddy-Bench average and JobBench score in all four pairs, and on LAB in three of four (Meta-Harness leads for Gemini under Codex, 76.5 against 75.6). Harness Scaling falls below the base harness in seven of twelve benchmark-configuration pairs.
  * *More budget keeps paying.* Parallel recursion at k = 5 adds 2.9 to 3.9 points on WorkBuddy-Bench, 3.0 to 4.2 on JobBench, and 2.6 to 6.7 on LAB over one step. On WorkBuddy-Bench Code and Office both recursion forms rise monotonically from k = 1 to 5 (parallel: 76.5 to 80.8 and 79.5 to 83.4), while Harness Scaling regresses from k = 2 to 3.
  * *Each component contributes.* With Gemini/OpenCode at k = 1, removing the library costs 3.1 (WorkBuddy-Bench) and 1.8 (JobBench), replacing the two scoped editors with two generic ones costs 2.9 and 3.7, and skipping composition costs 1.6 and 1.9.
  * *The probes, not just a better editor, carry the gain.* Letting the editor rewrite the base harness directly, without references, probes, or library, lowers WorkBuddy-Bench Code from 73.4 to 63.2 and Web from 69.9 to 65.0.
  * *Experience transfers somewhat.* A library built at k = 5 supports one-step gains of 0.9, 4.4, and 5.1 (Code, Web, Office) without further probing, and a JobBench library improves WorkBuddy-Bench by 0.6, 0.5, and 2.9.
  * *No stronger editor needed.* With the same model as executor and editor (OpenCode, k = 2), all five models from GLM-5 to Claude Opus 5 improve on every benchmark, for example GLM-5 by 13.7 on LAB.
  * *Fewer tool errors.* One step lowers the tool-error rate on all three benchmarks, most on JobBench (14.4% to 9.1%), while increasing the number of calls on JobBench and LAB.
* **Weaker or narrower than the headline.**
  * *Selector and judge share a model.* Opus 4.8 edits, composes, and selects, and Opus 4.8 is also JobBench's judge; WorkBuddy-Bench's judge items use Gemini 3.5 Flash, one of the executors; LAB is judged by Claude Sonnet 4.6. The guard hides rubrics and scores, but a selector that prefers what the same model family prefers as a judge would raise JobBench scores without better work (reader observation). No human scoring or cross-family judge is reported.
  * *Main tables are not compute-matched.* One step already runs the task four times (reference, two probes, composed harness), and parallel recursion at k = 5 runs it twenty times plus editor sessions, against one run for the base harness. The token comparison that addresses this (Harness² on the Pareto frontier) is in a figure whose values were not read. A Best-of-k baseline with the same selector is specified in Appendix C, but no Best-of-k number appears in the text or tables read, so how much of the k = 5 gain comes from picking among more runs rather than from harness edits is not shown.
  * *Small margins against noise.* Standard deviations reach 4.5 points, and several one-step gains are within one of them (Gemini/Codex on JobBench, 33.9 ± 2.6 to 35.3 ± 3.5; Gemini/OpenCode on LAB, 79.9 to 81.9). No significance tests are reported.
  * *Main results use a stronger editor.* In the main tables Opus 4.8 improves harnesses for weaker executors; the same-model study (k = 2) reports its gains in a figure, and only a few of them are stated in the text.
  * *Cross-task learning is the least-tested level.* The library's effect within a stream is measured by one ablation (k = 1, one configuration). The leave-one-out re-run (77.5 to 79.4 on WorkBuddy-Bench, 36.0 to 37.7 on JobBench) can read later tasks' entries and repeats execution, which the authors flag as offline analysis, not an online gain.
  * *Selection can pick the worse output.* The failure analysis shows the selector choosing a 55-point output over a 95-point one, and a LAB case falling from 54 to 26 through narrower coverage; an incorrect premise can also spread across all candidates.

# Q9 Contributions

* A definition of recursive agent harnessing that separates the execution harness being improved from the improvement harness doing the improving, with only the latter carried across tasks.
* A label-free improvement step that uses matched re-runs of the current task as evidence and splits proposals into cross-domain and domain-specific scopes, with parallel and sequential ways to scale it.
* Gains over offline search, retrieval memory, and per-task revision on three judge-scored professional benchmarks, a test-time scaling study, and ablations showing the scoped editors and the probes matter.
* A concrete eight-component, file-per-component harness layout (including a middleware plugin that enforces behavior from inside the tool loop) and worked cases of which component a diagnosed failure leads to editing.

# Q10 Next Steps

* **From the authors.** Library management (consolidating overlapping components, revising stale experience, better retrieval) and adaptive recursion that allocates budget by task difficulty or stops when probes stop adding evidence; better selection that balances coverage and precision, probes that challenge shared premises, and repeated runs to separate edit effects from noise.
* **Isolate selection (reader suggestion).** Report Best-of-k with the same selector at matched executions, and the score of the composed harness's single run before selection.
* **Decouple judge and selector (reader suggestion).** Re-score JobBench with a judge from another family, or have humans grade a sample, and repeat with a selector from a different family than the judge.
* **Measure the library over longer streams (reader suggestion).** Plot per-task gain against stream position to show whether later tasks benefit more than earlier ones, which is the online effect the leave-one-out test cannot show.
* **Project fit (reader note).** The invariant-versus-domain split maps onto this repository's own layering: cross-project rules in the root agent instructions and skills, domain knowledge in project files. The probe-then-compose discipline (run the edited setup on the same task beside an unedited reference before keeping a change) is a cheap check worth adopting when revising agent instructions here.
