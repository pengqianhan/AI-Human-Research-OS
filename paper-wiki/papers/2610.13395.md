# Q1 Problem Definition

* **Input (X):** for environment construction, a source-available repository $P_i$. For the task agent, an execute-only reference program $B_i^\star$, its usage documentation $D_i$, and a network-isolated sandbox $\mathcal{S}_i$; no source code.
* **Output (Y):** from the pipeline, an environment $e_i = (B_i^\star, D_i, \mathcal{T}_i, \mathcal{S}_i)$ where $\mathcal{T}_i$ is a black-box behavioral test suite. From the agent, source code in any compiled language plus a compile script producing a candidate executable $\widehat{B}_i$ whose observable behavior matches the reference on the tests.
* **Constraints:** the agent must discover requirements by running the reference and decide the design itself. Passing $\mathcal{T}_i$ shows agreement on tested behavior, not semantic equivalence.
* **Core problem:** (i) building verifiable training environments at scale, which needs a working build for each repository and tests that both cover behavior and reject wrong reproductions; (ii) keeping a long development run coordinated, since a single session can start coding before exploring enough and lose early observations when its context is compressed.

# Q2 Problem Novelty

The task is not new: ProgramBench and MirrorCode define program reproduction from a binary and documentation, and MindForge already trains on it. The paper's claimed gaps are that issue-resolution environment generators (SWE-Gym, SWE-smith) start from an existing codebase, that MindForge is limited to command-line programs and does not filter trajectories by recovered behavior, and that general harnesses have no workflow for exploration-then-implementation. MindForge is not compared because its environments and trajectories are unreleased.

# Q3 Scientific Hypothesis

1. **Feedback loops make environment construction reliable.** If build attempts and generated tests are validated and the diagnostics returned to the constructing agent, repositories can be turned into environments with high behavioral coverage and discriminating tests.
2. **Training on such environments helps.** If a model is fine-tuned on trajectories filtered by test pass rate in these environments, it reproduces more program behavior on a held-out benchmark.
3. **Separated roles with a build gate help more.** If analysis, implementation, and review run in separate sessions that exchange only written artifacts, and every round must compile independently, the same model recovers more behavior than in one long session, and more rounds recover more.

# Q4 Related Work and Key People

* **Program reproduction from scratch.** ProgramBench (Yang et al., 2026), MirrorCode, MindForge.
* **Issue resolution and repository generation.** SWE-bench and variants; NL2Repo-Bench and other requirements-document settings, which the paper says reduce the task to implementation.
* **Scaling coding environments.** SWE-Gym, SWE-smith, SWE-Master, and R2E-Gym, which the paper cites as evidence that generated environments improve issue-resolution agents.
* **Key people.** Xiamen University (Jinsong Su and Fei Long, corresponding authors), with Washington University in St. Louis, the Institute of Automation of the Chinese Academy of Sciences, and Unisound. Likely critics: the ProgramBench authors, who would point out that the flagship numbers used for comparison come from a different scaffold, and test-generation researchers, who would ask how well the suites separate nearly-correct from correct programs.

# Q5 Key Solution Idea

**Program-Env** (Claude Code as the harness, DeepSeek-V4-Flash-0731 as the model, with outer feedback loops):

* **Collection.** A stratified GitHub search by language and star bucket (41,833 repositories), metadata validation and removal of repositories used by existing code benchmarks (35,710), a locked commit each, and static detection of build configuration (30,459 candidates).
* **Build.** The agent writes `download.sh` for online dependency preparation and `compile.sh` for offline compilation; the loop advances only if both succeed and the executable passes a loadability check, otherwise diagnostics go back for revision.
* **Dispatch.** The source is split into functional modules, the executable is instrumented for coverage, and documentation such as the README is extracted.
* **Tests.** One subagent per module writes tests over several rounds. After each round it reads three feedback documents: a *summary* of what was done and what remains; *program analysis* that finds uncovered functionality by dynamic coverage and traces it to public entry points by static analysis (Joern or CodeQL); and *validation* from four checks: the pass check (test fails on the reference), the double check (inconsistent across repeated runs), the dummy check (test accepts a dummy implementation), and the weak-assert check (a 37-rule static linter for weak oracles such as exit-code-only assertions). A subagent stops at 80% functionality coverage, at a round limit of 5 to 20 scaled by repository complexity, or early when coverage stalls. Only tests passing all checks are kept.

**Program-Agent** (built on Claude Code):

* **Analysis.** An analyst session reads the documentation and explores the reference program without touching the workspace, and writes `analysis.md`, which is then frozen.
* **Implement.** A separate session writes code from the hand-off artifacts and has *no access to the reference program*; it records changes in `delivery.md`. The first round must deliver something that builds.
* **Review.** The analyst role, in a fresh session with read-only access, compares the reference with the newly built candidate and writes verified discrepancies to `review.md` as requirements for the next round.
* **Revision management.** After each implementation round a clean Git archive of the committed source is compiled outside the workspace (300-second timeout). A stage that times out, misses artifacts, or fails the build is retried in a fresh session (two attempts by default) with only a bounded diagnostic; if it still fails, the workspace rolls back to the last revision that built.
* **Budget.** One analysis stage, then $K$ alternating implement and review rounds ($K=5$).

# Q6 Experiment Design

* **Training data.** Trajectories from rejection sampling DeepSeek-V4-Flash-0731 with Claude Code on all 1,648 environments, filtered by test-case pass rate. Because Claude Code resets or switches context within a rollout, each context segment is one training example: 64,505 trajectories, which the paper notes are not 64,505 independent rollouts.
* **Fine-tuning.** Qwen3.8-27B, all parameters, two epochs with ms-swift, sequences packed to 262,144 tokens, loss on assistant tokens only, and turns that call tools unavailable in the environment masked out.
* **Evaluation.** ProgramBench (200 tasks) in isolated containers with 8 CPU cores, 16 GB RAM, 30 GB storage, and an 8-hour limit. Metrics follow ProgramBench: *Tests Passed* (macro-average of per-task pass rates), *Almost Resolved* (at least 95% of tests), and *Resolved* (all tests, no cheating flag).
* **Comparisons.** Claude Code as the single-session baseline against Program-Agent, for Qwen3.8-27B, its fine-tuned version, and DeepSeek-V4-Flash-0731; flagship-model rows are copied from the ProgramBench paper, where they ran under mini-SWE-agent.
* **Analyses.** Environment statistics, iteration budget $K \in \{1,3,5\}$ for the fine-tuned model, action-type distributions, token cost, pass-rate distributions, and code size against the reference.

# Q7 Datasets and Code

A [project page](https://programgym.github.io/), a GitHub repository at [Acm1011/ProgramGym](https://github.com/Acm1011/ProgramGym) (1 star at fetch time), and a Hugging Face organization (`huggingface.co/ProgramGym`). The paper says it *will* release environments, construction code, and training artifacts; what is available now was not checked. Environment statistics: 1,648 repositories in eight functional categories (developer tools 441, CLI and system utilities 372, data and scientific computing 243, security and forensics 227, and four smaller ones); 5,918 test-writing subagents; 665,512 validated test cases (mean 404 per repository), 98.50% written from scratch rather than adapted from native tests; mean coverage 72.99% (median 81.63%); 136.77B tokens in total, about 82.99M per environment. By the paper's size-based complexity score, 1,492 tasks are easy, 151 medium, and 5 hard.

# Q8 Evidence Quality

* **Supported.**
  * *The pipeline produces environments at scale.* The counts above, with per-stage retention in the collection funnel and the stated termination settings.
  * *Fine-tuning raises average behavior recovered under a fixed scaffold.* With Claude Code, Tests Passed goes from 34.87% to 42.84% (+7.97).
  * *The workflow raises it far more for the same weights.* Program-Agent takes Qwen3.8-27B from 34.87% to 55.71% and the fine-tuned model from 42.84% to 56.25%; the share of tasks passing at least 50% of tests goes from 40.5% to 62.0% and at least 75% from 18.0% to 34.0% for the base model.
  * *Rounds matter.* For the fine-tuned model, Tests Passed is 43.49% at $K=1$, 54.13% at $K=3$, and 56.25% at $K=5$. One round of Program-Agent is about equal to the single-session baseline (42.84%), so the gain comes from review and revision, not from role separation alone (reader observation). The paper also reports that all three budgets use fewer output tokens than the base model's Claude Code run.
  * *Whole programs remain unsolved.* Resolved is 0.00-0.50% in every row.
* **Weaker or narrower than the headline.**
  * *Fine-tuning improves partial credit and reduces near-complete solutions.* Under Claude Code, Almost Resolved falls from 3.50% to 1.50% and Resolved from 0.50% to 0.00% after SFT, and the share of tasks passing at least 75% of tests falls from 18.0% to 9.5%. The paper acknowledges that SFT "cannot reliably boost the high-fidelity cases". The training set is 1,492 easy tasks out of 1,648 and is filtered on pass rate, so it may teach getting common behavior right more than finishing (reader inference).
  * *Under the stronger scaffold the training gain almost disappears.* With Program-Agent, SFT adds 0.54 points of Tests Passed (55.71% to 56.25%) and Almost Resolved goes from 5.50% to 4.50%.
  * *The SFT result is also a distillation result.* Trajectories come from DeepSeek-V4-Flash-0731, which scores 57.68% with Claude Code, well above the student. No control trains on unfiltered trajectories, or on the same teacher in environments without validated tests, so the claim that the verified tests are what make the supervision useful is not isolated (reader observation). The pass-rate threshold used for filtering was not found in the sections read.
  * *Program-Agent helps the weak model, barely the strong one.* DeepSeek-V4-Flash-0731 goes from 57.68% to 58.97% (+1.29).
  * *"Exceeding flagship models" mixes scaffolds and dates.* Claude Opus 4.7 (50.90%) and Gemini 3.5 Flash (53.60%) are release-time ProgramBench numbers under mini-SWE-agent, while this paper's runs use Claude Code with context compression or a five-round workflow; the paper's own footnote says later flagship results are on the ProgramBench site. Opus 4.7 at xhigh effort (55.10%) is within 1.2 points of both Program-Agent runs.
  * *No ablation of Program-Agent's parts, and single runs.* Role isolation, the implementer's lack of reference access, and build-gated rollback are not removed one at a time; no variance is reported.
  * *Test quality is checked structurally.* The four checks remove tests that fail on the reference, flake, accept a dummy, or assert weakly; there is no measurement of how often a suite passes a wrong but plausible reproduction, and coverage has a long lower tail the paper attributes to code unreachable through the black-box interface.

# Q9 Contributions

* A feedback-driven pipeline that converts repositories into program-reproduction environments, with a four-check test validator and coverage-guided test writing, and 1,648 environments built with it.
* A staged agent workflow with session isolation, frozen hand-off documents, and an independent build gate with rollback.
* Evidence that both help on ProgramBench, and that the workflow accounts for most of the improvement.
* Descriptive findings: successful reproductions are usually smaller than the reference (median line-count ratio 0.64 among solutions passing at least 75% of tests, 182 runs over 93 tasks), most so for C/C++ references (0.39) and least for Rust (0.72).

# Q10 Next Steps

* **From the authors.** Extend the pipeline to the medium and hard repositories as models improve, and to the rest of the 30,459 candidates; release ProgramGym.
* **Isolate the supervision (reader suggestion).** Train on the same teacher's trajectories without pass-rate filtering, and with a random subset of tests, to measure what the validated suites add beyond distillation.
* **Target completion (reader suggestion).** Since SFT lowers Almost Resolved, try filtering or weighting by near-complete outcomes, or collecting trajectories under Program-Agent rather than single-session Claude Code so the training data contains review-and-fix behavior.
* **Ablate the workflow (reader suggestion).** Remove reference access restrictions, the build gate, or session isolation one at a time at fixed $K$.
* **Project fit (reader note).** Program-Agent's rules map closely onto this repository's dispatch pattern: a frozen analysis document, an implementer that cannot see the oracle, a reviewer with read-only access, and rollback to the last state that verified. The measured result that one round equals a single session, and that the gain arrives with review rounds, is a reason to budget review iterations rather than longer single runs.
