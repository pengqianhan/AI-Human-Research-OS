# Q1 Problem Definition

* **Input (X):** developer-chosen capability requirements for AI coworkers (multi-turn communication, information gathering across services, tool coordination, and deciding when not to act), turned into a coverage plan of service combinations, difficulty, and scenarios, plus service catalogs and example tasks.
* **Output (Y):** executable task environments T_i = (u_i, s_i⁰, A_i, G_i): a user request, initial service records, tool interfaces, and grading checks; from these, curated teacher demonstrations for SFT and task references for online RL; and compact student models (PocketWorker) trained on them.
* **Constraints:** records about the same entity must agree across services; the information needed to answer must be discoverable through tools but not leaked in the request; graders must reward the intended actions and outcomes and zero the safety score when a prohibited action is called; training tasks are built independently of the benchmark test sets.

# Q2 Problem Novelty

Executable task synthesis for agents is an active line: AgentGen and MATRIX construct environments or scenarios, APIGen-MT links task blueprints to multi-turn interactions, CUA-Gym jointly builds instructions, environments, and rewards for computer use, CuES explores existing tool environments, and DreamGym, Qwen-AgentWorld, PatchWorld, and AgentEvolver simulate or adapt environments. Nemotron-Terminal, SERA, and OpenThoughts-Agent expose data choices for terminal and coding agents, and Occamy extends execution-grounded training to coworker workloads; Cowork-Gym is concurrent. The paper's own framing is practical rather than a new problem: how to turn targeted coworker capabilities into executable tasks that support both imitation and RL. Its distinguishing elements are cross-service consistency of records, tools, and checks from one specification, a grading-consistency gate on every generated grader, and a separate grader-writing role for safety scenarios.

# Q3 Scientific Hypothesis

If target coworker capabilities are turned into multi-service task specifications whose records, tools, and grading checks come from one specification and are validated programmatically before use, then teacher executions on those tasks give useful SFT supervision and the tasks give a usable RL signal. A compact model trained on them should improve substantially on independent coworker benchmarks, most on the capabilities the tasks target (multi-turn interaction), with gains growing with the amount of data, and RL training rewards should rise on the constructed tasks.

# Q5 Key Solution Idea

**From capability to specification.** A coverage plan slot names the task, services (for example CRM, helpdesk, and mail), category, difficulty, language, a fixed reference date, and a scenario with selection conditions, distractors, and action constraints. An LLM turns the slot, the service catalogs, and example tasks into a request, initial records, structured completion checks, and prohibited actions. Programs then instantiate it: service configurations come from a registry, and checks and prohibited tools are inserted into a fixed grader template, so variation changes data rather than code. A check can test tool-call presence, specific arguments, or a service audit record (a helpdesk update recorded under `updated_tickets`, an outgoing message under `sent`).

**Linking evidence across services.** An escalation task, for example, must combine ticket creation times with customer tiers to find enterprise tickets open more than 48 hours, then fetch the account manager's address from the CRM; a recent high-priority ticket is a distractor that fails the age condition. Safety scenarios use a Generator-Discriminator split: the Generator drafts the request and records, and the Discriminator, given the records and a safety note but not the full request, writes the completion checks and forbidden actions. In a payment-change example the agent is rewarded for reading the suspicious and the legitimate messages and the transaction history, and calling the report-submission or send-mail tool zeroes the safety factor; the score is safety × (0.8 completion + 0.2 robustness).

**Validation and repair.** Each candidate must parse, use registered services with initial records, have completion weights summing to one, avoid conflicts between required and prohibited tools, and not reveal designated answer identifiers in the request. A grading-consistency gate then runs the generated grader on synthetic records: the full set of required calls must score 1 for completion and safety, an empty record 0 for completion, and adding a prohibited call 0 for safety. A failure returns diagnostic feedback for one regeneration; a candidate that fails twice is dropped.

**Teacher execution and curation.** A teacher runs each task through a Claude Code adapter in Harbor, with repeated attempts per task (three attempts by claude-opus-4-8 in both documented examples). Tasks are labeled by mean teacher completion: TRIVIAL (≥ 0.999), UNSOLVABLE (≤ 0.001, set aside), or KEEP. TRIVIAL tasks contribute one demonstration per task-name prefix; KEEP tasks can contribute several. Reward thresholds then filter exports (0.5 for the mixed pool, 0.8 for multi-service and safety, 0.3 for ClawMark), and conversion drops records with no usable exchange, fewer than five messages, more than 20 tool calls, or more than 40,000 characters, truncating each tool observation to 1,000 characters. Replaying the converter on a 1,809-record snapshot keeps 937 demonstrations.

**Training.** SFT uses LoRA (rank 32) on Qwen3-VL-8B-Instruct with loss on assistant responses and tool calls. For RL the student interacts with the same services and graders online; incomplete or infrastructure-failed rollout groups are rejected and retried.

# Q6 Experiment Design

* **Models.** PocketWorker-8B (Claw-Eval SFT) and a separate mixed-data PocketWorker-8B (ClawMark SFT), both from Qwen3-VL-8B-Instruct; PocketWorker-4B, a dialogue-only SFT of Qwen3-VL-4B-Instruct selected after two epochs.
* **Benchmarks.** Claw-Eval's 161 General and 38 Multi-turn tasks (199), three trials per task, reporting mean score, Pass@3 (at least one trial scores ≥ 0.75), and Pass^3 (all three do); the 101 Multimodal tasks are added only in the RL table. ClawMark's 100 tasks across 13 professional domains, one run.
* **References.** 14 published Claw-Eval rows copied from the Claw-Eval paper (v3) and seven ClawMark website rows (OpenClaw harness, Run 1); the paper states that matching task counts do not establish aligned settings.
* **RL comparison.** GRPO, Dr.GRPO, GDPO, and GiGPO (step-advantage weight 1.0), each from one shared supervised warm-up checkpoint, about three epochs on the constructed tasks; the GRPO baseline uses groups of eight rollouts.
* **Data-scale ablation.** SFT with 20%, 50%, and 100% of the data, sampled within each SFT stage.

# Q7 Datasets and Code

The paper says the datasets and construction pipeline will be released and links code, models, and a lessons page; the repository is [HKUST-KnowComp/CoworkEnv](https://github.com/HKUST-KnowComp/CoworkEnv) (3 stars per `hf papers info`), not opened for this note. The construction libraries hold 602 task identifiers for the Claw-Eval branch and 263 for the ClawMark branch, 236 of them shared; these are library snapshots, not training-set sizes. Regenerating the teacher trajectories needs access to a proprietary model, as the Limitations section notes.

# Q8 Evidence Quality

* **Supported.**
  * *Large SFT gain on Claw-Eval, mostly multi-turn.* Overall 46.6 to 64.1 (+17.5), General 46.7 to 60.9, Multi-turn 45.9 to 77.8 (+31.9), under the same evaluation configuration for base and SFT; Pass@3 / Pass^3 rise from 28.6 / 21.6 to 50.8 / 37.2.
  * *More data helps.* With 20%, 50%, and 100% of the SFT data the Overall score is 50.8, 55.6, and 64.1.
  * *A second benchmark.* On ClawMark the mixed-data SFT model goes from 11.8 to 19.4.
  * *RL runs train.* From the shared warm-up, Overall reaches 56.6 (GRPO), 57.2 (GDPO), 54.3 (Dr.GRPO), and 60.7 (GiGPO), and training rewards rise over about three epochs for all four.
* **Weaker or narrower than the headline.**
  * *RL's own contribution is not isolated.* The supervised warm-up checkpoint's score is not reported, so the RL table compares warm-up plus RL against the untrained base, not against the warm-up. Every warm-up-plus-RL run scores below the full-data SFT model on Overall (54.3-60.7 against 64.1), whose relation to the warm-up checkpoint the paper does not state (reader observation from Tables 1 and 3).
  * *The RL methods differ in more than the estimator.* GDPO also changes batch size, Dr.GRPO changes loss normalization, and GiGPO has no ω = 0 control, as Appendix B says; each method is one run.
  * *Graders check selected actions, not intent.* The paper notes that its ticket-update check identifies the right ticket but not the resolution text, and that avoiding a forbidden call does not show the agent recognized fraud or refused. The grading-consistency gate tests a grader against its own declared checks, so it catches inconsistent graders, not checks that miss the request's meaning (reader observation).
  * *Benchmark-oriented construction.* The construction libraries are organized per target benchmark, and independence is shown by task-identifier absence (the M1100-M1124 family is not in Claw-Eval's 300 tasks), not by content overlap analysis (reader observation).
  * *Small absolute scores on ClawMark.* 19.4 against reference models at 28.4-56.7, from one run, with the base and fine-tuned models outside the website's protocol comparison.
  * *Different checkpoints per benchmark.* The Claw-Eval and ClawMark results come from two different SFT models, and the 4B gain comes from dialogue-only data, so no single model is shown to improve on both benchmarks.
  * *Compact versus frontier.* PocketWorker-8B's Multi-turn 77.8 is inside the range of the 14 published reference rows (56.2-81.9), but the paper itself declines to claim it beats any reference model because settings differ.

# Q9 Contributions

* A capability-guided pipeline that produces executable multi-service coworker environments from one specification (request, records, tools, grader), including safety scenarios where the grader is written by a separate role.
* Programmatic validation with a grading-consistency gate and feedback-driven regeneration, so every accepted grader scores a complete, an empty, and a forbidden-call record as intended.
* A documented curation path from teacher executions to SFT data (difficulty labels by mean teacher completion, reward thresholds, structural filters), with counts of what each filter removes.
* Evidence that SFT on the resulting data lifts a compact VLM sharply on Claw-Eval, especially on multi-turn tasks, and a first comparison of four group-based RL estimators on the same constructed tasks.

# Q10 Next Steps

* **Report the warm-up (reader suggestion).** Scoring the shared warm-up checkpoint, and running RL from the full-data SFT model, would show whether RL on these environments adds anything beyond SFT.
* **Use failed and recovery trajectories (from the paper).** The Limitations note that teacher-success filters can discard useful recovery behavior and cite skill-evolution work where failures help; training on graded failures or partial recoveries is untested here.
* **Stronger graders (reader suggestion).** Adding checks on response content (did the agent refuse, did it explain the conflicting evidence) or a judge for open fields would make the safety scenarios test recognition rather than only avoidance of a tool.
* **Compare synthesis pipelines on one benchmark (reader suggestion).** [GraphForge](2609.38923.md) also synthesizes workspaces for working agents and cites Claw-Eval, and [MAI-Gym](2610.20939.md) checks generated verifiers against initial, golden, and reset states; training the same student with each pipeline's data and scoring on Claw-Eval would show which construction choices matter.
* **Close the harness gap (from the paper's lessons).** Teacher data comes from Claude Code in Harbor while benchmarks run under their own harnesses (OpenClaw for ClawMark); the paper flags training-inference mismatch across harnesses as an open issue.
