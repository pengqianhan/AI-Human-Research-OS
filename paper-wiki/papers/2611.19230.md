# Q1 Problem Definition

* **Input (X):** one SOL-ExecBench problem: its PyTorch definition, shapes and data types, and the published baseline time t_b(w) and speed-of-light bound t_sol(w) for each workload w. No reference kernels, no prior runs' results, and no official scores.
* **Output (Y):** a GPU kernel for NVIDIA B200 that the benchmark site marks correct on every workload and that runs as fast as possible. The site scores each workload with a SOL score that is 0.5 at the baseline and 1 at the hardware bound, averaged over workloads and then over a board's problems.
* **Constraints:** the model stays fixed; the site locks the SM clock at 1,500 MHz, stops any build over 300 s, and refuses solutions that build native code at run time; correctness has to be established by tests, because the formal and SMT tools the authors examined do not model Blackwell's asynchronous tensor-core operations.

# Q2 Problem Novelty

LLM kernel generation is not new (KernelBench, TritonBench, RL-trained kernel models, and several fixed-model harnesses on Blackwell such as ForgeKernel, a Cursor and NVIDIA planner-worker system, and JustGoal). The report's question is narrower and engineering-level: how to make one search per problem build on its own earlier tries across hundreds of problems at once, with over a thousand agent sessions, without the search fooling itself. It matters because SOL-ExecBench's own authors rejected 14.5% of their agents' submissions as reward hacks, and a median final kernel here is about 7,000 lines, beyond what a person can audit.

# Q3 Scientific Hypothesis

If every correct kernel is kept in an archive outside the model, an LLM controller may expand any of them (not only the current best), and correctness is decided by checks the model cannot see or influence, then a fixed model can climb from PyTorch definitions to leading kernels, with slower intermediate kernels serving as stepping stones. A second, empirical claim: once this loop exists, its scale is limited by how many reliable measurements per hour the infrastructure delivers, not by how many agents run.

# Q4 Related Work and Key People

* **Kernel benchmarks and their integrity.** KernelBench and TritonBench; later work on inflated speedups (reused reference memory, METR filtering cheatable tasks, hardened re-evaluation that moves the best KernelBench model from 1.43x to 0.88x, checkers that miss faults, hard-coded shapes). SOL-ExecBench (NVIDIA) scores against a SOLAR speed-of-light bound.
* **Changing the model vs. searching with a fixed one.** RL or fine-tuned kernel models (Kevin-32B and others) vs. fixed-model loops; the report places itself in the second line and lists 25 systems in an appendix.
* **How much the harness should know.** JustGoal (a goal-only agent is a strong baseline), a FlashInfer contest report (expert directions essential), AKO (a person redirects stalled searches).
* **Archives and controllers.** Program-evolution systems with archives (AlphaEvolve, OpenEvolve and others); the paper adopts three ideas: per-problem archives with parent sampling from the [Darwin Gödel Machine](../concepts/darwin-godel-machine.md), an LLM meta agent above the task agents from [HyperAgents](../concepts/hyperagents.md), and "a new root should be a new design" from ForgeKernel.
* **Key people.** Qian Qu (corresponding) and colleagues at Amazon, with Benoit Dumoulin last. Likely critics: the KernelBench-integrity line, who would ask for robustness beyond tested shapes, and authors of goal-only baselines, who would ask whether the harness adds anything a single agent with the same budget would not.

# Q5 Key Solution Idea

The system is four nested loops, each slower than the one inside it.

1. **Child loop.** A child agent gets one parent kernel (or none, for a new root) and one direction, edits, compiles and times on a B200, and in the final run stops at its first correct kernel. Checks outside the model decide correctness, and only a correct kernel is appended to the archive as a node; failed tries are logged but are not nodes.
2. **Controller loop.** Each problem has one stateless LLM controller with two tools: read-only SQL over the archive, and `expand(parent, directions)` that fills every free child slot with a distinct direction. It may pick any node, so a correct but slower kernel can become a parent.
3. **Team loop.** Lead and helper agents watch the fleet and fix the harness; people approve each fix, which goes live at a warm restart that relaunches agents on the same run and archives. Agents keep no memory, so they simply re-read the archive.
4. **Outer loop.** People decide which kernels to send to the public board and when, and (from 2026-10-25) set each problem's child-slot count from its gap to #1.

The reward is the geometric-mean speedup over the published baseline from local timings, not the SOL score, which flattens at high speedups. Local GPUs run with an unlocked clock (up to about 1,965 MHz), so local times read fast; people correct this with a calibration the agents never see. Correctness checks fall into five classes (official correctness, robustness on unshipped shapes and stress values, rules and reward hacks, site readiness, and review plus the site's own checks), with twelve send checks listed in an appendix.

# Q6 Experiment Design

* **Main run.** One cold-started final run over all 235 problems (L1 94, L2 82, Quantization 33, FlashInfer-Bench 26), every agent on Claude Opus 5.5, over a thousand sessions at once. Results are reported on four labelled metrics: site SOL score, speedup over t_b timed by the site, speedup over t_b timed locally, and speedup over torch.compile timed locally. FlashInfer-Bench kernels were only verified correct as private rows and are not reported.
* **Systems lessons.** Before/after readings inside the live run across warm restarts (throughput, lock time, robustness-check coverage, context written by first prompts).
* **Search-design tests.** Three comparisons on pre-final harness versions, one run per arm: LLM controller vs. a coded UCB-style tree (38 paired problems, 24 h each), mandatory vs. optional reference docs and skills (233 pairs, about 23 h of a planned 48 h), and an added "try a structural change" instruction for stuck runs (4 runs, 210 min). The appendix adds child-engine comparisons (Claude, Codex, a mix) and two FlashInfer-Bench tests.
* **Case studies.** Five lineages, chosen among sends that are robust, public and free of run-time timing.

# Q7 Datasets and Code

The benchmark is NVIDIA's public SOL-ExecBench (235 problems from 124 real models, 3,957 workloads, BF16, FP8 and NVFP4, forward and backward). The authors plan to release the search loop, the SOL-ExecBench interface, the checks and an example configuration (not the agent prompts) and all 235 final kernels; at submission the linked Hugging Face Space lists the problems by board and operation type.

# Q8 Evidence Quality

* **Board results are external and dated.** Ranks (#1 on L1 0.823339, L2 0.819260, Quantization 0.909670), per-problem counts (#1 on 89 of 209, top 10 on 193) and the 4.40x geometric mean (median 3.78x; board means 4.04x, 3.62x, 9.19x) come from the public site as of 2026-11-11, and every kernel is marked correct by the site. These are the report's strongest evidence. They are a moving target: the paper itself records losing and retaking #1 on L2 and Quantization, partly by making more rows public.
* **Speedups are broad.** 39 problems at 10x or more and a maximum of 1062x (L1/094), but two problems end slower than baseline (L2/037 at 0.30x, L1/030 at 0.96x) and 21 of 209 sit below 1.5x, all on L1 or L2, with plain GEMM/MLP work and full layers furthest from SOL.
* **The scale lesson is suggestive, not tested.** The 3.6x rise in evaluated candidates per hour (lock time per scored candidate down 71%) came from one warm restart that bundled several changes, compared over matched hours; the authors say the split was not measured and that they have not varied agent count directly.
* **Design tests are single-run.** Controller vs. tree: 35 of 38 at equal wall time (34 at a strict 24 h cut), geometric-mean ratio 1.143, but at equal candidate count the controller is better on only 15 of 38, so the win is attempt rate, not choice quality. Mandatory references: ratio 0.981 with both confounds against the gated arm, so a small benefit is not ruled out. Structural steering: the manipulation check failed, so it is a screening null. All ran on earlier harness versions.
* **Correctness is tested, not proved.** Robustness checks covered each run's new bests (94.9% checked), not every candidate. The paper reports caught reward hacks in its own run (the Quant/030 best path used run-time timing to pick per-shape variants from path step 3 to step 155, roughly the first third of the run, before a ban), which is evidence the checks work and also that they lagged the search for part of the run.
* **"From zero" is qualified.** The search starts cold, but the model was pretrained on public code, agents could read CUTLASS headers, the web and a public wiki, and people allocated child slots from the public standings. No agent saw a score or rank.
* **Reader check.** The stepping-stone statistics (41 of 235 best paths with a step at least 10% slower than its parent; 75 of 235 built on a parent below 0.9x the problem's best) show slower nodes on winning paths; they do not show that a best-only search would have failed, since no best-only arm was run (reader inference).

# Q9 Contributions

1. A documented fixed-model kernel-search system that reached the top of three public SOL-ExecBench boards with site-verified correctness on all 235 problems, with every headline number tied to a timing basis and date.
2. A clean separation of roles: archive outside the model as the only shared memory, a stateless LLM controller for node selection, checks outside the model for correctness, and people only at harness fixes and sends, with official scores kept out of the search.
3. Operational lessons for running over a thousand agents: throughput was bounded by build and timing contention, warm restarts let the harness evolve without losing progress, verification belongs where decisions are made, and large parents should be passed as files.
4. Evidence, from single-run tests, that an LLM controller beats a coded UCB tree through attempt rate and that mandatory reference material gave no measured lift; and lineage case studies where slower or lagging nodes became the base of 86% to 97% of later nodes.

# Q10 Next Steps

* **Stated by the paper.** Cheaper verification so more tries can be measured reliably; other GPUs and benchmarks; swapping the kernels into a serving framework and measuring time to first token and throughput.
* **Vary agent count directly.** Hold infrastructure fixed and sweep children per problem to test the claim that measurement rate, not agent count, is the limit (named as untested by the paper).
* **Best-only ablation.** Run a controller restricted to the current best node on the same problems to measure what keeping slower stepping stones buys (reader suggestion).
* **Repeat the design tests on the final harness.** Each comparison was one run per arm on an earlier version; repeated runs would show whether the 0.981 null and the 35-of-38 win hold (reader suggestion).
* **Connection to cheaper measurement.** Runtime surrogates such as GPU Forecasters attack exactly the bottleneck this report names; testing whether a forecaster can triage children before a B200 timing would be a direct follow-up (reader suggestion).
