# Q1 Problem Definition

* **Input (X):** at each execution turn, a multimodal observation `o_t = (I_t^rgb, I_t^d, q_t)` — an agent-view RGB image, a co-aligned metric depth map, and a robot proprioceptive state (end-effector pose plus gripper state) — together with a fixed natural-language task description `ℓ` and, during few-shot deployment, a retrieved Task Specific Memory record (a parameterized JSONL primitive trace plus a semantic "strategy"/"avoid" summary from a single prior bootstrapping run on the same task) and a persistent, benchmark-wide Global Memory of success rules and named failure models. A binary completion predicate `G` exists only as a sparse signal at episode termination and is never exposed to the planner as intermediate reward.
* **Output (Y):** a turn-by-turn sequence of structured JSON invocations of one primitive `c_t` drawn from a fixed library `P` — six analytic primitives (`move_to`, `move_pose`, `rotate_wrist`, `rotate_pitch`, `set_gripper`, `release`), one VLA-backed primitive (`vla_act`), and, for RoboCasa365 only, two mobile-base primitives (`navigate_to`, `move_base`) — executed in a physics simulator (MuJoCo via Robosuite) until `G` is satisfied or a step budget is exhausted. The planner never emits low-level torques, joint targets, or action chunks directly.
* **Core problem:** end-to-end frozen VLAs supply strong local contact-rich control but were trained on in-distribution trajectories, so they silently repeat training-time behavior once a deployment perturbation (semantic retargeting, goal re-binding, spatial-layout shift, or an unstable local contact) has invalidated their implicit binding of instruction to scene; LLM coding agents supply complementary semantic and compositional reasoning but their deterministic analytic primitives cannot themselves perform irregular grasping, constrained placement, or articulated-object interaction. The paper asks how to compose the two so the VLA is used only where it is reliable, without finetuning its weights and without growing the primitive vocabulary at deployment time.
* **Scope:** simulated manipulation only — LIBERO/LIBERO-Pro tabletop, RoboCasa365 household kitchen (including mobile staging), and RoboTwin bimanual clean-to-randomized transfer, all built on existing public benchmarks and pre-existing or paper-internal-but-frozen VLA checkpoints (RLinf's `π0.5`-SFT for LIBERO/LIBERO-Pro, RLDX-1 for RoboCasa365, an internally post-trained LingBot-VLA for RoboTwin C2R). Task-level bootstrapping uses exactly one reference seed per task. Two LLM planner backbones are tested (OpenAI Codex, Claude Code) as interchangeable orchestrators rather than as a studied design axis. No real-robot deployment is reported in the retrieved text.

# Q2 Problem Novelty

The paper does not claim to originate VLA-plus-coding-agent hybrids, LLM task planning over robot APIs, or persistent agent memory individually — its own Related Work traces each lineage (RT-1/RT-2/OpenVLA/`π0`/`π0.5`/GR00T/Gemini Robotics for VLAs; Code-as-Policies, ProgPrompt, Instruct2Act, RoboCodeX, ViperGPT, VoxPoser, RoboClaw, Maestro for coding-agent control; SWE-agent, OpenHands, Reflexion/Self-Refine, Statler for the general agent-harness/self-correction tradition; SayCan, Inner Monologue, SayPlan, RoCo for LLM task planners). Its stated novelty is narrower and specific: (1) keeping the primitive vocabulary **fixed and small** rather than letting the agent grow a skill library, contrasted explicitly against ASPIRE, which uses execution traces to diagnose failures and admit new validated skills into a continually expanding library — Harness VLA "deliberately keeps the primitive vocabulary fixed and studies how memory-guided composition can extend a frozen VLA without deployment-time primitive expansion"; and (2) exposing the frozen VLA itself as a single retryable primitive (`vla_act`) inside that fixed vocabulary, rather than as either a monolithic end-to-end controller or a component the agent could edit. The paper also flags a specific prior gap it fills: Voyager showed persistent memory helps an embodied agent in a digital sandbox, but "this memory-centric design has not been combined with a VLA-backed contact-rich primitive for physical manipulation" — Task Specific Memory (per-task reusable traces) and Global Memory (cross-task success rules/failure models) are the paper's answer to that combination.

# Q3 Scientific Hypothesis

If a frozen VLA is exposed only as a retryable, planner-staged contact-rich primitive — while all non-contact structure (target grounding, free-space transport, posture adjustment, mobile staging, re-staging after a failed attempt, and release) is handled by explicit, fixed analytic primitives under LLM planner control — then the composed system should extend the VLA's effective operating range far beyond its training distribution without any weight update, yielding large gains specifically under deployment perturbations (instruction redirection, position swaps, clean-to-randomized transfer) relative to both the raw frozen VLA and prior LLM-coding-agent baselines, while roughly preserving performance on the VLA's original in-distribution setting. The paper's own framing treats "operating range" as an empirical, measured property (Section 3.3's invocation-cap curves and primitive-usage statistics), not merely an assumption.

# Q4 Related Work and Key People

* **End-to-end VLA models.** The generalist-policy line (RT-1, Octo, RT-2, Open X-Embodiment) through OpenVLA, flow-matching `π0`/`π0.5`, and recent scaled systems (GR00T, Gemini Robotics) is cited as strongest at contact-rich visuomotor phases but degrading sharply on instruction following, long-horizon composition, and out-of-distribution scenes — the asymmetry the paper's factorization is built to exploit.
* **LLM-driven multimodal agents.** Frontier VLMs (GPT-5.2, Gemini 3, Qwen3-VL, the Claude 4 family, Llama 4) are cited as having closed the gap on dense perception and spatial reasoning within roughly a year, motivating delegating semantic grounding and deterministic manipulation phases to a frontier model at the top of the agent stack rather than driving the robot end-to-end with a VLM.
* **Coding agents for robot manipulation.** Code-as-Policies, ProgPrompt, Instruct2Act, ChatGPT-for-Robotics, RoboCodeX, ViperGPT, VisProg, VoxPoser, RoboClaw, and Maestro recast control as program synthesis over perception/motion APIs. ASPIRE is the paper's most direct point of contrast (skill-library-growing diagnosis-synthesis-admission, described as "complementary" rather than superseded). SWE-agent, OpenHands, and the executable-code-actions line supply the harness/REPL pattern this paper's Appendix A implements; Reflexion, Self-Refine, and Self-Debug supply the self-correction framing behind planner-staged VLA retry; Statler supplies persistent symbolic state across steps; Voyager supplies the persistent-memory precedent noted in Q2.
* **Key people and affiliations.** Corresponding author Chao Yu (zoeyuchao@gmail.com), Tsinghua University; co-authors span Tsinghua University, Striding AI, Purdue University, the Institute of Automation at the Chinese Academy of Sciences, Infinigence AI, Zhongguancun Academy, and Hong Kong University of Science and Technology — an academia-industry consortium. The `vla_act` backends are drawn from three separate efforts (RLinf, an RL framework/checkpoint source; RLDX-1; LingBot-VLA, the authors' own RoboTwin-post-trained checkpoint), so the paper's own ecosystem already spans several VLA-provider groups. A reader from the ASPIRE lineage (skill-library expansion) would likely press on whether a permanently fixed primitive vocabulary can cover genuinely novel task families; a reader from the scaled end-to-end VLA lineage (`π0.5`, GR00T) might question whether the hand-specified JSON primitive interface and simulator-only evaluation generalize to unstructured real-world deployment — both are this note's inferences, not claims the paper itself makes about its critics.

# Q5 Key Solution Idea

1. **A fixed primitive library as the only action interface.** The planner never emits raw actions; it selects one primitive per turn and binds arguments from language, RGB-D, proprioception, and memory. Analytic primitives split into *composite* (an embedded solver coordinates multiple DOF toward a world-frame goal, e.g. `move_to`) and *atomic* (drive one channel to a set-point, e.g. `set_gripper`). `vla_act` is structurally distinct: the planner supplies a task-conditioned prompt and an early-return predicate `τ`, and the frozen VLA emits action chunks until `τ` is satisfied or a chunk budget is exhausted.
2. **A synchronous, file-mediated REPL harness (Appendix A).** A long-running environment worker owns live simulator state; the planner writes one JSON command to `command.json`, the worker executes it and writes the next indexed observation and diagnostic record, and the planner waits before acting again. The planner never accesses privileged simulator state or object poses directly — only rendered RGB-D and proprioception.
3. **Two-phase lifecycle.** In *Exploratory Bootstrapping* (one reference seed `s0` per task, `reset` primitive available, generous wall-clock budget), the planner trials staging orders, pre-contact poses, `vla_act` invocation timing, and early-return thresholds, correcting course on failure. In *Deployment Evaluation* (`reset` disabled, step budget shortened, held-out seeds only), the planner retrieves the stored trace and re-grounds it dynamically from the live observation rather than replaying stored coordinates.
4. **Task Specific Memory.** A parameterized JSONL trace (primitive calls with spatial arguments treated as reference-scene bindings, re-grounded at deployment) plus a semantic JSON summary recording *why* the strategy worked and what to avoid (e.g. "do not reuse reference xyz values; verify placement with the benchmark success signal"). It is a task-level solution skeleton, not an open-loop trajectory, and is refined rather than purely accumulated: a later bootstrapping attempt can replace the stored trace if it is shorter or more reliable.
5. **Global Memory.** Task-independent operating knowledge shared across a benchmark: success rules (e.g. use the full task instruction when prompting `vla_act`; prefer analytic motion for long transport once a stable grasp is held) and named failure models (an *empty grasp* — gripper closes but the object does not move with the end-effector — and a *false success* — do not terminate from visual proximity alone; check the benchmark signal and the latest execution record).
6. **Planner-staged VLA retry (Key Finding 2).** Each `vla_act` call is a planner-chosen local attempt, not a one-shot black box: the planner stages a feasible pre-contact configuration, invokes the VLA, inspects whether the contact post-condition holds, and on failure re-stages the approach pose or viewpoint before retrying — localizing a transient contact failure to the current subtask instead of letting it derail the whole rollout.

# Q6 Experiment Design

**Few-shot, with Task Specific Memory (Section 3.2).**
* *Standard LIBERO* (400 rollouts: 4 suites × 10 tasks × 10 held-out seeds, `s0` reserved for bootstrapping): Harness VLA (Claude Code) reaches 96.0% (384/400, 100.0% on Object, 93.0% on LIBERO-10) versus the frozen RLinf `π0.5`-SFT checkpoint's own 95.3% — near-parity on the VLA's in-distribution setting.
* *LIBERO-Pro* (800 rollouts: 4 task families × T/instruction-redirection and S/position-swap × 10 tasks × 10 seeds): RATS is reported as the strongest prior baseline at 43.8% overall (on its reported cells only). Harness VLA reaches 72.1% with Codex and 82.4% with Claude Code — an 82.4 − 43.8 = **38.6 percentage-point** gain, matching the abstract's headline number. The direct RLinf baseline under the paper's own protocol reaches 50.0% — higher than RATS but far below Harness VLA, which the paper offers as evidence the gain is not simply the frozen-VLA backbone.
* *RoboCasa365* (target50 split, 340 rollouts: Atomic-Seen 18×10, Composite-Seen 16×5, Composite-Unseen 16×5): the direct RLDX-1 baseline — the same checkpoint used inside `vla_act` for this benchmark, evaluated under the paper's protocol — reaches a task-weighted 30.0% overall (60.0% Atomic-Seen, 21.3% Composite-Seen, 5.0% Composite-Unseen). Harness VLA reaches 55.4% with Codex (55.4 − 30.0 = **25.4 percentage points**, matching the abstract) and 48.6% with Claude Code. Other prior-paper baseline rows exist in Table 4 but their specific values were not retrievable from the fetched text (see Q8).

**Zero-shot, without target-setting Task Specific Memory (Section 3.2).**
* *LIBERO-Pro Goal*, memory withheld: Harness VLA (Claude Code) reaches 79.0% on instruction-redirection and 31.0% on position-swap, versus Cap-X's 16.8% and 25.6% — evidence that planner reasoning over the fixed primitive interface transfers even without a per-task retrieved trace, though the much lower position-swap number versus the few-shot aggregate suggests Task Specific Memory contributes disproportionately for spatial (versus semantic) perturbations.
* *RoboTwin C2R* (250 rollouts: 50 tasks × 5 randomized seeds; trace obtained only from one expert-verified `demo_clean` seed, no randomized-setting bootstrapping or finetuning): direct LingBot-VLA reaches 50.4%; Harness VLA raises the same frozen backend to 58.0% (Codex) and 58.4% (Claude Code) — the abstract's headline RoboTwin number, an 8.0-point lift over the un-composed VLA.

**Mechanism analyses (Section 3.3).** Figure 4 caps the number of `vla_act` invocations allowed per episode across all three perturbed benchmarks: success rises quickly after the first few calls and saturates toward the full-harness result, read as evidence that invocation is sparse but repeated staging/retry matters. Figure 6 attributes which primitive class triggers the final success predicate: LIBERO Pro-family tasks are usually finished by an analytic primitive after contact is established, while RoboCasa365 and RoboTwin C2R finish inside `vla_act` more often because their completion predicates depend directly on a contact-rich operation. Appendix F's primitive-usage table (canonical-name aggregation across Harness VLA (Claude Code) runs) shows `vla_act`'s share of all primitive calls rising with contact density: 15.8% on LIBERO (`move_to` alone is 61.8%), 35.3% on RoboCasa365 (mobile-base primitives add 19.4%), and 47.4% on RoboTwin C2R — with analytic primitives still holding a slight majority even there.

# Q7 Datasets and Code

No new pretraining or evaluation dataset is released; all four benchmark families (LIBERO, LIBERO-Pro, RoboCasa365, RoboTwin) are pre-existing public benchmarks. Checkpoints differ in provenance and are frozen with different histories: RLinf's official `π0.5`-SFT checkpoint (trained on LIBERO-130, used as-is), the official RLDX-1 checkpoint (used as-is), and an internally **post-trained** LingBot-VLA checkpoint — pretrained on cross-embodiment teleoperation data, then SFT-adapted on RoboTwin trajectories by the authors before being frozen for both the direct-baseline and Harness VLA numbers. The paper's own "extends pretrained VLAs... without finetuning" claim refers to the harness itself performing no additional weight updates at deployment time, not to every backend VLA being untouched by any task-specific training — LingBot-VLA is the one exception, and this distinction is worth keeping separate when citing the paper's "frozen VLA" framing. A project page (harnessvla.github.io) and GitHub repository (github.com/RLinf/RPent, 691 stars at fetch time) are listed in HF's metadata; the retrieved arXiv text does not itself describe the repository's contents, and neither URL was independently browsed for this note (see Q8 for a caveat about the repo's host organization).

# Q9 Contributions

1. Harness VLA, a memory-augmented agentic framework that exposes a frozen VLA as a single retryable contact-rich primitive (`vla_act`) composed with a small, deployment-time-fixed library of analytic primitives for grounding, staging, transport, navigation, and release — extending a pretrained VLA beyond its original trajectory distribution without finetuning its weights or expanding the primitive vocabulary.
2. Empirical evidence that this composition substantially extends the frozen VLA's effective operating range under deployment perturbations specifically: +38.6 points over the strongest reported LIBERO-Pro baseline (RATS, 43.8% → 82.4%), +25.4 points over the RoboCasa365 frozen-VLA backend (RLDX-1, 30.0% → 55.4%), and +8.0 points on RoboTwin C2R zero-shot clean-to-randomized transfer (50.4% → 58.4%), while roughly preserving standard in-distribution LIBERO performance (95.3% → 96.0%).
3. A two-tier memory design — per-task parameterized JSONL traces with semantic strategy/avoid summaries (Task Specific Memory) built from a single bootstrapping episode, plus cross-task success rules and named failure models (Global Memory, e.g. empty-grasp and false-success detection) — validated under a strict deployment regime that disables environment reset and shortens the step budget, forcing genuine re-grounding rather than trace replay.
4. A mechanism-level account (Key Findings 1–3, backed by an invocation-cap ablation and primitive-usage statistics) attributing the gains to planner-level semantic re-grounding, planner-staged retry/re-staging of `vla_act`, and a division of labor where analytic primitives handle non-contact structure while `vla_act`'s call share tracks each domain's contact density (15.8% → 35.3% → 47.4% from LIBERO to RoboCasa365 to RoboTwin C2R).

# Q10 Next Steps

The paper's own stated limitations (Section 5): an open feedback loop between the high-level planner and the low-level VLA (no closed-loop joint adaptation); no joint finetuning via environmental reward or human preference, explicitly naming sample-efficient RL (e.g. GRPO) as future work; and the absence of fine-grained image captioning, which the authors say constrains structural reasoning in highly cluttered, long-horizon tasks. The authors also propose combining their fixed-vocabulary composition strategy with automatic skill-discovery systems such as ASPIRE, so that a repeatedly-observed missing abstraction could be proposed, validated, and admitted as a new reusable skill while retaining the auditable primitive interface and VLA-backed contact specialization studied here.

Beyond the paper's own framing: the single-reference-seed bootstrapping design (one exploration episode per task feeds the entire per-task memory) is a very small evidentiary basis for "learning the operating range" claims, and no ablation isolates how much of the reported gain depends on that one seed being representative. The RoboCasa365 headline comparison (Q8) measures Harness VLA's lift over its own frozen-VLA backend rather than over the strongest *published* RoboCasa365 method, which a reader should not conflate with the LIBERO-Pro comparison against RATS (an external competing method). Whether Harness VLA's fixed-vocabulary, two-phase-memory design would hold up on a real robot, where bootstrapping cannot rely on an unlimited-`reset` simulator and observation/diagnostic files are not free, is not addressed in the retrieved text and would be a natural next probe.

# Related

* [LIBERO-Pro](../concepts/libero-pro.md) - Harness VLA's primary perturbation-robustness benchmark: 82.4% (Claude Code) versus 43.8% for RATS (the strongest reported prior baseline) and 50.0% for the same frozen VLA backbone run directly under the paper's own protocol.
* [Agent harness engineering](../topics/agent-harness-engineering.md) - the topic's most structurally similar prior entry is [Zetta](../papers/2608.16590.md), and the comparison is genuinely informative: Zetta evolves runtime critics and recovery skills *online*, continuously, through three timescale-separated loops (action-frequency, rollout-level, validation-gated promotion) while its base VLA stays frozen across the whole evaluation run. Harness VLA's "learning" is structured differently — a one-time Exploratory Bootstrapping phase (single reference seed, `reset` enabled) produces a Task Specific Memory record that is then *frozen and merely re-grounded*, not further updated, during a strict Deployment Evaluation phase (`reset` disabled, shortened budget). So despite the shared "frozen VLA behind a harness" premise, Harness VLA is architecturally closer to a fixed planner-plus-primitives composition with a static per-task memory snapshot than to Zetta's continuously self-evolving harness; the one within-episode adaptive mechanism it does have — planner-staged `vla_act` retry and re-staging on a failed contact (Key Finding 2) — is turn-level reactive re-invocation inside the fixed vocabulary, not a mechanism that writes new validated critics into a persistent, growing harness. Against [Recuris](../papers/2608.24876.md), the fit is partial: Recuris's structured execution trace generalizes across many tasks to *localize which of four typed memory components* is at fault, with a measured accuracy gain (64.8% vs. 13.0% from outcome alone) the paper itself validates. Harness VLA's Task Specific Memory (a JSONL trace plus "strategy"/"avoid" annotations) and Global Memory's named failure models (empty-grasp, false-success) apply the same qualitative principle — structured evidence beats a bare pass/fail signal — but at a narrower, single-task-recipe grain, and without a comparable controlled ablation isolating how much the structured annotations contribute over raw success/failure. Against [Show-Harness](../papers/2609.10522.md), the two papers pick opposite halves of the same "fixed vocabulary, no deployment-time growth" design pattern: Show-Harness freezes the *model* (a VLM acts zero-shot through a fixed, view-relative semantic action vocabulary) while a deterministic per-embodiment interpreter handles low-level detail outside the model; Harness VLA freezes the *policy* (`vla_act`'s VLA backend) while a swappable LLM planner (the paper tests both Codex and Claude Code as interchangeable backbones) does the semantic reasoning through the same kind of fixed, structured interface.
* [Agentic robot manipulation](../topics/robot-manipulation-agents.md) - an LLM coding agent plans over a frozen VLA exposed as a tool at deployment time, in contrast to [EmbodiedSWE](2609.27308.md), which uses coding agents offline to generate VLA training data.
