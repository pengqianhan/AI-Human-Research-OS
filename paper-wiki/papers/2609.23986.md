# Q1 Problem Definition

* **Input (X):** a stream of observations o_t = (content x_t, optional timestamp τ_t, provenance μ_t) from a long multi-session interaction, and later a natural-language query q about that history.
* **Output (Y):** (i) a persistent memory M_t = (canonical nodes V_t, typed edge sets for semantic, temporal, causal, and entity relations, a vector index, a lexical index); (ii) for each query, a bounded evidence set E selected by an iterative retrieval loop and passed to a System-Two LLM that produces the answer y. Reported outputs are LLM-as-a-Judge answer accuracy, total memory build time, and mean per-query latency.
* **Core problem:** as agentic memory becomes more structured, *controlling* it — deciding what type a memory is, how it relates to existing memories, which relational view to search, how much to search, and when to stop — becomes a large share of latency and inference cost when those decisions are made by prompting an autoregressive LLM. Fixed heuristics are cheap but inflexible. The paper's observation is that most of these decisions are "semantic but not generative": they produce labels, probabilities, or scores, not free text.
* **Scope:** conversational long-term memory evaluated only on LoCoMo, with gpt-4o-mini as the System-Two answer model; the System-One controller is one specific commercial product (Jev from TypeSafe AI) accessed through `TypeSafeClient.system_one`.

# Q2 Problem Novelty

Partly new. Agentic memory architectures (A-MEM, Mem0, MemoryOS, Nemori, and the authors' own MAGMA multi-graph memory) and memory-efficiency work (SimpleMem, LightMem, Zero-Mem) already exist, and adaptive retrieval control (IRCoT, FLARE, Self-RAG, Adaptive-RAG) already treats *when/how much to retrieve* as a decision. The paper's claimed novelty is where the line is drawn: a dedicated control plane that owns *both* the write path (typing, relation construction, maintenance) and the read path (routing, budget, traversal, scoring, stopping) through one typed-decision interface. It is distinguished from model routing and cascades (FrugalGPT, RouteLLM) because those route whole requests, whereas Jev-Mem separates fine-grained decisions inside the memory lifecycle. The authors note that System One/Two is used "as an analogy for how computation is allocated, not as a claim that the underlying mechanisms correspond" (Appendix A.1).

# Q3 Scientific Hypothesis

If the frequent, bounded memory-control decisions are executed by a batched, non-autoregressive typed-probability controller over a shared multi-relational memory — with deterministic signals used wherever they suffice (timestamps create temporal edges, exact shared identifiers create entity edges) — then memory construction and query latency should drop sharply *without* losing answer accuracy, and query-adaptive routing plus evidence-sufficiency stopping should, if anything, *improve* accuracy by supplying the System-Two model a more focused evidence set.

# Q5 Key Solution Idea

Three planes: a System-One control plane, a shared memory data plane, and a System-Two reasoning plane.

* **Typed controller interface.** 𝒥(S, 𝒬) takes one structured state object and a *batch* of explicit decision questions. Independent propositions (Jev "Nouls" with true/false criteria) return scores in [0, 1], and mutually exclusive choices return a label plus a distribution. Decisions sharing a state are evaluated in one call. The appendix notes the returned values "are not assumed to be calibrated probabilities."
* **Write path** (observation → type → candidates → relations → memory):
  * Every valid observation is kept as a canonical node (admission filtering is disabled in the active profile), annotated with four overlapping type scores: episodic, semantic, procedural, preference.
  * Candidate discovery is deterministic: vector similarity, lexical overlap, shared entities, and temporal proximity select at most K_w neighbors.
  * The controller then judges only those pairs for semantic relatedness, directional causality, same-episode membership, entity equivalence, and implicit temporal order (before/after/during/contains/overlaps/same_time/unknown). An edge is inserted when P(g | v, u) ≥ θ_rel.
  * Periodic maintenance flags redundancy, contradiction, and obsolescence without deleting evidence. System Two is invoked only when the controller approves an explicit merge or promotion.
* **Read path** (route → retrieve → assess → expand → reassess):
  * The controller predicts per-view relevance p_g(q), a multi-hop requirement h(q), and a recency importance r(q). Views with p_g ≥ θ_act are activated.
  * An expansion budget B is split across active views by w_g ∝ p_g^γ after a minimum per view, and traversal depth D(q) = min(D_max, max(1, ⌈D_max·h(q)⌉)).
  * Anchors come from reciprocal-rank fusion of vector and lexical rankings (κ = 60).
  * Each round, the controller estimates evidence sufficiency, expected utility of more retrieval, missing evidence, and unresolved contradiction, and stops when sufficiency is high and gaps are low, or when utility is low.
  * New candidates are scored by a weighted mix of embedding similarity, relevance, relation usefulness, novelty, and support, with an optional recency adjustment. The top W form the next beam.
* **Bounded overhead:** one batched typing call plus at most one batched relation call per write; one routing call per query plus at most one assessment and one scoring call per round; hard caps on nodes, edges, depth, controller calls, and elapsed time.

# Q6 Experiment Design

* **Benchmark:** LoCoMo only, with six question categories (Multi-Hop, Temporal, Open-Domain, Single-Hop, Adversarial, and Overall). The setup text says "two widely used benchmarks," but only LoCoMo is described and reported.
* **Baselines:** Full Context, A-MEM, Nemori, MemoryOS, MAGMA, all with gpt-4o-mini as the answer model "whenever applicable."
* **Metrics:** LLM-as-a-Judge correctness; total memory build time (seconds); mean per-query latency (seconds).
* **Not designed in:**
  * no ablation of any mechanism (routing, budget allocation, stopping, candidate-pair limit, deterministic edge shortcuts);
  * no comparison against the same multi-graph with LLM-prompted control, which is the cleanest test of the System-One claim. MAGMA is the closest proxy but differs in more than the controller;
  * no variance or seeds, no second benchmark, no second System-Two model;
  * no efficiency comparison with memory-efficiency systems (SimpleMem, LightMem, Zero-Mem) or with Mem0;
  * no accounting of the controller's own API cost, only wall-clock time.

# Q7 Datasets and Code

No new dataset; evaluates on the public LoCoMo benchmark. Code is released at [libingzheren/Jev-Mem](https://github.com/libingzheren/Jev-Mem). Appendix B reproduces the typed prompts (Noul instructions and true/false criteria) used for writing and retrieval. Reproduction depends on access to TypeSafe's Jev System-One service; the paper describes Jev as "one concrete realization" of the controller but does not evaluate an open alternative.

# Q8 Evidence Quality

* **Supported, as far as the tables go:**
  * Table 1 gives Jev-Mem Overall 0.777 vs. the best baseline MAGMA's 0.700, an 11.0% relative gain. The largest category gain is Adversarial, 0.962 vs. 0.742.
  * Table 2 gives build time 158 s vs. Nemori's 1,044 s (the fastest baseline), a 6.6× speedup. Query latency is 0.93 s vs. MAGMA's 1.47 s and Full Context's 1.74 s.
  * The efficiency direction is plausible from the design: few batched classification calls replace free-form generation.
* **Internal inconsistency (found in the fidelity pass).** The prose in §4.2 does not match Table 1 as rendered in arXiv HTML v1:

  | Category | §4.2 prose | Table 1 | Best baseline in Table 1 |
  |---|---|---|---|
  | Multi-Hop | 0.625 | 0.623 | Nemori 0.569 |
  | Open-Domain | 0.610 | 0.618 | MAGMA 0.517 |
  | Single-Hop | 0.797 | 0.802 | MAGMA 0.776 |
  | Temporal | 0.650, "matches the best" | 0.637 | MAGMA 0.650 |

  By the table, Jev-Mem is *below* MAGMA on Temporal, not tied. The Overall (0.777) and Adversarial (0.962) values agree between prose and table. The discrepancies are small but mean the per-category claims should be read from the table, and the abstract-level result is unaffected.
* **Attribution is untested.** With no ablations, the accuracy gain cannot be assigned to System-One control versus the query-adaptive routing/stopping *algorithm* (which an LLM controller could also run) versus the always-retain write policy. The Adversarial jump could come from evidence-sufficiency stopping or from not discarding observations. The paper argues a mechanism for each, but no experiment separates them.
* **Narrow evidence base:** one benchmark, one answer model, one run per system, and judge-based scoring. The efficiency comparison omits the systems designed specifically for memory efficiency.

# Q9 Contributions

* A crisp systems framing: memory *control* is a distinct layer, and most of its decisions are bounded-output classifications that do not need autoregressive generation.
* A concrete end-to-end design that applies one typed-decision interface to both memory construction and retrieval, with explicit per-operation call bounds and deterministic shortcuts where structure already answers the question.
* Initial evidence on LoCoMo that such control can be both faster (6.6× build, 36.7% lower latency vs. the fastest memory baseline) and at least as accurate as LLM- or heuristic-controlled baselines.
* Published typed prompts (Appendix B) that make the controller's decision questions inspectable.

# Q10 Next Steps

* **Controller-substitution ablation:** run the identical multi-graph pipeline with (a) an LLM prompted for each decision, (b) a small open classifier, and (c) Jev, to isolate the System-One effect from the algorithm.
* **Mechanism ablations** for routing, budget allocation, sufficiency stopping, deterministic edge shortcuts, and always-retain writes, especially on Adversarial and Temporal.
* **Broader evaluation:** LongMemEval and agentic (non-conversational) memory tasks, multiple answer models, and efficiency comparison against SimpleMem, LightMem, and Zero-Mem; report controller API cost, not only wall-clock time.
* **Calibration:** the appendix says scores are not calibrated probabilities, yet every gate is a fixed threshold θ. Study threshold sensitivity and whether calibrating scores improves stopping.
* **Link to other wiki work (reader-constructed):** [VoiceMem](2608.26005.md)'s dual-brain split and [Recuris](2608.24876.md)'s "memory-control layer" name the same separation from other angles. A shared benchmark of memory-control decisions (typing, linking, stopping) with ground-truth labels would let these designs be compared directly.
