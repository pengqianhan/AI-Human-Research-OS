# Q1 Problem Definition

* **Input (X):** a question whose answer combines evidence spread over several documents, and a large heterogeneous corpus (email, chat, meeting notes, trackers, wikis, support articles) that an LLM agent explores with shell commands such as `find`, `grep`, and `cat`.
* **Output (Y):** an answer and the set of supporting documents the agent selected.
* **Core problem:** full-corpus agentic search gives the agent access to every file but no view of how files relate. A relevant document does not say which others complement it (for example, meeting notes that record a launch decision under a project codename), so the agent misses evidence and spends tokens rediscovering the same cross-document relations for every question, even though those relations do not depend on the question.
* **Constraint:** the navigation layer must be built from the corpus alone, offline, and must add to the original documents rather than replace them.

# Q2 Problem Novelty

Partly new. Graph-based RAG ([GraphRAG](../concepts/graphrag.md), HippoRAG) already builds entity graphs from a corpus, but uses them inside the retriever, so the generator still answers from one fixed retrieved context. Agentic search lets the model keep searching but treats the corpus as independent files. Recent agent-facing corpus structures organize it differently: LLM-maintained wikis (Karpathy's "LLM Wiki") let a model decide what becomes a page, and Corpus2Skill builds a topical tree in which each document sits in one or a few branches. The paper frames the problem as *corpus navigation* and argues that recurring entities (people, projects, incidents, configuration flags) are the right anchor, because one document can link to many others through the entities it mentions and those links can be computed once and reused.

# Q3 Scientific Hypothesis

If the corpus is organized around resolved cross-document entities, with each entity's page linking every document that mentions it and each fact attributed to its source, then an agent that can traverse these links should find more of the evidence a question needs and answer better, while reading fewer tokens than when it searches the flat corpus. The layer should also outperform navigation layers anchored on documents, folders, free-form LLM-written pages, or topical trees.

# Q4 Related Work and Key People

* **Retrieval-augmented generation:** BM25, dense retrieval, RAG, GraphRAG, and HippoRAG.
* **Agentic search and agent-facing corpus structures:** ReAct, iterative and adaptive retrieval (IRCoT, FLARE, Self-RAG, Adaptive-RAG), recent agentic search systems, LLM Wiki (Karpathy, 2026) and related LLM-maintained wikis, and Corpus2Skill's hierarchical skill tree.
* **Entity extraction and resolution:** named-entity recognition and open-type extractors such as GLiNER, entity linking against Wikipedia, cross-document coreference and entity resolution, LLM-based matching, and the lightweight zero-shot linker GLinker.
* **Key people:** Soyeong Jeong (KAIST; work done as a Microsoft intern), Sujay Kumar Jauhar and Andrew Joohun Nam (Microsoft), and Sung Ju Hwang (KAIST). Jeong and Hwang also wrote Adaptive-RAG. Likely critics: GraphRAG and HippoRAG authors, who would note that their methods are run retrieve-then-generate rather than as agent tools, and Corpus2Skill and LLM Wiki proponents, since those are reimplemented baselines.

# Q5 Key Solution Idea

* **A bipartite entity-document map.** Entities linked to more than one document become entity nodes, documents are document nodes, and a link joins an entity to each document where a mention was resolved to it. Two documents that share an entity are connected through it, and documents with no retained entity stay reachable by ordinary search.
* **Source-grounded Entity Pages.** Each entity is rendered as a file containing a short overview, key facts each tagged with its source document, the aliases under which it appears, and the file paths of every linked document.
* **Offline construction in four stages.** (1) *Cataloging:* an LLM proposes entity types from several document samples, merges them, and verifies the result into a fixed catalog with names, definitions, identity criteria, and examples. (2) *Extraction:* mentions are identified and typed per document and grouped into document-local entities. (3) *Resolution:* each local entity is compared against a growing registry and is either LINKed to an existing entity, ADDed as a new one, or left UNRESOLVED. (4) *Rendering:* entities linked to at least two documents get pages. Stages 2-4 can use off-the-shelf tools instead of an LLM.
* **Navigation with ordinary tools.** Pages sit beside the raw files, so the agent reads and greps them the same way. With each question the agent also receives candidate file paths, selected by ranking Entity Pages with BM25, pooling their linked documents, and reranking those documents with BM25; candidates are listed by title, path, and ID only, with no content.

# Q6 Experiment Design

* **Benchmarks:** only questions that need several documents. EnterpriseRAG-Bench contributes 80 questions (Project Related, Conflicting Info, and Completeness) over a fixed 2,819-document corpus of gold documents plus their one-hop distractors. WixQA contributes 79 multi-article questions over its full 6,221-article knowledge base. HERB contributes 238 content questions over 6,365 simulated software-company artifacts.
* **Methods:** Raw Corpus; Document Page (an LLM-written page per document); Group Page (one page per existing folder or group); LLM Wiki (free-form cross-linked pages); Corpus2Skill (a topical hierarchy of summarized clusters); CorpusMap; and a Gold Documents oracle. The original documents stay available in every method, and the same LLM builds each method's artifacts and answers.
* **Models and agent:** GPT-5.5 and GPT-5.6 Luna, Terra, and Sol for the main table; DeepSeek-V4-Pro, MAI-Thinking-1, and open-weight Qwen3.8-27B in analyses. The agent is EnterpriseRAG-Bench's terminal agent, with its per-question budget.
* **Metrics:** answer quality judged by GPT-5.6 Sol (correctness and completeness, WixQA factuality, and HERB content), retrieval quality (document recall and context recall), and input tokens over the whole trajectory. Results are means over three runs.
* **Analyses:** a paired bootstrap with Holm correction; a re-judge with DeepSeek-V4-Pro; retrieve-then-generate baselines (BM25, dense, HippoRAG, GraphRAG); amortized construction cost; reuse of a map built by one model for another; incremental updates in timestamp order; an LLM-free map built with GLinker; corpora padded with distractors; ablations of the candidates and of entity-entity edges.

# Q7 Datasets and Code

All three benchmarks are existing public datasets; the paper selects question subsets and fixed corpora from them (Appendix A lists the categories and splits). The construction prompts are in Appendix C. The retrieved text and `hf papers info` list no code repository, and the paper does not say that the constructed maps are released. API calls were made between August and September 2026.

# Q8 Evidence Quality

* **Supported:**
  * *Consistent gains over raw search at lower average token cost.* Overall quality improves over Raw Corpus by +6.45 (GPT-5.5), +11.74 (Luna), +6.76 (Terra), and +7.00 (Sol), with bootstrap 95% intervals well above zero and Holm-corrected p < 10⁻⁴. Input tokens relative to Raw Corpus are 0.43×, 0.65×, 0.66×, and 0.43× (geometric mean over benchmarks). EnterpriseRAG-Bench document recall rises from 61.62 to 76.17 (GPT-5.5) and from 56.40 to 75.11 (Luna).
  * *Other navigation layers do not reliably help.* Document Page, Group Page, LLM Wiki, and Corpus2Skill each fail to beat Raw Corpus with at least one model. With GPT-5.5, LLM Wiki scores 64.49 and Corpus2Skill 45.49 against Raw Corpus's 66.11, and CorpusMap beats every one of them significantly with all four models.
  * *Beyond GPT and beyond retrieve-then-generate.* On EnterpriseRAG-Bench, CorpusMap leads with DeepSeek-V4-Pro (71.11 vs. 68.02 raw) and MAI-Thinking-1 (45.07 vs. 34.06). Against retrieve-then-generate baselines it scores 76.60 and 73.20 (GPT-5.5 and Luna), versus 64.66 and 61.74 for HippoRAG and 47.95 and 43.46 for GraphRAG.
  * *The map is cheap to reuse.* A map built by GPT-5.6 Luna (construction cost at most $74.65, against at most $4,732.14 with GPT-5.5) still improves every answering model over Raw Corpus; for example, GPT-5.5 answering over it scores 73.59 against 65.60.
  * *Judge robustness.* Re-judged by DeepSeek-V4-Pro, CorpusMap is still top on all five LLM-judged metrics, and the two judges rank methods identically on correctness, completeness, and content (Kendall's τ = 1.00), though less so on WixQA context recall (0.47) and factuality (0.83).
  * *Entity-entity edges add nothing.* Adding relation or co-occurrence edges between entities changes document recall by −2.6 to +0.2 points while enlarging pages by 27-52% and input tokens by up to 28%. Without such edges, 86-90% of newly opened Entity Pages are found through search.
* **Weaker or bounded:**
  * *Much of the gain depends on the candidate list.* On EnterpriseRAG-Bench with GPT-5.5 (Table 8), CorpusMap without candidates scores 69.04, only 3.4 points above Raw Corpus's 65.60, and uses 496.4k input tokens, 2.4 times Raw Corpus's 206.5k. With BM25-selected linked documents (the default) it reaches 76.60 at 88.1k tokens. Random candidates drop quality to 60.76, below Raw Corpus. The headline efficiency therefore comes from the map *plus* a BM25 pre-selection step that raw search does not get. The authors do control for one version of this, giving Raw Corpus BM25-selected document candidates (66.19 at 107.4k tokens), but that ranks documents directly, not through Entity Pages.
  * *Token savings are average, not uniform.* With Luna on HERB, CorpusMap uses more tokens than Raw Corpus (254.2k vs. 219.4k); with Terra on EnterpriseRAG-Bench it uses 76.2k against 70.9k; and with MAI-Thinking-1 on EnterpriseRAG-Bench it uses 158.8k against 129.6k.
  * *Question selection favors the method.* All main results use only multi-document questions, the case the map targets. The authors do report that CorpusMap also helps on EnterpriseRAG-Bench's remaining, mostly single-document questions (correctness 94.76 vs. 89.05 with GPT-5.5, at fewer tokens), which partly addresses this.
  * *Scale is modest.* The main corpora hold 2,819-6,365 documents, and EnterpriseRAG-Bench's corpus is built around gold documents and their one-hop distractors. The distractor-scaling, incremental-update, amortized-cost, and GLinker results are reported only in figures, so their exact values (including the query count at which construction cost is recovered) are not in the text.
  * *LLM judges throughout.* Every answer-quality metric is LLM-judged; the DeepSeek re-judge reduces but does not remove this dependence.
  * *Reimplemented baselines.* LLM Wiki, Document Page, and Group Page are the authors' implementations under a shared protocol, and their tuning is not described in the retrieved text.

# Q9 Contributions

* A framing of agentic search over large collections as corpus navigation: reusable cross-document structure should be built once and exposed to the agent, not rediscovered per question.
* CorpusMap: a bipartite entity-document map with source-attributed Entity Pages, built offline by induced type cataloging, extraction, incremental registry-based resolution, and rendering, and stored as files the agent reads with its existing tools.
* A controlled comparison showing that anchoring on entities beats four other navigation units (documents, folders, free-form LLM wiki pages, topical trees) and four retrieve-then-generate baselines across seven models and three benchmarks.
* Practical evidence that the map can be built by a cheap model or without an LLM, reused across answering models, and updated incrementally, together with an ablation showing entity-entity edges are unnecessary.

# Q10 Next Steps

* **Separate the map from the candidate step (reader note):** give Raw Corpus and every other navigation layer the same BM25-over-pages candidate mechanism where it applies, and report CorpusMap without candidates on all three benchmarks, to measure how much of the gain is the entity structure itself.
* **Larger and messier corpora:** test at enterprise scale (millions of documents), with access permissions enforced per user, which the authors' ethics statement names as necessary because Entity Pages can aggregate sensitive facts scattered across the corpus.
* **Freshness and conflicting facts:** EnterpriseRAG-Bench includes a Conflicting Info category, but pages attribute facts to sources without ranking them by time or authority. How Entity Pages should represent superseded facts (the draft and v1 manifest in the case study) is open.
* **Relevance to this repository's paper wiki (reader note):** this wiki's concept pages are entity pages. A concept is created when two or more papers reference it, it is linked both ways with those papers, and its claims are tied to the papers in its `# Papers` list, which closely mirrors CorpusMap's rule of keeping only entities linked to at least two documents and tagging each fact with its source. The paper's finding that a free-form "LLM Wiki" does not reliably beat raw search, while entity pages do, supports keeping this wiki's entity-anchored structure rather than letting an agent write free-form synthesis pages. Its entity-edge ablation also suggests that concept-to-concept links add little once search is available.
* **Agent memory as a corpus map (reader note):** [Zep](2501.13956.md) and [Jev-Mem](2609.23986.md) build entity graphs over conversation history for retrieval. CorpusMap suggests exposing such graphs as readable files the agent navigates, rather than as a retriever's internal index.
