# Q1 Problem Definition

The paper studies **behavior localization** for agent harness evolution. The input is a natural-language request describing how a harness should behave differently, together with the current harness repository. The required output is the complete, source-grounded set of files, functions, branches, templates, and state locations that implement that behavior, followed by a focused edit plan.

This is a mismatch-of-representations problem: requests are expressed in behavioral language, while repositories are organized by files, functions, modules, and call relationships. A single harness behavior can be distributed across execution stages, shared state, fallback paths, mirrored implementations, and rarely executed branches. Code search can find matching text, but it does not by itself establish how all the pieces jointly realize a behavior or whether every affected site has been found.

# Q2 Problem Novelty

Repository maps, code search, code summarization, repository memory, and long-context coding agents already help inspect large codebases. Harness engineering and automated harness repair are also active research areas. The paper's narrower contribution is to make the missing **behavior-to-code mapping** an explicit artifact and to treat localization as a prerequisite task that can be evaluated separately from edit generation.

This is useful even if behavior localization is not wholly new as a software-maintenance concern. Agent harnesses make it unusually important because prompt construction, tool schemas, execution control, state transitions, permissions, and user-facing behavior are often coupled across modules. The proposed representation is therefore specialized around runtime behavior rather than being another file-centric repository summary.

# Q3 Scientific Hypothesis

If a coding agent is given a source-linked, behavior-centric representation of a harness and navigates it through coarse-to-fine progressive disclosure, then it should identify relevant implementation sites more completely and produce better-scoped edit plans with less repository exploration than an otherwise identical agent using the source repository alone.

The paper further predicts that the largest gains should occur when implementation sites are scattered, lie on cold or fallback paths, or interact through shared state across modules. Its experiments are designed around these localization conditions.

# Q4 Related Work and Key People

The paper connects three research lines:

* **Agent harnesses:** work treating prompts, tools, memory, state, orchestration, and environment interaction as an executable software layer rather than incidental glue. AutoGen, OpenHands, Claude Code, and Codex illustrate the practical importance of this layer.
* **Harness evolution:** systems that construct, optimize, adapt, or repair harnesses. This paper addresses the prerequisite question of where a requested behavioral change must land before deciding how to implement it.
* **Repository representations for coding agents:** repository maps, indexes, summaries, memory, search, and long-context editing. These remain primarily organized around implementation structure; Harness Handbook adds an operational behavior layer.

The author team spans Tencent HY LLM Frontier, Indiana University, the University of Maryland, the University of Georgia, and the National University of Singapore. The work is most relevant to researchers and engineers building coding agents, repository-understanding systems, agent runtimes, and self-modifying harnesses. A software-maintenance researcher would likely press hardest on generalization beyond two repositories, human-developer usefulness, benchmark construction, and end-to-end change correctness.

# Q5 Key Solution Idea

Harness Handbook combines a hierarchical behavior map with source authority:

1. **L1 system overview** describes the architecture, execution model, stages, and global data flow.
2. **L2 component overviews** describe each stage's responsibilities, inputs, outputs, dependencies, and local state.
3. **L3 unit entries** connect behavior descriptions to concrete source locations. A handbook uses either function-level leaves or file-level leaves, chosen once according to repository scale and the availability of a trustworthy stage skeleton.
4. **State registers** provide a cross-stage view of where shared state is read, written, cleared, or reset.

Construction has three phases. Deterministic static analysis extracts functions, named external boundaries, source locations, signatures, and resolved call edges. LLM-assisted behavioral organization maps functions or files into execution stages, leaving unresolved coverage explicit rather than inventing edges. Hierarchical synthesis then produces the L1-L3 documents and source locators.

During modification, **Behavior-Guided Progressive Disclosure (BGPD)** routes from the high-level request to relevant stages, follows coupled state registers, opens only the necessary lower-level entries, and verifies every candidate against the live repository. A separate planner emits the edit plan, a separate executor applies it, and any non-empty diff triggers resynchronization. Stale locators that cannot be revalidated are frozen and excluded, preserving the repository as the authority.

# Q6 Experiment Design

The evaluation isolates localization and planning rather than final patch execution. A read-only NexAU planner using DeepSeek-V4-Pro handles identical requests, repository snapshots, tools, and decoding settings in two arms: direct repository exploration versus repository exploration augmented by the handbook and BGPD instructions.

The two harnesses exercise different scales and leaf modes:

* **Terminus-2:** a Python terminal agent with 6 source files, 103 internal-function nodes, 20 L2 stages, 106 function-level L3 entries, and 10 state registers.
* **Codex:** a Rust monorepo with 2,267 source files, 34,363 internal-function nodes, 140 L2 stages, 2,267 file-level L3 entries, and 62 state registers.

Each harness contributes 30 behavior-driven requests, evenly divided among Query, Cross-file, and Search-Hostile changes and balanced across Easy, Medium, and Hard localization labels. Three independent LLM judges—GPT-5.5, Opus 4.8, and DeepSeek-V4-Pro—score Localization, Scope Control, and Reasoning. The paper also compares predicted files and symbols against reference plans from GPT-5.5 and Opus 4.8, reporting Recall, Precision, F1, and complete-miss rate (`Wrong`). Planner token use measures cost.

# Q7 Datasets and Code

The evaluation dataset is a 60-request suite: 30 requests for Terminus-2 and 30 for Codex, constructed from matched behavioral intents but adapted to each harness's implementation. Representative cases include multi-confirmation completion logic, per-command environment overrides, secret masking on every capture path, and consistency across compaction or mirrored tool schemas.

The paper and appendices publish detailed construction, BGPD, planning, answer-key, and LLM-judging prompts, which materially improves methodological inspectability. The Hugging Face paper metadata identifies a project page, but no linked dataset, model, Space, or GitHub repository was listed when this note was created. The public availability and license of the request suite and implementation therefore remain unverified from the sources used here.

# Q8 Evidence Quality

The strongest evidence is the controlled paired comparison: only handbook access and navigation instructions differ between arms. The direction is consistent across three judges, two independent reference-plan models, file- and symbol-level metrics, and request/difficulty slices. Handbook assistance raises overall plan-quality win rate from 28.3% to 38.3% on Codex and from 26.7% to 45.6% on Terminus-2, while average planner tokens fall by 12.7% and 8.6%, respectively. Across the 24 Recall, Precision, and F1 comparisons in Table 1, every Handbook-Assisted value is higher; F1 gains range from 5.0 to 18.8 points, and complete misses never increase.

The evidence does **not** yet establish that handbook-guided plans produce more correct final patches. The study stops at localization and plan quality, uses one planner model, covers only two harnesses, and relies on constructed requests and LLM-generated judges/reference plans rather than human-maintainer ground truth. Missing outputs and planner errors are excluded from the localization table. The reported results also do not quantify human onboarding benefit, handbook construction/resynchronization cost, behavior coverage accuracy, statistical uncertainty, or long-run degradation after repeated repository changes. These are significant boundaries for claims about production adoption or autonomous self-modification.

# Q9 Contributions

* Defines behavior localization as a separately inspectable bottleneck between a behavioral request and an edit.
* Introduces a behavior-centric L1-L3 representation with cross-stage state registers and verifiable source locators.
* Provides two construction modes—function-as-leaf and file-as-leaf—built from deterministic static facts plus bounded LLM structuring.
* Introduces BGPD, which routes from behavior to stages, state dependencies, and live-source verification before planning.
* Adds conservative automatic resynchronization so the handbook can evolve with the code while freezing unverifiable entries.
* Supplies controlled evidence that the representation improves localization and edit-plan quality with fewer planner tokens, especially for distributed and search-hostile changes.

# Q10 Next Steps

The most important next experiment is end-to-end: execute the plans, run repository tests and behavioral regression suites, and measure correct-change rate, introduced regressions, repair iterations, and total cost. This should be compared with strong repository maps, semantic code search, long-context baselines, and combinations of these tools rather than only direct source exploration.

Further work should measure handbook construction and incremental resynchronization cost, locator/coverage accuracy, robustness under large refactors, support for dynamic dispatch and generated code, and whether human maintainers navigate and modify unfamiliar harnesses faster. A multi-repository, multi-language benchmark with maintainer-authored requests and independently verified affected sites would strengthen external validity.

For self-evolving systems, the handbook could become shared behavioral memory across localization, planning, execution, evaluation, and resynchronization. That loop needs explicit regression gates and protection against stale or confidently misclassified behavior descriptions. For this Research OS, the paper suggests a concrete design test: navigation artifacts should map user-visible research behaviors to authoritative files and checks, not merely list directory structure.
