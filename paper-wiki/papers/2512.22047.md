# Q1 Problem Definition

* **Input (X):** for grounding, a GUI screenshot plus a natural-language instruction; for navigation, a POMDP observation stream (instruction + one or more screenshots) with a history of prior actions/observations, on a real Android device or emulator.
* **Output (Y):** for grounding, a coordinate point locating the target UI element; for navigation, one action per step from an action space that spans standard GUI operations (click, swipe, type, drag, system buttons) plus two extended actions the paper introduces — `ask_user` (request clarification from the user) and `mcp_call` (invoke an external MCP tool instead of manipulating the UI).
* **Core problem:** today's GUI agents are optimized for end-to-end execution under idealized assumptions that break down in real deployment: user instructions are often ambiguous rather than fully specified, UI-only action sequences are long and error-prone and cannot reach tasks outside the UI's surface, agents are built either as on-device-only (capacity-limited) or cloud-only (privacy/cost/latency-limited) with no native handoff between them, and agents trained on static trajectories overfit to specific interfaces and remain brittle to real-world dynamism (varying layouts, unexpected pop-ups).
* **Scope:** a family of foundation GUI agents (2B, 8B, 32B, 235B-A22B, built on Qwen3-VL) plus a device-cloud collaboration system and a self-evolving training pipeline; evaluated on GUI grounding, offline/online mobile navigation, and a new realistic-oriented benchmark (MobileWorld) that specifically tests agent-user interaction and MCP tool use.

# Q2 Problem Novelty

The paper frames itself against four gaps it argues prior GUI-agent work has left largely unaddressed for real deployment: (1) agent-user interaction — most systems execute end-to-end without asking clarifying questions or seeking consent for sensitive operations; (2) UI-only operation — relying solely on GUI manipulation amplifies per-step error and caps the agent to UI-reachable tasks, whereas MCP tool calls can compress long fragile sequences into a few API calls and reach previously UI-unreachable tasks (e.g., manipulating a GitHub repository from a phone); (3) no native device-cloud collaboration — agents are typically either lightweight on-device or cloud-only, forcing a privacy/cost/capability tradeoff rather than a routed one; (4) brittleness to dynamic environments from training on static, pre-collected trajectories. MAI-UI's claimed novelty is addressing all four simultaneously with one unified methodology rather than one at a time.

# Q3 Scientific Hypothesis

If a foundation GUI agent's action space is extended to include native agent-user clarification and MCP tool-use actions (trained via a self-evolving data pipeline that mixes rejection-sampled, human-annotated, and autonomous-rollout trajectories), if a device-cloud collaboration system routes execution between an on-device monitor/agent and a higher-capacity cloud agent based on detected trajectory deviation and data sensitivity, and if the model is further trained with online RL in scalable dynamic GUI environments, then the resulting agent will achieve state-of-the-art grounding and mobile-navigation accuracy at every model scale, substantially outperform end-to-end baselines on realistic tasks requiring clarification or tool use, and the device-cloud system will improve on-device performance while reducing cloud calls and preserving privacy relative to cloud-only or naive-switching alternatives.

# Q5 Key Solution Idea

1. **Extended action space.** Beyond standard GUI actions (click, long_press, type, swipe, drag, system_button, wait, terminate, answer), MAI-UI adds `ask_user` (request clarification for underspecified instructions) and `mcp_call` (invoke a named MCP tool with arguments), letting the agent choose among UI manipulation, user engagement, and tool use per step.
2. **Self-evolving SFT data pipeline.** Navigation task instructions come from app manuals, expert-designed tasks, and filtered open-source data; tasks are expanded (L1: parameter variation, L2: object substitution) and executed via both human annotation (on Android emulators) and model-based rollouts; an MLLM-as-judge validates trajectories end-to-end and additionally salvages the longest-correct-prefix of failed trajectories for reuse. Iterative rejection sampling alternates fine-tuning and rollout so the model and its training corpus co-evolve, explicitly closing the pass@1/pass@N gap while raising the pass@N ceiling. Agent-user-interaction and MCP-augmentation trajectories are constructed by deliberately omitting critical task information and routing `ask_user` queries to a synthetic LLM user agent conditioned on the hidden missing context.
3. **Online RL in scalable dynamic environments.** A containerized, RL-native GUI environment (Docker-encapsulated rooted AVDs, 35+ integrated real applications, standard `reset`/`step`/`get_observation`/`evaluate`/`close` primitives) is coordinated by a centralized Environment Manager that supports up to 512 concurrent instances on just 10 Alibaba Cloud ECS servers. Training uses a tailored GRPO (group size 16, DAPO-style asymmetric clip-higher with ε_low=0.2/ε_high=0.3, no KL penalty, action-repetition penalty, and an 8-trajectory-per-task experience replay buffer) on top of an asynchronous, hybrid-parallel (tensor+pipeline+context) rollout framework built on verl, needed because trajectories can reach millions of tokens. Tasks are dynamically stratified into four difficulty bands (frontier/exploration/near-mastery/exploitation) by the current policy's success rate to drive an automatic curriculum, and a hybrid rule-based + MLLM-as-judge verifier (83% agreement with human annotation) scores both deterministic and complex tasks.
4. **Native device-cloud collaboration (DCC).** A Local Agent (on-device) doubles as GUI actor and trajectory monitor, checking for execution failure, repeated non-progressing actions, or instruction deviation; on detected deviation *and* no privacy-sensitive data in context, it hands off to a higher-capacity Cloud Agent along with an auto-generated error summary, via a Local Unified Trajectory Memory that lets either model resume from any state. A separate local privacy-detection module can block the cloud handoff outright when sensitive content (e.g., password entry) is present, keeping execution on-device even under detected deviation.
5. **Full-spectrum model sizes.** Qwen3-VL backbone at 2B/8B/32B/235B-A22B, trained through four stages (grounding/perception SFT → navigation SFT → grounding RL → online navigation RL), letting the same methodology serve efficient on-device deployment and high-capacity cloud serving from one training recipe.

# Q6 Experiment Design

Evaluated across three benchmark categories against strong contemporary baselines at comparable scales. **Grounding** (five benchmarks): ScreenSpot-Pro 67.9% (73.5% with zoom-in) at 32B, a +4.1-point gain over the strongest baseline GTA1-32B; UI-Vision 47.1% (49.2% with zoom-in), +12.4 points over UI-Venus-Ground-72B; MMBench-GUI L2 91.3%, +7.9 over the prior best (GTA1); OSWorld-G 67.6% (70.9% with zoom-in); ScreenSpot-V2 96.5%. **Offline navigation:** GUI Odyssey 83.4% success (32B), a new SOTA; competitive but not SOTA on Android Control high-level. **Online navigation:** AndroidWorld (116 tasks, 20 apps, live emulator) — 235B-A22B reaches 76.7%, surpassing UI-TARS-2 (73.3%) and Gemini-2.5-Pro (69.7%); 32B/8B/2B reach 73.3%/70.7%/49.1% respectively, each best-in-class at its own parameter scale (2B beats the strongest on-device baseline Ferret-UI Lite-3B, 28.0%, by +21.1 points / +75.4% relative). **MobileWorld** (201 realistic tasks): 235B-A22B reaches 41.7% overall, +20.8 over the strongest end-to-end baseline (Doubao-1.5-UI-TARS, 20.9%), and remains competitive with (though not strictly comparable to) planner+executor agentic frameworks using GPT-5 or Gemini-3-Pro (43.8-51.7%); on the User-Interaction (45 tasks) and MCP (40 tasks) subsets specifically, 235B-A22B scores 51.1% and 37.5% respectively, +18.7 and +32.1 points over the best prior end-to-end scores. **Ablations:** online RL yields +3.5 to +6.0 points over SFT-only across scales; the tailored GRPO (curriculum + repetition penalty + experience replay) adds +4.2 points over standard GRPO on AndroidWorld/8B; interaction budget scaling from 15→50 steps adds +1.7→+6.0 points cumulatively; parallel-environment scaling from 32→512 improves AndroidWorld/8B from 65.5%→70.7%; DCC gives a 33.4% relative improvement over the on-device-only model and a 7.7-point gain over a random-switch baseline at equal cloud-call frequency, while cutting cloud calls by 42.7% and completing over 40% of AndroidWorld tasks fully on-device; removing the monitor's error summary at handoff costs 6.9 points.

# Q9 Contributions

1. **MAI-UI**, a 2B/8B/32B/235B-A22B family of foundation GUI agents (Qwen3-VL backbone) unifying GUI grounding and mobile navigation with two new native actions — `ask_user` for clarification and `mcp_call` for external tool use — trained through a self-evolving data pipeline that jointly evolves the model and its trajectory corpus.
2. A **native device-cloud collaboration system** (on-device monitor + high-capacity cloud agent + shared trajectory memory + local privacy gate) that improves on-device performance by 33% relative, cuts cloud calls by over 40%, and demonstrably preserves privacy by blocking cloud handoff on sensitive content even under detected trajectory deviation.
3. A scaled **online RL framework** for GUI agents (up to 512 parallel containerized environments on 10 cloud servers, asynchronous rollout, hybrid tensor/pipeline/context parallelism for million-token trajectories) with an automatic four-tier difficulty curriculum and a hybrid rule-based/MLLM-judge verifier.
4. New state-of-the-art results across GUI grounding (five benchmarks), offline (GUI Odyssey) and online (AndroidWorld, 76.7%) mobile navigation, and the paper's own realistic-oriented **MobileWorld** benchmark, at every evaluated model scale from 2B to 235B-A22B.

# Q10 Next Steps

Open questions this note cannot resolve from the retrieved text: how the device-cloud monitor's deviation-detection threshold trades off false handoffs (cost/latency) against missed handoffs (task failure) outside the single ablation reported; how MCP tool availability/selection is determined at inference time when the agent has not seen a given tool during training; and how much of MobileWorld's realism generalizes beyond its 15-20 self-hosted open-source applications to arbitrary commercial apps the agent has never seen. **Research-OS fit:** MobileWorld's explicit agent-user-interaction and MCP-tool-use subsets, and the finding that a native `ask_user` action plus a synthetic-user training pipeline meaningfully improves clarification behavior, are directly relevant to any project building or evaluating agents that must decide when to ask versus act — worth comparing against this wiki's simulated-user-evaluation and agent-environment threads once both are read in full.
