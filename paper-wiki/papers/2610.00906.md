# Q1 Problem Definition

* **Input (X):** a harness H_θ (prompts, tool interfaces, runtime control logic) around a fixed model; disjoint training, development, and test task sets; a fixed harness optimizer O that turns execution records into harness updates; and a shared rollout budget (ten times the size of train plus dev).
* **Output (Y):** a curriculum policy π that picks, at each iteration, the batch of at most three training scenarios X_t to execute, and the final harness selected on the development set from the resulting optimization trajectory.
* **Core problem:** automated harness optimizers decide *how* to update the harness from feedback, but the scenarios that produce the feedback are fixed in advance (the full training set or a pre-shuffled sequence of mini-batches). As the harness changes, a fixed schedule may leave unresolved failures too early, spend rollouts on scenarios already solved, and cannot shift between repairing known weaknesses and looking for new ones.
* **Formal framing:** with the optimizer held fixed, find π* = argmax_π E[J(θ̂_π)], where J is population performance and θ̂_π the dev-selected harness, under the same rollout budget for every policy.

# Q2 Problem Novelty

New as a framing for harness optimization. Automated curriculum learning (learning-progress bandits, teacher-student task selection, prioritized level replay) is established for training model weights, but there the target and its progress signal are explicit. Here a scenario does not name a fixed weakness: the weakness appears only after execution, the same scenario can expose different failures as the harness changes, the same weakness recurs across scenarios, and no loss says whether it is still unresolved. Nearby harness work adapts task selection on the evaluation side (Task-CoEvolve picks validation tasks that separate candidate harnesses; HarnessLens picks verification tasks per proposed change), and CoEvolve generates training tasks for weight updates. ActiveSaddler adapts the *training* scenarios that produce evidence for each harness update.

# Q3 Scientific Hypothesis

If the curriculum (a) groups failures into arms by the underlying harness weakness rather than by benchmark category or individual scenario, (b) re-scores those arms each iteration by their estimated remaining learning progress, and (c) decides adaptively when to explore unseen scenarios, then the same harness optimizer will find a better harness under the same rollout budget, and each of the three choices will be necessary.

# Q5 Key Solution Idea

* **Failure-pattern arms.** After each optimization step, a Failure-Pattern Extractor abstracts each failed execution into a candidate symptom (without looking at existing arms), then normalizes the candidates against the arm set: link to an existing pattern, compose existing patterns, or create a new arm. Each arm keeps a description, its supporting training scenarios, and the harness and diagnostic evidence under which it was seen. Arms are created during optimization; none are defined in advance.
* **Arm Prioritizer.** An LLM scores each arm's learning progress φ_t(a) in [0, 1] from four factors: severity (is the pattern still active under the current harness), fixability (can a harness change address it), breadth (how far a repair would generalize), and side-effect risk. Scores are recomputed at every selection, turned into a softmax with temperature 0.15, and sampled, so high-scoring arms dominate but lower-ranked ones can still be picked.
* **Exploration Controller.** A separate agent session makes a binary choice each iteration: Draw (sample scenarios from the unseen pool, without replacement) or Pull (optimize a known arm). Once every scenario has been explored and every arm visited, earlier successes that never created an arm become eligible again, so regressions can be rediscovered without re-running everything.
* **Instantiation.** The three components run on the GitHub Copilot SDK with a shared pattern registry exposed through a CLI. AutoSaddler's own loop (diagnosis and patch, candidate evaluation on the batch and dev set, reflection, EvoDAG update) is unchanged; its pre-patch and post-patch failures feed the extractor.

# Q6 Experiment Design

* **Benchmarks and splits (following AutoSaddler):** GAIA2 split by Universe (persona): train Universe 29 (75 tasks), dev Universe 30 (65), test Universes 21, 22, and 27 (300). Terminal-Bench 2.0 split at random: 30 train, 19 dev, 40 test.
* **Models and budget:** gpt-5.5 for the task agent (medium reasoning effort) and the optimizer sessions (xhigh); 1,400 rollouts on GAIA2 and 490 on Terminal-Bench 2.0; at most three scenarios per iteration for every method.
* **Comparisons:** the base harnesses; GEPA, Meta-Harness, and AutoSaddler with a random fixed scenario order; AutoSaddler with easy-to-hard orders by category accuracy or scenario accuracy (estimated from five base-harness runs, whose rollouts count toward the budget); Terminus-KIRA on Terminal-Bench 2.0.
* **Ablations:** category-level or scenario-level arms instead of failure-pattern arms; equal scores for every arm (no prioritizer); exploration fixed at every fifth iteration (no controller); non-LLM substitutes (EMA failure-persistence scoring after TSCL, a count-based UCB-AIR exploration rule).
* **Robustness and transfer:** a second independent GAIA2 optimization run for AutoSaddler, the two fixed curricula, and ActiveSaddler; ActiveSaddler applied to GEPA on GAIA2.
* **Reporting:** test Pass@1 as mean ± standard deviation over three test-time executions of each optimized harness; end-to-end cost including optimizer-side LLM usage.

# Q7 Datasets and Code

No new benchmark; GAIA2 and Terminal-Bench 2.0 are existing ones. # Q8 Evidence Quality

* **Supported:**
  * *Headline results.* GAIA2 test Pass@1: ActiveSaddler 59.8 ± 1.0 against AutoSaddler 55.4 ± 1.2 (fixed random order), 55.9 and 55.7 for the category and scenario difficulty orders, 54.2 for GEPA and Meta-Harness, and 53.6 for the default agent. Terminal-Bench 2.0: 80.0 ± 2.5 against AutoSaddler 72.5, the difficulty orders 70.8 and 73.3, GEPA 65.8, Meta-Harness 66.7, Terminus-KIRA 69.2, and Terminus 2 64.2.
  * *A second run agrees.* In an independent GAIA2 run, ActiveSaddler reaches 61.6 and AutoSaddler 56.6; across both runs ActiveSaddler beats every fixed-order baseline on each held-out universe, by 3.9-4.4 points in run 1 and 5.0-5.7 in run 2.
  * *Not tied to one optimizer.* Wrapping GEPA raises its GAIA2 Pass@1 from 54.2 to 57.2.
  * *Each component is needed.* On GAIA2, category or scenario arms give 56.8 and 56.2, no prioritizer 55.3, and fixed exploration 55.3; on Terminal-Bench 2.0, 69.2, 73.3, 72.5, and 71.7. EMA scoring (56.7) and UCB-AIR exploration (55.6) also fall short of the LLM components.
  * *Mechanism diagnostics.* Failure-pattern arms put an unresolved failure into 52.9% of GAIA2 mini-batches against 36.4% (category arms) and 17.6% (scenario arms), and 60.4% against 30.5% and 36.6% on Terminal-Bench 2.0. On GAIA2 the arm pool grows from 6 to 35; by the last selection, the 24 arms whose scenarios all pass hold 26.2% of the pull probability, against 68.6% under uniform allocation. Draws fall from 44% of decisions in the first half to 20% in the second, and Pull decisions occur with 2.0× (GAIA2) and 6.9× (Terminal-Bench 2.0) as many unresolved arms as Draw decisions, against 0.8× and 1.3× for the fixed schedule.
  * *Cost.* Optimizer-side cost per generated patch rises from $7.87 to $11.44 on GAIA2 and from $6.77 to $11.37 on Terminal-Bench 2.0, but ActiveSaddler reaches 58.5% GAIA2 dev accuracy at $298 where AutoSaddler needs $1,360, and 78.9% Terminal-Bench 2.0 dev accuracy at $128 against $220.
* **Weaker or bounded:**
  * *Small test sets and test-only variance.* Terminal-Bench 2.0's test split has 40 tasks, so the 7.5-point gain is 3 tasks, and its dev split has 19 tasks (one task is 5.3 points), which also governs harness selection and the cost curves. The ± values cover test-time executions of one optimized harness, not repeated optimization runs; only GAIA2 has a second run (reader note).
  * *Every ablation lands near the baseline.* Removing any single component returns to roughly AutoSaddler's level (for example 55.3 vs. 55.4 on GAIA2 and 72.5 vs. 72.5 on Terminal-Bench 2.0 without the prioritizer), and category arms on Terminal-Bench 2.0 fall below it. The gain needs all three parts together; no partial version helps (reader note).
  * *Several arms target the grader's format (reader note from Appendix H).* Many GAIA2 arms describe matching the oracle's conventions, for example "serialize as null instead of the oracle's empty path string", "wording diverges from concise oracle-style message content", or replies missing a "canonical subject". Test universes are disjoint personas but share GAIA2's checker, so part of the test gain may come from learning that checker's format conventions rather than general assistant behavior. The authors state that ActiveSaddler has no mechanism to detect reward hacking or specification gaming.
  * *AutoSaddler is weaker here than in its own paper (reader note).* This wiki's [AutoSaddler](2608.23041.md) note reports, with Claude Opus 4.6, GAIA2 53.0 → 62.0 and Terminal-Bench 2.0 40.0 → 50.0. Here, with gpt-5.5, AutoSaddler gains only 1.8 points on GAIA2 (53.6 → 55.4) and 8.3 on Terminal-Bench 2.0. The backbones and budgets differ, so this is context, not a contradiction, but ActiveSaddler's GAIA2 margin is measured against an AutoSaddler that gained little.
  * *Single model.* Every result uses gpt-5.5 as both task agent and optimizer.

# Q9 Contributions

* Adds a missing axis to harness optimization: which training scenarios generate feedback, as an automated curriculum problem with the optimizer held fixed.
* Failure-pattern arms induced online from diagnosed failures, with a many-to-many relation between scenarios and weaknesses, shown to be a better unit than benchmark categories or single scenarios.
* LLM-based learning-progress scoring (severity, fixability, breadth, side-effect risk) and an LLM explore-or-exploit controller, compared against EMA and UCB-AIR substitutes.
* Evidence that adaptive scenario selection improves two optimizers (AutoSaddler and GEPA) under equal rollout budgets and at lower end-to-end cost.

# Q10 Next Steps

* **The authors' stated limits:** a research method evaluated only on benchmarks, with no safety, security, or privacy evaluation; harness updates can change prompts, tools, and control flow, so promotion should be gated by independent review, least privilege, and rollback, and optimization traces from real deployments would need PII and secret handling.
* **Guard against grader fitting (reader note):** add a check to the Failure-Pattern Extractor or the Arm Prioritizer that flags arms describing evaluator formatting rather than task behavior, and report test gains with and without patches from such arms.
* **Repeated optimization runs on Terminal-Bench 2.0 (reader note):** with 40 test tasks and 19 dev tasks, several independent runs per method are needed before the 7.5-point gap can be read as more than a few tasks.
* **Cross-backbone check (reader note):** rerun with Claude Opus 4.6, where AutoSaddler's own gain was larger, to see whether the curriculum still adds on top of a stronger fixed-order optimizer.
* **Relevance to this repository (reader note):** the failure-pattern registry is a reusable idea for this repository's scheduled agent runs, such as this daily paper run: record each failure as a named pattern with its supporting runs, revisit patterns that are still active, and mark patterns resolved only when their supporting cases pass again.
