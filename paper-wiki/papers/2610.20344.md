# Q1 Problem Definition

* **Input (X):** a *build model* under evaluation, run inside a fixed builder harness ([OpenCode](../concepts/opencode.md) 1.17.0), given two files in an empty container: a *development document* that specifies a coding-agent harness clause by clause, and a *contract skeleton* stripped from [mini-swe-agent](../concepts/mini-swe-agent.md) (five Python files of about seventy lines, plus an install script, an entry script, and a project config) that declares three immutable interfaces: the CLI, a headless entry point, and an API for driving automated evaluation.
* **Output (Y):** a complete *candidate harness*, frozen the first time the model submits and a contract check passes (it compiles and installs, every required command exists, no placeholder stubs remain, the three interfaces are in place). A representative candidate has about 30 Python files and 16,000 lines, roughly 99.6% of them written by the build model.
* **What is scored:** the frozen harness, run in its own container per test case and driven end to end by a *scripted mock model*, on 328 test cases. Each case's effect is read from four channels: the requests sent to the model, the files on disk, the process exit code, and the command output. The build model's ability is ranked by pass rate, averaged over three independent builds.
* **Constraints:** no network except the model gateway; a two-hour wall clock and at most three submissions per build; OpenCode's one-turn `opencode run` resumed with `--continue` for up to 24 turns, with history compacted at 80% of the context window; 900 seconds per test case.

# Q2 Problem Novelty

Partly new. The paper sorts prior work into three groups and claims none of them scores whether a harness's own behavior conforms to a specification, clause by clause:

* **Benchmarks of existing harnesses.** Claw-SWE-Bench finds the choice of harness moves scores by 27.4 points against 29.4 for the choice of model; Harness-Bench argues ability should be reported per model-harness configuration.
* **Benchmarks of one harness capability.** Rule compliance across instruction surfaces (Harness-IF), skill retrieval (Skill-Use), component lifecycles (CordisBench), safety (Permission Denied, HarnessRisk, HarnessSafe), and keeping pace with a changing harness (EvoHarnessBench).
* **Benchmarks of producing or revising a harness** from an existing one plus execution feedback (HarnessDev, Evo-Bench, HarnessOpt-Bench). These measure gains on downstream tasks, which a later paper notes cannot be separated from extra test-time search, and which depend on the driving model too.

Against repository-level generation (Commit0, NL2Repo-Bench, RepoZero, [ProgramBench](../concepts/programbench.md), DeepSWE), the paper's argument is that those rebuild released software and judge it with unit tests through a fixed interface, whereas a harness feature can be implemented many ways and a harness cannot finish a downstream task on its own. It also argues harnesses are recent and change quickly, so building one leans on generalization more than rebuilding a mature library that may be in the training data. In this wiki, [AgentSWE](2610.13361.md) is the nearest neighbor: it also freezes an agent built by a coding agent, but scores it on downstream cases with a real runtime model and rubrics.

# Q3 Scientific Hypothesis

Not stated as a hypothesis; the paper's design implies one (reader formulation). If a harness is specified only through behavior observable outside it, and is driven by a scripted mock model instead of a real one, then its conformance can be scored deterministically and separately from any model's downstream skill, and that score will separate frontier models on the ability to build a harness. A second claim is drawn after the fact from the source analysis: at equal code size, harnesses split into more modules conform less.

# Q5 Key Solution Idea

**A specification that only describes behavior.** The development document is built in three steps. First, candidate features are crawled from the twelve harnesses' user documentation and filled in with invocation form, parameter meaning, and boundary behavior. Second, the inventory becomes clauses, each with a syntax, a meaning, and an expected behavior whose effect must show up on one of the four channels. Its chapters cover the deliverable and entry script, built-in tools, commands and subcommands, five permission modes and five role modes with deny rules, global flags, in-session commands, persistent memory, convention files, cross-chapter consistency rules, a closed set of exit codes, and the evaluation API. Third, two disambiguation rules: merge commands with the same meaning (Claude Code's `/compact` and Cursor's `/summarize` become `/compact`) and split one name used for different concepts ("plan" is a read-only permission mode in Claude Code, while Aider splits proposing and applying changes between architect and editor roles, so the document gives read-only to permissions and propose/apply to roles). Beyond the three skeleton interfaces, nothing about the implementation is constrained.

**Test cases grown from three sources, in turns.** Each case must be anchored to a clause and must be able to tell implementations apart. The authors switch method when the current one's yield falls:

1. *Public issue mining.* All 21,083 non-PR issues from Claude Code (9,868), OpenCode (5,438), Gemini CLI (4,831), and Kimi Code (946), ranked by relevance to the document and read from the top until review cost exceeds yield; issues are clustered by reported phenomenon, near-duplicate clusters on the same clause are merged, and a candidate survives only if it becomes a deterministic assertion not already covered. The premise is that build models will repeat the defects mature harnesses accumulated.
2. *Cross-harness comparison.* A candidate harness and a mature one (Kimi Code, Qwen Code) are both partitioned by the document's feature groups and diffed module by module; a difference becomes a case only if it can be derived from some clause's purpose.
3. *Single-variable expansion.* Starting from a case already known to discriminate, change exactly one thing in its scenario while keeping its assertion: which tool reaches the effect, the input form (for path escape: symlink to a file, to a directory, multi-level, relative), the parameter carrying a typical bug (treating 0 as absent), or where the result appears (stdout, stderr, error text). A candidate too close to its seed is dropped; survivors become new seeds.

**Positive controls for "must not happen" assertions.** A case like "a symlink pointing outside the workspace, read with the read tool, must not put that file's content in the model request" also passes if the read tool cannot read anything. A positive control shares the case's scenario and fixture, changes only the input or the access route, and asserts something that must happen if the observation works. There are three kinds: *channel* (an ordinary file read does reach the request), *same form* (the same symlink read through the bash tool, which the clause does not restrict, does resolve and is readable), and *reverse* (a symlink pointing inside the workspace is still read, which rules out refusing all symlinks). A case passes only if it and every control gating it pass; controls do not count toward the score. 130 of the 328 cases are gated (114 by one control, 15 by two, one by three); the widest control gates six cases.

**One fixed part per stage.** Building uses OpenCode rather than Claude Code or Codex CLI, because vendor harnesses are developed alongside their own models. Evaluation uses a mock model, because a real model would add run-to-run variation.

# Q6 Experiment Design

* **Models.** Nineteen from eleven vendors: Claude Opus 4.6, 4.7, 4.8, and 5; GPT-5.5, GPT-5.6-sol, and GPT-6 Astra; Qwen3.8 Max 0902; Kimi K3; GLM 5.2 and 5.3; DeepSeek V4 Pro and V4.1 Flash; Hy3 and Hy4 preview; Doubao Seed 2.1 Pro; MiMo-V2.6-Flash; Grok 4.7; Step 5 Preview. Three builds each, 57 scored harnesses, all on one 48-thread, 128 GB server.
* **Test suite.** 328 cases in nine disjoint categories: session state 84, file operations 75, permissions 61, headless 40, direct drive 33, interactive terminal 20, and "other" 15 (artifact checks 7, startup 7, extension discovery 1).
* **Analyses.** Pass rate by category; per-category strong-weak gap and the split of cases into floor (no harness passes), ceiling (all pass), and discriminating; the top two models on ordinary against boundary scenarios; rank movement and pairwise correlations across the six categories with at least 20 cases; KR-20 internal consistency over the 57 harnesses; and a source analysis of every scored harness (code lines, module count, lines per module, share of the largest module), with between-model variance shares and partial correlations under a leave-one-model-out check.
* **Not included.** No reference harness (human-written, or one of the twelve real harnesses) run on the suite to show what score the document allows; no test of whether pass rate predicts a harness's usefulness with a real model; no count of how many passes the positive controls overturned; no build-evaluate-repair loop.

# Q8 Evidence Quality

* **Supported.**
  * *The suite separates models and is not saturated.* Pass rates run from 53.05 ± 0.25 (GPT-6 Astra) through 46.65 ± 1.80 (Opus 5) and 45.83 ± 0.14 (Qwen3.8 Max) down to 27.44 ± 0.43 (Hy3), mean 38.30 (Table 2). 256 of the 328 cases discriminate; 56 are failed by every harness and 16 passed by every harness. KR-20 over the 57 harnesses is 0.913.
  * *Categories differ in what they reveal.* Permissions separates models most: average 43.7%, strong-weak gap 50.8 points, 51 of 61 cases discriminating. File operations has a similar average (39.6%) but a 20.9-point gap. The interactive terminal is near saturation (79.9% average, 7 of 20 cases passed by all). GPT-6 Astra leads four of the six main categories; Grok 4.7 leads file operations and Qwen3.8 Max the interactive terminal.
  * *Ranks move but abilities are largely one-dimensional.* A model's rank moves by up to sixteen places across categories (Grok 4.7 first on file operations and eleventh on session state; Opus 4.6 third on direct drive and nineteenth on permissions), yet all fifteen pairwise category correlations are positive (mean +0.521).
  * *The top two differ on edge cases.* On ordinary scenarios Opus 5 leads GPT-6 Astra (80.68% against 72.46%); on boundary scenarios GPT-6 Astra leads (48.97% against 37.02%).
  * *Implementation size belongs to the model.* 95.9% of the variance in code lines is between models; across a model's three builds the coefficient of variation averages 12.7%, against 60.1% across the nineteen model means. Per-model mean size ranges from 1,271 lines (GPT-5.5) to 16,681 (Qwen3.8 Max). Code lines correlate with pass rate at 0.614 over builds.
  * *More modules, lower score, at equal size.* Controlling for code lines, module count has a partial correlation of −0.423 with pass rate (−0.484 to −0.309 when leaving one model out), and lines per module +0.504 (0.312 to 0.649).
* **Weaker or narrower than the headline.**
  * *"Failures cluster around how cross-cutting functionality is split across modules" goes beyond the analysis shown.* The evidence is a correlation over 57 builds of 19 models, and 87.9% of the variance in module count is between models, so it mostly compares models, and overall capability could drive both modularity and pass rate. No case-level attribution of failures to module boundaries appears in the text, and the keyword rule for a "dedicated module" is defined but no result using it is reported there. The relation is also not monotone (reader observation from Table 4): Opus 5 (33.3 modules) and Qwen3.8 Max (40.0) rank second and third, while GPT-5.5 puts 78% of its code in one module and ranks thirteenth.
  * *Conformance is not usefulness.* The suite checks behavior against the merged document with a scripted model. How well a harness serves a real model (prompt quality, context management under real outputs) is not measured, and no downstream run of the 57 harnesses checks the ranking.
  * *Mid-table order is within build noise.* Standard deviations over three builds reach 3.29 (MiMo-V2.6-Flash, Step 5 Preview) while neighbors differ by as little as 0.30 (GPT-5.6-sol 43.80, Grok 4.7 43.50); only the top and bottom of the ranking are well separated (reader observation).
  * *When a model stops changes its score.* The contract check tests form, not behavior, so an early submitter freezes a less-revised harness; the authors call its score a lower bound. The two-hour wall clock also ties the score to provider latency (reader note). How many builds ended by submission versus by the time limit is not reported.
  * *The suite was partly selected on harnesses the models built.* Cross-harness comparison diffs a candidate harness against a mature one, and expansion seeds are cases already shown to discriminate; whether a case discriminates is settled after evaluation. The text does not say which models' harnesses were used, so selection effects on the ranking cannot be ruled out (reader concern). Correlated variants, which the authors list as a limitation, also raise KR-20.
  * *The 56 floor cases are not audited.* Cases no harness passes could be hard, unclear in the document, or faulty; with no reference harness this cannot be told apart.
  * *The builder harness is a fixed choice.* OpenCode avoids vendor home advantage, but its effect on the ranking is untested; [Learn2Play Bench](2610.08215.md) found OpenCode below Claude Code and Codex on the same backbone in a different task (reader cross-reference).

# Q9 Contributions

* A deterministic benchmark for building a harness from a specification: behavior-only clauses merged from twelve harnesses, an interface-only skeleton, and a mock-model black-box drive read on four channels.
* A positive-control design for prohibitions (channel, same-form, and reverse controls) that keeps "this must not happen" assertions from passing because a feature never ran; it applies to any black-box test of a negative requirement.
* A recipe for growing test cases from public issue trackers, cross-implementation diffs, and single-variable expansion with a distance check.
* A 19-model ranking with a category breakdown and a source analysis of all 57 scored harnesses.

# Q10 Next Steps

* **From the authors.** An iterative build-evaluate-repair protocol, since the current one measures a single build; handling correlated failures across expanded variants.
* **Anchor the scale (reader suggestion).** Run one or more of the twelve real harnesses, or a human-written implementation of the document, through the suite, and audit the 56 floor cases against it.
* **Check against downstream use (reader suggestion).** Run the 57 harnesses with a real model on a coding benchmark and test whether conformance rank predicts task success, the link between Doc2Harness and benchmarks like AgentSWE.
* **Attribute failures (reader suggestion).** Map failing cases to the modules involved, so the modularity finding rests on case-level evidence rather than a between-model correlation; repeat builds under Claude Code and Codex CLI to measure the builder-harness effect.
* **Project fit (reader note).** The positive-control rule (every check that something is absent needs a paired check that the same observation can see it when present) applies directly to verification scripts in this repository that assert a forbidden file, link, or string does not appear.
