# Q1 Problem Definition

* **Input (X):** a working scientific application (for example SU2, GROMACS, HPL, HPCG, QuEST, a paged LM generation workflow) in a container with fixed CPU cores (four or eight) and memory, plus a task statement fixing the workload, the outputs and numerical tolerances, stateful checks such as checkpoint recovery in a new process, the timing scope, and the files the agent may edit.
* **Output (Y):** a final submission (source, build options, dependencies, runtime configuration within the permitted directory) that a private verifier rebuilds, checks, and times on held-out inputs.
* **Constraints:** an eight-hour run; no reference optimization patch tells the agent where to intervene; only the end-to-end timed workflow counts, so a faster kernel helps only in proportion to its share; a shortcut that skips a required output or recovery step fails correctness.

# Q2 Problem Novelty

SWE-Perf, GSO, and SWE-fficiency build tasks from human optimization commits, so a known patch anchors each task; KernelBench and AlgoTune score self-contained functions against a reference; RE-Bench is closest in format (improve a working solution within eight hours) but targets ML research engineering and normalizes against expert solutions. Accelerate Bench defines a task by the computation to preserve and the workload to speed up (in the spirit of ProgramBench's behavioral specification), lets agents change algorithms, implementation, build, dependencies, and runtime settings, and scores the whole application workflow on private inputs.

# Q3 Scientific Hypothesis

Application-level optimization is a different skill from producing a correct patch: when correctness is checked on the full workflow, agents will mostly produce correct programs, and what separates them will be how much end-to-end runtime they remove, which depends on choices interacting across code, build, and runtime layers.

# Q5 Key Solution Idea

1. **Workload-defined tasks.** Each of 32 tasks fixes the computation, complete outputs, stateful checks, and timing boundaries (one-time setup and build excluded). Competition workloads are scaled down to one node by reducing input sizes and iteration counts while keeping stages and correctness criteria. 29 tasks build on a competition application; three (paged LM generation, Tucker reconstruction, graph sparsification) are workflows the authors wrote around a competition theme.
2. **Public tests, private verifier.** The public test rebuilds the candidate, runs typically two public inputs, and reports correctness, runtime, and usually the speedup; the agent never sees the checking code. The verifier reruns on typically four private inputs, often larger or freshly randomized.
3. **Reward.** r = C × max(0, 1 − T/B): the fraction of baseline runtime saved by a correct program (2× earns 0.5, 10× 0.9). Score@1 is the mean over tasks; A_τ is the share of tasks correct and at least τ× faster (τ = 1.25, 2, plus 5 and 10 in the appendix); GM is the geometric-mean speedup with incorrect or slower runs set to 1×.
4. **Verifier controls.** 14 planned controls on HPCG-derived and paged generation: all unchanged-source runs and both legal transformations pass; all eight invalid variants (omitting a second solution, NaN output, four attention variants that pass component tests) fail the check they violate.
5. **Process records.** Trajectories, candidates, timings, and feedback are kept for analysis, with LLM-assisted labeling and controlled replays of submitted programs.

# Q6 Experiment Design

* **Main evaluation (v1.1).** 16 agents, each a model plus harness: GPT-6 Astra, GPT-6.1 Sol, and GPT-6.1 Terra in Codex; the rest (Claude Sonnet 5.5, Claude Opus 5.5, Hy4-Preview, Hy4, Hy3, Kimi K3, DeepSeek variants, GLM variants, Grok 4.6) in Claude Code; high reasoning effort. One scored run per agent and task; GPT-6 Astra and Hy4-Preview run twice more for variance. Final programs are scored on one machine (two AMD EPYC 9K84 processors), pinned to one NUMA node's physical cores.
* **Failure accounting.** Infrastructure or API failures are replaced by a pre-fixed new run; agent-caused failures (wrong output, OOM, timeout) are scored. Three Claude Opus 5.5 runs stopped by the provider's safety classifiers (cybersecurity or biology flags) score zero.
* **Configuration-only baseline.** A fixed recipe of build and runtime settings without source changes (R1 -O3 -march=native; R2 the application's SIMD option; R3 threads equal to cores with pinning), chosen on public tests and judged once by the verifier, as an alternative reference.
* **Variance and resolution.** Re-judging frozen submissions; paired task-bootstrap intervals (10,000 resamples) for Score@1 differences; leave-out checks for the three authored workflows and HPCG-derived.
* **Process analysis (v1.0).** Five agents (DeepSeek-V4.1-Flash, Grok 4.6, DeepSeek-V4-Pro, DeepSeek-V4-Flash, Hy3), three runs per task, 480 runs. GPT-5.6 Luna labels techniques in 476 final submissions; DeepSeek-V4.1-Flash annotates every tool call; human review of 80 sampled trajectories estimates cross-layer dependencies; controlled replays on GROMACS, QiboTN, and HPCG-derived.

# Q8 Evidence Quality

**Main results (Table 1, v1.1, one run per agent).**

|---|---|---|---|---|---|---|
| Claude Sonnet 5.5 | Claude Code | 67.4 | 66.3 | 3.83 | 100.0 | 71.9 |
| Claude Opus 5.5 | Claude Code | 59.4 | 58.3 | 3.94 | 84.4 | 68.8 |
| GPT-6.1 Sol | Codex | 49.2 | 46.9 | 2.42 | 78.1 | 50.0 |
| GPT-6 Astra | Codex | 47.2 | 45.0 | 2.40 | 75.0 | 53.1 |
| Hy4-Preview | Claude Code | 45.2 | 42.9 | 2.31 | 71.9 | 50.0 |
| Hy4 | Claude Code | 45.0 | 42.9 | 2.41 | 75.0 | 46.9 |
| Kimi K3 | Claude Code | 42.5 | 42.0 | 2.47 | 68.8 | 40.6 |
| GPT-6.1 Terra | Codex | 37.9 | 36.7 | 1.92 | 75.0 | 25.0 |
| Hy3 | Claude Code | 25.5 | 23.2 | 1.76 | 37.5 | 28.1 |

(Seven further agents sit between 33.9 and 40.1.) Of 512 outcomes, 472 are correct and 346 also reach 1.25×; each agent is correct on 26 to 32 tasks. GPT-6.1 Terra is correct on all 32 yet scores below Kimi K3, correct on 28. On its 29 unflagged tasks Claude Opus 5.5 scores 65.6%; substituting Sonnet 5.5's runs on the three flagged tasks as a fallback gives 65.2%.

**What separates agents.** Paired task-bootstrap intervals put Sonnet 5.5 at least 13.4 points ahead of every non-Claude agent and Opus 5.5 0.1 to 18.2 points ahead of GPT-6.1 Sol; no two neighbors below them are separated (64 of 120 pairs exclude zero). Re-judging fixed programs moves Score@1 by about 1.5 points (SD), independent runs by 2.48 (GPT-6 Astra) and 4.42 (Hy4-Preview). Dropping the three authored workflows gives Kendall's τ_b = 0.95 with Table 1; also dropping HPCG-derived, 0.97.

**Baselines.** Unmodified programs measure 0.923× to 1.017× (median 0.999×). The configuration-only recipe exceeds 1.25× only on GROMACS (2.23×, switching SIMD from None to AVX2_256); using it as the reference lowers each agent's Score@1 by 0.5 to 2.4 points. The largest agent speedups are not configuration: GPT-6 Astra reaches 28.9× to 36.7× on HPCG-derived, where the operator admits a direct solver.

**Process findings (v1.0, five agents).** Computation or reuse changes appear in 225 of 476 labeled runs, parallelism or vectorization in 132, compiler and build tuning in 40. Same-model, same-task contrasts give +8.0 points of reward for computation or reuse changes (95% interval 1.4 to 15.9) and +8.9 for parallelism or vectorization (1.9 to 17.0). Runs with timing commands but no profiling beat runs without either by +4.4 points after adjusting for task and model (−4.0 to 12.8, not significant). In 31 version histories, 36 of 70 consecutive correct-candidate pairs are faster than their predecessor and 26 set a new best. One GROMACS source runs 0.289× to 2.123× under four build and runtime settings; in a QiboTN factorial replay deferred library loading is worth 1.01× alone and 6.3× to 6.4× once broader fast-simulator dispatch is on. Reviewers confirm a cross-layer dependency in 34 of 40 flagged and 15 of 40 unflagged trajectories, an estimated 72% of runs (63% to 80%), 52% (41% to 63%) for dependencies affecting an optimization.

**Limits on the evidence.**

* Speedups are relative to task-provided baselines of varying tuning, at single-node scale on one CPU platform (stated); a large speedup can reflect an untuned starting point or exploitable workload structure (the paper names HPCG-derived's direct solver).
* Rows compare model-plus-harness pairs, and harnesses differ (Codex vs Claude Code); reasoning effort settings are provider-specific (stated).
* One run per agent: the paper itself says single runs do not order agents a few points apart, which covers most of the table below the two Claude rows.
* The process analysis uses v1.0 and five lower-scoring agents, none of the v1.1 leaders, and the tool-call annotator (DeepSeek-V4.1-Flash) is also one of the five analyzed agents (reader observation).
* The Hugging Face organization for the paper is Tencent Hunyuan, and the Hy3, Hy4, and Hy4-Preview rows appear to be that organization's models; Hy4-Preview is one of the two agents given repeat runs. The text retrieved does not state the relationship (reader inference).
* In v1.0 Table 6, the reported run for Hy3 (9.76) and DeepSeek-V4-Flash (19.08) falls below all three of their round scores, because "reported" takes each task's median-reward run rather than one round (reader observation).
* The three Opus 5.5 zeros come from the evaluation gateway blocking the vendor's fallback model; the paper reports alternatives, but the headline ranking depends on that accounting choice.

# Q9 Contributions

1. A workload-defined optimization benchmark of 32 CPU tasks from scientific applications and supercomputing competitions, with public tests, private verification on held-out inputs, and stateful correctness checks validated by planned controls.
2. An evaluation of 16 agents showing correctness is nearly saturated while speedup size separates them, with explicit treatment of run-to-run variance, configuration-only baselines, and safety-classifier stops.
3. A process analysis and controlled replays showing that agents mostly change computation, rarely the build, and that gains depend on build settings, runtime settings, and other code changes.

# Q10 Next Steps

* **Stated by the paper.** Separate models from harnesses; measure sensitivity to hardware placement; evaluate other scales, hardware, and production environments.
* **Expert-tuned references.** An independently written reference is in Appendix G; scoring against expert-tuned programs on every task would show how much headroom remains beyond the supplied baselines (reader suggestion).
* **Process analysis for leaders.** Repeating the trajectory analysis on the v1.1 leaders would test whether their advantage comes from more build and runtime tuning or from better computation changes (reader suggestion).
* **GPU and multi-node tasks.** The benchmark is CPU and single-node; whether the cross-layer dependency findings carry over to GPU kernels and distributed runs is open.
