# Q1 Problem Definition

The paper asks how an agent can improve the entire **harness** around a fixed language model and then specialize that harness to each new case. The input is a labeled search set containing task instructions, visible case features, and reference outputs; the training output is a global harness plus a bank of execution experience. At evaluation time, the input contains only the new instruction and visible features, and the system must construct a case-specific harness without seeing the label, receiving feedback, updating weights, or running another search loop.

The optimization target is broader than a prompt. A harness controls context assembly, tools and retrieval, generation settings, multi-call orchestration, memory, and output processing. The desired result is therefore an executable control policy that improves task reward while using token cost only to break ties between equally correct candidates.

# Q2 Problem Novelty

Prompt optimization, declarative LM-program compilation, workflow search, textual feedback, and reflective memory already use execution signals to improve narrower artifacts. Meta-Harness is the closest cited work because it searches harness code end to end. MemoHarness's claimed novelty is the combination of three choices: structured editing across six harness dimensions, a dual-layer bank that preserves both individual executions and distilled cross-case patterns, and one-shot case adaptation at test time from a frozen bank.

The problem is important even if none of those ingredients is individually new. A single global harness is an average-case compromise: tasks differ in ambiguity, tool needs, reasoning depth, evidence requirements, and output format. MemoHarness makes the deployment-time control layer conditional on the case rather than forcing every case through the same prompt, tools, memory policy, and workflow.

# Q3 Scientific Hypothesis

The central hypothesis is: if harness search records verifier-grounded diagnoses instead of only scalar rewards, distils recurring failures into reusable patterns, and retrieves relevant successes and failures for each new input, then a fixed base model should outperform a static global harness without needing test-time labels or additional search.

Two secondary hypotheses follow. First, decomposing the harness into context, tool, generation, orchestration, memory, and output dimensions should make failures easier to attribute and repair than monolithic prompt search. Second, at least some learned control decisions should transfer across datasets and base-model families because they encode general execution policy rather than model-specific wording.

# Q4 Related Work and Key People

The paper places prior work in four layers:

* **Prompt and instruction optimization:** OPRO, ProTeGi, and Promptbreeder search instruction space, while Self-Refine and Reflexion use textual feedback or remembered reflections.
* **LM programs and compound systems:** DSPy/MIPRO and TextGrad optimize multi-stage language-model programs.
* **Agent workflow and harness search:** AutoFlow and AFlow search workflows; Meta-Harness treats harness code itself as the optimization object and is the closest conceptual predecessor.
* **Harness and interface engineering:** ReAct, Toolformer, SWE-agent, OpenHands, Terminal-Bench, Natural-Language Agent Harnesses, and practitioner work on context and harness engineering establish the surrounding control layer as a major determinant of behavior.

Yue Huang, Wenjie Wang, Han Bao, Xiaonan Luo, Haomin Zhuang, Zheyuan Liu, and Xiangliang Zhang are affiliated with the University of Notre Dame; Yuchen Ma with LMU Munich; and Yi Nian and Yue Zhao with the University of Southern California. Researchers in agent optimization, test-time adaptation, case-based reasoning, benchmark methodology, and software-agent infrastructure would likely focus on whether the experience bank—not merely global harness search—causes the gains, whether retrieval leaks task structure across splits, and whether the learned policy transfers beyond closely related executable benchmarks.

# Q5 Key Solution Idea

MemoHarness represents a harness as six editable control surfaces:

| Dimension | Control surface | Example edits |
|---|---|---|
| D1 | Context assembly | restructure instructions, add demonstrations, compress context |
| D2 | Tool interaction | enable retrieval, choose top-k, rerank evidence |
| D3 | Generation control | change token budget, temperature, or candidate count |
| D4 | Orchestration | move from one call to plan/execute/refine |
| D5 | Memory management | retain state, summarize traces, remove stale context |
| D6 | Output processing | extract answers, validate schemas, choose fallbacks |

Training starts from a deliberately minimal harness. In each of ten outer iterations, a controller retrieves a bounded slice of accumulated experience, edits the harness, executes it over the search cases, scores correctness, logs token cost, and diagnoses each outcome. A per-case entry records the case features, harness delta, trajectory, reward, cost, success/failure status, primary and secondary failure dimensions, and natural-language analysis. Periodic distillation converts recurring failure clusters into global patterns with supporting evidence and repair suggestions.

The final global harness is chosen lexicographically: maximize mean task reward first, then minimize tokens among reward ties. At test time, the bank is frozen. MemoHarness retrieves similar successful and failed cases plus feature-matched entries and global patterns, then applies a controller once to transform the global harness into a case-specific harness. The current test result does not trigger learning or iterative correction.

# Q6 Experiment Design

The evaluation covers three source tasks under GPT-5.3-Codex: Terminal-Bench for long-horizon shell agency, LiveCodeBench for single-shot code generation, and FinanceAgent for multi-step financial reasoning. The search runs for ten iterations from a minimal harness, with an 80/20 split and seed 42; generation is deterministic. The selected harness is chosen by validation rather than by taking the best held-out checkpoint.

The main results reported by the paper are:

| Benchmark | Base harness | Final MemoHarness | Absolute gain |
|---|---:|---:|---:|
| Terminal-Bench | 0.722 | 0.806 | +0.084 |
| LiveCodeBench | 0.900 | 0.967 | +0.067 |
| FinanceAgent | 0.600 | 0.767 | +0.167 |

Terminal-Bench uses an 18-task held-out split. MemoHarness's 0.806 mean exceeds the strongest compared baseline, Codex, at 0.722. FinanceAgent continues improving late in search and peaks at 65.0% around iterations 8–9 in the per-iteration analysis, whereas LiveCodeBench quickly saturates near the base-model ceiling.

For cross-dataset transfer, source-trained harnesses are evaluated on MMMLU, HumanEvalFix, StrongReject, Reasoning-Gym-Easy, LawBench, and SWE-Bench Pro. Transfer is selective: the Terminal-Bench harness improves MMMLU by 0.030, StrongReject by 0.030, and SWE-Bench Pro by 0.059; saturated suites do not move, and LawBench results depend on the source harness.

For cross-model transfer on Terminal-Bench, the GPT-5.3-Codex-derived harness improves all six additional models tested. The mean gain is 0.098, ranging from 0.038 for GPT-4.1 to 0.233 for GLM-5. The cost study reports 14.18M input tokens for MemoHarness, of which 13.32M are cached, producing a reported cost of $6.89 versus $10.28 for Codex under the paper's pricing assumptions.

# Q7 Datasets and Code

The benchmarks are Terminal-Bench, LiveCodeBench, and FinanceAgent for search and in-domain evaluation, plus six external suites for transfer. The primary Terminal-Bench result uses an 80/20 split of 89 tasks, giving 18 held-out tasks. The paper does not introduce a new standalone dataset or publish a separate experience-bank dataset.

The public Python repository contains configurations, scripts, the `memoharness` implementation, the dual-layer bank, controllers, Harbor/Daytona runtime integration, model and embedding utilities, and structured runtime bundles. Its documented setup requires Python 3.10+, Harbor and Daytona, and at least one model-provider key. Training and evaluation-only entry points are provided. The inspected sources do not establish a packaged release, archived raw trajectories, exact repeated-run outputs, or a turnkey artifact reproducing every table.

# Q8 Evidence Quality

The evidence is directionally consistent across three task families, six transfer suites, and six additional model families. Validation-selected rather than held-out-peak selection is a sound safeguard, and the paper reports selective or null transfer rather than portraying the learned harness as universally dominant. The correctness-first objective also prevents lower token use from compensating for wrong answers.

The causal and statistical evidence remains limited:

* The primary Terminal-Bench evaluation has only 18 held-out tasks and reports point estimates without confidence intervals or significance tests.
* The number of repeated runs behind the reported means is not specified in the inspected paper sections, limiting uncertainty analysis.
* Product-specific baselines do not all share the same base model and runtime surface, so some headline comparisons are system-level rather than controlled harness-only ablations.
* The paper does not separately ablate the global harness, per-case entries, distilled patterns, and test-time adaptation across all settings. It therefore cannot attribute the gain specifically to the dual-layer bank or case specialization.
* The diagnostic operator uses practical verifier-grounded heuristics and coarse dimension labels; the accuracy of those causal assignments is not independently evaluated.
* Cross-dataset transfer is small and selective, while two suites are saturated. Broader claims of generality need larger, less ceiling-limited suites.
* The favorable dollar cost depends on 13.32M of 14.18M input tokens being cacheable. A deployment with lower cache reuse may reverse the comparison.
* The operation-level analysis associates newly added shell commands with improving transitions, but these observational lifts do not establish that the commands caused the gains.

The paper therefore supports MemoHarness as a promising adaptive-harness prototype under a fixed protocol, not yet as a statistically robust or component-attributed general solution.

# Q9 Contributions

1. Defines harness optimization over six explicit, editable control surfaces rather than one prompt or opaque code artifact.
2. Introduces a typed dual-layer experience bank combining detailed execution entries with distilled global patterns.
3. Separates training-time global harness search from feedback-free, per-case test-time adaptation.
4. Uses correctness-first lexicographic selection so cost cannot trade against task reward.
5. Demonstrates in-domain gains on shell, code, and financial-reasoning tasks plus selective cross-dataset transfer.
6. Reports positive transfer of one learned terminal harness across six additional base models.
7. Provides a public implementation and a diagnostic record structure that makes harness edits and recurring failure patterns inspectable.

# Q10 Next Steps

The decisive experiment is a factorial ablation that compares: fixed base harness; global search only; per-case entries without global distillation; global patterns without nearest cases; successful versus failed retrieval; and full test-time adaptation. It should use larger held-out sets, preregistered metrics, confidence intervals, repeated seeds, per-task paired tests, and retrieval audits that rule out benchmark leakage.

The method also needs robustness tests for misleading or stale experience, out-of-distribution inputs, adversarially similar cases, contradictory global patterns, and long-running banks whose retrieval quality degrades. Cost should be reported under several cache-hit rates, and selection should eventually consider latency, safety, and robustness as explicit objectives rather than diagnostics only.

For this Research OS, the most reusable idea is the separation between **episode evidence** and **distilled patterns**. Task attempts, evaluator outputs, commands, failures, and artifact hashes can remain case-level records; only repeatedly supported lessons should enter durable project or skill guidance. A safe adaptation loop would retrieve both positive and negative precedents, propose a bounded run-specific workflow, preserve the global default as a fallback, and require held-out or human review before promoting the adaptation into the shared harness.
