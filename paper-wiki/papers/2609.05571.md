# Q1 Problem Definition

* **Input (X):** a source code unit (function, method, command-line entry point, or file-level component) plus its repository context, drawn from a pool of 19,769 GitHub repositories with more than 500 stars, available as of April 14, 2026.
* **Output (Y):** a typed, verified skill record — atomic operation, composite workflow, or recurring pattern — specifying applicability ("when to use"), execution steps, invariants, failure-handling anti-goals, and supporting source-span evidence with repository/file/symbol-level provenance; collectively, CodeSkillBank, a bank of 1,006,822 such accepted records with feature tags and purpose-indexed representative views for retrieval.
* **Core problem:** agentic systems need reusable procedural knowledge beyond what is encoded in model parameters, but the two existing skill-synthesis substrates each have a structural weakness — trajectory-based synthesis is coupled to the specific model, task distribution, tools, and harness that produced the trajectories, so quality is bounded by the generating agent's own competence; document-based synthesis avoids that coupling but lacks concrete executions to ground or verify the resulting skill. The paper asks whether source code — already executed, debugged, and repeatedly refined by humans (or, per RQ6, by tested AI coding) — can serve as a substrate that is both experience-independent and executable-evidence-grounded.
* **Scope:** skill *construction and retrieval* only — the underlying agent models and harness are held fixed; evaluation spans eight benchmarks (SWE-bench Verified, BigCodeBench, TerminalBench, LongCLI-Bench, AgentBench-OS, AIME 2026, HMMT 2025, GPQA) across five model families (DS4-Flash, Qwen3.5, Qwen3.6, Gemini 2.5 Pro, GPT 5.2) and one coding-RL setting (SWE-World); the retrieval pool used in most experiments is a random 10% sample of CodeSkillBank rather than the full bank, for computational efficiency.

# Q2 Problem Novelty

The paper does not claim to originate skill libraries, code representation learning, or reconstruction-based verification individually. It builds on trajectory-derived skill/memory systems (Reflexion, Self-Refine, ExpeL, Trace2Skill, SkillRL-adapted SkillBank) and document-derived synthesis (Liang et al. 2026's scheduling-structural-logical skill representation; Zhou et al. 2026), and cites code-representation methods (CodeBERT, GraphCodeBERT) and property-based/automated testing (EvoSuite, Pynguin, Hypothesis) as adjacent but distinct techniques it does not assume are available. The paper's most closely related prior work is Bi et al. (2026), which also mines open-source agent repositories but serializes retrieved skills as SKILL.md artifacts from *agent* repositories specifically. Code2Skill's stated differentiation is threefold: it operates over arbitrary procedural source units (not only agent-authored repositories), ranks them for reuse potential before extraction, and — its most load-bearing novelty claim — verifies each candidate through *source-body-blind reconstruction*: an LLM regenerates the implementation using only the synthesized record, and a source-aware judge compares that reconstruction against the original code, filtering unsupported or incomplete records rather than accepting extractor output on faith. This reconstruction-based check is explicitly framed as a scalable substitute for (not equivalent to) test-based verification, used because the pipeline does not assume executable tests or formal specifications are available for the mined code.

# Q3 Scientific Hypothesis

If reusable procedural skills are synthesized from large-scale, actively maintained source code — using a three-granularity typed schema (atomic/composite/recurring-pattern) to match the scope of the original implementation, and admitting only records whose reconstruction-based consistency check passes — then the resulting skill bank should (a) improve agent performance across model families and task domains without collecting any task-specific trajectories, (b) outperform trajectory-derived skill banks under an identical downstream interface, and (c) continue to scale as AI-generated code becomes a growing fraction of available implementations. The paper's own evidence: CodeSkillBank improves 57 of 72 protocol-matched evaluations (macro-average 42.90→47.90, +11.7% relative; Table 1); under a shared agentic loop, Code2Skill outperforms Trace2Skill, ExpeL, and SkillRL-Bank on all seven shared benchmarks, beating even an oracle that takes each baseline's best per-benchmark result by 9.5 points on average (Table 2); and skills extracted from tested AI-generated implementations reach a 93.50% LiveCodeBench pass rate versus 93.00% for human-code-derived skills (Sec. 5.7).

# Q5 Key Solution Idea

1. **Repository-scale candidate selection (Sec. 3.2.1).** Code2Skill scans GitHub repositories available as of April 14, 2026, retains those with more than 500 stars (19,769 repositories), then parses functions, methods, CLI entry points, and file-level components within each and uses an LLM tagger to select units exhibiting reusable intent, operational structure, and visible execution constraints — rejecting trivial, project-local, and unsupported code before extraction is attempted.
2. **Three-granularity typed skill records (Sec. 3.2.2).** Atomic skills capture a single well-defined operation within one function/method; composite skills capture ordered multi-operation workflows; recurring-pattern skills capture higher-level implementations beyond a single operation or workflow. Each record separates operational guidance (when to use, control rule, workflow steps) from execution constraints (invariants, failures, anti-goals) and retains source-span provenance, illustrated by a worked example (Figure 2: a DNS-over-QUIC connection-recovery workflow from AdGuard's dnsproxy).
3. **Source-body-blind reconstruction and consistency checking (Sec. 3.2.3).** A reconstructor LLM regenerates code using *only* the synthesized record (not the original source), exposing mismatches in steps, invariants, or failure handling when compared against the actual implementation. A source-aware judge directly accepts sufficiently consistent reconstructions and routes the rest to an adjudicator that distinguishes an unsupported skill record from a reconstruction-process failure; accepted records retain their acceptance status, rationale, and full provenance chain for later inspection or source-aware refresh.
4. **Retrieval-oriented feature tagging and purpose indexing (Sec. 3.2.4).** Feature tagging builds a task-oriented retrieval view for every accepted record while preserving a one-to-one correspondence with the evidence archive; purpose indexing separately filters low-value candidates and groups near-duplicate records by purpose, selecting one representative per cluster — both transformations leave the underlying evidence archive intact.
5. **A unified downstream utilization interface (Sec. 4.2, Eq. 1).** At decision step *t*, if the interface issues a retrieval query *q_t*, it renders the top-*k* matches from the bank and concatenates them into the recipient's usual policy or model call (generation, planning, review, verifier judgment, or RL training signal); the no-skill comparator is the identical protocol with an empty context, making every reported comparison protocol-matched by construction.

# Q6 Experiment Design

**RQ1 — does the bank improve agent performance (Sec. 5.2, Table 1)?** Nine model/reasoning-mode configurations (DS4-Flash, Qwen3.5-27B, Qwen3.6-27B, Gemini 2.5 Pro, GPT 5.2, several with and without an explicit reasoning mode) are each compared with vs. without post-generation-review access to a 10%-sampled CodeSkillBank retrieval pool, across all eight benchmarks, holding model, reasoning mode, benchmark task set, evaluator, and default agentic loop fixed.

**RQ2 — comparison with trajectory-derived banks (Sec. 5.3, Table 2).** Code2Skill is compared against re-implemented Trace2Skill (Creation+Error pipeline), ExpeL (experience memory), and a SkillRL-adapted SkillBank, all built on a held-out task split with Qwen3.5-397B-A17B, then evaluated with DS4-Flash through the identical downstream interface and agent loop (mean ± std over five runs, seven shared benchmarks) — isolating skill-source quality from loop design, since all four banks are queried through the same Eq. 1 interface.

**RQ3 — where skills should enter the workflow (Sec. 5.4, Figures 4–5, Table 1).** Three integration points are compared: generation-time prompting (skills appended to the first-pass prompt, review/revision removed), planning-time guidance (skills supplied while the agent plans), and post-generation critique (skills revealed only during review/revision, the RQ1 default) — each compared against its own matched no-skill control rather than against each other directly.

**RQ4 — retrieval depth and context efficiency (Sec. 5.5, Figure 6).** On BigCodeBench Instruct-Hard with DS4-Flash and Qwen3.5, retrieval depth k∈{1,3,10}, full-record vs. summary rendering, and accepted-records vs. purpose-indexed-representative retrieval are varied independently, holding the rest of the protocol fixed.

**RQ5 — integration in coding RL (Sec. 5.6, Table 3).** Starting from the same Qwen3-32B SWE-World checkpoint and coding-RL protocol (Sun et al. 2026b), CodeSkillBank is exposed at four different stages (full-prompt, summary-prompt, reward-side reference to the verifier only, post-generation review) against a no-skill control, all evaluated at the shared training step 150.

**RQ6 — skill scaling from AI-generated code (Sec. 5.7, Figure 7).** 25 tested human implementations from CodeSkillBank's accepted archive are paired with GPT-5.1-generated, interface-matched, equally-tested AI implementations (Codex, extra-high reasoning effort); origin labels are withheld from the extractor, each source yields a 50-skill bank, and both banks are evaluated on a 400-task LiveCodeBench subset with identical top-k=4 retrieval slots matched by functional pair, skill type, and rank.

**Design strength for the hypothesis.** RQ1's 72-cell sweep and RQ2's shared-interface comparison are the paper's two strongest pieces of evidence, because RQ2 specifically rules out the alternative explanation that RQ1's gains come from the agent loop itself rather than from code-derived skill *content* — a genuine ablation of the substrate holding the interface fixed. RQ5 is explicitly caveated by the paper itself as a single-checkpoint, single-seed result ("does not establish differences in learning speed, convergence, or final policy performance"), so its 14-point post-generation-review gain should be read as preliminary compatibility evidence, not a controlled RL comparison. RQ6's 0.50-percentage-point aggregate gap between human- and AI-code banks is explicitly not claimed as equivalence by the paper — the 16 task-level disagreements (7 human-only, 9 AI-only) are the more informative result, showing the two sources are complementary rather than interchangeable despite similar aggregate scores.

# Q7 Datasets and Code

CodeSkillBank itself is the paper's primary released artifact: 1,006,822 accepted skill records mined from 19,769 GitHub repositories (≥500 stars, available as of April 14, 2026), released via the project's "Dataset" link (per the arXiv HTML header) and GitHub repository (github.com/ant-intl/Code2Skill, 31 stars at fetch time). Evaluation uses eight pre-existing external benchmarks (BigCodeBench, SWE-bench Verified, TerminalBench, LongCLI-Bench, AgentBench-OS, AIME 2026, HMMT 2025, GPQA) plus a 400-task LiveCodeBench subset for the RQ6 provenance study — none released by this paper. Baseline skill-synthesis systems compared in RQ2 (Trace2Skill, ExpeL, SkillRL-adapted SkillBank) are re-implemented by the authors from their respective papers rather than run via the original authors' code, per the "implementing" language in Sec. 5.3. Human-annotation statistics for skill-description accuracy, reconstruction correctness, and retention value are reported in Appendix B but the underlying annotation protocol and inter-annotator agreement details were not read in full for this note (only the Sec. 4.1 summary: 92% description accuracy, 80% retention value, 84% correct reconstruction among directly accepted records, versus 32%/28%/0% for the rejected sample).

# Q9 Contributions

1. Code2Skill, a fully automated four-stage pipeline (candidate selection, typed record generation, source-body-blind reconstruction verification, retrieval-oriented indexing) that synthesizes grounded, verifiable skills directly from source code at repository scale, without requiring agent trajectories or prior task experience.
2. CodeSkillBank, a released bank of 1,006,822 accepted skill records mined from 19,769 actively maintained GitHub repositories, with workflow, boundary, provenance, and source-evidence metadata attached to every record for inspection, refresh, or deprecation as source evolves.
3. Evidence that code-derived skills provide a genuinely complementary substrate to trajectory-derived skills, not merely a redundant one: under an identical downstream interface, Code2Skill outperforms Trace2Skill, ExpeL, and SkillRL-Bank on all seven shared benchmarks by 6.6–13.3 points over the strongest baseline per benchmark, and beats even a per-benchmark oracle over those three baselines by 9.5 points on average.
4. A working utilization interface (Eq. 1) validated across five distinct integration points — generation-time, planning-time, post-generation review, reward-side RL reference, and policy-side RL prompting — plus initial evidence (RQ6) that the same pipeline continues to extract useful, non-redundant procedural knowledge from tested AI-generated code, suggesting CodeSkillBank can keep expanding as AI-authored software becomes more prevalent.

# Q10 Next Steps

The retrieved Conclusion does not enumerate a separate, explicitly labeled Limitations section in the main text (none was located by section heading in this fetch), so the following synthesizes evidence boundaries the paper itself states inline rather than a dedicated limitations list. The authors' own stated future direction (Sec. 5.7 insights) is that "tested implementations can therefore be reused by later agents, allowing CodeSkillBank to expand as new code appears" — framed as an ongoing-expansion premise rather than a settled result, since RQ6 tests only 25 matched pairs.

Beyond the paper's own text, three points are worth flagging for a reader assessing this note's evidence. First, the reconstruction-based verification step is explicitly described as a *substitute* for test-based verification when tests are unavailable, not validated *against* test-based verification on a shared sample — so the paper does not report how often reconstruction-based acceptance agrees or disagrees with an executable-test oracle on the same code units, which would be the more direct grounding check. Second, all baseline comparisons in RQ1–RQ2 use a random 10% sample of CodeSkillBank rather than the full 1,006,822-record bank; the paper does not report whether results scale, saturate, or degrade (e.g., from retrieval noise) as the sampled pool size increases toward the full bank. Third, RQ2's baselines (Trace2Skill, ExpeL, SkillRL-Bank) are the authors' own re-implementations built on a held-out split with one fixed backbone (Qwen3.5-397B-A17B) rather than each method's original published configuration, so the comparison's fairness depends on how faithfully those re-implementations match the original systems' intended designs — a reproduction-fidelity question this note cannot independently verify from the retrieved text.
