# Q1 Problem Definition

* **Input (X):** a target domain (a benchmark and execution harness), an initial skill `s` (a natural-language policy document), and a frozen target model `M` whose weights are never updated.
* **Output (Y):** an optimized, exported `best_skill.md` — a compact (roughly 300–2,000 token) natural-language policy — selected via held-out validation from candidate skills produced during training.
* **Core problem:** when domain adaptation for frozen frontier agents happens through natural-language skill documents rather than model weights, how should that skill document itself be optimized, with training-style controls over evidence, step size, validation, and update direction, rather than through one-shot writing or unconstrained rewriting?
* **Scope:** optimizes exactly one persistent skill artifact per domain; the target model's weights, the execution harness, and the evaluator all stay fixed throughout.

# Q2 Problem Novelty

Skill packaging (the Agent Skills standard) and skill construction/evolution (SkillFoundry, EvoSkill, AutoSkill, Trace2Skill, SkillX) are established, as is prompt optimization (TextGrad, GEPA, ABSTRAL, EvoTest). The paper's novelty is applying an explicit deep-learning training analogy — rollout and reflection batch sizes as evidence volume, a bounded textual learning rate with schedules as step size, a held-out gate as validation, a rejected-edit buffer as negative feedback, and an epoch-wise slow/meta update as a momentum term — specifically to one persistent, harness-agnostic skill document, rather than to full prompts, system designs, or growing skill libraries. The authors position this as, to their knowledge, the first systematic study of skill optimization as a domain-adaptation training method for frontier agents.

# Q3 Scientific Hypothesis

If skill editing is treated as a controllable domain-adaptation process — an external skill-document state, a separate frontier optimizer model, and training-style controls over evidence (rollout/reflection batch size), step size (a bounded textual learning rate and schedule), validation (a held-out acceptance gate), and update memory (a rejected-edit buffer and epoch-wise slow/meta update) — then the resulting compact skill artifact outperforms no-skill, human-written, one-shot LLM, trajectory-distillation (Trace2Skill), prompt-optimization (TextGrad, GEPA), and skill-evolution (EvoSkill) baselines, and transfers across models, harnesses, and related benchmarks without touching model weights. The paper tests this across 52 (model, benchmark, harness) comparison cells plus component ablations and transfer experiments; it does not test whether the learned rules reflect general procedural knowledge beyond the evaluated benchmark families, nor open-ended or subjectively-judged tasks without automatic scoring.

# Q4 Related Work and Key People

* **Prompt auto-tuning and agent-configuration search:** GEPA (reflective prompt evolution outperforms RL on several agent tasks); ABSTRAL and EvoTest extend this to multi-agent design documents and full agentic-system evolution. SkillOpt differs by optimizing a persistent, exportable, reusable skill document rather than a prompt or full configuration.
* **Skill construction and evolution:** SkillsBench and a SoK on agentic skills frame skills as reusable procedural knowledge; AutoSkill, Trace2Skill, SkillX, SkillFoundry, and Memp build such skills from experience, trajectories, or heterogeneous resources; EvoSkill, SkillForge, EvoSkills, SkillClaw, SkillRL, RL-for-skill-libraries, AutoRefine, ProcMEM, and Evolver further refine skills via failure analysis, co-evolution, collective updates, or reinforcement learning. SkillOpt studies a narrower problem — training one compact domain skill with deep-learning-style controls — rather than discovery, library growth, sharing, or policy optimization.
* **Foundational agent work cited for motivation:** ReAct, Toolformer, Voyager, SWE-agent (harness-agnostic tool-use deployment); Reflexion, Self-Refine (trajectory-driven reflection underlying the backward pass).

# Q5 Key Solution Idea

A per-step optimization loop, run by a separate optimizer model against one frozen target model `M`:

1. **Forward pass (rollout evidence).** `M` runs a rollout batch (default 40 tasks) from the training split with the current skill; the harness records full trajectories — messages, tool calls, observations, outputs, and verifier feedback.
2. **Backward pass (minibatch reflection).** The optimizer model separates successes from failures and partitions each into reflection minibatches (default size 8, with 16 parallel analyst workers), proposing structured add/delete/replace edits (or, in rewrite mode, full-rewrite suggestions). Local proposals are merged hierarchically, with failure-driven corrections prioritized and duplicate/contradictory/example-specific suggestions filtered out.
3. **Bounded text update.** The merged edit pool is ranked by expected utility and clipped to a textual learning rate `L_t` (default 4, cosine-decayed to a floor of 2; constant, linear, and autonomous schedules are also supported) — the key departure from unbounded prompt rewriting, which can erase useful rules or overfit to a single failure.
4. **Validation gate and rejected-edit buffer.** Each candidate skill is scored on a held-out selection split with the same frozen model and harness; it is accepted only if it strictly improves on the current selection score (ties are rejected), and becomes `best_skill.md` only if it also beats the best score so far. Rejected edits, and the score drop they caused, are logged in an epoch-local buffer and fed back into later reflection calls as negative feedback at no extra inference cost.
5. **Epoch-wise slow/meta update.** At the end of each epoch, the same training items are sampled under the previous- and current-epoch skill, grouped into improvements/regressions/persistent failures/stable successes, and a longitudinal-guidance block is written into a protected region of the skill document that step-level edits cannot overwrite — this candidate still passes through the same validation gate. A separate, optimizer-only "meta skill" (never shipped to the target model) summarizes which edit patterns helped or were rejected across epochs and is prepended to future optimizer prompts.
6. **Harness-agnostic deployment.** A lightweight `AgentAdapter` constructs batches, injects the current skill into the agent's context, and runs the native harness (direct chat, Codex CLI, or Claude Code CLI), returning scored trajectories. The same `best_skill.md` file format works across all three modes, which is what enables the paper's cross-harness transfer experiments.

# Q6 Experiment Design

Six benchmarks (SearchQA, SpreadsheetBench, OfficeQA, DocVQA, LiveMathematicianBench, ALFWorld) × seven target models (GPT-5.5, GPT-5.4, GPT-5.4-mini, GPT-5.4-nano, GPT-5.2, Qwen3.5-4B, Qwen3.6-35B-A3B) in direct chat, plus GPT-5.5 under Codex CLI and Claude Code harnesses (five benchmarks each — ALFWorld is excluded because it requires persistent embodied-environment interaction) — 52 (model, benchmark, harness) cells in total. Seven baselines per cell: no skill, human-written skill, one-shot LLM skill, Trace2Skill, TextGrad, GEPA, and EvoSkill (the harness-side competitor). Deterministic train/selection/test splits (seed 42, default 2:1:7 or 4:1:5 in ablation sweeps); the selection split is used only to accept or reject candidate edits, and every headline number is computed on the held-out test split. Default hyperparameters: 4 epochs, rollout batch 40, reflection minibatch 8 with 16 parallel workers, `L_t=4` with cosine decay to a floor of 2, a strict held-out gate, slow update sampling 20 tasks per epoch, patch edit mode, and an optional rejected-edit buffer. Ablations sweep training-set fraction, mini-batch and rollout-batch size, learning-rate value (1/2/4/8/16), schedule (constant/cosine/linear), slow-update sample count, and remove the rejected buffer or the meta-skill-plus-slow-update mechanism. Transfer experiments test cross-model (skill trained on one model size, deployed on another), cross-harness (Codex ↔ Claude Code), and cross-benchmark (OlympiadBench → Omni-MATH) generalization. A separate optimizer-strength ablation compares a strong frontier optimizer (GPT-5.5) against a target-matched optimizer of the same scale as the deployed model.

# Q8 Evidence Quality

The empirical breadth is strong: 52/52 cells best-or-tied against seven baseline families (no-skill, human, one-shot LLM, trajectory-distillation, two prompt optimizers, one skill-evolution harness competitor) is an unusually clean sweep, and the ablations isolate which components drive the gains — the largest single degradation in the ablation suite (-22.5 points on SpreadsheetBench) comes from removing both the meta-skill and slow update together. Cross-model, cross-harness, and cross-benchmark transfer results are uniformly positive (no row falls below the target's no-skill baseline), strengthening the reusability claim. Caveats: baseline comparisons (TextGrad, GEPA, Trace2Skill, EvoSkill) are the paper's own re-implementations rather than each method's original released code and hyperparameters, so relative baseline strength depends on that re-implementation fidelity; all six benchmarks use automatic exact-match or hard-success scoring, so the method's behavior on open-ended, subjectively-judged tasks is untested and explicitly flagged as a limitation; optimizer cost is substantial for some benchmarks (up to 46.4M training tokens per absolute test-point gain on DocVQA), though this cost is paid once during offline training and adds nothing at deployment.

# Q9 Contributions

1. Formulates agent-skill learning as optimization over an external natural-language state and introduces SkillOpt: rollout batches, reflection minibatches, add/delete/replace edits, textual learning rates and schedules, a held-out acceptance gate, a rejected-edit buffer, and an epoch-wise slow/meta update.
2. A broad empirical study — six benchmarks, seven target models, three execution harnesses — showing SkillOpt is best or tied-best on 52 of 52 cells, with an average GPT-5.5 gain of +23.5 points (direct chat), +24.8 (Codex), and +19.1 (Claude Code) over no skill.
3. Component ablations plus three transfer studies (cross-model, cross-harness, cross-benchmark) showing the exported `best_skill.md` — built from only 1–4 accepted edits and 300–2,000 tokens long — is compact, interpretable, and reusable without model-weight updates.

# Q10 Next Steps

* The paper's own limitations (Appendix B): the loop needs automatic verifiers, exact-match metrics, or otherwise reliable feedback signals, so open-ended or subjectively-judged domains need stronger human or model-based evaluation for the gate; training costs additional rollout computation and optimizer-model calls, amortized only when the skill is reused; the design deliberately optimizes one portable skill rather than growing a library or changing weights, which may be insufficient for highly heterogeneous domains needing many disjoint procedures; optimized skills can encode training-distribution-specific heuristics, so careful held-out evaluation remains necessary before transfer to substantially different models, harnesses, or tasks.
* The paper's own outlook: skill libraries that share infrastructure across domains; reuse of optimizer-side meta skills across benchmarks; reward-free or preference-driven validation gates for open-ended tasks; self-distillation of optimized skills back into the target model as a step toward weight-level adaptation.
* **Research-OS fit:** the held-out validation gate, rejected-edit buffer, and protected slow/meta-update region form a pattern directly comparable to this repository's own skill-authoring and memory-update conventions (merge-before-append, evidence thresholds in `human-cognition-cache`) — worth comparing if this repository ever automates skill-file tuning from execution logs rather than hand-editing `SKILL.md` files.
