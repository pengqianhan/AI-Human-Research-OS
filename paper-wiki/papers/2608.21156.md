# TL;DR

Prompt, Context, Harness, and Loop Engineering have pushed a single LLM agent's "Individual Intelligence" about as far as one agent loop can go; this survey argues the next frontier — "System Intelligence," multiple specialized agents coordinated into a coherent, adaptive whole — needs graph structures as its organizational substrate, and proposes Graph Engineering as that structural foundation across three coupled views: Task Organization, Agent Coordination, and Runtime State Management.

# Overview

The paper opens from a compact equation — `Agent = Loop(LLM + Harness)` — and uses it to narrate a three-stage progression it treats as the field's actual historical arc, not just an organizing device. Pre-training and post-training build parameter-level capability (Model Intelligence); Prompt and Context Engineering elicit and condition that capability at inference time without touching parameters; Harness Engineering then extends what a model can persistently access (tools, memory, skills, execution environments) while Loop Engineering organizes repeated use of those extensions into a bounded, feedback-driven process — together yielding Individual Intelligence, one agent's capacity for sustained, goal-directed execution. The paper's central claim is that Individual Intelligence has a hard ceiling: real tasks often need parallel and interdependent work, specialized and independently-verified expertise, and persistent recoverable state, none of which a single execution loop can structurally provide no matter how capable the underlying model or how rich its harness becomes. Graph Engineering is introduced as the paradigm for the resulting next stage, System Intelligence, and the survey organizes its literature review, benchmark/dataset catalogue (Section 7), open-source library survey (Section 8), and cross-domain application review (Section 9) all around this same three-tier Model/Individual/System Intelligence framework, plus a proposed further layer (Ontology Engineering, Section 6) for giving that graph structure shared, machine-interpretable meaning. The authors maintain a companion resource list at github.com/DEEP-JLU/Awesome-Graph-Engineering (led by a 35-person, largely China-based multi-university author team with a corresponding author at Jilin University).

# Framework

The survey's organizing move is formal before it is taxonomic. An **Individual Agent** is defined as 𝒜ᵢ = Loop(ℱᵢ, ℋᵢ, sᵢᵗ) — a Foundation Model, a Harness, and runtime state, animated by a Loop. An **Agent System** extends this to 𝒮ᵗ = (𝔸ᵗ, ℛᵗ, ℰᵗ, 𝚷ᵗ, 𝐱ᵗ): an Agent Team, Shared Resources, an Environment, Coordination Mechanisms, and System State. The paper then argues Individual Intelligence fails at complex tasks for three specific structural reasons, each illustrated with a worked example: (1) it **serializes parallel/interdependent subtasks** into one execution trace (e.g., log analysis, failure reproduction, and code inspection could run as independent branches in fault diagnosis, but a single loop forces them sequential, propagating wrong intermediate results downstream and making the faulty stage hard to localize); (2) it **cannot cleanly separate specialized roles or independent verification** within one control loop (e.g., an agent that both writes and evaluates its own code risks mistaking its own judgment for evidence of correctness, "role confusion and confirmation bias"); (3) it **has no organized, persistent state**, so an early error can silently propagate through many later steps before surfacing as failure, by which point its origin is hard to trace.

Graph Engineering answers these three failures with three coupled graph views, each addressing one organizational question:

| View | Question | Sub-mechanisms |
|---|---|---|
| Task Organization | What to do | Goal Decomposition (subgoal/dependency graphs) → Workflow Optimization (executable-operator graphs, searched and increasingly execution-adaptive) |
| Agent Coordination | Who works | Agent Capability Modeling → Agent Team Organization (chain / routing / fan-out-fan-in / dynamic topologies) → Multi-agent Communication (runtime information exchange, separate from stable team structure) |
| Runtime State Management | How the system operates | State Recording (structured, governed, scoped, consistent) → Fault Localization (hypothesis-evidence tracing) → Failure Recovery (selective repair + compensation for external effects) |

A fourth, cross-cutting dimension, **System Evolution**, distinguishes one-off runtime adaptation (routing, worker reassignment, recovery within one execution) from *persistent* structural change carried into future runs — task decomposition, team topology, communication patterns, and accumulated state-derived experience can all evolve, but the paper insists this only counts as genuine evolution when changes are validated and can be committed or rolled back, not merely applied once. Section 5 extends the framework three research directions further (graph-native capability substrates unifying memory/skill/tool graphs with task/agent/state graphs; self-evolving graph systems that coordinate cross-graph structural change under governance; graph-native agent operating systems providing scheduling, provenance, and rollback as shared infrastructure, explicitly modeled on AIOS's kernel-style separation of concerns). Section 6 adds a final, explicitly-scoped layer: **Ontology Engineering**, a shared, machine-interpretable model of goals, agents, capabilities, evidence, policies, states, and outcomes, framed as necessary because "explicit graph structures alone do not ensure that system entities and relations are defined consistently" — the paper is careful to present this as a semantic foundation *connecting* Graph Engineering to broader System Intelligence, not a competing or complete solution to it.

# Key Techniques

* **Workflow-as-optimizable-graph (Task Organization).** GPTSwarm represents an entire language-agent system as a computational graph and optimizes both node behavior and inter-agent edges; AFlow instead searches executable workflow code directly via LLM-guided search, treating the workflow's own structure as the optimization object; ADAS automates workflow design more broadly by searching over code-defined workflows. Later work makes this execution-adaptive rather than fixed-before-runtime: DyFlow generates and adjusts operator subgraphs from intermediate feedback mid-execution, EvoFlow maintains and evolves diverse workflow candidates concurrently as competing hypotheses, and QualityFlow uses intermediate quality checks to decide whether to accept, debug, clarify, or roll back a program-synthesis workflow in flight.
* **Team-topology patterns (Agent Coordination).** The survey classifies existing multi-agent systems into four topology families: chain (MetaGPT's SOP-governed assembly line; ChatDev's sequential design→code→test chat chain), routing (Magentic-One's orchestrator that plans, delegates, monitors, and replans; WorkTeam's supervisor invoking specialized orchestrator/filler agents), fan-out/fan-in (Mixture-of-Agents' layered parallel-generate-then-integrate structure; MacNet's DAG generalization allowing multiple paths to converge downstream), and dynamic (Puppeteer selecting and sequencing agents by current task state; AgentNet removing the central controller entirely so agents route work by local expertise; SwarmAgentic jointly optimizing agent functions and collaboration patterns).
* **Structured runtime state (Runtime State Management).** Magentic-One externalizes shared execution progress through orchestrator-maintained Task and Progress Ledgers; "Graph of States" organizes structured belief states with causal graphs and explicit state-machine transitions. PatchBoard validates agent-generated patches against schemas, role permissions, and runtime invariants before committing them, and MemTX distinguishes tentative writes from transactional belief commits with explicit provenance and repair semantics — together motivating what the survey calls an explicit proposal-validation-commit boundary between observed/proposed change and authoritative state. MAGE represents execution as paths through a hierarchical state tree, letting erroneous branches and nearby valid decision boundaries be identified directly from that structure for both fault localization and selective repair.
* **Failure attribution and recovery.** "Who & When" attributes failures to both the responsible agent and the causal step; MAST distinguishes system-design, inter-agent-coordination, and task-verification failure classes; TraceElephant argues diagnosis needs full execution traces and intermediate context, not just final outputs. For recovery, event-sourced designs, AgentGit, and Shepherd enable replay, rollback, and branching over recorded execution states, while DART constrains restoration to semantically valid boundaries under downstream dependencies; SagaLLM, RAC, and Atomix specifically address effects that cannot be rolled back directly (external side effects) via checkpoint-plus-compensation rather than pure state restoration.
* **System Evolution mechanisms.** TDAG dynamically decomposes tasks and spawns specialized agents mid-execution; SwarmAgentic and AgentNet evolve team structure via feedback-guided population search and decentralized local reconfiguration respectively; ReCreate derives reusable domain patterns from analyzing success/failure in interaction histories, and SkillGraph distills failures into an evolving Skill Bank — but the survey pairs these accumulation mechanisms with a governance counterweight (MemTX's cascading repair when a committed belief is retracted; ActiveGraph's event-sourced replay/forking) to argue that evolution without validation and rollback is not yet trustworthy structural change.

# Case Studies

**Application Domains.** Software engineering shows the clearest Individual-to-System-Intelligence transition already in production: MetaGPT/ChatDev's predefined-stage teams gave way to SWE-agent's repository-interface-shapes-behavior insight, OpenHands' persistent multi-tool event stream, and now Codex's isolated-worktree concurrent agents and Claude Code's subagents/checkpoints/hooks/agent-teams — the survey's own framing is that coding tools moved from managing one trajectory to managing concurrent branches, dependencies, and merge decisions. Scientific discovery (SciAgents' ontology-grounded coordination, AI Scientist's long-running ideation-to-review pipeline, Virtual Lab's PI-plus-specialist-scientist team linked to physical validation, Co-Scientist's generate-critique-rank-refine loop, Robin's literature-plus-lab-result feedback) increasingly closes the loop between hypothesis and evidence, but the survey cautions this iterative refinement should not be mistaken for persistent evolution of the *agent organization itself*. Healthcare (MAC's multi-doctor consultation, DeepRare's central-host-plus-specialist-agent diagnostic architecture, AMIE's dialogue-plus-management-reasoning split across multiple visits) illustrates why runtime state there is more than conversational memory — prior symptoms and treatments change the validity of later actions, and graph organization alone does not establish clinical correctness. Enterprise workflows (WorkTeam, SOAN's hierarchical reusable-workflow-as-agent encapsulation, Gemini Enterprise Agentic RAG's orchestration-plus-sufficiency-checking retrieval) foreground permissions, transaction boundaries, and rollback obligations as concrete structural requirements rather than abstractions. General-purpose digital agents (OpenClaw's gateway maintaining separate identities/workspaces/sessions across channels; Hermes Agent's cross-session skills and scheduled execution) represent persistent computational entities rather than single-task instantiations, but the survey notes their cross-run adaptation still falls short of general structural self-evolution. Social/economic simulation (AgentSociety, EconAgent, SRAP-Agent, TwinMarket) inverts the usual relationship — the graph is part of the phenomenon under study, not just an execution mechanism — and the survey flags a real epistemic risk: emergent simulated behavior depends heavily on model choice, persona construction, and interaction topology, and should not be read as evidence of real-world causality without calibration.

**Cross-Domain Findings (the survey's own synthesis, Section 9.7).** Work Organization and Agent Team Engineering are already common practice across domains; explicit Runtime State Management is becoming visible (checkpoints, longitudinal records, event streams); but persistent System Evolution "remains rare" — most systems adapt execution within a predefined organizational structure rather than durably revising that structure from accumulated evidence. The survey draws a sharpened distinction from this evidence: contemporary systems are increasingly **graph-structured** (they execute through explicit work/team/state graphs) without yet being **graph-engineered** (those graphs are still usually selected manually or fixed before execution, not made structural objectives with observability, controlled mutation, and evidence that changes persist and transfer across tasks and time).

# Evidence Boundaries

This is a survey, not an empirical paper: it runs no new experiments, and its central claims (the Model/Individual/System Intelligence progression, the three-graph-view taxonomy, the graph-structured/graph-engineered distinction) are the authors' own conceptual synthesis overlaid on several hundred cited works, not something independently benchmarked by this paper or, per its own Section 6.1, benchmarkable yet by any existing evaluation resource — the paper is explicit that "end-task success alone is insufficient to determine whether a system has developed System Intelligence," since gains could come from a stronger base model, more context, or more compute rather than better organization, and no current benchmark cleanly separates these. This note is built from the arXiv HTML full text of the Introduction, Preliminaries, Sections 3–6 (the conceptual core) read in full, plus the prose synthesis of Sections 7.1–7.4, 8.1–8.4, and 9.1–9.7 (evaluation-resource, library, and application summaries); it does **not** reflect a row-by-row reading of the paper's large benchmark/dataset/environment table (Section 7, roughly 800 lines of reference-table markdown) or its open-source-library table (Section 8), so specific named entries in those tables beyond what the prose summaries mention are not independently verified here. Every named technique in this note (GPTSwarm, AFlow, MAGE, MemTX, and the rest) is a claim about what *this survey* says the cited paper does, filtered through the survey's own summarization — this note has not gone back to any of those ~300 individually cited original papers to verify the survey's characterization of them, so treat each named method here as one layer of summary on top of the survey's own summary of the source. The paper itself is a recent (submitted 2026-08-21, arXiv v1) multi-institution community survey with a companion GitHub resource list (50 stars per HF metadata at the time of this note) rather than a peer-reviewed venue publication with an established citation record.

# Takeaways

* The **graph-structured vs. graph-engineered** distinction (Section 9.7) is a genuinely useful evaluative lens beyond this one paper: it gives a concrete question — "is this system's coordination structure a fixed design-time choice, or a structural objective with observability, controlled mutation, and evidence of persistence across runs?" — for judging whether a new multi-agent paper entering this wiki's [Multi-agent systems](../topics/multi-agent-systems.md) topic represents a durable structural advance or another manually-selected topology dressed as one.
* The paper's **System Evolution** framing (persistent, validated, rollback-able structural change vs. one-off runtime adaptation) is a vocabulary upgrade worth carrying into how this wiki's [Agent self-evolution](../topics/agent-self-evolution.md) topic already discusses skill- and harness-level update loops (SkillOpt's validation gate, MemoHarness's frozen test-time bank) — the same validated-vs-unvalidated-change question this survey raises at the task/team/state-graph level is exactly the question those papers already ask at the skill/harness level, one layer down.
* Section 6.1's warning — that end-task success alone cannot distinguish genuine "System Intelligence" from a stronger model or more compute — is directly relevant to how this repository should evaluate any future multi-agent research-automation tooling it builds or adopts: a win on a benchmark is not evidence that the *coordination structure* did the work unless the evaluation is designed (matched compute budgets, structural ablations, intervention studies) to isolate that specifically, which the survey itself says current resources rarely do.

# Open Questions

* **Graph-native capability substrates** (Section 5.1): memory, skill, and tool repositories are still largely independent collections rather than graph-connected to task/agent/state graphs — what does it take to make capability selection (dependency, substitution, composition, permission, applicability) a structural, queryable operation rather than an implicit runtime decision?
* **Self-evolving graph systems** (Section 5.2): how should a system distinguish one-off runtime adaptation from persistent, validated structural evolution, and how should changes across coupled task/agent/capability/state graphs be coordinated under shared constraints rather than evolving independently and inconsistently?
* **Graph-native agent operating systems** (Section 5.3): can a shared runtime — graph scheduling, capability discovery, state storage, provenance/event logging, structural transactions, checkpointing, replay, rollback, graph-level observability — be built as common infrastructure the way AIOS separates scheduling/memory/tools/access-control from individual agent applications, rather than each framework (LangGraph, AutoGen, CrewAI, Mastra) reimplementing these concerns incompatibly?
* **Measuring System Intelligence** (Section 6.4, 7.4): what benchmark design (matched execution budgets, versioned graph artifacts, complete traces and state snapshots, controlled structural perturbations, intervention studies, structural ablations) would let a result be attributed to organizational structure specifically, rather than to a stronger model, larger context, more tool calls, or more retries?
* **Privacy, ethics, and accountability** (Section 5.4): as state is replicated and propagated across more agents, tools, and persistent memory over longer horizons, how should responsibility be assigned when biased evidence or adversarial input is amplified through a distributed system rather than contained in one agent's context?
