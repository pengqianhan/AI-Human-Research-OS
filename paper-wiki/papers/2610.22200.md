# Q1 Problem Definition

* **Input (X):** a computer task given as an instruction, a computer state s_t, and a frozen frontier model inside the OpenGCUA harness. At each step the model sees its working state m_t (plan, progress record, retained observations) and the last observation o_t.
* **Output (Y):** at each step, three decisions made jointly, (q_t, p_t, m_{t+1}) ~ π_θ(· | m_t, o_t): which extra views to request (q_t ⊆ {screenshot, accessibility tree}, possibly none); a program p_t whose statements call GUI, accessibility, shell, and API primitives and may use loops, branches, and variables; and the updated working state. Executing p_t yields the next computer state and an execution output e_t; the next observation is e_t plus the requested views. Over a task, the output is the final computer state, scored by the benchmark's evaluator.
* **What is measured:** OSWorld-v2 partial-credit task score and full-task success, with steps (model calls) and output tokens per task as efficiency metrics; on a real Mac, task completion, steps, output and reasoning tokens, and estimated dollar cost.
* **Constraints:** this release trains no model. Everything is done through prompts, tool interfaces, and the execution runtime around existing models; OSWorld-v2 is run on its offline subset to keep results independent of external websites.

# Q2 Problem Novelty

The problem of computer use is not new; the paper's claim is that its framing has shifted. Most of the literature treats computer-use agents as GUI-only (screenshots in, mouse and keyboard out), while frontier systems combine GUI interaction with shell commands, accessibility access, and tools, and OpenAI's computer-use guide now recommends writing GUI operations as code. The question becomes how well a system completes work on a real computer by whatever means works.

The term *generalist computer-use agent* (GCUA) follows the system-level view of [Agents' Last Exam](../concepts/agents-last-exam.md), which splits an agent into five layers (model, GUI perception, orchestration, tools, runtime). The paper's refinement is to define a GCUA by *who decides*, not by which layers it has: a system with all five layers can still click through a dozen screens where one shell command would do. In its formalization, GUI agents, CLI agents, multi-agent hybrids, and the authors' own batched GUI+CLI agent (Qwen-UI-Agent) are restricted cases that fix one or more of the three decisions in advance (Table 1). The motivation for an open project is that frontier GCUAs such as GPT-6 Astra's are closed: weights, prompts, real-device harnesses, device SDKs, and trajectories are unavailable.

# Q3 Scientific Hypothesis

If the model writes each step as a program over all interfaces, so that intermediate results decide later operations within one call, and if selected workflow decisions (when to look at the screen, how to record progress) move from fixed harness rules to the model, then frontier models will complete more computer tasks with fewer model calls than under batched GUI actions, and code execution will help even when GUI and shell access are held equal. A second, design-level claim: as models improve, harness control should move into the model, with the harness supplying mechanisms and the model deciding when to use them.

# Q5 Key Solution Idea

**Code execution as the action format.** The system prompt asks for one Python program in a `<code>` block per step. On OSWorld-v2 it may call PyAutoGUI for desktop input and a `bash()` function for shell commands; the real-device prompt adds Playwright for browsers. The harness syntax-checks and runs the program and returns standard output, standard error, and status. The paper contrasts this with batched actions: a batch is fixed before the first action runs, while a program can branch on what happens (dismiss a dialog if visible), loop (fill three fields per row), and assert (the status now reads Saved), so a dozen round trips become one. In its words, a batch is a program without control flow. From GPT-6 Astra trajectories it names five recurring patterns: cross-interface composition (click, then check output files before the next click), loops over targets determined at run time (seven website sections, each checked through the DOM), result-dependent execution (click Send only if the copied draft matches the saved one), observation preparation (assemble 25 cropped views of a 3D object into one contact sheet before looking), and executable verification (after editing two slide backgrounds, check that the other 64 package entries are unchanged).

**Harness-to-model decision transfer.** The principle is "mechanism in the harness, decision in the model". Three model-initiated mechanisms ship in this release:

* *On-demand observation.* A `screenshot()` call lets the model choose whether its next input includes a new screenshot. The environment still captures one every step for the record; only what the model receives changes.
* *Task-state tracking.* A `todo` ledger (`todo.update()`, `todo.list()`) records progress, facts, and open questions, with statuses that separate pending work, attempted changes, `changed_unverified`, and `claimed_verified`. Entries are the model's own assessment, not a check of the environment.
* *Action intent.* An `<intent>` block before each program states what it should change and preserve (for example, one sentence summarizing a 64-line program that updates 29 CRM lead statuses), mainly so that a user on a real device can follow the agent.

Two context policies stay with the harness: a *rolling screenshot buffer* that removes older images in batches, so the cached prompt prefix changes less often, and *micro-compaction*, which replaces older tool outputs with short placeholders in batches (see [Context compaction](../concepts/context-compaction.md)).

**From benchmark to a user's computer (Section 4).** The paper lists five ways a real machine differs from a benchmark: the user shares the pointer, keyboard, and focus; windows open, move, and cover each other while the model thinks; requests change mid-task; the relevant window or tab need not be in front, so a desktop screenshot can show the wrong page; and tasks start among existing files, tabs, and sessions. The response has two parts.

* A *Cross-Device SDK* binds every operation to an explicit resource (device, application, window, tab) whose handle keeps its target even when focus changes. It keeps accessibility (`ui.ax`) and vision (`ui.vision`) as separate ways to observe and act, and separates capturing an observation into the program (`observe()`) from delivering it to the model (`mu.emit`). Platform-specific features stay in namespaces (`.android`, `.macos`, `.browser`), and one program can coordinate several devices, for example with `mu.files.copy`.
* A *five-layer real-device harness* (model, runtime with a persistent interpreter, device SDK, driver, applications and OS). It prefers element-level accessibility actions, then window-targeted coordinate input, then foreground input after coordinating with the user. It filters accessibility trees into a flat list linked by `parent_id`, with `search`, `page`, and `read` over a retained snapshot, and an `ask_user` interface handles clarification, login, and authorization of consequential actions. Successful delivery of an action is not treated as evidence that the task-level effect happened.

# Q6 Experiment Design

* **Benchmark and protocol.** The 82-task offline subset of OSWorld-v2 v2.1 (excluding 26 tasks that need the internet), following the GPT-6 Astra release's protocol. Task score is the evaluator's mean partial score on a 0-100 scale; success means a normalized score above 0.999999. Within a run, the latest attempt with an evaluator result is kept for each task, not the best. Steps and tokens are averaged over all tasks including failures, cross-model means weight models equally, and relative reductions are computed per model and then averaged.
* **Models.** Claude Opus 5, GPT-6 Astra, Gemini 3.8 Flash, Qwen3.8-Max, Qwen3.8-Flash, Kimi K3, DeepSeek-V4.1-Flash, GLM-5.3-Flash.
* **Comparisons.** (1) GUI-only with batched actions against the full configuration, all eight models (Table 2); (2) batched GUI+CLI against the full configuration, four models (Table 3); (3) a code-execution ablation over single-action GUI, batched GUI, batched GUI+CLI, and code execution, three models (Figure 6); (4) a decision-transfer ablation that adds each mechanism to code execution separately and then all together, two models, with cache-hit rates (Table 4); (5) retrospective money and time caps per task applied to the recorded full-setting runs (Figure 7).
* **Real device.** Four macOS tasks: a workbook with race rules, seven worked examples, and 125 questions; a four-page Schengen visa form filled from synthetic records; dietary-constrained snack research over 22 candidates on Amazon (no purchase); and a constrained live hotel comparison. Seven model configurations, up to three runs each; Table 5 reports five, using run 1 per task. Case studies use earlier low-effort trajectories under the same harness.
* **Not included.** No trained model; no repeated runs or variance on OSWorld-v2 (the text speaks of "selected runs" without saying how they were selected); no external hybrid agent (CoAct-1, UltraCUA, StateAct) run on the same split; no controlled wall-clock measurement.

# Q8 Evidence Quality

* **Supported.**
  * *The full design beats batched GUI-only actions on every model.* Mean score rises from 45.3 to 64.9 (+19.6) and success rises for all eight; steps fall by 53.0% on average (Table 2). Gains are largest for the weakest baselines: GLM-5.3-Flash 29.6 to 64.9 (+35.2) and DeepSeek-V4.1-Flash 28.0 to 57.7 (+29.8). They also hold for the strongest: GPT-6 Astra goes from 67.1 to 75.7 with steps from 102.1 to 33.5. The best-to-worst spread shrinks from 39.1 to 18.0 points.
  * *Code execution adds something beyond shell access.* Against batched GUI+CLI with the same interfaces, the full design gains 4.4 to 9.1 points with fewer steps (Qwen3.8-Max 57.2 to 64.0 and 66.1 to 57.0 steps; Claude Opus 5 65.7 to 70.1 at nearly equal steps, Table 3). Code execution alone lifts GLM-5.3-Flash from 55.8 to 63.2 and cuts Qwen3.8-Max's steps from 66.1 to 54.9.
  * *On-demand screenshots improve cache reuse.* Cache-hit rates rise from 75.6% to 86.1% (Qwen3.8-Max) and from 61.9% to 76.3% (DeepSeek-V4.1-Flash) with slightly higher scores (Table 4). The rolling screenshot buffer adds 16.0 and 13.4 points of cache hit; micro-compaction lowers it (75.6% to 68.6%, 61.9% to 58.9%), and neither policy lowers the score.
  * *Real-device efficiency differs by model under one harness.* GPT-6 Astra averages 34.5 steps and 12.9K output tokens per task and completes 4 of 4. Qwen3.8-Max averages 50.8 steps and 73.4K tokens (5.7 times as many), with reported reasoning of 50.2K against 2.6K (19.4 times), and completes 3 of 4. Dollar cost ranks the other way: about $1.49 per task for Qwen3.8-Max against $18.29 for GPT-6 Astra (Table 5). On the workbook, GPT-6 Astra checks a reusable solver against the seven examples and fills all 125 answer cells; Qwen3.8-Max loops over fixed row ranges and leaves 40 empty without checking.
* **Weaker or narrower than the headline.**
  * *Single, selected runs.* No OSWorld-v2 number has a variance, and the selection rule for "selected runs" is not given. Several ablation differences are one to two points (for example 62.4 to 64.0 with the todo ledger), which may be within run-to-run noise.
  * *The baseline is the authors' own harness.* "GUI + batch" is their implementation; the comparison shows the value of their design over their weaker configurations, not over other published computer-use agents.
  * *Fewer steps is not less output.* Output tokens fall 27.2% on average, but rise for GPT-6 Astra (30.8K to 31.9K) and Gemini 3.8 Flash (80.3K to 82.0K). The paper says end-to-end latency must be measured separately, and its time curves are uncontrolled and labelled exploratory.
  * *On-demand screenshots also add steps (reader observation from Table 4).* Steps per task rise from 54.9 to 63.0 (+14.8%) for Qwen3.8-Max and from 74.5 to 90.0 (+20.8%) for DeepSeek-V4.1-Flash, which the text does not discuss.
  * *Decision transfer is mostly about efficiency and legibility, not score.* Intent annotations lower scores (62.4 to 61.5; 56.7 to 53.3), and all mechanisms together give a lower cache-hit rate than the rolling buffer alone (84.1% against 91.6% for Qwen3.8-Max). The claim that harness control *should* move into the model is a design position; the evidence covers when to take screenshots and how to keep a todo list, not the broader decisions.
  * *The real-device study is small.* Four tasks and one recorded run per model; the authors say the results describe the configurations, not a ranking. The 19.4-times reasoning ratio in the abstract comes from the Table 5 runs, while the case studies use separate low-effort trajectories. DeepSeek lacks a hotel trajectory.
  * *Comparability with other OSWorld numbers (reader cross-reference).* [RSIAgent](2609.15364.md) reports GPT-6 Astra at 72.60 partial on an 82-task OSWorld 2.0 offline split (0808, from official reports); OpenGCUA's 67.1 (GUI + batch) and 75.7 (full) are on v2.1 under the authors' harness, so the three figures are not directly comparable.

# Q9 Contributions

* A decision-based definition of generalist computer use, with a formalization under which GUI, CLI, multi-agent hybrid, and batched GUI+CLI agents are restricted cases.
* A code-execution harness for computer use and a catalogue of five code-execution patterns drawn from frontier-model trajectories.
* Harness-to-model decision transfer as a design principle, with three concrete mechanisms (on-demand screenshots, a status-typed todo ledger, intent statements) and two cache-aware context policies, ablated separately.
* An eight-model OSWorld-v2 comparison, released prompts, and trajectories from all eight frontier models, including GPT-6 Astra and Claude Opus 5.
* A design for running on a user's own computer: a five-requirement analysis of the benchmark-to-device gap, a cross-device SDK with explicit resource binding and separate accessibility and vision channels, and a five-layer harness.
* Budget curves that turn a final score into a resource-aware model choice (for example Qwen3.8-Flash at 60.5 for about $0.38 per task against GPT-6 Astra at 75.7 for about $15.26).

# Q10 Next Steps

* **From the authors.** A trained GCUA model that unifies computer and browser use and learns code execution, on-demand observation, and task-state tracking; more concise reasoning for routine operations; real-device benchmarks on macOS with more applications and user interaction; extending the harness and SDK across computers, browsers, and phones; deciding which further workflow decisions to move from harness rules to the model.
* **Repeat and report variance (reader suggestion).** Several runs per configuration on OSWorld-v2, so that one-to-two-point ablation effects can be told apart from noise.
* **Audit the ledger (reader suggestion).** Compare `claimed_verified` entries against evaluator outcomes, since the ledger records the model's own belief and an agent that marks unchecked work as verified would mislead a real user.
* **Guard conditional actions on real devices (reader suggestion).** Programs that act on a computed condition (click Send if the drafts match) remove a model call and also a chance to stop; consequential actions inside programs could be routed through `ask_user` or a harness-level approval list.
* **Combine with frozen environment memory (reader suggestion).** RSIAgent's frozen action-condition-outcome memory and OpenGCUA's code-execution harness target the same OSWorld split; layering one on the other would show whether their gains add.
