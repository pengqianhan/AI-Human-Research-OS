# Q1 Problem Definition

* **Input (X):** an initial LLM-generated skill document S₀ for one interactive environment, an action agent π that runs with the skill in context, and disjoint training, validation, and test task sets.
* **Output (Y):** a frozen final skill S* (the last Validated Skill after E = 4 epochs) that raises test task success when given to π. No model weights change.
* **Core problem:** existing skill-evolution methods turn execution feedback into edits but lose the link between an edit and the behavior that motivated it, so they cannot check whether the edit changes that behavior. They also judge a whole revision by one validation score, so a rejected revision discards every edit in it, including ones that worked locally. The paper asks how to keep, test, and revisit the execution basis of each edit before it becomes persistent guidance.

# Q2 Problem Novelty

Partly new. Trajectory-driven skill construction and revision is a crowded line: Trace2Skill distills trajectory-local lessons into patches, SkillDisCo compiles shared procedures from successful traces, SkillGrad turns diagnoses into textual update signals, SkillAdaptor and SkillRevise revise from failures, EvoSkill proposes skills through failure analysis, and SkillOpt applies bounded edits under a held-out validation gate and keeps rejected edits as feedback. EviSkill's new elements are (1) a per-edit evidence object that can be replayed from the recorded state rather than a textual lesson, and (2) a separation between local support for one edit and global acceptance of a revision, with locally supported edits carried forward provisionally. The two preliminary studies motivate both: Trace2Skill edits re-run on their own motivating tasks sometimes help, sometimes do nothing, and sometimes hurt (Figure 2), and a subset of edits picked from globally rejected Trace2Skill revisions raises training-set accuracy over the previous Validated Skill (Figure 3).

# Q3 Scientific Hypothesis

1. **Replay beats plausibility.** If each candidate edit is re-executed on the exact step ranges that motivated it and kept only when the replay shows the intended change without new failures, fewer ineffective edits will enter the skill and test accuracy will rise (ablation "w/o Replay").
2. **Rejected revisions contain useful edits.** If replay-supported edits from a revision that fails global validation are retained provisionally, and unresolved evidence is carried into later epochs, some of them will later enter an accepted skill and accuracy will rise (ablation "w/o Cross-Epoch", Cards Only / Edits Only).
3. **Evidence-grounded evolution generalizes across backbones.** If the method works, it will beat no-skill, the fixed initial skill, and four evolution baselines across three environments and six action models (Tables 1 and 4).

# Q5 Key Solution Idea

EviSkill keeps two skill states: the **Validated Skill** S^V (changed only when a candidate revision beats it on validation) and the **Working Skill** S^W = S^V ⊕ P, where P is a **Provisional Edit Ledger** of replay-supported edits not yet validated (at most 16). Each epoch:

1. **Evidence-Grounded Edit Synthesis.** π runs every training task once with S^W. A GPT-5.5 extractor writes **Replayable Evidence Cards** C = ⟨id, trigger ranges, proposed correction⟩, where a trigger range (task, epoch, start step, end step) points at the exact trajectory interval that supports the correction; a grounding verifier discards cards whose ranges do not support them. **Contrastive cards** come from comparing a task's trajectories in adjacent epochs for edits already in use. Active cards are clustered (Qwen3-Embedding-0.6B plus HDBSCAN) into Evidence Windows of 4-20 cards, and an editor turns each window into candidate edits (append, insert, replace, or delete on the Markdown skill) that keep their card links.
2. **Replay-Guided Edit Verification.** For each edit, the recorded trajectory prefix is replayed to rebuild the state just before a trigger range, and π re-executes that segment under S^W ⊕ edit (at most three ranges per edit). A GPT-5.5 evaluator compares source and replayed segments and returns accept, reflect (a local, fixable defect, with feedback), or reject. A reflected edit is revised once and replayed again. Accepted edits are consolidated into a candidate revision.
3. **Cross-Epoch Evidence Propagation.** If the candidate beats S^V on validation, it becomes the new S^V and the ledger is cleared. If not, each consolidated edit is replayed again under S^V ⊕ edit alone (post-rejection replay), and edits that still pass enter the ledger, so the next epoch's Working Skill uses them. Cards change state: active (eligible for new windows), protected (supporting a provisional edit), archived (incorporated), or stale (after two replay rejections).

The difference from SkillOpt's validation gate is where the rejection lands: SkillOpt keeps rejected edits as negative feedback, while EviSkill keeps the replay-supported part of a rejected revision as live guidance in the Working Skill until a later validation accepts or supersedes it. The test-time skill contains only validated edits.

# Q6 Experiment Design

* **Environments and splits.** ALFWorld (6 task families; 96 train, 48 validation, 134 valid_unseen test), AppWorld (official 90 train, 57 dev, 168 test_normal), ScienceWorld (24 families; 96 train, 48 validation, 211 official test). Metric: task-success accuracy.
* **Baselines.** No Skill; LLM Skill (the fixed initial skill S₀); Trace2Skill, EvoSkill, SkillGrad, SkillOpt. The action backbone, splits, environment, and evaluation are held fixed per setting. The retrieved text does not say which model writes S₀ or which optimizer model the baselines use.
* **Action backbones.** GPT-5.5, GPT-5.4, GPT-5.4-mini (medium reasoning) and Qwen3.6-35B-A3B, Qwen3.5-9B, Qwen3.5-4B (non-reasoning), temperature 0.7, an 8-step interaction window, 50-step limits on ALFWorld and AppWorld. EviSkill's extractor, editor, and evaluator are GPT-5.5 for every backbone.
* **Ablations.** w/o Replay, w/o Cross-Epoch (averaged per model family), and Cards Only / Edits Only on ALFWorld with the three Qwen backbones.
* **Mechanism analysis.** 18 runs (6 backbones × 3 environments) over 72 epochs: replay decision rates, reflection recovery, promotion of provisional edits, card reuse across epochs, contrastive correction of tracked edits, card support breadth (single-task against cross-task), and replay workload.
* **Not designed in.** One run per setting with no variance or significance tests; no token or dollar cost; no variant that uses the same GPT-5.5 budget without replay; no human check of the evaluator's accept/reflect/reject decisions.

# Q8 Evidence Quality

* **Supported.**
  * *Main comparison.* EviSkill has the best accuracy in 14 of 18 model-environment settings and is in the top two in 16. It improves over No Skill in all 18 (mean +17.93 points) and over LLM Skill in 17, tying it in the eighteenth (Qwen3.5-9B on AppWorld, 43.45). On ALFWorld it is best with all six backbones.
  * *ScienceWorld is where evolution most often fails and EviSkill holds up.* With GPT-5.5, LLM Skill scores 76.78 while Trace2Skill, EvoSkill, and SkillGrad fall to 65.40, 54.50, and 67.30; SkillOpt reaches 80.09 and EviSkill 83.41. With Qwen3.5-9B, EviSkill reaches 37.91 against 22.27 for the best baseline.
  * *Ablations.* Averaged over the GPT backbones, removing replay costs 2.49, 4.56, and 2.85 points (ALFWorld, AppWorld, ScienceWorld), and removing cross-epoch propagation drops AppWorld from 89.68 to 85.52. For the Qwen backbones cross-epoch propagation matters more on ALFWorld and ScienceWorld (3.48 and 1.58 points) and replay more on AppWorld (3.17). On ALFWorld (Qwen average), Cards Only and Edits Only each recover part of the gain (86.32, 86.82) and both together reach 88.06, against 84.58 without either.
  * *Mechanism.* 20.7% (ALFWorld), 41.8% (AppWorld), and 42.5% (ScienceWorld) of candidate edits do not pass their first replay; reflection then recovers 13 of 16 reflected edits on AppWorld and 49 of 54 on ScienceWorld. Of 155 consolidated edits from rejected revisions, 128 were replayed, 96 accepted, and 70 (72.9% of accepted) later entered a Validated Skill; 27.1% were still provisional when the four-epoch budget ended. Of 29 tracked edits targeted by contrastive cards, 20 received a replay-accepted correction.
* **Weaker or narrower than the headline.**
  * *AppWorld margins are thin or negative.* EviSkill is third with GPT-5.4-mini (83.93 against EvoSkill's 85.12), second with Qwen3.6-35B-A3B (63.10 against Trace2Skill's 64.88), and fourth with Qwen3.5-9B (43.45 against SkillOpt's 47.62). With GPT-5.5 it beats the fixed initial skill by 0.59 points, one of 168 test tasks. One test task is worth 0.75, 0.60, and 0.47 points on the three test sets, and each setting is a single run at temperature 0.7, so differences of one or two tasks are within run-to-run noise.
  * *Asymmetric optimizer.* EviSkill's evidence extractor, editor, and replay evaluator are GPT-5.5 even for the 4B and 9B Qwen action models. The large Qwen gains (mean +22.85 points over No Skill, against +13.00 for GPT backbones) may partly reflect a stronger model writing the skill; the retrieved text does not say whether the baselines' optimizer was also GPT-5.5.
  * *Cost is understated.* The efficiency table (3.77 validation points per 100 training rollouts, against 1.55 for EvoSkill and 0.84 for SkillGrad) counts only training rollouts. Replay adds about 19,200 executed agent steps over the 18 runs (18,007 for window replay and 1,205 post-rejection, on top of copied prefixes), plus GPT-5.5 calls for extraction, grounding checks, editing, and evaluation; no token or dollar comparison is reported.
  * *Replay acceptance is an LLM judgment.* The accept/reflect/reject decision comes from a GPT-5.5 evaluator reading paired segments, not from a re-measured success rate on held-out tasks, and its decisions are not checked against humans. Replay is also on the training tasks that produced the evidence, so it shows the edit changes the motivating behavior, not that it generalizes; global validation remains the only out-of-sample check.
  * *Preliminary study 2.2 is in-sample.* The "useful edits in rejected revisions" result picks min(3, N−2) edits per revision by asking GPT-5.5 which look most promising, then measures GPT-5.4-mini accuracy on the full training set, the same tasks the edits came from. It shows that rejected revisions are not uniformly useless, but not that the retained edits generalize.
  * *Mechanism statistics need a denominator.* 72.9% of provisionally retained edits were later promoted, but promotion means a later candidate that included them passed validation together with other edits; it is not a test of each edit alone.

# Q9 Contributions

* A diagnosis of two gaps in experience-driven skill evolution: edits lose the execution evidence that motivated them, and revision-level validation discards locally useful edits.
* EviSkill: Replayable Evidence Cards with step-range provenance, localized replay from the recorded state to verify and repair each edit, and a provisional ledger plus card lifecycle that carry supported edits and unresolved evidence across epochs while keeping the deployed skill validation-gated.
* An evaluation on three environments with six action backbones against four evolution baselines, with ablations and lifecycle statistics, released code, and prompts.

# Q10 Next Steps

* **Matched-budget control.** Give a baseline the same GPT-5.5 optimizer and the same extra agent steps (spent on more rollouts instead of replay) to separate the value of replay from the value of more compute.
* **Variance.** Repeat each setting with several seeds; many AppWorld and ALFWorld differences are one or two tasks.
* **Judge the judge.** Label a sample of replay decisions by hand, or replace the LLM verdict with re-measured task outcome on the replayed segment where the environment allows it, and report agreement.
* **Generalization of accepted edits.** Replay accepted edits on training tasks that did *not* produce their evidence, to test whether replay acceptance predicts transfer.
* **Interaction with the validation gate.** Provisional edits shape the next epoch's trajectories before they are validated; measure whether a bad provisional edit can bias later evidence toward its own retention.
* **Project fit (reader note).** This repository installs hub skills into agents and edits them by hand; EviSkill's card format (the step range that justified a change, kept with the change) is a usable convention for recording why a skill line was added, so a later reviewer can re-run the case that motivated it.
