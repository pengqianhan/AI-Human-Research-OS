# Q1 Problem Definition

* **Input (X):** an executable task x = (E, s_0, g, V): an environment E (an Android device, a desktop virtual machine, or a browser application), an initial state s_0 (application records, files, accounts, and settings such as the current date), a natural-language instruction g, and a verifier V. At each step the harness builds a context c_t from the instruction, the interaction history, and the current observation (a screenshot, plus command output on computers).
* **Output (Y):** a trajectory of model decisions. Each step is one decision that may emit an ordered batch of GUI actions (click, type, drag, hotkey, open, system buttons, wait), shell commands (computers only), API calls, `ask_user`, or `terminate` with a final answer and claimed status. The verifier scores the final state and, when needed, the trajectory through weighted binary criteria: reward r = Σ w_j b_j / Σ w_j gives partial credit, and success S is the product of the required criteria.
* **The platform problem:** run evaluation, data collection, and online RL on the same agent at the scale RL needs, where every attempt needs its own reset device, and supply enough realistic, verifiable tasks to keep RL learning.
* **The training problem:** one GUI policy for mobile and computer use, trained by online RL on synthesized tasks and judged on benchmark tasks it never trained on.

# Q2 Problem Novelty

The paper argues that existing GUI gyms each solve part of the problem (Table 1). Infrastructure gyms (BrowserGym, WebGym, MobileGym, SCALECUA, ClawGUI) make evaluation or training reproducible but cover one platform and, where training code is released, run at most hundreds of environments in parallel. Data gyms (CUA-Gym, Gym-Anything, GUI-Genesis, PhoneWorld) add apps and tasks but release neither training code nor a way to run existing benchmarks; their tasks usually start from one input file or from sample data shared by all tasks of an app. Training recipes (DigiRL, MobileRL, WebRL, ComputerRL, UI-TARS-2, EvoCUA-1.5, [UI-Mate](2608.15930.md)) mostly build their own environments for the domains they study, and cross-domain policies are often made by merging per-domain RL experts. A second, practical motivation is harness drift: when evaluation and training keep separate copies of the agent, preprocessing, history truncation, or prompt templates diverge, and the authors "repeatedly saw such drift" as unexplained gaps between training reward and evaluation score.

# Q3 Scientific Hypothesis

If evaluation, data collection, and training share one harness and rollout path, and the platform supplies resettable mocked apps, coherent cross-app worlds, and execution-tested verifiers at scale, then: (1) one joint online RL run on synthesized mobile and computer tasks will produce a small GUI policy that solves new tasks in its training environments and also improves in environments it never trained in; (2) joint training will beat merging separately trained domain experts; (3) more synthesized tasks at a fixed rollout budget will generalize better; and (4) skills learned in a clone of a real app will carry over to the real app on a physical device.

# Q5 Key Solution Idea

**One harness, one rollout path.** For each environment and agent configuration there is exactly one harness: context construction, policy invocation, output parsing, and action dispatch. A rollout scheduler queues attempts, a worker leases an instance through the environment client and runs the harness, and the trajectory and verifier reward go to a buffer. Evaluation aggregates trajectories, data collection stores them (for example as SFT data), and RL trains on them and syncs new weights to the inference engines, so a harness fix reaches all three. The environment manager exposes five operations (request instances, observe, reset to a task, step, evaluate). Behind them it handles provisioning, session leases, reset, cleanup, rewards, and trajectory storage. Environment adapters keep each benchmark's native initialization and verifier and contain nothing RL-specific.

**Rollouts that survive scale.** Phones run as ReDroid containers on the host kernel, avoiding the nested virtualization that the standard emulator needs, and reset by restoring a golden `/data` snapshot. Desktops get stricter readiness checks, per-instance ports and caches, mid-attempt container recovery, and waits for applications to finish saving so the verifier does not read half-written state. Browser tasks run in headless Chromium. Provisioning is asynchronous with warm pools, and screenshots travel through object storage rather than control messages. Failures stay inside their session: leases reject actions from replaced workers, action identifiers make retries idempotent, and verifiers run in separate process groups. Environment failures are recorded apart from zero rewards so infrastructure faults do not enter the training signal.

**Window-wise history.** The common keep-the-last-k-screenshots policy changes the prompt prefix at every step and defeats KV-cache reuse. MAI-Gym groups steps into windows of K = 10 that overlap by O = 2. Within a window it only appends; at a boundary, older screenshots collapse into placeholders while their text stays. The prefix therefore changes once every K − O steps, and later requests of a trajectory are routed to the engine holding its cache. Training reuses the same windows as samples: each window is one causal sequence, the loss applies only to its new steps, and the sampled tokens are replayed exactly, with a fallback to step-wise samples when turns do not form a consistent prefix (see [Context compaction](../concepts/context-compaction.md)).

**Synthesis of every task component.** Each stage is an agent skill that a coding agent such as Claude Code follows:

* *Mocked apps (E).* Real-world clones of seven apps whose actions cannot be undone: 12306 (rail tickets), China Construction Bank, DiDi, Meituan, Dianping, Douyin, and Xiaohongshu. Each is built from scratch with the real app as reference, over a resettable backend, and checked by testers who run the same tasks in both. There are also 42 novel apps, invented outright as deterministic state machines on a shared HTML5 template. They are validated with reference action sequences, reset tests, rejection of untouched and random-action states, and agreement between browser and browser-free execution.
* *Cross-app worlds (s_0).* A persona and a scenario (timeline, events, constraints) generate files and app records that share people, events, and facts, such as a project brief, a budget sheet, an email thread, and a calendar entry. A task can then say "move the budget review to the day after the revised spreadsheet is due" instead of "create an event named Budget review".
* *Tasks and verifiers (g, V).* A diagnosis report of the model's failed rollouts steers the generator toward weak capabilities. Each task specification fixes success criteria and a hidden answer context before any code exists. Two independent calls then write golden code (which sets the completed state directly) and verifier code, and a reward audit compares the verifier against the specification. The verifier must score 0 on the initial state, 1 after the golden code, and 0 again after reset. Several models then attempt the task through the agent interface, and their trajectories are reviewed for executability, difficulty, clarity, and reward-hacking risk. Models help build tasks, but RL rewards come only from executing verifiers.

**Online RL recipe.** The trainer builds on slime (Megatron-LM for training, SGLang for rollouts) and supports GRPO, DAPO, GSPO, REINFORCE++, SAO, and PPO. The main recipe is [GRPO](../concepts/grpo.md) with group size 8 and a per-token loss. *Policy-adaptive task sampling* gives unseen and sometimes-solved tasks the full group, and never-solved and mastered tasks (success above η = 0.8) 4 and 2 attempts, so that rollouts go where advantages are non-zero. A task's advantages are computed only after all its attempts finish. *Train-rollout consistency* compares trainer and rollout log-probabilities on every token and gates the run on the k3 estimator of their KL divergence, which flags corrupted kernels, misaligned histories, or version skew.

# Q6 Experiment Design

* **Model and training.** MAI-Gym-9B starts from Qwen3.5-9B. An SFT warm-up on mixed mobile and desktop data teaches mixed GUI and CLI instructions; one joint GRPO run then trains on 5,000 synthesized tasks across MobileWorld and OSWorld environments, with code-verifier rewards only, policy-adaptive sampling, and K = 10, O = 2 windows. The run uses 512 GPUs and up to 20,000 concurrent environments for about 96 hours, with a constant learning rate of 1e-6 and a KL loss coefficient of 1e-3 (no entropy bonus).
* **Benchmarks.** Seven of the ten supported: MobileWorld (GUI-only, 117 tasks) and OSWorld-Verified (361) are *Task OOD*: same environments as training, unseen tasks. AndroidWorld (116), MobileGym (256, partial score), OSWorld 2.0 (108, binary/partial), MacAgentBench (676), and MyPCBench (184, perfect-task rate) are *Env OOD*: environments never trained in (OSWorld 2.0 adds 31 self-hosted websites and long workflows). Evaluation uses the training harness, temperature 0.0, and 3 trials per task, and reruns attempts that end in environment failures.
* **Baselines.** Frontier API models (Claude Opus 4.8, GPT-5.5, Qwen3.8-Max) and the open Qwen3.8-27B; GUI agents GUI-Owl-1.5 (8B, 32B), UI-Venus-2-9B, SCALECUA-Qwen3.5-9B, EvoCUA-1.5-32B, CUA-GYM (35B-A3B, 397B-A17B), and Qwen-CUA (397B-A17B); and the Qwen3.5-9B base. Entries come from published reports and leaderboards except eight the authors ran.
* **Analyses.** Infrastructure throughput and reliability (Table 5); step-wise against window-wise history (Table 6); gains split into SFT and RL (Figure 6); joint RL against three weighted merges of per-domain experts (Table 7); 500, 1,000, and 5,000 training tasks at a fixed rollout budget (Figure 8); clone-only RL measured on 52 paired tasks in the 12306 clone and the real app on a physical phone (Figure 9); RL on 252 novel-app tasks, tested on 62 held out (Figure 12); GRPO against SAO on MobileWorld (Figure 10).

# Q8 Evidence Quality

* **Supported.**
  * *Strong in-environment results for a 9B model.* MAI-Gym-9B reaches 78.4% on MobileWorld and 76.2% on OSWorld-Verified, up from 18.0% and 41.8% for the base (Table 4). That is 3.2 and 5.4 points above UI-Venus-2-9B and 40.2 and 23.3 above GUI-Owl-1.5-8B. On MobileWorld it is also above Claude Opus 4.8 (69.2%), GPT-5.5 (62.4%), and Qwen3.8-Max (77.8%), and on OSWorld-Verified it is within 2.5 points of GPT-5.5; only Qwen-CUA (86.2%) is higher among the reported GUI agents.
  * *RL helps beyond its environments.* SFT supplies most of the gain (Task-OOD average 29.9 to 66.4, Env-OOD average 18.8 to 32.3). Joint RL then lifts the cross-domain average from 44.1 to 50.5 (Mobile +8.7, Computer +4.2) and improves every Env-OOD benchmark, by 4.2 on average.
  * *Joint RL beats merging, in this comparison.* With the combined budget of the two experts, joint RL reaches 78.4 and 76.2, above every merge. The best merges reach 76.4 on MobileWorld (50/50) and 74.8 on OSWorld-Verified (30/70), and no merge leads in both domains (Table 7).
  * *More synthesized tasks help at a fixed rollout budget.* 500, 1,000, and 5,000 tasks give 69.2, 73.5, and 78.4 on MobileWorld and 69.7, 70.9, and 76.2 on OSWorld-Verified (Figure 8).
  * *Clone training transfers partly.* On 52 paired 12306 tasks, clone-only RL raises success from 36.5% to 73.1% in the clone and from 28.8% to 48.1% in the real app on a physical phone. Novel-app RL raises held-out success from 25.8% to 45.2%, with budget-exhausting attempts falling from 27 to 5 and mean length from 33.3 to 16.4 steps.
  * *The infrastructure claims are measured.* 1,000 fresh environments come up in 328.4 s (mobile), 88.9 s (computer), and 94.2 s (browser); median resets take 165.0, 37.2, and 6.0 s; and 1.2%, 1.9%, and 0.0% of attempts are rerun after environment failures (Table 5). Against step-wise history, window-wise history doubles prefix-cache hits (42.5% to 85.9%), cuts training tokens per trajectory by 84.7%, and cuts update time from 2166.4 s to 810.9 s, at an 18.9% lower rollout rate (Table 6).
* **Weaker or narrower than the headline.**
  * *"State of the art under 10B" holds on the two Task-OOD benchmarks.* In environments it never trained in, MAI-Gym-9B trails UI-Venus-2-9B on AndroidWorld (75.9 against 80.2) and MobileGym (46.5 against 52.7). It is far below frontier models on computer Env-OOD, for example OSWorld 2.0 at 3.7/11.3 against 20.3/54.8 for Claude Opus 4.8 and MyPCBench at 15.2 against 62.0 (reader reading of Table 4).
  * *Task OOD is in-environment.* The 5,000 training tasks are synthesized inside the MobileWorld and OSWorld environments, so the headline benchmarks share apps, files, and screen layouts with training. The text states that benchmark tasks never appear in training but does not describe a check for near-duplicates between synthesized and benchmark tasks (reader observation).
  * *Mixed baseline provenance.* Most baseline numbers come from published reports and leaderboards with their own harnesses, while MAI-Gym-9B runs in its training harness. The paper's own premise is that harness changes alone shift scores, so cross-model gaps of a few points are hard to attribute (reader inference).
  * *Single runs.* Each training configuration (joint, experts, task-scale runs, SAO) appears to be one run, with no seeds or variance, and the SAO comparison is read off a curve. The merge comparison covers three weightings only.
  * *Transfer is incomplete.* The clone-to-real gap widens from 7.7 to 25.0 points after RL, so clone gains overstate real-app gains. The real-app test is 52 tasks in one app.
  * *The diagnosis loop is untested over rounds.* Failure-driven synthesis is described and used, but the paper says repeated rounds of diagnose, synthesize, and retrain are not yet evaluated.

# Q9 Contributions

* An open platform that unifies GUI-agent evaluation, data collection, and online RL across mobile, computer, and web through one harness per configuration, with ten integrated benchmarks and a 20,000-instance scale test.
* Systems techniques for GUI RL at scale: container-native Android with snapshot resets, asynchronous provisioning with warm pools, failure isolation that keeps infrastructure faults out of rewards, KV-cache-friendly window-wise history reused as training samples, policy-adaptive task sampling, and a per-token KL gate on train-rollout consistency.
* A synthesis pipeline covering all four task components: resettable real-app clones and novel apps, persona-and-scenario cross-app worlds, and requirements-first verifiers accepted only after an initial-completed-reset execution test and multi-model trajectory review.
* MAI-Gym-9B, a single 9B mobile and computer policy from one joint RL run, with released weights, 49 apps, and 2,000 verified tasks.
* Evidence that joint RL beats expert merging, that task count matters at a fixed rollout budget, and that clone training transfers partly to a real app on a physical phone.

# Q10 Next Steps

* **From the authors.** Evaluate repeated diagnose-synthesize-retrain rounds; apply the synthesis skills to new apps through the web adapter; compare more RL algorithms on the shared interface.
* **Close the clone-to-real gap (reader suggestion).** Measure which clone differences (layouts, latency, pop-ups, login state) account for the widening gap, and mix a small amount of real-app evaluation into task selection.
* **Train beyond the two training environments (reader suggestion).** Since RL gains are largest in-environment, synthesize worlds inside AndroidWorld-like or macOS environments and test whether the Env-OOD gap to UI-Venus-2-9B closes.
* **Report variance and harness-matched baselines (reader suggestion).** Re-run the size-matched baselines (UI-Venus-2-9B, SCALECUA-Qwen3.5-9B) through MAI-Gym's own harness, which the platform makes cheap, and report seeds for the joint-versus-merge result.
* **Combine with code-as-action (reader connection).** The same team's [OpenGCUA](2610.22200.md) finds that programs over GUI and shell beat batched GUI+CLI actions for frozen frontier models. MAI-Gym-9B uses batched actions, so training a small policy to write programs inside MAI-Gym would test whether that finding survives RL.
