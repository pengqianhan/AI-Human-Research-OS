# Q1 Problem Definition

* **Input (X):** a user instruction describing a game, the current game version $G_t$ (code and assets), feedback from the previous round, and optionally explicit textual preferences a user supplies while playing.
* **Output (Y):** a revised, playable game candidate $C_t$ each round, plus the Reviewer's choice of which version to retain and a structured feedback record for the next round. The loop runs for a configurable number of rounds with the model parameters fixed.
* **Core problem:** coding agents can already build runnable games, but "program correctness does not ensure an enjoyable experience". Difficulty, mechanics, presentation, and feedback decide whether a game is worth playing, and the paper asks how to make that experience, and a particular player's taste, an explicit target of repeated build-play-review cycles.

# Q2 Problem Novelty

Partly new. Iterative agentic game development already exists: Harness-of-Harness (multi-day development with independent assessment), VibeGame (prompt-to-game with a self-evolving adversarial agent team), AVR-Agent (revision from audio-visual recordings), GUI agents that test games for continual generation, and, concurrently, [RSIGame](2609.39045.md), which refines games recursively from evaluation feedback. Benchmarks such as GameDevBench, GameCraft-Bench, and GameXpert-Bench score generation, repair, and optimization. The paper's claimed difference is the target: not functional correctness or benchmark score alone but player experience, measured through many cheap code-driven playthroughs, and adaptation to an individual player's inferred or stated preferences.

# Q3 Scientific Hypothesis

1. **Code-written play beats screenshot play for testing.** If a Player writes reusable policies that act on the game's exposed state through a programmatic interface instead of choosing each action from a screenshot, playtesting becomes frequent, diverse, and reproducible enough to expose difficulty and failure points (Sec. 3.2; illustrated in Fig. 4, not measured against a GUI player).
2. **Experience-oriented review improves games over rounds.** If the Reviewer combines trajectory statistics, a game-specific rubric, and visual evidence, and keeps only the better version each round, game quality will rise across rounds and exceed iterative baselines (GameCraft-Bench, GameASG-Bench).
3. **Preference feedback steers games toward a player.** If inferred and explicit preferences are recorded and passed to the Designer, revisions will move toward the intended experience (expert-rated user study).

# Q5 Key Solution Idea

* **Designer.** Expands the brief and the previous feedback into a plan $P_t = (h_t, \Delta_t, A_t, X_t)$: a hypothesis about which experiential improvement to make and why, concrete changes plus strengths to preserve, acceptance goals stated as scenes, player inputs, and observable outcomes, and asset requests.
* **Builder.** Selects tools by the game's mechanics and visual direction, drafts a playable version (with placeholders), has the framework generate the requested assets, integrates them, and checks them in gameplay scenes against collision, animation, and interaction regions.
* **Coding-native Player.** Reads the game's state schema, legal actions, and testing objectives, and writes a policy that observes state, chooses actions, and repeats until the episode ends or the budget runs out. Policies vary in strategy, skill, exploration, and risk tolerance; rollouts run as parallel or repeated execution jobs and record states, actions, events, progress, elapsed time, and termination outcome. No language-model call is needed per action, and policy code is revised when execution fails.
* **Experience-oriented Reviewer.** Uses (1) shared signals: success rate across policies of different skill (targeting a suitable difficulty, not the highest success rate) and playtime read together with progress, so a long varied run is distinguished from being stuck; (2) a game-specific rubric instantiated from shared dimensions (control responsiveness, content richness, pacing, visual coherence, support for exploration or replay), for example steering in a racing game or coherent dialogue in a visual novel; (3) sampled screenshots and recordings, examined without seeing source code or version order. It writes a preference record stating the desired experience, the supporting evidence, whether each preference is inferred or user-stated, and its priority.
* **Version retention.** The Reviewer compares the candidate with the retained version on anonymized evidence and returns an A/B preference, a tie, or an unavailable judgment with reasons and evidence paths; the harness keeps the preferred artifact and passes the feedback to the Designer.

# Q6 Experiment Design

* **GameCraft-Bench.** Three refinement rounds on 45 tasks selected by Harness-of-Harness (Yan et al., 2026), scored 0-100 on five game categories (Action, Timing, Strategy, Simulation, Adventure) and overall. Comparisons: vanilla and Harness-of-Harness rounds 1-3 with Codex + GPT-5.5 (high), OpenCode + DeepSeek-V4-Pro, and Pi + MiniMax-M3, and a GPT-6 Astra (high) baseline, the model the harness itself uses.
* **GameASG-Bench.** 47 browser-game tasks. L1 checks the source; L2 runs the game in a browser at three priorities (P0 startup and test interface, P1 required gameplay, P2 extended features). Task success requires valid delivery, completed evaluation, every L1 check, and every applicable L2 P0/P1 check. Baseline rows are copied from the GameASG-Bench paper's Table 3.
* **Qualitative development traces.** Early, intermediate, and later versions (V1-V3) of an action game, a visual novel, and a three-character "Meme Arena" combat game, and three showcase games (a MOBA, a racing game, a visual novel).
* **Player exploration.** Visitation heatmap from 48 recorded policy rollouts in an FPS test scene, beside three illustrative GUI-style routes.
* **User study.** Controls, playability, depth, and art rated 1-10 by experts, plus average playtime, across three rounds of preference-guided revision.

# Q8 Evidence Quality

* **Supported.**
  * *Rounds improve the same model's games on GameCraft-Bench.* Overall rises from 72.70 (round 1) to 75.35 and 77.89, against 71.26 for the GPT-6 Astra baseline (+6.63) and 71.52 for the best Harness-of-Harness entry (Codex + GPT-5.5 at round 3, +6.37). All five categories improve from round 1 to round 3; Action rises most (67.96 to 77.62), although rounds 1 and 2 stay below the baseline's 73.33 Action score.
  * *Large gain over the same model under Codex CLI on GameASG-Bench.* Task success is 25/47 (53.2%) against 9/47 (19.1%) for GPT-6 Astra (high) with Codex CLI, a 34.1-point gain; the mean L2 pass rate (93.4%) and the P2 extended-feature rate (93.9%) are the highest in the table.
  * *Code-written play covers a level.* The 48 policy rollouts reach 97.1% of the FPS scene's grid, including 11 interiors; the authors state this shows coverage, not a measured speedup over GUI play.
* **Weaker or narrower than the headline.**
  * *Not the best on GameASG-Bench task success.* GPT-6 Astra (ultra) with Codex CLI passes 26/47 (55.3%), and Recursive Game Creator is also not the column maximum on L1 (98.3 against 99.6), P0 (99.0 against 100.0), or P1 (92.2 against 92.7). The contribution list's claim of the highest overall score on both benchmarks holds only for GameCraft-Bench and for the mean L2 rate. The abstract's "34.1% improvement" is a percentage-point gain, and the introduction's "from 9.47 to 25/47" appears to mean 9/47.
  * *Model and harness are confounded in the baseline comparisons.* Harness-of-Harness is run only with GPT-5.5, DeepSeek-V4-Pro, and MiniMax-M3, never with GPT-6 Astra, so the 6.37-point lead over it mixes harness and model. The GameCraft-Bench GPT-6 Astra baseline's harness is not stated, and the GameASG-Bench baselines are copied from another paper rather than rerun.
  * *No compute matching or ablations.* The harness uses three rounds of design, build, play, and review against single-pass or differently configured baselines, with no reported cost. No experiment removes the coding-native Player, the game-specific rubric, the visual evidence, or the preference record, so which component drives the gains is not shown.
  * *The user study is thin.* Table 3 gives single integer scores per round (for example, playability 1, 4, 7) and average playtime (1.50, 4.87, 12.41 minutes) with no count of experts, players, or games, no variance, and no comparison condition. The abstract calls it a user study; the table calls the ratings expert scores.
  * *Subset and evaluator.* GameCraft-Bench results cover 45 of its 140 tasks, a subset chosen by another paper; the paper does not describe GameCraft-Bench's scoring protocol or report repeated runs, so run-to-run variance is unknown.

# Q9 Contributions

* A four-role harness that makes player experience the revision target: an explicit design hypothesis and acceptance goals per round, a Player that writes and runs policies instead of acting from screenshots, a Reviewer that combines trajectory statistics, a game-specific rubric, and visual evidence, and anonymized A/B version retention.
* A preference record that separates observed behavior, inferred preferences, and explicit user requests, letting the same loop serve general quality improvement and customization to one player.
* Results on GameCraft-Bench (45-task subset) and GameASG-Bench showing large gains over the same base model, plus qualitative version traces and an expert-rated customization study.

# Q10 Next Steps

* **From the authors.** Advance functional prototypes toward product-level games and evaluate continued adaptation to individual players; for the Player, a controlled comparison with GUI-based play that matches budgets and observation access, counting policy construction, repair, execution, and review.
* **Matched comparisons (reader suggestion).** Run Harness-of-Harness and RSIGame with GPT-6 Astra under equal round and token budgets, and ablate each Reviewer input, to separate the harness's contribution from the model's and from extra compute.
* **Proxy alignment.** The Reviewer rewards suitable success rates and longer, more varied playtime from synthetic policies, and the Builder revises toward that feedback. Whether this tracks human enjoyment, or teaches the Builder to lengthen games, needs a human study with stated sample sizes and blinded version order, analogous to RSIGame's free-play check.
* **What the interface exposes.** Code-written policies only test what the game's programmatic interface reveals; a bug visible on screen but absent from the state schema reaches the Reviewer only through sampled frames. Measuring how many defects each channel catches would show whether the visual pass is enough.
* **Beyond small games.** All results concern games that agents can build in a few rounds; whether coding-native playtesting scales to large engine projects (Unreal, as in AutoUE) or long progression is untested.
