# Q1 Problem Definition

* **Input (X):** a long-horizon task and a computer environment (desktop VM, terminal, or hybrid GUI/CLI workspace), a chosen backbone model, and an executor backend (Claude Code, Codex CLI, OpenClaw, or Hermes Agent).
* **Output (Y):** an audited task-completion trajectory ending in one of four manager decisions — done, blocked, ask, or round-budget-exhausted — driven by an externally maintained task state (requirements, artifacts, and facts, each marked completed/pending/blocked/untrusted with supporting audit evidence).
* **Core problem:** existing agent harnesses keep task execution, task-state tracking, and completion self-assessment inside one continuously growing context, so the state becomes difficult to track and an agent's own — possibly wrong — self-assessment of "done" can be recorded and used as a premise for later decisions.
* **Scope:** a harness-layer intervention. Model weights and each backend's native agentic loop (planning and tool use within an episode) are left untouched; only the surrounding role structure and state-persistence contract change.

# Q2 Problem Novelty

Long-horizon agent execution and its named failure modes — compounding errors and goal drift, context rot, and task-state loss — are established concerns (the paper cites METR's finding that the task-completion horizon of advanced agents has roughly doubled every seven months). Existing harnesses such as Claude Code, Codex CLI, and OpenClaw already support planning, task decomposition, tool use, and isolated-context subagents for execution or review. The paper's novelty is diagnosing two specific structural couplings behind these harnesses' long-horizon failures — (i) task execution and task-state management share the same growing context, and (ii) task execution and completion assessment remain coupled in the same agent — and fixing both by fully separating three roles (manager, executor, auditor), with a read-only auditor that never trusts the executor's own completion claim, wrapped around existing backends through a lightweight `AgentAdapter` that preserves their native agent loops.

# Q3 Scientific Hypothesis

If task state is maintained as an explicit record entirely outside task execution, advanced only by facts an independent, read-only auditor verifies directly against the environment (never by the executor's self-reported completion claim), and each subtask is executed in a fresh, budget-bounded context whose raw trajectory is discarded afterward, then long-horizon task-completion reliability improves consistently across backbone models, execution backends, and interaction domains (GUI, CLI, hybrid), without requiring new capabilities at the model level. The paper does not claim MEA improves single-step task-solving ability itself — it explicitly finds the framework does not compensate for a model capability the agent lacks (e.g., visual perception or algorithm design) — only that it improves how reliably existing per-step capability converts into completed long-horizon outcomes.

# Q5 Key Solution Idea

A Manage-Execute-Audit (MEA) loop, run for up to `N_max=25` rounds per task:

1. **Manager.** Owns the persistent task state and has no environment access whatsoever — it cannot observe application state, inspect the workspace, invoke tools, or modify anything. It reads the task, the current task state, and every accumulated audit report to update the task state and choose a control decision (execute / done / blocked / ask). When executing, it emits a bounded subtask contract — goal, acceptance criteria, boundary constraints, and relevant prior evidence — routed to a GUI or CLI executor depending on which interface the transition needs.
2. **Executor.** The only role permitted to change the environment. Runs the contract as a fresh, budget-bounded episode (1,800 seconds) containing only the current round's supplied context — no raw trajectory from earlier rounds. It may internally cycle through planning, interaction, and revision multiple times; when the episode ends, only its execution report (a self-reported summary, not proof of completion) is forwarded, and the raw trajectory and reasoning are discarded. GUI executors receive screenshot/click/scroll/type tools; CLI executors receive shell/file-edit/test tools — a role-scoped capability boundary. Backends are instantiated through a common `AgentAdapter` as one bounded episode of an existing system (Claude Code, Codex CLI, OpenClaw), which controls context, tools, permissions, and budget without altering the backend's internal loop.
3. **Auditor.** Read-only and budget-bounded (300 seconds). It receives the task, task state, contract, referenced prior audit reports, and the executor's report — but never the executor's raw trajectory or reasoning. It independently inspects the resulting environment (GUI: observation-only interactions; CLI: non-mutating commands and log/file inspection) to produce an audit report with three parts: (a) a completion status (complete/incomplete/blocked) judged against the contract's acceptance criteria; (b) an integrity status (clean/suspect/violation) from checking for unauthorized mutations or unexplained artifact changes — any mutation the auditor itself causes is flagged as an integrity violation and cannot support a "completed" record; (c) proposed task-state updates (verified facts, supporting evidence, remaining gaps). The manager alone decides how these findings are incorporated into the next task state.

The key design choice: the executor's report is explicitly treated as "an unverified execution summary," while only the auditor's independently verified report can advance the persistent task-state record — this is what stops a plausible-but-wrong completion claim from propagating into later decisions.

# Q6 Experiment Design

Matched comparisons (same backbone model, same Claude Code executor backend, baseline vs. MEA) on three benchmarks: **WeaveBench** (114 hybrid GUI+CLI tasks across 8 domains; PassRate = fraction of tasks scoring ≥0.8, Overall = mean score; judged by Claude Opus 4.7 as a trajectory-aware judge), **OSWorld 2.0** (108 desktop-workflow tasks, ~1.6h median human completion time, official Docker VM infrastructure; Binary Accuracy = fraction scoring exactly 1, Partial Accuracy = mean score — LongHorizon-Harness uniquely uses a hybrid GUI+CLI tool pool where the official baselines are GUI-only), and **Terminal-Bench 2.1** (pure CLI tasks via Harbor/Docker, three independent runs per task averaged, 5-hour timeout per trial). The primary backbone is Qwen 3.7-Plus, with a generality check using Claude Opus 4.7 on a 34-task OSWorld 2.0 subset. Manager and auditor are each budgeted 300 seconds, the executor 1,800 seconds, with `N_max=25` rounds. A token-consumption breakdown by role (manager/executor/auditor share of total tokens) is reported per benchmark. Four paired case studies present baseline-vs-MEA trajectories on identical tasks — stalled-interaction recovery, auditing an apparently-complete-but-wrong result, preserving pre-repair evidence, and continuing from verified progress — with before/after per-task scores.

Headline matched results: WeaveBench PassRate 51.8% → 80.7% (Qwen 3.7-Plus, Claude Code backend); Terminal-Bench 2.1 69.7% → 77.2% (same configuration); OSWorld 2.0 binary completion 2.8% → 8.3% and partial score 21.5% → 35.2% (Qwen 3.7-Plus); OSWorld 2.0 34-task subset binary completion 20.0% → 34.3% and partial 55.8% → 66.9% (Claude Opus 4.7).

# Q8 Evidence Quality

The core comparisons are matched — same backbone model, same Claude Code executor backend, isolating only the MEA wrapper — across three independently-sourced, official benchmarks spanning hybrid GUI+CLI, desktop, and pure-CLI domains, with consistent gains in every matched comparison. This is reasonably strong evidence that the MEA mechanism, not just backbone strength, drives the improvement, and the paper is transparent about cost and boundary conditions: token consumption rose 2.3×–3.6× on WeaveBench/OSWorld but fell 24% on Terminal-Bench (not a fixed multiplier), and gains concentrate where progress is representable as verifiable environment state, shrinking or reversing on tasks bottlenecked by a single model capability that auditing cannot supply. Caveats: the WeaveBench comparison against officially reported numbers uses root privileges inside the task VM versus the official regular-user account, so those cross-configuration rows are explicitly flagged as reference points rather than matched comparisons; the OSWorld 2.0 baseline uses GUI-only tools while LongHorizon-Harness uses a hybrid GUI+CLI tool pool, so part of the OSWorld gain may come from added tool access rather than the MEA structure alone — no GUI-only MEA ablation is reported to isolate this; the WeaveBench judge (Claude Opus 4.7) and the auditor role both rely on LLM-as-judge-style verification, so both inherit whatever blind spots that judging paradigm carries.

# Q9 Contributions

1. Reformulates long-horizon agent execution as a task-state management problem: state is maintained explicitly outside execution, updated only by independently verified facts, and used to determine each next subtask.
2. Designs the Manage-Execute-Audit loop with three role-separated components — a state-owning, environment-blind manager; an environment-modifying, fresh-context executor; and a read-only, independently-verifying auditor — plus a lightweight `AgentAdapter` enabling interchangeable backends (Claude Code, Codex CLI, OpenClaw, Hermes Agent) across models (Qwen, Claude, GPT).
3. Empirically validates the approach on WeaveBench, OSWorld 2.0, and Terminal-Bench 2.1 under matched comparisons, showing consistent gains across hybrid, desktop, and pure-CLI domains and across two backbone models, plus a token-cost/role breakdown and four qualitative case studies showing the recovery mechanisms concretely.

# Q10 Next Steps

* The paper's own analysis surfaces boundaries rather than a formal limitations section: MEA's benefit concentrates on tasks whose bottleneck is long-horizon execution reliability, not tasks bottlenecked by a single model capability (visual perception, math reasoning, coding, algorithm design) — independent auditing "cannot supply a capability the model does not possess." Cost is not a fixed multiplier and depends on task and model: a weaker model (Qwen) spends more tokens on repeated execution and recovery (10.7M → 34.3M tokens/task), while a stronger model (Opus) needs fewer audit-replan rounds and its cost actually falls (16.5M → 11.1M).
* Natural follow-ups: isolate whether OSWorld 2.0 gains come from the hybrid GUI+CLI tool pool or the MEA structure itself via a GUI-only MEA ablation; rerun the WeaveBench comparison under matched (non-root) privileges for a clean apples-to-apples row; study whether auditor judgment quality itself degrades on tasks with ambiguous ground truth (embodied visual precision, temporal video evidence, multiple valid interpretations) — the paper's own listed concentration of remaining failures.
* **Research-OS fit:** the manager/executor/auditor separation, where the auditor never trusts the executor's self-report and task state persists only from independently verified facts, is directly relevant to this repository's own evidence-gating language ("repository evidence wins over summaries and hand-off snapshots") — worth comparing against how delegated or multi-step agent work in this repository is currently verified.
