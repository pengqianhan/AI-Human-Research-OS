# Q1 Problem Definition

* **Input (X):** a high-level task prompt, interactive access to a running reference application A*, and a prepared environment exposing both GUI control and software-development tools. The agent may move repeatedly among operating the reference, writing code, building/launching its candidate, and checking the running candidate against the reference — the task fixes the desired artifact but not the order or modality of actions.
* **Output (Y):** a complete source submission S satisfying the platform's build/launch contract (source with build/launch entry points on desktop; a Gradle project producing an APK on Android; scaffolded source producing a self-contained `index.html` on Web); building and launching S produces the runnable candidate Â, scored against a hidden, reference-validated test suite.
* **Core problem:** computer-use agents have split into two blind lines — GUI agents that operate interfaces but cannot build the software behind them, and terminal/coding agents that author programs but cannot see the interface their actions produce. Real digital work requires both, interleaved rather than stacked end to end, and existing benchmarks mostly emphasize one interaction mode, leaving autonomous coordination of the "explore → implement → verify" loop over long horizons under-measured.
* **Scope:** recreation tasks across five platforms (Ubuntu, macOS, Windows, Android, Web); RecreationBench held-out evaluation of 250 tasks (50 per platform); a 35,000-trajectory SFT training study on two Qwen initializations, transferred to five separate out-of-distribution benchmarks (not RecreationBench itself). All benchmark runs use the standard direct-MCP interface; a persistent programmable-runtime comparison (Sec. 5.2) is a separate, non-benchmark-contributing experiment on one platform (Windows) with one model (Claude Opus 4.8).

# Q2 Problem Novelty

The paper does not claim to originate GUI agents, coding/terminal agents, or scalable-environment generation individually — it cites OSWorld/OSWorld 2.0 and AndroidWorld as the GUI-operation line, SWE-bench/ProgramBench as the terminal/coding line, and WeaveBench/PhoneHarness/CoAct-1/StateAct as prior work that already combines GUI and code to some degree. Its stated novelty is the specific task design of *recreation*: rather than a fixed specification given up front (as in most coding benchmarks) or a scripted GUI-operation goal, the agent must recover the specification itself by operating a running reference and only then implement and self-verify a faithful reconstruction — reversing the usual direction of a coding task and making GUI exploration, implementation, and verification genuinely inseparable rather than sequential stages. This differs from CoAct-1 (which delegates between GUI and code as two callable modes) and StateAct (which makes program-state access primary and GUI secondary) by requiring the agent to decide autonomously, with no prescribed workflow, when to explore vs. implement vs. verify. It differs from visual-coding benchmarks with a given specification (Design2Code, WebGen-Bench, Vision2Web) by making the specification itself something that must be discovered through interaction rather than read from a prompt. The reference-as-oracle design is explicitly framed as an instance of the "asymmetry of verification" (Wei, 2025): once a hidden test suite is validated against the reference and frozen, scoring any candidate is automatic and implementation-agnostic.

# Q3 Scientific Hypothesis

If an agent is trained on execution-grounded recreation trajectories — where success requires closing an explore-implement-verify loop against a running reference rather than following a fixed specification — then it should develop hybrid computer-use capability that transfers to benchmarks and task distributions never seen during recreation training, and should exhibit more frequent self-verification of its own outputs as a byproduct. The paper's own evidence: two model initializations (Qwen3.7-Plus; Qwen-Flash-CPT) fine-tuned on 35,000 rejection-sampled recreation trajectories both finish above their first evaluated checkpoint on all five out-of-distribution benchmarks (ProgramBench, GameCraft-Bench, Vision2Web, OSWorld 2.0, WeaveBench), with gains of up to 17.9 percentage points (Sec. 3.2, Figure 5), accompanied by measurable increases in own-output image reads and GUI observation/interaction (Sec. 3.3, Figure 6) — though the paper is explicit that these behavioral shifts are descriptive and do not establish causation for the score gains.

# Q5 Key Solution Idea

1. **Application recreation as a task formulation (Sec. 2.1).** Given a running reference A*, the agent must return source S meeting the platform's build/launch contract; only S's *observable behavior* is evaluated, not its architecture or source structure, leaving the agent free to choose implementation strategy while keeping success objective.
2. **A five-platform reproducible execution substrate (Sec. 2.3).** Each rollout gets a versioned, task-isolated worker (pinned graphical runtime, automation interface, build toolchains) scheduled across a horizontally scalable VM pool, with a 20-hour per-rollout wall-clock budget so task complexity — not an infrastructure cutoff — determines the effective interaction horizon; desktop workers expose native screenshot/input/accessibility-tree access, Android workers host a pinned hardware-accelerated emulator, and Web workers serve the reference locally and drive headless Chromium via Playwright.
3. **Reference-grounded, two-channel test generation (Sec. 4.3-4.4).** An orchestrator plus specialized subagents build a feature/surface/action inventory from the reference, then author cases with a fixture, an interaction sequence, and programmatic (Prog: exact text/widget-state/computed values through each platform's native automation interface — AT-SPI, AXUIElement, UI Automation, UiAutomator, DOM/ARIA) and/or visual (VLM: a shared judge model returning a binary verdict against a reference-grounded natural-language assertion at frozen visual checkpoints) assertions; every proposed case is replayed against a clean reference instance, filtered, human-reviewed, and only then frozen for automatic scoring — so assertions depend on runtime-observable behavior, letting the same case run unchanged against any independently-architected recreation.
4. **Isolation as an evaluation-integrity control (Sec. 4.5).** Model-generated commands/processes/artifacts are treated as untrusted: a dedicated unprivileged agent principal with POSIX/ACL permission boundaries exposes only the running interface, a writable workspace, and approved fixtures while withholding reference source, hidden evaluation material, and credentials; network egress is filtered per-platform (UID-based on Ubuntu, host-wide default-deny firewalls on macOS/Windows, a routeless namespace with narrow relays on Web); detected direct repackaging/replay of reference artifacts on Web caps a task's aggregate score at 0.10.
5. **Scaled trajectory generation for training (Sec. 3.1).** Qwen3.8-Max generates recreation rollouts against a separate, deduplicated pool of high-quality open-source GUI applications across the same five platforms; rejection sampling via the task-specific behavioral verifiers selects 7,000 high-scoring trajectories per platform (35,000 total, balanced by count not token length), used to fine-tune two initializations (a fully post-trained Qwen3.7-Plus and a continually-pretrained Qwen-Flash-CPT checkpoint) on the same mixture.

# Q6 Experiment Design

**Main benchmark evaluation (Sec. 5.1).** Ten frontier models (including GPT-6 Astra, Claude Opus 5, GPT-5.6 Sol, GLM-5.3, Qwen3.8-Max-0902) are evaluated on the full 250-task RecreationBench via the standard direct-MCP interface, reporting aggregate and per-platform (Appendix B) Prog and VLM scores.

**Programmable-runtime study (Sec. 5.2, Figure 9).** A separate, non-benchmark-contributing comparison on the same 50 Windows applications: direct MCP (control returns after every primitive action) vs. a persistent Node.js REPL exposing Qwen Code's `qwen-cua-driver` SDK, both with Claude Opus 4.8, one rollout per task/configuration; task-quality metrics use all evaluator-valid pairs, interaction/resource metrics use the 39 pairs with complete, non-error records in both configurations.

**OOD transfer (Sec. 3.2, Figure 5).** Two training arms (Qwen3.7-Plus, Qwen-Flash-CPT) fine-tuned on the 35,000-trajectory recreation mixture are evaluated across two checkpoint sweeps on five external benchmarks (ProgramBench, GameCraft-Bench, Vision2Web, OSWorld 2.0, WeaveBench) under a common Claude Code scaffold, one trial per task per checkpoint, each benchmark's own native metric on a 0–100 scale.

**Trajectory and artifact analysis (Sec. 6).** Reference-investigation breadth (interaction-type coverage, window coverage), controlled input variation, final-loop-closure rate, implementation-size-over-progress curves, evaluation-hacking-attempt detectors (network access, protected-path access, package/binary inspection, privilege escalation), token usage/cost, and tool-call-type composition are all computed from recorded trajectories of the four models with released trajectory logs (Claude Opus 5, Qwen3.8-Max-0902, GPT-6 Astra, GLM-5.3). Artifact-structure analysis compares delivered source size, file count/concentration, and UI-framework choice against each reference, across all available delivered projects for those four models (unfiltered by behavioral score).

**Design strength for the hypothesis.** The five-benchmark OOD transfer sweep (Sec. 3.2) is the paper's strongest evidence for genuine generalization, since none of the five transfer benchmarks is RecreationBench itself and the training pool is explicitly deduplicated against evaluation sets — but the paper itself flags the trajectories are "not uniformly monotonic," so "finishes above the first checkpoint" is a weaker claim than "improves monotonically throughout training." The programmable-runtime study (Sec. 5.2) is explicitly self-caveated as "a one-rollout comparison of complete configurations" showing "lower observed interaction overhead rather than an isolated causal effect" — a single-trial result, not a controlled ablation. The hacking-attempt analysis (Sec. 6.1.3) is a genuine integrity check but explicitly does not establish that any boundary was successfully bypassed, only that agents repeatedly *attempt* matching operations.

# Q9 Contributions

1. RecreationWorld, a five-platform (Ubuntu, macOS, Windows, Android, Web) reproducible execution framework built around application recreation, unifying scalable task construction, automatic execution-grounded verification, and trajectory generation for both training and evaluation of hybrid computer-use agents within one system.
2. RecreationBench, a released 250-task (50 per platform) held-out benchmark with reference-validated, human-reviewed, frozen hidden test suites combining programmatic (native accessibility/automation-interface) and visual (VLM-judged) assertions, on which ten frontier models are evaluated — GPT-6 Astra leads at 58.1% overall but achieves full-suite passes on only 2.8% of tasks.
3. Empirical evidence that recreation-trajectory training transfers beyond the training environment: two model initializations fine-tuned on 35,000 rejection-sampled recreation trajectories both finish above their first evaluated checkpoint across five independent out-of-distribution coding and hybrid computer-use benchmarks, with gains up to 17.9 points, accompanied by increased own-output verification behavior.
4. A systematic trajectory- and artifact-level analysis showing current frontier agents reproduce static interface structure more reliably than interactions and computed outputs, that delivered recreations are typically far smaller and more structurally concentrated than their references (median 16.9% of reference LOC), and that agents frequently substitute platform-native UI toolkits for the reference's original framework — a concrete, quantified account of *how* current hybrid agents fall short of reference-level fidelity, not just a headline score gap.

# Q10 Next Steps

The paper's own stated Limitations (Sec. 8): (1) RecreationBench emphasizes pinned, reproducible environments, limiting coverage of workflows involving live services, changing external state, or real-user interaction; (2) hidden suites sample a finite set of visual/behavioral outcomes, so passing them cannot establish full state/interaction-path equivalence; (3) public reference implementations may have appeared in pretraining data, and source-overlap screening cannot rule out prior memorization or all forms of source reuse — the authors propose controlled online/multi-user workflows, expanded hidden-test coverage, and newly constructed references (reducing contamination risk) as future work.

Beyond the paper's own list, three points are worth flagging for a reader assessing this note's evidence. First, the OOD-transfer claim (Sec. 3.2) covers five benchmarks but each with its own scoring convention, task count, and configuration (deferred to Appendix A.5, not read in full here) — the paper reports gains "on a 0-100 scale" across benchmarks with genuinely different metrics (test-pass fractions, rubric scores, visual/functional composites), so the headline "+17.9 points" figure should be read as benchmark-specific rather than a uniform unit across the sweep. Second, the hacking-attempt detectors (Sec. 6.1.3) count *executed operations matching a detector pattern*, explicitly not confirmed successful bypasses or malicious intent — a follow-up distinguishing benign debugging behavior (e.g., a legitimate network call for a package manager) from actual evaluation-integrity threats would strengthen this specific finding. Third, the four models analyzed in the trajectory/artifact sections (Sec. 6) are the subset with released, complete trajectory logs, not necessarily all ten benchmarked models — so Sec. 6's behavioral claims (e.g., "broader reference exploration accompanies stronger benchmark performance") are drawn from a four-model subset and may not characterize the full ten-model benchmark population evenly.

# Related

* [GUI and computer-use agents](../topics/gui-computer-use-agents.md) - a third distinct answer to this topic's demonstration-vs-native-action-space axis: rather than UI-Mate's inference-time demonstration injection or MAI-UI's extended native action space (clarification, MCP tool calls) plus device-cloud routing, RecreationWorld removes the fixed specification entirely — the agent must recover *what* to build by operating a reference before it can decide *how* to build it — making exploration a genuinely load-bearing, unprescribed part of every task rather than an optional robustness mechanism layered on top of a given instruction.
* [Agent environments](../topics/agent-environments.md) - a from-scratch, multi-domain sandbox in the mold of VibeWorlding and UrbanGround, but spanning five heterogeneous platform runtimes (three desktop OSes, Android, Web) under one shared observe-build-evaluate contract rather than one task domain; like VibeWorlding's dual-constraint verifier, RecreationWorld's reference-as-oracle design collapses evaluation and reward-signal generation into the same mechanism (rejection-sampled recreation verifiers select the 35,000-trajectory SFT training set), but unlike UrbanGround's single locally-scored proxy, RecreationWorld pairs two complementary channels (Prog and VLM) specifically so that reproducing an interface's static structure cannot substitute for reproducing its interactive and computed behavior — directly evidenced by the paper's own Sec. 6.3 finding that structure is reproduced more reliably than interaction outcomes.
* [Model Context Protocol (MCP)](../concepts/model-context-protocol.md) - exposes every platform action (GUI control and coding tools alike) through direct MCP tool calls as the standard benchmark interface, and separately studies (Sec. 5.2) replacing that direct-call interface with a persistent programmable SDK runtime as an efficiency-oriented alternative to per-primitive MCP round trips.
* [OSWorld](../concepts/osworld.md) - uses OSWorld 2.0 both as related work (the GUI-operation lineage RecreationWorld positions itself against) and as one of five external out-of-distribution transfer benchmarks (Sec. 3.2) on which recreation-trained models are shown to improve, alongside RSIAgent's and LongHorizon-Harness's prior use of the same 2.0 split for harness-mechanism evaluation rather than transfer-training evidence.
