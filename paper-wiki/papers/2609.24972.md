# Q1 Problem Definition

* **Input (X):** a frozen backbone policy π, an initial harness H₀ (prompts, control flow, tool interfaces and descriptions, memory/skill files, context management), and a finite *evolve set* of tasks with a verifier r(x, τ) ∈ [0, 1] (unit tests in coding, an LLM judge in agentic-workspace tasks, a frozen simulator in engineering design). A proposer LLM edits harness source; each candidate is scored on the same evolve set with k stochastic trials per task.
* **Output (Y):** an evolved harness H_T that is run *unchanged* on held-out tasks — an in-distribution held-out split where one exists, and out-of-distribution benchmarks with different task descriptions, tool interfaces, or verifiers — reported as task score S(H; D) and mean policy-token cost C(H; D) per trial.
* **Core problem:** iterative harness evolution reuses the same evolve set adaptively across rounds (each round's candidates depend on earlier measurements on the same tasks), so evolve-set gains can come from three coupled failure modes the paper names — *benchmark-specific fitting*, *noise chasing*, and *complexity accumulation* — rather than from reusable agent mechanisms. The paper's Figure 1(a) and Table 1 show prior methods retaining little of their evolve-set gain out of distribution, and several ending below H₀.
* **Scope:** harness-level RSI with frozen weights only (the Limitations section excludes weight updates); one domain-specific evolve suite per domain; Claude Opus 4.8 is the policy, proposer, failure analyst, and leakage critic in the main runs, with Gemini 3.5 Flash as a second search policy in the coding domain only.

# Q2 Problem Novelty

Not a new problem. Harness evolution itself is prior art (Meta-Harness, AHE, TTHE, HarnessX are the compared baselines), and the overfitting concern was already raised by concurrent evaluation papers the authors cite — "Rethinking the evaluation of harness evolution for agents" (Wang et al., 2026b), Evo-Bench (Huang et al., 2026d), delta-attribution analysis (Ding et al., 2026) — and targeted by concurrent methods: HarnessCompass makes generalization an explicit search objective and a gated semantic quality-diversity method replaces greedy selection with an archive. What RRSI claims as new is the *framing*: treat the evolution loop as adaptive empirical optimization and import classical regularization (L0 cardinality, L1 sparsification, L2 shrinkage, entropy-style exploration, holdout-reuse caution from Dwork et al., 2015) into both the proposal and the selection side, *without* restricting which harness components may be edited. The problem matters because harness engineering is currently where much agent-product progress comes from (the paper cites frontier-lab engineering posts from Anthropic and OpenAI and a Lilian Weng post), and an evolution method whose gains vanish off its own benchmark is not delivering recursive self-improvement at all.

# Q3 Scientific Hypothesis

If the harness search is constrained in *how* it converts finite, noisy feedback into persistent edits — fewer bundled edits per candidate as the run progresses, falsified hypotheses remembered as negative evidence, benchmark-specific content rejected before scoring, only gains above the measured noise band accepted, cost growth allowed only in proportion to gain, and components that stop earning measured gain deleted — then the evolved harness should show a *smaller* evolve-set gain than unregularized evolution but a *larger* held-out and out-of-distribution gain at lower policy-token cost. Table 2 is the direct test: unregularized evolution reaches 92.8 on Harvey LAB (evolve) but only 40.3 OOD average at 3.80M tokens/trial; RRSI reaches 90.5 evolve, 43.6 OOD at 2.42M tokens/trial (H₀: 89.4 / 39.7 / 1.56M).

# Q5 Key Solution Idea

Leave the edit space Ω(H) fully open (prompts, control flow, configuration, context management, tools, skills, memory, subagents) and regularize the *search trajectory* instead:

* **Proposal side.**
  * *L0-style annealed update sparsity* — cap independently attributable edits per candidate at b_t = ⌈b_min + (b_max − b_min)·½(1 + cos(πt/T))⌉, so early rounds may bundle coordinated changes and late rounds become sparse and attributable.
  * *Evidence-aware credit assignment* — log, per evaluated candidate, the component touched, the hypothesis tested, the diff, score and cost deltas, and acceptance; the proposer conditions on this so rejected mechanisms stay negative evidence.
  * *Structured exploration* — when progress over the last w rounds stays inside the noise band δ, reserve part of the proposal budget for components not yet exercised (analogous to entropy regularization).
* **Selection side.**
  * *Leakage screening* — a critic reads each diff *before* evaluation and rejects task names, entity names, task-specific values, answers, or inert machinery, so leaking candidates never earn an inflated score.
  * *Stability-aware acceptance* — estimate δ by repeatedly evaluating H₀, then require Ŝ(H′) ≥ S* − δ against the best score so far, blocking a walk downhill through individually noise-sized regressions.
  * *Ridge/L2-style complexity-aware acceptance* — for gains above δ, require relative cost increase ΔC ≤ β₀ + β₁ΔS (β values chosen on the evolve set, then frozen).
  * *Lasso/L1-style structural pruning* — components without strictly positive measured gain over a pruning window are handed to the proposer as deletion targets.

The paper is explicit that the L0/L1/L2 names are qualitative analogies: no norm-penalized objective is optimized and harness components are not a shared parameter vector (Sec. 3.1, Appendix C).

# Q6 Experiment Design

* **Three domains, each evolved on one suite and transferred unchanged:** coding (evolve on Terminal-Bench 2.1, 89 tasks; OOD SWE-bench Verified); agentic workspace (evolve on 120 Harvey LAB legal tasks, ID held-out 40 tasks; OOD JobBench, GDPval, APEX-Agents); engineering design (evolve on 61 license-free EngDesign tasks; OOD Frontier-Eng Medal Score, 38 of 47 tasks buildable in their sandbox, with its EngDesign domain excluded).
* **Baselines:** H₀ and four evolution methods (Meta-Harness, AHE, TTHE, HarnessX), all started from the same H₀ with the same frozen policy, evolve set, and candidate budget. Base harnesses are Terminus-2 for coding, and a ReAct loop over an MCP tool gateway with a dynamic toolbelt and ReSum-style context management for the other domains.
* **Controls against confounds:** every number is paired with H₀ measured in the same window (guards against evaluation-infrastructure drift); engineering design uses deterministic simulators, which rules out a harness gaming the LLM judge; APEX-Agents counts infrastructure failures as failures over the full 480-task denominator; GDPval uses a three-judge cross-vendor panel in both presentation orders.
* **Analyses:** a two-group ablation (proposal vs. acceptance regularizers vs. both removed) with token cost (Table 2); policy robustness by re-running coding evolution with Gemini 3.5 Flash (Table 3); cross-model transfer of the Gemini-evolved harness to the unseen Gemini 3.1 Flash Lite (Table 4); cost and steps per trial for every arm (Figure 4).
* **What is not designed in:** baseline comparisons (Table 1) and ablations (Table 2) are reported only for the agentic-workspace domain; no per-regularizer ablation (only the two groups); the reported noise band δ and number of seeds for the final numbers are not given in the main text (they may be in Appendix D, which this reading did not reach).

# Q7 Datasets and Code

No new datasets. Uses public benchmarks — Terminal-Bench 2.1, SWE-bench Verified, Harvey LAB, JobBench, GDPval, APEX-Agents, EngDesign (license-free subset), and Frontier-Eng. # Q8 Evidence Quality

* **Supported:**
  * Table 1 (agentic workspace) directly supports the central claim. RRSI has the *lowest* evolve-set score of the evolved harnesses (90.5 vs. 90.7–93.0) but ties for the best ID held-out (89.2) and is best on all three OOD benchmarks: JobBench 40.7, GDPval 52.3, APEX-Agents 37.9, vs. H₀ 36.0/48.8/34.2. AHE and TTHE end below H₀ on GDPval and APEX-Agents.
  * The ablation (Table 2) shows the predicted trade-off monotonically — removing either regularizer group raises the evolve score and lowers OOD.
  * The deterministic engineering-design transfer (Frontier-Eng +4.3 Medal points, which the paper states is a 24.3% relative gain) weakens the "harness learned to please the judge" explanation.
* **Weaker than the headline suggests:**
  * "Up to 14.1 points" on the evolve split is the Gemini 3.5 Flash coding run (64.6 → 78.7). The Claude Opus 4.8 run gains +6.0 on Terminal-Bench and only +1.8 on SWE-bench Verified.
  * The Harvey LAB evolve gain is +1.1.
  * The engineering-design and coding domains have no baseline comparison, only H₀ vs. RRSI.
  * The OOD gains are 1.8–4.7 points on single evaluation windows. Without reported confidence intervals in the main text, the smaller margins — Harvey held-out 89.2 vs. Meta-Harness 89.2, a tie — cannot be distinguished from noise.
* **Mechanism attribution is coarse.** Only group-level ablations are shown, so the individual contribution of the leakage critic versus the noise floor versus pruning is not established. The critic is the same model family as the proposer.
* **Cost claim:** the "30% fewer policy tokens than the unregularized evolution" in the abstract is not stated as a formula in the text I read. Table 2's 2.42M vs. 3.80M works out to about 36% fewer, and Figure 4 compares against baselines rather than unregularized evolution, so the exact reference for "30%" is unclear from the retrieved text (reader observation). Every evolved harness, RRSI included, still costs more than H₀ (1.56M tokens, 21.2 steps), and the paper says so.

# Q9 Contributions

* A clear diagnosis, backed by a same-budget comparison, that current harness-evolution methods trade out-of-distribution performance for evolve-set gain. Several fall below their own starting harness on unseen benchmarks.
* A reusable set of search-dynamics regularizers that keep the harness edit space open. They are method-agnostic in principle: the leakage critic, noise-band floor, and cost-per-gain rule could wrap any propose-evaluate-select loop.
* Evidence that the resulting harness transfers across benchmarks, across policy families (Claude, Gemini), and to a weaker unseen backbone (Gemini 3.1 Flash Lite, 11.2 → 14.6 on Terminal-Bench 2.1). It also produces the cheapest evolved harness in the comparison.
* An evaluation-hygiene template: same-window H₀ pairing, full-denominator scoring, deterministic-grader domains, and judge panels with order swapping.

# Q10 Next Steps

* **Per-regularizer attribution:** ablate each of the seven mechanisms individually, and report δ, seeds, and confidence intervals so small OOD gains can be judged against noise.
* **Independent leakage critic:** test a critic from a different model family than the proposer. Measure its false-reject rate on generic improvements, because an over-strict critic would look like "regularization" while simply blocking progress.
* **Longer runs and weight updates:** the Limitations name longer-running self-improvement and weight-updating settings as open. It is untested whether the annealed budget and pruning keep harness complexity bounded over many more rounds.
* **Combination with other methods (reader-constructed direction):** the regularizers are orthogonal to *what* is edited, so they could be layered onto [SoL-Pi](2609.20519.md)'s held-out-never-feeds-back rule or [AutoSaddler](2608.23041.md)'s diagnosis-patch loop to test whether gains compose.
* **Project fit (reader note):** any harness-evolution loop in this repository — skills, AGENTS.md, memory policies — faces the same adaptive-reuse problem. A noise-band floor and a leakage screen are cheap safeguards to adopt before trusting self-reported improvements.
