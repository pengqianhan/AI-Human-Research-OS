# Summary

This paper introduces Arbor, a general framework for long-horizon autonomous research in a setting the authors call Autonomous Optimization. In this setting, an agent starts from an initial artifact, iteratively changes it using development-evaluator feedback, and should only count progress when improvements transfer to a held-out evaluator.

Arbor's core mechanism is Hypothesis Tree Refinement. A persistent coordinator maintains a tree of hypotheses, evidence, artifact references, and distilled insights, while short-lived executors test individual hypotheses in isolated git worktrees. The tree is meant to turn research from a flat sequence of local trials into cumulative branching, falsification, insight propagation, and verified artifact improvement.

# Key Ideas

* Autonomous Optimization frames autonomous research as iterative improvement of a mutable artifact under a fixed objective, development evaluator, and held-out test evaluator.
* Hypothesis Tree Refinement makes the research state explicit: each node records a hypothesis, score/result evidence, reusable insight, and a code reference.
* The coordinator owns global strategy and the tree; executors own local implementation and evaluation for one assigned hypothesis.
* Upward insight propagation turns local results, including failures, into constraints and priors for later ideation.
* A held-out merge gate separates development-set exploration from verified artifact-level progress.
* The design makes autonomous research inspectable: every accepted or rejected change is attached to a hypothesis and evidence record rather than hidden in a long chat transcript.

# Method

Arbor runs a repeated observe-ideate-select-dispatch-backpropagate-decide loop. The coordinator observes the current tree, proposes child hypotheses under promising or unresolved parents, selects pending leaves for execution, dispatches executors, writes returned evidence into the relevant nodes, propagates distilled insights to ancestors, then decides whether to merge, prune, continue, or stop.

Executors are deliberately hypothesis-bound. Each executor receives one hypothesis, relevant ancestor insights, the current best artifact, and the development evaluator. It creates a fresh worktree, implements the minimal intervention needed to test the hypothesis, runs the development evaluator, repairs implementation failures when needed, and returns a dev score, factual result, distilled insight, and branch reference.

The held-out evaluator is only used through the merge gate. A candidate branch is evaluated in a separate worktree and promoted only if it improves the current best under the held-out objective, which is the paper's main guard against overfitting the development feedback.

# Experiments

The paper evaluates Arbor on six real Autonomous Optimization tasks spanning model training, harness engineering, and data synthesis:

* Optimizer Design on NanoGPT-Bench.
* Architecture Design on an autoresearch LLM training benchmark.
* Terminal-Bench 2.0 harness engineering.
* BrowseComp search-harness engineering.
* Search-Agent Data Synthesis.
* Math-Reasoning Data Synthesis.

Across those six tasks, Arbor reports the best held-out result on all six under the same task interface and resource budget used for Codex and Claude Code baselines. The paper reports more than 2.5x the average relative held-out gain of the two single-agent baselines. On MLE-Bench Lite, Arbor reports 86.36 percent Any Medal with GPT-5.5, with the same controller transferred through a task adapter.

The ablations argue that the gains are not only from executability: removing the tree or disabling insight feedback keeps valid submissions high but reduces medal outcomes on MLE-Bench Lite. The paper also reports that Arbor's BrowseComp-optimized harness transfers to unseen search-agent tasks, suggesting at least some learned harness changes generalize beyond the source benchmark.

# Limitations

The evaluation is still a controlled proxy for research. The AO suite covers AI-oriented tasks with executable metrics, not open-ended domains where hypotheses are harder to specify, validate, or compare.

The current formulation mostly optimizes fixed scalar objectives. Real research usually involves multiple objectives, including robustness, cost, novelty, interpretability, reproducibility, and safety.

The method depends strongly on model quality and infrastructure. The paper notes that agents can still fail to generate genuinely new mechanisms, abandon promising directions too early, or chase score patterns instead of first-principles explanations. Long-horizon runs also incur substantial systems costs from model calls, evaluator scheduling, worktree management, and artifact handoffs.

# Notes

Reading questions:

* How should this Research OS represent hypothesis trees if autonomous experiments become a first-class project workflow?
* Can the existing `task_plan.md`, `CHANGE_SUMMARY.md`, OKF notes, and generated visualizations act as a lightweight version of Arbor's persistent research state?
* Where should held-out evaluation gates live for non-code research tasks such as literature synthesis or paper drafting?
* How should negative results be promoted into reusable constraints without overfitting future ideation to a narrow benchmark?
