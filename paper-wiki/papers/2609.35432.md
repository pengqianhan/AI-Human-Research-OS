# Q1 Problem Definition

* **Input (X):** a natural-language task for a robot (a kitchen task in RoboCasa365, a manipulation task in RoboDojo, a physics experiment in PhyBench, or a tabletop task on a real dual-arm robot), camera images, depth, proprioception, and a registry of tools. The tools include perception, motion planning, grasping, and learned action models such as a vision-language-action (VLA) policy.
* **Output (Y):** a completed task, or a quantitative result for experiments, plus a typed execution trace (world program, policy program, observations, tool calls, outcomes, verifier verdicts, memory) that can be reused as training data or as evidence for revising tools and workflows.
* **Core problem:** VLA and world-action models (WAMs) map observations and instructions directly to action chunks and a stop signal, so subgoals, completion conditions, and recovery are implicit and cannot be inspected or corrected. The authors support the diagnosis with their own probe: a QwenGR00T policy trained on LIBERO with the instruction masked still succeeds 92.3% of the time, against 96.2% with the instruction.
* **Constraint:** the world program must be built from what a real robot has (images, proprioception, tool outputs), not from privileged simulator state, and success must be decided by a verifier independent of the model's own completion claim.

# Q2 Problem Novelty

Partly new. Code as Policies and its successors (CaP-X, CaP-Gym, CaP-Agent0) already make the program the policy, and structured-state systems (VisProg, ViperGPT, ConceptGraphs, SayPlan, Statler, VoxPoser, ReKep) represent perception or constraints as code. Embodied harnesses around frozen policies (Thea, Guava, [Harness VLA](2607.08448.md), [Zetta](2608.16590.md), SHAPER, GaP, BATON, ASPIRE) already evolve critics, recovery rules, and skills. The authors argue each of these improves one component while holding the rest fixed, and stores what it learns outside the model. Their proposed differences are: (1) state and procedure share one executable representation checked by one independent verifier; (2) the representation persists across episodes, so failures become edits to predicates, tools, or workflows; and (3) verified traces are used to *train the next model*, so the harness is also a data-collection instrument.

# Q3 Scientific Hypothesis

If task state is kept as an executable world program and execution as a typed policy program, and a frozen action model is called as one tool inside that program, then long-horizon success should rise because the agent can verify progress, interrupt, and recover rather than trusting the action model's stop signal. If the resulting verified traces are used to fine-tune the planner, the new model should improve inside the same harness, showing that code traces internalize physical execution. If failed traces are used to revise tool code against a fixed evaluator, tool success should rise without any weight change.

# Q4 Related Work and Key People

* **Action models:** VLA and WAM families (π0.5, GR00T-style heads, XR-1), and evidence that released VLAs are insensitive to instructions and fragile under viewpoint, initial-state, or layout changes.
* **Code as policy:** Code as Policies, earlier work grounding language plans in available skills (such as "Do As I Can, Not As I Say"), CaP-X (CaP-Gym, CaP-Bench, CaP-Agent0), Inner Monologue, ReAct, and Voyager.
* **Code as world:** VCode (image understanding as SVG generation), Visual Sketchpad, scene graphs, state records, and program-synthesized world models; the authors adopt VCode's approach of writing the world program from images.
* **Embodied harnesses:** Thea, Guava, Harness VLA, Zetta, SHAPER, GaP, BATON, ASPIRE.
* **Self-evolving systems:** GenSim, RoboGen, MimicGen, Eureka, Text2Reward, AlphaEvolve, the Darwin Gödel Machine, The AI Scientist, AutoML-Zero, KernelBench, Evolution Gym, and autoresearch (an agent editing a training script under a fixed evaluation protocol).
* **Key people:** HexaFuture (hexafuture.ai). Hongcheng Gao is project lead, Hongcheng Gao and Jingjing Zhou are equal-contribution first authors, and Sihang Wu and Xiao He are corresponding authors. Likely critics: end-to-end VLA groups, who would ask for comparisons against stronger or fine-tuned action models, and the CaP-X authors on how much of the gain comes from designer-supplied tools.

# Q5 Key Solution Idea

* **Physical Coding.** *Code as World* records objects, relations, measurements, constraints, and progress predicates, each tied to the observation it came from. *Code as Policy* organizes planning, tool calls, verification, stopping, and recovery as explicit nodes that can be checked statically. The harness is the "compiler and runtime" between them.
* **HexaAnything runtime.** The harness has five interfaces: tools (including the VLA/WAM as one action tool), workflow, verifier, recovery, and memory with provenance. It adds explicit contracts: a GoalContract that keeps the user's task text immutable, a typed policy with a small set of node kinds (observation, action, VLA invocation, judging, verification, recovery, branching, sequencing, looping), an ObservationEnvelope recording where each observation came from, and TrialOutcome and ExperimentSpec records.
* **Typed verdicts.** The verifier returns Pass, Fail, InsufficientEvidence, Blocked, or SafetyStop. A model's "finished" claim or an action model's stop status never counts as success, and reaching a step limit is logged as a stop reason, not a task failure. Recovery is fail-closed: ambiguous states are not promoted to success.
* **Self-evolution loop.** Each round runs seven operations (specify, execute, verify, diagnose, propose, evaluate, select-and-commit) over a versioned bundle of world program, policy, harness, data, memory, and evaluator configuration. A change is kept only if it improves a fixed hold-out suite without regressing protected suites and can be rolled back. An evidence ladder separates E0 (an artifact runs) through E4 (transfer to a real robot or documented shift).
* **Four evolution targets:** the harness, data and environments, the model, and embodiment and compute, with representation and interface evolution cutting across them. The paper tests only harness and tool evolution and one data-to-model update.
* **Vibe as Policy (real robot).** A programming agent writes, validates, and freezes tools between episodes, and a frozen execution agent composes them at run time through URAI, a tool interface that human operators and agents share.

# Q6 Experiment Design

* **Harness effect (RoboCasa365):** 50 tasks (18 Atomic-Seen, 16 Composite-Seen, 16 Composite-Unseen), 50 seeds each, with the same maximum environment steps. Conditions: XR-1 native, HexaAnything calling XR-1 with GPT-5.6-Sol as planner, and Codex (same model) calling XR-1. A case study runs three Composite-Unseen tasks with 100 seeds each.
* **Model evolution:** HexaModel v0.1 is Qwen3.8-27B fine-tuned for one epoch on 178.6M tokens. Harness-returned data make up 38.8% of the tokens: 1,010 agent traces (703 successful runs of base Qwen3.8-27B, 204 recovery runs of GPT-5.6-Sol, 103 recovery runs of an earlier fine-tuned checkpoint) and 9.3K RoboCasa365 VQA examples with chain-of-thought. The rest is general embodied VQA, scene captions, and math, code, and instruction data. It is compared as planner inside the same harness.
* **Tool evolution (RoboDojo):** three simulated tasks (Fold cloth, Pour vase, Press by number) with a fixed task and evaluator. A programming agent reads failed traces and edits tool code over two revision rounds. The Fold cloth history is also re-evaluated without privileged information on 5 development and 5 held-out seeds.
* **PhyBench:** a new Isaac Sim laboratory with three experiments: a spring constant (success within 15%), gravitational acceleration from three pendulums (within 3%), and two normal-mode frequencies of coupled oscillators (within 10%). Each run has a 7,200 s wall-clock limit and an 18,000-frame budget, 10 trials per model and task, and four models: GPT-6-Astra, Opus 5.5, GPT-5.6-Sol, and Qwen3.8-Max. The metric is mean relative error over valid runs.
* **Real robot:** an AgileX PiPER-X dual-arm system with four RealSense cameras runs seven tabletop tasks, three trials each, with GPT-6-Astra as execution agent. Times are compared with published results for the same model on other hardware (GPT-Policy, Robocurve).

# Q8 Evidence Quality

* **Supported:**
  * *The harness helps a fixed VLA, most on unseen compositions.* With XR-1 unchanged, HexaAnything + GPT-5.6-Sol raises success from 34.3% to 38.3% on Composite-Unseen, 54.8% to 61.5% on Composite-Seen, 78.0% to 80.9% on Atomic-Seen, and 56.6% to 61.1% overall. With the open Qwen3.8-27B as planner, Composite-Unseen reaches 37.3%.
  * *Large per-task gains on long tasks.* Over 100 seeds each: LoadKebabSandwich 17%→48%, PortionHotDogs 22%→37%, WaffleReheat 53%→70%. Doubling the native action budget on PortionHotDogs does not help (21/100 vs. 22/100), so the gain is not just more steps. Case studies show the mechanism: the agent refuses to close the oven until a "both ingredients inside" predicate holds.
  * *Training on harness traces improves the planner.* HexaModel v0.1 beats its Qwen3.8-27B base on every split (Composite-Unseen 37.3%→39.5%, overall 60.5%→61.7%) and edges past GPT-5.6-Sol in the same harness on every split, by 0.1-1.2 points.
  * *Agent-revised tools improve without weight changes.* On RoboDojo, success goes from 0%/40%/0% to 80%/100%/100% on Fold cloth, Pour vase, and Press by number after two rounds. Improvement is not monotonic: Pour vase drops to 0% after the first revision.
  * *The same harness runs physics experiments.* GPT-6-Astra and Opus 5.5 produce valid results in all 30 runs each, and GPT-5.6-Sol in 27 of 30. All three keep mean relative error below 5% on every task (for example Opus 5.5: 1.3% on the spring constant, 1.0% on g; GPT-6-Astra: 0.8% on normal modes). Qwen3.8-Max gets valid results in only 5, 3, and 3 of 10 runs.
  * *Real-robot execution works on most tasks.* Five of seven tasks succeed in all three trials. Toss blocks and fold clothes succeed once each (77.8% and 83.3% progress), failing on perception and reach rather than on tools.
* **Weaker or bounded:**
  * *The harness gain is modest and model-bounded.* It is measured with one action model (XR-1) on one benchmark. The overall margin over Codex with the same model is only 1.6 points, and Codex is ahead on Atomic-Seen (81.7% vs. 80.9%). The authors list these limits themselves.
  * *The model-evolution gain is small.* The HexaModel gains are 0.2-2.2 points, reported with 50 seeds per task and no confidence intervals. The training mix is 61% non-harness data, and there is no ablation isolating the harness traces from the general data (reader note).
  * *Tool-evolution numbers rest on few seeds, and one task used privileged inputs during development.* On Fold cloth, the operator consulted garment keypoints that share a source with the official check when choosing pixels for three development seeds, and the operator chose the pixels for every call. Re-evaluated without privileged information, the final tool succeeds on 3/5 development and 4/5 held-out seeds. By the authors' own statement this measures the tool and interface, not autonomous perception.
  * *PhyBench is new, simulated, and author-built*, with 10 trials per model and task. The Hooke's-law and pendulum case studies were selected runs that completed with full traces.
  * *Real-robot comparisons are not same-robot.* The GPT-Policy and Robocurve references (2.7×, 3.5×, and 2.4× faster) come from other hardware and operating limits, with three trials per task.
  * *Several claims are programmatic, not demonstrated.* Model-architecture evolution, representation evolution, embodiment and hardware evolution, and the longer RoboCasa365 tasks (designed, not evaluated) are future work, as the paper states.

# Q9 Contributions

* The Physical Coding formulation: world and policy as coupled executable programs, with provenance-tagged observations and a typed, independent verifier as the gate for any self-evolution.
* HexaAnything: a concrete harness with execution contracts (GoalContract, typed policy nodes, ObservationEnvelope, fail-closed recovery) that makes gains attributable to workflow, verifier, recovery, model, or tool changes.
* Controlled evidence of harness, model, and tool improvement around a fixed VLA, including an open 27B planner trained on harness traces that matches a frontier planner in the same harness.
* PhyBench, a simulated laboratory in which the deliverable is a quantitative physical estimate backed by recorded evidence, and a first real-robot deployment with tool evolution driven only by camera and joint traces plus operator judgment.

# Q10 Next Steps

* **Weight internalization with reduced harness help** (the authors' staged plan): test whether HexaModel keeps its gains when verification and recovery scaffolding are removed or on held-out compositions.
* **Stronger action models and more benchmarks:** repeat the harness comparison with other VLAs/WAMs and benchmarks, as the single-VLA, single-benchmark limit is the main threat to generality.
* **Autonomous perception for tool evolution:** replace operator-chosen pixels with agent-chosen ones and re-measure Fold cloth-style gains.
* **Verifier-model co-adaptation:** the authors list preventing the model and verifier from co-adapting as open; this matters once the verifier also evolves.
* **Offline vs. deployment-time agent effort (reader note):** [EmbodiedSWE](2609.27308.md) spends coding-agent effort offline to generate VLA training data, while HexaAnything spends it at run time around a frozen VLA and then distils traces into the *planner*. Running both on the same RoboCasa365 tasks would answer the open question in [Agentic robot manipulation](../topics/robot-manipulation-agents.md).
* **Where the verifier sees (reader note):** [Zetta](2608.16590.md) falls back on privileged simulator signals when visual evidence is insufficient, which HexaAnything deliberately avoids. A matched comparison would show what that restriction costs in simulation.
