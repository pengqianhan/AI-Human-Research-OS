# Q1 Problem Definition

* **Input (X):** a natural-language request (a specific object, an ordered list of two to five targets, or a high-level need such as preparing a workspace) and, at each step, four RGB images labelled front, right, back, and left from a robot in an unfamiliar indoor scene.
* **Output (Y):** a sequence of tool calls (observe, turn, navigate to an image point, update goal progress, terminate) that moves the robot to the requested targets in order and ends with an explicit achieved or blocked declaration.
* **Constraints:** the multimodal LLM is used as is, with no navigation-specific fine-tuning; it must judge task completion itself; benchmark scoring is separate from that declaration.
* **Core problem:** navigation that is general over both tasks and scenes. Modular zero-shot pipelines hard-code when the model is consulted and when a run ends, so a new kind of request needs a new workflow; end-to-end models fine-tuned on navigation trajectories generalize only as far as their training data covers.

# Q2 Problem Novelty

Not a new problem, and the harness approach to embodied agents is an active line the paper cites: [Show-Harness](2609.10522.md) (semantic actions to robot motion), AgenticNav (pixel-goal motion with depth queries and image retrieval), HarnessVLN (event memory and a spatiotemporal graph), and the concurrent DemandAgent, which introduces Demand-Bench. SuperNav's stated differences are a single visual-point interface shared by interchangeable motion backends, Navigation Skills as readable guidance, media-only context pruning, and leaving every task-level action choice and completion judgement with the model. The move it makes, borrowing the Skills-plus-tools-plus-context-management pattern of coding agents for a robot, is the interesting part for this wiki.

# Q3 Scientific Hypothesis

1. **Division of labour.** If a general MLLM only interprets the request, reads the scene, and chooses destinations, while a tool executes motion, it navigates across task types and scenes better than models fine-tuned to emit navigation actions.
2. **Pointing is a sufficient interface.** If the model names a destination as a normalized point in one of four labelled views, the same decision workflow works over a geometric planner and a learned controller, and external language grounding adds nothing.
3. **Skills carry the procedure.** If search, recheck, recovery, and completion procedures are supplied as Markdown guidance the model reads on demand, success rises substantially over the same tools without that guidance.
4. **The harness is model-portable.** If the decision model is swapped with the harness fixed, the system still works.

# Q4 Related Work and Key People

* **Modular navigation pipelines.** SemExp, L3MVN, VLFM, VoroNav, SG-Nav, ApexNav: models hold fixed roles inside task-oriented pipelines.
* **Hierarchical systems.** InstructNav, OmniNav (slow reasoning plus a fast waypoint policy), SysNav: model reasoning over dedicated navigation modules.
* **End-to-end navigation models.** NaVid, UniNaVid, StreamVLN: vision-language models fine-tuned on instruction-trajectory pairs. See also [LightNav-0](2608.30935.md) in this wiki.
* **Agentic systems and harnesses.** Inner Monologue, Code as Policies, SWE-agent; embodied harnesses [Show-Harness](2609.10522.md), AgenticNav, HarnessVLN, DemandAgent.
* **Key people.** Zhejiang University (the zju3dv group), Shenzhen University, and Causa Robotics; Sida Peng, Xiaowei Zhou, and Hujun Bao are among the authors. Likely critics: authors of the fine-tuned navigation baselines, who would point to the privileged geometry and the frontier model behind the best numbers, and embodied-AI evaluators who would ask for full-split results.

# Q5 Key Solution Idea

* **Agent loop.** The runtime is Codex CLI; environment operations are exposed through the [Model Context Protocol](../concepts/model-context-protocol.md). Each step the model chooses to observe, move, update goal state, or read Skill guidance, and tool returns enter the context for the next decision.
* **Visual-point navigation.** An observation returns four labelled RGB views. The model calls $\mathrm{PointNav}(d,[u,v])$ with a view $d$ and normalized coordinates $u,v\in[0,1]$, pointing at a candidate object or at visible floor. The tool runs the motion and returns new four-view images, execution status, and diagnostics, so no separate observation call is needed after a move.
* **Two motion backends behind one interface.** The *Geo-based Executor* back-projects the point with depth, camera calibration, and pose, snaps to a reachable location, and follows a planned path (in simulation: rendered depth, simulator poses, and the navigation mesh; on the robot: LiDAR and odometry). The *Learned Executor* uses RGB only: a NoMaD-inspired policy with a marked reference image, a DINOv2 ViT-S/14 encoder, an age-aware history of at most 12 frames, and a conditional flow head that predicts eight displacement increments plus a stop score, trained by imitation on simulator expert trajectories.
* **Progress and termination tools.** Goal records hold pending and found items; termination records the model's achieved or blocked judgement. Both are the model's reports, not independent verification.
* **Navigation Skills.** A bundle of Markdown packages (a main navigation Skill, backend-specific tool-use instructions, references for exploration, recovery, and entrance search). The harness exposes names and descriptions; the model loads what it needs. Guidance covers where to search (record inspected areas and unexplored openings), how to recover (change the point or route, step back, look for an entrance when glass blocks access), and when to finish (check appearance, requested relations, and surroundings). Skills add no capabilities and enforce nothing.
* **Context management.** Once an image has been processed and superseded, its media payload is dropped from later requests while text history, task state, and image paths remain; the model can reopen earlier images from the workspace.

# Q6 Experiment Design

* **Decision model.** GPT-5.6 Terra at high reasoning effort, with a 3,600 s budget per episode.
* **Instance navigation (own benchmark).** Habitat-GS with InteriorGS scenes: 150 single-object tasks and 150 ordered multi-object tasks (two to five targets). Arrival means navmesh geodesic distance below 1 m to an approved viewpoint, with explicit STOP.
* **Demand-driven navigation.** 200 AI2-THOR tasks from Demand-Bench under an adapted protocol: one to eight ordered stages, each satisfied within 2 m of an admissible object's bounding box, with explicit STOP.
* **Baselines for both.** NaVid, UniNaVid, StreamVLN, and OmniNav's Action Former, each with its native inputs and history; no agentic controller or stage-progress signal is added to them.
* **Category-level navigation.** A 120-episode HM3D-OVON val-unseen subset and 1,000 HM3Dv2 validation episodes, set beside published numbers from other methods.
* **Ablations (OVON subset, Geo-based Executor).** Remove Navigation Skills; replace the four-view tools with a front-only interface; remove both; replace direct pointing with an external grounding model (LocateAnything) plus candidate confirmation; swap the model for GPT-6 Astra at medium effort.
* **Real robot.** A Unitree Go2 with four RGB cameras and LiDAR-based geometric execution, shown through three example runs.

# Q8 Evidence Quality

* **Supported.**
  * *Large margins on the authors' task sets.* With the Geo-based Executor: single-object 78.00% SR and 0.4127 SPL, multi-object 34.00% and 0.1388, demand-driven 59.50% and 0.1801. Best baselines: 34.00% SR (UniNaVid) and 0.2133 SPL (OmniNav) on single-object, 4.00% on multi-object, 37.50% on demand-driven (OmniNav).
  * *The harness components matter, by ablation.* On the OVON subset at 0.25 m: full system 68.33% SR; without Skills 35.00%; front-only tools 52.50%; without both 31.67%; grounding-model interface 55.83%. Without Skills the agent makes 7.43 tool calls and travels 7.56 m per episode against 11.17 calls and 16.44 m for the full system, which suggests it stops searching early (reader reading of Table 6); the front-only interface needs 30.28 calls and 17.56 turns.
  * *The harness survives a model swap.* GPT-6 Astra at medium effort scores 71.67% SR and 0.4579 SPL at 0.25 m (86 of 120 episodes) against 68.33% and 0.3837 for Terra at high effort.
  * *Later goals.* On multi-object tasks SuperNav leads at every stage (first-goal completion about 86% against at most 44% for baselines; fifth-goal 34-39% against 0%).
* **Weaker or narrower than the headline.**
  * *The best configuration uses privileged geometry.* The Geo-based Executor relies on rendered depth, simulator poses, and the navigation mesh, while the baselines are RGB video policies; the authors note that the backend comparison "changes both the controller and its supporting geometric resources". The RGB-only Learned Executor keeps much of the success rate (68.00% single-object, 45.00% demand-driven) but its single-object SPL of 0.2059 is below OmniNav's 0.2133, and on HM3D its SPL falls to under 40% of the geometric backend's, for example 0.1355 against 0.3837 on OVON at 0.25 m (reader comparison from Tables 1 and 2).
  * *Unequal models and budgets.* A frontier hosted MLLM with up to an hour per episode is compared with fine-tuned navigation models (the NaVid and UniNaVid checkpoints are 7B); no cost, latency, or step-count comparison is given. The closest like-for-like control is internal: the same model with neither Skills nor the tool design scores 31.67% at 0.25 m.
  * *HM3D comparisons are across protocols.* SuperNav with the Geo-based Executor scores 68.33% SR at 0.25 m and 73.33% at 1 m on OVON (published rows: SoftNav 66.70% at 0.25 m, AstraNav-Memory 62.50% at 1 m) and 80.30% at 0.2 m and 86.50% at 1 m on HM3Dv2 (ApexNav 76.20%, MSGNav 74.10%). It runs on a 120-episode OVON subset; the other rows are published numbers on different subsets, thresholds, step limits, and STOP rules, which the appendix lists and the authors acknowledge. SuperNav's OVON scoring requires no STOP action, and two episodes per configuration are credited as successes under MTU3D's unreachable-goal rule.
  * *Small samples, single runs.* With 120 episodes, the Astra-Terra gap at 0.25 m is four episodes. No repeated runs or intervals are reported.
  * *The instance benchmark is the authors' own and the demand protocol is adapted.* Demand-driven scores measure ordered arrival near relevant objects, not completing the activity, and are not comparable with DemandAgent's reported scores (both stated by the authors). No method completes six or more demand stages, and only three tasks have that many.
  * *Evaluation isolation is by instruction.* Codex runs with full filesystem access and approvals disabled; the prohibition on reading scene assets, ground-truth annotations, and evaluator metadata is an instruction, not an operating-system restriction, and the paper reports no audit of whether runs complied (reader observation from Appendix A.2).
  * *Real-robot evidence is qualitative.* Three illustrated Go2 runs, no success rates.

# Q9 Contributions

* A navigation harness (agent loop, tools, Skills, progress records, media-only context pruning) that lets an unmodified MLLM handle category-level, instance-level, ordered multi-object, and demand-driven navigation.
* A unified visual-point motion interface with two interchangeable backends, including an RGB-only learned point-goal controller.
* An instance-navigation benchmark in Habitat-GS (150 single-object and 150 ordered multi-object tasks).
* Ablations separating the contribution of Skills, tool design, grounding interface, and decision model, with interaction statistics.

# Q10 Next Steps

* **From the authors.** The system is limited by the MLLM's semantic judgement; geometric execution needs maps or scene geometry; MLLM inference adds cost and variable latency; demand-driven evaluation does not measure activity completion; more real-world settings and better reliability on long sequences remain to be done.
* **Enforce the evaluation boundary (reader suggestion).** Run the agent in a sandbox that cannot see scene assets or evaluator files, or audit tool and shell logs for such reads. [MiMo-V2.6](2610.11959.md) documents coding agents fetching published fixes when the environment allows it, and responds by removing the paths (artifact cleanup, network isolation) in addition to instructing against them.
* **Matched comparisons (reader suggestion).** Report the Learned Executor as the headline when comparing with RGB-only baselines; add a baseline that gives the same MLLM a plain action interface; report tokens and seconds per episode.
* **Which Skill lines matter (reader suggestion).** Skills account for the largest ablation drop. Removing search, recovery, and completion guidance one at a time, or optimizing the Skill text with a validation gate as in the skill-evolution papers this wiki tracks, would show how much of the gain is a few instructions such as "verify at close range before stopping".
* **Project fit (reader note).** The harness is the same shape as this repository's agent setup: Markdown skills discovered by name and description, tools behind MCP, state kept in files. The no-Skills ablation is direct evidence that such guidance changes agent behaviour, here by keeping the agent searching instead of stopping early.
