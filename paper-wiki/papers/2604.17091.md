# Q1 Problem Definition

* **Input (X):** a long-horizon agentic task (file operations, code execution, web browsing) potentially spanning multiple episodes or repeated encounters with similar tasks, executed by an LLM agent that accumulates tool descriptions, retrieved memories, and raw environmental feedback as interaction lengthens.
* **Output (Y):** an action trace produced by GenericAgent (GA) -- a system combining a fixed minimal atomic toolset, hierarchical on-demand memory, an execution-gated self-evolution mechanism that converts verified past trajectories into reusable SOPs and executable code, and a four-stage context truncation/compression layer -- that completes the task using substantially fewer tokens and interactions than baseline agent systems at equal or better success, and that improves on repeated encounters with similar tasks.
* **Core problem:** long-horizon LLM agents are argued to be fundamentally limited not by context length per se but by how much decision-relevant information survives within a finite context budget as tool descriptions, retrieved memories, and raw feedback accumulate and crowd it out; useful experience gained from completed tasks is also typically lost across episodes rather than retained and reused.
* **Scope:** a systems paper proposing an agent architecture and evaluating it empirically against named baseline agent systems (Claude Code, OpenClaw, with CodeX mentioned as a related system) across task completion, tool-use efficiency, memory effectiveness, self-evolution, and web browsing; self-evolution operates entirely on the agent's informational environment (SOPs, scripts, memory) rather than on the underlying LLM's weights, except for a preliminary, explicitly-flagged reflection-based weight-adaptation exploration.

# Q2 Problem Novelty

Prior long-horizon-agent approaches generally attack the problem by extending the context window, bolting on a memory/retrieval subsystem, or exposing a large tool surface for generality. GenericAgent's stated reframing is that performance is governed by "context information density" -- how much decision-relevant information survives within a fixed, deliberately small budget (the paper targets a "hallucination-free context length" under 30k tokens) -- rather than by how much context is available. It operationalizes this by explicitly rejecting the standard completeness/conciseness/naturalness trilemma framing, arguing the primary tension is between completeness and conciseness with naturalness a secondary constraint, which motivates a minimal 9-tool interface (versus the dozens of tools the paper reports in compared systems) and an aggressive, staged compression pipeline, combined with a self-evolution mechanism explicitly gated by a "No Execution, No Memory" rule so that only verified, successfully-executed information is retained long-term.

# Q3 Scientific Hypothesis

If an agent (a) exposes only a minimal atomic tool set, (b) organizes memory hierarchically so only a compact index is always visible while deeper procedural and raw layers are reached through explicit tool calls, (c) evolves task-specific SOPs and executable scripts only from verified successful executions, and (d) aggressively truncates and compresses context in stages to maintain a small, high-density working context, then it will match or exceed the task success of agent systems that expose large tool surfaces and rely on extended context windows, while consuming substantially fewer tokens and interactions, and its performance will continue to improve across repeated encounters with similar tasks rather than remaining static.

# Q5 Key Solution Idea

1. **Minimal atomic toolset.** Nine tools across five capability classes -- file operations (`file_read`, `file_patch`, `file_write`), code execution (`code_run`), web interaction (`web_scan`, `web_execute_js`), memory management (`update_working_checkpoint`, `start_long_term_update`), and human-in-the-loop (`ask_user`) -- composing complex capabilities through combination rather than enumerating many specialized tools. The paper reports that compared systems' much larger tool surfaces still concentrate execution in a small subset (one tool accounting for roughly half of all calls), arguing the remaining tools mostly add prompt overhead and decision complexity without proportionate behavioral benefit.
2. **Hierarchical on-demand memory.** Four layers -- L1 (an always-visible, compact index of pointers), L2 (a fact layer of verified information), L3 (an SOP layer of procedural knowledge), and L4 (a raw session archive) -- where only L1 sits in the default working context; deeper layers are reached only through explicit tool calls, keeping the active context minimal while preserving reachability to richer stored knowledge.
3. **Execution-gated self-evolution.** A fixed tool layer is kept separate from an evolving knowledge layer; task-specific capabilities accumulate as reusable SOPs and scripts, governed by a "No Execution, No Memory" rule under which only information verified through successful task execution is written to long-term memory, explicitly preventing pollution of the knowledge layer from failed attempts -- a stricter, execution-outcome-gated variant of the validation gates this wiki already tracks in the SkillOpt family of papers.
4. **Four-stage context truncation and compression.** (1) per-tool output truncation via head-tail character retention; (2) tag-level compression every five turns, replacing redundant blocks and truncating reasoning traces; (3) FIFO message eviction once the context budget is exceeded; (4) continuously-injected working-memory anchor prompts that preserve task-critical information across the above lossy stages -- together targeting a working context under roughly 30k tokens rather than relying on an extended context window.

# Q6 Experiment Design

Evaluated across five axes on named benchmarks: task completion and token efficiency (SOP-Bench, Lifelong AgentBench, RealFin-Benchmark), tool-use efficiency (a long-horizon complex-task setting), memory effectiveness (repeated-run efficiency, a condensed-memory ablation, and long-term fact retention versus embedding-based retrieval), self-evolution and autonomous exploration (a skill-tree curriculum planner scored along breadth/depth/utility/innovation, illustrated with case studies), and web browsing (DOM analysis and element-visibility classification before serialization). Reported headline numbers: on Lifelong AgentBench, GA reaches 100% accuracy using 222k input tokens versus Claude Code's 800k and OpenClaw's 1.43M; on RealFin-Benchmark, GA reaches 65% accuracy on 114k total tokens versus Claude Code's 55-60% and OpenClaw's 35%; an accuracy-per-million-tokens efficiency metric ranges 4.15-5.70 for GA across benchmarks. On a long-horizon complex-task setting, GA reports a 100% success rate using 188,829 tokens, roughly 35% of Claude Code's and 30% of OpenClaw's consumption, at equivalent or superior success. A memory-effectiveness ablation reports a condensed, high-density memory configuration matching a verbose configuration's task success rate (66.48%) while using only 165 tokens versus 288-575 tokens for the verbose variants. Repeated-run efficiency is reported to improve markedly across runs on the same task family, with operation time falling from 102 seconds (run 1) to 66 seconds (later runs) and token consumption from 200k to 100k.

# Q9 Contributions

1. Reframes long-horizon agent performance around context information density rather than context length, operationalized through four connected components: a minimal atomic toolset, hierarchical on-demand memory, execution-gated self-evolution, and staged context compression.
2. A concrete execution-gated self-evolution mechanism ("No Execution, No Memory") that converts only verified, successfully-executed trajectories into reusable SOPs and executable code while keeping the base tool layer fixed and separate from the evolving knowledge layer.
3. Reported empirical efficiency gains -- matching or exceeding two named baseline agent systems' task success while using roughly a third of their tokens on at least one long-horizon task setting -- across five evaluation axes, pending independent verification against the paper's own PDF and tables.

# Q10 Next Steps

* Limitations acknowledged in the retrieved secondary source: the sub-30k-token budget target requires careful context orchestration; reflection-based weight adaptation for exploration tasks remains preliminary without long-term validation; self-improvement logs currently require manual curation; and skill-tree management remains manual rather than automated.
* Open questions this note cannot resolve from the sources retrieved: how the four components' contributions decompose individually, since no per-component ablation beyond the memory-condensation comparison was present in the retrieved rendering; whether the "No Execution, No Memory" gate can be satisfied by an execution that superficially succeeds without being substantively useful, a concern this wiki's [Agent self-evolution](../topics/agent-self-evolution.md) topic already raises about validation-gated update loops generally; and how the fixed nine-tool interface would need to extend for task domains outside the five evaluated benchmarks.
