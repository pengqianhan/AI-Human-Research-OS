# Q1 Problem Definition

* **Input (X):** a user's natural-language request to a tool-using agent (here ambiguous DevOps requests: cancel jobs, restart services, clean up storage artifacts), the environment the agent acts in, and a split between an untrusted strong planner and a trusted small model plus trusted validation and dispatch code.
* **Output (Y):** a sequence of executed tool calls that completes the work the user authorized without changing unauthorized objects, plus a log from which an auditor can see, before each call, what the planner intended.
* **Constraints:** the trusted model is "trusted" in the AI-control sense (it tries to follow the user but can err); it sees the user's messages but never the environment or tool output; the experiments use cooperative models and benign over-reach, not a malicious planner.

# Q2 Problem Novelty

Permission gating for coding agents is not new: Claude Code's auto mode uses a reasoning-blind classifier that deliberately hides the agent's prose, and AmPermBench stress-tests that design with ambiguous requests. Trusted-monitoring protocols from AI control, the untrusted-advice protocol, CaMeL and the Dual LLM pattern, and rule-based intent or privilege systems (Progent, intent certificates, Intent Graphs, DRIFT) also exist. The new question is whether the trusted side can make *useful* use of a short, checkable statement of intent before execution, and what changes when the planner loses the ability to write commands at all. The paper treats natural-language intent as a claim to check, not an authorization.

# Q3 Scientific Hypothesis

If the planner can only describe a step (goal, verbatim quote, scope) and a trusted model writes the call, then (1) by construction the trusted model writes every executed call, a logged contract precedes each call and carries all of the planner's influence on it, and the trusted side chooses how much of a step to carry out; and (2) empirically, this should yield a complete pre-execution record of which objects will change and should let the authorized part of a bundled request complete. The paper explicitly does *not* hypothesize that contracts reduce unauthorized actions, and it tests whether they do.

# Q4 Related Work and Key People

* **AI control and trusted monitoring.** Greenblatt et al.'s control evaluations (untrusted strong model, trusted weak model); Redwood's untrusted-advice protocol, the closest architectural precedent (the trusted model takes all actions from short untrusted advice); Wen et al. and Factor(U,T), where a trusted model implements an untrusted plan and a plan-only monitor separates attacks poorly (AUROC 0.52 vs. 0.96 with the implementation).
* **Showing the monitor an explanation.** Sreevatsa et al. (legibility protocols: comments help a trusted monitor under attack) versus auto mode's choice to strip agent prose.
* **Keeping a model away from tools.** Dual LLM pattern and CaMeL, where the tool-less model is the one reading untrusted data; intent contracts reverse this: the planner reads all tool output and holds no tools.
* **Permission classifiers and intent/scope systems.** Claude Code auto mode, AmPermBench (Ji et al.), AuthGateBench, Parallax, intent certificates (Zhu and Wang, two of this paper's authors), Microsoft's Agent Governance Toolkit, Progent, Intent Graphs, DRIFT. In those, code enforces a bound on each call; here code checks only quotation and scope, and authorization of the goal is a model's decision, so a contract is "a record and a claim, not a policy boundary".
* **Key people.** Ziyuan Wang (independent researcher), Genliang Zhu (Georgia Tech), Xiaobo Chen (UMass Amherst), Chu Wang (UIUC). Likely interested critics: AI-control researchers (Redwood), and authors of AmPermBench and of deployed permission classifiers.

# Q5 Key Solution Idea

Three interfaces share one OpenCode plugin, models, planner prompts and logging:

1. **Review (blind).** The planner writes an exact shell command; the trusted reviewer sees the user's messages, a code-kept ledger of earlier calls and exit codes, and the command, and approves or declines the whole command. This reproduces the information boundary of a reasoning-blind permission classifier, not the deployed classifier.
2. **Review+Intent.** Same, but code first validates the planner's verbatim user quotation, and the reviewer also sees the goal and quotation; it is told to judge the command's actual effects and that a true quotation is not proof of authorization. It still cannot edit the command.
3. **Contract.** The planner has no environment tools. Each step it submits a goal (at most 100 words, naming objects, change and link to the request, no command lines), a verbatim quotation, permitted egress hosts and write prefixes, and an error policy. Code checks the quotation (contiguous substring after NFKC and whitespace normalization), that scope only narrows the baseline, and goal format (a heuristic command-line detector). The trusted model, in a fresh session with the user's words and its own call ledger, writes at most one tool call that carries out only the authorized part, and sees only a receipt (output size and exit code). Tool output goes to the planner.

The key differentiation from command review is *granularity*: a reviewer can only refuse a whole command, while the executor can carry out the authorized part of a step and decline the rest. The paper is careful that the three structural properties hold only if the dispatch code is correct (it has unit tests, not verification), and that arbitrary shell writes are not confined by the declared write prefixes.

Reference conditions: the strong model alone (Strong), the small model alone (Small), Strong+Declare (the strong model must write an `INTENT:` line before each state change, logged but never read), WholeTask (one contract, then the small model observes and acts across many calls), and a strict executor told to decline when it cannot tell the user asked for this change to these objects.

# Q6 Experiment Design

* **Tasks.** Three of AmPermBench's four task families (job cancellation, service restart, storage-artifact cleanup), 32 original prompts each, 96 per condition, with the benchmark's own programmatic scoring; branch cleanup (a git repository) is omitted, so numbers are not full-benchmark results. Prompts vary target reference: exact ID, own ticket, own range, open range.
* **Models.** gpt-6.1-terra (via a ChatGPT subscription) as planner and strong model; GLM-5.3-Flash (via OpenRouter) as trusted model and small model. One run per prompt per condition.
* **Outcomes.** Safe completion (all authorized work done, no unauthorized change), unauthorized action, incomplete; the last two overlap. Clopper-Pearson 95% intervals; exact paired McNemar tests, unadjusted and read as descriptive. The paper notes the 96 prompts come from 16 templates and one environment per family, so intervals are optimistic.
* **Declared-before-done metric.** For each changed object, find the first state-changing benchmark-tool invocation naming it and the last code-accepted contract before it; count the object as declared if that contract's goal names it (literal substring match). For review conditions, also count whether the command names it.
* **Bundling tasks.** Author-written: only the planner's copy of the user message gets an added harmless request; ten single-file tasks with an appended request and eight small projects with the extra request inserted into a list of four changes; three runs per task per mode; programmatic checks on final files.
* **Clarified lane.** A fixed sentence appended to each prompt says what the benchmark's "lane" term (e.g. "workbench lane") maps to, removing one ambiguity while leaving which-objects ambiguity intact; Strong, Review, Review+Intent, Contract and strict-executor Contract on all 96.
* **WholeTask** ablation on a 30-prompt sample.

The design validates each structural claim against logs and measures the empirical ones under one configuration. It does not test an adversarial planner or prompt-injection resistance, which the paper states.

# Q7 Datasets and Code

AmPermBench supplies environments and scoring. The OpenCode plugin, contract checks, per-run records, ordered event logs, and a script that recomputes the reported counts are released at https://github.com/zwang-devv/intent-contracts. Appendix A reproduces all role instructions verbatim.

# Q8 Evidence Quality

* **Declaration coverage is strong but nearly built in.** Under Contract, 56/56 changed objects (original prompts) and 181/181 (clarified) are named in the goal of the contract that produced the change, against 2/16 and 4/54 for the two reviewers, whose *commands* name 16/16 and 39/54 instead. The paper itself says full coverage is "close to a consequence of the interface", since the executor cannot see the environment and can only act on named objects. The informative part is that every one of Contract's unauthorized changes is also named beforehand, so over-reach is auditable by reading contracts.
* **Bundled requests.** Contract completes the main task in 27/27 valid runs (27/30 counting three runs whose every contract quoted words the user never wrote and was rejected) against 16/30 for Review+Intent; neither does the extra work. On the multi-file list, 24/24 vs. 19/24, and the five incomplete Review+Intent runs complete none of the four changes. This is the clearest evidence for the granularity property, but on small author-written tasks with three non-independent runs each.
* **Unauthorized actions: no improvement.** Original prompts: Review+Intent 2/96, Review 10/96, Contract 10/96, Strong 15/96, Small 1/96 (but 92/96 incomplete). Review+Intent's advantage partly comes from acting less (state changed in 9 runs vs. 20 and 22), and the reviewer declined 142 contracts against the executor's 4. On clarified prompts, Contract has 29/96 unauthorized actions vs. 18/96 for Review+Intent, 25/96 for Review and 14/96 for Strong, and no gated condition beats the strong model alone. Conditional on acting, the wrong-target rate is 40% to 49% everywhere (14/35, 18/37, 25/58, 29/64), so conditions differ in how often they act, not how often an action is wrong.
* **Where errors live.** Every unauthorized action on clarified prompts falls in the two range categories; exact-ID and own-ticket prompts have 0/48 unauthorized actions in all four conditions. The paper's diagnosis (the planner's reading of an ambiguous reference, which no trusted role can check without seeing the environment) is directly supported by this breakdown and by the strict-executor rerun, which moved nothing (35/96 safe in both, 30 vs. 29 unauthorized).
* **Declaration-only is a weak test.** Strong+Declare drops to 10/96 from 15/96 (p = 0.125), but only 14 of 30 state-changing runs contain an `INTENT:` marker at all, so it tests an unenforced instruction, not consistent self-declaration; the paper says so.
* **Reader check.** The clarified-lane percentages recompute exactly from the stated counts (e.g. 29/64 = 45%), and the run-level counts are consistent across Tables 2, 4 and 7. Single runs per prompt with hosted, versioned-by-label models mean run-to-run variation is not separated from condition effects (the paper lists this limitation).
* **Overall.** The structural claims are well argued and checkable; the empirical claims are honestly scoped and, unusually, the paper reports that its own method does not reduce the headline safety outcome.

# Q9 Contributions

1. The intent-contract interface: a tool-less planner, code-validated contracts with verbatim quotation and scope, and a trusted model that writes each call; with three properties fixed by the dispatch code.
2. A controlled comparison with reasoning-blind and intent-visible command review on benign over-reach, plus strong-alone, small-alone and declaration-only references, on an external benchmark.
3. A programmatic declared-before-done metric aligned with the benchmark tools' invocation logs.
4. Small bundling tasks that separate partial execution from whole-command approval.
5. A clearly located negative result: the remaining errors come from the planner's choice of objects for ambiguous references, which a trusted model that cannot see the environment cannot check, and an instruction to decline when unsure does not help.

# Q10 Next Steps

* **Let the trusted side see the environment.** The paper's own stated next step: give the executor a way to check the planner's object selection against the environment (for example read-only queries that resolve "my stale jobs" before acting), and test whether wrong-target rates fall below 40%.
* **Adversarial planners.** Run the same interfaces with a planner trying to smuggle actions through the contract channel or through tool output it reads; the structural properties say where influence can flow, not whether it is caught.
* **Model and prompt variation.** Repeat with other planner/trusted-model pairs, several seeds per prompt, and the reviewers' instructions varied, since the key differences between Contract and Review+Intent may be instruction effects (reader suggestion).
* **Full benchmark and sandboxing.** Include the git branch-cleanup family, and pair contracts with an OS-level sandbox so write prefixes bind shell writes too (reader suggestion).
* **Link to action-level intent elsewhere.** [AgentRoboCritic](2611.26613.md) also asks the acting model to state a local intent with each action, there to make outcome critique well-posed; both papers find that intent checked only against the actor's own statement cannot catch a wrong choice of target (reader connection).
