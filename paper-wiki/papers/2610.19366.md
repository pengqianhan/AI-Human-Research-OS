# TL;DR

Agents that remember what they saw, heard, or did on a screen or in a room have to decide two things: in what form each experience is kept (the raw image, a feature vector, a caption, a graph node, a hidden state, an adapter), and whether the rules that maintain memory may themselves change with use. This survey sorts about three hundred systems along those two choices and shows they are linked. The form decides what can later be checked, corrected, or deleted; and the few systems whose memory rules learn from deployment all keep some memory as editable text or structure. Read it if you design memory for multimodal or embodied agents, or if you need a test for whether a "self-evolving memory" claim is more than ordinary memory updating.

# Overview

**Scope.** Memory is defined as experience-derived state that persists beyond the step in which it is formed and later affects reasoning, generation, planning, or action, where at least one non-text modality contributes to its formation or use. Transient activations, one-pass reasoning traces, and incidental prompt context are excluded unless deliberately persisted and reused. The survey separates memory from *context* (what the model currently sees; a retrieved image is both) and from long-context processing and context management. Coverage spans images and documents, video and audiovisual streams, audio and speech, GUI interaction, and embodied or 3D environments. The current version of the taxonomy holds 297 memory architectures and 82 benchmark records.

**Why multimodality changes the problem.** Text experience can be stored compactly in a form an LLM can read and edit. A frame, a sound, or a 3D scene cannot always be reduced to one representation without loss, so each storage choice keeps some aspects (fidelity, efficiency, editability, recoverability of the source, fit with the downstream model) and discards others. And the same entity may be held as raw media, features, captions, and a world-state record at once, so maintenance must keep several linked representations consistent.

**Lifecycle.** Two coupled stages: *formation and representation* decides what is kept, how it is cut into memory units (an image, a region, a clip, an event, an object track, an interface state, a transition, a trajectory, an episode), and in what form; *management* decides how it persists, changes, is accessed, and is used. No access mechanism can recover what formation discarded.

**Positioning.** Earlier agent-memory surveys classify memory by source, representation, function, temporal scope, or operation, and multimodal ones by memory types, VLM taxonomies, architectures, benchmarks, and applications. This one makes the operational lifecycle the unit of analysis: how experience becomes memory, how the representation limits later retrieval, revision, and verification, and where adaptation happens.

# Framework

| Axis | Branch | What it holds | Main trade-off |
|---|---|---|---|
| I. Formation and representation | Source- and modality-specific | Retained source evidence (images, crops, screenshots, frames, audiovisual segments, posed RGB-D); or modality-native encodings and geometric state (visual tokens, patch features, voxel maps) | Source evidence is recoverable and checkable but costly; encodings are compact but lossy and tied to a compatible model interface |
| | Cross-represented explicit | Perception-to-text records (captions, events, facts, profiles, procedures); or spatial, temporal, and cross-modal structured memory (scene graphs, temporal knowledge graphs, schema records) | Inspectable, searchable, editable per entry; detail lost at write time cannot be recovered |
| | Internalized latent and parametric | Persistent latent state (hidden states, memory tokens, deliberately retained KV caches); or experience-conditioned parameters (weight updates, per-task or per-video adapters) | Tight integration with inference; hard to inspect, edit, trace, or transfer |
| | Hybrid (a composition, not a fourth type) | Several of the above, often *source-linked*: an abstract record keeps a pointer to the observation it came from | Efficient abstraction plus grounded recall, if links stay valid as records change |
| II. Memory management | T1 Static | Memory formed once, then only read | Stable and safe from unverified writes; keeps formation errors and goes stale |
| | T2 Dynamic | Memory state changes under a policy fixed during deployment (heuristic or trained beforehand) | Predictable updates; the policy cannot learn from its own mistakes |
| | T3 Self-evolving | Feedback persistently revises the policy that writes, maintains, or retrieves | Can adapt to deployment; needs attribution and validation of policy changes |

Two classification rules carry the taxonomy. On Axis I, a system is classified by the representation *ultimately supplied to the reasoner or policy*, not by what is used as an index. PixelRAG indexes screenshot tiles with visual embeddings but feeds the screenshots themselves to the VLM, so it is source-evidence memory. On Axis II, T3 is written as M_{t+1} = U_{π_t}(M_t, x_t) with π_{t+1} = E(π_t, f_t), where f_t is a task outcome, verifier judgment, or user correction. Changes to retrieval keys, skill descriptions, or usage statistics stay T2 as long as the selection and update mechanisms do not change. Each architecture is placed at its highest supported tier.

T2 is broken into five operations, each described by its *representation-handling pattern* (within one representation, coordinated across separable representations, or projected or fused across them) and its *computational mechanism* (heuristics, a prompted LLM, a trained update module, or iterative optimization): **update** (add or integrate new evidence), **consolidation** (merge or abstract accumulated records), **revision** (correct a record that new evidence contradicts), **reorganization** (move records between tiers, relink graph edges, reindex), and **forgetting** (remove, reduce detail, or lower retrieval priority). T3 is broken into write-policy, maintenance-policy, and retrieval-policy evolution.

The cross-axis analysis (Table 1 of the paper) states what each tier needs from the representation, each tier inheriting the previous one's needs:

* **T1:** formation keeps task-relevant information in a form that can be located and reused.
* **T2:** *editability* with a minimal sufficient operation scope; *verifiability* through a trace linking previous state, operation, evidence, and result; *reversibility* through versions, operation logs, or inverse operations (regenerating a summary from a stochastic LLM will not restore the old one); and *update propagation* that is complete but selective across linked representations.
* **T3:** *policy addressability* (an identifiable component to revise), *policy-level feedback attribution* (separating failures of writing, maintenance, retrieval, reasoning, and action), and *persistent, validated policy revision* tested on later or held-out cases for regressions.

# Key Techniques

## Source- and modality-specific memory

* **Retained source evidence.** The memory unit stays in its original modality and can be handed back to the model. For images and GUIs this preserves layout, typography, color, and fine spatial detail. For video and audio the evidence must first be localized in time, and the survey sorts organizations into frame-level (ToolMerge composes global, region, and OCR retrieval tools over sampled frames), event-level (HippoMM writes event records with summaries, boundaries, and pointers to source spans), and entity-level (M3-Agent links text, image, and audio evidence to persistent people, objects, and events). Embodied systems pair retained images with spatial structure (GraphEQA, DovSG).
* **Encoded features and geometric state.** Video systems persist the features themselves: MovieChat merges similar adjacent frame tokens into long-term memory, MA-LMM keeps patch features as cross-attention keys and values, Flash-VStream combines low-resolution centroids with high-resolution key frames. Embodied systems persist geometry (DynaMem's sparse voxel map with timestamps and vision-language features) or policy-facing history (MemoryVLA's perceptual-token bank). The compression is generally non-invertible and model-specific. Image agents mostly keep source images and use embeddings only for indexing, and persistent audio-feature memory is barely explored.

## Explicit memory

* **Perception-to-text.** Video agents turn frames into event records (VideoAgent's temporal descriptions; Video-EM's when/where/what/who episodes; ReMA's timestamped clip descriptions merged as overlapping observations arrive). MIRIX routes screens and dialogue to six specialized textual memory components. The limit is the semantic bottleneck at write time: what the captioner did not judge salient is gone, and pure text is rare for image and embodied memory, which depend on details and metric relations.
* **Structured memory.** ConceptGraphs fuses open-vocabulary detections into 3D object nodes and relations; DovSG locally refines a changing scene graph that the planner reads as the current world state; GraphEQA's hierarchical scene graph also tells the agent where to explore next. PyraVid and WorldMM give video a fact-clip-narrative graph and multi-resolution temporal knowledge graphs. TAME separates dynamic from stable personal attributes, and PolarMem links memories to concepts with HAS and NOT_HAS edges so verified absence can be represented and used to suppress similar-looking but excluded memories. Structured GUI memory is uncommon because layouts change across versions and window sizes.

## Latent and parametric memory

* **Latent state.** ReKV and MuKV retain video KV caches and restore query-relevant blocks; VisMem and TRAM keep visual evidence and intermediate reasoning influential over long generations; L2-VMAS shares perception and thinking memory banks among vision-language agents; Mem-W compresses retrieved trajectories and expired in-session history into memory tokens; LaMem-VLA compresses short- and long-term vaults into fixed-length tokens for action generation.
* **Parametric memory.** MemEIC keeps separate visual and textual LoRA adapters for knowledge edits, alongside explicit edit records; Frames2LoRA generates a video-specific LoRA from one forward pass of a hypernetwork, so later questions need no visual tokens; SE-GA consolidates GUI experience into the policy with LoRA updates; VLA-Pro stores per-task adapters indexed by procedural states and composes them by similarity.

## Hybrid memory

VimRAG keeps a reasoning DAG whose nodes carry summaries and a visual-token bank sized by relevance and recency. FOLIO stores structured stream records with references to cached keyframes it can restore. MementoGUI keeps textual event summaries with crops of the relevant screen regions and resolves region identifiers back to crops after compression. VISTA keeps revisable notes beside a lossless frame archive. ObsGraph builds a room-view-object hierarchy that also tells the agent whether to search another room, refine a view, or explore a frontier.

## Management mechanisms

* **T2 examples.** FluxMem consolidates by recency tier; ReMA is the survey's worked example of why merging and refining records under a fixed rule is T2, not T3; tier migration (MovieChat short- to long-term, TAME dynamic to static), relinking (DovSG's local subgraph, M3-Agent's face-voice association), and reindexing are reorganization. Forgetting comes in four kinds: evicting active evidence (FIFO, reservoir sampling, recency weighting), decaying detail (downsampling memory images as they age), decaying accessibility (a time-dependent retrieval priority restored on recall), and coordinated forgetting that drops detail in one representation while keeping a compact one.
* **T3 examples.** Write policies adapted from task feedback, including failure traces that repair graph construction and source-to-record mappings; maintenance policies that retain information longer after a failed query reveals it was dropped; retrieval policies distilled from successful and failed retrieval trajectories (RRM in long video), validated rules prioritizing directly observed object records, and utility estimates updated from downstream feedback in a clinical setting.

## Systems infrastructure

The survey separates *logical memory* (the experience-derived state), its *physical realization* (records, tensors, adapters, replicas, indexes), and *materialized execution state* (what a computation actually consumes). It then reviews residency across HBM, DRAM, SSD, and pooled memory (ReKV, Mooncake, InferCept's preserve/swap/discard, Continuum's retention TTL, MORI); transfer, compression, and recomputation (CachedAttention, CacheGen, Cake, MPIC, TokenCake); reuse and scheduling (SGLang's radix prefix cache, Prompt Cache, CacheBlend, Preble, ThunderAgent, KVFlow); and consistency (ownership, publication of in-progress writes, copy-on-write, permission-filtered retrieval, embedding backfill after model updates). Two rules from this section matter for classification: evicting a reconstructible cache or redundant replica need not forget the underlying experience, and neither cache replacement (as T2 adaptation) nor workload-responsive scheduling (as T3 policy evolution) counts on its own.

# Case Studies

## Application Domains

* **Recall and evidence-based reasoning:** multimodal QA, episodic retrieval, long video and audio, enterprise document analysis (MARDoc), financial reasoning (FinAcumen). The property it stresses is recoverable provenance and temporal validity.
* **Personalization and cross-session continuity:** M2A, TAME, Persode; identity scoping, selective retention, and revising preferences without cross-user leakage.
* **Control and task execution:** GUI skills that transfer across interface changes (MAGNET), embodied navigation and manipulation, market decisions (FinAgent), business-document extraction (Matrix), phishing response (MemoPhishAgent). Memory must change what the agent does and stay revisable.
* **Generation and world consistency:** slide creation (MemSlides), agentic video with executable event structures, financial reports (FinSight); the regime with the fewest dedicated memory benchmarks.

## Evaluation landscape

Benchmarks are described by six shared capabilities: cross-modal evidence (CE), long-range evidence (LE), state changes (SC), conflicting memories (CF), unanswerable queries (UQ), and memory-grounded action (MA). Modality-specific capabilities sit beside them (image: fine-grained detail, entity tracking, visual change; video: temporal localization, temporal relations, multi-event integration; audio: speaker tracking, acoustic cues, repair persistence; GUI: interface state, action-outcome association, cross-session reuse; embodied: spatial memory, object state, task progress). The authors map LE, TL, ME, and XR to T1, the state-change and conflict capabilities to T2, and UQ and MA to utilization; no label alone establishes T3. Examples include [LoCoMo](../concepts/locomo.md), whose shared images are replaced by captions in the original QA and summarization experiments, and ChatMem-Bench, introduced with [VoiceMem](2608.26005.md) (316 questions over 53 hours of dialogue). The survey's reading: coverage is broad in modality and narrow in lifecycle. Retrieval is well tested; conflicts and insufficient evidence are sparse; memory-grounded action sits mostly in GUI and embodied benchmarks; source provenance, end-to-end attribution, and policy adaptation are weakly evaluated.

# Evidence Boundaries

* **What the survey itself establishes** is a vocabulary, a two-axis classification, a set of tier-specific representation requirements, and corpus counts under its own classification. The counts: of 297 architectures, 221 (74.4%) update memory state or policy during operation, 204 (68.7%) at T2 and 17 (5.7%) at T3, which leaves 76 at T1 (reader subtraction). Hybrids are the largest representation category with 139 (46.8%). Of the 17 T3 systems, 13 are cross-represented explicit memory and 4 are hybrids with an explicit component; no source-preserving or latent/parametric-only system is T3 "to the best of our knowledge".
* **How the corpus was built is not described** in the text read: no search protocol, inclusion window, or inter-annotator check for the tier and representation labels, and the corpus is called "taxonomy-current", so counts may change between versions. The mosaic and incidence figures and the per-capability benchmark coverage percentages (Figure 12) were read only through their captions.
* **Per-system performance claims are relayed, not compared.** Statements such as FluxMem's "competitive performance" or VLA-Pro's cross-task transfer gain come from each system's own paper under its own setup; the survey runs no common benchmark.
* **Some patterns are argued, not counted.** "Policy evolution is concentrated on retrieval" (Section 8.2.2) is stated without a per-target breakdown of the 17 T3 systems in the text read. The explanation for why T3 needs explicit memory (explicit units give identifiable targets for revision) is the authors' interpretation of a 17-system pattern.
* **The prescriptions are proposals.** A minimal provenance bundle, validity states (current, historical, superseded, uncertain), selective verification, representation-aware budgeting, forgetting specified across representations, and lifecycle-staged evaluation are directions without empirical tests here.
* **Reader-constructed elements in this note:** the T1 count, the exemplar-table framing, and the takeaways below.

# Takeaways

Reader notes on what to carry into one's own work:

1. **Classify a memory by what the model reads, not by how it is indexed.** It settles many apparent disagreements about whether a system is "visual" or "textual" memory.
2. **Test self-evolution claims with the T2/T3 line.** A system that rewrites records, keys, or skill descriptions under a fixed rule is updating memory, not learning how to manage it. This is a useful filter for papers in [Agent self-evolution](../topics/agent-self-evolution.md).
3. **Plan for reversibility at write time.** Keeping the source observation is not enough to undo an LLM-generated revision; keep the previous version or an operation log.
4. **Deletion and verification pull against each other.** Provenance and version history make memory checkable and also keep copies alive; a forgetting request has to be specified across every derived representation.
5. **Evaluate by stage.** Separate formation, maintenance, access, and utilization, and use counterfactual removal of retrieved evidence to show an answer actually depended on memory.
6. **Project fit.** This repository's own memory layers (global and project memory files, the cognition cache) are explicit textual memory maintained under rules written in instructions, which places them at T2 in the survey's terms; their provenance links and size-and-decay rules map onto its verifiability and forgetting requirements.

# Open Questions

* What minimal provenance should every formed memory carry, per modality and representation, so that abstraction stays recoverable without retaining all source observations? (authors, 8.1.1)
* Can latent or parametric memory expose units that management can identify, revise alone, and verify afterwards, without losing the compactness that motivates it? (authors, 8.1.2)
* When should new evidence replace an older state, when should both coexist, and when should uncertainty be preserved rather than resolved? (authors, 8.2.1)
* How can delayed, cross-modal feedback be assigned to the earlier write, merge, revision, or forgetting decision that caused a failure, so policy evolution extends beyond retrieval? (authors, 8.2.2)
* How much change in which modality a revised policy relies on is healthy adaptation, and when is it a loss of grounding that should block the update? (authors, 8.3.3)
* How can forgetting be verified when the target information has spread into captions, embeddings, summaries, latent states, and shared parameters? (authors, 8.3.4)
* Reader question: the 17 T3 systems all have explicit memory. Is that because explicit memory is needed for policy evolution, or because policy evolution is mostly built today with LLM prompting over text, which only works on explicit memory? A latent-memory system with a learned, feedback-updated write gate would separate the two.
