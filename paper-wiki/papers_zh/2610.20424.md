# Q1 问题定义

* **输入（X）：** 在一个重建的支付业务环境中的一次客户请求。任务固定了客户目标、初始数据库状态、预定事件和客户场景。智能体有 9 个常驻工具，用来检索 789 份知识文档、查询记录，并发现和调用 601 项业务能力；一个 LLM 用户模拟器扮演客户，掌握客户的私有事实和材料，并执行审批等客户侧操作。
* **输出（Y）：** 完整的执行历史 τ = (s0, e1, s1, ..., eT, sT)，包括工具执行、环境事件和业务状态，最后落到一个终态。
* **衡量什么：** 严格成功率，Success = G ∧ P ∧ F。G 检查请求的结果和允许的终止条件；P 检查约束执行过程的要求（审批必须覆盖实际执行的条款且发生在操作之前，最低备付金之类的约束必须全程成立）；F 检查受保护对象和禁止的副作用。所有检查都是针对状态、账本、回执和事件历史的确定性代码，不用 LLM 评审，也不把执行过程与参考轨迹逐步比对。
* **约束：** 规则分散在多份文档中，其中有过时的指引，也有相关产品的指引，智能体必须根据适用范围（scope）、版本和生效期判断哪条规则适用。多个工作流共享资金、授权额度和截止时间，有些信息会延迟到达，所以"等一等"可能让截止时间变得无法满足。

# Q2 问题新颖性

作者认为，现有长程智能体基准大多只看最终任务是否成功，看不到"中途违规、事后补救"的情况，比如一笔未经授权的付款，资金后来退回了。论文把 BizBench 放在三条工作线之间。长程技术类基准（SWE-bench、Terminal-Bench、SWE-Milestone、Long-Horizon-Terminal-Bench）在终态上检查软件进展。τ 系列（τ-bench、[τ²-Bench](../concepts/tau2-bench.md)、τ-Knowledge）和企业类套件（WorkArena、TheAgentCompany、CRMArena、CRMArena-Pro）研究受政策约束的工具使用和组织语境；[ToolSandbox](../concepts/toolsandbox.md) 被引用为有状态、受政策约束、需要知识访问的工具使用基准。[AutomationBench](../concepts/automationbench.md) 只看最终的应用状态，不规定工具调用顺序。BizBench 声称的新组合是：工作流之间通过共享资源、截止时间和先前承诺相互关联；指引是否适用取决于范围、版本和生效期；对执行历史做过程与保护要求的确定性检查，同时仍接受不同的合法策略。

# Q3 科学假设

如果评测器既检查任务达成了什么，也检查任务是如何执行的，它就会否决那些只看结果时会被算作成功的运行；在目标上看起来有能力的智能体，一旦强制执行审批、持续约束和"选对适用规则"，可靠性就会下降。论文的检验方式是：对 10 个模型分别报告目标、过程、保护和严格通过率；统计达成目标却未通过 P 或 F 的运行；再用信息消融定位成功率损失在哪里（找到适用文档，还是从客户那里问出客户自己的事实）。

# Q4 相关工作与关键人物

* **长程技术类基准。** SWE-bench、Terminal-Bench、SWE-Milestone（在各里程碑检查功能完成度和回归）、Long-Horizon-Terminal-Bench（在终态上做子任务检查）；WebShop、Mind2Web、WebArena、VisualWebArena、OSWorld 等网页与桌面基准作为更大的背景。
* **商业工作流智能体。** τ-bench、τ²-bench、τ-Knowledge；WorkArena 和 WorkArena++；TheAgentCompany；CRMArena 和 CRMArena-Pro；AutomationBench。运行器处理上下文溢出的规则也来自 τ-Knowledge。
* **过时与随时间变化的信息。** HoH（过时信息对检索增强生成的影响）和 TimelyRAG（在相互重叠、不断演化的文档上做时间敏感检索）为带版本的指引提供了动机。
* **规划与澄清。** ReAct、Toolformer、Reflexion、Voyager、Tree of Thoughts、LATS；*Ask early, ask late, ask right* 研究澄清对长程智能体何时有用。
* **关键人物。** 共同第一作者为 Enhan Zhao（北京大学、Ant International）和 Yongqi Tong（Ant International）；通讯作者 Wei Wu（Ant International）；北京大学的 Di He 是合作者。Tong 也是被引用的"silicon concierge"工作（把复杂业务流程内化到单一模型）的作者之一。可能的批评者：τ-bench 与 τ-Knowledge 的作者（Yao、Narasimhan、Barres、Shi），BizBench 扩展了他们的用户模拟器和政策文档设计；同样不规定工具顺序的 AutomationBench 作者；以及 Salesforce 的 CRMArena 团队。

# Q5 关键解决思路

**给执行过程打分，而不只给结果打分。** 评测器区分"已执行的操作"与"提议""审批"或"被拒绝、没有副作用的调用"。审批检查要求审批覆盖实际操作及其条款、来自有权审批的人，并且发生在执行之前；持续性检查在每次相关状态变化时检验约束。论文的例子：账户里有 60 美元，必须始终保留 20 美元；支付 60 美元的预付费会被工具接受，但当场就跌破下限，之后即使退款让期末余额恢复，也弥补不了这次违规。由于不与参考轨迹比对，不同的合法操作顺序都能满足同一组标准。

**带范围、版本和生效期的规则。** 源业务文档被整理成 SOP（算法 1：抽取带证据链接的候选工作流，归并成计划，生成 SOP，逐一对照证据审查，删除冲突无法解决的内容，再为模拟改写敏感细节）。凡是能用范围、版本或生效期解释的差异都保留下来，所以环境文档中现行指引与历史指引并存。

**相互关联的工作流。** 任务把共享资金或授权额度、或者一方输出是另一方前提的工作流组合在一起，预定事件还把不同工作流的时间联系起来。在交付案例（Q34）中，优先配送的预订窗口在仓库确认到达之前就关闭了，等待确认的智能体无法赶上第一个截止时间。在 Q24 中，最终付款都正确，但退款手续费、担保费、中间行扣费和补足费合计 80 美元，超过了 75 美元的费用预算，任务仍然失败。

**经过验证的任务。** 每个发布的任务都有一条参考（Golden）轨迹，从初始状态重放可以通过。评测器还在以下情形上受过检验：其他合法轨迹、针对性的违规轨迹（临时跌破备付金必须让 P 失败）、改变事实后合法性随之改变的情形，以及不应改变结果的幂等重试。5 名研究者和一个业务领域专家团队审查了任务和检查项，只有同时通过验证和审查的任务才保留。

# Q6 实验设计

* **模型。** Claude Opus 5、GPT-6 Sol、GLM-5.3-Flash、DeepSeek-V4.1-Flash、DeepSeek-V4-Pro、Muse Spark 1.3、Qwen3.8-27B、DeepSeek-V4-Flash、Qwen3.5-397B-A17B 和 Qwen3.5-9B，全部跑 50 个任务。Claude Opus 5 和 Muse Spark 1.3 每个任务只跑一次，其余模型跑三次，取单次成功率的平均。
* **运行器。** 每次运行使用独立的数据库副本。对 token、工具调用次数或调度步数不设累计上限，只设墙钟超时和工具错误阈值。若服务商报告上下文溢出，就在模型可见的上下文中替换最早四分之一的知识检索与文档读取结果，同时保留完整记录。默认客户模拟器是 DeepSeek-V4.1-Flash。基础设施故障和模拟器协议故障与业务结果分开记录。
* **指标。** G、P、F、中间失败（¬(P ∧ F)）、严格成功率，以及 pass^k（在 k 次运行中每次都成功的任务比例，对所有 k 次子集取平均）。
* **消融与诊断（DeepSeek-V4.1-Flash）。** Gold-doc（直接提供适用文档）和完全客户披露（客户知道的所有事实都写进开场请求，但仍需审批）；按每个任务 Golden 调用次数的 1.2、1.5、2.0 倍做事后的工具调用上限截断；轨迹统计（完全相同的重复数据库读取、工具错误、读取的不同文档数）。
* **模拟器检查。** 两个角色都用 DeepSeek-V4.1-Flash，比较原始和修订后模拟器提示词下的协议违规；以 Qwen3.8-27B 为智能体，比较四种模拟器模型。
* **没有做的。** 人类基线、主表的置信区间，以及在 DeepSeek-V4.1-Flash 以外模型上的消融。

# Q7 数据集与代码

冻结版本包含 50 个任务、789 份知识文档（正文 598,827 个 token，cl100k_base 分词）、9 个常驻智能体工具、601 项可发现的业务能力、10 个模拟器工具、398 个可查询的数据库集合（227 个非空）和 2,994 条记录。Golden 轨迹平均每个任务 111.8 次助手工具调用（中位数 100.5，范围 51-282）、28.6 次模拟器调用、读取 5.4 份不同文档和 29.9 条不同记录、执行 14.2 个业务请求。出于保密，敏感业务细节被改写，记录是合成的，所以环境重建的是公司的决策逻辑而不是真实数据。代码在 [ant-intl/BizAgentBench](https://github.com/ant-intl/BizAgentBench)（`hf papers info` 显示 1 星）；论文首页还链接了 Hugging Face 上的发布。本笔记没有打开二者。

# Q8 证据质量

* **有支撑的结论。**
  * *前沿模型仍有很大差距。* 严格成功率：Claude Opus 5 为 64.0%，GPT-6 Sol 为 61.3%，GLM-5.3-Flash 和 DeepSeek-V4.1-Flash 为 43.3%，DeepSeek-V4-Pro 为 39.3%，Muse Spark 1.3 为 38.0%，Qwen3.8-27B 为 32.7%；DeepSeek-V4-Flash 为 5.3%，Qwen3.5-397B-A17B 为 0.7%，Qwen3.5-9B 的 150 次运行全部失败（表 1）。
  * *过程检查能抓住目标检查漏掉的问题。* 每个模型都有中间失败，从 Claude Opus 5 的 50 次中 2 次（4.0%）到 Qwen3.5-9B 的 150 次中 125 次（83.3%）；每个模型的 P 通过率都低于 F（18.7-96.0% 对 87.3-100.0%）。达成目标却未通过 P 或 F 的运行：DeepSeek-V4.1-Flash 有 150 次中 5 次（4 次跌破现金备付下限后又补回，1 次在审批前尝试执行并被拒绝），Qwen3.8-27B 有 14 次（其中 8 次是被拒绝的审批前执行），所以 Qwen3.8-27B 42.0% 的目标达成率降到 32.7% 的严格成功率。
  * *运行结果不可重复。* pass^3：GPT-6 Sol 为 40.0%，DeepSeek-V4.1-Flash 为 26.0%，GLM-5.3-Flash 为 22.0%，Qwen3.8-27B 为 10.0%，DeepSeek-V4-Flash 和两个 Qwen3.5 模型为 0%。
  * *客户事实比文档更关键。* 对 DeepSeek-V4.1-Flash，直接给出适用文档让严格成功率从 43.3% 升到 50.0%，给出全部客户事实则升到 70.0%；即使如此仍有 30% 的任务没有解决（表 2，正文误称为表 3）。
  * *轨迹长不等于有进展。* DeepSeek-V4.1-Flash 平均 191.3 次助手调用，Golden 轨迹为 111.8 次；多出来的部分在信息获取（数据库查询 111.1 次对 59.2 次，检索或读文档 43.3 次对 11.5 次），业务调用和执行则相近（26.9 对 28.7）。它打开 20.1 份不同文档，Golden 为 5.4 份。GLM-5.3-Flash 用 118.3 次调用、9.4 份文档就达到同样的严格成功率；Qwen3.5-397B-A17B 用 216.4 次调用，150 次运行只成功 1 次。Qwen3.5-9B 每次运行收到 101.6 次工具错误回复，其中 71% 来自查询非公开资源。
  * *预算会造成明显损失。* 把 DeepSeek-V4.1-Flash 的运行事后截断在 Golden 调用次数的 1.2、1.5、2.0 倍，严格成功率分别只剩 0.7%、6.7%、26.7%，不设上限时为 43.3%。
* **比标题结论更弱或更窄的地方。**
  * *排名第一依赖单次运行。* Claude Opus 5（64.0%）和 Muse Spark 1.3 每个任务只跑一次，而 GPT-6 Sol 的 61.3% 是三次运行的平均，其 pass^3 为 40.0%，论文也没有给出置信区间。2.7 个百分点的领先只相当于一到两个任务（笔记作者观察）。
  * *分析集中在一个模型上，而它同时扮演客户。* 消融、调用上限和轨迹研究都用 DeepSeek-V4.1-Flash，而它也是默认模拟器，所以它作为智能体时是在和自己的副本对话。模拟器模型检查（四种模拟器下严格成功率 30.7-36.0%，与默认的 32.7% 最多相差 3.3 个百分点）只用了 Qwen3.8-27B 作为智能体（笔记作者观察）。
  * *调用上限是事后截断。* 在调用次数处截断已完成的运行，只能说明成功运行有多长，不能说明告知预算后智能体会怎么做，所以这张表是损失运行数的上界，而不是一次按预算进行的评测（笔记作者推断）。
  * *是重建而非真实环境。* 业务逻辑是真实的，但记录是合成的，敏感细节经过改写；50 个任务与真实客户请求分布有多接近，论文没有报告。
  * *对模拟器提示词敏感。* 原始模拟器提示词在 50 个任务中有 4 个出现协议违规，修订后为 0（配对 McNemar 检验 p = 0.125），所以修订的依据是一个很小且不显著的差异；论文把它设为默认，但没有报告智能体分数是否随之变化。

# Q9 贡献

* 一个让业务要求可以在执行历史上检验的基准：成功要求目标、过程和保护检查同时通过，因此补救过的中间违规仍算失败。
* 一套环境构建方法：从业务文档中抽取带证据链接的 SOP，指引带有明确的范围和生效期，工作流通过共享资源和时间相互关联，LLM 客户的审批绑定到具体条款。
* 一套超出参考轨迹重放的评测器验证流程：其他合法轨迹、针对性违规轨迹、事实改变、幂等重试和专家审查。
* 能区分失败来源的测量：目标与过程与保护、运行间可重复性、文档检索与客户信息引导、冗余与有效的工具使用。

# Q10 后续方向

* **作者提出的。** 让智能体把信息收集与行动选择协调起来：判断证据何时足以行动，以及随着执行推进哪些义务必须持续满足。
* **按预算评测（笔记作者建议）。** 事先告诉智能体工具调用预算，而不是截断已完成的运行，并报告严格成功率与实际调用次数的关系；GLM-5.3-Flash 只用 DeepSeek-V4.1-Flash 62% 的调用次数就达到了同样的分数。
* **把模拟器和被测智能体分开（笔记作者建议）。** 用不在被测之列的模型家族做模拟器重跑主表，并对最强的几个智能体也报告模拟器模型带来的波动，而不只对 Qwen3.8-27B。
* **把信息引导当成可训练的技能（笔记作者建议）。** 完全披露带来的 43.3% 到 70.0% 的提升，隔离出了"向客户问对问题"这一能力；可以针对业务信息引导训练或提示一个澄清策略，并直接用这个上限来衡量。
* **与"先证据后行动"类基准的联系（笔记作者的关联）。** [SafeActBench](../papers/2610.07753.md) 检查每个关键操作之前是否有绑定到正确实体和状态的证据。用这个视角给 BizBench 的审批前执行尝试打分，可以看出它们源于证据缺失，还是忽略了智能体已有的证据。

# 相关

* [智能体基准与评测](../topics/agent-benchmarks.md) - 一个商业工作流基准，成功要求在执行历史上同时通过目标、过程和保护检查，评测器在其他合法轨迹和针对性违规上做过验证。
* [模拟用户评测](../topics/simulated-user-evaluation.md) - LLM 客户掌握私有事实并给出绑定具体条款的审批；论文测量了两种提示词下的协议违规，以及四种模拟器模型下严格成功率的波动。
* [τ²-Bench](../concepts/tau2-bench.md) - BizBench 所扩展的 τ 系列之一；BizBench 增加了带版本的指引、通过共享资源和截止时间关联的工作流，以及对执行历史的过程检查。
* [AutomationBench](../concepts/automationbench.md) - 同样只看结果、不规定工具顺序；BizBench 另外在关键步骤检查授权等要求。
* [ToolSandbox](../concepts/toolsandbox.md) - 被引用为有状态、受政策约束、需要知识访问的工具使用基准；BizBench 认为只看最终成功会掩盖中间违规。
* [FDE-Gym](../papers/2610.22350.md) - 另一个企业基准，最大的下降同样来自被隐去的信息而不是工程能力：FDE-Gym 的领先模型在必须自己发现约束时损失 0.28，BizBench 的完全披露消融让 DeepSeek-V4.1-Flash 提高 26.7 个百分点（笔记作者的关联）。
* [From Evidence to Action（SafeActBench）](../papers/2610.07753.md) - 同样用确定性评测器而非 LLM 评审给关键操作的过程打分（笔记作者的关联）。
