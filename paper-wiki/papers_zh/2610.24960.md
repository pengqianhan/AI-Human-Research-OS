# Q1 问题定义

* **输入（X）：** 开发者为 AI 协作者（AI coworker）选定的能力需求（多轮沟通、跨服务收集信息、协调工具、判断何时不该行动），被转化为一份覆盖计划，列出服务组合、难度和场景，再加上服务目录和示例任务。
* **输出（Y）：** 可执行的任务环境 T_i = (u_i, s_i⁰, A_i, G_i)：用户请求、初始服务记录、工具接口和评分检查；由此得到用于 SFT 的经筛选的教师示范、用于在线强化学习的任务引用，以及在其上训练出的紧凑学生模型（PocketWorker）。
* **约束：** 同一实体在不同服务中的记录必须一致；回答所需的信息必须能通过工具发现，但不能在请求中泄露；评分器必须奖励预期的动作和结果，并在调用被禁止的动作时把安全分置零；训练任务独立于基准测试集构建。

# Q2 问题新颖性

为智能体合成可执行任务是一个活跃方向：AgentGen 和 MATRIX 构建环境或场景，APIGen-MT 把任务蓝图与多轮交互相连，CUA-Gym 为计算机使用联合构建指令、环境和奖励，CuES 通过探索已有工具环境生成任务，DreamGym、Qwen-AgentWorld、PatchWorld 和 AgentEvolver 则模拟或自适应地生成环境。Nemotron-Terminal、SERA 和 OpenThoughts-Agent 公开了终端与编码智能体的数据选择，Occamy 把基于执行的训练扩展到协作者工作负载；Cowork-Gym 是同期工作。论文对自身的定位偏实用，而非提出新问题：如何把目标协作者能力转化为同时支持模仿学习和强化学习的可执行任务。它的区别在于：请求、记录、工具和检查都来自同一份规格，从而保证跨服务一致；每个生成的评分器都要通过评分一致性门控；安全场景由单独的角色编写评分器。

# Q3 科学假设

如果把目标协作者能力转化为多服务任务规格，并让其中的记录、工具和评分检查都来自同一份规格、在使用前经过程序化验证，那么在这些任务上的教师执行能提供有用的 SFT 监督，而这些任务本身也能提供可用的强化学习信号。在其上训练的紧凑模型应当在独立的协作者基准上显著提升，在任务所针对的能力（多轮交互）上提升最多，且收益随数据量增长；在构建的任务上，强化学习的训练奖励应当上升。

# Q5 关键解决思路

**从能力到规格。** 覆盖计划中的每个槽位写明任务、服务（例如 CRM、工单系统和邮件）、类别、难度、语言、固定的参考日期，以及包含筛选条件、干扰项和动作约束的场景。一个大语言模型根据槽位、服务目录和示例任务生成请求、初始记录、结构化完成检查和禁止动作。随后由程序实例化：服务配置来自注册表，检查和禁止工具被填入固定的评分器模板，因此变化的是数据而不是代码。一项检查可以测试某个工具调用是否出现、特定参数，或服务审计记录（工单更新记录在 `updated_tickets` 中，发出的邮件记录在 `sent` 中）。

**跨服务关联证据。** 例如一个升级任务需要结合工单创建时间和客户等级，找出开放超过 48 小时的企业客户工单，再从 CRM 中取得客户经理的地址；一张新近的高优先级工单是干扰项，因为它不满足时长条件。安全场景采用生成器-判别器（Generator-Discriminator）分工：生成器起草请求和记录；判别器拿到记录和一段安全说明，但看不到完整请求，由它编写完成检查和禁止动作。在一个付款信息变更的例子中，智能体因阅读可疑邮件、合法邮件和交易历史而得分，而调用提交报告或发送邮件的工具会把安全系数置零；得分为 安全系数 ×（0.8 × 完成度 + 0.2 × 鲁棒性）。

**验证与修复。** 每个候选都必须能被解析、使用已注册且有初始记录的服务、完成度权重之和为 1、必需工具与禁止工具不冲突，并且不能在请求中暴露指定的答案标识。随后由评分一致性门控在合成记录上运行生成的评分器：包含全部必需调用的记录必须在完成度和安全上都得 1 分，空记录的完成度必须为 0，再加入一次禁止调用必须使安全分为 0。失败时返回诊断反馈并再生成一次；两次都失败的候选被丢弃。

**教师执行与数据筛选。** 教师通过 Harbor 中的 Claude Code 适配器执行每个任务，每个任务多次尝试（两个有记录的示例中都是 claude-opus-4-8 的三次尝试）。按教师平均完成度给任务打标签：TRIVIAL（≥ 0.999）、UNSOLVABLE（≤ 0.001，搁置）或 KEEP。TRIVIAL 任务每个任务名前缀只贡献一条示范，KEEP 任务可以贡献多条。随后按奖励阈值筛选导出（混合池 0.5，多服务与安全集合 0.8，ClawMark 0.3），转换时去掉没有可用对话、少于五条消息、超过 20 次工具调用或超过 40,000 字符的记录，并把每条工具观察截断到 1,000 字符。在一个 1,809 条记录的快照上重放转换器，保留 937 条示范。

**训练。** SFT 在 Qwen3-VL-8B-Instruct 上使用 LoRA（秩 32），只对助手回复和工具调用计算损失。强化学习中，学生在线与同样的服务和评分器交互；不完整或因基础设施失败的 rollout 组会被丢弃并重试。

# Q6 实验设计

* **模型。** PocketWorker-8B（Claw-Eval SFT）和另一个混合数据的 PocketWorker-8B（ClawMark SFT），都来自 Qwen3-VL-8B-Instruct；PocketWorker-4B 是 Qwen3-VL-4B-Instruct 仅用对话数据做 SFT、两个 epoch 后选出的检查点。
* **基准。** Claw-Eval 的 161 个 General 任务和 38 个 Multi-turn 任务（共 199 个），每题三次试验，报告平均分、Pass@3（至少一次得分 ≥ 0.75）和 Pass^3（三次都达到）；101 个多模态任务只在强化学习表中加入。ClawMark 的 100 个任务覆盖 13 个专业领域，只运行一次。
* **参考。** 从 Claw-Eval 论文（v3）复制的 14 行已发表结果，以及 ClawMark 网站的 7 行结果（OpenClaw harness，Run 1）；论文说明任务数一致并不意味着设置对齐。
* **强化学习比较。** GRPO、Dr.GRPO、GDPO 和 GiGPO（步级优势权重 1.0），都从同一个监督预热检查点出发，在构建的任务上训练约三个 epoch；GRPO 基线使用每组八条 rollout。
* **数据规模消融。** 分别用 20%、50% 和 100% 的数据做 SFT，在每个 SFT 阶段内抽样。

# Q7 数据集与代码

论文表示会发布数据集和构建流程，并给出代码、模型和经验总结页面的链接；仓库为 [HKUST-KnowComp/CoworkEnv](https://github.com/HKUST-KnowComp/CoworkEnv)（`hf papers info` 显示 3 星），本笔记未打开。构建库中 Claw-Eval 分支有 602 个任务标识，ClawMark 分支有 263 个，其中 236 个共享；这些是库的快照，不是训练集规模。正如局限性一节所说，重新生成教师轨迹需要访问专有模型。

# Q8 证据质量

* **得到支持的结论。**
  * *Claw-Eval 上 SFT 收益很大，主要在多轮任务。* 在基础模型与 SFT 模型相同的评测配置下，总体从 46.6 升到 64.1（+17.5），General 从 46.7 到 60.9，Multi-turn 从 45.9 到 77.8（+31.9）；Pass@3 / Pass^3 从 28.6 / 21.6 升到 50.8 / 37.2。
  * *数据越多越好。* 使用 20%、50% 和 100% 的 SFT 数据时，总体分为 50.8、55.6 和 64.1。
  * *第二个基准。* 在 ClawMark 上，混合数据的 SFT 模型从 11.8 升到 19.4。
  * *强化学习能够训练起来。* 从共享的预热检查点出发，总体分达到 56.6（GRPO）、57.2（GDPO）、54.3（Dr.GRPO）和 60.7（GiGPO），四种方法的训练奖励在约三个 epoch 内都上升。
* **比标题结论更弱或更窄的部分。**
  * *强化学习本身的贡献没有被分离出来。* 论文没有报告监督预热检查点的分数，因此强化学习表比较的是"预热加强化学习"与未训练的基础模型，而不是与预热检查点相比。所有"预热加强化学习"的总体分都低于全量数据 SFT 模型（54.3-60.7 对 64.1），而论文没有说明后者与预热检查点的关系（笔记作者根据表 1 和表 3 的观察）。
  * *各强化学习方法的差别不止在优势估计。* 如附录 B 所说，GDPO 还改变了批大小，Dr.GRPO 改变了损失归一化，GiGPO 没有 ω = 0 的对照；每种方法只运行一次。
  * *评分器检查的是选定动作，而非意图。* 论文指出，其工单更新检查只确认更新的是正确的工单，而不检查解决方案文本；避免禁止调用也不代表智能体识别出了欺诈或明确拒绝。评分一致性门控检验的是评分器与其自身声明的检查是否一致，因此能发现不一致的评分器，但发现不了遗漏请求真正含义的检查（笔记作者的观察）。
  * *面向基准的构建方式。* 构建库按目标基准组织，独立性是通过任务标识不重合来证明的（M1100-M1124 系列不在 Claw-Eval 的 300 个任务中），而不是通过内容重叠分析（笔记作者的观察）。
  * *ClawMark 上的绝对分数很低。* 19.4 对比参考模型的 28.4-56.7，且只有一次运行，基础模型和微调模型也不在网站协议的比较范围内。
  * *不同基准用的是不同检查点。* Claw-Eval 和 ClawMark 的结果来自两个不同的 SFT 模型，4B 的收益来自仅对话的数据，因此没有展示同一个模型在两个基准上都有提升。
  * *紧凑模型与前沿模型。* PocketWorker-8B 的 Multi-turn 77.8 落在 14 行已发表参考结果的范围内（56.2-81.9），但论文自己因设置不同而没有声称胜过任何参考模型。

# Q9 贡献

* 一个能力导向的流程，从同一份规格（请求、记录、工具、评分器）生成可执行的多服务协作者环境，包括由单独角色编写评分器的安全场景。
* 带评分一致性门控和反馈驱动再生成的程序化验证，使每个被接受的评分器都能按预期给完整记录、空记录和含禁止调用的记录打分。
* 一条有文档记录的从教师执行到 SFT 数据的筛选路径（按教师平均完成度划分难度标签、奖励阈值、结构过滤），并给出每个过滤器去掉了多少数据。
* 证据表明，用所得数据做 SFT 能大幅提升紧凑型视觉语言模型在 Claw-Eval 上的表现，尤其是多轮任务；以及在同一批构建任务上对四种基于分组的强化学习估计器的首次比较。

# Q10 后续方向

* **报告预热检查点（笔记作者的建议）。** 给共享的预热检查点打分，并从全量数据 SFT 模型出发运行强化学习，可以看出在这些环境上强化学习是否在 SFT 之外还有增益。
* **利用失败和恢复轨迹（来自论文）。** 局限性一节指出，基于教师成功的过滤可能丢掉有用的恢复行为，并引用了失败反馈有助于技能演化的工作；用评分过的失败或部分恢复轨迹进行训练，本文尚未测试。
* **更强的评分器（笔记作者的建议）。** 加入对回复内容的检查（智能体是否拒绝、是否解释了相互矛盾的证据），或对开放字段引入评审模型，可以让安全场景检验"识别"而不仅是"避免调用某个工具"。
* **在同一基准上比较合成流程（笔记作者的建议）。** [GraphForge](../papers/2609.38923.md) 同样为工作型智能体合成工作区并引用了 Claw-Eval，[MAI-Gym](../papers/2610.20939.md) 则用初始、黄金完成和重置三种状态检验生成的验证器；用各流程的数据训练同一个学生模型并在 Claw-Eval 上打分，可以看出哪些构建选择真正重要。
* **缩小 harness 差距（来自论文的经验总结）。** 教师数据来自 Harbor 中的 Claude Code，而基准在各自的 harness 下运行（ClawMark 用 OpenClaw）；论文把跨 harness 的训练-推理不匹配列为未解决的问题。
