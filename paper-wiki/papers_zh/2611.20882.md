# Q1 问题定义

* **输入（X）：** 一个可运行的科学应用（如 SU2、GROMACS、HPL、HPCG、QuEST、分页语言模型生成流程），放在固定 CPU 核数（四或八核）和内存的容器中；任务说明固定了工作负载、输出与数值容差、新进程中断点恢复等有状态检查、计时范围以及允许修改的文件。
* **输出（Y）：** 最终提交（在允许目录内的源码、构建选项、依赖、运行时配置），由私有验证器重新构建、检查，并在留出输入上计时。
* **约束：** 每次运行八小时；没有参考优化补丁告诉智能体在哪里动手；只有端到端计时流程算数，因此更快的内核只按其所占比例带来收益；跳过必需输出或恢复步骤的捷径判为错误。

# Q2 问题新颖性

SWE-Perf、GSO、SWE-fficiency 的任务来自人工优化提交，每个任务都有已知补丁作锚点；KernelBench 和 AlgoTune 针对自包含函数与参考实现比较；RE-Bench 形式最接近（八小时内改进一个可用方案），但面向机器学习研究工程，并以专家方案归一化。Accelerate Bench 用"要保留的计算"和"要加速的工作负载"来定义任务（借鉴 ProgramBench 的行为规格思路），允许智能体修改算法、实现、构建、依赖与运行时设置，并在私有输入上对整个应用流程计分。

# Q3 科学假设

应用级优化是不同于"写出正确补丁"的能力：当正确性在完整流程上检验时，智能体大多能交出正确程序，区分它们的是去掉了多少端到端运行时间，而这取决于代码、构建、运行时各层选择之间的相互作用。

# Q4 相关工作与关键人物

* **代码优化基准：** 函数级的 PIE、EffiBench、Mercury、ECCO、EvalPerf、ENAMEL、ParEval；仓库级的 SWE-Perf、GSO、SWE-fficiency；Chen 等（2026）发现跨机器重放会破坏它们的有效性规则；面向自包含内核与求解器的 KernelBench、AlgoTune；面向生产集群优化的 ECO。
* **长程迭代评测：** RE-Bench、AlphaEvolve、ALE-Bench、AutoLab、MLS-Bench。
* **科学编程：** SciCode、ScienceAgentBench、AInsteinBench、SWE-bench Science。
* **任务来源：** ASC、PAC、IPCC、SC 与 ISC 的 SCC、IndySCC；任务设计由 ASC 学生超算竞赛决赛选手审阅。
* **关键人物：** Bowen Liu、Yuhan Li 等；Hugging Face 论文页标注机构为 Tencent Hunyuan。可能的批评者：GSO、SWE-fficiency 与 RE-Bench 的作者，以及会质疑基线未经专家调优的高性能计算从业者。

# Q5 核心方法

1. **以工作负载定义任务：** 32 个任务各自固定计算、完整输出、有状态检查与计时边界（一次性准备和构建不计时）。竞赛工作负载通过缩小输入规模和迭代次数缩到单节点，同时保留各阶段与正确性标准。29 个任务基于竞赛应用；3 个（分页语言模型生成、Tucker 重建、图稀疏化）是作者围绕竞赛主题编写的流程。
2. **公开测试与私有验证器：** 公开测试会重建候选程序、在通常两个公开输入上运行，并报告正确性、运行时间和通常的加速比；智能体看不到检查代码。验证器在通常四个私有输入上重跑，这些输入往往更大或每次重新随机生成。
3. **奖励：** r = C × max(0, 1 − T/B)，即正确程序节省的基线运行时间比例（2 倍得 0.5，10 倍得 0.9）。Score@1 为任务平均；A_τ 为正确且至少快 τ 倍的任务占比（τ = 1.25、2，附录另有 5 与 10）；GM 为几何平均加速比，错误或变慢的运行记为 1 倍。
4. **验证器对照：** 在 HPCG-derived 与分页生成上做了 14 个预设对照：所有未改源码的运行和两个合法变换都通过；全部八个非法变体（省略第二个解、输出 NaN、四个通过组件测试的注意力变体）都在其违反的检查上失败。
5. **过程记录：** 保留轨迹、候选程序、计时和反馈，用于大模型辅助标注和对提交程序的受控重放。

# Q6 实验设计

* **主评测（v1.1）：** 16 个智能体，每个是"模型加脚手架"：GPT-6 Astra、GPT-6.1 Sol、GPT-6.1 Terra 用 Codex；其余（Claude Sonnet 5.5、Claude Opus 5.5、Hy4-Preview、Hy4、Hy3、Kimi K3、DeepSeek 各版本、GLM 各版本、Grok 4.6）用 Claude Code；高推理强度。每个智能体每个任务一次计分运行；GPT-6 Astra 与 Hy4-Preview 各额外跑两次测方差。最终程序在同一台机器（两颗 AMD EPYC 9K84）上计分，绑定在一个 NUMA 节点的物理核上。
* **失败计分：** 基础设施或 API 故障用预先固定的新运行替换；智能体自身导致的失败（输出错误、内存溢出、超时）计分。Claude Opus 5.5 有三次运行被提供方的安全分类器（网络安全或生物标记）中止，计为零分。
* **仅配置基线：** 一个不改源码、只改构建与运行时设置的固定配方（R1 -O3 -march=native；R2 应用自身的 SIMD 选项；R3 线程数等于核数并绑核），在公开测试上选出后由验证器评一次，作为另一种参照。
* **方差与分辨力：** 对冻结的提交重新评测；Score@1 差值的成对任务自助法区间（10,000 次重采样）；去掉三个自编流程与 HPCG-derived 后的稳健性检查。
* **过程分析（v1.0）：** 五个智能体（DeepSeek-V4.1-Flash、Grok 4.6、DeepSeek-V4-Pro、DeepSeek-V4-Flash、Hy3），每任务三次，共 480 次运行。GPT-5.6 Luna 标注 476 份最终提交中的优化技术；DeepSeek-V4.1-Flash 标注每次工具调用；人工审阅 80 条抽样轨迹以估计跨层依赖；在 GROMACS、QiboTN、HPCG-derived 上做受控重放。

# Q8 证据质量

**主要结果（表 1，v1.1，每个智能体一次运行）：**

| 智能体 | 脚手架 | Score@1 | 配置参照 | GM | A_1.25 | A_2 |
|---|---|---|---|---|---|---|
| Claude Sonnet 5.5 | Claude Code | 67.4 | 66.3 | 3.83 | 100.0 | 71.9 |
| Claude Opus 5.5 | Claude Code | 59.4 | 58.3 | 3.94 | 84.4 | 68.8 |
| GPT-6.1 Sol | Codex | 49.2 | 46.9 | 2.42 | 78.1 | 50.0 |
| GPT-6 Astra | Codex | 47.2 | 45.0 | 2.40 | 75.0 | 53.1 |
| Hy4-Preview | Claude Code | 45.2 | 42.9 | 2.31 | 71.9 | 50.0 |
| Hy4 | Claude Code | 45.0 | 42.9 | 2.41 | 75.0 | 46.9 |
| Kimi K3 | Claude Code | 42.5 | 42.0 | 2.47 | 68.8 | 40.6 |
| GPT-6.1 Terra | Codex | 37.9 | 36.7 | 1.92 | 75.0 | 25.0 |
| Hy3 | Claude Code | 25.5 | 23.2 | 1.76 | 37.5 | 28.1 |

（另有七个智能体在 33.9 到 40.1 之间。）512 个结果中 472 个正确，其中 346 个还达到 1.25 倍；每个智能体在 32 个任务中正确 26 到 32 个。GPT-6.1 Terra 32 个全对，但得分低于只对 28 个的 Kimi K3。Claude Opus 5.5 在未被标记的 29 个任务上得 65.6%；若把 Sonnet 5.5 在那三个任务上的运行当作回退结果，则为 65.2%。

**区分智能体的因素：** 成对任务自助法区间显示 Sonnet 5.5 领先所有非 Claude 智能体至少 13.4 分，Opus 5.5 领先 GPT-6.1 Sol 0.1 到 18.2 分；二者之下没有任何相邻两名被区分开（120 对中 64 对的区间不含零）。对固定程序重新评测会使 Score@1 波动约 1.5 分（标准差），独立运行之间为 2.48（GPT-6 Astra）与 4.42（Hy4-Preview）。去掉三个自编流程后与表 1 的 Kendall τ_b = 0.95；再去掉 HPCG-derived 为 0.97。

**基线：** 未改动程序测得 0.923 到 1.017 倍（中位数 0.999）。仅配置配方只在 GROMACS 上超过 1.25 倍（2.23 倍，SIMD 从 None 改为 AVX2_256）；以它为参照，各智能体 Score@1 降低 0.5 到 2.4 分。最大的加速并非来自配置：GPT-6 Astra 在 HPCG-derived 上达到 28.9 到 36.7 倍，该算子允许直接求解。

**过程发现（v1.0，五个智能体）：** 476 次有标注的运行中，计算或复用类修改出现 225 次，并行或向量化 132 次，编译器与构建调优仅 40 次。同模型同任务对比下，计算或复用修改带来 +8.0 分奖励（95% 区间 1.4 到 15.9），并行或向量化 +8.9（1.9 到 17.0）。只有计时命令而无性能剖析的运行，在调整任务与模型后比两者都没有的运行高 +4.4 分（−4.0 到 12.8，不显著）。在 31 条版本历史中，70 对相邻且源码不同的正确候选里有 36 对比前一个快，26 对创下新纪录。同一份 GROMACS 源码在四种构建与运行时设置下从 0.289 倍到 2.123 倍；在 QiboTN 的析因重放中，延迟加载库单独只值 1.01 倍，打开更广的快速模拟器分派后值 6.3 到 6.4 倍。审阅者在 40 条被标记的轨迹中确认 34 条、40 条未标记中确认 15 条存在跨层依赖，估计 72% 的运行（63% 到 80%）存在，52%（41% 到 63%）的依赖影响某项优化。

**证据边界：**

* 加速比相对于调优程度不一的任务基线，且限于单节点和一种 CPU 平台（论文自述）；大幅加速可能反映基线未调优或工作负载本身可被利用的结构（论文点名 HPCG-derived 的直接求解）。
* 各行比较的是"模型加脚手架"的组合，脚手架不同（Codex 对 Claude Code），推理强度设置也因提供方而异（论文自述）。
* 每个智能体只跑一次：论文自己也说单次运行无法区分相差几分的智能体，这覆盖了表中两行 Claude 之下的大部分。
* 过程分析使用 v1.0 和五个得分较低的智能体，不包含 v1.1 的领先者；工具调用标注者（DeepSeek-V4.1-Flash）本身也是被分析的五个智能体之一（读者观察）。
* 论文在 Hugging Face 上的机构为 Tencent Hunyuan，Hy3、Hy4、Hy4-Preview 看起来是该机构的模型，且 Hy4-Preview 是两个获得重复运行的智能体之一；所获正文未说明这层关系（读者推断）。
* v1.0 表 6 中，Hy3（9.76）和 DeepSeek-V4-Flash（19.08）的"报告运行"低于各自三轮得分，因为"报告"取的是每个任务的中位奖励运行，而不是某一轮（读者观察）。
* Opus 5.5 的三个零分来自评测网关阻止了厂商的回退模型；论文报告了替代算法，但总排名依赖这一计分选择。

# Q9 贡献

1. 一个以工作负载定义的优化基准：32 个来自科学应用和超算竞赛的 CPU 任务，含公开测试、在留出输入上的私有验证，以及经预设对照验证的有状态正确性检查。
2. 对 16 个智能体的评测，表明正确性已接近饱和、加速幅度才区分智能体，并明确处理了运行间方差、仅配置基线与安全分类器中止。
3. 过程分析与受控重放，表明智能体主要修改计算、很少动构建，而收益取决于构建设置、运行时设置以及其他代码修改。

# Q10 下一步

* **论文提出：** 把模型与脚手架分开；测量对硬件放置的敏感性；在其他规模、硬件和生产环境中评测。
* **专家调优参照：** 附录 G 有一个独立编写的参照；在每个任务上与专家调优程序比较，可以看出提供的基线之外还剩多少空间（读者建议）。
* **对领先者做过程分析：** 在 v1.1 领先者上重复轨迹分析，可检验其优势来自更多构建与运行时调优，还是更好的计算修改（读者建议）。
* **GPU 与多节点任务：** 基准只覆盖 CPU 单节点；跨层依赖的发现能否推广到 GPU 内核与分布式运行仍待研究。
