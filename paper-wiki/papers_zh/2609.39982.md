# Q1 问题定义

* **输入（X）：** 一个终端任务、一个固定的动作生成模型 π，以及一个固定的驾驭层（harness）。在第 t 步，智能体拥有由此前动作和终端观察组成的交互历史 h_t。
* **输出（Y）：** 每一步实际执行的动作，以及由此得到的轨迹是否成功（完全通过任务测试）。
* **核心问题：** 终端智能体要连续执行一长串随机采样出的命令，而每条命令都会改变环境。一条糟糕的命令（错误的包安装或代码修改）可能阻碍后续进展，即使同一个模型本可以给出更好的备选动作。作者追问：在每个动作*执行之前*投入测试时算力，何时能提高轨迹成功率，又是什么让它有效。
* **约束：** 生成模型的权重和驾驭层循环都保持不变；干预只发生在模型调用的封装层里，并且只需要一个环境实例，而不是多个并行副本。

# Q2 问题新颖性

部分新颖。通过采样与验证做测试时扩展，在推理任务上（数学验证器、过程奖励模型、V1 这样的成对锦标赛）和完整智能体轨迹上（借助 [LLM-as-a-Verifier](../papers/2607.05391.md) 的 Best-of-N、顺序改进）都已确立。对候选动作逐步验证也有先例：为 SWE 智能体训练的评判器（Zainullina et al., 2025），以及 LLM-as-a-Verifier 在 Terminal-Bench 上的逐步候选验证。本文的贡献是在多类终端任务上做受控研究：在动作层面*哪种*验证机制有效，在强验证者之下生成模型自己的候选有多少价值，这样的验证者能否蒸馏进生成模型自身的骨干，以及动作扩展如何与轨迹扩展组合。

# Q3 科学假设

如果生成模型在某一步的采样中已经包含有用的备选动作，那么一个能识别它们的验证者就应当在不改变生成模型的情况下提高轨迹成功率。因此，收益应更多取决于验证者质量和比较方式，而不是候选数量；并且它应当与轨迹层面的扩展相加，而不是相互替代。

# Q5 关键解法思路

* **在模型与驾驭层的边界上扩展。** 每一步从同一历史中采样 N 个候选动作（`<think>` 中的推理会生成，但不给验证者看），对完全相同的工具调用去重、丢弃无法解析的调用，再由验证者返回其中一个；驾驭层执行它，其余候选被丢弃。集成只需在模型调用封装里改几行。
* **三种验证机制。** 列表式（listwise）：一次调用看到所有候选并选出一个。逐点式（pointwise）：每个候选独立打分，类似过程奖励模型。成对式（pairwise）：在同一历史下比较两个候选，给出理由、两个 1-10 分和 A/B/平局偏好。N = 4 时比较全部六对；N = 8 时先做一轮环形比较再做四枢轴阶段（22-25 次比较，即 LLM-as-a-Verifier 的枢轴锦标赛），用按分差加权的胜率汇总。
* **验证者蒸馏。** 在生成模型自身骨干上加一个只在验证时启用的 LoRA 适配器，训练它复现 GPT-5.6 Sol 的成对比较理由、分数和偏好：数据为 117,631 个输入，来自 244 个困难的 TMAX-15k 任务（每个任务三条 TMAX-9B 轨迹），A/B 已平衡，另留 21 个任务做分析。
* **仅决策变体。** 验证者只输出一个 A/B token，按归一化后的 A/B 平均概率给候选排序，以减少验证者的解码开销。

# Q6 实验设计

* **主设定：** TerminalBench-Lite（OpenThoughts-TBLite：100 个任务，两个因沙箱错误被排除，剩 98 个），生成模型 TMAX-9B（由 Qwen3.5-9B 在合成终端任务上用强化学习训练）运行于 Vanillux2 驾驭层。生成温度 0.8，至多 64 步，上下文 65,536 token；验证者关闭思考，温度 0。每个任务跑三次；Pass@1 为平均成功率，Pass@3 为至少成功一次的任务比例。全程使用三倍的智能体超时系数。
* **机制与宽度：** 列表式、逐点式、成对式各在 N = 4 和 8 下比较；“首个可运行”对照（执行第一个可解析的样本，不做验证）；GPT-5.6 Sol 作为前沿列表式验证者。
* **成本：** 并行化输出 token（理想化的延迟代理）、验证者总输出 token，以及按 Qwen3.5-9B 的 OpenRouter 参考价格计算的 token 成本。
* **离线分析：** 在 21 个留出任务的 1,355 个状态上测量与 GPT-5.6 Sol 教师的一致率；由 GPT-5.6 Terra 审阅与教师的分歧，并按预定义的失败分类归类。
* **组合：** 在 4B、9B、27B 上，Best-of-T 轨迹（T = 3、5、7，由 TMAX 轨迹验证者挑选）和顺序改进（Sequential Refine，R = 1-3），各自带或不带 Mid-Harness。
* **迁移：** 用 TMAX 模型跑 Terminal-Bench 2.1（89 个任务）、SWE-bench Verified Mini（50 个任务）和 FeatureBench-Mini（23 个 CPU 任务）；在 Terminus-2 驾驭层中跑 Qwen3.5-9B、Nemotron3.5 Lightning 和 Nemotron3 Ultra。
* **不确定性：** 对六组“基础智能体 vs. Mid-Harness”比较做按任务配对的自助法（100,000 次重采样）95% 区间；并按领域、难度和基础智能体执行长度分组分析。

# Q8 证据质量

* **有支撑的：**
  * *生成模型的候选中包含有用的备选。* 以 GPT-5.6 Sol 作为列表式验证者时，Pass@1 从 50.00% 升到 64.63%（N = 4）和 68.03%（N = 8），Pass@3 从 69.39% 升到 80.61%。只采样不验证没有帮助：“首个可运行”对照为 49.66%。
  * *自验证时，验证格式比宽度更重要。* 零样本列表式只从 49.32%（N = 4）升到 51.02%（N = 8）；逐点式为 52.72% 和 52.38%；成对式为 54.42% 和 54.76%（Pass@3 71.43%）。
  * *蒸馏在不动生成模型的情况下有帮助。* 蒸馏后的成对验证者达到 55.44%（N = 4）和 57.14%（N = 8），Pass@3 75.51%。离线指标上，与教师的分数误差从 2.59 降到 1.05，成对一致率从 59.01% 升到 74.58%，首选候选一致率从 38.52% 升到 57.79%。经审阅确认的明确失败从 3,328 例降到 1,810 例；其余失败中候选语义与执行可行性两类占 67.4%。
  * *动作扩展与轨迹扩展可以叠加。* 9B 上，单独 Best-of-3 为 55.10%，叠加零样本 Mid-Harness 为 61.22%，叠加蒸馏版为 66.33%，环境执行次数同样是三次。顺序改进出现平台（R = 1-3 分别为 55.10%、56.46%、55.78%），叠加蒸馏版 Mid-Harness 后达到 60.20%。单独的蒸馏版 Mid-Harness（57.14%）与 Best-of-5 持平，参考价格成本约为其三分之一；两种组合都以更低的参考价格成本超过 Best-of-7（59.18%）。
  * *规模与迁移。* 4B 上 Pass@1 从 38.78% 升到 41.50%（零样本）再到 43.88%（蒸馏）；27B 上从 71.09% 到 73.13% 再到 76.19%。Terminal-Bench 2.1 上，TMAX-9B 从 21.72% 升到 27.34%（零样本），Nemotron3 Ultra 从 50.94% 升到 56.18%。FeatureBench-Mini 上，TMAX-9B 从 1.45% 升到 7.25%，TMAX-27B 从 17.39% 升到 23.19%（蒸馏）。在全部七个迁移设定中，零样本 Mid-Harness 都提升了 Pass@3，且 Pass@1 持平或提升。
* **较弱或有边界的：**
  * *样本少，区间宽。* 主基准只有 98 个任务、每个任务三次运行。作者的配对自助法中，六组“基础 vs. Mid-Harness”的 Pass@1 差值全部为正，但只有蒸馏版 9B（+7.14，[+1.36, +12.93]）和蒸馏版 27B（+5.10，[+0.34, +9.86]）的区间不含零；零样本 9B 为 +4.76，区间 [−0.68, +10.20]。各验证机制之间 2-3 分的差异没有给出区间，迁移基准的规模更小（50 个和 23 个任务）。
  * *前沿“上界”用的是另一种机制。* 出于成本原因，GPT-5.6 Sol 只以列表式运行，而最好的自验证是成对式，所以 68.03% 既不是上限，也不是同条件比较。正如作者所说，由于没有动作级的金标准标签，候选覆盖度只能通过轨迹成功率间接推断。
  * *成本只是代理指标。* token 价格是本地部署模型的参考价，并行化输出 token 假设理想并行。N = 8 的成对验证每步要调用验证者 22-25 次（每次运行验证者总输出 125.7k token，列表式只有 0.6k）。三倍超时下的实际墙钟延迟没有报告。
  * *未检验的替代方案。* 研究没有在相同成本下比较动作扩展与“给单个候选更多推理强度”，作者把这列为局限。
  * *更便宜的变体结果不一致。* 仅决策的成对验证提高了 9B 的 Pass@1（零样本 56.12%，蒸馏 59.18%），但在 4B、27B 以及 N = 4 时降低了 Pass@1。每对采样五个验证回答会让 Pass@1 从 57.14% 降到 53.40%，同时验证者输出增加到五倍。
  * *不同任务上的收益不均。* 蒸馏验证在所有规模上都提升了软件工程任务（27B 上 +20.5 分），但让 27B 在科学计算任务上的 Pass@1 下降 10.0 分。失败分类来自 GPT-5.6 Terra 对照教师参考的审阅，而不是实际执行的结果。获取到的正文没有说明 TMAX-15k 蒸馏任务与 TerminalBench-Lite 之间是否做过重叠检查（读者注）。

# Q9 贡献

* Mid-Harness：一个即插即用的模型调用封装，把逐步的动作采样与验证变成可控的测试时扩展维度，生成模型和驾驭层都不需要改动。
* 对列表式、逐点式、成对式动作验证的受控比较，表明决定额外样本是否值得的是比较格式和验证者质量，而不是候选宽度。
* 证据表明：从前沿验证者蒸馏到生成模型骨干上的验证者能弥补部分差距；离线分析把剩余错误定位到对命令语义和执行可行性的判断上。
* 证据表明：动作扩展可以与 Best-of-T 和顺序改进叠加，并改善成本-成功率权衡，成本以 token 和参考价格核算。

# Q10 下一步

* **作者列出的方向：** 用强化学习训练验证者或与生成模型联合训练（如 V1）；用世界模型预测命令效果；按步骤自适应地调整候选宽度和验证投入，而不是每步都验证；在计算机使用和机器人智能体上测试；在相同成本下与提高单个候选的推理强度比较；等环境可以克隆后，从中间状态分支构建评测。
* **追问何时验证（读者注）：** 验证者在后期、依赖状态的步骤上最容易出错（第 1-4 轮与教师一致率 68.13%，第 17-32 轮为 54.07%），而这些步骤恰恰是错误动作代价最高的地方。只在不可逆或改变环境的命令（安装、删除、启动服务）上投入验证的门控，或许能以远少于每步 22-25 次调用的代价保住大部分收益。
* **与本仓库的关联（读者注）：** Research OS 的智能体在 shell 中行动，`project-dispatch` 流程会把工作交给 Claude Code 或 Codex 会话。Mid-Harness 给出了在模型调用边界做执行前检查的具体模式，可与权限提示互补：论文的伦理声明指出，动作验证应补充而不是取代受限权限、环境隔离和对敏感操作的人工批准。

# 相关

* [智能体测试时扩展](../topics/agent-test-time-scaling.md) - 把动作扩展确立为独立于轨迹扩展的维度，并展示两者如何组合（Best-of-3 加蒸馏动作验证达到 66.33%，以更低的参考价格成本超过 Best-of-7 的 59.18%）。
* [LLM-as-a-Verifier](../papers/2607.05391.md) - 提供 N = 8 时成对动作验证所用的枢轴锦标赛，以及与 Mid-Harness 组合的 Best-of-T 轨迹选择器。
* [Terminal-Bench](../concepts/terminal-bench.md) - 主评测在 TerminalBench-Lite 上（98 个任务，TMAX-9B Pass@1 从 50.00% 到蒸馏版的 57.14%），并迁移到 Terminal-Bench 2.1（TMAX-9B 21.72% → 27.34%；Nemotron3 Ultra 50.94% → 56.18%）。
* [SWE-bench Verified](../concepts/swe-bench-verified.md) - 用 TMAX-9B 在 50 题的 Mini 子集上做迁移检查：蒸馏验证者下 Pass@1 从 46.67% 到 48.67%，Pass@3 从 54.00% 到 62.00%。
* [LLM 评审（LLM-as-a-Judge）](../concepts/llm-as-a-judge.md) - 验证者是在候选动作执行前比较它们的生成式 LLM 评审；GPT-5.6 Sol 担任教师评审，GPT-5.6 Terra 审阅验证者的分歧。
* [Meta-Harness](../concepts/meta-harness.md) - 被引为自动化驾驭层优化；Mid-Harness 做的是相反的设计选择：保持驾驭层不变，把算力花在每个动作上。
