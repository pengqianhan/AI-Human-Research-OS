> 论文：**StateM: Reaching 95.3% Raw Accuracy, or a $15 Frontier Run, on Terminal-Bench 2.1 via Harness Scaling**
> 论文链接：<https://arxiv.org/abs/2608.15089>
> 代码：<https://github.com/henryqin1997/statem>
> 说明：独立/个人时间项目，论文明确声明不代表任何所属机构的立场。

# Q1 问题定义

* **输入 `X`**：一个长程 CLI-agent 任务、一个冻结的基础模型（GPT-5.5、GPT-5.6 各变体，或 DeepSeek-V4-Flash），运行在既有 agent harness（Codex）之上，加上一份为目标任务族定义状态、转移、钩子、检查的版本化 YAML runbook。
* **输出 `Y`**：一次完成或被终态记录的任务运行——由同一模型通过 StateM 的控制层执行；以及（跨实验而言）一份不断演化的 runbook，把选定的复盘经验编码为持久的、可执行的前置条件与实践。
* **核心问题**：即使底层模型能够解决每个局部步骤，长程 agent 仍会失败——它们会丢失可变状态、无法重新激活先前执行中学到的经验、跳过已知步骤，或过早停止。改进 agent 周围的执行系统（"harness"）而非模型本身，能在多大程度上弥补这种看似的能力差距？由此得到的控制层能在多大程度上跨模型代际、跨供应商、跨任务族迁移？
* **范围**：面向长时间运行的 CLI agent（Codex、Claude Code）的单 agent 控制流；运行时无需模型微调或访问模型内部；角色隔离的多 agent 运行时被明确留作未来工作。

# Q2 问题的新颖性

有状态/图式编排（StateFlow、LangGraph）与 harness 自适应方法（Agentic Harness Engineering、Life-Harness、Self-Harness、"Better Harnesses, Smaller Models"）都已存在。StateM 的新颖之处在于以不同方式组合二者：不是让开发者编写的图成为主要控制产物（agent 被调用于其节点内部），而是让通用 CLI agent 保持为主要执行者，把状态、转移、钩子、检查作为一份共享的、agent 与用户皆可编辑的 runbook，通过 agent 自身的常规 CLI 动作空间来操作。论文将其贡献概括为三个通常不会同时出现在一个系统里的特性：状态边界同时是刷新的上下文与可执行的转移契约；agent（而非被拆解成节点级的调用）保持为主要执行者；runbook 是一份 agent 与用户都可检视、审计、可机器操作的共享产物。

# Q3 科学假设

如果一个控制层把可变执行状态外化为阶段级状态，配以经检查、有记录（但非完全事务性）的转移，在进入状态时刷新阶段局部上下文，并把经筛选的复盘经验以版本化实践的形式积累进一份 agent 与用户共享可编辑的 runbook，那么：(1) 在模型权重固定的前提下，这种 harness scaling 能弥补长程任务上相当于一次模型代际升级的能力差距；(2) 由此得到的控制层能在同一供应商内近邻模型代际间零修改迁移；(3) 跨供应商边界时，精确的 profile 迁移会失败，但运行时、runbook 结构与开发方法论仍可复用，使得低成本的重新适配成为可能；(4) 迁移到新任务族的泛化效果取决于控制层是否匹配该任务族真实的执行边界结构，而非单纯堆砌更多流程。论文在 Terminal-Bench 2.1 与 BusinessBench 上检验了以上四点，但明确未将状态机运行时本身的贡献与演化出的、针对基准调优的控制内容分离（第 4 节），也未测试角色隔离的多 agent 运行时。

# Q4 相关工作与关键人物

* **有状态/图式编排**：StateFlow（状态驱动的任务求解）、LangGraph（持久状态、条件边、检查点、人机协同）。StateM 的区别在于默认执行抽象：控制产物停留在执行 agent 的常规工具环境内部，而非把 agent 外化成受控制器拥有的图节点。
* **CLI agent 与软性控制**：Codex、Claude Code——提供计划/清单/钩子，但这些仍是软性的、自然语言的，或挂载在生命周期事件上，而非一个统一的、感知转移的执行状态。
* **agent 长期可靠性**：AgingBench（跨多个会话的压缩老化/干扰老化/修订老化/维护老化）——与本文互补而非重叠：AgingBench 诊断跨运营生命周期的可靠性退化，而 StateM 在单次及跨次长程执行内部控制程序化状态。
* **harness 自适应/自我改进**：Agentic Harness Engineering、Life-Harness、Self-Harness、"Better Harnesses, Smaller Models"（Yang 等 2026，StateM 也在其 BusinessBench 上做了评测）。StateM 的区别性产物是一份显式的状态机 runbook（状态、转移条件、钩子、修复路径、历史），可直接被执行 agent 操作，同时充当运行时控制、审计界面与失败驱动优化的搜索空间三重角色。
* **作者**：Ziheng Qin、Yaxin Lu（并列一作，核心贡献者）、Zhangyang "Atlas" Wang、Kai Wang——独立/个人时间项目，论文未将其归属于任何机构。

# Q5 核心解法

1. **状态作为上下文与契约边界**。一份 runbook `Σ = (S, s_0, T, τ, δ)` 定义阶段级状态（而非单次模型调用）。进入状态会运行一个 `in_hook`（初始化、加载上下文、刷新进度）；agent 在状态内部自由工作；离开状态需要 `before_transfer` 检查通过，随后 `out_hook` 持久化进度。检查的证据强度分级：从主机端评估的命令/谓词检查，到人工/清单/消息式自我陈述，再到 `llm_review` 语义判断——框架明确不把某个结构化字段本身当作证明。
2. **经检查、有记录、可恢复（非事务性）的转移**。`goto TARGET` 执行一套有序协议：验证目标边存在 → 评估 `before_transfer` 检查 → 运行持久化/`out_hook` → 评估边守卫/转移钩子 → 仅当所有前置步骤成功时才提交并记录 → 运行目标状态的 `in_hook`。失败的检查会让运行停留在源状态，可见且可修复，而非静默传播下去。
3. **单次运行的恢复记录**。每次执行都有独立于可复用 runbook 的可变状态（运行 ID、当前状态、转移历史、钩子/检查结果、证据引用），使得重启或经历上下文压缩的 agent 拥有一个明确的阶段与义务集合可以从中恢复——而不对任意外部副作用做 ACID 式回滚。
4. **共享、可联合编辑但有边界的自我修改**。当 runbook 允许时，agent 可以注册额外的运行局部动态检查；但削弱或删除既有不变量/权限需要一次特权策略决策；在跨模型评估前会冻结基础 runbook，以避免 runbook 演化与评估时适配相混淆。针对 Codex/Claude Code 的停止钩子集成会把未满足的义务返回给 agent，而不是允许过早终止。
5. **失败驱动的 harness 优化作为选择性程序化记忆**。失败被归因于三类缺口之一——认知缺口（知识缺失，由 `in_hook` 上下文刷新应对）、程序合规缺口（正在执行的流程未完成，由检查过的转移应对）、程序记忆缺口（先前运行中的经验未被保留，由版本化实践应对）。论文强调经验必须先经筛选才能成为记忆：BusinessBench 的迭代显示，通用/过量的流程反而会损害某些任务族（RefactorBench、WooCommerce），直到控制被收窄到真正的不变量边界；而 Attendance-Payroll 则说明放弃对某任务族施加 StateM 工作流本身可能就是正确决策。

# Q6 实验设计

**Terminal-Bench 2.1**（89 个任务，每任务 5 次试验，共 445 次/轮）：先用 GPT-5.5 xhigh 在 Codex 下开发出 profile，然后**冻结**（不再依据目标模型的评估结果做修改）后评测 GPT-5.6 Sol xhigh、GPT-5.6 Luna、DeepSeek-V4-Flash——依次检验固定模型提升、同代内冻结迁移、跨供应商适配迁移这三个逐步升级的实证层级。DeepSeek 一轮额外经历一次显式适配阶段（成本低于 38 美元），先测得冻结迁移失败后再进行适配。成本核算把实际发生的 API 费用（最终评测与适配）与流水线报告的"API 等价模型成本估算"分开列出。**BusinessBench**（Yang 等 2026，用 Codex + GPT-5.6 Luna 运行）：为每个被处理的任务族（7 个中的 6 个；Attendance-Payroll 被弃权处理）分别开发一份 profile，在开发集上打磨后，于**首次**留出评测前冻结（宏观/微观平均）；之后的改进作为事后诊断性验证单独报告，不与未经触碰的一次性数字混合。一项运营韧性案例研究报告了一次持续 22 小时的 profile 开发运行，用以检验 StateM 的持久记录能否在上下文刷新/压缩/停止钩子持续运行中存活。

# Q7 数据集与代码

* 使用两个已有基准——Terminal-Bench 2.1（Merrill 等 2026）与 BusinessBench（Yang 等 2026）——未发布新的基准数据集；论文发布的是 StateM 运行时本身。

# Q8 证据质量

主要数字有力且具体：GPT-5.5 xhigh + StateM 达到 92.1%，对比 83.1% 的参考基线（+9.0 分，已逼近**下一代**模型 91.9% Sol Ultra 的参考水平）；冻结的 runbook 未经修改直接应用于 GPT-5.6 Sol xhigh，取得 95.28% 原始分数（424/445，一位小数记为"95.3%"），对比 84.9% 的参考基线（+10.4 分）。论文对这个头条数字的裁定敏感性异常坦诚：它是一次未合并、裁定前的公开提交（PR #142，写作时仍处于开放状态），作者自己披露若把 4 条被标记为疑似奖励作弊的轨迹计零则降为 94.38%，若把全部 9 条被标记轨迹计零则降为 93.26%——他们明确将 95.28% 仅作为"原始公开提交分数"报告，这是一种少见且可信的自我披露裁定敏感性的做法。跨供应商迁移结果的诚实之处在于先负后正：把冻结的 GPT profile 直接应用于 DeepSeek-V4-Flash 反而**降低**了准确率（82.7%→82.0%），只有经过明确核算成本的适配阶段（低于 38 美元）才恢复了增益（→88.09% 全套件，89.09% 公共核心）——这才是论文关于"运行时与方法论可迁移、具体实践不可迁移"这一论断的真正证据。BusinessBench 的结果是全文中在认识论上最审慎的部分：论文同时报告了两个任务族的负迁移（RefactorBench −2.78、WooCommerce −3.70），并明确把"冻结一次性"证据与使用聚合反馈的"事后诊断性验证"区分开——这个边界很重要，因为后者在同等意义上并非留出评测。需要注意的限制：结果衡量的是**运行时 + 演化出的、针对基准调优的控制 profile**的组合效果，而非单独的状态机抽象本身（论文明确承认）；BusinessBench 的逐实例结果每臂只有一条随机轨迹，因此任务族级与实例级平均回答的是不同问题，且都没有重复试验的误差条；本文写作时是一个独立/个人时间项目，未经机构同行评审。

# Q9 主要贡献

1. 把 harness scaling 表述为与模型 scaling 互补的能力轴，并区分出四个逐步升级的实证检验：同模型内提升、冻结跨代迁移、适配跨供应商迁移、留出任务族泛化。
2. 提出 StateM，一个 agent 原生的运行时（YAML runbook + CLI），其中持久状态同时是被刷新的控制上下文和显式的、经检查的转移契约，同时保留执行 agent 统一的推理循环，而非将其拆解为受控制器拥有的节点。
3. 把三类不同的执行失败来源——认知缺口、程序合规缺口、程序记忆缺口——具体化，并为每一类配上对应的控制机制（状态局部上下文、经检查的转移、版本化实践）。
4. 一个失败驱动的优化循环，把选定的复盘发现转化为版本化的 runbook 变更，使程序化知识能够在模型权重之外持续积累。
5. 跨 GPT-5.5、两个 GPT-5.6 变体、DeepSeek-V4-Flash、Terminal-Bench 2.1、BusinessBench 的实证展示，明确报告了原始分数的裁定敏感性、冻结与适配迁移、任务级回退，以及实际发生的 API 成本（约 15 美元的最终证据成本，对比匹配的 GPT 参考的 574.68 美元，约便宜 38.9 倍）。

# Q10 下一步

* 论文自陈的局限/展望：精确的 profile 能在同一供应商内的近邻模型间迁移，但跨供应商时若不经适配则无法迁移；记住更多流程并不等于更好的记忆——RefactorBench 与 WooCommerce 只有在通用流程被替换为真正的跨系统不变量后才有改善，而 Attendance-Payroll 说明正确的策略有时就是完全不介入；该框架提供的是控制点而非正确性判决——即便有结构化形式，语义自我审查与 agent 自述的凭证仍可能出错；角色隔离的多 agent 运行时（每个 agent 角色独立的上下文视图与读写权限边界）被列为一组独立的协调问题，留待未来工作。
* **对 Research-OS 的启示**：可直接与本仓库自身的记忆层约定（`human-cognition-cache` 中的先合并再追加、证据阈值、衰减）以及 `HANDOFF.md` 的 Active Work/Decisions 模式对照——StateM 的状态局部 `in_hook`/`out_hook` 与经检查转移的纪律，是对"持久记录能在上下文丢失后存活"这一问题的一种更形式化的版本，而本仓库目前的会话启动契约只是非正式地尝试解决同一问题。
* 下次本 OS 中的长程 agent 任务需要设计持久状态时，值得把 StateM 的三缺口分类法（认知/程序合规/程序记忆）与本仓库自身的失败模式词汇做对照，因为该分类法能干净地映射到"缺失上下文""已知流程被跳过""经验未被重新激活"这三种情形。
