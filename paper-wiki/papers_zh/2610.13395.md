# Q1 问题定义

* **输入（X）：** 对环境构建而言，是一个有源码的仓库 $P_i$。对任务智能体而言，是一个只能执行的参考程序 $B_i^\star$、它的使用文档 $D_i$，以及一个断网的沙箱 $\mathcal{S}_i$；没有源码。
* **输出（Y）：** 流水线产出环境 $e_i = (B_i^\star, D_i, \mathcal{T}_i, \mathcal{S}_i)$，其中 $\mathcal{T}_i$ 是黑盒行为测试集。智能体产出任意编译型语言的源码加一个编译脚本，生成候选可执行文件 $\widehat{B}_i$，其可观察行为在测试上与参考程序一致。
* **约束：** 智能体必须通过运行参考程序自己发现需求，并自己决定设计。通过 $\mathcal{T}_i$ 说明在被测行为上一致，不等于语义等价。
* **核心问题：** （i）大规模构建可验证的训练环境，这需要每个仓库都能构建成功，测试既要覆盖行为又要能拒绝错误的复现；（ii）让一次很长的开发过程保持协调，因为单会话可能还没探索够就开始写代码，并在上下文被压缩时丢掉早期的观察。

# Q2 问题新颖性

任务本身不新：ProgramBench 和 MirrorCode 定义了从二进制和文档出发的程序复现，MindForge 已经在这个任务上做训练。论文声称的空白是：面向 issue 修复的环境生成器（SWE-Gym、SWE-smith）从现成代码库出发；MindForge 只限命令行程序，且不按恢复出的行为过滤轨迹；通用 harness 没有“先探索再实现”的工作流。论文没有与 MindForge 比较，因为它的环境和轨迹没有公开。

# Q3 科学假设

1. **反馈循环让环境构建可靠。** 如果构建尝试和生成的测试都经过验证，并把诊断信息返回给负责构建的智能体，就能把仓库变成行为覆盖率高、测试有区分力的环境。
2. **在这样的环境上训练有帮助。** 如果模型在这些环境中按测试通过率过滤的轨迹上微调，它在留出的基准上能复现更多程序行为。
3. **角色分离加构建关口帮助更大。** 如果分析、实现和评审在只交换书面产物的独立会话中进行，且每一轮都必须能独立编译，那么同一个模型比在一个长会话中恢复更多行为，轮数越多恢复越多。

# Q4 相关工作与关键人物

* **从零复现程序。** ProgramBench（Yang et al., 2026）、MirrorCode、MindForge。
* **Issue 修复与仓库生成。** SWE-bench 及其变体；NL2Repo-Bench 等基于需求文档的设置，论文认为它们把任务简化成了“实现”。
* **扩展编码环境。** SWE-Gym、SWE-smith、SWE-Master 和 R2E-Gym，论文引用它们来说明生成的环境能提升 issue 修复智能体。
* **关键人物。** 厦门大学（通讯作者 Jinsong Su 和 Fei Long），以及圣路易斯华盛顿大学、中国科学院自动化研究所和 Unisound。可能的批评者：ProgramBench 的作者会指出，用于比较的旗舰模型数字来自另一种脚手架；测试生成方向的研究者会追问这些测试集区分“接近正确”与“正确”程序的能力。

# Q5 关键解决思路

**Program-Env**（以 Claude Code 为 harness，DeepSeek-V4-Flash-0731 为模型，外加反馈循环）：

* **收集。** 按语言和 star 区间分层的 GitHub 搜索（41,833 个仓库），元数据校验并剔除已被现有代码基准使用的仓库（35,710 个），每个仓库锁定一个 commit，再静态检测构建配置（30,459 个候选）。
* **构建。** 智能体写 `download.sh` 负责联网准备依赖，写 `compile.sh` 负责离线编译；只有两者都成功、且可执行文件通过可加载性检查，循环才前进，否则把诊断信息返回供修改。
* **分派。** 把源码切分成功能模块，对可执行文件做覆盖率插桩，并提取 README 等文档。
* **测试。** 每个模块由一个子智能体分多轮编写测试。每轮之后它读取三份反馈文档：*总结*（做了什么、还剩什么）；*程序分析*（用动态覆盖率找出未覆盖的功能，再用 Joern 或 CodeQL 的静态分析追溯到公开入口）；以及来自四项检查的*验证*：pass 检查（测试在参考程序上失败）、double 检查（重复运行结果不一致）、dummy 检查（测试接受一个空壳实现）、weak-assert 检查（一个 37 条规则的静态 linter，专查只断言退出码之类的弱判据）。子智能体在功能覆盖率达到 80%、到达按仓库复杂度设定的 5 到 20 轮上限，或覆盖率停滞时提前停止。只保留通过全部检查的测试。

**Program-Agent**（构建在 Claude Code 之上）：

* **分析。** 分析员会话阅读文档并探索参考程序，不碰工作区，写出 `analysis.md`，之后冻结。
* **实现。** 一个独立会话依据交接产物写代码，并且*不能访问参考程序*；它把改动记录在 `delivery.md` 中。第一轮必须交付一个能构建的版本。
* **评审。** 分析员角色在一个新的、只读的会话中，把参考程序与新构建出的候选程序做比较，把核实过的差异写入 `review.md`，作为下一轮的需求。
* **修订管理。** 每轮实现之后，把已提交源码的干净 Git 归档导出到工作区之外编译（300 秒超时）。超时、缺少产物或构建失败的阶段会在新会话中重试（默认两次尝试），新会话只收到一段有界的诊断信息；仍然失败则把工作区回滚到上一个能构建的修订。
* **预算。** 一次分析，然后 $K$ 轮交替的实现与评审（$K=5$）。

# Q6 实验设计

* **训练数据。** 用 DeepSeek-V4-Flash-0731 + Claude Code 在全部 1,648 个环境上做拒绝采样得到轨迹，按测试用例通过率过滤。由于 Claude Code 在一次 rollout 中会重置或切换上下文，每个上下文片段算一个训练样本：共 64,505 条轨迹，论文说明这不等于 64,505 次独立 rollout。
* **微调。** Qwen3.8-27B，全参数，用 ms-swift 训练两个 epoch，序列打包到 262,144 个 token，只在助手 token 上计算损失，并屏蔽调用了环境中不存在的工具的轮次。
* **评测。** ProgramBench（200 个任务），在隔离容器中运行，8 核 CPU、16 GB 内存、30 GB 存储、8 小时上限。指标沿用 ProgramBench：*Tests Passed*（各任务测试通过率的宏平均）、*Almost Resolved*（至少通过 95% 的测试）、*Resolved*（通过全部测试且没有作弊标记）。
* **对比。** 以 Claude Code 作为单会话基线，与 Program-Agent 比较，模型包括 Qwen3.8-27B、其微调版本和 DeepSeek-V4-Flash-0731；旗舰模型的各行抄自 ProgramBench 论文，在那里它们运行于 mini-SWE-agent。
* **分析。** 环境统计，微调模型在迭代预算 $K \in \{1,3,5\}$ 下的表现，动作类型分布，token 成本，通过率分布，以及与参考实现的代码量对比。

# Q7 数据集与代码

有[项目主页](https://programgym.github.io/)、GitHub 仓库 [Acm1011/ProgramGym](https://github.com/Acm1011/ProgramGym)（抓取时 1 星）和 Hugging Face 组织（`huggingface.co/ProgramGym`）。论文说*将会*发布环境、构建代码和训练产物；目前实际可获取哪些内容，本笔记没有核查。环境统计：1,648 个仓库，分属八个功能类别（开发者工具 441、命令行与系统工具 372、数据与科学计算 243、安全与取证 227，以及四个较小的类别）；5,918 个写测试的子智能体；665,512 个通过验证的测试用例（每个仓库平均 404 个），其中 98.50% 是从零编写，而不是改自仓库原有测试；平均覆盖率 72.99%（中位数 81.63%）；总计 1367.7 亿 token，每个环境约 8,299 万。按论文基于规模的复杂度评分，1,492 个任务为简单，151 个中等，5 个困难。

# Q8 证据质量

* **有支撑的结论。**
  * *流水线能成规模地产出环境。* 即上面的各项数字，加上收集漏斗每一阶段的留存率和明确的终止设置。
  * *在固定脚手架下，微调提高了平均恢复的行为。* 使用 Claude Code 时，Tests Passed 从 34.87% 升到 42.84%（+7.97）。
  * *同样的权重下，工作流带来的提升大得多。* Program-Agent 把 Qwen3.8-27B 从 34.87% 提到 55.71%，把微调模型从 42.84% 提到 56.25%；对基座模型，通过至少 50% 测试的任务占比从 40.5% 升到 62.0%，通过至少 75% 的从 18.0% 升到 34.0%。
  * *轮数很重要。* 微调模型的 Tests Passed 在 $K=1$ 时为 43.49%，$K=3$ 时 54.13%，$K=5$ 时 56.25%。一轮 Program-Agent 与单会话基线（42.84%）大致相当，所以提升来自评审与修订，而不是角色分离本身（读者观察）。论文还报告，这三种预算的输出 token 都少于基座模型的 Claude Code 运行。
  * *完整复现程序仍未解决。* 每一行的 Resolved 都在 0.00-0.50%。
* **比标题结论更弱或更窄之处。**
  * *微调提高了部分得分，却减少了接近完成的解。* 在 Claude Code 下，SFT 之后 Almost Resolved 从 3.50% 降到 1.50%，Resolved 从 0.50% 降到 0.00%，通过至少 75% 测试的任务占比从 18.0% 降到 9.5%。论文承认 SFT“无法稳定提升高保真的情况”。训练集的 1,648 个任务中有 1,492 个是简单任务，且按通过率过滤，因此它教会的可能更多是把常见行为做对，而不是把事情做完（读者推断）。
  * *在更强的脚手架下，训练带来的提升几乎消失。* 使用 Program-Agent 时，SFT 只让 Tests Passed 增加 0.54 个点（55.71% 到 56.25%），Almost Resolved 从 5.50% 降到 4.50%。
  * *SFT 的结果同时也是蒸馏的结果。* 轨迹来自 DeepSeek-V4-Flash-0731，它在 Claude Code 下得分 57.68%，远高于学生模型。没有对照实验在未过滤的轨迹上训练，或让同一个教师在没有验证过测试的环境中产生轨迹，因此“让监督有用的是经过验证的测试”这一说法没有被单独验证（读者观察）。过滤所用的通过率阈值在已读部分中没有找到。
  * *Program-Agent 帮助弱模型，对强模型几乎没用。* DeepSeek-V4-Flash-0731 从 57.68% 到 58.97%（+1.29）。
  * *“超过旗舰模型”混用了脚手架和时间点。* Claude Opus 4.7（50.90%）和 Gemini 3.5 Flash（53.60%）是 ProgramBench 发布时在 mini-SWE-agent 下的数字，而本文的运行使用带上下文压缩的 Claude Code，或五轮的工作流；论文自己的脚注说旗舰模型后来的结果在 ProgramBench 网站上。xhigh 档的 Opus 4.7（55.10%）与两个 Program-Agent 结果相差不到 1.2 个点。
  * *没有对 Program-Agent 的各部分做消融，且只跑一次。* 角色隔离、实现者不能访问参考程序、带构建关口的回滚，都没有逐项去掉；没有报告方差。
  * *测试质量只做了结构性检查。* 四项检查剔除在参考程序上失败、不稳定、接受空壳实现或断言过弱的测试；但没有测量测试集让“错误但看似合理”的复现通过的频率，覆盖率也有一条长长的低尾，论文将其归因于黑盒接口无法到达的代码。

# Q9 贡献

* 一条由反馈驱动的流水线，把仓库转换成程序复现环境，带四项检查的测试验证器和由覆盖率引导的测试编写，并用它构建了 1,648 个环境。
* 一个分阶段的智能体工作流：会话隔离、冻结的交接文档，以及带回滚的独立构建关口。
* 证据表明两者在 ProgramBench 上都有帮助，其中工作流贡献了大部分提升。
* 描述性发现：成功的复现通常比参考实现小（在通过至少 75% 测试的解中，代码行数比的中位数为 0.64，共 182 次运行、93 个任务），参考实现为 C/C++ 时最明显（0.39），为 Rust 时最不明显（0.72）。

# Q10 下一步

* **作者提出的。** 随着模型变强，把流水线扩展到中等和困难的仓库，以及 30,459 个候选中的其余部分；发布 ProgramGym。
* **把监督信号单独分离出来（读者建议）。** 在同一教师的未过滤轨迹上训练，以及只用随机一部分测试来过滤，以测量经过验证的测试集在蒸馏之外增加了什么。
* **以完成为目标（读者建议）。** 既然 SFT 降低了 Almost Resolved，可以尝试按接近完成的结果来过滤或加权，或者在 Program-Agent 而不是单会话 Claude Code 下采集轨迹，让训练数据包含“评审并修复”的行为。
* **对工作流做消融（读者建议）。** 在固定 $K$ 下，逐项去掉对参考程序的访问限制、构建关口或会话隔离。
* **项目契合（读者笔记）。** Program-Agent 的规则与本仓库的 dispatch 模式高度对应：冻结的分析文档、看不到判定依据的实现者、只读的评审者，以及回滚到上一个通过验证的状态。“一轮相当于单会话、提升随评审轮次到来”这一实测结果，是把预算花在评审迭代而不是更长的单次运行上的理由。
