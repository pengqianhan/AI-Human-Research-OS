# Q1 问题定义

* **输入 (X)：** 一个策略模型（Qwen3.5-4B 或 9B）、一个基础 harness H0（DeepSeek Harness，简称 DSH）、带二值验证器的训练与验证任务，以及一个负责改写 harness 的 LLM 编辑器。
* **输出 (Y)：** 一个更新后的策略，要求在*原始 H0 下*表现更好，也就是训练时借用的额外执行支持在部署时不再需要。副产品是一个可复用的兄弟 harness 池和一个路由器，推理时也可以为每个任务挑选一个 harness。
* **约束：** 兄弟 harness 必须保留 H0 的执行底座、环境接口和验证器；策略训练期间 harness 池固定不变；只有策略生成的 token 进入损失。

# Q2 问题新颖性

部分新。自动化 harness 优化（Meta-Harness、ADAS、GEPA、Darwin Gödel Machine）和 harness 与策略联合优化（WHALE、HarnessForge、Co-Harness、HarnessX、HarnessBandit）都已存在。本文的新角度是：策略必须在没有帮过它的 harness 时也能工作。作者用在 AppWorld 上对 Qwen3.5-4B 测得的三个性质说明动机：*局部性*（locality，一次修改修好一部分失败，同时弄坏一部分原本能解的任务）、*互补性*（complementarity，兄弟 harness 能补救彼此的错误，它们的并集覆盖的任务多于任何单个兄弟，也多于同样 rollout 数下在 H0 上重复采样）、*非平稳性*（nonstationarity，随着策略训练，某个 harness 相对 H0 的优势可能变成劣势，排名也会反转）。据此作者认为，把各种修复合并成一个"最佳 harness"，或者让 harness 跟着策略反复重新演化，都不是正确的目标。

# Q3 科学假设

如果只在 H0 下所有 rollout 都失败的任务上，调用那些修复不同失败的兄弟 harness，那么同一策略在它们下面的成功 rollout 就能恢复 GRPO 需要的奖励对比；这些 rollout 强化的行为在策略回到 H0 运行时应当保留下来。若假设成立，在 H0 下评测的策略应当在相近采样成本下胜过"在 H0 上重新采样"，而且训练后路由器应当更常选择 H0。

# Q4 相关工作与关键人物

* **智能体强化学习与稀疏奖励。** [GRPO](../concepts/grpo.md)、DAPO 对混合组的动态采样、RAGEN、在 AppWorld 上的 LOOP、AgentGym-RL、[Agent Lightning](../papers/2508.03680.md)，以及处理稀有成功的经典方法（Hindsight Experience Replay、RUDDER、Go-Explore）。
* **知识迁移。** 策略蒸馏（policy distillation）、kickstarting、专家迭代、STaR、DAgger、GKD，以及特权信息学习（Learning by Cheating）。最接近的类比是后者：辅助 harness 是训练时才有、部署时没有的支持。
* **关键人物。** 第一作者 Kangning Zhang；通讯作者为上海交通大学的 Weiwen Liu、Weinan Zhang 与小红书的 Wenxiang Jiao、Yuan Lu；合作者来自中关村人工智能研究院、东南大学和卡内基梅隆大学。可能的批评者：WHALE 和 HarnessForge 的作者（他们的方法在本文中以复现版出现），以及 Meta-Harness 的作者，他们会问：共同演化出的 harness 如果在自己的 harness 里评测、而不是在 H0 下评测，结果如何。

# Q5 关键解决思路

**定向 harness 演化（Directional Harness Evolution）。** 从 H0 出发，每一轮在训练任务上运行父 harness，把失败归并成若干修复方向（每个方向包含两到三个相关根因，每个根因至少出现在两个失败任务中），再由编辑器（GLM-5.3）为每个方向写出一个子 harness。修改可以涉及提示、技能、上下文、记忆、钩子（hooks）或工具视图。下一轮的父代（最多四个）按验证任务解出数量的*并集*最大化来选，所以能覆盖别人失败的父代比单项得分高的父代更有价值。所有可执行且符合协议的子代都保留下来。三轮之后，池中有 H0 和 19 个兄弟 harness，随后冻结。附录 D 给出典型修改：一个提醒"翻页直到出现短页或空页"的钩子、一条"按条件取交集而不是扩大到所属集合"的规则，以及一个"预算不足时留一步给 `complete_task`"的提醒。

**互补 harness 救援训练（Complementary Harness Rescue Training）。** 对每个任务，策略先在 H0 下采样 K = 8 条 rollout。只要有一条成功，这组照常训练；如果全部失败，路由器选出八个兄弟 harness，同一策略从任务初始状态在每个兄弟下各尝试一次，用这组新的 rollout 替换失败的那组。之后 GRPO 使用组内相对优势，裁剪不对称（0.20 和 0.28），不加 KL 项，对 rollout 后端与训练后端给同一 token 不同概率的情况做截断校正，损失在每个任务内按策略 token 平均。harness 注入的文字和工具观察不进入损失。

**自适应 harness 路由器（Adaptive Harness Router）。** 对每个兄弟 harness，由一个 LLM 比较配对的验证轨迹（兄弟对 H0），写出由"偏好"和"避免"条目组成的*行为画像*（behavior profile），每条包含"何时"（When）和"行为"（Behavior）。随后多个 LLM 根据画像、验证成功率和相似任务上的结果，为每个任务给四个候选排名，投票按权重 1、3/4、1/2、1/4 相加。*感知策略的画像重锚定*（policy-aware re-anchoring）每十次更新用冻结的当前策略重建一次画像，因为兄弟 harness 的有用程度会随策略学习而变化。推理时，同一个路由器可以在任何尝试之前，从包括 H0 在内的全部 20 个 harness 中为每个任务选一个（"Rank-1"）。

# Q6 实验设计

* **基准。** [AppWorld](../concepts/appworld.md)（训练 320、验证 150、测试 262）、DBBench（1,600、200、300）和 [SWE-Gym](../concepts/swe-gym.md)（240、100、160）。训练任务用于 harness 编辑和策略更新；验证任务用于选父代和建画像；测试任务留作最终评测。
* **指标。** Pass@3（三次 rollout 中至少成功一次，见 [Pass@K](../concepts/pass-at-k.md)）和 Avg@3，报告为三次随机化运行的均值，只有 Harness-S 给出标准差。
* **对比方法（都从同一个 Qwen3.5 初始策略和基础 harness 出发）。** 普通 GRPO；带 H0 救援的 GRPO（全失败的组在 H0 下用相同的单任务配额重新采样）；两种固定混合（每个任务四条 DSH 加四条 Claude Code rollout，或 DSH 加四个兄弟 harness）；冻结策略的 Meta-Harness；冻结策略的 Harness-S（只做 harness 演化）；以及复现的 WHALE 和 HarnessForge。Meta-Harness、WHALE 和 HarnessForge 用各自选出的最佳 harness 评测，Harness-S 在 H0 和 Rank-1 路由下评测。GPT-6-Sol、DeepSeek-v4-Flash 和 GLM-5.3-Flash 在 H0 下的结果作为参照。
* **机制与消融（大多在 AppWorld、4B 上）。** 训练过程中的有效组比例和 token 占比（图 3）；固定八条救援 rollout 预算下的分配变体（随机、无画像的规则路由、四个 harness 各两条、固定画像 Top-8、自适应 Top-8；表 2）；AppWorld 和 SWE-Gym 上由 LLM 标注的 H0 下行为频率（表 3）；两个追踪迁移的案例（表 4）；训练前后的路由排名（表 5）；迁移到 Claude Code 和 OpenClaw harness（图 4）；以及成本（表 9 和表 10）。

# Q8 证据质量

* **有支持的结论。**
  * *在 H0 下更好，而且不只是多采样。* 在 H0 下，Harness-S 在全部 12 个"基准 × 规模 × 指标"格子里都胜过普通 GRPO 和带 H0 救援的 GRPO（读者统计）。4B 在 AppWorld 上达到 67.56 Pass@3 和 56.87 Avg@3，GRPO 为 60.31 和 48.98，H0 救援为 61.83 和 51.91。救援对照用的 rollout 比 Harness-S 多（3,616 对 3,032），GPU 时间也更多（97.77 对 67.19 GPU 小时），得分仍更低。这一成本对比只针对 AppWorld 4B。
  * *测试时不靠辅助也领先联合演化基线。* 在 9B 上，Harness-S 在 H0 下（AppWorld、SWE-Gym、DBBench 的 Pass@3 为 72.52、40.00、76.33）胜过在自身最佳 harness 下的 WHALE（68.70、33.75、74.00）。加上 Rank-1 路由后，它在 DBBench 上达到 78.00 Pass@3，高于那里的三个前沿参照（最高 76.67），但在 AppWorld 和 SWE-Gym 上没有。
  * *可用的组更多。* 同时含成功和失败的组在整个训练中占 79.38%，H0 救援为 70.94%，GRPO 为 64.69%；对应的 token 占比为 80.88% 对 72.68%。H0 下的验证成功率最终为 63.33%，对比 54.00% 和 48.00%。两种固定混合最后都低于普通 GRPO，说明 harness 多样性要用在失败任务上才有用，平均撒在所有任务上不行。
  * *重锚定有作用。* 在同样八条救援 rollout 下，自适应画像在四个训练阶段都胜过固定画像，最终 Avg@3 高 4.71 分。
  * *训练后对辅助的依赖下降。* 训练后路由器把 H0 排第一的任务占 22.52%，训练前为 1.53%；Rank-1 相对 H0 的 Avg@3 优势从 13.49 分缩小到 4.58 分。
* **比标题弱或范围更窄的地方。**
  * *报告的"均值"看起来像单次运行的计数。* 测试任务分别为 262、160、300 个，单次运行的 Pass@3 以 1/N 为步长变化，Avg@3 以 1/(3N) 为步长；三次运行的均值只有大约三分之一的概率恰好落在这个网格上。表 1 的 150 个格子里有 149 个正好落在上面，这更符合单次运行或中位数，而不是所说的三次均值（读者核查）。唯一的例外是 4B 基础模型 42.62 的 AppWorld Pass@3，它也和第 4.6 节引用的 14.21 分 Rank-1 优势对不上（56.87 减 42.62 是 14.25）。± 只属于 Harness-S，基线没有给出波动。
  * *SWE-Gym 的增益主要来自"广度"。* 在 4B 上，Pass@3 比 GRPO 高 14.37 分，Avg@3 只高 6.25 分；Harness-S 两个指标之间差 10 分，而 GRPO 不到 2 分（读者计算）。策略变得更擅长在三次中找到一次修复，而不是每次都修好。
  * *分阶段的救援成功率建立在很少的任务上。* 表 9 的 rollout 数意味着每次更新八个任务（40 次更新共 2,560 条 rollout，每组八条），Harness-S 多出的 472 条 rollout 意味着整个训练中约救援了 59 个任务，平均每十次更新的阶段约 15 个（读者算术）。因此表 2 各阶段之间的差异不确定性很大。
  * *验证集身兼数职。* 同一批验证任务用来选父代、建画像，又给出图 3c 的学习曲线；第二个迁移案例也是验证集实例。只有表 1 和行为频率使用留出的测试任务。
  * *迁移证据是行为层面的、个案性的。* 行为频率由一个未具名的 LLM 标注轨迹得到，迁移案例是两个挑选出来的 AppWorld 例子。它们与"行为被内化"相符，但不能证明正是救援轨迹导致了 H0 下的行为；那需要一个去掉救援组的消融。
  * *基本上只有一个设置。* 机制、消融、路由和成本分析都是 AppWorld 加 4B 模型。跨 harness 迁移只在一张图里展示，而且训练后的策略在 Claude Code 和 OpenClaw 下的得分低于在 DSH 下。
  * *基线是改编版。* WHALE 和 HarnessForge 是在公共框架内复现的，冻结策略的对比也用的是改编过的 Meta-Harness，因此可能与原系统有差异。
  * *Rank-1 不是免费的。* "相同执行 rollout 数"没有算进推理时每个任务的多 LLM 投票调用；表 10 的 API token 总数只统计了完整流程（读者观察）。

# Q9 贡献

* 用测量说明来自同一基础的 harness 变体具有局部性、互补性和非平稳性，并由此得出设计结论：一个池优于一个合并后的单一 harness。
* 一个训练方案：只用 harness 池救援全失败的组，并在不带池的条件下评测结果，从而把策略保留下来的增益和推理时的额外支持分开。
* 一种路由方法：用相对于当前策略的行为画像描述每个兄弟 harness，并随策略变化刷新，推理时也能复用。
* 与重新采样、固定混合、冻结策略的 harness 搜索以及复现的联合演化基线做了带成本的对比。

# Q10 下一步

* **池的复用与扩展（论文提出）。** 在不同策略之间复用一个池，让独立构建的 harness 之间交换任务状态，并测量增加修复多样性如何影响增益和校准成本。
* **因果性的迁移检验（读者建议）。** 训练时去掉救援组，或者在 H0 下以相同数量和成功率采样救援组，再比较 H0 下的行为频率，以区分"从兄弟 harness 的行为中学习"和"只是有了更多混合组"。
* **报告每次运行的结果（读者建议）。** 公布每个格子的三次运行以及基线的波动，可以解决网格问题，也能判断几个百分点的差距是否显著。
* **更便宜的路由（读者建议）。** 用 LLM 投票蒸馏出一个小分类器，可以看出不做每任务多 LLM 调用时，Rank-1 剩余的 Avg@3 优势还剩多少。
* **harness 特有的行为（读者建议）。** 这里迁移的行为（先查 schema、翻页、写后读回、断言检查）看起来是通用流程。检验增加新*工具*而不是提醒和规则的兄弟 harness 是否也能迁移，可以看出方法的边界。
