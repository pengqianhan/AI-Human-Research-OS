# Q1 问题定义

* **输入（X）：** 一条描述某种不良智能体行为的自然语言查询（例如“工具调用失败后原样重试”）、一批部署轨迹记录（指令、消息、工具调用、工具结果等事件），以及目标基准规模区间（默认 5 到 50 个实例）。查询还可以附带行为参数、领域限制、轨迹约束（如“上下文超过 100,000 token”），或用 AND/OR 组合两种行为。
* **输出（Y）：** 一个基准，由若干上下文输入组成，每个输入是某次已确认出现该行为之前的轨迹前缀；外加一份针对该行为的 0-5 分评分细则（rubric）。若无法构建有效基准，则返回拒绝及理由。
* **如何测试模型：** 被评测的 LLM 读入前缀，只生成下一个助手回合（文本、工具调用或两者兼有），由评审模型组只对这一回合打分。不执行动作、不续写轨迹，也没有参考答案：部署中原模型的那一回合只是“不良行为确实发生过”的证据，不是标准答案。
* **约束：** 目标行为必须留下代码可检索的可观测信号（工具报错、调用参数、事件顺序、关键词）。需要 LLM 或人逐条阅读每个会话才能发现的行为不在范围内，因为在部署规模下代价过高。

# Q2 问题新颖性

部分新。Terminal-Bench、RE-Bench、MLE-bench、PaperBench 等结果型基准检查任务是否完成；AgentHarm 等安全与过程型评测检查执行中的行为，但用例和目标行为都是固定的。轨迹审计工具能在记录中找出失败和模式，却不会把这些记录变成用来测试其他 LLM 的基准。从历史记录或保存状态续写 LLM 的做法已有先例，OpenAI 也会在发布前用部署对话重新生成候选模型的回复。作者的主张更窄：TraceDance 是第一个能针对用户指定的不良行为、从部署轨迹*按需*构建基准的系统。动机在于：随着智能体和部署环境变化，会不断出现新的行为问题；而许多轨迹来自私有仓库、内部工具或 MCP 服务器，无法回放。

# Q3 科学假设

作者的直觉是：部署中的智能体确实表现出不良行为的那段上下文，很可能也会把其他 LLM 引向同样的行为。如果在该行为之前截断轨迹，并用针对该行为的评分细则给各 LLM 的下一回合打分，那么得到的基准应当（1）有效，即人工认同实例确实在测所要求的行为；（2）可由 LLM 评审组打分，可靠程度接近人工；（3）有信息量，能暴露结果型基准看不到的弱点。另一条工程假设是：先在 CPU 上做廉价的可编程检索，再只让 LLM 确认检索到的候选，就能以可承受的成本处理几十万个会话。

# Q4 相关工作与关键人物

* **结果层面的智能体评测：** Terminal-Bench（检查最终容器状态）、RE-Bench 与 MLE-bench（性能指标）、PaperBench（基于评分细则的 LLM 评审）。
* **安全与过程层面的评测：** AgentHarm 等固定评测集，以及让 LLM 评判拟执行动作或已记录轨迹的方法。
* **基于续写的评测：** 从交互历史、合成的风险触发决策点快照或保存的执行状态继续生成；Prefix-GRPO 在训练中使用教师前缀；OpenAI 发布前在部署对话上重新生成回复。
* **智能体审计与自动基准构建：** 总结行为模式或定位用户指定违规的轨迹审计工具；BenchTrace 在固定环境中让智能体以标注过的失败为条件；生成行为或安全场景的方法（包括开源自动行为评测工具 Bloom）；从记录会话重建可执行任务的 REAP 和 SWE-Together；用真实日志播种合成对话的 WildToolBench。会话领域聚类沿用 Clio 的做法。
* **关键人物：** Dehai Min（联系人，伊利诺伊大学芝加哥分校）和 Philip S. Yu（UIC），以及字节跳动的合作者；部署轨迹来自字节跳动运营、主要由豆包 Seed 模型驱动的智能体。可能的批评者：环境回放型基准的构建者（会指出只评一个回合看不到最终结果），以及对 LLM 评审持怀疑态度的人。

# Q5 关键解法思路

* **决策点续写，分三种框架。** *动作*框架在目标动作之前截断（“这里该做什么？”）；*失败*框架保留观察到的失败、去掉原回复（“该如何应对失败？”）；*声明*框架保留已记录的工作和结果、去掉原声明（“应当声明什么，还是不声明？”）。实例只有同时满足三点才保留：被留出的原回合确实表现出该行为；上下文包含做决定所需的信息；该决定在前缀末尾尚未做出。
* **行为规格由四部分组成：** 定位候选位置的可执行锚点（anchor）、确认标准、按框架确定的截断规则，以及评分细则。
* **锚定-确认（Anchor-and-Confirm）。** 锚点在 CPU 上扫描轨迹，不调用 LLM；随后由廉价的“Flash”模型（DeepSeek-V4-Flash）只确认检索到的候选。GPT-5.6-Sol 担任强模型，负责选择和编写规格；Claude Opus 4.8 担任审查模型，审计自定义规格及其锚点代码。
* **目录加合成。** 从每个场景预留的 10,000 个会话中挖掘出 28 个行为族（动作 13、失败 10、声明 5），经人工审核后编入目录。复用目录中的规格时，三次独立的族选择须至少两次一致，随后三次等价性检查须全部通过；否则进入*锚点合成循环*（Anchor Synthesis Loop）：编写新规格、做安全检查和代码审查、运行锚点，再依据检索统计修改。限制为最多 5 轮、至少检查 8 个会话、确认率不低于 25%、至少 8 个确认样例，其中 3 个即可开始验收审查。一个例子里，依赖清单（manifest）锚点被改为检查决策点当时的状态，而不是要求之后有清单编辑，匹配会话数从 3 增加到 32。
* **忠实保留前缀。** 每个实例保留系统指令、工具定义、用户输入与脚手架注入的输入（系统提醒、技能说明）、助手消息和工具结果，只删除原模型的推理块；在脚手架强制的回合（如请求压缩摘要）处不截断。
* **评分。** 三个评审模型（GPT-5.6-Sol、Gemini-3.5-Flash、Claude Opus 4.8）按 0-5 分细则打分，平均分不低于 4 即算通过。

# Q6 实验设计

* **轨迹：** 六周内收集的 252,557 个去标识化会话，来自 Claude Code（75,076 个，编程）和 OpenClaw（177,481 个，通用工具使用），主要由豆包 Seed 2.0 模型驱动。每个场景预留 10,000 个会话用于行为发现，不参与基准构建。
* **查询：** 139 条测试查询，其中 107 条应当构建成功（98 条预定义、9 条自定义），32 条应当被拒绝（27 条对抗性查询、5 条缺少必要数值参数）。查询由 LLM 起草、作者审核。
* **被评测模型：** Claude Opus 4.8、GPT-5.6-Sol、GLM-5.2、DeepSeek-V4-Flash、DeepSeek-V4-Pro、Qwen3.7-Max、MiniMax-M3、Doubao-Seed-2.1-Pro、Kimi-K3。每个模型通过各自提供方的工具调用 API 接收原样记录的系统提示和工具定义，推理强度设为高，输出上限 32,768 token。
* **人工验证：** 8 名标注者，每项由两人独立标注，覆盖 100 条查询和 100 个按行为族分层抽样的实例；标注者看不到评审分数和模型身份。
* **稳健性检查：** 评审自偏好、对 107 个基准做 5,000 次自助重采样以得到排名区间、替换通过阈值，以及比较来自豆包模型与其他模型的实例。

# Q7 数据集与代码

构建内容：TraceDance 流水线、28 个行为族的目录，以及 107 个基准共 4,125 个实例。代码见 [ZhishanQ/TraceDance](https://github.com/ZhishanQ/TraceDance)，另有[项目主页](https://zhishanq.github.io/TraceDance/)。部署轨迹不公开，因此作者说明无法用公开数据重建完全相同的基准，但流水线可用于其他轨迹集合。附录给出了精简版提示词，以及一个从构建到评分的完整示例。

# Q8 证据质量

* **有支撑的：**
  * *能规模化构建。* 107 条应构建的查询中有 102 条成功（95.3%），32 条应拒绝的查询全部被拒。每条成功查询平均扫描 128,297 个会话，把 706 个候选交给 Flash 模型，保留 40.4 个实例，共调用 LLM 552 次（被拒的对抗性查询仅 1.3 次）。
  * *大多能理解查询。* 标注者认为 78% 的系统理解准确、17% 部分正确；在 100 条查询中，两名标注者对“是否需要澄清”的判断有 96 条一致。
  * *实例和评分细则大多有效。* 100 个抽样实例中，两名标注者都确认存在目标行为的有 84 个；两人都给评分细则打 4 分及以上的占 90%（平均 4.75）。最常见的意见是相邻分档边界不清（21 次）。
  * *评审组与人工的一致程度接近人工之间的一致程度。* 在 84 个实例上，评审组与人工的通过/不通过一致率为 81.0%（单个评审 65.5%-79.8%），Cohen's κ 为 0.40，两名标注者之间为 0.31。
  * *前沿 LLM 在这些决策点上大多失败。* 总体通过率从 22.9%（Qwen3.7-Max）到 33.5%（Claude Opus 4.8），平均 26.7%。声明框架最难（平均 20.3%），OpenClaw 比 Claude Code 更难（22.9% 对 28.3%）。在自助重采样中 Opus 有 99.9% 排第一，领先第二名 4.2 个百分点（95% CI 1.7-6.6）。九个模型分为三组，组内差异不显著。
  * *“先检查再行动”最弱。* 平均通过率：发出格式正确的工具调用 67.9%，处理失败 33.5%，诚实声明 28.9%，执行必要检查 8.1%。单个行为族最低可到 6.9%（保护密钥）、0.9%（提交规范）和 0.6%（查看失败日志）。把通过阈值从 4 改为 3，“先检查”升到 26.8%，但在所有测试的阈值下，四组的排序和 Opus 的第一名都不变。
  * *总体排名掩盖了单项强项。* 在“按错误提示修正”上，Kimi-K3 通过 57.8%，Opus 只有 27.8%。GPT-5.6-Sol 总体排第五，却在 28 个行为族中的 8 个领先，包括“测试声明有据”（60.2%，其他模型最高 39.5%）。GPT-5.6-Sol 公开报告的 SWE-bench Pro 和 Terminal-Bench 2.1 分数高于 DeepSeek-V4-Pro 和 GLM-5.2，但在这里并不胜过二者。
  * *检查了两个混杂因素。* GPT-5.6-Sol 作为评审对自己的回复有轻微偏好（0-5 分制上 0.22 分，置信区间不含零），Opus 没有明显偏好；去掉每个模型自己的评审后，其排名不变。Doubao-Seed-2.1-Pro 在来自豆包模型的实例上没有家族特有的劣势（总体 −0.9 个百分点；只看 Seed 2.0 来源时为 −1.2，CI −3.3 到 +0.9）。作者指出这些区间排除了大于约 3 个百分点的劣势，但不能排除更小的。
* **较弱或有边界的：**
  * *只评一个回合看不到结果。* 先做规划或收集信息的回复之后可能表现很好，通过的回复真正执行时也可能失败；作者说明这是对任务级评测的补充，而非替代。以 TodoWrite 开头的回复在同样实例上通过率为 4.6%，其他首动作为 30.8%（九个模型都如此），但作者强调这是相关而非因果。这种惩罚可能部分来自单回合设计本身（读者推断）。
  * *通过率是条件性的。* 每个实例都来自不良行为已经发生过的上下文，因此通过率不能估计该行为在部署中的发生频率；评分细则也只奖励最恰当的回复。
  * *评审组偏宽松。* 三个评审的平均分都高于人工（2.02-2.90 对 1.68；0 分比例 11.9% 对 39.3%）。由于人工只判 16.7% 的回复通过，原始一致率被抬高：全部判为不通过也能达到 83.3% 的一致。κ = 0.40 只算中等，验证样本也只有 100 个实例。
  * *16% 的抽样实例未得到两名标注者共同确认*，所以每个基准里都有一部分实例可能并不在测所要求的行为。
  * *无法用公开数据复现。* 轨迹不公开，非豆包来源的模型构成也属保密。
  * *构建侧的模型也在被评测之列。* GPT-5.6-Sol、DeepSeek-V4-Flash 和 Opus 4.8 参与编写规格或确认候选，同时也在九个被评测模型之中。论文分析了评审自偏好和来源模型家族，但我在检索到的正文中没有找到对构建角色偏差的分析（读者笔记）。
  * *递归自我改进的定位尚未验证。* 作者把在 RSI 循环中评估 TraceDance 留作未来工作。

# Q9 贡献

* 决策点续写：无需环境回放、就能在真实部署上下文中评测智能体行为的方法，也适用于来自私有工具和 MCP 服务器的轨迹。
* 锚定-确认加锚点合成循环：一条从自然语言行为查询到经验证基准的、成本可控的流水线，带有明确的接受与拒绝规则。
* 一份覆盖编程和通用工具使用、基于真实部署的 28 族不良行为目录，以及 107 个经过人工验证（实例、评分细则、评分）的基准。
* 对九个前沿 LLM 在智能体决策点上的量化画像：必要检查、密钥处理和诚实声明远弱于工具调用格式，而总体排名掩盖了明显的单项反转。

# Q10 下一步

* **闭环**（作者明确的未来工作）：在模型改进循环中使用 TraceDance 基准，检验后续版本能否修复目标行为且不引入回归。
* **多回合续写：** 评几个回合，或在可能时在沙箱中执行下一回合，能区分“先规划、后来做得好”和真正的失败——这正是 TodoWrite 结果中最大的不确定性。
* **构建偏差对照（读者笔记）：** 换用不同的强模型和 Flash 模型重建部分基准，检查被评测模型的排名是否改变。
* **基础发生率（读者笔记）：** 该流水线测的是“给定坏上下文时的行为”。结合同一批轨迹中的发生频率估计，能看出哪些弱点在部署中最要紧。
* **与本 wiki 的联系（读者笔记）：** [RRSI](../papers/2609.24972.md) 主张脚手架自我改进需要留出、考虑噪声的门控，TraceDance 基准可以作为这种门控的来源之一。[AI Agents Do Not Fail Alone](../papers/2607.14275.md) 在执行前给上下文打分，TraceDance 则在固定上下文下给模型的决定打分，两者结合可以区分上下文问题和模型问题。[EmbodiedSWE](../papers/2609.27308.md) 在整次运行层面审计奖励投机，这类过程检查在 TraceDance 的声明框架中对应到单个决策点。
