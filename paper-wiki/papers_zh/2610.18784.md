# Q1 问题定义

* **输入（X）：** 长程智能体不断增长的交互历史（动作、观察、截图、推理摘要），以及它所操作的环境；已经完成的工作其实已经保存在文件、文档或应用状态里。
* **输出（Y）：** 每次折叠（fold）时，用来替换被覆盖历史的上下文视图 V_t = (A_k, E_k, L_t)：A_k 是延续载体（continuation carrier）记录的集合，E_k 是执行上下文（execution context），L_t 是自上次折叠以来的实时尾部（live tail）交互。
* **目标：** 让智能体仍能继续完成任务（得分不变或更高），同时不再反复阅读"环境里已经存好的进展是如何得来的"这类叙述，使活动上下文和成本不再随轨迹长度增长。
* **约束：** 一次折叠只能提交有绑定证据支持的载体修改；原始交互保存在只追加的日志里；论文明确说明，运行时的检查保证的是一致性，而不是任务正确性。

# Q2 问题新颖性

论文把已有工作分成两类。压缩与选择类方法缩短或检索过去的交互：提示词压缩（LLMLingua、LongLLMLingua）、轨迹精简、周期性摘要（ReSum、ACON、AgentFold、HiAgent）、分支返回（context folding）、外置历史（MemGPT、ACM），以及对照后续执行来验证压缩结果（Slipstream）。状态外置类方法把进展保存为显式记录：把先前记忆与新观察合并成内部状态（MEM1、Context as a Tool），执行状态树、持久变量或任务记录（*Memory as execution state management*、AgentProg、StructAgent、[LongHorizon-Harness](../papers/2608.01964.md)），以及持久工作区加重建视图（InfiAgent、*Context as an environment*、FS-Researcher）。论文的主张是：这两类方法仍然依赖一份关于进展的叙述（压缩的或重建的）来继续工作，而这份叙述可能与智能体实际检查、修改的状态产生偏差。CarryOn 把可复用的任务对象本身当作延续的单位，文本中只保留这些对象没有承载的信息。

# Q3 科学假设

如果长程上下文围绕可复用的任务对象来组织——每个载体说明某个对象承载了哪些进展、在什么条件下可以复用——而执行上下文只保留对象没有涵盖的目标、约束和未完成工作，那么智能体就可以丢掉被覆盖的历史而不丢失继续所需的信息。它应当在处理少得多的 token 的同时，得分不低于保留完整历史的情形。论文还预期起作用的是结构而不只是"变短"：长度相近的通用摘要或滑动窗口应当更差，而跨折叠维护记录应当优于每次折叠都重写一份完整摘要。

# Q4 相关工作与关键人物

* **压缩与选择。** LLMLingua 和 LongLLMLingua；轨迹精简（Xiao 等）；ReSum、ACON（论文复用了它的 FIFO 截断和摘要基线）、AgentFold、HiAgent；通过分支返回实现的 context folding；把历史放在提示词之外的 MemGPT 和 ACM；检索式记忆 Memory OS 和 A-MEM；做预测式抽取的 PACE；对照后续执行验证压缩的 Slipstream。
* **状态外置。** MEM1 和 Context as a Tool（把新观察并入内部状态）；Agent Workflow Memory，属于把历史转成显式进展记录的方法；执行状态与任务记录类方法（*Memory as execution state management*、AgentProg、StructAgent、LongHorizon-Harness）；持久工作区（InfiAgent、*Context as an environment*、FS-Researcher）。
* **基准。** OSWorld 2.0（主评测，v2026.08.08 版）、BrowseComp-Plus，以及作为早期桌面基准的 OSWorld。
* **关键人物。** Yuchen Lu、Julian McAuley 和 Lei Zhang（通讯作者），均来自加州大学圣地亚哥分校。可能的批评者：ACON 和 AgentFold 的作者，他们经过学习或主动式的压缩方法不在基线之列；LongHorizon-Harness 和 *Context as an environment* 的作者，他们同样外置状态，但保存的是维护好的记录而不是对象引用。

# Q5 关键解决思路

**三种载体。** *外部对象*（external object）是独立存在、可以重新打开的工作产物（代码文件、文档、表格），它的记录引用该对象并说明其中承载的进展。*信息产物*（information product）是通过交互获得、但没有保存到任何地方的结论（综合出的信息、排错结论），因此记录直接以带来源引用的断言（claim）形式保存它。*情境状态*（situated state）是只存在于某个应用、会话或流程内部的进展（停在支付步骤的结账流程、未保存的工作簿），它的记录写明环境锚点、已建立的状态，以及该状态保持可复用的范围。每个载体都有稳定身份，修订时在同一身份下生成后继版本。

**执行上下文与实时尾部。** 执行上下文保存当前焦点、未完成的义务、生效中的约束和下一步操作中没有被任何载体覆盖的部分，每条都附有来源。实时尾部保存自上次折叠以来的原始交互。

**四阶段折叠。** (1) 追踪器（Tracker）读取最近的交互，维护候选项（潜在的新载体或对已有载体的更新），并在某个候选项足以支撑继续执行时请求编译。(2) 运行时把每个请求绑定到证据：信息产物绑定来源摘录；对象则由校验器（Grounder）做限定范围的只读检查（文件是否存在、内容哈希是否不同于初始快照、文件是否非空、docx/pptx/xlsx 容器是否有效、文档文本差异、是否包含从任务说明中复制的文本），每个条件返回"支持""矛盾"或"未知"。只有完全得到支持的对象请求才会继续。(3) 编译器（Compiler）只对选中的候选项提出载体修改，并以其绑定证据为依据；同时依据整个实时尾部修订执行上下文，确保候选项之外的信息不丢失。(4) 运行时检查身份、引用、来源授权，以及输入记录是否仍是最新版本。一次折叠必须至少改动一个载体；通过后原子提交并清掉整个实时尾部，否则什么都不变。未受影响的载体保留原记录，因此大部分进展是被延续下来，而不是被重建。

# Q6 实验设计

* **基准。** 完整的 OSWorld 2.0（每个任务 500 步预算；按官方协议报告部分分和二值分），以及随机抽取的 100 道 BrowseComp-Plus 题（BM25 检索，每次调用返回 5 条 512 token 的片段，60 轮；答案由 Qwen3-32B 按官方提示词评分）。
* **模型。** Claude Opus 4.7 同时担任宿主智能体、追踪器和编译器，不做训练；OSWorld 智能体使用最高档自适应思考。基线是同一智能体使用其原生上下文处理，由作者复现；其他模型的 OSWorld 2.0 结果取自已发表的数据，仅作参考。
* **触发条件。** OSWorld 2.0 上，自上次扫描或折叠以来累计约 6,000 token 的交互文本（字符数除以 4）时运行追踪器；BrowseComp-Plus 上，提示词增长 120,000 token 后运行，连续扫描未产生折叠则阈值翻倍。
* **计量。** 总 token 数为智能体和运行时所有调用的未缓存输入、缓存读取、缓存写入和输出之和；成本按 Claude Opus 4.7 名义价格计算（每百万未缓存输入 5 美元，缓存读取 0.50 美元，输出 25 美元）。
* **比较与消融。** 在共享的 40 个 OSWorld 2.0 任务子集上比较：基线、滑动窗口、通用摘要（GS）、CarryOn 引导摘要（CGS，即把相同的组织原则写进每次折叠时重新生成的一份完整摘要）和 CarryOn，三者使用相同的宿主模型、触发条件和步数预算；另外分别对智能体隐藏载体或执行上下文。载体持久性在 494 次已提交的折叠上统计。

# Q7 数据集与代码

没有新数据集。论文列出了所用的 40 个 OSWorld 2.0 任务 ID 和 100 个 BrowseComp-Plus 题目 ID，并给出追踪器、编译器、GS 和 CGS 的提示词（GS 全文，其余为节选）。代码在 [Ethannju/carryon](https://github.com/Ethannju/carryon)（`hf papers info` 显示 4 星），另有项目主页；本笔记没有打开二者。

# Q8 证据质量

* **有支撑的结论。**
  * *在 OSWorld 2.0 上分数更高、成本更低。* 使用同一宿主模型，部分分从 43.9% 升到 49.7%，二值分从 15.7% 升到 19.4%。每个任务的总 token 从 40.10M 降到 19.30M（−51.9%），成本从 36.83 美元降到 23.62 美元（−35.9%），其中包括 3.11 美元的运行时调用。
  * *上下文不再增长。* 在长轨迹上，基线的输入上下文超过 200K token，而 CarryOn 稳定在约 65K。累计成本曲线在第 200 轮之前交叉，到第 500 轮时 CarryOn 便宜 34.1%（已计入开销）。
  * *结构比长度更重要。* 在 40 任务子集上，滑动窗口（保留 12.08K 字符）和通用摘要（17.60K）都低于基线（部分分 37.41% 和 44.94%，基线 50.32%）。CGS 回升到 50.93%，完整的 CarryOn 以 21.54K 字符达到 55.93%，文本比 CGS 少约 10%，二值分与基线持平（22.50%）。
  * *视图的两个部分承载不同信息。* 隐藏执行上下文后部分分降到 44.00%，智能体调用次数变化不大。隐藏载体后部分分降到 44.62%，智能体调用次数增加 23.8%，成本增加 22.3%；一条轨迹显示，被隐藏载体的智能体重新提取了一份它早已用过的 PDF 价目表。
  * *记录得以延续。* 494 次折叠中的 813 个载体观测里，278 个保持不变、372 个被更新（共 79.95%），163 个是新增的。
* **比标题结论更弱或更窄的地方。**
  * *单次运行、小子集。* 每种配置只运行一次，没有报告区间。40 任务子集上一个任务就是 2.5 个二值分百分点；BrowseComp-Plus 上 7 个百分点的提升就是 7 道题（笔记作者计算）。
  * *论文没有讨论的消融结果。* 在同一子集上，隐藏载体后的二值分（25.00%）反而高于完整 CarryOn（22.50%），所以载体的好处体现在部分分和成本上，而不在完全完成的任务数上（笔记作者从表 5 观察）。
  * *"超过其他前沿模型"的幅度很小且跨设置。* CarryOn 49.7% 的部分分只比已发表的 GPT-5.5（49.5%）和 Claude Opus 4.8（49.3%）高 0.2 到 0.4 个百分点，而这些结果来自基准作者自己的运行，GPT-5.5 还是批量执行动作。真正同条件的结论是相对复现的 Claude Opus 4.7 基线的提升。
  * *只有一个宿主模型。* 追踪器、编译器和智能体都是 Claude Opus 4.7，因此更小或不同的模型能否胜任追踪器和编译器、或者作为宿主是否同样受益，都没有检验。
  * *基线都是基于提示词的。* 压缩对比只有 ACON 风格的滑动窗口和通用摘要，没有 ACON 优化后的压缩器、AgentFold、LongHorizon-Harness 或其他状态外置方法，所以相对最强已有方法的提升没有测量。
  * *成本取决于缓存。* 成本按名义价格计算，缓存读取只有未缓存输入的十分之一，所以 35.9% 的成本节省小于 51.9% 的 token 节省，换一套价格就会变化；在 BrowseComp-Plus 上成本只节省 7.1%。

# Q9 贡献

* 一种面向对象的长程上下文框架：环境中已保存的进展以"引用 + 复用条件"的形式表示，而不是被摘要；文本只承载对象没有承载的内容。
* 一套折叠协议：候选追踪、证据绑定、只读环境检查、载体与执行上下文的联合编译，以及原子化、带版本的提交，未受影响的记录保持不动。
* 在 OSWorld 2.0 和 BrowseComp-Plus 上的证据，表明这种方法对一个前沿宿主模型既降低 token 和成本又提高得分，并与滑动窗口、通用摘要和同原则摘要基线做了受控比较。
* 消融表明载体和执行上下文承载不同的信息，持久性分析表明大多数载体记录在多次折叠中得到维护。

# Q10 后续方向

* **论文分析中提出的。** 作者认为，随对象演化而维护记录、而非重写摘要，可能是优于 CGS 的原因；直接检验这一点，可以把"持久性"的作用与"结构化格式"的作用分开。
* **加入方差和更多宿主模型（笔记作者建议）。** 把 40 任务的比较重复多次，并换用开源权重宿主和更小的追踪器/编译器，看相对 CGS 的 5 个百分点提升是否超过运行间噪声、在较弱的运行时模型下是否依然成立。
* **与状态外置类框架比较（笔记作者建议）。** [LongHorizon-Harness](../papers/2608.01964.md) 和 [PoS](../papers/2610.01415.md) 也用维护的状态取代历史，分别是经审计的任务状态和经验证的信念，而 PoS 已经在共享基准上比较过几种此类方法。把 CarryOn 加入这一比较，可以看出对象引用是否优于维护的记录。
* **更强的校验器检查（笔记作者建议）。** OSWorld 集成中的检查只看文件是否存在、哈希、容器和文本差异，不看内容是否正确。如果能把文档与它要满足的需求对照检查，载体承载的就是"已验证"而不只是"已存在"的进展，这也许能解释载体消融中二值分的反常。
