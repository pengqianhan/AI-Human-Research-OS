# Q1 问题定义

* **输入（X）：** 真实桌面（Linux、macOS 或 Windows）上的任务，带有自身代码、shell 和文件工具的通用智能体，以及当前状态的应用无障碍树和截图。
* **输出（Y）：** 通过模型自行选择的通道完成任务，每次动作后都返回证据。
* **约束：** 不训练模型，不加规划器或子智能体，同一接口要能接入不同的 harness。所有通道作用于同一桌面，所以一个通道的动作可能让另一个通道持有的证据失效。无障碍（AX）的覆盖范围取决于应用暴露了什么。

# Q2 问题新颖性

部分是新问题。结合 GUI 和代码的智能体已有先例（CoAct-1、StateAct、ALE 的 GUI-as-Tool、WeaveBench 插件），语义访问也出现在 UFO2、Tactile 和基线 [CUA Driver](../concepts/cua-driver.md) 中，后者同样具备三个通道，但优先采用尽力而为的后台输入。新的部分是：为长时间工作组织 AX 通道的方式（在绘制紧凑视图之前绑定引用、带等待步骤的批处理、随动作返回差异）、跨通道守卫，以及对模型自由选择时如何分配通道的工具调用分析。本文未引用的 [OpenGCUA](../papers/2610.22200.md) 也以模型自选接口为前提，但把每一步写成 Python 程序，因此两者的区别在于动作如何组合（读者比较）。

# Q3 科学假设

如果智能体可以在程序、语义和视觉通道之间选择，并且 AX 通道能让它紧凑读取、批量操作、无需新观察就看到效果，那么相比以截图为中心或组合性较弱的接口，任务成功率和效率都应提升，不同模型使用通道的方式也应不同。

# Q5 关键解决思路

**一个循环，三个通道。** 模型为每次观察或动作选择通道。程序工具留在 harness 中，HCU 增加 AX 和 GUI 两个 MCP 工具，截图可以为之后的 AX 动作提供信息。因为没有规划器，同一接口可以接入 Codex、Claude Code、Gemini CLI 和 Grok Build。

**紧凑视图与稳定引用。** HCU 保留采集到的 AX 记录，在投影出去掉包装层、汇总重复内容的短视图之前，就把引用（rN）绑定到元素。缩短视图不会改变引用的含义，被省略的元素仍可用 `find` 找到。

**内置验证的批处理。** 一次 `act` 调用在单个窗口内按序执行步骤（评估版最多 32 步，发布版最多 64 步），可以包含不发送输入、等待某状态出现的等待步骤（评估版中是后置条件和 `assert_ax`）。遇到第一个失败就停止并报告位置。

**随动作返回反馈。** 默认情况下，调用返回每个目标的效果和相对上次合格观察的 AX 差异。HCU 区分已知未送达和效果未知，因此不会把输入送达当作已确认的结果。

**输入前的守卫。** AX 目标守卫针对实时元素重新解析每个引用，拒绝缺失、歧义或被替换的目标，而不是重定向到名字相近的元素。GUI 布局守卫把桌面边界、可见窗口、堆叠顺序、活动窗口和目标点布局与上一张截图比较，不一致时阻止输入并返回新截图。

**一份使用技能。** 从开发轨迹中的错误提炼而来，内容包括每个通道能做什么、如何批处理并依据反馈继续、如何验证和恢复。其中不含针对具体任务的解法。

# Q6 实验设计

* **主实验。** OSWorld 2.0 全集（108 个任务，0808 版本），500 步上限：HCU 配 GPT-6 Astra（Codex，Code Mode）和 Claude Opus 5（Claude Code），均用最高强度；配对基线是 CUA Driver 配 GPT-6 Astra；另有榜单、StateAct 和厂商报告的结果。
* **消融。** OSWorld 1.0（361 个任务），GPT-5.4 xhigh，每组三次运行，100 步和 1800 秒上限：分别去掉 GUI、AX 或技能，以及 CUA Driver。
* **跨模型。** HCU 对 CUA Driver，模型为 GPT-5.4（xhigh）、Claude Opus 5.5（low）、Gemini 3.8 Flash（high）和 Grok 4.7（xhigh），各用自己的 harness，关闭网页搜索、记忆、子智能体和规划模式，开启前台输入。
* **发布版。** OSWorld 1.0、WeaveBench（114 个任务，medium 强度）、MacAgentBench 中 28 个依赖界面的任务子集，以及 111 个 Windows Agent Arena 任务，均用 GPT-5.4。

# Q8 证据质量

* **有证据支持。**
  * *在比较的全集结果中居首。* GPT-6 Astra 为 72.37 Partial、32.40 Binary，每任务 10.03 美元；Claude Opus 5 为 72.06 和 35.19，每任务 22.67 美元。官方 Opus 5 结果是 68.31 和 31.43，每任务 28.43 美元；CUA Driver 配 GPT-6 Astra 是 68.82 和 31.5，每任务 10.05 美元。
  * *比配对基线更高效。* 配 GPT-6 Astra 时工具调用减少 29.81%，平均时间减少 21.00%。在 OSWorld 1.0 上配 GPT-5.4，得分高 3.29 分，步数少 29.80%，输入 token 少 56.85%，成本低 55.36%。
  * *每个模型在 OSWorld 1.0 上都有提升。* 分数从 62.30 升到 65.59（GPT-5.4）、68.68 升到 71.62（Opus 5.5）、54.67 升到 67.57（Gemini 3.8 Flash）、67.90 升到 74.71（Grok 4.7），输入 token 少 18-57%，成本低 8-55%。几乎全部增益来自 HCU 用到桌面工具的任务。
  * *在 GPT-5.4 上 AX 比 GUI 更重要。* 去掉 AX 损失 2.79 分，且每次运行 HCU 都领先该组。去掉 GUI 的得分在运行间波动范围内（66.08 ± 1.66 对 65.59 ± 0.61），但步数多 12.45%。
  * *技能修复调用错误。* 在 2166 条轨迹中，参数格式错误被拒比例从 17.37% 降到 1.36%，出现重复拒绝的任务运行比例从 44.69% 降到 0.37%。分数效应较小，为 1.59 分。
  * *不同模型分配通道的方式不同。* AX 占桌面调用的比例：GPT-5.4 为 80%，Grok 为 68%，Gemini 为 51%，Claude 为 6%；Claude 也更常批处理（58% 的动作调用，其他模型为 11-21%）。出错后 Claude 很少切换通道（55 次中 1 次），其他模型切换比例为 25-37%。
  * *其他平台。* WeaveBench 为 53.25 对 46.37，MacAgentBench 为 25 对 24（共 28 个任务），Windows Agent Arena 为 80.86 对 71.89，成本低 46-51%。
* **比标题所说更弱或更窄。**
  * *配对的 Binary 增益看起来只是一个任务。* 32.40 和 31.5 符合 108 个任务中的 35 和 34 个，附录提到的多次运行只针对 OSWorld 1.0 消融和 Opus 5.5（读者推断）。MacAgentBench 同样只差一个任务。这里 Partial 和效率差异才是更强的证据。
  * *Claude 在 OSWorld 2.0 上的增益不是配对比较。* Opus 5 比较的是其官方循环结果，而不是相同 harness 设置下的 CUA Driver。OpenAI 的 GPT-6 Astra 结果（72.60，离线子集）高于 HCU，但被视为不计入排名；StateAct、Gemini 和 Kimi 的结果来自其他版本。
  * *70.13 是后来版本在相同任务上的结果。* 引言中的 GPT-5.4 分数来自发布版，它在主实验之后改进，再在 OSWorld 1.0 上重跑，而评估版为 65.59。+4.36 中可能有一部分是对该基准的调优，技能所依据的“开发轨迹”也未说明来源（读者推断）。
  * *Gemini 的增益主要来自步数上限。* CUA Driver 在 148 个任务上达到 100 步上限，HCU 为 93 个；Gemini 在长任务上增益 30.5 分，其他任务 7.7 分。最大的分数增益有一部分是效率透过上限转化而来，这一点作者自己也有展示。
  * *消融只用了一个模型。* “AX 贡献最大”依据的是 GPT-5.4，而 Claude Opus 5.5 几乎不用 AX。通道占比也无法解释分数排序：Grok 以 68% 的 AX 领先，Claude 以 6% 排第二；不过 Claude 用 low 强度，其他模型更高，分数不能直接比较（读者观察）。
  * *守卫没有做消融。* 没有实验组单独去掉守卫、批处理、等待步骤或差异反馈。它们的价值靠设计论证和记录下的示例说明，陈旧类错误只在有无技能之间比较（14160 次调用中 107 次，10783 次调用中 88 次）。因此 AX 设计内部的归因仍未解决（读者观察）。
  * *苦涩教训的解读超出了数据。* AX 本身是为使用辅助技术的人构建的，并没有摆脱人类先验；这里比较的是一个基准家族上的接口设计，而不是对一般性主张的检验（读者观察）。
  * *只用前台，harness 受限。* 所有调用用前台输入并关闭 harness 功能，让比较更干净，但 CUA Driver 的设计目标是后台使用，[OpenGCUA](../papers/2610.22200.md) 讨论的用户共享桌面也没有测试。

# Q9 贡献

* 一种由模型主导的接口，向通用智能体暴露程序、语义和视觉通道，不增加规划器。
* 一种 AX 设计：稳定引用、带等待步骤的批处理、随动作返回的差异，以及跨通道守卫。
* OSWorld 2.0、OSWorld 1.0 和另外三个基准（覆盖 Linux、macOS 和 Windows）上的证据，说明仅接口设计就能改变分数和成本。
* 对四个模型如何分配相同通道的工具调用分析，包括 GUI 词汇效应（Claude Opus 5.5 用 Claude 风格动作 +0.82，GPT-5.4 则为 −2.03）。

# Q10 下一步

* **把桌面当作可编程环境（论文提出）。** AX 状态可以进入代码执行和程序化工具调用，批处理和等待步骤可作为基础。
* **组件消融（读者建议）。** 在多个模型上逐一去掉守卫、等待步骤和差异反馈，可以看出 AX 设计中哪部分带来增益。
* **HCU 对代码即动作（读者建议）。** 在相同任务和模型上运行 HCU 和 OpenGCUA，可以比较结构化 AX 批处理与基于 GUI 和 shell 的程序。
* **无障碍支持差的应用（读者问题）。** 可以按每个应用的 AX 暴露程度拆分分数。净步数节省已经集中在 LibreOffice 和 Thunderbird 任务上，但论文没有测量各应用的 AX 覆盖度。
* **在该接口上训练（读者问题）。** 冻结模型只能从技能中学习通道。如果在这些通道上训练，会改变 Claude 式的 GUI 偏好或进一步减少调用错误吗？
