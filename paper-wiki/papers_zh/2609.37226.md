# Q1 问题定义

* **输入（X）：** 一个答案需要综合多份文档证据的问题，以及一个大型异构语料库（邮件、聊天、会议纪要、任务追踪、wiki、客服文章），由 LLM 智能体用 `find`、`grep`、`cat` 等 shell 命令探索。
* **输出（Y）：** 答案，以及智能体选出的支撑文档集合。
* **核心问题：** 全语料的智能体搜索（agentic search）让智能体能访问每个文件，却看不到文件之间的关系。一份相关文档不会告诉你哪些文档能与它互补（例如用项目代号记录发布决定的会议纪要），于是智能体会漏掉证据，并为每个问题重复花 token 去重新发现同样的跨文档关系，尽管这些关系与具体问题无关。
* **约束：** 导航层必须只依据语料本身离线构建，并且是在原始文档之上增加一层，而不是替换它们。

# Q2 问题新颖性

部分新颖。基于图的检索增强生成（[GraphRAG](../concepts/graphrag.md)、HippoRAG）早已从语料构建实体图，但只在检索器内部使用，生成器仍只能依据一次检索返回的固定上下文作答。智能体搜索允许模型持续搜索，却把语料当作相互独立的文件。近期面向智能体的语料结构有不同的组织方式：由 LLM 维护的 wiki（Karpathy 的“LLM Wiki”）让模型决定哪些内容成为页面；Corpus2Skill 构建主题树，每份文档只落在一个或少数几个分支。本文把问题定义为*语料导航*，并主张反复出现的实体（人、项目、事件、配置开关）是合适的锚点：一份文档可以通过它提到的实体链接到许多其他文档，而且这些链接可以一次算好、反复使用。

# Q3 科学假设

如果围绕跨文档解析后的实体来组织语料，每个实体页面链接所有提到它的文档、且每条事实标注来源，那么能沿这些链接遍历的智能体应能找到问题所需的更多证据、答得更好，同时比在扁平语料上搜索读取更少的 token。这一层还应优于以文档、文件夹、LLM 自由撰写的页面或主题树为锚点的导航层。

# Q4 相关工作与关键人物

* **检索增强生成：** BM25、稠密检索、RAG、GraphRAG、HippoRAG。
* **智能体搜索与面向智能体的语料结构：** ReAct，迭代与自适应检索（IRCoT、FLARE、Self-RAG、Adaptive-RAG），近期的智能体搜索系统，LLM Wiki（Karpathy，2026）及相关的 LLM 维护 wiki，以及 Corpus2Skill 的层级技能树。
* **实体抽取与消解：** 命名实体识别和 GLiNER 等开放类型抽取器、以 Wikipedia 为知识库的实体链接、跨文档共指与实体消解、基于 LLM 的匹配，以及轻量零样本链接器 GLinker。
* **关键人物：** Soyeong Jeong（KAIST；工作完成于微软实习期间）、Sujay Kumar Jauhar 和 Andrew Joohun Nam（微软）、Sung Ju Hwang（KAIST）。Jeong 与 Hwang 也是 Adaptive-RAG 的作者。可能的批评者：GraphRAG 和 HippoRAG 的作者，他们会指出自己的方法在这里是以“先检索后生成”方式运行、而非作为智能体工具；以及 Corpus2Skill 和 LLM Wiki 的支持者，因为这些基线是重新实现的。

# Q5 关键解法思路

* **实体-文档二部图。** 与多于一份文档相连的实体成为实体节点，文档成为文档节点；某文档中的提及被消解到某实体时，二者之间连一条边。共享同一实体的两份文档经由它相连；没有任何保留实体的文档仍可通过普通搜索访问。
* **有来源依据的实体页面（Entity Page）。** 每个实体渲染为一个文件，包含简短概述、逐条标注来源文档的关键事实、它出现时使用过的别名，以及所有相连文档的文件路径。
* **离线构建四阶段。** (1) *编目*：LLM 从若干文档样本中提出实体类型，合并并核验，得到固定的类型目录（名称、定义、同一性判据、示例）。(2) *抽取*：逐文档识别并标注提及，把同一文档内指向同一对象的提及合为一个文档局部实体。(3) *消解*：把每个局部实体与不断增长的注册表比较，结果为 LINK（链接到已有实体）、ADD（新增实体）或 UNRESOLVED（不处理）。(4) *渲染*：与至少两份文档相连的实体生成页面。第 2-4 阶段可以用现成工具代替 LLM。
* **用普通工具导航。** 页面放在原始文件旁边，智能体用同样的方式读取和 grep。每个问题还会附上一份候选文件路径：先用 BM25 给实体页面排序，汇集其相连文档，再用 BM25 对这些文档重排；候选只列标题、路径和 ID，不含内容。

# Q6 实验设计

* **基准：** 只用需要多份文档的问题。EnterpriseRAG-Bench 贡献 80 个问题（Project Related、Conflicting Info、Completeness 三类），语料固定为 2,819 份（金标文档及其一跳干扰文档）。WixQA 贡献 79 个多文章问题，语料为完整的 6,221 篇知识库文章。HERB 贡献 238 个内容型问题，语料为 6,365 份模拟软件公司的工作产物。
* **方法：** Raw Corpus；Document Page（每份文档一个 LLM 写的页面）；Group Page（按已有文件夹或分组各一页）；LLM Wiki（自由撰写、相互链接的页面）；Corpus2Skill（由摘要聚类构成的主题层级）；CorpusMap；以及金标文档 Oracle。所有方法中原始文档都可访问，且由同一个 LLM 构建各方法的产物并作答。
* **模型与智能体：** 主表用 GPT-5.5 和 GPT-5.6 Luna、Terra、Sol；分析中还用了 DeepSeek-V4-Pro、MAI-Thinking-1 和开放权重的 Qwen3.8-27B。智能体沿用 EnterpriseRAG-Bench 的终端智能体及其单题预算。
* **指标：** 由 GPT-5.6 Sol 评审的答案质量（正确性与完整性、WixQA 事实性、HERB 内容分）、检索质量（文档召回与上下文召回），以及整条轨迹累计的输入 token。结果为三次运行的均值。
* **分析：** 带 Holm 校正的配对自助法检验；用 DeepSeek-V4-Pro 重新评审；先检索后生成的基线（BM25、稠密检索、HippoRAG、GraphRAG）；摊销的构建成本；由一个模型构建、另一个模型使用的地图复用；按时间戳顺序的增量更新；用 GLinker 构建、不调用 LLM 的地图；加入干扰文档扩大语料；对候选列表和实体-实体边的消融。

# Q8 证据质量

* **有支撑的：**
  * *相对原始搜索稳定提升，平均 token 更少。* 总体质量相对 Raw Corpus 提升 +6.45（GPT-5.5）、+11.74（Luna）、+6.76（Terra）、+7.00（Sol），自助法 95% 区间远高于零，Holm 校正后 p < 10⁻⁴。相对 Raw Corpus 的输入 token 为 0.43×、0.65×、0.66×、0.43×（基准间几何平均）。EnterpriseRAG-Bench 的文档召回从 61.62 升到 76.17（GPT-5.5），从 56.40 升到 75.11（Luna）。
  * *其他导航层并不稳定有效。* Document Page、Group Page、LLM Wiki 和 Corpus2Skill 在至少一个模型上不如 Raw Corpus。GPT-5.5 下 LLM Wiki 为 64.49、Corpus2Skill 为 45.49，Raw Corpus 为 66.11；CorpusMap 在四个模型上都显著优于它们每一个。
  * *不限于 GPT，也不限于先检索后生成。* 在 EnterpriseRAG-Bench 上，CorpusMap 用 DeepSeek-V4-Pro（71.11 对原始 68.02）和 MAI-Thinking-1（45.07 对 34.06）时仍领先。与先检索后生成的基线相比，它得 76.60 和 73.20（GPT-5.5 和 Luna），HippoRAG 为 64.66 和 61.74，GraphRAG 为 47.95 和 43.46。
  * *地图复用成本低。* 由 GPT-5.6 Luna 构建的地图（构建成本至多 74.65 美元，GPT-5.5 构建至多 4,732.14 美元）对每个作答模型都优于 Raw Corpus；例如 GPT-5.5 在其上作答得 73.59，原始为 65.60。
  * *评审稳健性。* 换 DeepSeek-V4-Pro 重新评审，CorpusMap 在全部五个 LLM 评审指标上仍居首，两位评审在正确性、完整性和内容分上的方法排序完全一致（Kendall τ = 1.00），在 WixQA 上下文召回（0.47）和事实性（0.83）上一致性较低。
  * *实体-实体边没有帮助。* 加入关系边或共现边后，文档召回变化为 −2.6 至 +0.2 个百分点，而页面变大 27-52%，输入 token 最多增加 28%。没有这些边时，86-90% 新打开的实体页面是通过搜索找到的。
* **较弱或有边界的：**
  * *大部分收益依赖候选列表。* 在 EnterpriseRAG-Bench、GPT-5.5 上（表 8），不带候选的 CorpusMap 得 69.04，只比 Raw Corpus 的 65.60 高 3.4 分，输入 token 为 496.4k，是 Raw Corpus（206.5k）的 2.4 倍。带上 BM25 选出的相连文档（默认设置）则达到 76.60、88.1k token。随机候选使质量降到 60.76，低于 Raw Corpus。因此宣称的效率来自地图*加上*原始搜索所没有的 BM25 预选步骤。作者确实控制了其中一种情况：给 Raw Corpus 提供 BM25 选出的文档候选（66.19、107.4k token），但那是直接给文档排序，而不是经由实体页面。
  * *token 节省是平均意义上的，并非处处成立。* Luna 在 HERB 上，CorpusMap 用的 token 比 Raw Corpus 多（254.2k 对 219.4k）；Terra 在 EnterpriseRAG-Bench 上为 76.2k 对 70.9k；MAI-Thinking-1 在 EnterpriseRAG-Bench 上为 158.8k 对 129.6k。
  * *问题筛选对方法有利。* 主结果只用多文档问题，正是地图所针对的情形。作者也报告了 EnterpriseRAG-Bench 其余以单文档为主的问题上 CorpusMap 同样有帮助（GPT-5.5 下正确性 94.76 对 89.05，且 token 更少），部分回应了这一点。
  * *规模有限。* 主语料只有 2,819-6,365 份文档，EnterpriseRAG-Bench 的语料围绕金标文档及其一跳干扰文档构建。干扰扩展、增量更新、摊销成本和 GLinker 结果只在图中给出，因此确切数值（包括构建成本在多少次查询后回本）不在正文里。
  * *全程依赖 LLM 评审。* 所有答案质量指标都由 LLM 评审；DeepSeek 重评降低但没有消除这种依赖。
  * *基线是重新实现的。* LLM Wiki、Document Page 和 Group Page 都是作者在统一协议下的实现，获取到的正文没有描述它们的调参。

# Q9 贡献

* 把大规模文档集合上的智能体搜索定义为语料导航问题：可复用的跨文档结构应一次构建并暴露给智能体，而不是每个问题重新发现。
* CorpusMap：带来源标注实体页面的实体-文档二部图，经类型编目、抽取、基于注册表的增量消解和渲染离线构建，并以文件形式存放，智能体用现有工具即可读取。
* 受控比较表明，以实体为锚点胜过另外四种导航单位（文档、文件夹、LLM 自由撰写的 wiki 页面、主题树）和四个先检索后生成基线，覆盖七个模型、三个基准。
* 实用证据：地图可以用便宜模型甚至不用 LLM 构建，可跨作答模型复用，可增量更新；消融还表明实体-实体边并不必要。

# Q10 下一步

* **把地图与候选步骤分开（读者注）：** 在适用处给 Raw Corpus 及其他每个导航层提供同样的“对页面做 BM25”候选机制，并在全部三个基准上报告不带候选的 CorpusMap，以衡量收益中有多少来自实体结构本身。
* **更大、更杂的语料：** 在企业规模（数百万文档）上测试，并按用户实施访问权限。作者的伦理声明指出这一点是必要的，因为实体页面会把散落在语料各处的敏感事实聚到一起。
* **时效与冲突事实：** EnterpriseRAG-Bench 有 Conflicting Info 类别，但页面只给事实标注来源，没有按时间或权威排序。实体页面应如何表示已被取代的事实（如案例中的草案和 v1 manifest），仍是开放问题。
* **与本仓库论文 wiki 的关联（读者注）：** 本 wiki 的概念页就是实体页。当两篇或以上论文引用某个概念时才建页，页面与这些论文双向链接，其论断都挂靠在 `# Papers` 列表中的论文上，这与 CorpusMap“只保留至少连到两份文档的实体、并为每条事实标注来源”的规则高度一致。论文发现自由撰写的“LLM Wiki”并不稳定优于原始搜索，而实体页面稳定有效，这支持本 wiki 保持以实体为锚点的结构，而不是让智能体自由撰写综述页面。它对实体-实体边的消融也提示，在可以搜索的前提下，概念之间的互链作用有限。
* **把智能体记忆当作语料地图（读者注）：** [Zep](../papers/2501.13956.md) 和 [Jev-Mem](../papers/2609.23986.md) 都在对话历史上构建实体图用于检索。CorpusMap 提示，可以把这类图以智能体可浏览的可读文件形式暴露出来，而不是只作为检索器的内部索引。
