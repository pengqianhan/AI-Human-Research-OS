> 论文:**Multi-module GRPO: Composing Policy Gradients and Prompt Optimization for Language Model Programs**
> 论文链接:<https://arxiv.org/abs/2508.04660>
> 机构:圣母大学 / 斯坦福大学 / 加州大学伯克利分校 / 麻省理工学院 / Databricks / Contextual AI / Normal Computing / Zoom, Inc.

# Q1 问题定义

* **输入 `X`**:一个由模块集合 `M = {M_1, ..., M_{|M|}}` 组成的语言模型程序 `Φ`,每个模块都有自己的 prompt 模板 `π_M` 与 LM 权重 `θ_M`,由控制流负责在模块间路由结构化的输入与输出(例如:一个查询生成模块把结果送给检索器,检索器再把结果送给一个响应生成模块);一个由程序输入及可选元数据组成的数据集 `D = {(x, m)}`;以及一个对最终输出 `y` 与模块调用轨迹 `ρ` 打分的程序级奖励函数 `μ(y, ρ, m)`。
* **输出 `Y`**:MMGRPO,一种对分组相对策略优化(GRPO)的多模块推广,它从按模块分组的、模块级别的 rollout 比较中更新每个模块自己的 LM 权重,而不是把整个程序当作一次不加区分的策略调用来处理;该方法已作为 `dspy.GRPO` 优化器开源发布在 DSPy 库中。
* **核心问题**:GRPO 最初是为单阶段场景设计的——一个 prompt、一组共享该 prompt 的完成结果、一个被更新的策略——但现代基于 LM 的系统正越来越多地被实现为混合多个不同 LM 调用的模块化程序,每个调用都有自己的 prompt 模板与角色,此外还可能混入非 LM 工具。目前尚不清楚如何把 GRPO 的分组优势机制扩展到这种多模块场景:同一个程序级输入产生的不同 rollout,可能因控制流分支或早期终止(例如某个模块级解析失败)而在步数、涉及模块及其顺序上互不相同。
* **范围**:本文提出的是一个刻意保持简单的首个基线设计(模块级分组),而非对多模块 RL 各种可能形式的穷举搜索;在三个语言模型程序上(一个单模块分类器、一个两模块隐私委托流水线、一个两模块四跳检索增强型断言核验器)用两个 80 亿参数的开源模型(llama3.1-8b-instruct、qwen3-8b)做了验证,明确未在更大模型规模上测试,也未与全参数(非 LoRA)微调对比。

# Q2 问题的新颖性

论文并不声称首创 GRPO(Shao et al. 2024,DeepSeekMath)、面向语言模型程序的 prompt 优化(MIPROv2,Opsahl-Ong et al. 2024;DSPy 自身基于拒绝采样的优化器,Khattab et al. 2024),或权重优化与 prompt 优化的一般性组合——BetterTogether(Soylu et al. 2024)已表明这种组合有帮助,但仅限于通过对结果过滤后的轨迹做拒绝式微调的离线 RL 设置。其具体新颖之处,论文在引言中直接声明:这是"第一个能应用于复杂 LM 流水线的 GRPO 实现"——先前的多轮 RL 方法(Search-R1、ReTool,以及本知识库其他地方所收录的 RAGEN 一类方法)是在多轮中把单个 LM 的 prompt 逐轮串行扩展,而任意 LM 程序的控制流是通过为每个模块选择其输入来决定该模块能看到什么上下文——这在结构上是一个不同的问题,因为像 PAPILLON 隐私保护委托调用这样的模块,是被刻意设计为看不到完整交互历史的。这促使论文提出一种真正新的多模块形式化,而非直接复用现有的多轮 RL 机制,并借此在同一批 LM 程序上首次做出 prompt 优化单独使用、在线多模块 RL 单独使用、以及二者分阶段组合(把 BetterTogether 延伸到在线 RL 场景)的受控三方对比。

# Q3 科学假设

如果放松 GRPO 要求组内共享同一个 prompt 的限制,改为在*模块层面*对 rollout 分组——按模块身份以及该模块在轨迹内出现的相对顺序,把不同程序轨迹 rollout 中结构上可比的模块调用对齐起来,而不要求相同的输入或固定的轨迹结构——那么 GRPO 式的策略梯度更新就可以独立应用到每个模块自己的权重上,用程序级的结果奖励作为统一的信用信号,而无需共享历史、中间监督,或为单一策略重新设计训练信号。论文进一步假设这种在线 RL 方法与自动 prompt 优化是互补而非替代关系,因此先做 prompt 优化、再把 mmGRPO 应用到得到的 prompt 优化后程序上(沿用离线的 BetterTogether 配方、现在把它用在在线场景),应当优于单独使用任一方法,因为 prompt 优化会产生质量更高的初始 rollout,为 mmGRPO 训练早期提供更强的训练信号。

# Q4 相关工作与关键人物

* **语言模型的权重优化。** PPO(Schulman et al. 2017)作为 RLHF 时代的标准方法;DPO(Rafailov et al. 2023)作为避免显式奖励建模的对比式偏好替代方案;GRPO(Shao et al. 2024)作为本文直接扩展的、免价值函数、组内归一化优势的方法。本知识库另有 [GRPO](../concepts/grpo.md) 概念页面收录了其他把 GRPO 用于单策略 agent 场景的论文。
* **Prompt 优化。** 提示 LM 生成指令的方法(Yang et al. 2024;Zhou et al. 2023;Fernando et al. 2024 的 Promptbreeder);基于梯度的离散 prompt 优化(Shin et al. 2020;Wen et al. 2023);基于 RL 的 prompt 优化器(RLPrompt,Deng et al. 2022);MIPROv2(Opsahl-Ong et al. 2024)作为本文用作 PO 基线、也是 BetterTogether 第一阶段所用的具体最先进的贝叶斯优化式 prompt 优化器。
* **联合优化 LM 程序的 prompt 与权重。** DSPy(Khattab et al. 2024)作为本文优化器发布所在的框架,最初围绕基于拒绝采样的 prompt 优化构建;BetterTogether(Soylu et al. 2024)作为本文直接延伸的方法学前作,把它从离线拒绝式微调 RL 推广到在线策略梯度 RL。
* **用作 LM 程序测试床的基准。** Banking77(Casanueva et al. 2020,单模块意图分类);PUPA/PAPILLON(Siyan et al. 2024,隐私保护式委托,两个模块);建立在 HotPotQA(Yang et al. 2018)之上的 HoVer(Jiang et al. 2020,多跳断言核验,两个模块在配备 ColBERTv2 检索器(Santhanam et al. 2021)的情况下迭代四跳)。
* **关键人物与机构。** 作者来自多个机构,包括圣母大学、斯坦福大学、加州大学伯克利分校、麻省理工学院、Databricks、Contextual AI、Normal Computing 与 Zoom, Inc.;三位作者(Ziems、Soylu、Agrawal)标注为并列第一作者贡献。Omar Khattab(麻省理工学院)与 Christopher Potts(斯坦福大学)是 DSPy 的原始创建者,本文实质上是 DSPy 团队为自家框架的优化器套件所做的延伸工作。提交于 2025 年 8 月 6 日(arXiv v1);代码作为持续维护的 `stanfordnlp/dspy` 仓库的一部分发布。

# Q5 核心解法

1. **LM 程序的形式化。** 一个程序 `Φ(x)` 采样 `(y, ρ) ~ Φ(x)`,其中 `ρ = [ζ_1, ..., ζ_{|ρ|}]` 是模块调用的有序轨迹,每条记录 `ζ_t = ⟨M_t, q_t, o_t⟩` 保存被调用的模块、其实际生成的 prompt 与输出(式 3)——轨迹只记录 LM 层面的调用,不记录其他控制逻辑。
2. **模块级分组,而非 prompt 级分组。** 标准 GRPO 对共享同一个输入 prompt 的完成结果分组(式 1-2);mmGRPO 改为从一个共享的程序级输入 `x` 采样一个由多条完整程序轨迹组成的元组(meta-group),再按模块身份与该模块在轨迹中出现的相对顺序,把不同轨迹间的模块调用对齐,形成模块级的 GRPO 组 `{(q_i, o_i, r_i)}_{i=1}^G`——组内成员可以有不同的 prompt `q_i`(反映不同的上游上下文),但都被归属到同一个模块。
3. **统一的程序级信用分配。** 每个模块级分组的奖励 `r_i` 都被设为产生该组数据的整条轨迹所对应的同一个程序级结果奖励 `r = μ(y, ρ, m)`——这是论文刻意选择的、最简单的设计,明确的动机是希望这个基线相对既有 GRPO 实现尽可能保持模块化,而不是设计一套更精细的分模块信用分配方案。
4. **按模块更新策略。** 修改后的 GRPO 损失(式 4)被独立应用到每个模块级分组上,只更新该分组所对应模块自己的 LM 权重 `θ_M`(实践中多个模块往往共享同一套底层 LM,即便参数绑定在一起,更新仍是按分组分别施加的)——这与标准 GRPO 的不同之处在于:更新的是按模块划分的策略而非单一共享策略,并且允许组内 prompt 有所不同,而不要求完全共享同一个 prompt。
5. **对轨迹结构分歧的鲁棒性。** 由于控制流可能分支或提前终止(例如某个模块级的解析失败),同一输入 `x` 产生的不同轨迹未必具有相同的长度或模块序列;mmGRPO 在应用损失之前可选择把较小的分组填充(pad)到固定大小(细节见附录 A),而不要求 rollout 之间结构完全一致。
6. **教师增强式采样。** mmGRPO 不仅可以从正在训练的学生程序采样轨迹,也可以从一组固定的教师程序中采样,从而支持从一个已做过 prompt 优化的程序热启动、或从更强大 LM 的 rollout 中学习等灵活训练设置;在没有教师、只有单模块程序的情况下,mmGRPO 精确退化为标准 GRPO。
7. **BetterTogether(PO, mmGRPO) 分阶段组合。** 论文没有另行设计一个联合目标,而是把 BetterTogether 的离线 RL 配方(先用 MIPROv2 优化 prompt,再对得到的程序做权重调优)直接延伸到在线场景:先由 MIPROv2 产出一个 prompt 优化后的程序,再由 mmGRPO 在保持优化后 prompt 固定不变的情况下对其做权重微调。

# Q6 实验设计

**LM 程序与任务。** Banking77(单个思维链模块,77 类意图分类,250 条训练/500 条开发样本,精确匹配评测)。基于 PUPA 基准的 PAPILLON(两模块流水线:脱敏一条私密查询,把脱敏后的版本发送给一个不受信任但能力更强的外部 LM `gpt-4.1-mini`,再据其回答生成最终响应;由一个大 LM 判定隐私泄露与回答质量的复合指标;111 条训练/221 条开发样本)。HoVer<sub>4-HOP</sub>(查询生成与事实摘要两个模块,在配备基于 HotPotQA 维基百科片段索引的 ColBERTv2 检索器的情况下迭代四跳;以最多返回 100 篇文档中的 Recall@100 评测;从原始 HoVer 训练集中按来源 HotPotQA 问题去重后构建 500/500 条训练/开发样本)。两个开源 LM:llama3.1-8b-instruct 与 qwen3-8b,通过 vLLM 运行(最大上下文 32,768 token,最大输出 1,032 token,每个模块解析失败最多重试 3 次)。

**对比方法。** 未调优的原始思维链(Vanilla CoT)基线;单独使用 MIPROv2 做 prompt 优化(`auto=medium`,12 次试验,12 个少样本候选与 6 个指令候选,80% 训练集划为验证集);单独使用 mmGRPO(HuggingFace GRPOTrainer,750 步,每步 4 个样本,每个样本 12 次 rollout,LoRA 秩 16、alpha 64、dropout 0.05,作用于投影模块 [q,k,v,o,up,down,gate],学习率 `1×10^-5`,训练上下文 8,192 token,qwen3-8b 用 `β=0.01`/梯度裁剪 0.1,llama3.1 用 `β=0.04`/梯度裁剪 0.5);BetterTogether(PO, mmGRPO)(先 MIPROv2、再在得到的固定 prompt 程序上跑 mmGRPO)。全部结果均为在 3 个随机种子上平均后的开发集准确率;开发集在优化过程中完全不参与。

**主要结果(六个 LM-任务组合的平均值)。** Vanilla CoT:66.3。单独 MIPROv2(PO):70.0(相对 CoT +5%)。单独 mmGRPO:71.2(相对 CoT +7%)。BetterTogether(PO, mmGRPO):73.4——在大多数任务-模型组合中都是最佳结果,相对 Vanilla CoT 提升 11%,相对单独 MIPROv2 提升 5%,相对单独 mmGRPO 提升 3%。分任务-模型细节:单独 mmGRPO 在 Banking77-llama3.1 上优于 MIPROv2(63.7 对 59.4),在 qwen3.1 上大致持平或略逊(64.9 对 65.9),在 HoVer-qwen3 上优于 MIPROv2(71.0 对 69.3)但在 HoVer-llama3.1 上落后(60.2 对 63.4),在 PAPILLON-qwen3 上则实际领先(83.3 对 78.1)——即便平均而言 mmGRPO 胜出,但逐个任务看它并不总是稳定压制 MIPROv2。

**算力代价权衡(论文明确将其作为一项发现,而非附带的局限说明)。** 单独 mmGRPO 训练平均每次运行耗费 2 块 H100 上的 18.7 GPU 小时;MIPROv2 平均仅需 1 块 H100 上的 1.4 GPU 小时——为换取较小的平均准确率增益(5% 对 7%),算力成本相差约 13 倍,论文据此指出在计算预算有限的场景下,PO 类方法"可能可行性要高得多"。

本文的三个评测数据集均为已有公开基准,并非本文新发布:Banking77(Casanueva et al. 2020)、PUPA/PAPILLON(Siyan et al. 2024)、建立在 HotPotQA(Jiang et al. 2020;Yang et al. 2018)之上的 HoVer。本文自身的贡献是 mmGRPO 优化器的实现,已作为 `dspy.GRPO` 开源发布在持续维护的 DSPy 库中([github.com/stanfordnlp/dspy](https://github.com/stanfordnlp/dspy),撰写本笔记时据 HF 元数据有 37,989 个 star——这反映的是 DSPy 整体框架的受欢迎程度,而非该优化器本身的使用量),文档见 [dspy.ai](https://dspy.ai)。训练使用 DSPy 的 RL 库 Arbor(Ziems et al. 2025,与本知识库另一篇同名 [Arbor](../papers/2606.11926.md) 假设树论文是完全不同的系统,只是碰巧同名),该库本身受 Verifiers 库启发。所用 LM 均为已有的开源权重模型(llama3.1-8b-instruct、qwen3-8b)加上 PAPILLON 中使用的一个专有外部模型(`gpt-4.1-mini`);未发布新的模型权重。

# Q9 主要贡献

1. MMGRPO:第一个可应用于模块化、多模块语言模型程序(而不仅是单阶段/单轮 LM 调用)的 GRPO 实现,通过按模块身份与相对顺序对齐不同轨迹间的模块调用来做模块级 rollout 分组,而不要求共享 prompt 或结构完全相同的轨迹。
2. 一种处理变长且结构上可能分歧的轨迹(控制流分支、解析失败导致的提前终止)的机制——通过分组填充实现——以及支持从固定教师程序采样以配合学生程序训练,使 mmGRPO 能够从已做过 prompt 优化的程序或更强的 LM 中热启动。
3. 首次在同一批 LM 程序与 LM 上,对 prompt 优化(MIPROv2)、在线多模块 RL(mmGRPO)及二者分阶段组合(BetterTogether(PO, mmGRPO))做出受控的实证对比,显示三者相对未调优思维链均能带来一致的提升(平均相对增益分别为 5%、7%、11%),且在多数任务-模型组合中,分阶段组合优于单独使用任一组件。
4. 一项明确的算力成本核算,表明 mmGRPO 相对 MIPROv2 更大的平均增益(7% 对 5%)是以约 13 倍的 GPU 小时数为代价换来的(18.7 对 1.4 小时),为从业者在这两种优化策略之间做资源预算权衡提供了具体依据。
5. 将 mmGRPO 作为 `dspy.GRPO` 优化器开源发布在 DSPy 中,使其可以作为一个开箱即用的优化器,用于已经用 DSPy 表达的任意复合 AI 系统,而无需为每个程序单独实现一套定制的 RL 方案。

# Q10 下一步

论文直接陈述而非隐含的局限:结果未必能推广到比测试所用 80 亿参数更大的模型;LoRA 微调可能不如未曾评测过的全参数更新;只测试了"许多可能的替代形式"中的一种多模块 GRPO 设计,替代的模块分组或信用分配方案的设计空间尚未被探索;以及 Banking77 在仅靠奖励信号训练的设置下,尚未达到对该具体任务做监督微调所能取得的效果,论文并未声称已解决这一开放的负面结果。论文的结论部分明确呼吁未来工作在"离线与在线设置下"都进一步探索策略梯度 RL 与 prompt 优化的融合,把 BetterTogether(PO, mmGRPO) 当作二者组合方式的一个初步答案,而非最终定论。

除论文自身框架之外,有两点值得向评估本笔记证据基础的读者指出。第一,mmGRPO 统一的程序级信用分配(轨迹中每个模块,无论其行为是否真正导致成功或失败,都获得相同的标量奖励)与本知识库[Agent fine-tuning](../topics/agent-fine-tuning.md)主题中已经追踪的 Agent Lightning 逐 transition 奖励、VibeWorlding 逐轨迹奖励属于同一种粗粒度信用分配设计——mmGRPO 并未尝试在一条轨迹内部对不同模块做区分,因此一个在整体失败的轨迹中表现良好的模块,会与真正导致失败的模块受到完全相同的惩罚;论文没有报告这种粗粒度是否会在两模块程序(PAPILLON、HoVer)上比单模块的 Banking77(该区分在单模块下没有意义)更明显地限制收益。第二,由于本文实际实验中各模块共享同一套底层 LM 权重("我们对每个模块使用相同的底层 LM 权重,以实现轻量级的训练与部署"),报告的结果并未直接检验 mmGRPO 自身形式化所针对的更困难情形——真正独立更新的分模块权重集——因此模块级分组的收益(相对于把整条轨迹当作一个共享策略的单一 GRPO 分组)在模块参数真正出现分化之后会保持、缩小还是扩大,仍是一个未解问题。

# Related

* [Agent fine-tuning](../topics/agent-fine-tuning.md) - 为该主题持续追踪的 GRPO 扩展比较增加了一种不同的信用分配答案:不同于 Agent Lightning 的逐 transition 分解或 ContextPilot 的逐快照分支平均估计器,mmGRPO 在*模块*层面分组——对齐不同轨迹间对同一具名模块的调用,而非把一条轨迹拆解成若干顺序片段——是该主题第一篇针对真正异质、(原则上)可分别参数化的 LM 组件(而非一个策略在多轮中反复行动)的论文。
* [GRPO](../concepts/grpo.md) - 本知识库该概念页面第四个把 GRPO 从单策略、单 prompt 的原始形式向外扩展的实例(继 Agent Lightning 的逐 transition 分组、ContextPilot 的逐快照分组、WideSeek-R1 的多 agent token/agent 双层重加权之后),也是第一个放松"组内共享同一个 prompt"这一假设本身、改为按模块身份分组的实例,证明即便组内成员不再共享同一个输入,GRPO 核心的分组优势机制依然成立。
* [DSPy](../concepts/dspy.md) - mmGRPO 作为该框架的 `dspy.GRPO` 优化器发布,与 DSPy 既有的 prompt 优化器(包括本文既用作基线、又用作 BetterTogether 第一阶段的 MIPROv2)并列,成为在不需要手写 prompt 或针对特定奖励模型编写训练代码的情况下,编译一个 LM 程序的第二种、基于 RL 的手段。
