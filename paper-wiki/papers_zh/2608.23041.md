> 论文：**AutoSaddler: Automatic Harness Optimization with Durable Updates from Agent Execution Traces**
> 论文链接：<https://arxiv.org/abs/2608.23041>
> 项目主页：<https://autosaddler-projectpage.github.io/>
> 代码：<https://github.com/microsoft/AutoSaddler>

# Q1 问题定义

* **输入 `X`**：一个包裹着冻结基础模型（默认 Claude Opus 4.6）的基础 harness（系统提示词、工具定义、中间件/控制逻辑），一个基准任务族的训练集，以及从该 harness 在训练集上运行所得的小批量执行轨迹（既包含成功也包含失败）。
* **输出 `Y`**：一个更新后的 harness（同一冻结模型，修订过的提示词/工具/中间件），在留出测试集上取得更高的 Pass@1；同时产出一份 EvoDAG，记录整个优化谱系（每个节点的补丁、经验教训与性能信号）。
* **核心问题**：长程 LLM-agent 的可靠性会因局部小失败不断累积而下降，外部 harness 可以显著提升鲁棒性，但手工设计 harness 代价高昂,需要在提示词变体、工具配置和控制逻辑的巨大空间中人工搜索。能否把这种搜索本身自动化为一个离线学习问题——把 harness 当作可训练对象、把小批量失败信号当作训练信号,就像权重空间的训练由梯度驱动一样?
* **范围**：面向冻结模型的 harness 中的提示词、工具、中间件三层；论文明确排除了针对无状态单回合任务的记忆或技能整理。

# Q2 问题的新颖性

自动 harness/提示词优化并非全新方向——论文直接将自己定位在两个同期的自动化基线之上：GEPA（由浅层反思驱动的、以提示词为中心的进化式优化）和 Meta-Harness（基于 Claude Agent SDK 构建的端到端 harness 优化系统）。AutoSaddler 声称的新颖性不在于优化目标本身,而在于论文认为此前自动化方法未充分具备的三项要素的特定组合：(1) 证据驱动的诊断——主动探索执行轨迹与 harness 自身源代码,而非单次浅层反思调用;(2) 补丁被约束在一个带类型的分类体系内（按 harness 层级、按能力型/引导型），并配有明确的两阶段调度，而非不受约束的自由文本编辑;(3) 接受与否取决于经过验证、具备泛化证据的评估（小批量加可选的留出开发集检查），而非仅根据单条失败轨迹就直接修复。论文自己的表述是,此前的自动方法各自探索了这一空间的"互补方面",而非把三者结合在一起。

# Q3 科学假设

如果 harness 优化执行了：(a) 证据驱动、代码级别的诊断,而非浅层反思;(b) 受约束的、代码结构化、分阶段调度的补丁,而非不受约束的自由文本编辑;(c) 小批量加开发集的验证式筛选,而非针对单条轨迹的修复,那么由此产生的自动化循环将在留出测试准确率上超越现有的自动 harness 优化基线,并且达到给定准确率所需的执行轨迹数量会显著少于那些基线。论文的三项消融实验（RQ1-RQ3，每项对应一个要素）分别用于分离验证：是这个具体要素、而不只是整个系统,支撑着这两项主张。

# Q4 相关工作与关键人物

* **GEPA**——以提示词为中心、由浅层反思驱动的进化式优化；在 GAIA2 与 SWE-Bench Pro 上作为基线对比。
* **Meta-Harness**——基于 Claude Agent SDK 构建的端到端 harness 优化极简系统；在 GAIA2 与 Terminal-Bench 2.0 上作为基线对比，也是 AutoSaddler 效率论断（达到峰值所需轨迹数减少约 10 倍）的参照对象。

# Q5 核心解法

1. **由 Diagnosis-Patch Agent 完成的失败轨迹诊断。** 不同于对轨迹摘要做单次浅层反思调用，该 agent 主动探索原始执行轨迹与 harness 自身的源代码，借助结构化引导在长轨迹中逐步检索相关细节，缓解长 agent 轨迹带来的上下文长度压力——即"深度调试而非浅层反思"。
2. **结构化、带类型的补丁生成。** 补丁被约束在一个交叉分类体系内：按 harness 层级（Prompt：系统提示词规则的增改；Tool：新增工具、参数修正、实现修正、描述更新；Middleware：钩子、基础设施或 agent 循环逻辑的变更），再叠加补丁种类（Capability：可执行代码/编排变更；Steering：纯文本编辑）——即"有针对性的修改而非不受约束的编辑"。
3. **分阶段补丁调度（Phased Patch Scheduling）。** 优化先从 Capability 补丁开始，随后在运行后期转向 Steering 补丁，明确类比传统权重空间训练中的学习率调度。
4. **基于验证的更新筛选。** 候选补丁必须先在小批量上带来性能提升才会被暂时接受，随后可选地经过留出开发集检查以验证泛化性后才会被保留——即"具备泛化意识的筛选而非针对单条轨迹的修复"。
5. **EvoDAG。** 优化历史被保存为有向无环图而非单一线性链，在每个节点记录经验教训与性能信号，使得来自不同优化谱系的成功补丁组件可以被重新组合，而不是只能沿着最近一次的 harness 状态继续线性延伸。

# Q6 实验设计

三个基准、三种不同的基础 harness 与任务领域，底层 LLM 固定为 Claude Opus 4.6（即只优化 harness，不优化模型）：

* **GAIA2**——模拟智能手机环境中的通用助理任务，评测覆盖三个各含 107-112 个任务的测试"宇宙"；基础 harness 为默认的 ReAct 式 agent。
* **SWE-Bench Pro**——涵盖三个仓库的企业级软件工程任务（96 个 Ansible、85 个 Flipt、56 个 Element-web 任务）；基础 harness 为 SWE-agent 框架。
* **Terminal-Bench 2.0**——系统管理、机器学习、网络安全任务（40 个测试任务）；基础 harness 为 Terminus 2。

任务按不同任务组（而非随机划分）被分为互不重叠的训练/开发/测试集合，因此留出结果衡量的是跨领域泛化能力而非同分布记忆。核心指标是相对基础 harness、以及（在有报告的情况下）相对 GEPA 与 Meta-Harness 的测试集 Pass@1。在 GAIA2 上还单独报告了一项优化效率对比：开发集准确率相对所消耗任务执行次数/rollout 数的变化曲线。三项消融实验分别分离出方法的三个组成部分（RQ1：把深度诊断替换为单次浅层反思调用；RQ2：移除补丁分类体系与分阶段调度；RQ3：移除反思/开发集泛化筛选），均在 GAIA2 上测量。另有一项跨模型迁移探测：把 Opus 优化出的 harness 原样应用于 Haiku 4.5。

# Q8 证据质量

头条测试集增益具体且在三个互不相关的任务领域间内部一致，且是本笔记直接依据论文自身报告的点值重新计算得出，而非转引某个二手摘要：GAIA2 默认 agent 53.0% → AutoSaddler 62.0%（+9.0 个百分点），同时在同一测试集上超过 GEPA（54.6%）与 Meta-Harness（53.2%）；SWE-Bench Pro 上 SWE-agent 基线 37.3% → AutoSaddler 46.9%（+9.6 个百分点），同样超过 GEPA（42.5%）与 Meta-Harness（35.3%）；Terminal-Bench 2.0 上 Terminus 2 基线 40.0% → AutoSaddler 50.0%（+10.0 个百分点），超过 GEPA（42.5%）、Meta-Harness（43.3%），以及——值得注意的是——人工专家调优的 Terminus KIRA harness（47.5%）。这三个增量与论文摘要自述的"9.0、9.6 与 10.0 个百分点"完全吻合。效率论断是第二条独立证据，而非准确率增益的重复表述：在 GAIA2 上，AutoSaddler 用约 1,000 次任务执行就达到 72.3% 的开发集准确率，而 GEPA 与 Meta-Harness 即便消耗约 2,800 次执行仍分别饱和在较低的 64.6% 与 61.5%；AutoSaddler 自身在消耗 147 条轨迹后即达到峰值开发集分数，而 Meta-Harness 需要 1,400 条（约少 10 倍）。消融实验对"为何"每个组件重要而非仅仅"是否"重要给出了相当有诊断力的说明：在没有结构化、带类型补丁的情况下，91.5% 的生成补丁退化为纯文本 Steering 编辑，只有 4% 是能力型（New Tool、Loop Change、Infra Change）补丁类型——尽管这些能力型类型的接受率更高（67%-83%），且在被提出时其修复率与 Steering 补丁相当（55% 对 58%），回退（regression）却少得多（8% 对 17%）——这说明该分类体系不仅仅是记账工具，而是切实改变了系统愿意提出的修复种类。移除反思/开发集筛选（RQ3）带来了单项最大跌幅（62.0% → 50.6%），且各迭代间的回退趋势也出现了性质上的差异（AutoSaddler 呈 -0.24 个百分点/迭代的下降趋势，而消融版本呈 +0.16 个百分点/迭代的上升趋势），与该筛选机制专门用于防止在整个运行过程中累积泛化能力差的窄补丁（而不只是提升单次评分）这一解释相符。本笔记的说明性限制：以上数字证据来自对论文 HTML 渲染版本的自动化重新抓取（经三轮独立抓取交叉核对算术一致性），而非人工逐页阅读 PDF，因此表格中带有不确定"±"标注的数值被刻意省略，而非按猜测解读后报告；论文非常新（提交于 2026-08-24），撰写本笔记时尚未积累独立复现或同行评审；跨模型迁移证据只是单一数据点（Opus→Haiku，相对 Haiku 基础 harness +5.6 个百分点），而非系统性的迁移研究。

# Q9 主要贡献

1. 明确把自动 harness 优化表述为一个基于小批量失败信号的离线学习问题，把 harness 本身当作可训练产物。
2. 提出 Diagnosis-Patch Agent，将补丁提议同时建立在执行轨迹与 harness 源代码之上，而非仅依赖轨迹层面的浅层反思。
3. 提出带类型的补丁分类体系（层级 x 能力型/引导型）与分阶段补丁调度（能力型补丁先于引导型补丁），并通过消融实验证明这种结构本身——而不仅仅是"存在某种约束"——改变了哪些补丁类型会被提出与接受。
4. 提出基于验证、具备泛化意识的更新筛选（小批量加可选开发集检查），以及一份保留多条优化谱系以供后续重组的 EvoDAG，而非强制严格线性延续。
5. 在三个互不相关的基准（GAIA2、SWE-Bench Pro、Terminal-Bench 2.0）与三种基础 harness 上进行实证展示，取得一致的 9-10 个百分点 Pass@1 增益、相对基线（Meta-Harness）所需轨迹数量减少一个数量级，以及在 Terminal-Bench 2.0 上超越人工专家调优 harness（Terminus KIRA）的同基准胜出。

# Q10 下一步

* 论文自陈的局限：目前的范围覆盖 harness 的提示词、工具、中间件三层，但明确排除了针对无状态单回合任务的记忆或技能整理；作者提出"专门化的 LLM 驱动进化算法"作为超越当前基于 Claude Agent SDK 的诊断/补丁循环的一个方向；跨模型可迁移性（Opus 优化出的 harness 应用于 Haiku，+5.6 个百分点）被报告为有前景，但只是单次探测而非系统性研究。
* **对 Research-OS 的启示**：AutoSaddler 的诊断-撰写-验证循环在结构上与本 wiki 已有的 harness 优化谱系高度接近——可直接与 [MemoHarness](../papers/2607.14159.md)（六维 harness 搜索加双层经验库）、[SkillOpt-Lite](../papers/2607.03451.md)（文件原生轨迹探索加独立验证）、以及 [EnvHarness](../papers/2608.19880.md)（相同的诊断-撰写-验证模式应用于环境而非 agent 一侧）对照。AutoSaddler 对这一对比的具体贡献在于其带类型的补丁分类体系加分阶段调度，以及基于 EvoDAG 的谱系重组机制——值得在本仓库下一次评估某个 harness 优化方法用于自身 agent 工具时，与这些论文各自的补丁表示与验证门设计做比较。
