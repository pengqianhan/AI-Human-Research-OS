# Q1 问题定义

* **输入（X）：** 一条自然语言请求（某个具体物体、一个包含二到五个目标的有序列表，或"布置一个工作区"这样的高层需求），以及每一步来自陌生室内场景中机器人的四张 RGB 图像，分别标注为前、右、后、左。
* **输出（Y）：** 一串工具调用（观察、转向、导航到图像上的一个点、更新目标进度、结束），把机器人按顺序带到所要求的目标处，并以明确的"已完成"或"受阻"声明结束。
* **约束：** 多模态大模型原样使用，不做导航专用的微调；它必须自己判断任务是否完成；基准评分与这一声明相互独立。
* **核心问题：** 对任务和场景都通用的导航。模块化的零样本流水线把"何时咨询模型、何时结束"写死，新类型的请求就需要新的工作流；在导航轨迹上微调的端到端模型，其泛化范围止于训练数据的覆盖范围。

# Q2 问题新颖性

不是新问题，而且用框架（harness）做具身智能体是论文引用的一条活跃路线：[Show-Harness](../papers/2609.10522.md)（把语义动作转成机器人运动）、AgenticNav（像素目标运动加深度查询和历史图像检索）、HarnessVLN（事件记忆和时空图），以及同期提出 Demand-Bench 的 DemandAgent。SuperNav 自述的不同之处是：一个由可互换运动后端共享的统一"视觉点"接口、作为可读指导的 Navigation Skills、只裁剪媒体内容的上下文管理，以及把所有任务层面的动作选择和完成判断都留给模型。它所做的这一步——把编程智能体的"技能 + 工具 + 上下文管理"模式搬到机器人上——是本 wiki 最感兴趣的部分。

# Q3 科学假设

1. **分工。** 若通用多模态大模型只负责理解请求、读懂场景和选择目的地，而由工具执行运动，它在不同任务类型和场景中的导航表现会好于被微调来输出导航动作的模型。
2. **指点是足够的接口。** 若模型把目的地表示为四个带标注视图之一中的归一化坐标点，同一套决策流程在几何规划器和学习型控制器上都能工作，外部的语言定位模型不会带来额外好处。
3. **技能承载流程。** 若把搜索、复查、恢复和完成判定的流程写成模型按需阅读的 Markdown 指导，成功率会比只有同样的工具而没有这些指导时高出很多。
4. **框架可以换模型。** 若保持框架不变而更换决策模型，系统仍然可用。

# Q4 相关工作与关键人物

* **模块化导航流水线。** SemExp、L3MVN、VLFM、VoroNav、SG-Nav、ApexNav：模型在面向任务的流水线中担任固定角色。
* **分层系统。** InstructNav、OmniNav（慢速推理加快速路点策略）、SysNav：模型推理叠加在专用导航模块之上。
* **端到端导航模型。** NaVid、UniNaVid、StreamVLN：在"指令-轨迹"对上微调的视觉语言模型。另见本 wiki 中的 [LightNav-0](../papers/2608.30935.md)。
* **智能体系统与框架。** Inner Monologue、Code as Policies、SWE-agent；具身框架 [Show-Harness](../papers/2609.10522.md)、AgenticNav、HarnessVLN、DemandAgent。
* **关键人物。** 浙江大学（zju3dv 团队）、深圳大学和 Causa Robotics；Sida Peng、Xiaowei Zhou 和 Hujun Bao 在作者之列。可能的批评者：被比较的微调导航基线的作者，他们会指出最佳数字背后的特权几何信息和前沿模型；以及会要求完整数据划分结果的具身智能评测者。

# Q5 关键解决思路

* **智能体循环。** 运行时是 Codex CLI；环境操作通过[模型上下文协议（MCP）](../concepts/model-context-protocol.md)暴露。每一步模型选择观察、移动、更新目标状态或阅读技能指导，工具返回的内容进入上下文，供下一次决策使用。
* **视觉点导航。** 一次观察返回四张带标注的 RGB 视图。模型调用 $\mathrm{PointNav}(d,[u,v])$，其中 $d$ 是视图，$u,v\in[0,1]$ 是归一化坐标，指向候选物体或可见的地面。工具执行运动并返回新的四视图图像、执行状态和诊断信息，因此移动之后不需要再单独调用观察。
* **同一接口背后的两种运动后端。** *Geo-based Executor*（几何执行器）用深度、相机标定和位姿把所选点反投影，吸附到可达位置，再沿规划路径行进（仿真中用渲染深度、模拟器位姿和导航网格；真机上用 LiDAR 和里程计）。*Learned Executor*（学习型执行器）只用 RGB：一个受 NoMaD 启发的策略，包含带标记的参考图、DINOv2 ViT-S/14 编码器、最多 12 帧且带"帧龄"编码的历史，以及一个条件流（flow）头，预测八个位移增量和一个停止分数，用模拟器专家轨迹做模仿学习训练。
* **进度与结束工具。** 目标记录保存待找和已找到的条目；结束工具记录模型给出的"已完成"或"受阻"判断。两者都是模型自己的报告，不是独立验证。
* **Navigation Skills（导航技能）。** 一组 Markdown 包（一个主导航技能、与后端对应的工具使用说明，以及关于探索、恢复和寻找入口的参考）。框架暴露名称和描述，模型按需加载。指导内容涵盖去哪里搜索（记录已查看的区域和尚未探索的开口）、如何恢复（换一个点或路线、后退一步、玻璃挡路时寻找入口），以及何时结束（核对外观、请求中的关系和周围环境）。技能不增加任何能力，也不强制任何行为。
* **上下文管理。** 一张图像被处理且被更新的观察取代后，它的媒体内容会从之后的请求中去掉，文字历史、任务状态和图像路径保留；模型可以从工作区重新打开更早的图像。

# Q6 实验设计

* **决策模型。** GPT-5.6 Terra，高推理强度，每回合预算 3,600 秒。
* **实例导航（自建基准）。** Habitat-GS 加 InteriorGS 场景：150 个单物体任务和 150 个有序多物体任务（二到五个目标）。到达的定义是到某个认可视点的导航网格测地距离小于 1 米，并显式 STOP。
* **需求驱动导航。** 来自 Demand-Bench 的 200 个 AI2-THOR 任务，采用改编过的协议：一到八个有序阶段，每个阶段要求进入某个合格物体包围盒 2 米范围内，并显式 STOP。
* **以上两项的基线。** NaVid、UniNaVid、StreamVLN 和 OmniNav 的 Action Former，各自使用原生输入和历史机制；没有给它们加智能体式控制器或阶段进度信号。
* **类别级导航。** HM3D-OVON val-unseen 的一个 120 回合子集，以及 1,000 个 HM3Dv2 验证回合，与其他方法已发表的数字并列。
* **消融（OVON 子集，Geo-based Executor）。** 去掉 Navigation Skills；把四视图工具换成只有前视的接口；两者都去掉；把直接指点换成外部定位模型（LocateAnything）加候选确认；把模型换成中等推理强度的 GPT-6 Astra。
* **真机。** 一台 Unitree Go2，配四个 RGB 相机和基于 LiDAR 的几何执行，以三个示例运行展示。

# Q7 数据集与代码

代码在 [zju3dv/SuperNav](https://github.com/zju3dv/SuperNav)（抓取时 63 星），另有[项目主页](https://zju3dv.github.io/SuperNav/)。实例导航基准是新建的：物体标注由视觉语言模型生成并经人工复核，AI 使用声明还说明生成式 AI 协助生成了评测指令。所读文本没有说明该基准、技能包或 Learned Executor 的权重是否发布。Demand-Bench 来自同期的 DemandAgent 论文（以匿名方式引用）。决策模型是托管模型（GPT-5.6 Terra），论文没有报告每回合的 token 成本或墙钟时间。

# Q8 证据质量

* **有支撑的结论。**
  * *在作者的任务集上优势很大。* 使用 Geo-based Executor：单物体 78.00% SR、0.4127 SPL，多物体 34.00% 和 0.1388，需求驱动 59.50% 和 0.1801。最佳基线：单物体 34.00% SR（UniNaVid）和 0.2133 SPL（OmniNav），多物体 4.00%，需求驱动 37.50%（OmniNav）。
  * *消融显示框架的各组件都有作用。* 在 OVON 子集、0.25 米阈值下：完整系统 68.33% SR；去掉技能 35.00%；只有前视的工具 52.50%；两者都去掉 31.67%；定位模型接口 55.83%。去掉技能后，智能体每回合平均只做 7.43 次工具调用、行进 7.56 米，而完整系统为 11.17 次和 16.44 米，这提示它过早停止了搜索（读者对表 6 的解读）；只有前视的接口需要 30.28 次调用和 17.56 次转向。
  * *框架经得起换模型。* 中等推理强度的 GPT-6 Astra 在 0.25 米下得到 71.67% SR 和 0.4579 SPL（120 回合中成功 86 个），高推理强度的 Terra 为 68.33% 和 0.3837。
  * *靠后的目标。* 在多物体任务上，SuperNav 在每个阶段都领先（第一个目标完成率约 86%，基线最高 44%；第五个目标 34-39%，基线为 0%）。
* **比标题更弱或更窄的地方。**
  * *最佳配置使用了特权几何信息。* Geo-based Executor 依赖渲染深度、模拟器位姿和导航网格，而基线是 RGB 视频策略；作者指出后端的比较"同时改变了控制器及其依托的几何资源"。只用 RGB 的 Learned Executor 保住了大部分成功率（单物体 68.00%，需求驱动 45.00%），但它的单物体 SPL 0.2059 低于 OmniNav 的 0.2133，在 HM3D 上它的 SPL 降到几何后端的 40% 以下，例如 OVON 0.25 米下为 0.1355 对 0.3837（读者根据表 1 和表 2 的比较）。
  * *模型与预算不对等。* 一个每回合最多可用一小时的前沿托管多模态大模型，与微调的导航模型（NaVid 和 UniNaVid 的检查点是 7B）相比；没有给出成本、时延或步数的比较。最接近"同条件"的对照是内部的：同一模型在既没有技能也没有工具设计时，0.25 米下为 31.67%。
  * *HM3D 的比较跨越了不同协议。* 使用 Geo-based Executor 的 SuperNav 在 OVON 上 0.25 米为 68.33% SR、1 米为 73.33%（已发表的行：SoftNav 0.25 米 66.70%，AstraNav-Memory 1 米 62.50%），在 HM3Dv2 上 0.2 米为 80.30%、1 米为 86.50%（ApexNav 76.20%，MSGNav 74.10%）。它跑的是 120 回合的 OVON 子集；其他行是在不同子集、阈值、步数上限和 STOP 规则下发表的数字，附录列出了这些差异，作者也承认这一点。SuperNav 的 OVON 评分不要求 STOP 动作，并且每个配置有两个回合按 MTU3D 的"目标不可达"规则直接记为成功。
  * *样本小，单次运行。* 120 个回合下，Astra 与 Terra 在 0.25 米处的差距是四个回合。没有报告重复运行或区间。
  * *实例基准是作者自建的，需求协议是改编的。* 需求驱动的分数衡量的是按顺序到达相关物体附近，而不是完成那项活动，并且与 DemandAgent 报告的分数不可比（两点均为作者所述）。没有任何方法完成六个或更多需求阶段，而有这么多阶段的任务只有三个。
  * *评测隔离靠的是指令。* Codex 以完整文件系统访问权限运行，且关闭了审批；禁止读取场景资产、真值标注和评测器元数据只是一条指令，而不是操作系统层面的限制，论文也没有报告对运行是否遵守的审计（读者根据附录 A.2 的观察）。
  * *真机证据是定性的。* 三个带图示的 Go2 运行，没有成功率。

# Q9 贡献

* 一个导航框架（智能体循环、工具、技能、进度记录、只裁剪媒体的上下文管理），让未经修改的多模态大模型处理类别级、实例级、有序多物体和需求驱动的导航。
* 一个统一的视觉点运动接口，配两种可互换的后端，其中包括只用 RGB 的学习型点目标控制器。
* 一个 Habitat-GS 中的实例导航基准（150 个单物体任务和 150 个有序多物体任务）。
* 把技能、工具设计、定位接口和决策模型各自的贡献分开的消融，并附交互统计。

# Q10 下一步

* **作者提出的方向。** 系统受限于多模态大模型的语义判断；几何执行需要地图或场景几何；大模型推理带来成本和不稳定的时延；需求驱动的评测不衡量活动是否完成；更多真实环境和长序列上的可靠性仍有待改进。
* **强制执行评测边界（读者建议）。** 让智能体在看不到场景资产和评测器文件的沙箱中运行，或审计工具与 shell 日志中是否有这类读取。[MiMo-V2.6](../papers/2610.11959.md) 记录了编程智能体在环境允许时抓取已发布修复的情况，其应对是在给出指令之外，把这些路径去掉（清理产物、隔离网络）。
* **条件对齐的比较（读者建议）。** 与只用 RGB 的基线比较时，把 Learned Executor 作为主要结果；增加一个给同一多模态大模型配普通动作接口的基线；报告每回合的 token 和秒数。
* **哪些技能条目起作用（读者建议）。** 技能造成了消融中最大的降幅。逐一去掉搜索、恢复和完成判定的指导，或者像本 wiki 跟踪的技能进化论文那样在验证关口下优化技能文本，可以看出这一收益中有多少来自"停止前先近距离核实"这样的少数几条指令。
* **与本项目的契合（读者注）。** 这个框架与本仓库的智能体配置形态相同：按名称和描述发现的 Markdown 技能、MCP 后面的工具、保存在文件中的状态。去掉技能的消融直接说明这类指导会改变智能体的行为——在这里是让智能体继续搜索而不是过早停止。
