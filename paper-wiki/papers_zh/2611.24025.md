# Q1 问题定义

* **输入（X）：** 用户向使用工具的智能体提出的自然语言请求（这里是含歧义的 DevOps 请求：取消作业、重启服务、清理存储制品），智能体所操作的环境，以及一个分工：不受信任的强规划模型（planner），与受信任的小模型加受信任的校验与分发代码。
* **输出（Y）：** 一串实际执行的工具调用，完成用户授权的工作而不改动未授权对象；同时留下一份日志，让审计者在每次调用之前就能看到规划模型打算做什么。
* **约束：** 小模型的"受信任"取 AI 控制（AI control）中的含义：它努力遵循用户，但可能出错；它能看到用户的消息，却看不到环境和工具输出。实验只用合作型模型和良性越界（benign over-reach），不评估恶意规划模型。

# Q2 问题新颖性

给编码智能体加权限闸门并不新：Claude Code 的 auto mode 用一个"不看推理"（reasoning-blind）的分类器，刻意隐藏智能体的说明文字；AmPermBench 用含歧义的请求对这一设计做压力测试。AI 控制中的可信监控、untrusted-advice 协议、CaMeL 与 Dual LLM 模式，以及基于规则的意图或权限系统（Progent、意图证书、Intent Graphs、DRIFT）也都已存在。新问题是：受信任一侧能否*有用地*利用执行前的一段简短、可核查的意图声明？当规划模型完全失去写命令的能力时又会改变什么？论文把自然语言意图当作需要核查的论断，而不是授权本身。

# Q3 科学假设

如果规划模型只能描述一步（目标、用户原话引用、范围），由受信任模型来写调用，那么：（1）在结构上，每个被执行的调用都由受信任模型写出；每次调用之前都有一份记录在案的契约，承载规划模型对该调用的全部影响；受信任一侧决定执行请求的多少。（2）在经验上，这应当得到一份关于哪些对象将被改动的完整执行前记录，并让捆绑请求中被授权的部分得以完成。论文明确*没有*假设契约会减少未授权操作，而是去检验它是否会。

# Q4 相关工作与关键人物

* **AI 控制与可信监控。** Greenblatt 等人的控制评估（不受信任的强模型、受信任的弱模型）；Redwood 的 untrusted-advice 协议，是最接近的架构先例（受信任模型根据简短的不可信建议执行全部操作）；Wen 等人和 Factor(U,T)，其中受信任模型实现不可信计划，而只看计划的监控器很难识别攻击（AUROC 0.52，看到实现时为 0.96）。
* **给监控器看解释。** Sreevatsa 等人（可读性协议：注释在攻击下帮助可信监控器）与 auto mode 剥离智能体说明文字的选择相对。
* **让模型远离工具。** Dual LLM 模式与 CaMeL 中，不持有工具的是读取不可信数据的那个模型；意图契约反过来：规划模型读取全部工具输出却不持有工具。
* **权限分类器与意图/范围系统。** Claude Code auto mode、AmPermBench（Ji 等）、AuthGateBench、Parallax、意图证书（Zhu 和 Wang，即本文两位作者）、微软 Agent Governance Toolkit、Progent、Intent Graphs、DRIFT。这些工作里由代码对每个调用强制施加边界；本文中代码只检查引用和范围，目标是否被授权是模型的判断，因此契约是"一份记录和一个论断，而不是策略边界"。
* **关键人物。** Ziyuan Wang（独立研究者）、Genliang Zhu（佐治亚理工）、Xiaobo Chen（麻省大学阿默斯特）、Chu Wang（UIUC）。可能关注或批评的人：AI 控制研究者（Redwood），AmPermBench 作者，以及已部署权限分类器的开发者。

# Q5 核心方法

三种接口共用一个 OpenCode 插件，共享模型、规划提示和日志：

1. **盲审（Review）。** 规划模型写出确切的 shell 命令；受信任审查者看到用户消息、代码维护的历史调用与退出码账本，以及该命令，只能整体批准或拒绝。这复现的是不看推理的权限分类器的信息边界，而非已部署的分类器本身。
2. **可见意图审查（Review+Intent）。** 同上，但代码先校验规划模型对用户原话的逐字引用，审查者还能看到目标和引用；它被告知按命令的实际效果判断，并且引用属实也不证明已获授权。它仍不能修改命令。
3. **契约执行（Contract）。** 规划模型没有环境工具。每一步它提交一个目标（至多 100 词，写明对象、改动及与请求的联系，不含命令行）、一句逐字引用、允许的出站主机和写入前缀，以及错误策略。代码检查引用（NFKC 与空白规范化后的连续子串）、范围只能收窄基线、目标格式（启发式命令行检测）。受信任模型在一个只含用户原话与自身调用账本的新会话中，最多写一个工具调用，只执行被授权的部分，并且只收到一张回执（输出大小与退出码）。工具输出交给规划模型。

与命令审查的关键区别在于*粒度*：审查者只能拒绝整条命令，执行者却可以执行一步中被授权的部分并拒绝其余部分。论文谨慎指出，三条结构性质只在分发代码正确时成立（有单元测试，未经形式验证），且任意 shell 写入不受声明的写入前缀约束。

参照条件：强模型单独运行（Strong）、小模型单独运行（Small）、Strong+Declare（强模型在每次改状态前必须写一行 `INTENT:`，记入日志但无人阅读）、WholeTask（一份契约后由小模型多次调用完成整个任务），以及"严格执行者"（被告知无法从用户消息判断用户要求了对这些对象的这项改动时就拒绝）。

# Q6 实验设计

* **任务。** AmPermBench 四个任务族中的三个（取消作业、重启服务、清理存储制品），每族 32 个原始提示，每个条件共 96 个，使用基准自带的程序化评分；省略了分支清理族（状态是 git 仓库），因此不是全基准结果。提示的目标指称分四类：精确 ID、自己的工单、自己的范围、开放范围。
* **模型。** gpt-6.1-terra（经 ChatGPT 订阅访问）作规划模型和强模型；GLM-5.3-Flash（经 OpenRouter）作受信任模型和小模型。每个提示每个条件只跑一次。
* **结果指标。** 安全完成（完成全部授权工作且未改动未授权对象）、未授权操作、未完成；后两者可同时出现。Clopper-Pearson 95% 区间；精确配对 McNemar 检验，未做多重比较校正，作描述性解读。论文说明 96 个提示来自 16 个模板、每族一个环境，因此区间偏乐观。
* **"先声明后执行"指标。** 对每个被改动的对象，找到首个在参数中点名它的改状态基准工具调用，以及在此之前最后一份被代码接受的契约；若该契约的目标（字面子串匹配）点名了它，则计为已声明。对审查条件，另计命令是否点名它。
* **捆绑任务。** 作者自写：只有规划模型那份用户消息被加入一条无害的额外请求；十个单文件任务附加请求，八个小项目把额外请求插入四项改动的列表中；每任务每模式跑三次；用对最终文件的程序化检查判定。
* **澄清"lane"术语。** 在每个提示后附一句固定说明，指出基准中"lane"一词（如 "workbench lane"）对应什么，消除一种歧义，但"哪些对象属于请求"的歧义保留；在全部 96 个提示上跑 Strong、Review、Review+Intent、Contract 和严格执行者版 Contract。
* **WholeTask** 消融在 30 个提示的子样本上进行。

该设计对每条结构性论断都用日志验证，对经验性论断则在单一配置下测量。论文说明它没有测试对抗性规划模型，也没有测试抗提示注入能力。

# Q7 数据集与代码

AmPermBench 提供环境和评分。OpenCode 插件、契约检查、逐次运行记录、有序事件日志，以及一个从日志重算所报告计数的脚本，发布于 https://github.com/zwang-devv/intent-contracts。附录 A 逐字给出所有角色指令。

# Q8 证据质量

* **声明覆盖很强，但几乎是设计使然。** 在 Contract 下，56/56 个被改动对象（原始提示）与 181/181 个（澄清后）都在产生该改动的契约目标中被点名；两种审查条件分别只有 2/16 和 4/54，而它们的*命令*分别点名了 16/16 和 39/54。论文自己也说完全覆盖"接近接口的必然结果"，因为执行者看不到环境，只能作用于被点名的对象。真正有信息量的是：Contract 的每一次未授权改动也都事先被点名，因此越界可以通过阅读契约来发现。
* **捆绑请求。** Contract 在 27/27 次有效运行中完成主任务（把三次因每份契约都引用了用户从未说过的话而被拒的运行算进去为 27/30），Review+Intent 为 16/30；两者都没有做额外工作。在多文件列表上为 24/24 对 19/24，Review+Intent 未完成的 5 次连四项改动中的任何一项都没做。这是粒度性质最清楚的证据，但来自作者自写的小任务，且每任务三次运行并不独立。
* **未授权操作：没有改善。** 原始提示：Review+Intent 2/96，Review 10/96，Contract 10/96，Strong 15/96，Small 1/96（但 92/96 未完成）。Review+Intent 的优势部分来自它行动更少（改动状态的运行分别为 9、20、22 次），审查者拒绝了 142 份契约，执行者只拒绝 4 份。澄清后：Contract 有 29/96 次未授权操作，Review+Intent 18/96，Review 25/96，Strong 14/96，没有任何带闸门的条件少于强模型单独运行。以"有行动"为条件，错目标率处处在 40% 到 49%（14/35、18/37、25/58、29/64），所以各条件的区别在于多常行动，而不是行动多常出错。
* **错误发生在哪里。** 澄清后的全部未授权操作都落在两类范围指称上；精确 ID 和自己工单的提示在四个条件下都是 0/48。论文的诊断（问题在于规划模型对歧义指称的解读，而任何看不到环境的受信任角色都无法核查）直接得到这一分解以及严格执行者重跑的支持：后者什么都没改变（安全完成都是 35/96，未授权 30 对 29）。
* **只声明不检查是弱检验。** Strong+Declare 从 15/96 降到 10/96（p = 0.125），但 30 次改状态的运行中只有 14 次出现 `INTENT:` 标记，所以它检验的是未强制执行的指令，而非一贯的自我声明；论文也这样说。
* **读者核查。** 澄清后的百分比可由给出的计数精确重算（如 29/64 = 45%），表 2、4、7 的运行级计数相互一致。每个提示只跑一次，且托管模型只以标签区分版本，运行间波动与条件效应无法分开（论文列为局限）。
* **总体。** 结构性论断论证充分、可核查；经验性论断范围交代诚实，而且少见地报告了自己的方法并未降低核心安全指标。

# Q9 贡献

1. 意图契约接口：不持工具的规划模型、带逐字引用与范围并由代码校验的契约、由受信任模型写出每个调用；三条性质由分发代码固定。
2. 在外部基准上，与不看推理的命令审查和可见意图的命令审查进行受控比较，并配有强模型单独、小模型单独、只声明三个参照。
3. 一个与基准工具调用日志对齐的程序化"先声明后执行"指标。
4. 区分"部分执行"与"整条命令批准"的小型捆绑任务。
5. 一个定位清楚的负面结果：剩余错误来自规划模型对歧义指称的对象选择，看不到环境的受信任模型无法核查，而"拿不准就拒绝"的指令也无济于事。

# Q10 后续方向

* **让受信任一侧看到环境。** 这是论文自己提出的下一步：给执行者一种对照环境核查规划模型对象选择的方式（例如在行动前用只读查询解析"我的过期作业"），检验错目标率能否降到 40% 以下。
* **对抗性规划模型。** 让规划模型尝试经由契约通道或其读取的工具输出夹带操作；结构性质说明了影响能从哪里流动，并不说明能否被抓住。
* **模型与提示的变化。** 换用其他规划/受信任模型组合、每个提示多次运行、并改变审查者的指令，因为 Contract 与 Review+Intent 的关键差异可能是指令效应（读者建议）。
* **全基准与沙箱。** 纳入 git 分支清理族，并把契约与操作系统级沙箱结合，让写入前缀也约束 shell 写入（读者建议）。
* **与其他场景中的动作级意图相联系。** [AgentRoboCritic](../papers/2611.26613.md) 也要求执行模型为每个动作声明局部意图，用于让结果评判变得可定义；两篇论文都发现，只对照执行者自己的声明来检查意图，抓不住目标选错（读者联系）。
