# Q1 问题定义

* **输入（X）：** 自然语言游戏规格 x；由生成器策略采样得到的冻结初始项目 P₀（源码、视觉与文本资产、配置文件，以及可回放的演示轨迹）；目标引擎（Godot 或 Phaser）；每轮工具预算（每轮最多 26 次工具调用，最多 30 轮开发）。
* **输出（Y）：** 改进后的项目 P_T，其回放演示轨迹在隐藏的任务专属评分标准上得分更高：Q = BUILD × (0.15·机制 + 0.35·深度 + 0.15·视觉 + 0.35·美术)，其中 BUILD ∈ {0, 1}，不可运行的游戏直接记零分。第二个输出是经微调的生成器（Qwen3.8-27B SFT），其一次生成（one-shot）的起点更高。
* **核心问题：** 对生成游戏做"测试—诊断—修改"的迭代循环，容易过拟合它恰好触及的少数测试用例，收敛到脆弱的版本：未测出的 bug、缺失的行为、未处理的边界情况；并且随着轮数增加会停滞甚至退化（图 3）。论文要回答的是：如何让长程自主开发*可靠地*把额外轮数转化为更高的游戏质量。
* **范围：** 可在实际智能体预算内完成的紧凑 2D 游戏；质量只在 GameCraft-Bench 的四个维度上度量（附录 B 明确指出原创性、叙事、长期参与度、主观乐趣不在评估范围）；主实验中改进智能体是 GLM-5.3-Flash，探索/测试智能体与基准评审（judge）都是 Qwen3.8-27B。

# Q2 问题新颖性

问题本身不新。迭代式智能体游戏开发已有先例：Play2Code 在游玩与代码修改之间交替、利用交互反馈指导后续编辑；VibeGame 用八角色智能体团队（含验证与优化角色）；OpenGame 跨项目积累可复用技能。论文所依赖的基准（OpenGame-Bench、GameCraft-Bench、GameDevBench）只给单次提交的版本打分。论文自己对"新在哪里"的界定（第 6 节与附录 F.1）很窄也很明确："本文并不声称智能体能改进自己生成的游戏——好几个系统都能做到。本文声称的是，要*可靠地*做到这一点需要一个控制器：一个判断余量在哪里、保留最佳版本、并知道何时停止的东西。"同一团队的姊妹论文 [RSIAgent](../papers/2609.15364.md) 已经做过 40 个 GameCraft-Bench 任务对比 Play2Code 的泛化检验；RSIGame 把游戏开发作为主场景，扩展到全部 140 个任务和两个引擎，并新增基于训练的经验内化步骤。这个问题之所以重要，是因为游戏项目是多模态、多文件、依赖运行时行为的工程压力测试，仅靠编译检查会漏掉大多数失败（表 2b：仅构建检查对行为性失败的检出率为 0%）。

# Q3 科学假设

两个相互耦合的假设：

1. **控制器假设。** 如果开发循环 (a) 广泛探索可运行的游戏而不是反复测同一批用例，(b) 每次编辑都以观测证据为依据并通过回放验证，(c) 把问题与指导累积在持久的检查清单中，(d) 由一个保留最佳检查点、在饱和时停止的全局监控器管辖，那么在朴素迭代停滞或退化的地方，额外的开发轮数应带来期望意义上单调的质量提升。检验：表 1（与 Play2Code 的等预算对比）、图 3（开发时扩展）、图 4a-b（最佳检查点保留与饱和停止）、图 5（自适应方向选择 vs. 轮询）、表 2（验证审计）。
2. **内化假设。** 如果生成器在经验证的规划、生成和改进轨迹上微调，而不只是在最终产物上微调，那么一次生成的质量应在四个维度上全面提升，且循环达到给定质量所需的 token 更少。检验：表 1 中 Qwen3.8-27B (SFT) 行、图 4c、表 18 的嵌套训练数据消融。

# Q4 相关工作与关键人物

* **游戏生成与开发基准。** OpenGame-Bench（网页游戏，构建有效性与指令对齐）、GameCraft-Bench（引擎游戏，交互落地的机制/深度/视觉/美术，本文使用的评测套件）、GameDevBench（更大的代码库与资产），以及 OmniGameArena、V-GameGym、WebGameBench、CreativeGame。它们都只给单个版本打分。
* **迭代式智能体游戏开发。** Play2Code（主基线）、VibeGame（附录 F.1 的对比对象）、OpenGame（跨项目技能积累），根植于更广的智能体编程谱系（SWE-agent、MetaGPT、ReAct、Reflexion）。
* **验证与从开发经验中学习。** LLM-as-a-judge 协议、StructAgent（同团队针对长程数字智能体的过程控制工作）、GameGen-Verifier（运行时状态注入）、Self-Refine、Self-Debug、STaR、代码与单测协同演化、M⋆ 记忆框架。RSI 框架引用了 Meta-Rewarding LMs 以及本团队的 [RSIAgent](../papers/2609.15364.md)。
* **关键人物。** arXiv HTML 列出的机构为加州大学圣迭戈分校、字节跳动、卡内基梅隆大学；检索到的文本没有把作者逐一对应到机构。Wenyi Wu 与 Minghao Fu 为共同一作；Kun Zhou 为通讯联系人。Wenyi Wu、Kun Zhou、Aayush Salvi、Biwei Huang 与 StructAgent、RSIAgent 的作者名单重叠，因此这是同一团队关于数字智能体递归自我改进的第三篇论文。可能的批评者：Play2Code 与 VibeGame 的作者（他们的系统被展示为停滞或退化），以及 GameCraft-Bench 的作者，因为本文用 Qwen3.8-27B 评审替代了基准自身规定的协议。

# Q5 关键解法思想

区别所在是围绕一个原本标准的编辑循环加了两层控制结构，并把循环产出的已验证轨迹喂回生成器。

* **局部循环（探索—诊断—改进），四个智能体共享一份检查清单 𝒞_t。** *控制器*读取规格、当前项目、检查清单和可选的阶段级指导 γ_s，选出开发方向 d_t。*探索器*沿该方向游玩可运行的游戏，返回包含具体行为证据的轨迹 τ_t。*编辑器*把证据转化为项目编辑 Δ_t。*验证器*回放编辑后的游戏，判断目标问题是否已修复且无回归，并把结果写回。检查清单更新 𝒞_{t+1} = U(𝒞_t, d_t, τ_t, Δ_t, v_t) 是跨轮传递证据的载体，使每一轮从已验证状态而非从零开始。
* **全局循环（质量监控与收敛控制）。** 游戏质量监控器把最新版本与保留的冠军 P*_s 比较，留下更好者。它读取一份独立的代理评分标准，从不接触基准的隐藏评分标准、分数或反馈；其读取像素的比较器与决定方向和停止的阶段相互隔离（附录 C.2）。持续无法超越冠军即视为收敛：运行返回 P*_s，或可选地在人类或更强模型给出的稀疏高层指导下开启新阶段（一份"简报"，给的是战略方向而非编辑指令）。
* **自适应方向而非轮询。** 控制器把精力转向当前瓶颈（构建失败后转向修复，视觉落后时转向美术）；盲法成对评审以 59% 对 37% 偏好自适应运行。
* **基于训练的内化。** 2,213 条生成轨迹（GPT-5.5 在 Godot 与 Phaser 中生成）、2,108 条规划轨迹、2,013 轮已验证改进（从 4,003 个候选中筛出，由 GLM-5.3-Flash 运行）被序列化为长文档，用于对 4-bit 量化的 Qwen3.8-27B 做 LoRA SFT。构建语料时排除了基准任务 ID，并在事后重新扫描（2,511 个任务 ID 中零重叠）。

论文刻意*不*宣称新颖的部分：迭代、LLM 评审、多智能体角色。附录 F.1 基于 VibeGame 对比论证："流水线中存在验证与优化角色，并不是产生持续改进的原因。"

# Q6 实验设计

* **基准与引擎。** GameCraft-Bench 全部 140 个任务（15 个游戏家族），在 Godot 与 Phaser 中用相同的规格、评分标准和协议实例化，因此 Phaser 是跨引擎稳健性检验。
* **实验臂。** 冻结的 P₀、Play2Code、RSIGame，均从 P₀ 的同一副本出发，使用相同的改进骨干模型与每轮工具预算（每轮 26 次工具调用，30 轮）。Godot 上五种生成器设置（Codex + GPT-5.5、Codex + Kimi-K2.6、Codex + GLM-5.3-Flash、Codex + Qwen3.8-27B、Codex + Qwen3.8-27B SFT），Phaser 上三种（OpenGame + GPT-5.5、OpenGame + Qwen3.8-27B、OpenGame + Qwen3.8-27B SFT）。
* **打分。** Qwen3.8-27B 评审，三次独立回放打分取均值；RSIGame 行记录饱和停止触发时监控器持有的检查点，Play2Code 行记录 30 轮后的版本。
* **针对具体主张的分析。** 40 个任务上的开发时扩展曲线（图 3）；oracle 最佳 vs. 保留检查点以及饱和停止（图 4a-b）；盲法成对评审下自适应 vs. 轮询（图 5、附录 D.6）；以 Claude Opus 5 为独立审计者、覆盖 40 个会话与 48 轮裁定的验证审计（表 2、附录 D.7）；嵌套的 S1 ⊂ S2 ⊂ S3 训练数据消融（表 18）；共享任务上的 VibeGame 对比（附录 F.1）。
* **可靠性控制。** 20,000 次重采样的配对任务 bootstrap 与 Wilcoxon 符号秩检验（表 14）；529 个三次打分的 Godot 产物的回放稳定性（中位数极差 0.73 分，529 个中有 225 个三次完全一致）；用 GPT-5.5 对 40 个任务重新打分得到相同的方法排序（表 12）；20 个任务上的自由游玩评估，盲法智能体自行选择轨迹（RSIGame 在 20 个中有 17 个优于基线，18 个优于 Play2Code；59 个已判定对比中有 45 个与基准排序一致）。
* **未纳入设计。** 主表中没有单独移除检查清单或验证器的消融；除图 3 的"仅局部循环"曲线外，没有把增益在局部循环与监控器之间做逐组件归因；全规模只运行了一个迭代基线（Play2Code）；Kimi 与 GLM 生成器没有在 Phaser 上评估。

# Q7 数据集与代码

没有新基准。使用 GameCraft-Bench（140 个任务）在 Godot 与 Phaser 中的实例。已发布：实现、提示词与输出契约、打分框架、项目页上六个可玩的演化游戏，以及一个包含 51,644 个打分文件（逐任务分数、评审输出、回放报告）的 Hugging Face 数据集（`RSIGame/RSIGame-TableArtifacts`）。冻结的基础项目、训练轨迹和逐轮运行树在提交时"正在内部审查"。复现需要 GPT-5.5（生成）、GLM-5.3-Flash（改进）、Qwen3.8-27B（探索器、评审、SFT 基座）和 Claude Opus 5（仅审计）。

# Q8 证据质量

* **支撑充分。**
  * 在 Godot 上，等预算下对 Play2Code 的增益大且一致：五种生成器下 Overall 提升 +7.2 到 +13.8 分，任务 bootstrap 区间均在零以上，表 14 中测试的两个 Godot 生成器均通过 Wilcoxon 显著性检验。Play2Code 在强基座 GPT-5.5 上只加不到 1 分（50.26 → 50.74），而 RSIGame 加 14 分（→ 64.53）且成本更低（每任务 $0.88 对 $1.06）。
  * 内化主张在其自身设定下成立：Qwen3.8-27B 一次生成从 37.07 升到 48.22，嵌套语料消融把增益归于规划与改进轨迹而非仅生成轨迹（机制 +14.9，深度 +14.1），token 从 6.41M 降到 0.57M。
  * 回放噪声相对任务差异很小，跨评审排序稳定，自由游玩检验回应了"增益仅限于开发时回放脚本"这一明显担忧。
* **弱于标题所示。**
  * 摘要中"超过 GPT-5.5 一次生成分数"比较的是*经 30 轮开发*的 Qwen SFT 游戏（61.38）与*一次生成*的 GPT-5.5 游戏（50.26）；GPT-5.5 加 RSIGame 达到 64.53，同口径下前沿模型仍然胜出。在 Phaser 上，Qwen SFT + RSIGame（58.53）确实略高于 GPT-5.5 + RSIGame（58.21），但 Qwen3.8-27B 在 Phaser 上对 Play2Code 的比较不显著（+1.55，p = 0.394）。
  * 评审、探索/测试智能体和 SFT 学生模型都是 Qwen3.8-27B。用 GPT-5.5 对 40 个任务重新打分能缓解但无法消除"Qwen 系评审偏好 Qwen 系输出"的担忧，SFT 行尤其如此。
  * 基线行显示 Qwen3.8-27B 一次生成消耗 6.41M 计费 token，而 GPT-5.5 为 0.26M，说明开源模型生成基础游戏的成本高得多；论文没有讨论原因。
  * VibeGame 对比每任务只跑一次，角色模型由作者设定；论文自己说"对 VibeGame 在其他模型或更大预算下的表现不作任何声称"。
  * 来自人类或更强模型的多阶段指导只在有限案例上评估（附录 B），所以"可选指导"机制基本未经检验。
* **读者观察。** 监控器与基准评分标准的隔离有充分记录，但监控器的代理评分标准与基准评分标准针对的是同样四个维度，因此部分增益可能来自优化一个与指标高度相近的代理，而非一般意义上的游戏质量。自由游玩研究是论文给出的回应，而它只有 20 个任务。

# Q9 贡献

* 一个面向长程自主开发的具体控制架构：自适应方向选择、证据驱动的编辑、基于回放的验证、持久检查清单、最佳检查点保留和饱和感知停止，并给出论证与证据说明：让轮数转化为质量的是控制器，而不是角色或迭代本身。
* 第一个全基准（140 任务、两引擎、五生成器）等预算的迭代游戏开发方法对比，可靠性报告异常完整（配对 bootstrap、回放稳定性、跨评审、自由游玩）。
* 量化智能体验证带来什么的验证审计：编辑前落地精度 58.6% → 72.3%，编辑后失败召回 76.2%，而仅构建检查检出为零。
* 证据表明把规划与已验证改进轨迹内化进 27B 模型，可全面提升一次生成的四维质量，并把生成 token 减少约 11 倍，污染筛查有记录。
* 发布了代码、提示词、可玩游戏和 51,644 个打分产物。

# Q10 下一步

* **评审独立性。** 用非 Qwen 评审重打全部 140 个任务而非 40 个，并单独报告 SFT 行，因为评审与学生同族的影响在那里最大。
* **组件归因。** 在主表中分别消融检查清单、验证器和自适应方向；表 2 审计了验证质量，但没有展示它对最终分数的影响。
* **更强的迭代基线。** 以相同预算运行 OpenGame 的技能积累和调优后的 VibeGame，并增加一个"Play2Code + 最佳检查点保留"臂，把监控器的贡献与局部循环分开。
* **持续 RSI。** 论文提到可反复内化新经验；在 RSIGame-with-SFT 轨迹上再做一轮 SFT，可检验这个循环是持续回报还是饱和。
* **更大的项目。** 附录 B 把资产更丰富、跨系统依赖更复杂的大型游戏列为开放问题；在那种规模下检查清单的增长与监控器的成本尚未度量。
* **项目契合（读者笔记）。** "最佳检查点 + 饱和停止"模式，加上监控器与验收指标隔离，可直接用于本仓库中任何自我改进循环（技能、框架编辑、记忆策略），并与 [RRSI](../papers/2609.24972.md) 的噪声带验收下限互补。

# 相关

* [递归自我改进](../topics/recursive-self-improvement.md) - 把游戏开发框定为两层 RSI：一个免训练循环，其检查清单与冠军跨轮持续；一个训练循环，把已验证的开发经验折回生成器；决定改进什么的机制（控制器）本身固定，所以在该主题的尺度上它是一个具体的受控循环，而非自指式 RSI。
* [智能体自我演化](../topics/agent-self-evolution.md) - 循环期间的可变对象是生成产物加共享检查清单，循环之后是生成器权重；验收门是回放验证器加与基准评估器隔离的冠军监控器。
* [智能体测试时扩展](../topics/agent-test-time-scaling.md) - 扩展*单任务内的轮数*，并表明这种扩展只有在保留最佳检查点和饱和停止下才成立；同预算下 Play2Code 随轮数增加而停滞或退化。
* [RSIAgent](../papers/2609.15364.md) - 同一团队；其 40 任务 GameCraft-Bench 对 Play2Code 的检验是本文全基准、双引擎研究的前身。
* [RRSI](../papers/2609.24972.md) - 互补的保障：RRSI 用噪声带下限和泄漏审查器正则化自我改进编辑的*验收*，RSIGame 用冠军保留和评估器隔离的监控器保护进展。
* [LLM-as-a-Judge](../concepts/llm-as-a-judge.md) - Qwen3.8-27B 依据隐藏评分标准为主表全部结果打分（三次回放均值）；40 个任务用 GPT-5.5 重打、20 个任务用自由游玩智能体检验评审依赖性。
