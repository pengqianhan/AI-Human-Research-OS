# SearchOS-V1 阅读笔记

> 论文：**SearchOS-V1: Towards Robust Open-Domain Information-Seeking Agent Collaboration**  
> 论文链接：<https://arxiv.org/abs/2607.15257>  
> 项目代码：<https://github.com/antins-labs/SearchOS>  
> 相关论文：RLM（Recursive Language Models），<https://arxiv.org/abs/2512.24601>

---

## 1. 一句话总结

SearchOS 将开放域信息搜索从“让一个长上下文 Agent 不断搜索并最终写答案”，重构为：

> **先把用户问题编译成一个显式的全局搜索结构，再持续识别结构中的信息缺口，调度多个局部 Agent 搜索、抽取证据、写回状态，最后从结构化状态生成带引用的答案。**

它的核心不是“多开几个 Agent”，而是把搜索进度、事实证据、未知区域、冲突和任务依赖都变成系统中的一等状态。

可以概括为：

```text
User Query
   ↓
Global Schema / Coverage Map
   ↓
Find Gaps
   ↓
Dispatch Local Search Agents
   ↓
Extract Evidence Automatically
   ↓
Update Global State
   ↓
Repeat Until Coverage / Budget Condition
   ↓
Citation-grounded Writing
```

---

## 2. SearchOS 试图解决的问题

普通 ReAct 或 Deep Research Agent 在长程开放域搜索中常见四类问题：

1. **搜索状态埋在对话历史里**  
   哪些实体已经查过、哪些字段仍然缺失、哪些结论来自什么来源，都依赖模型从长对话中“回忆”。

2. **容易重复搜索和循环**  
   Agent 可能不断改写同一个 query、反复打开相同页面，或者多个子 Agent 搜索同一个对象。

3. **搜索、抽取、记忆和总结职责混在一起**  
   子 Agent 不仅要找网页，还要自己记住全局任务、统一字段格式、保存引用，长任务中很容易遗漏。

4. **停止条件模糊**  
   模型通常依赖“信息似乎够了”的主观判断，而不是检查任务结构中究竟还有多少缺口。

SearchOS 的基本判断是：

> 长程搜索的主要瓶颈，不只是模型不会搜索，而是搜索过程没有一个可靠、可计算、可恢复的全局状态。

---

## 3. 核心抽象：Citation-grounded Relational Schema Completion

SearchOS 将开放域搜索统一建模为：

> **带引用的关系模式补全。**

例如，用户要求比较多个 AI coding agents：

| Agent | Model | Price | Context | Sub-agent | Open source |
|---|---|---|---|---|---|
| Claude Code | ? | ? | ? | ? | ? |
| Codex | ? | ? | ? | ? | ? |
| Gemini CLI | ? | ? | ? | ? | ? |

每一个 `?` 都是一个明确的 coverage gap。

传统 Agent 的下一步通常是：

```text
继续找一些关于 Gemini 的信息。
```

SearchOS 的下一步则可以被明确表示为：

```text
查找 Gemini 当前旗舰 coding agent 的价格，并优先寻找官方来源。
```

这种表示带来了三个直接结果：

- 搜索目标可计算；
- 搜索任务可去重；
- 停止条件可检查。

---

## 4. SOCM：Search-Oriented Context Management

SearchOS 的核心状态层叫作 **SOCM**。它不是普通的 conversation memory，而是整个搜索过程的结构化共享状态。

SOCM 主要由以下部分组成：

### 4.1 Frontier Memory：任务前沿

Frontier 保存所有待执行、运行中、阻塞和完成的任务。

每个任务通常包括：

- task id；
- task prompt；
- task kind：explore / search / write；
- status；
- priority；
- `blocked_by` 依赖；
- target table；
- target cells；
- skills；
- budget。

任务之间可以形成依赖 DAG：

```text
发现大学列表
    ↓
确定具体项目
    ↓
搜索申请截止日期
    ↓
核验招生周期
```

因此，SearchOS 不会在关键实体尚未确定时盲目派发后续搜索。

---

### 4.2 Coverage Map：覆盖地图

Coverage Map 记录每个实体—属性单元格的状态，例如：

| Company | Revenue | Employees | CEO |
|---|---:|---:|---|
| A | ✓ | ? | ✓ |
| B | ? | ✓ | Conflict |

它不仅支持单表，还支持：

- 多表 schema；
- primary key；
- composite primary key；
- foreign key；
- column type；
- column description；
- hard validation；
- supporting evidence ids；
- conflicting evidence ids。

Coverage Map 是 SearchOS 的“任务地图”：

- `MISSING` 表示未探索区域；
- `FILLED` 表示已有候选证据；
- `CONFLICT` 表示需要进一步核验；
- row-set 缺失表示 schema 中甚至还没有创建应有的行。

一个重要警告是：

> **已有行的 cell 全部填满，不等于真实任务已经完整覆盖。**

例如只创建了 Computer Science 的前五名大学，表格内部可能是 100% coverage，但 Economics、Engineering 等学科的整批行仍未进入 schema。

因此 SearchOS 额外加入 row-set audit 和 empty-table audit。

---

### 4.3 Evidence Graph：证据图

Evidence Graph 保存的是：

```text
实体 → 属性 → 候选值 → 来源 → 原文片段 → 置信度
```

一个 Evidence Node 通常包括：

- entity；
- attribute；
- value；
- source URL；
- source excerpt；
- confidence；
- source authority；
- alignment；
- table id。

同一个 cell 可以由多个 evidence 支持：

```text
Stanford.deadline
  ├── 官方招生页面
  ├── 院系 FAQ
  └── 第三方聚合网站
```

如果来源给出不一致值，SearchOS 不直接用新值覆盖旧值，而是保留冲突关系并触发后续核验。

因此：

- Evidence Graph 是“事实与来源层”；
- Coverage Map 是“任务进度与状态层”。

---

### 4.4 Strategy / Failure Memory

这部分保存：

- 已执行 query；
- 无效来源；
- fetch error；
- 反爬或登录墙；
- 重复搜索模式；
- scope mismatch；
- 某种策略失败的原因；
- 推荐的替代搜索路径。

例如：

```text
失败：直接搜索“Company X employee count 2025”
原因：结果均为第三方估算
替代：搜索 annual report / ESG report / 10-K
```

这使失败不再只存在于某个子 Agent 的私有轨迹中，而可以成为系统级可复用知识。

---

### 4.5 Writer Outline 与 Budget

Writer 不直接维护一段不断增长的大文本，而是维护结构化 Outline：

```text
Section
  - id
  - title
  - content
  - cited_evidence_ids
  - notes
  - order
```

同时，SOCM 保存：

- query budget；
- time budget；
- iteration budget；
- consumed budget；
- per-agent status。

整个状态持久化到 `workspace/search_state.json`，作为系统的 single source of truth。

## 5. SearchOS 的六阶段工作流

### 5.1 Explore

Explore Agent 负责：

- 判断 query type；
- 找 hub page；
- 识别搜索空间；
- 列出候选实体；
- 建议 schema 和字段；
- 制定初步搜索计划。

Explore 不负责逐实体填值。

如果 schema 尚未创建，Explore 的 summary 会先存入 `pending_agent_summaries`，待 schema 创建后 replay extraction。

---

### 5.2 Schema

Orchestrator 调用 `create_schema()` 建立关系结构。

Schema 定义包括：

```json
{
  "table_id": "programs",
  "attributes": ["university", "program", "deadline"],
  "primary_key": ["university", "program"],
  "column_desc": {
    "deadline": {
      "type": "date",
      "desc": "Official deadline for the specified admission cycle"
    }
  }
}
```

`column_desc` 不只是 UI metadata，而是 extraction specification：它帮助抽取模型判断网页中多个相似数值究竟哪一个属于目标字段。

SearchOS 还会机械检查：

- primary key 是否属于 attributes；
- hard range / enum；
- 单位与数量级冲突；
- 重复 schema；
- 多表关系是否合法。

---

### 5.3 Enqueue / Dispatch

Orchestrator 将 coverage gaps 转换成 Frontier tasks。

一个任务可明确声明：

```json
{
  "task": "Find the official MIT EECS PhD deadline",
  "kind": "search",
  "priority": 0.9,
  "target_table": "programs",
  "target_cells": ["MIT EECS PhD.deadline"],
  "skills": ["university_admissions"],
  "max_searches": 8
}
```

`target_cells` 有两个作用：

1. 限定 Agent 的搜索范围；
2. 让 Scheduler 对重叠任务进行去重。

开放枚举任务由于目标行尚未知，可以省略 target cells；针对已知字段的 backfill 任务应明确填写。

---

### 5.4 Search / Extract

Search Agent 的主要职责是：

- search；
- open；
- find；
- 定位正确页面；
- 给出简要 conclusion。

它通常不直接写 Coverage Map 或 Evidence Graph。

当 Agent 调用 `open` 或 `find` 后，Extraction Middleware 自动：

```text
页面内容
  ↓
Evidence Observation
  ↓
Judge / Extraction Model
  ↓
(entity, attribute, value, source, confidence)
  ↓
Evidence Graph
  ↓
Coverage Map
```

这将“找到网页”和“把网页转化为规范化事实”分开。

---

### 5.5 Assess / Adjust

Orchestrator 定期通过 `check_agents()` 获取 Agent Report，并检查：

- 新增了哪些 evidence；
- 哪些 rows / columns 被填；
- 是否发现新实体；
- 是否有 conflict；
- 是否有 dead end；
- 是否存在空表；
- 是否还有 scope 缺失；
- 是否应重新派发任务。

Agent Report 不是由子 Agent 自己声称，而是通过运行前后 SOCM snapshot diff 自动计算。

---

### 5.6 Write / Synthesize

Writer Agent 从 SOCM 中读取：

- Coverage Map；
- Evidence Graph；
- Writer Outline；
- 缺失项和 caveat。

每个 section 必须携带 `cited_evidence_ids`。因此引用约束被放在工具层，而不是仅靠 prompt 提醒。

Writer 还可以在搜索尚未结束时提前启动，随着新 evidence 增加被继续唤醒，形成搜索—写作流水线。

## 7. Agent Runtime：LangGraph / deepagents

所有角色本质上都运行在同一个受约束的 ReAct loop 上。

核心工厂：

```python
create_search_agent_graph(...)
```

底层调用：

```python
create_deep_agent(
    model=model,
    tools=tools,
    system_prompt=prompt,
    middleware=middleware,
    checkpointer=checkpointer,
)
```

SearchOS 借用了 deepagents 提供的：

- ReAct loop；
- tool calling；
- message state；
- streaming；
- LangGraph thread；
- checkpointer；
- continuation。

每个 Agent 有独立 thread id，通过相同 thread 继续执行，因此可以保留自己的局部对话记忆。

但需要特别注意：

> SearchOS 主动禁用了 deepagents 的大量默认能力。

被关闭或剥离的包括：

- 默认 `task` subagent；
- filesystem；
- shell execute；
- todo；
- compact conversation；
- 默认 Deep Agent prompt。

原因是 deepagents 默认 subagent 会绕开 SearchOS 的中央 Scheduler，破坏：

- 并发限制；
- scope isolation；
- middleware coverage；
- 任务审计；
- 全局状态一致性。

因此，deepagents 在这里主要提供底层 Agent loop，而不是 SearchOS 的核心架构。

## 8. Scheduler：SearchOS 最像操作系统的部分

Scheduler 维护全局 task pool，并统一限制：

- Explore Agent；
- Search Agent；
- Writer Agent；
- continuation。

所有角色共同占用 `max_parallel_agents` 槽位。

Scheduler 负责：

- priority scheduling；
- blocked task unblocking；
- dependency cycle detection；
- task dedup；
- writer singleton；
- zombie task recovery；
- budget-aware dispatch；
- targeted repair allowlist。

### 8.1 Pipeline Parallelism

`check_agents()` 使用：

```python
asyncio.wait(..., return_when=asyncio.FIRST_COMPLETED)
```

不是等待全部 Agent，而是等待至少一个完成。

流程：

```text
先 tick，补满空闲槽位
   ↓
等待第一个 Agent 完成
   ↓
回收所有此刻已完成 Agent
   ↓
读取新报告
   ↓
立即根据新 gap enqueue
   ↓
再次 tick，补位
```

这使搜索任务形成持续流水线，而不是按批次等待最慢 Agent。

### 8.2 为什么 tick 需要锁

多个并行工具调用可能同时触发 `tick()`。若都先读取相同 running count，就可能共同超卖并发槽位。

因此 Scheduler 用 `asyncio.Lock()` 串行化 tick chain，保证全局并发上限不会被突破。

## 9. 三层 Middleware

SearchOS 将 middleware 组织为：

```text
Context → Sensor → Extraction
```

### 9.1 Context Middleware

每次模型调用前，注入与当前角色和任务相关的 SOCM 投影视图：

- target table；
- target cells；
- scoped evidence；
- relevant gaps；
- failure patterns；
- remaining budget；
- recent memory；
- selected skills。

关键点是：

> 不把整个 search_state.json 塞入每个 Agent，而是根据角色和任务做 scoped projection。

---

### 9.2 Sensor Middleware

负责检测：

- 重复 query；
- 重复 URL；
- 无新增 evidence；
- tool loop；
- stall；
- budget；
- writer trigger。

典型策略是：

1. 首次检测时提醒 Agent 换方法；
2. 若继续发生，将 Agent 标记为 looped；
3. Orchestrator 从新角度重新派发任务。

---

### 9.3 Extraction Middleware

核心拦截点：

```python
awrap_tool_call()
```

当前主要抽取：

- `open`；
- `find`；
- `skill_*` 输出。

普通网页使用 buffered extraction，可以批量调用 judge model；Skill 输出通常同步处理。

系统会跳过：

- fetch error；
- 太短内容；
- duplicate content；
- unextractable page；
- schema 尚未建立；
- skill error。

Agent 最终 summary 也会作为 `agent://.../final_summary` 进入 Evidence Intake，但其证据等级通常低于直接页面来源。

---

## 10. Skill 系统

SearchOS 将 Skill 分成三层：

1. **Orchestration Skill**：高层研究方法；
2. **Strategy Skill**：排名、multi-hop、entity disambiguation 等策略；
3. **Access Skill**：针对特定网站、API、登录墙或反爬结构的执行方法。

每次 dispatch 最多加载少量 Skill，避免把整个技能库塞入上下文。

Access Skill 的输出仍然要经过 Evidence Intake，不绕开证据体系。

这意味着 Skill 不是单纯 prompt，而是可以成为：

```text
成功访问经验
→ 可执行访问方法
→ 结构化证据来源
```

## 11. 实验结果的核心结论

论文在 WideSearch 和 GISA 上评估。

最值得注意的是：

- SearchOS 在 headline F1 指标上领先；
- 最大提升出现在 enumeration / Set F1；
- Set F1 相比次优 baseline 提升约 13.4。

这与其归纳偏置一致：

> Coverage Map 会持续驱动系统寻找尚未覆盖的实体和字段，因此主要提升 recall，而不是让单个事实的 precision 出现巨大飞跃。

论文结果使用 `max@3`，因此应谨慎区分：

- 系统最佳潜力；
- 单次运行期望；
- 平均稳定性；
- 成本与 wall-clock。

## 12. SearchOS 与 RLM 的关系

两者最深层的共同点不是“都调用子 Agent”，而是：

> **先构造覆盖整个问题的外部骨架，再持续识别骨架中的空缺并局部补全。**

统一模式：

```text
任务
  ↓
全局结构
  ↓
Gap Selection
  ↓
Local Computation
  ↓
Write-back
  ↓
Replanning
```

可以写成：

\[
S_{t+1}=
\operatorname{Update}
\left(
S_t,
\operatorname{Solve}(
\operatorname{SelectGap}(S_t)
)
\right)
\]

### 12.1 RLM 的全局结构

RLM 主要结构化：

- 超长 context；
- chunk；
- index；
- Python 变量；
- 中间结果；
- pending recursive calls；
- computation graph。

它回答的问题是：

> 下一步应该在哪一部分输入或计算空间中执行局部推理？

### 12.2 SearchOS 的全局结构

SearchOS 主要结构化：

- entity；
- attribute；
- relation；
- missing cell；
- evidence；
- conflict；
- frontier task。

它回答的问题是：

> 最终答案空间中还有哪些信息没有被可靠覆盖？

因此：

```text
RLM 更偏向结构化输入与计算空间
SearchOS 更偏向结构化答案与证据空间
```

可以将 SearchOS 看作一个面向开放域信息检索的、领域特化的 RLM-style system。

---

## 13. 两者的全局结构是否是“世界模型”

可以，但更准确地说，它们是：

> **显式、任务条件化、可更新的认知世界模型。**

它们不是传统强化学习中完整的环境动力学模型：

\[
p(s_{t+1},r_t\mid s_t,a_t)
\]

它们主要建模：

- 当前任务世界由什么组成；
- Agent 已经知道什么；
- 哪些区域仍未知；
- 哪些证据相互冲突；
- 哪些行动仍待执行；
- 当前完成度如何。

SearchOS 的世界模型可以分为：

### 13.1 事实世界

Evidence Graph：

```text
实体—属性—值—来源
```

### 13.2 认知世界

Coverage Map：

```text
known / missing / uncertain / conflicting
```

### 13.3 行动世界

Frontier：

```text
pending / running / blocked / failed / completed
```

可写为：

\[
M_t=(K_t,B_t,Q_t)
\]

其中：

- \(K_t\)：事实与证据；
- \(B_t\)：知识覆盖与信念状态；
- \(Q_t\)：行动队列与依赖。

RLM 的外部环境则更像“计算任务的世界模型”：

\[
M_t=(\text{data layout},\text{computation state},\text{partial results},\text{pending calls})
\]

---

## 14. 为什么它还不是完整世界模型

SearchOS 当前主要是反应式的：

```text
发现空缺
→ 搜索
→ 获取观察
→ 更新状态
```

它尚未显式学习：

\[
P(M_{t+1}\mid M_t,a_t)
\]

即：采取某个搜索动作后，预期会填多少 cell、成功率多少、成本多高。

更完整的模型化调度可以优化：

\[
a^*=
\arg\max_a
\frac{\mathbb{E}[\Delta Coverage(a)]}{Cost(a)}
\]

也就是选择单位成本预期信息增益最高的搜索动作。

这可能是 SearchOS 后续非常自然的发展方向。

## 15. SearchOS 与 Research World Model 的关系

可按时间尺度理解：

### Session-level world model

SearchOS / RLM 当前任务中的：

- coverage；
- evidence；
- pending tasks；
- failed paths；
- partial results。

### Cross-task world model

Research World Model 保存：

- 哪种搜索策略在什么任务上有效；
- 哪些数据源可靠；
- 哪些失败模式会重复；
- 某类研究任务的结构与经验规律。

可以形成：

```text
单次任务中的显式结构化状态
          ↓
多任务经验积累
          ↓
策略压缩 / Skill 提取
          ↓
Research World Model
```

SearchOS 的 Strategy Memory、Failure Memory 和 Access Skills 已经是这一过渡的雏形。

---

## 16. 能否用 Pi Agent SDK 实现 SearchOS

结论：

> **可以。Pi Agent SDK 可以替代 SearchOS 的 Agent/ReAct runtime，但不能自动替代 SOCM、Scheduler、Coverage Map、Evidence Graph 和多 Agent 生命周期。**

### 16.1 能直接对应的部分

| SearchOS | Pi Agent SDK 对应 |
|---|---|
| ReAct loop | Agent / AgentSession |
| LangGraph thread | 独立 Session |
| MemorySaver | SessionManager / JSONL session |
| Explore/Search/Writer | 不同 prompt、tools、extensions |
| Context Middleware | context / before-agent hook |
| Sensor Middleware | tool_call / tool_result / turn_end |
| Extraction Middleware | tool_result hook 或包装后的 open 工具 |
| continuation | 对同一个 Session 再次 prompt / follow-up |
| event stream | subscribe / EventBus |

### 16.2 仍需自己实现

- Frontier priority queue；
- blocked-by DAG；
- dependency cycle detection；
- max parallel agents；
- task dedup；
- pipeline refill；
- writer singleton；
- coverage-triggered writing；
- zombie recovery；
- atomic SOCM；
- conflict resolution；
- stopping logic。

### 16.3 推荐架构

```text
SearchOS Domain Runtime
  - SOCM
  - Scheduler
  - Coverage Map
  - Evidence Graph
  - Failure Memory
  - Writer Outline
          │
          ▼
Pi Agent Runtime
  - Orchestrator Session
  - Explore Session
  - Search Sessions × N
  - Writer Session
  - extensions / tools / events
```

Pi Session 应保存每个 Agent 的局部对话状态；全局 SOCM 应保存在 SQLite、Postgres 或结构化 JSON store 中。

不要把 SOCM 不断追加进 Session message，否则系统会退化回 SearchOS 试图避免的“状态埋在对话里”。

---

## 17. 为什么 SearchOS 选择 LangGraph / deepagents

没有看到作者明确声明“因为更容易”，但从代码结构可以合理推断：

> LangGraph / deepagents 降低了底层 Agent loop、tool calling、streaming、thread、checkpoint 和 continuation 的实现成本。

同时，项目本身已经是：

- Python；
- Pydantic；
- asyncio；
- LangChain tools。

因此继续使用 LangGraph 具有较低集成成本。

但 deepagents 不是完美匹配。SearchOS 甚至要 monkey-patch 掉大量默认功能，这说明：

```text
deepagents 提供：
  Agent loop + messages + tools + checkpoint

SearchOS 自己提供：
  SOCM + roles + scheduler + middleware + evidence + coverage
```

因此 SearchOS 的核心能力主要来自后者，而不是 LangGraph/deepagents 本身。

---

## 18. Pi 与 LangGraph/deepagents 的取舍

| 维度 | LangGraph/deepagents | Pi Agent SDK |
|---|---|---|
| 语言 | Python | TypeScript |
| ReAct loop | 已提供 | 已提供 |
| Checkpoint | LangGraph thread | SessionManager |
| Middleware | AgentMiddleware | Extension hooks |
| Graph / DAG | 较强 | 需自建 |
| 默认 subagent | 有，但 SearchOS 禁用 | 默认极简 |
| Scheduler | 自建 | 自建 |
| SOCM | 自建 | 自建 |
| 自由度 | 中等 | 高 |
| 快速复现 SearchOS | 更容易 | 工作量更大 |
| 极简 Harness 实验 | 略重 | 更合适 |

如果目标是快速复现论文，继续使用当前 Python + LangGraph/deepagents 最合理。

如果目标是验证 SearchOS 的能力是否主要来自显式状态和 middleware，而非具体 Agent framework，那么使用 Pi 重实现很有研究价值。

## 19. SearchOS 最重要的理论启发

### 19.1 从 conversation-centric 到 state-centric

传统 Agent：

```text
我记得我似乎查过这个。
```

SearchOS：

```text
coverage[Stanford][deadline] = MISSING
frontier[task_17] = RUNNING
evidence[e_31].source = official
```

长期能力的来源，不一定是更长 context，而是：

\[
\text{Local Reasoning}
+
\text{Global Scaffold}
+
\text{Stateful Iteration}
\]

### 19.2 将认知负担外部化

模型不再负责“记住整个任务”，只需要：

1. 读取当前相关局部；
2. 做局部推理；
3. 将结果写回；
4. 根据更新后的全局结构选择下一处缺口。

### 19.3 Harness 负责不变量

LLM 决定：

- 搜什么；
- schema 怎么设计；
- 是否换策略；
- 是否需要核验。

代码保证：

- 并发上限；
- 依赖合法性；
- provenance；
- validation；
- task dedup；
- persistence；
- citation IDs；
- budget。

这是非常典型的 Harness Engineering：

> 模型负责柔性决策，Harness 负责必须稳定满足的执行约束。

## 20. 局限与风险

### 20.1 Schema 错误

如果全局框架定义错了，系统可能高效地完成一个错误任务。

\[
\text{completion of representation}
\neq
\text{completion of real task}
\]

### 20.2 Extraction model 单点风险

即使页面正确，抽取仍可能：

- 错配实体；
- 错判年份；
- 错选数值；
- 忽略限定条件；
- 错误归一化单位。

### 20.3 Coverage 不等于 truth

一个 cell 被填，只说明有候选证据，不代表绝对正确。

### 20.4 Orchestrator 认知负担较重

它仍需判断：

- schema；
- granularity；
- priority；
- conflict；
- scope；
- stopping；
- writer timing。

### 20.5 全局状态写入瓶颈

如果大量 Agent 同时向 `search_state.json` 写 evidence，atomic update 可能成为并发热点。

扩展到更大规模时可能需要：

- append-only event log；
- transactional database；
- optimistic concurrency control；
- materialized Coverage Map。

### 20.6 不适合所有任务

SearchOS 的归纳偏置最适合：

- 宽表信息收集；
- 排名；
- 产品比较；
- 市场扫描；
- 尽调；
- 完整枚举；
- 文献表格化提取。

对于理论综合、开放性解释和科学推理，关系表补全不一定足够。

---

## 21. 总体评价

SearchOS 不是新的语言模型推理算法，而是一套较完整的长程信息搜索系统架构。

其最有价值的贡献是：

1. 把开放域搜索重新定义为带引用的 schema completion；
2. 把进度、证据、冲突和失败显式外部化；
3. 将多 Agent 协作变成调度、依赖和资源管理问题；
4. 用 middleware 自动将网页观察转化为共享证据；
5. 用 Coverage Map 将“是否完成”变成可观测状态；
6. 展示了 state-centric harness 对 recall 和长程稳定性的价值。

最核心的一句话是：

> **Search progress should be a first-class system state.**

更一般地：

\[
\text{Long-horizon Agent}
\neq
\text{LLM + Longer Context}
\]

而更接近：

\[
\text{Long-horizon Agent}
=
\text{LLM}
+
\text{Explicit State}
+
\text{Progress Metric}
+
\text{Scheduler}
+
\text{Failure Recovery}
\]

## 22. 我的最终理解

SearchOS、RLM、Global Workspace 和 Research World Model 可以被放在同一条思想线上：

```text
越来越长的自然语言上下文
          ↓
可查询、可更新、可验证的外部工作空间
          ↓
任务级认知地图 / 世界模型
          ↓
基于缺口、证据和预期价值的主动探索
          ↓
跨任务积累的长期 Research World Model
```

SearchOS 的独特之处在于，它为开放域搜索选择了一个非常具体的世界模型表示：

```text
Coverage Map
+ Evidence Graph
+ Frontier
+ Strategy Memory
+ Writer Outline
```

Agent 不再通过“回忆自己的搜索轨迹”判断任务进度，而是直接读取一个可计算的外部任务世界。
