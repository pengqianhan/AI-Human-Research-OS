# Q1 问题定义

* **输入（X）：** 在搜索阶段，输入是另一个运行基础执行框架（Pi）的智能体在两类互不重叠的可执行环境上产生的执行轨迹——495 个源自代码仓库的任务（GitHub issue + 修复前的仓库状态 + 隐藏的回归测试，只保留那些测试在补丁应用前失败、应用后通过的任务）和 40 个"验证器驱动"的合成任务（先构建可执行的成功判据，允许多条有效解题路径，接口风格类似 Terminal-Bench-2），共 535 个环境。在留出评测阶段，输入是一个已冻结的执行框架，加上四个独立的基准测试面：EdgeBench 公开发布的 51 个任务（共 134 个中的一部分）、63 个纯 CPU 的 Terminal-Bench 4 任务、6 道要求用 Lean 4 验证的 IMO 2026 试题，以及一个以 20 个工作智能体组成的"蜂群"运行的内核优化"带回家"基准测试。
* **输出（Y）：** SoL-Pi，一组固定的四种机制（Action Fusion、Online Context Compact、ObservationPack、Evidence-Preserving Reducer），以扩展形式实现在开源 Pi 执行框架之上；按任务记录的 token 流量（拆分为输入/缓存读取/缓存写入/输出/总计，单位十亿 token）、按 2026 年 8 月 17 日固定价格快照计算的 API 成本（美元）、平均任务得分，以及一个派生的 token 效率指标（每单位综合任务得分对应的 API 成本）。
* **核心问题：** 随着编程智能体从单轮补全转向无人值守、工具中介的长轨迹执行，token 成本会随轨迹长度增长而上升，而现有的效率工作（更快的注意力核、量化、使用更便宜的模型）都作用在执行框架层之下。执行框架层的改动是一个可行的效率杠杆，但执行框架的各个组件（工具使用、上下文管理、验证、委托、恢复、终止）彼此紧密耦合，一处局部有益的改动可能把成本转移到后续阶段或破坏能力；人工寻找这类改动难以规模化，而论文引用的一项前人研究（Wang 等人，《Rethinking the evaluation of harness evolution for agents》，arXiv:2607.12227）发现自动演化出的执行框架可能对搜索阶段所用任务过拟合，在留出任务上只有边际收益。因此 SoL-Pi 要解决的问题是：如何以规模化方式运行自动化执行框架发现流程，既能降低 token/成本，又能切实证明其在留出任务和未见过的模型后端上具有可迁移性，而不是对搜索期信号过拟合。
* **范围：** 仅限执行框架层的改动——模型权重全程保持不变；四种机制均以扩展形式实现在同一个特定的开源执行框架（Pi / pi-mono，Earendil Works）之上；开发与搜索均在同一后端（GPT-5.6 Sol）上进行，跨后端迁移测试仅针对另外一个后端（Claude Opus 5），未测试第三个模型家族；留出评测覆盖 EdgeBench 公开的 51/134 个任务、63 个（排除 GPU 相关）Terminal-Bench 4 任务、6 道 IMO 2026 试题，以及一次内核优化蜂群实验——并非广泛的多基准或多后端扫描；论文自己也明确说明其搜索规模数字（"约 150 个提案方向和约 500 个可执行环境……超过 3,000 次运行"）"描述的是我们搜索的规模，并不构成一条 scaling law"。

# Q2 问题新颖性

论文并不声称首创自动化执行框架搜索、RSI 启发式智能体设计，或对执行框架演化的留出泛化问题的关注。它明确建立在 Meta-Harness（Lee 等人，arXiv:2603.28052——在可执行的执行框架程序上搜索，并通过任务表现与上下文成本的帕累托前沿评测其向留出数据集/模型的迁移能力）和 Recursive Harness Self-Improvement / RHI（Lee 等人，arXiv:2607.15524——针对单个任务迭代精炼智能体循环的提示级规范）之上；论文还引用了 AutoHarness（Lou 等人，arXiv:2603.03329——合成特定环境的代码防护，某些情形下合成完整的代码策略）、Agentic Harness Engineering / AHE（Lin 等人，arXiv:2604.25850——从轨迹证据出发演化模块化的编程执行框架组件，并评测其跨任务/跨模型迁移能力），以及 MemoHarness（Huang 等人，arXiv:2607.14159，本 wiki 中已有 [MemoHarness](../papers/2607.14159.md) 笔记——存储执行经验，并在推理时针对具体测试用例调整执行框架配置）。论文自陈的新颖之处，是对 Wang 等人 [20] 过拟合发现的直接回应：SoL-Pi 的贡献不是又一种针对执行框架代码的搜索算法，而是一种架构层面的设计——一个"由宽到深"的漏斗（广度：约 150 个外层提案方向、覆盖约 500 个环境；深度：针对每个候选方案的"提出-实现-审查-修订"循环），围绕一条结构性规则构建：留出结果绝不反馈进搜索（EdgeBench 验证失败只会拒绝该候选方案，而不会触发进一步调优），再加上通过一次性、隔离的搜索谱系实现的可扩展编排（每条搜索都是共享的最小研究循环技能模板的一次性副本，运行结束后除保留的候选方案与证据外全部丢弃）。这与 MemoHarness 的按用例、无反馈的推理时适应不同，也与本 wiki 其他执行框架工程论文（例如 SkillOpt-Lite 的人工把关式补丁-回滚循环）不同——SoL-Pi 把"搜索/验证分离"本身作为被检验的对象，并把 token 效率作为一个受门控约束的一级优化目标，而非仅仅关注任务成功率。

# Q3 科学假设

如果在一个宽泛、多样的提案方向与可执行环境池上规模化运行执行框架层的自动研究，同时满足：(a) 能力与效率指标及其容差在搜索开始前就已固定，并置于优化智能体控制范围之外；(b) 严格的双重门控接受规则（能力指标必须保持在预先声明的容差内，且候选方案必须在至少一项声明的效率指标上有所改善）；(c) 留出评测结果在结构上被阻止反馈回搜索过程——那么所得到的执行框架机制应当能大幅降低 token 流量与成本，同时把任务能力保持在很小的容差范围内，并且——这一点至关重要——应当能迁移到搜索过程中从未使用过的基准和模型后端上，而不是像 Wang 等人 [20] 记录的其他执行框架演化方法那样过拟合。论文自身的证据：在 EdgeBench 上，冻结后的四机制完整版 SoL-Pi（称为 SoL-Pi [Efficiency]）在其 GPT-5.6 Sol 搜索后端上，把总记录 token 流量削减 49.0%、API 成本削减 33.2%，同时保留 Pi 平均得分的 93.7%；而在不做任何进一步搜索或适配的情况下，把这套方案直接应用到 Opus 5 上，在这个未见过的后端上把 token 流量削减 44.7%、成本削减 33.5%，同时保留 Pi 平均得分的 94.3%（第 3.1 节，表 1–2）。

# Q5 关键解法思路

1. **"由宽到深"的搜索漏斗，配合严格的搜索/验证分离（第 2.1–2.2 节）。** 能力指标、容差与效率指标在搜索开始前就已固定，并与优化智能体的控制权隔离，以防止其"钻空子"。候选方案筛选采用两道顺序门控——每项能力指标都必须保持在预先声明的容差范围内，且候选方案必须在至少一项声明的效率指标上有所改善——在通过门控的候选方案中，流水线保留帕累托意义上的非支配结果。EdgeBench 完全保留用于最终验证：执行框架与接受规则在评测前就已冻结，留出验证失败只会拒绝该候选方案，而不会触发进一步的优化。
2. **六大提案家族，构成 152 个外层搜索方向**，在此之前先由一次"Oracle Analysis"（先知式分析）扫描既有开发轨迹，找出基础执行框架中具体、可避免的开销来源：上下文、进度、工具、委托、提示与策略、改进与评测。这些家族按提案的*来源*分类，而非按最终改动落在何处——例如 ObservationPack 源自两个"上下文"家族的假设，但最终修改的是观测边界。每个方向都运行一个自动研究循环（提出 → 实现 → 运行一个固定实验 → 检视 → 保留/修订/丢弃，归功于 Karpathy 的"Autoresearch: the experiment loop"），并在此基础上叠加了一个基于 Anthropic "Ralph Wiggum" Ralph Loop 模式的迭代实现循环：实现者针对一条明确的完成判据不断精炼候选方案，一位独立审查者对其进行检查，审查未通过则触发修订。独立的轨迹分析器（每条探索轨迹配一个，检查重复动作、上下文增长、过大的观测结果或稀疏的诊断信号）将结果汇总给一个"归约器"（reducer），后者综合出候选方案级别的摘要，指导下一轮提案。
3. **一次性、隔离的搜索谱系。** 每次独立搜索都作为一个共享技能模板（内含最小化的研究循环与操作说明）的一次性实例运行；每次实验复制该模板、设置参数、运行至完成，并保留候选方案及其证据，同时丢弃被修改过的编排代码——这就是"可扩展编排"原则，使广度可以通过运行更多隔离循环来扩展，而不会让各候选方案之间的失败相互耦合。
4. **两类互不重叠的搜索环境，与 51 个任务的 EdgeBench 留出集合保持分离**（第 2.3 节）：495 个源自代码仓库的环境（GitHub issue + 修复前仓库状态 + 离线依赖，以已被接受的补丁/变更历史作为参考轨迹，PR 与回归测试对智能体隐藏，只保留那些测试在补丁前失败、补丁后通过的环境）和 40 个"验证器驱动"的合成环境（先编写一个可执行的成功验证器，再围绕它构建任务环境，接口风格类似 Terminal-Bench-2，允许多条有效解题路径）。在 EdgeBench 的 51 个任务中，11 个仅用于对已冻结候选方案的单向接受判定，40 个则完全保留用于最终的泛化评测。
5. **四种被保留的机制，各自作用于智能体-环境交互循环的不同阶段（第 2.4–2.5 节）：**
   * **Action Fusion（动作融合）**——基础版 Pi 经常先编辑一个文件，再单独发出一条命令去测试、构建或运行它；Action Fusion 为文件变更类工具增加了一个可选的"后续命令"字段，使两个动作合并为一次请求发出，其结果一并返回在同一个观测中，把往返次数从 3 次 API 调用降为 2 次。需要先查看变更结果才能决定下一步的命令仍保持独立。
   * **Online Context Compact（在线上下文压缩）**——在每个计划步骤完成时（通过智能体自身调用的 `update_plan` 追踪）重新评估是否需要压缩上下文，而不是只在固定的上下文占用阈值触发。在每个这样的边界点，执行框架根据"已完成步骤之间观测到的请求数"与"未完成步骤数"估计剩余的模型请求量，并用"按已观测增长速率填满当前上下文窗口所需的请求数"给该估计设上限，再把预计节省的输入 token 与重写提示缓存的预计额外成本进行比较；后续的压缩需要更大的节省余量，以弥补此前压缩中未能收回的重写成本。当这一成本门控通过、或上下文用量已接近窗口上限且压缩仍能缩短上下文时，就会调用 Pi 原生的压缩功能。
   * **ObservationPack（观测打包）**——把超过 10 KiB 的工具输出在本地归档，并在接下来的两次向服务商发出的请求中完整发送；从第三次请求起，改为发送一个稳定的检索句柄、原始大小，以及完整头尾若干行的简短摘录，精确内容可按需通过该句柄取回。较小的输出保持不变。
   * **Evidence-Preserving Reducer（证据保全归约器）**——针对来自一组预先定义命令、大小至少 4 KiB 的构建/测试日志（文件读取与搜索结果完全绕过该机制），把原始输出精确归档，并让一个独立的低成本模型（GPT-5.6 Luna，"high" 强度）提炼出一份紧凑的"凭据"（receipt）。一个确定性的验证器会在使用前检查该凭据的模式（schema）、来源哈希、退出状态、精确引用与体积；如果验证失败、疑似包含凭证信息，或该凭据未能带来任何体积缩减，则回退到未经改动的原始日志。该归约器在 ObservationPack 之前运行，ObservationPack 能识别归约器留下的凭据标记并跳过这些结果，以避免对已验证的证据进行二次压缩；辅助模型只负责提炼证据，诊断与动作选择的责任始终留在主智能体一侧。

# Q6 实验设计

**EdgeBench（第 3.1 节，表 1–2）。** EdgeBench 共 134 个任务中公开发布了 51 个，评测使用这一公开子集。表 1 在 GPT-5.6 Sol 后端下比较了八种配置：一行不参与排名的 EdgeBench 官方 GPT-5.5 参考成绩、原生 Codex、四个第三方执行框架（OpenSquilla、Oh-My-Pi、OpenCode、Oh-My-Opencode）、Pi、SoL-Pi [Efficiency]（固定的完整四机制组合）以及 SoL-Pi [Performance]（该后端下平均得分最高的单机制配置，选自表 4 的消融结果——在 GPT-5.6 Sol 下对应 ObservationPack）。表 2 则针对跨模型迁移重复了这一比较：在 GPT-5.6 Sol 上开发出的 SoL-Pi [Efficiency] 被直接（不做任何进一步搜索或适配）应用到 Claude Opus 5 上，与该后端上的原生 Claude Code 及 Pi 相比较；Opus 5 上的 SoL-Pi [Performance] 对应的是 Action Fusion 而非 ObservationPack。

**Terminal-Bench 4 与 IMO 2026（第 3.2 节，表 3）。** 在 63 个纯 CPU 的 Terminal-Bench 4 任务上比较 Codex、Pi 与 SoL-Pi（出于基础设施限制排除了依赖 GPU 的任务），报告解决任务数、总 API 成本以及每个已解决任务的成本。同样三个执行框架还在 6 道 IMO 2026 试题上使用 GPT-5.6 Sol（"xhigh"）进行了比较，要求每个解答都用 Lean 4 形式化并验证（依据 AxiomMath/IMO2026 的形式化题设与 Humanfia 的验证流程），每道题的时间预算上限为 150 分钟。

**内核优化智能体蜂群（第 3.3 节，图 5）。** 一项基于 Anthropic "original performance takehome" 内核优化基准的多智能体实验，以模拟机器周期计分（数值越低越好）。三种配置各运行一次两小时的实验，全部从同一个冻结的、需要 147,734 个周期的起始点开始，使用全新会话且不携带任何早前运行的解答或笔记：单个 Codex 智能体；一个 Codex 协调者搭配 20 个 Pi 基线工作智能体；以及一个 Codex 协调者搭配 20 个使用全部四种机制的 SoL-Pi 工作智能体。协调者与单智能体使用 GPT-5.6 Sol（"xhigh"）；工作智能体使用 GPT-5.6 Luna（"xhigh"）。工作智能体分成 5 组、每组 4 个，各自拥有独立工作空间，并在组内共享一块证据看板；协调者在各组之间传递发现，共享的最优结果只有在协调者提交一个不可变的候选快照、并经独立验证确认为严格改进后才会更新。

**消融与激活模式分析（第 3.4 节，表 4，图 6–7）。** 通过"逐一添加"评测，在两个后端上分别隔离出每种机制的独立贡献（Pi 基线 + 单一机制，与完整组合相比），并给出触发率（机制被激活的任务占比）与触发强度（每个被触发任务的平均激活次数）分析，以及每种机制在自身被触发任务子集上、独立配置与完整组合相比的 token 效率增益对比（论文明确说明这一对比只是描述性的，并不能分离出真正的交互效应）。

**案例研究（第 3.5 节，图 8）。** 追溯了 Action Fusion 长达 27 次迭代的开发谱系，跨越四个阶段（先知式分析、基线构建、提示与工具模式优化——含 18 次探索、最终的留出验证），其中包括智能体自己引入"触发率"作为任务得分之外的中间接受指标这一细节。

**对假设覆盖度的评估强度。** EdgeBench 跨后端迁移测试（表 2）以及 Terminal-Bench 4／IMO 2026／内核蜂群实验，是本文最接近真正泛化检验的部分，因为执行框架、指标与接受规则在这些评测之前均已冻结。有一处真实的不对称性值得特别指出：在 Terminal-Bench 4 上，SoL-Pi 实际解决的任务数（15/63）反而少于 Codex 和 Pi（各自 18/63），因此它在成本上的优势（总成本 $211.12，对 Pi 的 $286.45；每个已解决任务 $14.07，对 Pi 的 $15.91）是伴随着一次真实的能力下降出现的，而不像 EdgeBench 上那样只是容差范围内的权衡。在 IMO 2026 上，Codex 实际通过的题目数（5/6）多于 Pi 或 SoL-Pi（各自 3/6）；SoL-Pi 在这里的优势（每道通过题目 $20.90，对 Codex 的 $22.89）是相对于一个在这项指标上能力相当的对手（Pi）而言的成本优势，而不是相对 Codex 的"能力+成本"双重胜出。

# Q9 贡献

1. SoL-Pi——对 Pi 编程智能体执行框架的一组固定四机制扩展（Action Fusion、Online Context Compact、ObservationPack、Evidence-Preserving Reducer），通过一个"由宽到深"、搜索与验证相分离的自动研究循环发现得到；在两个模型后端（作为搜索后端的 GPT-5.6 Sol，以及完全未参与搜索的 Opus 5）上，都把 EdgeBench 记录的 token 流量削减 44.7%–49.0%、API 成本削减约三分之一，同时保留 Pi 平均任务得分的 93.7%–94.3%。
2. 对 Wang 等人 [20] 关于自动化执行框架演化泛化性批评的一个结构性回应：留出的 EdgeBench 结果在架构上被阻止反馈回搜索过程，执行框架与接受规则在评测前即已冻结，搜索以一次性、隔离的谱系形式运行——并证明其既能迁移到未见过的模型后端（Opus 5，不做任何进一步搜索或适配），也能迁移到完全不同的任务分布（Terminal-Bench 4、IMO 2026、内核优化智能体蜂群），尽管在这三个迁移基准中的两个上存在真实的能力权衡（见 Q6、Q8）。
3. 证据表明，独立搜索发现的各机制在合并后依然保持净收益：四种机制在两个后端下单独使用时都能降低总 token 数，合并后的完整组合在两个后端下都拥有最低的总 token 数与成本（表 4）；并有一个有据可查的案例（Action Fusion，第 3.5 节）显示自动研究过程本身会主动发明出一个事先未指定的中间接受指标（"触发率"）。
4. 一次具体的演示，说明执行框架层的效率增益能在多智能体层面产生叠加效应：在同样的两小时预算下，一个 20 个工作智能体的 SoL-Pi 蜂群在内核优化任务上相对同等规模的 Pi 蜂群把 API 成本降低 26.8%，并通过了全部 8 项速度阈值（Pi 蜂群只通过了其中 7 项，差一步及格）——不过在这三种配置中，单个 Codex 智能体本身的总成本仍是最低的。

# Q10 下一步

论文自陈的局限性（第 5.1 节）：**预训练执行框架（Pre-Training the Harness）**——通过 RSI 式搜索发现的执行框架产物如何泛化，"仍是一个持续存在的挑战"；作者把"扩大可执行环境规模与研究想法多样性"表述为一个他们计划持续检验的假设，并明确类比模型预训练，而非一个已经确立的结论。**多后端训练（Multi-Backend Training）**——当前的执行框架只从 GPT-5.6 Sol 的轨迹中习得，在 Opus 5 上各机制的触发频率与强度都更低（图 6），但被触发时依然带来净收益；作者提出未来可以联合多个后端进行训练与验证，以提升鲁棒性。**递归效率改进（Recursive Efficient Improvement）**——"用更便宜的执行框架资助规模更大的下一轮研究"（更低的单次运行成本让固定预算能覆盖更多环境、轨迹与研究想法）这一构想被明确称为"一个长期研究愿景，而非本研究已证明存在的复合效应"；作者表示计划把 SoL-Pi 本身作为下一轮研究的起始执行框架。**搜索覆盖度与成本（Search Coverage and Cost）**——完整运行自动研究循环在计算上成本高昂，这使得在固定预算下对搜索广度与深度进行受控比较"格外困难"；作者明确将这类 scaling-law 式的系统性研究留给未来工作。

除论文自己列出的这些之外，有三点值得提醒依赖本笔记的读者。第一，Terminal-Bench 4 上的能力短板（解决 15/63，少于 Codex 与 Pi 各自的 18/63）在表 3 中如实报告，但正文并未将其作为局限性讨论——如果读者只依据摘要"表现与 Pi 相当"的说法来理解全文，应当对这一在非 EdgeBench 基准上出现的真实能力回退给予足够权重。第二，跨后端迁移的结论仅建立在单一一对后端（GPT-5.6 Sol → Opus 5）之上；论文未测试第三个模型家族（例如某个开源权重模型，或来自与搜索/留出后端均不同实验室的模型），因此"可迁移到未见过的后端"这一说法应从较窄的意义上理解。第三，内核优化蜂群实验（第 3.3 节）每种配置只运行了一次、为期两小时，未报告重复试验的方差，因此 26.8% 的成本降低以及"7/8 对 8/8"这一阈值结果，都有可能对论文未量化的运行间方差较为敏感——一个自然的后续工作是在多个随机种子下重复这一具体实验，之后再将其幅度视为精确结论。
