> 论文:**Agent READMEs: An Empirical Study of Context Files for Agentic Coding**
> 论文链接:<https://arxiv.org/abs/2511.12884>
> 机构:皇后大学(加拿大)、奈良先端科学技术大学院大学(日本)、泰国农业大学(Kasetsart University)

# Q1 问题定义

* **输入 `X`**:一批智能体上下文文件——即项目根目录下的 Markdown 文件,如 `CLAUDE.md`、`AGENTS.md`、`copilot-instructions.md`,由智能体编码工具(Claude Code、OpenAI Codex、GitHub Copilot)在会话开始时加载,作为持久性的项目级指令;另外还包括每个文件的 Git 提交历史,用于维护性分析。
* **输出 `Y`**:围绕四个维度对这些文件的实证刻画:(RQ1)结构特征(篇幅、可读性、标题层级结构);(RQ2)维护节奏(提交频率、提交间隔、增删行数);(RQ3)一个 16 类的指令内容分类体系及各类别的出现比例;(RQ4)该分类体系能否被大语言模型自动完成。
* **核心问题**:智能体编码工具依赖这些文件来理解一个项目的架构、约定与限制,但官方工具文档只给出高层级的建议(例如"描述架构与工作流程"),因此开发者目前只能靠试错来设计这些文件,缺乏关于什么样的内容、结构、维护方式真正有效的实证依据——论文认为这是一个真实存在、却完全游离于软件文档实证研究文献之外的软件产物空白。
* **范围**:纯观察性研究,且只限定于仓库根目录——文件仅通过精确文件名匹配(不区分大小写的 `CLAUDE.md`、`AGENTS.md`、`copilot-instructions.md`)从 AIDev 数据集(Li et al., 2025b)筛选出的、至少有 5 个 GitHub star 的 1925 个仓库根目录中收集;论文不对任何文件属性是否影响智能体任务表现做因果性主张。

# Q2 问题的新颖性

这是一次扩展而非首次尝试:同一作者团队此前发表于 PROFES'25 的论文(Chatlatanagulchai et al., 2025)只研究了 253 个 Claude Code 文件。本文把这一语料规模扩大约 9 倍(2303 个文件),并新增两种工具(OpenAI Codex 的 `AGENTS.md`、GitHub Copilot 的 `copilot-instructions.md`),使每一项发现都能以跨工具比较的形式呈现,而不再是单一工具的描述;扩大后的多工具语料还催生出两个新的内容类别(Maintenance、Debugging)。放在本知识库 [Context engineering](../topics/context-engineering.md) 主题下看,该主题的其他每一篇论文研究的都是智能体执行期间的*运行时*上下文组装、压缩或状态外置机制,而本文研究的是那个在会话开始之前就先行"播种"该运行时上下文的、静态的、纳入版本控制的指令文件本身——这是该主题下第一篇以此为研究单元的论文。论文自己的 Related Work 部分也划出了类似的边界:既有文献要么研究智能体的内部架构与协作方式(规划、工具使用、多智能体协作),要么研究瞬时的、任务级的提示(思维链、临场指令),而智能体上下文文件是持久的、项目级的、由开发者(而非智能体)在外部撰写的一类产物——论文认为这类产物无论在智能体编码文献还是它同时回顾的经典软件文档文献(README/API 文档研究)中都尚未被大规模研究过。

# Q3 科学假设

如果在多个智能体编码工具之间大规模挖掘并编码智能体上下文文件,将会呈现出单纯依靠试错式撰写无法预见的规律性:(a)这些文件表现为主动维护、增量演进的配置类产物,而非一次写成的文档,这与传统 README 形成对比;(b)其指令内容系统性地偏向功能性/操作性类别(构建、架构、实现),而牺牲了非功能性需求(安全性、性能);(c)这种偏斜并非人工编码噪声的产物,因为一个基于相同类别定义训练的大语言模型分类器能够以有实用价值的准确率复现同样的类别划分,从而使得生态系统级别的自动化监测成为可能。

# Q4 相关工作与关键人物

* **直接前作**:Chatlatanagulchai 等(2025,PROFES'25)——《On the Use of Agentic Coding Manifests: An Empirical Study of Claude Code》研究了 253 个 Claude Code 文件;本文是其明确的、多工具、9 倍规模的后续工作,沿用并扩展了其标签体系(新增 Maintenance、Debugging 两个类别)。
* **与之形成对比的、关于智能体内部架构与协作的文献**:Wang 等(2024,综述)关于软件工程中的智能体;Zhang 等(2024a)的多智能体结对编程(Navigator/Driver 角色);Bouzenia 等(2024)的 RepairAgent;Hassan 等(2025)的《Agentic Software Engineering: Foundational Pillars》——论文的 Related Work 认为这些工作研究的是智能体如何进行内部推理与协作,而非它们如何从外部被配置。
* **与之形成对比的传统文档文献**:Gaughan 等(2025)关于 README/CONTRIBUTING 文件引入情况的研究,发现传统文档是"一次写成"的,后续只有少量修改;Prana 等(2019)关于 README 内容分类的研究;Aghajani 等(2018、2019、2020)关于文档反模式与从业者视角的研究——本文 RQ2 的发现(67.4% 的 Claude Code 文件被多次提交修改)被明确设计为与这类"一次写成"发现相对照的证据。
* **与之形成对比的上下文工程文献(任务级而非持久级)**:Shin 等(2023)关于提示工程与微调的比较;Li 等(2025a)的《Understanding Prompt Management in GitHub Repositories》;Shrivastava 等(2022)的仓库级提示生成——论文把自己定位为第一篇研究这些任务级上下文工程技术最终会被嵌入其中的那个*持久的、项目级*产物本身的实证工作。
* **作者/机构**:皇后大学(加拿大金斯顿)——Hao Li、Bram Adams、Ahmed E. Hassan;奈良先端科学技术大学院大学(日本)——Yutaro Kashiwa、Brittany Reid、Hajimu Iida;泰国农业大学——Worawalan Chatlatanagulchai、Kundjanasith Thonglek、Pattara Leelaprute、Arnon Rungsawang、Bundit Manaskasemsak。

# Q5 核心解法

* **语料构建**:通过 AIDev 数据集(Li et al., 2025b)识别使用智能体编码工具的仓库,筛选出至少有 5 个 GitHub star 的仓库(共 8370 个候选,以排除玩具项目),再用 GitHub REST API 在每个仓库根目录中不区分大小写地匹配 `CLAUDE.md`、`AGENTS.md`、`copilot-instructions.md`,最终得到跨 1925 个仓库的 922 个 Claude Code 文件、694 个 OpenAI Codex 文件、687 个 GitHub Copilot 文件。
* **RQ1(结构特征)**:用 `\w+` 正则统计词数,用 Flesch Reading Ease 衡量可读性,统计各级 Markdown 标题(H1 到 H6)的数量分布;工具间差异用 Mann-Whitney U 检验与 Cliff's delta 效应量检验。
* **RQ2(维护情况)**:挖掘每个仓库中对上下文文件做出新增/删除/修改的每一次提交,记录时间戳与每次提交的增删行数(共计 5655 次 Claude Code 提交、2767 次 OpenAI Codex 提交、2237 次 GitHub Copilot 提交),再用同样的统计检验比较提交数量、提交间隔、增删行数在不同工具间的分布差异。
* **RQ3(内容分类体系)**:两阶段人工编码。第一阶段(标签创建):从 Claude Code 文件中提取所有 H1/H2 标题,提示三个大语言模型(Claude Opus 4.1、Gemini 2.5 Pro、GPT-5)生成候选类别标签,由一名作者筛选、两名作者复核,最终收敛为 16 个类别(在此前 14 类方案基础上新增 Maintenance、Debugging)。第二阶段(标签分配):两名标注者独立地对 332 个 Claude Code 文件按 16 个类别做多标签标注(共 2227 次标注,原始一致率 80.3%,438 处分歧),由第三名标注者裁决分歧,最终得到 2069 条标签分配。
* **RQ4(可自动化程度)**:把同一个 16 类方案构造成多标签二分类任务;向 GPT-5 提供完整文件内容以及每个类别的描述与代表性示例,把预测结果与 RQ3 的人工标注真值对照,计算每类的精确率/召回率/F1,以及按支持样本数加权的微平均。

# Q6 实验设计

纯观察/描述性研究——没有任何干预或消融实验,只有跨工具的统计比较(Mann-Whitney U,alpha=0.05,配合 Romano 等 2006 给出的 Cliff's delta 效应量阈值)以及分类器与人工真值的对照评测:

* **RQ1**:Claude Code(中位数 485 词)与 GitHub Copilot(535 词)在篇幅上彼此无统计学显著差异,但都显著长于 OpenAI Codex(335.5 词,小效应量,d≈0.21-0.22)。可读性方面:Claude Code 最难读(FRE 中位数 16.6,属于"非常困难",可比作密集的法律或学术文本),GitHub Copilot 次之(26.6,相对 Claude Code 为小效应量,d=0.24),OpenAI Codex 最易读(39.6,"困难";相对 Claude Code 为中等效应量,相对 Copilot 为小效应量)。结构方面:各工具的 H1 数量中位数均恰好为 1,H2 数量中位数为 6-7;Copilot(H3 中位数 12.0)与 Claude Code(11.0)比 Codex(9.0,小效应量)更细致;H5 及以上标题几乎不存在(H5 仅出现在 6 个 Claude Code 文件中,H6 完全没有出现)。
* **RQ2**:67.4% 的 Claude Code 文件被多次提交修改(对比 Copilot 的 59.7%、Codex 的 59.2%);Claude Code 收到的提交数显著多于另外两种工具(相对 Copilot 为中等效应量,d=0.35;相对 Codex 为小效应量,d=0.15)。提交间隔中位数:Copilot 约 70.7 小时(约 3 天),Claude Code 约 24.1 小时,Codex 约 22.0 小时(后两者约 1 天),两两差异均显著(p<0.001,Copilot 与 Claude Code 之间效应量最大,达中等水平 d=0.37)。删除量在各工具间普遍可忽略不计(中位数低于 15 词);新增量更大且更具变异性,其中 Claude Code 每次提交的新增词数中位数(57 词)最大,不过效应量可忽略。
* **RQ3(Table 3,基于 332 个 Claude Code 文件子集)**:出现比例最高的类别是 Testing(75.0%)、Implementation Details(69.9%)、Architecture(67.7%)、Development Process(63.3%)、Build and Run(62.3%);出现比例最低的是 Project Management(5.4%)、UI/UX(8.7%)、Performance(14.5%)、Security(14.5%)。
* **RQ4(Table 4,GPT-5 对照人工标签,共 2069 次标注)**:微平均精确率 0.73,召回率 0.86,F1 0.79。表现最好的类别:Testing(F1 0.94)、Implementation Architecture(0.93)、Build & Run(0.92)、Implementation Details(0.89)、System Overview(0.89)。表现最差的类别:Project Management(0.42,支持样本仅 18 条)、AI Integration(0.48)、Documentation(0.57)、Quality/Maintenance(0.56)、UI/UX(0.56)。

# Q8 证据质量

内部效度处理得比较合理:RQ3 的标注采用两名独立标注者加第三方裁决的流程,论文透明地报告了原始一致率(80.3%),而非只给出裁决后的最终数字。作者自己在 Construct Validity 一节中指出了一个与解读 Table 3 直接相关的真实局限:类别标注是二元的"有/无",因此一个文件中只有一行提到代码风格,与另一个文件中有大段详尽的风格指南,会被记为完全相同的"存在"——报告出的百分比衡量的是主题的*出现比例*,而非覆盖的深度或质量。外部效度方面,论文也自我承认存在局限:只扫描了三种工具、只扫描了根目录文件(某些工具支持的子目录级上下文文件被结构性地排除在外),而且 ≥5 星的筛选条件会偏向更成熟、更受关注的开源仓库,而非能代表所有智能体编码使用场景的样本(例如私有/企业仓库完全不在其中)。RQ4 的评测在一点上方法论上是干净的,值得明确指出:虽然第一阶段用三个大语言模型(包括 GPT-5)辅助*生成候选类别标签*,但用于评测 RQ4 中 GPT-5 分类器的真值标签完全来自第二阶段"两名人工标注者加裁决"的流程,因此 RQ4 的评测并不存在用 GPT-5 早期阶段的输出去循环验证 GPT-5 自身的问题。RQ4 的错误模式(在具体、高频的类别上 F1 高,在抽象或稀有的类别上 F1 低,尤其是仅有 18 条支持样本的 Project Management)与一个受样本量限制的多标签分类器的预期表现是内部一致的,这也从侧面说明报告出的数字不太可能是过拟合的结果。

# Q9 主要贡献

1. 第一篇大规模、跨多种工具(Claude Code、OpenAI Codex、GitHub Copilot)的智能体上下文文件实证研究,挖掘了跨 1925 个仓库的 2303 个文件——相较于同一作者团队此前的单工具研究,规模扩大了 9 倍,工具覆盖翻倍。
2. 确立了智能体上下文文件按标准可读性指标衡量普遍篇幅较长、"非常难读"(FRE 中位数依工具不同介于 16.6 到 39.6 之间),组织为一致的浅层单一 H1 层级结构,并且——与所引文献显示传统 README 文档基本是"一次写成"不同——它们被主动且增量式地维护(67.4% 的 Claude Code 文件被多次提交修改,提交间隔中位数为 1 到 3 天,主要通过小幅新增而非删除来演进)。
3. 从真实文件内容中构建并验证了一个 16 类指令分类体系,量化出一个具体、可行动的内容缺口:功能性类别(Build and Run、Implementation Details、Architecture、Testing)的出现比例达 62-75%,而非功能性需求类别(Security、Performance、UI/UX)的出现比例均低于 15%。
4. 证明这个 16 类分类体系可以被以有实用价值的准确率自动化(GPT-5,微平均 F1 0.79),为未来在不依赖穷尽式人工编码的情况下,对智能体上下文文件实践做生态系统规模、纵向的持续监测提供了可能——同时也指出了自动化目前失效的地方(抽象、低频的类别,如 Project Management)。

# Q10 下一步

* 作者提议把"上下文债务(context debt)"定义并量化为一种专属于智能体面向配置文件的新型技术债务,并建议构建持续集成(CI)集成的检查器,核验文件中声明的构建与运行命令(出现比例 62.3%)是否仍与实际的 `package.json`/`Makefile` 一致——这是论文提出但并未实现的一种自动化协同演进检查。
* 他们呼吁建立新的基准或评测框架,显式测试智能体对其上下文文件中声明的非功能性需求的遵从程度(目前诸如 SWE-bench 之类的基准只奖励功能正确性,因此本文记录的安全性/性能盲区目前没有任何基准压力去纠正它)。
* 面向工具开发者,他们建议提供预填充了这 16 个已识别类别的模板脚手架(并显式留出非功能性需求的占位符),以及具备类别语义感知能力的上下文检索(例如把调试类任务路由到 Debugging/Testing 相关段落,而非对整个文件做朴素的文本分块)。
* **对本知识库的启示**:本文对一个自身根目录指令链条(`INSTRUCTION.md`/`CLAUDE.md`)恰好就是本文所研究这类产物的知识库而言具有直接的自我指涉意义。其 16 类分类体系为审计本知识库自身的上下文文件提供了一份具体的、有实证依据的检查清单(例如是否存在任何安全性/性能相关指导,对照本文记录的盲区);其"健康的上下文文件通过小幅、频繁的增量演进,而非大规模重写"这一发现,也与本知识库自身迭代式维护指令文件的实践相符。这是本知识库目前唯一一篇专门研究智能体上下文文件静态内容本身(而非运行时上下文管理机制)的条目,因此它被归入 [Context engineering](../topics/context-engineering.md) 主题,作为该主题内一个新的、互补的视角,而非与某个直接的同类条目并列。
