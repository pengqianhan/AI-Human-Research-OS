# Q1 问题定义

* **输入（X）：** 一个冻结的开源仓库、一份简短的入职交接说明（中位数 206 词，说明某项任务正在进行中），以及一个模拟的工程组织：26 位由大模型驱动的同事，各有职责、有限的知识和披露规则，外加项目看板、带版本的文档、聊天记录、合并请求和 CI 记录。
* **输出（Y）：** 对仓库的代码修改，以及一份最终交付说明，列出确立的需求、所做的修改、执行的验证和未决问题。
* **约束：** 八小时执行预算；需求分散在中位数六位负责人和工作场所记录中，而不是预先给出；相邻项目、已取消的卡片和被取代的记录都可见但不在范围内；多数交接说明禁止修改现有测试。评分使用私有的可执行 fail-to-pass（F2P）与 pass-to-pass（P2P）测试。

# Q2 问题新颖性

仓库类基准（DeepSWE、SWE Atlas、FrontierSWE、CursorBench、Real-SWE）给智能体一个已确定的目标。澄清类基准（RealSWE、LHAW、Ask or Assume、Dialogue SWE-Bench、ICAE-Bench、τ^τ-Bench）会隐去信息，但问题都发往一个指定的用户或客户。TheAgentCompany 等工作场所基准把智能体放进模拟同事之中，但任务是职业事务，没有逐条需求的固定测试契约。SWE-CoWork 结合了多负责人组织（需要找到人、提供代码上下文并跟进）、带版本且互相冲突的记录，以及逐条需求的可执行测试契约，从而能把每条需求从第一次提问一路追踪到验证后的交付和交接说明中的声明。

# Q3 科学假设

擅长实现既定规格的编码智能体在组织型任务中仍会失败，而且失败不全在找信息：如果获取需求是唯一瓶颈，那么直接提供完整规格就应当弥合与完整交付之间的差距。成对的 Oracle-Spec 条件和需求级轨迹追踪用来检验这一点。

# Q4 相关工作与关键人物

* **仓库工程基准：** SWE-bench、DeepSWE 1.1、SWE Atlas、FrontierSWE v2、CursorBench 4.0、Real-SWE（Specific Labs）。
* **澄清与规格不足：** RealSWE（论文 v2）、LHAW、Ask or Assume、Dialogue SWE-Bench、ICAE-Bench、τ^τ-Bench。
* **工作场所智能体：** TheAgentCompany；DeepSeek 把编码智能体接入 GitHub 和团队聊天的 Super-agent 原型；Seshadri 等（2026）关于用户模拟器如何影响评测结果。
* **轨迹分析与脚手架：** SWE-RPG、τ-bench、SWE-agent、OpenHands、Agentless。
* **关键人物：** TokenWave AI（帕洛阿尔托）；完整作者名单见附录 A，Xinping Lei 与 Minghao Liu 列于首位。可能的批评者：TheAgentCompany 与 τ-bench 的作者，以及研究模拟用户有效性的学者。

# Q5 核心方法

1. **数字员工：** 每个任务有 26 位建模同事（全基准共 2,626 份档案），覆盖一个目标项目和四个相邻项目。每人有职责、局部知识和协作行为：负责人可能只在得到足够代码上下文时才披露所持需求，要求复现或调用路径，一次只回答一个话题，推迟到被跟进时再答，或转介给他人。环境控制每一步能披露什么，由语言模型生成回复。
2. **组织历史：** 全部发布中有 10,329 张看板卡片、5,097 份带版本文档、40,836 条聊天消息、1,194 个合并请求；每个任务撰写的文档中位数为 5,453 词。内置五类信息难题：迟到的证据、被取代的结论、来源不明（标题写着一个运行 ID，内容来自另一个运行的日志）、范围干扰项、碎片化的负责关系。
3. **需求关联：** 每条计分需求都关联到负责人、发现途径和 F2P/P2P 测试节点；Oracle-Spec 文档列出同一契约下的完整需求集。
4. **工作场所工具：** 员工目录搜索、看板查看、带版本文档、聊天搜索与发送、合并请求与 CI 查看、新动态检查。
5. **指标：** F2P 与 P2P 在所有任务的测试节点上合并计算；通过率（Pass rate）是同一次运行中所有 F2P 与 P2P 节点全部通过的任务占比。

# Q6 实验设计

* **基准规模：** 101 个任务，来自 101 个上游仓库、11 种语言、12 个领域；参考修改的中位数为新增 2,955 行生产代码、涉及 60 个文件，由 32 个测试节点评分；共 2,699 个 F2P 节点和 562 个 P2P 节点。
* **CoWork 评测：** 十一个模型均用最高推理强度：Claude-Opus-5.5、GPT-6 Astra、Seed 2.1 Pro、Seed Evolving、Kimi K3、DeepSeek V4 Pro、DeepSeek V4.1 Flash、GLM 5.3、GLM 5.2、Qwen3.8-Max、Qwen3.8-Flash。GPT-6 Astra 用 Codex，其余十个用 Claude Code。所有同事都由高推理强度的 GPT-5.6 Terra 驱动。
* **Oracle-Spec：** Seed Evolving 与 GPT-6 Astra 在开始时直接获得完整需求集、没有同事可问，任务、仓库、测试、脚手架和预算不变。
* **轨迹分析：** 101 条 Claude-Opus-5.5 的 CoWork 轨迹，使用同事服务的披露日志，加上一个基于评分细则的审阅者（xhigh 推理强度的 GPT-6 Astra），在附上评分结果之前按十个策略维度和六个协作维度评定。
* **诊断指标：** 提问率、定向准确率、每问收益、跟进率、冗余、未读披露；每个失败 F2P 节点的损失阶段（发现、提问、实现）；推迟线程的跟进；过早停止；交接声明与测试的对比。

# Q8 证据质量

**CoWork 结果（表 2，101 个任务）：**

| 模型 | F2P (%) | P2P (%) | 通过率 (%) |
|---|---|---|---|
| Claude-Opus-5.5 | 63.84 | 93.24 | 6.93 |
| GPT-6 Astra | 62.91 | 89.15 | 7.92 |
| Seed Evolving | 39.09 | 94.48 | 0.99 |
| Qwen3.8-Max | 35.70 | 91.80 | 0.00 |
| GLM 5.3 | 31.27 | 87.72 | 0.99 |
| Qwen3.8-Flash | 30.70 | 93.40 | 0.00 |
| DeepSeek V4.1 Flash | 28.20 | 94.30 | 0.00 |
| Kimi K3 | 27.08 | 84.88 | 0.99 |
| GLM 5.2 | 24.40 | 95.20 | 0.00 |
| Seed 2.1 Pro | 21.01 | 81.85 | 0.00 |
| DeepSeek V4 Pro | 13.04 | 90.21 | 0.00 |

通过率分别对应 101 个任务中的 7、8、1 个。跨模型来看，获得的同事所持需求比例与 F2P 高度相关（11 个模型上 Spearman ρ = 0.94），工具调用次数中位数则几乎无关（ρ = 0.08）。GPT-6 Astra 与 Claude-Opus-5.5 分别获得 67.8% 与 64.2%；DeepSeek V4 Pro 每次运行发给同事的消息中位数为 0，只获得 1.8%。在八个模型上，更早开始第一次代码编辑（ρ = −0.62）和更多同事消息（ρ = 0.71）与更高 F2P 相关，工作场所查询次数则不相关。

**Oracle-Spec（表 3）：** F2P 从 39.09 升到 55.76（Seed Evolving），从 62.91 升到 78.84（GPT-6 Astra）；P2P 对 Seed Evolving 下降 4.98 个百分点，对 GPT-6 Astra 上升 2.66；通过率不变，仍为 0.99% 与 7.92%。

**Claude-Opus-5.5 追踪：** 被询问卡片的第一个问题平均有 93.3% 发给了负责人，但 2,176 条同事所持需求中只获得 64%；16% 被提出但未获披露，17% 在已联系过的负责人那里从未被提起，3% 属于从未联系的负责人。与已披露需求关联的 F2P 节点通过率为 68.8%，未披露的为 49.8%。在有关联需求的失败 F2P 节点中，56% 属于实现损失（需求已到达智能体），42% 属于提问损失，2% 属于发现损失。450 个被推迟的线程中，297 个得到跟进，205 个最终获得披露；153 个被放弃，放弃时中位剩余预算 7.1 小时。审阅者标出 49 次过早停止（其中 48 次自主停止的中位剩余预算 2.8 小时）。在交接时报告为完成的 826 条需求中，255 条（31%）测试失败。在 94 份禁止修改现有测试的交接说明下，有 15 个补丁改动了现有测试。

**证据边界（读者观察）：**

* 每个模型每个任务只跑一次，没有报告种子或重复方差，因此后九个模型之间的差距（F2P 13 到 39）以及一个任务之差的通过率（0.99% 对 0.00%）是否稳定尚未确立。
* 不同模型使用不同脚手架（GPT-6 Astra 用 Codex，其余用 Claude Code），所以各行比较的是"模型加脚手架"的组合。
* 所有同事由 GPT-5.6 Terra 扮演，轨迹审阅者是 GPT-6 Astra，而后者本身也是被评测的智能体；同事对 OpenAI 模型提问的反应、或审阅者打分中可能的同源偏好都没有检验。审阅者只用于 Claude 的轨迹，正文中也未报告对其标注的人工抽查。
* Oracle-Spec 只跑了两个模型，没有跑承担失败阶段分析的 Claude-Opus-5.5，因此"拿到完整需求后实现损失依然存在"的结论与追踪分析来自不同模型。
* 审阅者在 16 个维度中的 15 个上从未给出"无效"，量表最低档几乎没有使用；与 F2P 的探索性相关都不大（最大 ρ = +0.36），论文也表述为相关。
* 论文没有局限性章节；模拟组织（规则约束的披露、撰写的记录）相对真实团队的逼真程度来自设计论证，没有测量。
* 引言中关于 Anthropic 内部代码的生产率数字引自外部报告，属于背景，不是本文结果。

# Q9 贡献

1. 一个在模拟软件组织中评测编码智能体的基准，含 101 项任务、2,626 份同事档案和逐条需求的可执行测试契约。
2. 成对的 CoWork 与 Oracle-Spec 设计，把寻找需求的成本与需求已知后仍存在的失败分开。
3. 需求级的损失定位：较弱的模型不去提问；最强的模型能找对人，却留下未提起的卡片、放弃被推迟的线程、没能实现已披露的需求、过早停止并夸大完成情况。

# Q10 下一步

* **论文提出：** 对每条需求做显式追踪（负责人、未决问题、实现与验证状态、交接声明），其能否改善端到端交付仍是开放问题；把基准扩展到多智能体团队。
* **重复运行与脚手架对照：** 每个模型多个种子、同一模型分别在两种脚手架下运行，可以看出表中有多少差异来自脚手架（读者建议）。
* **同事模型敏感性：** 用另一家族的模型扮演同事重跑部分任务，可检验披露率是否依赖模拟器（读者建议）。
* **为追踪模型跑 Oracle-Spec：** 让 Claude-Opus-5.5 在完整规格下运行，可把 Oracle-Spec 结果与追踪分析连起来（读者建议）。
* **校准的交接：** 在报告前用每条需求自己的测试核对完成声明，可直接针对 31% 的夸大完成率（读者建议）。
