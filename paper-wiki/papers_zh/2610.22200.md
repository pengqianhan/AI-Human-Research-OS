# Q1 问题定义

* **输入（X）：** 一项以指令给出的计算机任务、计算机状态 s_t，以及运行在 OpenGCUA harness 中的冻结前沿模型。每一步模型看到自己的工作状态 m_t（计划、进度记录、保留的观察）和上一步的观察 o_t。
* **输出（Y）：** 每一步联合做出三个决定，(q_t, p_t, m_{t+1}) ~ π_θ(· | m_t, o_t)：请求哪些额外视图（q_t ⊆ {截图, 无障碍树}，可以为空）；一个程序 p_t，其语句调用 GUI、无障碍（accessibility）、shell 和 API 原语，可以使用循环、分支和变量；以及更新后的工作状态。执行 p_t 得到下一个计算机状态和执行输出 e_t；下一步观察是 e_t 加上所请求的视图。就整个任务而言，输出是最终的计算机状态，由基准的评估器打分。
* **衡量什么：** OSWorld-v2 的部分得分（partial score）和全任务成功率，以每任务步数（模型调用次数）和输出 token 作为效率指标；在真实 Mac 上衡量任务完成情况、步数、输出与推理 token，以及估算的美元成本。
* **约束：** 这次发布不训练模型。一切都通过现有模型周围的提示、工具接口和执行运行时完成；OSWorld-v2 只跑离线子集，使结果不依赖外部网站。

# Q2 问题新颖性

计算机使用本身不是新问题；论文的主张是其问题框架已经改变。多数文献把计算机使用智能体看作纯 GUI 智能体（输入截图，输出鼠标和键盘操作），而前沿系统已把 GUI 交互与 shell 命令、无障碍访问和工具结合起来，OpenAI 的计算机使用指南也开始推荐把 GUI 操作写成代码。问题于是变成：一个系统能否用任何可行的手段，在真实计算机上把工作完成好。

*通用计算机使用智能体*（generalist computer-use agent，GCUA）一词沿用 [Agents' Last Exam](../concepts/agents-last-exam.md) 的系统级视角，后者把智能体分为五层（模型、GUI 感知、编排、工具、运行时）。论文的细化是按*由谁做决定*而不是按有哪些层来定义 GCUA：一个五层俱全的系统，仍可能在一条 shell 命令就能解决的地方点击十几个界面。在其形式化中，GUI 智能体、CLI 智能体、多智能体混合系统，以及作者自己的批量 GUI+CLI 智能体（Qwen-UI-Agent），都是事先固定了三个决定中一个或多个的受限情形（表 1）。要做开放项目，是因为 GPT-6 Astra 这样的前沿 GCUA 是封闭的：权重、提示、真实设备 harness、设备 SDK 和轨迹都无法获得。

# Q3 科学假设

如果模型把每一步写成覆盖所有接口的程序，让中间结果在一次调用内决定后续操作，并且把部分工作流决定（何时看屏幕、如何记录进度）从固定的 harness 规则移交给模型，那么与批量 GUI 动作相比，前沿模型会以更少的模型调用完成更多计算机任务；而且即使 GUI 和 shell 访问相同，代码执行仍然有帮助。另一个设计层面的主张是：随着模型变强，harness 的控制权应当移入模型，由 harness 提供机制、由模型决定何时使用。

# Q4 相关工作与关键人物

* **开源计算机使用基础设施。** trycua 的 cua（跨平台驱动和沙箱，其 Cua Driver 被 macOS 适配器原样使用）、Agent S 系列，以及 Open Computer Use（以 MCP 封装的桌面运行时）。
* **基准。** OSWorld 2.0 / OSWorld-v2（Yuan 等，2026），见 [OSWorld](../concepts/osworld.md)。
* **关键人物。** 阿里巴巴 Token Hub 的 MAI-UI 团队：Hanzhang Zhou、Long Li、Quyu Kong、Lei Wang、Panrong Tong（共同贡献），以及 Steven Hoi 和通讯作者 Yue Wang。可能的批评者：OSWorld 2.0 的作者，他们会问离线子集和"选定运行"与官方协议是什么关系；以及其他混合智能体（CoAct-1、UltraCUA、StateAct）的作者，论文讨论了这些系统但没有运行它们。

# Q5 关键解决思路

**以代码执行作为动作格式。** 系统提示要求每一步在 `<code>` 块中给出一个 Python 程序。在 OSWorld-v2 上，程序可以调用 PyAutoGUI 做桌面输入、调用 `bash()` 函数执行 shell 命令；真实设备的提示还加入了用于浏览器的 Playwright。harness 对程序做语法检查后运行，并返回标准输出、标准错误和状态。论文把它与批量动作对比：批量在第一个动作运行前就已固定，而程序可以根据发生的情况分支（若弹出对话框则关闭）、循环（每行填三个字段）和断言（状态现在显示为 Saved），于是十几次往返变成一次。用论文的话说，批量就是没有控制流的程序。论文从 GPT-6 Astra 的轨迹中归纳出五种反复出现的模式：跨接口组合（点击后先检查输出文件，再进行下一次点击）、对运行时确定的目标循环（访问网站的七个栏目，每个都通过 DOM 检查）、依赖结果的执行（只有复制出的草稿与保存的版本一致时才点击发送）、准备观察（先把 3D 物体的 25 个裁剪视图拼成一张联系表再看）、可执行的验证（修改两页幻灯片背景后，检查其余 64 个包内条目未变）。

**从 harness 到模型的决策移交。** 原则是"机制在 harness，决定在模型"。这次发布包含三种由模型发起的机制：

* *按需观察。* `screenshot()` 调用让模型决定下一步输入是否包含新截图。环境仍然每步都截图留档；变化的只是模型收到什么。
* *任务状态追踪。* 一个 `todo` 账本（`todo.update()`、`todo.list()`）记录进度、事实和未决问题，用状态区分待办、已尝试的改动、`changed_unverified`（已改未验证）和 `claimed_verified`（声称已验证）。这些条目是模型自己的判断，并不检查环境。
* *动作意图。* 每个程序之前的 `<intent>` 块说明它应当改变什么、保留什么（例如用一句话概括一个更新 29 条 CRM 线索状态的 64 行程序），主要是为了让真实设备上的用户能看懂智能体在做什么。

两条上下文策略仍由 harness 掌握：*滚动截图缓冲区*分批删除较旧的图片，使缓存的提示前缀变化得更少；*微压缩*（micro-compaction）分批把较旧的工具输出替换为简短占位符（见[上下文压缩](../concepts/context-compaction.md)）。

**从基准到用户的电脑（第 4 节）。** 论文列出真实机器与基准的五点不同：用户与智能体共享指针、键盘和焦点；窗口会在模型思考时打开、移动和相互遮挡；请求会在任务中途改变；相关的窗口或标签页不一定在前台，所以桌面截图可能显示错误的页面；任务开始时电脑里已有文件、标签页和会话。应对分两部分。

* *跨设备 SDK* 把每个操作绑定到一个明确的资源（设备、应用、窗口、标签页），其句柄即使在焦点变化后也保持指向原目标。它把无障碍（`ui.ax`）和视觉（`ui.vision`）作为两种独立的观察与操作方式，并把在程序中捕获观察（`observe()`）与把观察交给模型（`mu.emit`）分开。平台特有的功能放在命名空间里（`.android`、`.macos`、`.browser`），一个程序可以协调多台设备，例如用 `mu.files.copy`。
* *五层真实设备 harness*（模型、带持久解释器的运行时、设备 SDK、驱动、应用与操作系统）。它优先使用元素级的无障碍操作，其次是针对窗口的坐标输入，最后才是与用户协调后的前台输入。它把无障碍树过滤成一个用 `parent_id` 相连的扁平列表，并在保留的快照上提供 `search`、`page` 和 `read`；`ask_user` 接口处理澄清、登录和对重要操作的授权。动作成功送达不被当作任务层面效果已发生的证据。

# Q6 实验设计

* **基准与协议。** OSWorld-v2 v2.1 的 82 个离线任务子集（排除 26 个需要联网的任务），沿用 GPT-6 Astra 发布时的协议。任务分数是评估器给出的平均部分得分（0-100）；归一化得分高于 0.999999 才算成功。每次运行中，每个任务保留最后一次有评估结果的尝试，而不是最好的一次。步数和 token 对所有任务（含失败）取平均，跨模型均值对各模型等权，相对降幅先在每个模型内计算再求平均。
* **模型。** Claude Opus 5、GPT-6 Astra、Gemini 3.8 Flash、Qwen3.8-Max、Qwen3.8-Flash、Kimi K3、DeepSeek-V4.1-Flash、GLM-5.3-Flash。
* **比较。** (1) 纯 GUI 批量动作对完整配置，八个模型（表 2）；(2) 批量 GUI+CLI 对完整配置，四个模型（表 3）；(3) 代码执行消融，比较单动作 GUI、批量 GUI、批量 GUI+CLI 和代码执行，三个模型（图 6）；(4) 决策移交消融，在代码执行基础上逐一加入各机制，再全部加入，两个模型，并报告缓存命中率（表 4）；(5) 对记录下的完整配置运行，事后施加每任务的金钱和时间上限（图 7）。
* **真实设备。** 四个 macOS 任务：一个含比赛规则、七个示例和 125 道题的工作簿；用合成资料填写一份四页的申根签证表；在亚马逊上对 22 种零食做饮食限制调研（不下单）；以及一项带约束的实时酒店比较。七种模型配置，每种最多三次运行；表 5 报告其中五种，每个任务取第 1 次运行。案例研究使用同一 harness 下较早的低推理强度轨迹。
* **未包括。** 没有训练模型；OSWorld-v2 上没有重复运行或方差（正文提到"选定的运行"，但没有说明如何选定）；没有在同一划分上运行外部混合智能体（CoAct-1、UltraCUA、StateAct）；没有受控的墙钟时间测量。

# Q8 证据质量

* **有支撑的结论。**
  * *完整设计在每个模型上都胜过批量纯 GUI 动作。* 平均分从 45.3 升到 64.9（+19.6），八个模型的成功率全部上升；步数平均减少 53.0%（表 2）。基线越弱，增益越大：GLM-5.3-Flash 从 29.6 到 64.9（+35.2），DeepSeek-V4.1-Flash 从 28.0 到 57.7（+29.8）。最强的模型也受益：GPT-6 Astra 从 67.1 到 75.7，步数从 102.1 降到 33.5。最好与最差之间的差距从 39.1 分缩小到 18.0 分。
  * *代码执行带来的不只是 shell 访问。* 在接口相同的批量 GUI+CLI 基线之上，完整设计提高 4.4 到 9.1 分且步数更少（Qwen3.8-Max 从 57.2 到 64.0，步数从 66.1 到 57.0；Claude Opus 5 从 65.7 到 70.1，步数几乎不变，表 3）。仅代码执行就让 GLM-5.3-Flash 从 55.8 升到 63.2，让 Qwen3.8-Max 的步数从 66.1 降到 54.9。
  * *按需截图提高缓存复用。* 缓存命中率从 75.6% 升到 86.1%（Qwen3.8-Max），从 61.9% 升到 76.3%（DeepSeek-V4.1-Flash），分数略有上升（表 4）。滚动截图缓冲区使命中率分别提高 16.0 和 13.4 个百分点；微压缩则使其下降（75.6% 到 68.6%，61.9% 到 58.9%），两种策略都没有降低分数。
  * *同一 harness 下真实设备上的效率因模型而异。* GPT-6 Astra 平均每任务 34.5 步、12.9K 输出 token，四个任务全部完成。Qwen3.8-Max 平均 50.8 步、73.4K token（5.7 倍），报告的推理 token 为 50.2K 对 2.6K（19.4 倍），完成四个中的三个。美元成本的排序则相反：Qwen3.8-Max 每任务约 1.49 美元，GPT-6 Astra 约 18.29 美元（表 5）。在工作簿任务上，GPT-6 Astra 先用七个示例检验一个可复用的求解程序，再填满全部 125 个答案格；Qwen3.8-Max 按固定的行范围循环，留下 40 个空格且没有检查。
* **比标题更弱或更窄的地方。**
  * *单次的、选定的运行。* OSWorld-v2 的数字都没有方差，"选定的运行"如何选定也没有说明。若干消融差异只有一到两分（例如加 todo 账本后从 62.4 到 64.0），可能落在运行间噪声之内。
  * *基线是作者自己的 harness。* "GUI + batch"是作者的实现；比较说明的是其设计相对于自己较弱配置的价值，而不是相对于其他已发表计算机使用智能体的价值。
  * *步数少不等于输出少。* 输出 token 平均减少 27.2%，但 GPT-6 Astra（30.8K 到 31.9K）和 Gemini 3.8 Flash（80.3K 到 82.0K）反而增加。论文说端到端延迟需要另行测量，其时间曲线未受控制，被标为探索性结果。
  * *按需截图也增加了步数（读者从表 4 观察到）。* Qwen3.8-Max 的每任务步数从 54.9 增至 63.0（+14.8%），DeepSeek-V4.1-Flash 从 74.5 增至 90.0（+20.8%），正文没有讨论这一点。
  * *决策移交主要关乎效率和可读性，而非分数。* 意图注释使分数下降（62.4 到 61.5；56.7 到 53.3），而所有机制合在一起的缓存命中率低于单用滚动缓冲区（Qwen3.8-Max 为 84.1% 对 91.6%）。"harness 的控制*应当*移入模型"是一种设计立场；证据只覆盖何时截图和如何维护待办列表，不覆盖更广的决定。
  * *真实设备研究规模很小。* 四个任务，每个模型一次记录的运行；作者说结果描述的是这些配置，而不是排名。摘要中 19.4 倍的推理比例来自表 5 的运行，案例研究用的则是另外的低推理强度轨迹。DeepSeek 缺少酒店任务的轨迹。
  * *与其他 OSWorld 数字的可比性（读者交叉对照）。* [RSIAgent](../papers/2609.15364.md) 报告 GPT-6 Astra 在一个 82 任务的 OSWorld 2.0 离线划分（0808，取自官方报告）上的部分得分为 72.60；OpenGCUA 的 67.1（GUI + batch）和 75.7（完整）是在 v2.1、作者的 harness 下得到的，三者不能直接比较。

# Q9 贡献

* 一个基于决策的通用计算机使用定义，以及一个使 GUI、CLI、多智能体混合和批量 GUI+CLI 智能体都成为受限情形的形式化。
* 一个用于计算机使用的代码执行 harness，以及从前沿模型轨迹中归纳出的五种代码执行模式。
* 把"从 harness 到模型的决策移交"作为设计原则，给出三种具体机制（按需截图、带状态类型的待办账本、意图说明）和两种考虑缓存的上下文策略，并分别做了消融。
* 八个模型的 OSWorld-v2 比较、公开的提示，以及包括 GPT-6 Astra 和 Claude Opus 5 在内全部八个前沿模型的轨迹。
* 一套在用户自己电脑上运行的设计：对基准与设备之间差距的五点分析、带明确资源绑定和独立无障碍与视觉通道的跨设备 SDK，以及五层 harness。
* 把最终分数转化为考虑资源的模型选择的预算曲线（例如 Qwen3.8-Flash 以每任务约 0.38 美元得 60.5 分，GPT-6 Astra 以约 15.26 美元得 75.7 分）。

# Q10 下一步

* **作者提出的。** 训练一个统一计算机与浏览器使用的 GCUA 模型，使其学会代码执行、按需观察和任务状态追踪；让常规操作的推理更简洁；在 macOS 上建立覆盖更多应用和用户交互的真实设备基准；把 harness 和 SDK 扩展到电脑、浏览器和手机；决定还应把哪些工作流决定从 harness 规则移交给模型。
* **重复运行并报告方差（读者建议）。** 在 OSWorld-v2 上对每种配置跑多次，才能把一到两分的消融效应与噪声区分开。
* **审计账本（读者建议）。** 把 `claimed_verified` 条目与评估器结果对照，因为账本记录的是模型自己的判断，把未检查的工作标成已验证的智能体会误导真实用户。
* **在真实设备上守住条件动作（读者建议）。** 按计算出的条件行动的程序（草稿一致就点击发送）省掉了一次模型调用，也省掉了一次停下来的机会；程序中的重要操作可以经由 `ask_user` 或 harness 级的审批清单。
* **与冻结的环境记忆结合（读者建议）。** RSIAgent 冻结的"动作-条件-结果"记忆和 OpenGCUA 的代码执行 harness 针对的是同一个 OSWorld 划分；把两者叠加，可以看出它们的增益能否相加。

* [GUI 与计算机使用智能体](../topics/gui-computer-use-agents.md) - 用每一步的三个模型决定（覆盖 GUI、无障碍、shell 和 API 接口）重新定义计算机使用，并以代码作为动作格式。
* [智能体 harness 工程](../topics/agent-harness-engineering.md) - 在冻结前沿模型上的 harness 研究：把部分 harness 规则移交给模型决定、考虑缓存的上下文策略，以及五层真实设备 harness。
* [OSWorld](../concepts/osworld.md) - 所有基准比较都在 OSWorld-v2 v2.1 的 82 个离线任务子集上进行。
* [Agents' Last Exam](../concepts/agents-last-exam.md) - 五层系统视角的来源，GCUA 定义把它细化为三个决定。
* [上下文压缩](../concepts/context-compaction.md) - 对较旧工具输出的微压缩和滚动截图缓冲区，以缓存命中率衡量其效果。
* [MAI-UI](../papers/2512.22047.md) - 同一团队较早的基础 GUI 智能体，因其真实设备上的移动端运行时被引用。
* [RecreationWorld](../papers/2609.22000.md) - 作为交错 GUI 与代码轨迹的环境被引用。
* [RSIAgent](../papers/2609.15364.md) - 同样在 82 任务的 OSWorld 2.0 离线划分上用代码即策略的动作改进冻结模型，靠的是自主构建的记忆而非 harness 设计。
* [SoL-Pi](../papers/2609.20519.md) - 其在线压缩权衡 token 节省与重写提示缓存的代价，正是 OpenGCUA 两种上下文策略以缓存命中率衡量的取舍（读者联想）。
