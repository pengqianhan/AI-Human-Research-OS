# Q1 问题定义

* **输入 `X`**:一条自然语言任务请求 `u_0`,由此导出一个形式化的任务契约 ℰ = (𝒲, W₀, q, 𝒜, 𝒯, Ω, **B**, D, V_D):工作空间状态空间与初始工作空间、归一化后的目标 `q`、动作集合、状态转移算子、观测接口、资源预算向量、交付契约,以及任务级校验器。
* **输出 `Y`**:Apodex 1.1,一个通用模型加执行系统(一套共享 harness 与 AgentOS 运行时),产生一条由动作、观测与异步用户干预组成的执行轨迹,终止于一个交付物满足交付契约(由任务级校验器判定)的最终工作空间——外加一个用于本地部署的 350 亿参数"Apodex 1.1 Mini"变体。
* **核心问题**:通用语言模型往往能推理、也常常知道正确答案,但在论文所称的"工作能力(working capability)"上会失败——即在长时程上取得持续、可验证的进展:找到并解读证据、在异构文件上操作、执行并调试代码、在多个步骤中维护并修订一个连贯的计划、在不丢弃有效进展的前提下从失败动作中恢复,以及交付另一个人能检查或继续使用的产物。论文将其定位为一个模型与系统结合的问题,而非仅仅是答案质量的问题。
* **范围**:横跨专业工作、金融、科学研究、数学、编码与搜索的通用系统。这是开发方自己的技术报告:部分对比数字是作者自己在其 harness 下的内部复现结果,而非外部报告结果,论文在表格说明中对此做了明确披露。

# Q2 问题的新颖性

本文并不声称首创推理-行动(ReAct)、工具使用(Toolformer)或多 agent 协调(AutoGen、MetaGPT、ChatDev、AgentVerse)——这些均被列为已有工作。其声称的新意在于,把模型开发组织在两个超出参数、数据或推理算力之外的、明确命名的扩展维度上:**Environment Scaling**(策略学习和行动所处的文件、搜索与代码世界的多样性、逼真度与可验证性)以及 **Agentic Coordination Scaling**(把分解、委派、分阶段结果整合与重新规划训练为模型行为,而不仅是推理时的外层封装),二者由一个执行 harness(AgentOS)绑定在一起,使得同一契约既服务于训练期间的轨迹采集,也服务于运行时的持续执行。论文明确论证,多 agent 工作中真正的扩展变量不是 agent 数量或并行样本数,而是"当目标不断演变时,能被协调起来的有用工作量"——即 Agent Team 的大部分收益来自持续的分阶段结果整合与重新规划,而非单纯的并行度。

# Q3 科学假设

如果一个模型在 (a) 多样、可验证、具有因果结构的可执行文件、搜索与代码环境(Environment Scaling)之上,以及 (b) 跨越 agent 与时间的分解、委派、分阶段结果整合与重新规划轨迹(Agentic Coordination Scaling)之上进行训练,二者均通过一套共享 harness(AgentOS)采集与执行——该 harness 在工具、agent、上下文压力、干预与部分失败之间维持权威状态——那么由此产生的策略应当在专业、金融、科学、数学、编码与搜索等领域达到"工作能力"(持续、可验证的任务完成)的领先梯队,并且使用的模型规模显著小于许多前沿系统,这一效率优势应当一直延续到一个 350 亿参数的"Mini"变体上。

# Q5 核心解法

1. **一个形式化的任务契约**。ℰ = (𝒲, W₀, q, 𝒜, 𝒯, Ω, **B**, D, V_D) 把输入请求 `u_0` 与归一化后的目标 `q`、以及单独被校验的交付契约 `D` 区分开;异步的用户干预被当作对工作空间的运行时更新来接纳,而非模型自己选择的一个动作;一条实质性改变目标或所需交付物的消息会实例化一个新的任务契约,即便运行时会把仍然有效的工作空间状态延续下去。
2. **横跨共享同一契约的三类环境的 Environment Scaling**。文件世界(权威性与变换——一个覆盖 33 个领域、318 个职业、1208 个交付集群的、按职业分层的注册表;校验锚定在可独立重新推导、经代码核实的数值上,而非依赖语言模型判断是否"看起来合理")。搜索世界(发现与证据对齐——黄金对象包含相关来源集合与"论断-证据"对齐关系,而不只是一个最终答案)。代码世界(可执行变换——真实收集的 pull request 加上经过合成与扰动的任务,沙盒化的 fail-to-pass/pass-to-pass 测试校验,以及在信任一个合成世界之前明确检验"求解者能否在未真正完成任务的情况下获得奖励"的对抗性检查;构建遵循"正向廉价、逆向昂贵"原则)。
3. **Agent Team:运行时的 Agentic Coordination Scaling**。把主导 agent 的分解过程外化到一块持久化的 Task Board 上——这是一份共享的协调记录,而非对私有推理过程的可视化——因此一个返回的结果能立即解锁一个依赖它的任务,一个失败的前提只会使其后代任务失效,一个缓慢的分支也不会阻塞独立的工作。相比 Apodex 1.0 隐式的分解方式,Apodex 1.1 增加了四项能力:异步人类干预(执行中途的一条消息更新实时看板;由运行时决定这是一次保持任务不变的编辑,还是一个新的任务契约);非对称验证(校验者只拿到一条具体论断、其支持证据和适用的交付约束——绝不是整个问题重来一遍——以避免让校验本身成为"又一个上下文污染的来源",引入第二条同样不受约束的错误链);自适应 Max Team Effort(额外的调查只分配给薄弱、有争议或举足轻重的论断,并在每次结果返回后重新分配,而非固定 agent 数量);以及证据驱动的综合(一个专门的执行后阶段,在写作 agent 起草之前,从最终的任务看板、子 agent 报告、证据和校验结果中构建一个论断-证据图,而不是把主导 agent 最后一条消息当作报告状态)。
4. **AgentOS:共享的执行基座**。把工作空间状态实例化为文件状态、检索到的证据、可执行状态/日志、工件索引、依赖图,以及可选的协调控制状态;三个文件系统命名空间(只读的 `/inputs`、草稿区 `/workspace`、作为收集根目录的 `/outputs`)使交付契约变得可核验;协调状态(Task Board 与 Agent Bus)存放在 LLM 消息历史之外,并被周期性地重新注入,使计划能在上下文压缩后存活;分层压缩由推理服务商自己上报的 token 用量触发(先做便宜的工具观测淘汰,只有在缓解不足时才启用 LLM 摘要);软截止时间/硬超时的预算处理能恢复一份有边界的部分结果,而不是直接丢弃正在进行的工作;受控的工件交付使用单一写者的发布租约与一份精确声明的清单,并与租约授予时的基线快照进行核对,使一个陈旧或空的文件无法悄悄满足交付契约。
5. **训练**。一个统一的 SFT 混合数据(按行为有效性过滤,针对可打分的评分标准任务用阈值筛选而非单一聚合裁判过滤,并跨领域专精变体做模型汤式合并)建立冷启动策略。之后的 agentic RL 使用 **PIVOT-RL**:以事后视角定位轨迹中举足轻重的"pivot"决策点(模型开始采取无效策略、依赖不充分证据、误用工具,或未能修正某个假设之处),从被保留下来的有用前缀构建一个局部延续任务,并附上一条简短的纠正性提示——该提示只出现在延续任务的构建中,推理时不出现,也从不作为预测目标——与不带提示的完整任务 rollout 混合训练;异步训练让文件、代码、搜索和协调这些在耗时上差异巨大的轨迹进入优化,而不必等待最慢的那一条完成。从观察到的失败,到 Task Pipeline,到 Environment/Coordination Scaling,再到训练、评测与失败归因,再回到下一轮 Task Pipeline 目标,这整个循环被描述为一个受控的工程循环;论文明确说明这里的"自我演化"措辞仅指这一受管理的循环,而非不受约束的模型自我修改。

# Q6 实验设计

全程使用两种执行模式:ReAct(最小化外层封装,隔离出模型自身的策略)与 Agent Team(经训练的协调加上额外组织化的算力)。公开基准结果覆盖专业工作(APEX-Agents、GDPVal)、金融与商业模拟(FrontierFinance、YC-Bench)、科学研究(FrontierScience-Research、BioMysteryBench Human-difficult)、通用推理与深度搜索(Humanity's Last Exam、DeepSearchQA),以及本笔记未完整阅读的数学与编码章节,每项都与一批同代的专有和开源模型(DeepSeek V4、Gemini 3.x、Claude Opus 4.x/5、GPT-5.x、GLM-5.2、Kimi K3、Qwen3.x)对比。表格说明明确标注了哪些行是作者自己在 Apodex harness 下的内部复现结果——所有外部模型的 GDPVal 胜率条目、Claude Opus 5 在 APEX-Agents 上的结果,以及 DeepSeek V4 在 FrontierFinance 上的条目——其余行则是外部报告的参考结果。除公开表格外,论文还报告了一个内部的 FrontierSearchBench,并引入了一个新的 FrontierResearchBench 用于端到端研究交付(§4.4,本笔记未详细阅读)。评测部分以 **HDS6** 收尾,这是一个六维能力、24 条评分项的过程验证框架(长时程状态一致性、证据保真度、假设管理、边界与失败推理、工具使用与执行状态管理、验证下的自我纠错),由一套针对整理好的执行日志运行的、角色专精的 agentic 裁判流水线打分,并设有一个硬性完整性门槛:一旦发现一次被捏造的工具结果或一个被叙述但从未真正执行的动作,整条轨迹的分数即被清零。HDS6 在三个面板上比较 Apodex 1.0 与 1.1(Deep Discover:3970 亿参数模型,Agent Team;Deep Solve:3970 亿参数模型,ReAct;Deep Research:350 亿参数模型,ReAct),论文明确说明应把这些理解为面板内部的比较,而非一次严格匹配的跨面板消融实验——各面板在聚合方式上也不同(Apodex 1.0 的 Deep Discover 结果聚合了八次独立运行,Apodex 1.1 的结果来自单次运行)。此外,350 亿参数的"Apodex 1.1 mini" 被单独与规模相当的开源和专有模型在 FrontierFinance、FrontierScience-Research 与 APEX-Agents 上对比,作为模型规模效率的直接检验。

# Q9 主要贡献

1. 一个形式化的任务契约(工作空间、目标、动作、转移/观测算子、资源预算、交付契约、校验器),被一致地用来定义文件、搜索和代码领域中"已完成的工作"是什么,把输入请求与归一化后的目标、以及单独被校验的交付契约区分开来。
2. 两个超出参数、数据和推理算力之外、被明确命名的扩展维度——Environment Scaling 与 Agentic Coordination Scaling——由一套执行 harness(AgentOS)绑定,使训练与运行时执行共享同一契约。
3. Apodex Agent Team 1.1:一块显式的持久化 Task Board,取代了主导 agent 的隐式分解,外加异步人类干预、窄范围的非对称验证、自适应 Max Team Effort 分配,以及一个专门的、基于证据图的综合阶段。
4. AgentOS:一个持久化的执行基座,拥有稳定的三命名空间文件系统、被外化到 LLM 消息历史之外并周期性重新注入的协调状态、由服务商 token 用量触发的分层压缩、带优雅部分结果恢复的软/硬预算处理,以及带基线核对的单一写者租约式工件交付。
5. PIVOT-RL:以事后视角定位轨迹中举足轻重的"pivot"决策点,用于有针对性的 RL 延续训练,并与不带提示的完整任务 rollout 混合,外加针对异构成本 agentic 轨迹的异步训练。
6. 报告的评测结果显示,在论文自己的 FrontierFinance 和 FrontierScience-Research 表格中,Apodex 1.1 Agent Team 是所比较模型中得分最高的系统,而在 BioMysteryBench、APEX-Agents、GDPVal、Humanity's Last Exam 与 DeepSearchQA 上的同一批表格中得分低于 Claude Opus 5——相较论文"领先表现梯队"这一表述,实际是一个有得有失、而非全面领先的结果。350 亿参数的"Apodex 1.1 mini"在自己的对比表中于 FrontierFinance 上领先(50.2),但在 FrontierScience-Research 上落后于 DeepSeek-V4-Flash-0731(51.7 对 55.0),在 APEX-Agents 上同时落后于 DeepSeek-V4-Flash-0731 和 GLM-5.2(27.7 对 34.4/35.6),同时在所有报告的重叠评测上相较 Apodex 1.0 mini 都有大幅提升。
7. HDS6,一个六维能力、24 项评分标准的过程验证框架,配有一套 agentic 裁判流水线和针对捏造工具结果的硬性完整性门槛,用于比较 Apodex 1.0 和 1.1 在执行过程质量上的差异,而不仅仅是结果分数。

# Q10 下一步

论文自己陈述的长期方向,朝着其 "Heavy-Duty Solver" 目标推进:进一步扩展可执行环境的覆盖面和逼真度、在更长时程上强化经过学习的协调能力、改进跨层级多 agent 轨迹上的训练与信用分配,以及更紧密地闭合真实部署失败、任务构建、训练与评测之间的循环。论文自身也点明了若干明确的边界,值得保留:协调层面(Task Board、Agent Bus)是限定在单次运行范围内的,而非一个持久的分布式数据库,因此进程重启后的恢复和历史文件系统的回溯明确"在当前契约之外",协调状态、消息历史和工作空间的联合版本化被称为"所描述机制的自然延伸",而非已经建成的东西;发布防护是一个工具层面的策略,"而非系统调用级别的文件系统监控";论文明确指出,AgentOS 的任何机制都"不保证一个检索到的来源、一次计算、一种科学方法或一个最终结论是正确的"——在高风险场景中,这些论断仍然需要与任务相适应的校验和人工审查。

本笔记指出报告没有直接触及的一个开放问题:HDS6 的裁判流水线由发布该模型的同一团队构建并运行,使用一个 agentic 裁判来评判该模型自己的执行日志。论文正文仅承认 HDS6"无法分离出单个系统组件的因果贡献",但没有讨论一个自我评分的过程评测框架是否也需要本知识库 [Multi-agent systems](../topics/multi-agent-systems.md) 主题已经通过 [ARIS](2605.03042.md) 的跨模型家族执行者/审核者设计所揭示的那种独立性保障——这与 Apodex Agent Team 自身"同一团队、缩窄范围"的非对称验证是不同的独立性机制。
