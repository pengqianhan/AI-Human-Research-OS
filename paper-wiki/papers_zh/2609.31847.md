# Q1 问题定义

* **输入（X）：** 一个用户请求，其素材和交付物可能混合七类产物（文本、图像、音频、视频、文档、3D 资产、代码），外加此前轮次登记过的资产。由一个现成的通用宿主智能体处理，论文使用 GPT-5.6 Sol 和 Claude Sonnet 5。
* **输出（Y）：** 所需交付物，从一份分析到一整套协调的产出（例如海报、带音效的宣传视频和落地页），每件都登记为资产，后续轮次可以修改或复用。
* **核心问题：** 编程和知识工作类智能体已经很会规划和执行，但它们的产出面止步于软件和文本。给基础模型增加模态，会把能力增长绑在昂贵的再训练上；接入专用模型和工具，又没有解决流程、依赖、中间资产和跨轮修改如何协调的问题。
* **约束：** 宿主智能体的推理内核保持不变，一切以可加载的驾驭层（harness）形式加入。

# Q2 问题新颖性

部分新颖。全模态基础模型（Unified-IO 2、AnyGPT、Chameleon、NExT-GPT、Transfusion、Qwen-Omni 系列）把多模态放进单一模型。模型协调型智能体（MM-ReAct、Agent-Omni、OmniGAIA）把任务委派给各模态专家，但作者指出它们主要在理解和问答上评测。Agent Skills 方向的工作（[SkillsBench](../concepts/skillsbench.md)、CUA-Skill、MMSkills）封装了流程，却不涉及多资产的媒体生产。本文定位在三者交汇处：任意到任意（any-to-any）的生产工作流，配以依赖感知的执行和跨轮持久的资产状态。

# Q3 科学假设

如果给现成智能体配上分层 Skills、标准化的多模态执行接口、依赖感知的图执行和持久化资产注册表，那么它应能接收测试集中所有输入模态，并产出结构更好、质量更高的多模态结果，而无需改动模型。

# Q4 相关工作与关键人物

* **全模态基础模型：** 统一自回归模型（Unified-IO 2、AnyGPT、Chameleon）与离散-连续混合模型（NExT-GPT、Transfusion、JanusFlow、Qwen2.5-Omni 和 Qwen3-Omni），以及 Moshi、Ming-Omni 等流式系统。
* **驾驭层与多模态智能体：** ReAct、[模型上下文协议（MCP）](../concepts/model-context-protocol.md)、驾驭层工程相关工作、MM-ReAct、Agent-Omni、OmniGAIA。
* **技能：** SkillsBench、CUA-Skill（把计算机使用流程表示为参数化图）、MMSkills（文本流程配状态卡和视觉关键帧）。
* **关键人物：** 新加坡国立大学，另列牛津大学。Hao Fei 为通讯作者和项目负责人；Mong-Li Lee 和 Wynne Hsu 为资深作者。评测所用的 UniM 基准（CVPR 2026）出自同一团队、第一作者相同；Shengqiong Wu 和 Hao Fei 也是 NExT-GPT 的作者。可能的批评者：全模态模型的构建者，会问该驾驭层与原生全模态模型相比如何；智能体评测研究者，会要求其他驾驭层基线和消融。

# Q5 关键解法思路

* **智能体与工具之间的四层结构。** Skill Entry 层选择并展开 Skills。MCP Tool Service 层通过统一契约（任务类型、自包含提示、参数、依赖已解析的资产输入）暴露理解、生成和工具类操作。Provider and Configuration 层把每种任务类型绑定到工具、提供方、模型、凭据引用、默认参数和回退策略，因此更换提供方无需修改 Skills。Asset Registry 层记录每一个输出。
* **按粒度而非模态组织 Skills。** 每个 Skill 声明适用条件、输入、流程、输出以及指向下层 Skills 的链接。共有 19 个 Atomic Skill（单一操作，如图像理解、视频生成、语音合成、3D 生成、PPT 生成、网页搜索），2 个 Expert Skill（海报设计和复杂视频制作，各覆盖一个成品从规划到检查的全过程，出问题时只重新生成失败部分），6 个 Scenario Skill（社交媒体帖子、办公文档、求职申请、教育分享、活动物料、游戏资产），负责判断一个请求需要哪些交付物。高层 Skill 递归展开，直到每一步都可执行。
* **声明式执行图（Declare Execution Graph，DEG）。** 终端任务成为图节点（id、类型、提示、参数、依赖）。执行前检查图中是否有无法解析的引用或环，不合格的图会重建而不是提交。前驱全部完成的节点组成一个“Wave”并发执行。某节点失败时，其后代被取消，独立分支继续，已完成的输出不回滚。
* **用资产而非路径。** 资产记录包含 id、类型与子类型、路径、描述、实际参数、轮次 id，以及记录来源关系的 source-asset id。注册表是只追加的 JSON，写入原子化并加文件锁。后续轮次按引用指向旧资产，它会在新图中成为一个已完成的源节点，因此像“换一种落地页风格”这样的修改只需重跑受影响的节点。

# Q6 实验设计

* **基准：** UniM-90，从 UniM 中固定选出的 90 个实例，覆盖全部七种模态及其交错组合。作者称子集的选择与任何智能体的原生能力无关；选择流程被指向一个附录，但获取到的正文中没有该附录。
* **条件：** GPT-5.6 Sol 和 Claude Sonnet 5 各自分别以 Base Agent（默认环境、内置 Skills 和工具，不装第三方扩展）和加载 Omni-IO Skills（其余不变）两种方式运行。作者只做同一智能体内的比较，不做跨智能体比较。
* **指标（UniM 评测套件）：** 输入支持率 τ（智能体能完整接收输入的实例比例）、语义-质量耦合分（SQCS：语义正确性加生成质量）、交错连贯性分（ICS），以及严格与宽松结构分（StS、LeS）。绝对分只统计受支持的实例；相对分乘以 τ，覆盖整个集合。无法产出所需输出的实例仍计为失败。
* **定性：** 两个案例：由一段视频及其讲解生成 11 张图的绘画教程，以及产品推广套件。

代码见 [any2any-mllm/Omni-IO-Skill](https://github.com/any2any-mllm/Omni-IO-Skill)（获取时 Hugging Face 显示 10 星）。UniM-90 是现有 UniM 基准的子集；获取到的正文未说明该子集的实例列表是否公开。正文也没有写明各工具背后使用了哪些图像、视频、音频或 3D 模型。

# Q8 证据质量

* **有支撑的（表 3）：**
  * *输入全覆盖。* τ 从 40.00%（GPT-5.6 Sol）和 38.89%（Claude Sonnet 5）都升到 100%。
  * *相对分大幅提升，主要来自覆盖率。* 相对 SQCS 从 26.99 升到 74.94、从 27.82 升到 77.78（+47.95 和 +49.96）。相对 ICS 从 34.61 升到 93.98、从 32.00 升到 83.28。
  * *受支持实例上的提升较小但真实。* 绝对 SQCS 从 67.49 升到 74.94、从 71.53 升到 77.78；不过基线的绝对分只覆盖它能接收的 35-36 个实例（τ × 90），而加载驾驭层后的分数覆盖全部 90 个。
  * *输出结构。* StS 达到 100.00 和 99.78（绝对分原为 47.84 和 52.21），LeS 两者都是 100.00。
* **较弱或有边界的：**
  * *比较对象只是“没有驾驭层”。* 基线是只带默认工具的裸智能体，所以相对分的大部分提升来自智能体终于能接收输入、调用生成器。没有与其他多模态驾驭层或全模态智能体（如 Agent-Omni、OmniGAIA）比较，也没有在同样实例上运行原生全模态模型。
  * *没有消融。* 分层结构、DEG 调度和资产注册表是论文的主要设计主张，但都没有被单独去掉以衡量其贡献。作为亮点的跨轮复用只在示例中展示，没有被测量。
  * *评测规模小且自建。* 90 个实例，每个条件跑一次，不报方差或显著性，基准和评测套件都来自同一团队。SQCS 和 ICS 的计算方式（例如是否由模型评审）继承自 UniM，获取到的正文没有复述。
  * *不报告成本。* 没有 token、延迟、金额，也没有外部生成服务的失败率，后端模型也未点名，因此无法把质量数字归因于驾驭层而非所选提供方。
  * *案例仅作示意。* 两个案例展示了两个宿主的完整输出，但没有人工评分。

# Q9 贡献

* 全模态智能体驾驭层的形式化：无需再训练，就把通用智能体扩展到任意到任意的生产。
* 一个具体的四层设计：声明式三级 Skills；带提供方绑定的 MCP 工具契约；经依赖检查、按 Wave 调度、能隔离失败的执行图；以及带来源记录、支持跨轮修改的只追加资产注册表。
* 面向应用的 27 个 Skill 目录，覆盖七类产物、四大能力族（理解、生成、推理、检索）中的 38 个代表性任务。
* 在 UniM-90 上的首次测量，表明同一个驾驭层能为两个不同的宿主智能体补上大部分模态缺口。

# Q10 下一步

* **对设计做消融（读者注）：** 去掉 Scenario 和 Expert 层（只保留扁平的 Atomic Skills），用顺序调用替代 DEG 的 Wave，再去掉注册表，在多轮任务上测量质量、墙钟时间和修改成本。
* **与原生和协调型全模态系统比较（读者注）：** 在 UniM-90 上运行原生全模态模型和 Agent-Omni 式协调器，把驾驭层本身的贡献与“有生成器可用”区分开。
* **报告提供方身份和成本（读者注）：** 既然提供方按设计可替换，一次替换提供方的实验就能检验论文自己的主张：后端演进时 Skills 和执行图保持不变。
* **别处的资产注册表（读者注）：** [Raven](../papers/2609.33439.md) 让所有多智能体交接都经过可记录、可按引用复用的文件产物，是同一思路在智能体层面（而非工具调用层面）的体现。Omni-IO 带 `source_asset_id` 来源记录的只追加资产记录，是任何跨轮产出文件的智能体都能复用的小模式。
