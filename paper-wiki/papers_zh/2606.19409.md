> 论文:**OpenRath: Session-Centered Runtime State for Agent Systems**
> 论文链接:<https://arxiv.org/abs/2606.19409>
> 机构:清华大学(据作者邮箱推断),2026 年 6 月 17 日提交

# Q1 问题定义

* **输入 `X`**:一个用 OpenRath 的对象词汇表(Session、Agent、Workflow、Tool、Memory、Sandbox、Selector)构建的 agent 程序——用户或 agent 的上下文创建一个初始 Session,随后该 Session 流经各个 agent、工具和工作流。
* **输出 `Y`**:同一个运行时概念被变得可审计:一个 Session 可以被放置到某个执行后端、为并行工作分叉(fork)、审阅后合并(merge)、以 JSONL 血缘记录持久化,并可重放——把对话片段、分支溯源、工具证据、记忆的存取事件、用量统计和待办工作都作为一个可检查的值携带,而不是分散在控制器一侧的簿记中。
* **核心问题**:简单的推理-行动循环(ReAct 风格:追加消息、调用模型、执行工具、追加观测)对单个助手而言是不错的状态边界,但一旦工作被分散到多个角色、工具、记忆存储、沙箱和被恢复的执行之间,这个边界就变得脆弱——最终输出可能是正确的,但产生它的运行时路径(哪个分支产生了结果、哪个工具改动了哪个文件、检索了什么记忆、压缩过程中丢弃了什么证据)却分散在各个旁路通道中,难以重建或审计。
* **范围**:报告明确将 OpenRath 定位为特定边界上的补充性基础设施——承载其他层"效果"的运行时值——而非图运行时(LangGraph)、追踪 SDK(OpenAI Agents SDK、OpenTelemetry)、工具/数据协议(MCP)、沙箱提供方或评测框架的替代品。其主张明确限定于确定性、可本地验证的运行时属性(血缘导出、本地沙箱执行、工具分发、聚焦测试);广泛的基准优势、人类偏好结果和跨系统排行榜比较被明确保留给后续评测,本文不做此类主张。

# Q2 问题的新颖性

论文自己对相关工作的梳理认为,该领域正收敛为若干专门化的运行时层(推理/行动方法、多智能体编排框架、持久图运行时、追踪 SDK、工具/数据协议、真实环境基准),每一层各自负责一个关切点,并提出一个明确的"交叉对象"问题:什么样的单一状态能够流经所有这些层,同时把对话、血缘、放置、工具效果、记忆和产物维系在一起?其自陈的新颖性不是一种新的编排模式或新基准,而是识别并填补这一特定的边界空缺——文中直接与 LangGraph(其检查点式图状态是写给调度器用来恢复/重放/分叉的,而非写给 agent 程序自身传递的)以及 OpenAI Agents SDK / OpenTelemetry 这类追踪系统(其 span 是面向观察者、事后记录发生了什么的信号,而非程序据以继续操作的值)相对照。受 PyTorch 启发的对象词汇表(Session 作为流动的"张量",Agent 作为类似层的变换,`forward(session) -> session`,`session.to(backend)` 表达放置)被明确定位为一种教学类比,而非"agent 系统就是神经网络"这样的技术主张。

# Q3 科学假设

如果一个多智能体系统把所有运行时效果——对话片段、工具分发与结果、记忆的存取事件、沙箱放置、分支血缘、用量统计——都通过一个统一类型的一等运行时值(Session)来传递,由每个组件对其进行变换或标注,而不是各自记录进私有的旁路通道,那么由此产生的系统将能够把分支、合并、持久化和重放当作对该值的普通程序操作,而不是事后从控制器日志、工具日志和提供方追踪中重建出来的状态——从而使多智能体运行变得可审计、可调试、可审阅,这是以旁路簿记为核心的循环式设计所不具备的;而且这种优势应当随着系统在角色、工具、记忆存储、沙箱和被恢复执行上变得更加分布式而扩大,而非退化。

# Q4 相关工作与关键人物

* 按每个领域留下的"交叉对象"问题对已有工作分组:工具使用/行动型 agent 方法(ReAct、MRKL、Toolformer、HuggingGPT、Gorilla、ToolLLM、Tree of Thoughts)推进的是模型*如何*推理和行动,论文将其视为互补而非竞争关系,因为 OpenRath 针对的是这些行动产生的运行时状态,而非推理方法本身。
* 多智能体编排框架(AutoGen、CAMEL、MetaGPT、ChatDev、AgentVerse)被定性为负责*哪个角色何时行动*(例如 MetaGPT 的 SOP),而 OpenRath 自陈的区别在于负责*各角色之间传递什么值*——因此多智能体组合不需要第二套、框架私有的状态格式。
* 运行时/可观测性层被直接对照:LangGraph 的检查点式图状态服务于调度器(从某个检查点恢复/重放/分叉),OpenAI Agents SDK 和 OpenTelemetry 产生面向观察者、事后描述"观察到了什么"的追踪/span,TensorFlow 的静态计算图被用作一个有启发性的数据流运行时类比(OpenRath 让值保持命令式,而非图结构化)。MCP 和 OpenAPI 被视为 OpenRath 加以补充而非取代的连接性/接口标准。
* 记忆与检索工作(Reflexion 的 episodic 反思缓冲区、Generative Agents 的检索-反思记忆流、MemGPT 受操作系统启发的分页层级、Voyager 的终身技能库)明确未被取代——论文写道"OpenRath 并不提出新的记忆模型;它只是让记忆操作在会话层面可见"。
* Agent 基准与环境(AgentBench、τ-bench、SWE-bench/SWE-agent/SWE-bench Verified、Terminal-Bench 系列、WebArena/VisualWebArena/WorkArena/OSWorld/WebShop/Mind2Web/ALFWorld/ScienceWorld/GAIA/TheAgentCompany)被定性为在真实环境中给结果打分,而 OpenRath 提出的互补问题是:产生某个结果的轨迹本身是否可检查、可重放——文中称其为"可信打分的一个前提条件"。
* 与本知识库 [Agent harness engineering](../topics/agent-harness-engineering.md) 主题下的 LongHorizon-Harness 和 StateM 共享"把持久运行时/任务状态外部化到不断膨胀的执行上下文之外"这一关切,但 OpenRath 的 Session 被定位为 agent 自身分叉/合并/重放的普通程序值,不同于 LongHorizon-Harness 那种由独立审计者门控的持久任务状态记录,也不同于 StateM 的 YAML+CLI 运行手册。

# Q5 核心解法

1. **Session 作为唯一的一等运行时值。** 借鉴 PyTorch 风格的架构接口(而非张量数学):Session 扮演流动值的角色,Agent 是类似层的可复用变换,Workflow 是组合式容器,二者都遵循统一的 `forward(session) -> session` 契约,放置通过 `session.to(backend)` 显式表达,Memory 是绑定在 agent 上的持久状态平面,而非隐藏的提示词文本。由于每次变换都保持 Session→Session 的形状,agent 可以嵌套进工作流,而无需发明第二套运行时状态格式。
2. **边界收窄、词汇精简的对象体系。** Session、Sandbox、Tool、Agent、Memory、Workflow、Selector 各自被刻意限定了狭窄的归属边界:Agent 不拥有整个对话图(血缘归 Session 所有);Tool 不拥有放置权(它通过当前活跃的沙箱执行);Workflow 不创建独立的编排状态(它是对会话的变换组合);Memory 不会变成隐藏的提示词文本(存取始终是可见的运行时事件)。Selector 读取当前 Session 并在运行时路由到若干自描述工作流之一——使分支/循环成为写入会话记录、可检查的运行时决策,而不是消失在控制器代码里的逻辑。
3. **分支作为一等运行时操作,而非控制器约定。** `fork` 复制状态并保留父子关系;`detach` 从已复制内容开始一条新的血缘根;`merge` 合并兼容的会话并记录双亲——当前实现中,合并兼容性要求共享同一个存活的沙箱句柄,或指向同一个未绑定后端,从而把放置本身变成运行时图的一部分,而不是对 Session 记录不可见的外部执行细节。
4. **分层的、会话可见的工具执行。** 模型看到的是 FlowToolCall 模式;会话循环把内置工具和用户工具合并,将模式发送给模型提供方,按名称解析返回的工具调用,校验参数,并用当前活跃的 Session 调用被选中的工具;需要产生副作用时,工具通过会话的沙箱分发一个后端负载。参数错误、未知工具、异常和成功结果都会变成附着在会话上的工具结果片段,而不是消失在控制器流程里。
5. **审计优先、低于基准声明的发布协议。** 报告中的每条主张都被一一映射进一份主张台账(目前分类为十条:五条有操作性证据包支持、一条部分支持、一条仅前置条件被支持、一条依据文献定位的主张、一条版面冒烟测试主张、一条证据待补的主张);每个证据包包含可复现的命令、清单、来源与环境元数据、会话 JSONL/工具日志、输出产物,以及一段明确说明该证据包能证明什么、不能证明什么的说明。论文主张这种更窄、可复现的证据包式问题("系统能否保留并暴露让后续评测真正有意义所需的状态?")应当先于广泛的基准比较(SWE-bench Verified、GAIA)——后者把运行时语义和模型选择、提示词设计、任务分布混在了一起。

# Q6 实验设计

这明确是一份系统技术报告,而非基准论文:它论证的是确定性、可本地验证的运行时主张,而非报告相对基线的任务成功率对比数字。所谓"评测"就是把上述(Q5.5)主张台账/证据包协议应用于当前实现:会话核心(有序片段、分支操作、用量统计、JSONL 血缘导出)、本地沙箱放置和工具分发路径都由聚焦测试验证;工具/工作流行为进一步由自定义工具、MCP 和脚本化工作流示例演示。可选的 OpenSandbox 后端和 LLM 提供方层被明确标注为存在但依赖具体环境或提供方,实时模型质量被明确排除在本报告范围之外。附录 A 的案例研究(仓库编辑与长时间运行的编码、带分支特定上下文和受控压缩的研究综合、记忆辅助工作流、沙箱隔离执行)被明确定位为"限定范围内的适用性论证",用来把已审计的运行时主张与真实工作负载模式联系起来,而非度量化的性能结果——论文明确写道"案例研究的作用……是在不把定性适用性转化为量化性能主张的前提下"完成这种联系。

# Q8 证据质量

本笔记基于通过 `hf papers read` 检索到的 arXiv HTML 完整论文正文撰写(从引言到附录 A 案例研究,加上参考文献列表);正文中提到的若干表格和图(表 1 各层读者对象、表 2 运行时栈趋势、表 3-10 涵盖对象词汇表、会话生命周期、后端边界、证据协议和局限性,以及嵌入的架构图)在周边文字中有描述,但其确切的表格内容未以机器可读形式被检索到,因此本笔记依赖论文自身对每张表内容的文字描述,而非原始表格数据。论文对自身证据边界的态度异常明确且自我约束——它直接声明自己*不*主张什么(广泛的基准优势、经过验证的本地记忆实现、有保障的 OpenSandbox 可用性、完全可复现的实时模型输出、任何安全属性),并将其局限性一节定位为范围边界而非道歉。这使得论文整体的认知姿态比典型的发布公告论文更值得信赖,但也意味着其几乎所有主张都未在共享任务上与其他 agent 运行时框架(AutoGen、LangGraph、OpenAI Agents SDK)做过基准对比——相关工作一节中的比较纯属定性/架构层面,而非实证的。

# Q9 主要贡献

1. 一个以会话为中心的运行时数据流,把对话片段、放置、血缘、用量、待办工作、工具证据和记忆边界记录表示为一条可检查的流,而不是分散的控制器簿记。
2. 一套受 PyTorch 启发、边界狭窄的对象词汇表(Session、Sandbox、Tool、Agent、Memory、Workflow、Selector),其中每个组件都保持同样的 Session→Session 形状,包括通过 Selector 实现的运行时路由控制流。
3. 运行时状态与执行/记忆后端(负责运行工具与持久化可检索状态)之间的后端感知式分离,使本地执行、可选的 OpenSandbox 放置、MCP 风格工具和记忆服务能够共同参与同一个以会话为中心的模型。
4. 一套审计优先的发布协议,通过一份明确的主张台账把报告中的每条主张映射到一个可复现的证据包,刻意把报告的主张限定在确定性运行时属性上,而非基准排行榜上的优势。

# Q10 下一步

* 本笔记无法从检索到的正文解答的问题:当分叉的会话在重叠状态上出现分歧时,合并冲突如何解决(超出所述的沙箱兼容性要求之外);会话在执行中途被分离(detach)时,飞行中的工具调用或沙箱资源会发生什么;Selector 的运行时路由控制流本身如何被审计或约束以防止意外循环,因为论文指出路由决策是"在运行时根据会话状态"做出的,而非来自静态图。
* 论文自己的表 9(局限性)被描述为记录"每个边界、当前状态,以及更强主张需要什么条件",但其逐行内容未在本笔记中被检索到——在依赖本笔记获取完整局限性清单之前,值得直接对照 arXiv 的 PDF 或 HTML 表格重新核实。
* **与本仓库的关联**:OpenRath 的核心区分——追踪是写给观察者的,图检查点是写给调度器的,而 Session 是写给程序本身的,因此证据附着在这个值上,而不是事后从旁路通道重建——为本仓库自身在 [Agent harness engineering](../topics/agent-harness-engineering.md) 方面的关切及更广泛的"证据到主张"纪律提供了一个有用的框架:本仓库未来为并行或 agent 主导的项目工作构建任何编排机制时,都可以提出同样的问题——"什么是所有组件读取、变换并据以解释的运行时值",而不是假定日志和会话记录本身就足以作为事后审计轨迹。
