# Q1 问题定义

* **输入（X）：** 以 1 秒为单位到达的用户音频流，以及注入的观测（前端可调用工具的 schema、此前调用的结果）；用户请求可能不流畅，并在说话中途更正（论文的贯穿例子里，用户从"两台笔记本"改成"一台平板"）。
* **输出（Y）：** 每个单位输出一个轮次状态（听或说）、要说出的文本，以及一个可能为空的私有动作（一次不会被说出的工具调用）。成功要求：实际执行的调用与标准调用完全一致（无缺失、无多余、归一化参数全对）；口头回答只依据返回的观测；信息足够时在期限内行动（否则只追问缺失值）；轮次控制正确（用户说完时接话、停顿时不抢话、被打断时停下、遇到附和音（backchannel）时继续）。
* **约束：** 同一个因果策略必须同时做对话决策和任务决策；工具可以直接暴露（Direct）、只经由后端智能体暴露（Backend，即 Realtime-Venus 的前后端设计）、或两者都暴露（Both）。

# Q2 问题新颖性

全双工语音模型（Moshi、MiniCPM-o、Realtime-Venus）、把任务委派给文本智能体的前后端语音智能体（Realtime-Venus Harness、DuplexOmni、Gander、JoyAI-VL-Interaction、SALMONN-duo、Hu 等人的前后端架构），以及能直接调用工具的语音前端（GPT-Realtime、Qwen-Audio-3.1-Realtime、NemotronLabs VoiceChat）都已存在。本文的新框架是诊断性的：在基于请求的委派下，Pass@1 可分解为"前端发出交接（hand-off）的会话占比"乘以"这些交接的通过率"，因此交接占比是任何后端都无法突破的硬上限。它把前后端智能体的瓶颈定位在*发起*而不是执行，并追问全双工模型如何在不丢失对话能动性的前提下获得任务能动性。

# Q3 科学假设

如果训练一个全双工模型，让它在与领域工具相同的动作接口中把后端当作又一个工具，并在流式强化学习中奖励按时、完整、正确的调用和有依据的回答，那么它会发出基线前端从未发出的请求，在同一后端下提高任务成功率；如果之后只重新拟合思考器到发声器（thinker-to-talker）的投影器，就能挽回思考器训练中损失的语音可懂度，而不抵消任务收益。

# Q4 相关工作与关键人物

* **全双工交互系统。** dGSLM、Moshi、SyncLLM 以及基于预训练 LLM 的双工改造；Full-Duplex-Bench 系列评测停顿、附和音、轮次转换和打断，v3 加入了基于真实不流畅语音的工具使用。
* **前后端智能体。** Realtime-Venus 的异步 Harness、JoyAI-VL-Interaction（每秒在说话、沉默和委派中选择）、DuplexOmni（可插拔思考层）、Hu 等（委派 token 加流式 ASR 送入文本后端）、SALMONN-duo（用成本感知 RL 决定何时委派）、DuplexAgent-RSI（根据交互轨迹改进委派框架）。本 wiki 中的 [Gander](../papers/2609.08977.md) 是另一种前后端设计，其公开的 FDB v3 Pass@1（GPT-5.6 后端下 40.0）出现在 Duopra 的参照点中。
* **直接工具使用与混合路由。** GPT-Realtime、NemotronLabs VoiceChat、Qwen-Audio-3.1-Realtime（用 GRPO 训练工具使用）、DuplexSLA、SHANKS、Qwen-Audio-Agent。
* **关键人物。** Chiyu Chen 等，来自上海交通大学与腾讯（Chenglu Sun 标为项目负责人）及布里斯托大学；HTML 中 Gongshen Liu 与 Zhuosheng Zhang 标为通讯作者。可能的批评者：Realtime-Venus 团队（其模型既是基座也是主要基线）和 Full-Duplex-Bench 作者。

# Q5 核心方法

1. **统一动作空间。** Duopra 保留 Realtime-Venus-Audio（RV-Audio）的流式循环（思考器 LLM 每 1 秒单位输出双工控制 token 和文本；发声器根据投影后的思考器隐藏状态把文本说出），但把原本私有的自由文本委派换成私有 `<delegate>` 片段中的结构化 JSON：`select` 获取工具 schema，`call(f, args)` 调用任一已暴露工具。后端智能体就是 `query(task)`，其参数是一段自包含的自然语言任务，必须带上用户最新给出的值、步骤和依赖。直接调用与委派共用一个接口和一个成功标准；在 Both 下由模型自己选路，没有单独的分发器。
2. **阶段 1：协议 SFT。** 训练思考器（Transformer 层和最终归一化；嵌入、输出头、音频编码器和语音模块冻结），数据为 12,800 个合成语音会话（中英文），混合工具使用示范与能力保持对话，共 400 次更新、每次 32 个会话。产出 Duopra-SFT。
3. **阶段 2：全双工强化学习。** 在思考器上用 LoRA 和 Dr. GRPO，每组 G = 8 条流式 rollout，共享同一段脚本化用户音频和工具目录；直接调用打到模拟工具，阶段 2b 的委派交给冻结的 Qwen3.8-27B 后端；打分器把日志中的调用与标准调用比对并从日志读时间，评判模型对照当时可得的观测检查口头陈述。阶段 2a（7,908 个任务：直接调用、更正、澄清、打断、附和音）奖励时效（在 k_act = 3 个单位内行动 +0.1），对使用已被更正的值每个罚 -0.6，并给对话控制打分，产出 Duopra-RL1。阶段 2b 新增五类任务（有依赖和有条件的调用、不同工具可见性下的委派、失败恢复）和按结果分档的奖励：完整且有依据的执行在 3 个单位内 / 8 个单位内 / 更晚分别得 1.2 / 1.1 / 0.9，如实报告部分完成得 0.1 + 0.15c，编造结果得 -0.95，重复执行受罚，产出 Duopra-RL。
4. **阶段 3：只修投影器的发声器修复。** 冻结 Duopra-RL 思考器，只训练 370 万参数的思考器到发声器投影器，使其在 RL 隐藏状态上的 L2 归一化输出与基座投影器在原模型隐藏状态上的输出对齐（余弦损失），并加 L2-SP 惩罚使其靠近基座权重。产出 Duopra。

# Q6 实验设计

* **基准。** Full-Duplex-Bench v3（100 条不流畅英文录音、12 个模拟 API；分别有 66、18、16 条需要一次、两次、三次调用）衡量任务能动性；FDB v1.0 的接管率（turn-taking、停顿、打断、附和音）、FDB v1.5 和 VoiceBench 衡量对话与一般口语能力。
* **系统。** 在作者的流式管线中，以相同的 Qwen3-8B 后端和模拟 API 运行的基线：RV-Audio + Harness 与 DuplexOmni；无工具对照 RV-Audio 与 MiniCPM-o 4.5。Duopra 各检查点（SFT、RL1、RL、最终版）在 Direct、Backend、Both 下运行，冻结后端为 Qwen3-8B 或 DeepSeek-V4.1-Flash。商业与开源系统的公开结果只作为来自其他设置和评判模型的参照点。
* **协议。** 每条录音三个解码种子（每个配置 300 个会话）；Qwen3.8-27B 评判参数和回答；配对 95% 区间按录音级自助法计算，同一录音的三次运行放在一起；不涵盖训练运行间的波动。
* **诊断。** Pass@1 = Call × Pass|call 分解；匹配会话分析收益来源；互斥的结果类别（通过、参数错、缺失、多余、未调用）；训练阶段对比；发声器条件余弦相似度与投影器修复的 CER/WER。

该设计直接检验了发起假设（同一后端、不同前端），并分离了各阶段的效应；但每个阶段只训练一次，且阶段 2b 同时改变了任务和奖励（论文自己指出）。

# Q7 数据集与代码

FDB v3、v1.0、v1.5 和 VoiceBench 都是公开基准。训练数据为合成语音，覆盖七个领域的 56 个领域工具（阶段 1 增加 16 个设备工具，划分为 40 个训练、16 个验证、16 个测试工具；阶段 2b 用 84 个目录表达 32 个工具功能，共 2,688 个 schema）。论文给出项目页、GitHub（cyChen2003/duopra）和 Hugging Face 链接；本笔记未核对发布内容。训练在昆仑芯 P800 加速器上完成。

# Q8 证据质量

* **"瓶颈在发起"的诊断有充分支持。** RV-Audio + Harness 在 300 个会话中只有 31 个执行了领域调用（Call 10.3%，交接发生在 33 个会话，11.0%），其中通过 14 个（Pass|call 45.2%，Pass@1 4.7%）。Duopra（Backend，同样的 Qwen3-8B）达到 Call 86.7%、Pass|call 51.5%（Pass@1 44.7%；提升 +40.0，95% CI [31.3, 48.7]）。在基线确实发起调用的 31 个会话上，Duopra 通过 12 个，基线 14 个；它的全部收益来自其余 269 个会话，其中通过了 122 个。换用 DeepSeek 提高了 Pass|call（+12.5，CI [4.8, 20.4]）却降低了 Call，Pass@1 的变化（+4.7，CI [-2.3, 11.7]）不显著。这些共同支持"更强的后端无法补上从未发出的请求"。
* **直接与委派。** Direct 47.7%，Backend 44.7%（Qwen3-8B），Both 44.3%；Duopra 各暴露方式在 Pass@1 上的差异都不显著。在 Both 下，Duopra 用 Qwen3-8B 时只在 1 个会话中委派，用 DeepSeek 时为 0，所以 Both 测的是原生调用，而不是路由能力，论文也这么说。Backend 更耗时（Qwen3-8B 下事实性回答延迟 14.85 秒对 10.42 秒），并且在 Qwen3-8B 下参数错误的会话更多（+10.7 个百分点，CI [4.3, 17.3]）。
* **训练阶段。** 阶段 2a 提高了调用频率但几乎没提高 Pass@1（26.0% 到 26.7%，+0.7，CI [-5.0, 6.0]）；阶段 2b 带来 +21.0（CI [15.3, 27.0]），多调用请求从 0.0%（RL1）升到 27.5%。未调用的会话减少之后，参数错误成为最大的失败类别（Duopra Direct 为 300 中 58 个），例子是订单号中的字母 O 变成了数字 0。
* **对话能力只部分保留。** 与 RV-Audio 相比，Duopra 的轮次接管率（59.1 到 75.6）、停顿接管率（18.1 到 5.4，越低越好）、打断接管率（79.5 到 91.3）都有改善。但打断接管率从 97.0（SFT）和 96.5（RL1）降到 91.3，轮次接管延迟从 2.27 秒升到 2.75 秒，所有后训练检查点在 FDB v1.0 的 55 个附和音样本上都不再产生附和音。"任务能动性可与关键对话能动性共存"只有带上这些限定才准确，论文也说明了这些限定。
* **投影器修复。** 与原始发声器条件的平均余弦从 0.929 升到 0.974；在 221 条语句的集合上 CER 从 6.01 降到 2.58，WER 从 9.74 降到 7.66。但同一批语句也用于从四个候选中选出投影器，所以这是选择集上的证据，论文有说明。
* **可比性。** 公开的商业系统数字（GPT-Realtime 60.0、Gemini Live 3.1 54.0、Gemini Live 2.5 49.0）来自不同设置和评判模型；"与 Gemini Live 2.5 相当"只是背景参考。
* **读者核查。** 所有 Pass@1 值都是 300 个会话的整数计数（47.7 = 143/300，44.7 = 134/300，49.3 = 148/300，4.7 = 14/300），所查各行 Call × Pass|call 都能重现 Pass@1。波动只来自解码种子；每个阶段只训练一次。评测用的评判模型（Qwen3.8-27B）与阶段 2b 冻结的 RL 后端是同一个模型，可能在需评判的 Arg./Resp. 列上偏好训练出的风格，但 Pass@1 本身依据调用匹配（读者观察）。

# Q9 贡献

1. 把全双工能动性形式化为一个同时做对话决策和任务决策的因果策略，直接调用与委派共用信息充分性和成功标准。
2. 交接上限分解（Pass@1 = Call × Pass|call），以及前后端基线主要失败于发起的证据。
3. Duopra：后端智能体作为自然语言参数工具的统一 JSON 动作接口，经协议 SFT、按结果分档的流式 RL 和只修投影器的发声器修复训练而成。
4. 在 FDB v3 上、同一后端下，比基座前端提升约十倍的 Pass@1，并同时报告对话和语音上的代价。

# Q10 后续方向

* **恢复附和音。** 在阶段 2 中加入附和音任务或奖励，或把只修投影器的思路扩展到控制 token 策略，检验任务收益能否保留（论文指出这仍是开放问题）。
* **参数忠实度。** 参数错误已是最大的失败类别；逐字母拼读的标识符（B-O-B、P-O-9-9-9）提示可以设计针对性奖励，或"调用前复述确认"的行为（读者建议）。
* **交互式用户。** FDB v3 使用预录请求和模拟 API；应在用户后续话语取决于智能体回复和结果的场景中评估（论文所述未来工作）。
* **真正的路由。** 既然 Duopra 在 Both 下几乎从不委派，可以构造部分工具只在后端可用的任务，并像 SALMONN-duo 那样带成本地衡量路由决策（读者建议）。
* **训练方差与其他基座。** 用多个种子重复各阶段，并在第二个双工基座模型上复现（读者建议；论文指出其他基座尚未测试）。
