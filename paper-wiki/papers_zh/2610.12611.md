# Q1 问题定义

* **输入（X）：** 一个软件类型（例如“电子表格”或“邮件客户端”）加上配套资源；除此之外没有任何针对单个应用的手写内容。
* **输出（Y）：** （a）一个可运行桌面应用的库，每个应用都有功能规格、各不相同的界面，以及经过 GUI 测试的行为；（b）以通过测试的功能为依据的自然语言 GUI 任务；（c）在这些任务上采集的轨迹，用于微调计算机使用智能体（computer-use agent，CUA）。
* **论文给自己设定的约束：** 界面与交互模式的*多样性*、每个规定功能在完整 GUI 流程中的*功能可靠性*，以及几乎不需要人工工程投入的*可扩展性*。
* **核心问题：** CUA 的训练数据要么来自一批固定的真实应用（把它们包装成可复现环境成本高，且容易对具体应用过拟合），要么来自托管在浏览器里的模拟软件（共用的 HTML/DOM 底座限制了交互深度和持久化工作流）。

# Q2 问题新颖性

不是新问题。为 GUI 智能体合成环境是一条活跃的研究线，论文引用了：InfiniteWeb 和 AutoWebWorld 生成网站和状态机网页世界，GUI-GENESIS 和 ScaleWoB 把软件合成为无后端网页，CUA-Universe 和 Gym-Anything 则包装现有软件。论文声称的不同在于产物本身：独立的桌面应用（Avalonia，编译后在 Ubuntu 虚拟机中运行），带持久化和文件流程，而不是网页；并且配有显式的结构多样性关口和 GUI 层面的“测试-修复”循环。

# Q3 科学假设

1. **结构必须被强制拉开。** 如果要求各风格变体至少在两个布局维度上不同，并通过树编辑距离关口，那么同一软件类别生成的界面就不会坍缩成同一种布局；不加约束的生成则会。
2. **修复需要 GUI 证据。** 如果修复由操作运行中的应用时观察到的失败驱动，可靠性会上升；只靠阅读源码的修复不会。
3. **合成软件可以迁移。** 如果智能体只在合成应用的轨迹上微调，它在从未见过的真实应用（OSWorld）上也会进步，说明学到的是通用 GUI 交互，而不是特定应用的操作步骤。

# Q4 相关工作与关键人物

* **在现有软件内合成数据。** OSWorld、Windows Agent Arena 和 AndroidWorld 让真实应用可以被可复现地用于评测；OS-Genesis、AgentSynth、ProCUA-SFT 和 EvoCUA 在这些应用内合成任务与轨迹；CUA-Universe 和 Gym-Anything 把现有软件配置成智能体环境；UI-TARS、OpenCUA 和 FedMABench 则精炼在线轨迹、采集人类演示或在去中心化数据上训练。
* **浏览器托管的合成环境。** InfiniteWeb、AutoWebWorld、GUI-GENESIS、ScaleWoB。
* **关键人物。** 上海交通大学（通讯作者 Siheng Chen）与浙江大学；Haoting Shi、Wenhao Wang、Tian Jin 和 Siheng Chen 同时是本文所引 CUA-Universe 的作者。可能的批评者：在真实应用上训练 CUA 的团队（OpenCUA、EvoCUA、UI-TARS），他们会追问合成应用的行为与真实应用相比如何；以及做网页环境合成的作者，他们会要求与浏览器托管数据做同等规模的对比。

# Q5 关键解决思路

三个阶段由使用 GPT-5.5 的 Codex CLI 智能体执行，另有一个独立的 GUI 智能体担任测试者。

* **设计。**
  * *FunctionDesigner* 分四步把软件类型扩展成规格：成熟产品的基线功能；领域专业功能（多条件检索、批量操作、历史记录、输入校验）；跨模块的完整工作流（含失败处理）；最后为每个功能写下一份契约（用户入口、动作、预期状态更新、可见响应、验收检查点）。
  * *StyleDesigner* 在同一组功能上写出多份风格规格，每份遵循一种布局原型；任意两份必须在四个布局维度（导航、空间组织、对象浏览、动作摆放）中至少两个不同。独立的 *SubStyleDesigner* 把每份规格落成 Avalonia XAML，并通过编译检查其有效性。
  * 每份蓝图被转成规范化的布局树（窗口、区域、面板、控件；去掉文字和颜色）。如果两两之间归一化树编辑距离的最小值低于 0.60，就重新生成最不独特的那份蓝图。
  * *IconDesigner* 和 *SubIconDesigner* 为每种风格生成 SVG 图标集，要求结构上不同，而不只是颜色不同。
* **实现。** *Coder* 构建完整应用，并写一份功能手册，为每个功能给出验收检查；*DevCoder* 对照手册审计绑定、逻辑、持久化、启动和文件接口，并补上缺口。
* **GUI 评估与修复。** *EvalTaskGenerateAgent* 在首次实现后根据手册一次性写出测试用例，此后测试集固定不变。GUI 智能体（Seed 2.1 Pro，鼠标键盘操作，每个用例最多 50 步）执行这些用例，记录轨迹、检查点证据、失败位置和修复建议，再交回给编码智能体。每个应用最多三个版本，全部用例通过则提前停止。一个设计令牌保真度分数（颜色、圆角、主色、字体和资源绑定的加权重合度；阈值 0.80）防止修复偏离蓝图；论文说明它不是感知意义上的图像相似度。
* **任务合成。** 根据手册和评估报告构建功能树；一项能力只有在引用了通过的用例、检查点或交互步骤时才算被支持。任务按三个难度规划（单一目标；带依赖关系的相关操作；每一阶段为下一阶段准备状态的多阶段流程），分为基于文件和空白状态两种形式，然后写成自然的用户请求，并附带内部规格：初始状态、结果判据、过程判据和预期终态。

# Q6 实验设计

* **合成。** 十二个类别（浏览器、聊天、代码编辑器、论坛、邮件、PDF、富文本编辑器、图像编辑器、幻灯片、电子表格、音乐播放器、视频播放器）；应用运行在隔离的 Ubuntu 22.04.3 虚拟机中。
* **训练。** 对 Qwen3.5-9B 的语言模型做全参数监督微调（SFT），视觉编码器和 merger 冻结；一个 epoch，学习率 5e-6，序列长度 16,384，使用 16 块 A800 GPU。候选轨迹由两个 GPT-5.5 评审打分，一个看结果（最后几条消息和截图），一个看过程（全部消息和至多十张采样截图）；两个分数都不低于 0.8 才保留。SoftwareGym 数据集在长度过滤前有 3,715 条轨迹、55,263 个序列化样本，过滤后 49,445 个。
* **评测。** OSWorld（来自八个应用领域的 244 个任务）和 SoftwareGym-Bench（每个类别选一个应用，每个应用十个人工核验的任务，共 120 个，带可复现的初始化器、程序化评估器，以及干扰对象和受保护对象）。使用 OSWorld 原生的上下文和工具协议，温度 1，100 步，每个任务三次独立运行。主指标是 Pass@3，即三次运行上的任务级成功；单次运行的平均值在附录 D。
* **基线。** 八个 API 模型（GPT-5.5、GPT-5.4、Gemini 3.1 Pro、Gemini 3 Flash、Seed 2.1 Pro、Seed 2.0 Pro、Qwen3.8-Flash、Qwen3.7-Plus），六个 32B 及以上的开放权重模型，以及 7-9B 的小型智能体（EvoCUA-8B、DART-GUI-7B、OpenCUA-7B、UI-TARS-1.5-7B、Qwen3.5-9B 基座）。
* **消融。** 完整设计对比只被告知“十个布局应当不同”的“简单”设计（每类十份蓝图，共 240 份）；在 36 个应用（每类三个）上，从同一个初版出发，对比 GUI 引导的修复和只看源码的修复；以及在规模匹配的条件下，分别用 SoftwareGym、OSWorld 应用或两者合并的轨迹训练。

# Q7 数据集与代码

代码在 [MrKiing-Jin/SoftwareGym](https://github.com/MrKiing-Jin/SoftwareGym)（抓取时 3 星），模型在 `huggingface.co/GothamLegend/SoftwareGym`。贡献列表称发布 182 个应用和 SoftwareGym-Bench；已读部分没有说明训练轨迹是否发布。已读文本也没有点名生成训练轨迹的模型（附录 E 只提到从“teacher schema”转换）。评测使用公开的 OSWorld；合成和评审依赖托管模型（GPT-5.5、Seed 2.1 Pro）。

# Q8 证据质量

* **有支撑的结论。**
  * *结构化的风格设计确实带来结构多样性。* 宏平均多样性（两两归一化树编辑距离的均值，0-100）完整设计为 83.6，简单设计为 4.9，十二个类别全部更高；十二组简单设计没有一组通过 0.60 关口，且每组都至少有一对布局树完全相同。
  * *让修复起作用的是 GUI 反馈。* 从相同的 50.4% 通过率出发，GUI 引导的修复达到 70.5%，再到 83.1%；只看源码的修复是 50.5%，再到 48.8%。最终 34.3 个点的差距，95% 分层自助法置信区间为 28.2-41.0，且 GUI 引导的修复在全部 36 个应用上都更好。
  * *按流水线自身的测试，库是可靠的。* 182 个应用的平均 GUI 通过率从初版的 54.9% 升到 81.1%，再到 91.5%。
  * *向真实应用的迁移在两个指标上都很大。* 在 OSWorld 上，Pass@3 从 41.39% 升到 56.97%，单次运行平均从 28.40% 升到 46.77%，八个领域的 Pass@3 全部提高（Chrome 28.26 到 58.70，VS Code 30.43 到 60.87，Calc 只有 27.66 到 31.91）。微调后的 9B 模型与 EvoCUA-8B（56.56%）持平，低于 EvoCUA-32B（67.62%）和所有 API 模型（67.62-79.51%）。
  * *成本。* 在 20 个应用的样本上：每个应用 237.3 分钟、1,480 万 token、1,718 次模型调用，估计 70.76 美元。
* **比标题结论更弱或更窄之处。**
  * *Pass@3 是三选优的数字。* 摘要中的 56.97% 是按三次运行来判定任务是否解决；微调模型单次运行的平均是 46.77%。相对基座的提升在两个指标上都成立，但与其他论文的单次得分比较时，应当只看 Avg@3 那几行。
  * *“严格域外”指没见过的应用，而不是没见过的软件种类。* 十二个合成类别中有八个是按 OSWorld 的应用领域选的（182 个应用中的 121 个），论文还测量了它们复现了对应真实应用多少功能（全部 49 个主要模块、78.8% 的具体功能）。训练中没有任何 OSWorld 应用、任务或轨迹，但训练分布是刻意按测试应用的功能来构建的（读者观察）。
  * *在 OSWorld 上，合成数据没有超过原生数据，加上它也没有帮助。* 规模匹配时，用 OSWorld 应用轨迹训练在 OSWorld 上得到 61.48% Pass@3，仅 SoftwareGym 为 56.97%，两者合并为 58.61%。单次运行平均分别是 48.06%、46.77% 和 47.10%，三者相差约 1.3 个点以内。“互补”的说法依靠的是 SoftwareGym-Bench（33.3%、40.0%、47.5%）。已读文本没有说明 OSWorld 应用的训练任务是否与 244 个评测任务重叠；如果重叠，那一行就是域内参考，而不是对等的竞争者。
  * *SoftwareGym-Bench 对微调模型来说是分布内的。* 它的十二个应用来自同一个库；已读部分没有说明这些应用，或与它们共用功能规格的同类变体，是否被排除在训练之外。每个应用只有十个任务，所以各类别的分数以 10 个点为步长变动。
  * *91.5% 的可靠性数字是模型判定的。* 测试用例由实现自己的功能手册生成，由 GUI 智能体执行并评判，因此“通过”是模型记录的检查点证据，“失败”也可能是测试者而非应用的问题。应用带着一些未通过的用例进入库；任务合成随后只使用有通过证据的功能。
  * *只训练一次，没有方差。* 评测用了三次运行，但每个模型只训练一次。
  * *没有与浏览器托管的合成方法对比。* 论文的出发点之一是网页限制了交互深度，但没有与用同等规模网页合成数据训练的模型做比较。

# Q9 贡献

* 一条多智能体流水线，把一个软件类型变成多个结构不同、经过 GUI 测试的桌面应用，并带有量化的多样性和保真度关口。
* 一个经过测量的结果：让智能体编写的应用变得可靠的，是 GUI 层面的失败证据，而不是源码层面的自我审查。
* 发布十二个类别的 182 个应用，以及一个带程序化评估器的 120 任务基准。
* 证据表明，仅在合成桌面软件的轨迹上做 SFT 就能迁移到真实的 OSWorld 应用，按单次运行平均衡量时接近在真实应用上做同等规模训练的结果。

# Q10 下一步

论文结论没有陈述局限性或未来工作；以下均为读者建议。

* **留出类别。** 去掉与 OSWorld 对齐的八个类别（或只用另外四个）来训练，以测量迁移中有多少来自与测试应用的功能相似性。
* **规模曲线。** 报告 OSWorld 得分随应用数量和每类变体数量的变化，看是多样性还是数量在驱动提升；结构多样性分数让这一点可以直接测量。
* **检查测试者。** 让人或程序化检查抽样审计 GUI 智能体的通过/失败判定，因为整个可靠性结论和任务证据关口都建立在这些判定之上。
* **与网页合成对比，并换更强的基座。** 与同等规模的 ScaleWoB 或 GUI-GENESIS 式数据比较，并在更大的模型上重复；[AutoGUIWorld](../papers/2610.01215.md) 在更大的模型上看到提升集中在多应用任务，而 Chrome 任务反而变差。
* **项目契合（读者笔记）。** 修复消融清楚地印证了本仓库智能体已经遵循的一条规则：验证必须实际运行产物，因为只看源码的审查让通过率原地不动、甚至略降。
