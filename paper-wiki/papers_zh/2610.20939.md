# Q1 问题定义

* **输入（X）：** 一个可执行任务 x = (E, s_0, g, V)：环境 E（一台 Android 设备、一台桌面虚拟机或一个浏览器应用）、初始状态 s_0（应用记录、文件、账号，以及当前日期等设置）、自然语言指令 g 和验证器 V。每一步，harness 根据指令、交互历史和当前观察（截图，在计算机上还有命令输出）构建上下文 c_t。
* **输出（Y）：** 一条由模型决策组成的轨迹。每一步是一次决策，可以输出一组有序的 GUI 动作（点击、输入、拖动、快捷键、打开应用、系统按键、等待）、shell 命令（仅计算机）、API 调用、`ask_user`，或带最终答案和自报状态的 `terminate`。验证器通过带权重的二元判据为最终状态（必要时也为轨迹）打分：奖励 r = Σ w_j b_j / Σ w_j 给出部分得分，成功 S 是所有必需判据的乘积。
* **平台问题：** 在强化学习所需的规模上，让评测、数据收集和在线 RL 作用于同一个智能体（每次尝试都需要一台重置过的设备），并持续提供足够多真实、可验证的任务，让 RL 一直有东西可学。
* **训练问题：** 用在线 RL 在合成任务上训练一个同时覆盖移动端和计算机的 GUI 策略，并在它从未训练过的基准任务上评判。

# Q2 问题新颖性

论文认为现有 GUI gym 各自只解决了问题的一部分（表 1）。基础设施类 gym（BrowserGym、WebGym、MobileGym、SCALECUA、ClawGUI）让评测或训练可复现，但只覆盖一个平台；公开了训练代码的，最多也只能并行运行数百个环境。数据类 gym（CUA-Gym、Gym-Anything、GUI-Genesis、PhoneWorld）增加了应用和任务，却既不公开训练代码，也不提供运行现有基准的方法；它们的任务通常从单个输入文件，或从同一应用所有任务共用的样例数据出发。训练配方类工作（DigiRL、MobileRL、WebRL、ComputerRL、UI-TARS-2、EvoCUA-1.5、[UI-Mate](../papers/2608.15930.md)）大多为自己研究的领域单独搭建环境，跨领域策略常常是把各领域的 RL 专家模型合并得到。另一个实际动机是 harness 漂移：评测和训练各自保留一份智能体代码时，预处理、历史截断或提示模板会逐渐分化，作者"反复看到这种漂移"表现为训练奖励与评测分数之间无法解释的差距。

# Q3 科学假设

如果评测、数据收集和训练共用一个 harness 和一条 rollout 路径，并且平台能大规模提供可重置的模拟应用（mocked app）、前后一致的跨应用世界和经过执行测试的验证器，那么：（1）在合成的移动端和计算机任务上做一次联合在线 RL，可以得到一个小型 GUI 策略，它能解决训练环境中的新任务，并在从未训练过的环境中也有提升；（2）联合训练优于合并分别训练的领域专家；（3）在固定 rollout 预算下，合成任务越多，泛化越好；（4）在真实应用的克隆中学到的技能，可以迁移到物理设备上的真实应用。

# Q5 关键解决思路

**一个 harness，一条 rollout 路径。** 每种环境与智能体配置只有一个 harness：负责构建上下文、调用策略、解析输出和派发动作。rollout 调度器把尝试排队，worker 通过环境客户端租用一个实例并运行 harness，轨迹和验证器奖励写入缓冲区。评测对轨迹做汇总，数据收集把它们存下来（例如作为 SFT 数据），RL 则用它们训练并把新权重同步到推理引擎，所以修好 harness 的一个问题，三种工作负载同时受益。环境管理器提供五个操作（申请实例、观察、重置到某个任务、执行一步、评估）；其后负责实例供应、会话租约、重置、清理、奖励计算和轨迹存储。环境适配器保留每个基准原生的初始化和验证器，其中没有任何与 RL 相关的代码。

**能承受规模的 rollout。** 手机以 ReDroid 容器的形式直接运行在宿主内核上，避开标准模拟器所需的嵌套虚拟化，并通过恢复一份"黄金" `/data` 快照来重置。桌面端加入更严格的就绪检查、每个实例独立的端口和缓存、尝试中途失败时的容器恢复，并等待应用完成保存，以免验证器读到写了一半的状态。浏览器任务运行在无头 Chromium 中。实例供应是异步的，并有预热池；截图通过对象存储传输而不放在控制消息里。故障被限制在发生它的会话之内：租约拒绝已被替换的 worker 发出的动作，动作标识符让重试只生效一次，验证器在独立的进程组中运行。环境故障与零奖励分开记录，基础设施故障不会进入训练信号。

**按窗口组织的历史（window-wise history）。** 常见的"保留最近 k 张截图"策略每一步都会改变提示前缀，使 KV 缓存无法复用。MAI-Gym 把步骤分成每窗 K = 10 步、相邻窗口重叠 O = 2 步的窗口。窗口内只追加内容；到窗口边界时，较早的截图折叠为占位符，文本保留。于是前缀每 K − O 步才变一次，一条轨迹后续的请求被路由到持有其缓存的引擎。训练复用相同的窗口作为样本：每个窗口是一条因果序列，损失只作用于其中新增的步骤，并精确重放采样时的 token；当各轮不能构成一致的前缀时，退回到逐步样本（见 [上下文压缩](../concepts/context-compaction.md)）。

**合成任务的每一个组成部分。** 每个阶段都是一个由 Claude Code 等编码智能体执行的智能体技能：

* *模拟应用（E）。* 七个真实应用的克隆，这些应用的操作无法撤销：12306（铁路购票）、中国建设银行、滴滴、美团、大众点评、抖音和小红书。每个克隆以真实应用为参照从零构建，后端可重置，并由测试人员在克隆和真实应用中执行相同任务来核对。另有 42 个完全新造的应用，是基于共享 HTML5 模板的确定性状态机；它们通过参考动作序列、重置测试、拒绝未动过和随机动作的状态，以及浏览器内外执行结果一致性来验证。
* *跨应用世界（s_0）。* 由一个人物设定（persona）和一个场景（时间线、事件、约束）生成共享人物、事件和事实的文件与应用记录，例如项目简介、预算表、邮件往来和日历条目。任务于是可以说"把预算评审挪到修订版预算表截止日的后一天"，而不是"创建一个名为预算评审的事件"。
* *任务与验证器（g, V）。* 总结模型失败 rollout 的诊断报告引导生成器针对薄弱能力出题。每个任务规格在任何代码出现之前就固定成功判据和一份对策略隐藏的答案上下文。随后由两次相互独立的调用分别写出黄金代码（直接把环境设为完成状态）和验证器代码，并用一次奖励审计把验证器与规格对照。验证器必须在初始状态得 0、执行黄金代码后得 1、重置后再得 0。之后由多个模型通过智能体接口尝试该任务，并审查其轨迹的可执行性、难度、清晰度和奖励投机（reward hacking）风险。模型参与构建任务，但 RL 奖励只来自验证器的执行结果。

**在线 RL 配方。** 训练器基于 slime（训练用 Megatron-LM，rollout 用 SGLang），支持 GRPO、DAPO、GSPO、REINFORCE++、SAO 和 PPO。主配方是 [GRPO](../concepts/grpo.md)，组大小为 8，按 token 计损失。*策略自适应任务采样*给未见过的和有时能解出的任务完整的一组尝试，给从未解出和已掌握（成功率高于 η = 0.8）的任务分别 4 次和 2 次，使 rollout 花在优势不为零的地方；一个任务的优势在其所有尝试完成后才计算。*训练与 rollout 一致性*检查在每个 token 上比较训练器和 rollout 的对数概率，并用两者 KL 散度的 k3 估计量作为运行闸门，以发现损坏的内核、错位的历史或版本不一致。

# Q6 实验设计

* **模型与训练。** MAI-Gym-9B 从 Qwen3.5-9B 出发。先用混合移动端与桌面数据做 SFT 预热，教会模型执行混合的 GUI 与 CLI 指令；再做一次联合 GRPO 训练，任务为 MobileWorld 和 OSWorld 环境中的 5,000 个合成任务，只用代码验证器奖励，并采用策略自适应采样和 K = 10、O = 2 的窗口。训练使用 512 张 GPU、最多 20,000 个并发环境，约 96 小时；学习率恒定为 1e-6，KL 损失系数为 1e-3（无熵奖励）。
* **基准。** 平台支持的十个中用了七个：MobileWorld（仅 GUI，117 个任务）和 OSWorld-Verified（361 个）属于*任务分布外（Task OOD）*：与训练同一环境、任务未见过。AndroidWorld（116）、MobileGym（256，部分得分）、OSWorld 2.0（108，二元/部分得分）、MacAgentBench（676）和 MyPCBench（184，完美任务率）属于*环境分布外（Env OOD）*：环境从未用于训练（OSWorld 2.0 还加入了 31 个自托管网站和长流程）。评测使用训练时的 harness、温度 0.0、每任务 3 次试验，并对因环境故障结束的尝试重跑。
* **基线。** 前沿 API 模型（Claude Opus 4.8、GPT-5.5、Qwen3.8-Max）和开源的 Qwen3.8-27B；GUI 智能体 GUI-Owl-1.5（8B、32B）、UI-Venus-2-9B、SCALECUA-Qwen3.5-9B、EvoCUA-1.5-32B、CUA-GYM（35B-A3B、397B-A17B）和 Qwen-CUA（397B-A17B）；以及 Qwen3.5-9B 基座。除作者自己运行的八个条目外，基线数字都来自已发表的报告和排行榜。

# Q8 证据质量

* **有支持的结论。**
  * *9B 模型在训练环境中的强结果。* MAI-Gym-9B 在 MobileWorld 上达到 78.4%，在 OSWorld-Verified 上达到 76.2%，基座分别为 18.0% 和 41.8%（表 4）。比 UI-Venus-2-9B 高 3.2 和 5.4 个点，比 GUI-Owl-1.5-8B 高 40.2 和 23.3 个点。在 MobileWorld 上它也超过 Claude Opus 4.8（69.2%）、GPT-5.5（62.4%）和 Qwen3.8-Max（77.8%）；在 OSWorld-Verified 上与 GPT-5.5 相差 2.5 个点以内；在报告的 GUI 智能体中只有 Qwen-CUA（86.2%）更高。
  * *RL 的作用超出训练环境。* 大部分收益来自 SFT（任务分布外平均从 29.9 升至 66.4，环境分布外平均从 18.8 升至 32.3）。联合 RL 再把跨领域平均从 44.1 提到 50.5（移动端 +8.7，计算机 +4.2），并提升了每一个环境分布外基准，平均 +4.2。
  * *在这组比较中，联合 RL 优于合并。* 使用两个专家的合计预算，联合 RL 达到 78.4 和 76.2，高于所有合并方案。最好的合并在 MobileWorld 上为 76.4（50/50），在 OSWorld-Verified 上为 74.8（30/70），没有任何合并能在两个领域同时领先（表 7）。
  * *固定 rollout 预算下，合成任务越多越好。* 500、1,000 和 5,000 个任务在 MobileWorld 上分别得到 69.2、73.5 和 78.4，在 OSWorld-Verified 上得到 69.7、70.9 和 76.2（图 8）。
  * *克隆训练部分迁移。* 在 52 个配对的 12306 任务上，只在克隆中做 RL，使克隆内成功率从 36.5% 升至 73.1%，物理手机上真实应用的成功率从 28.8% 升至 48.1%。在新造应用上做 RL，使留出任务成功率从 25.8% 升至 45.2%，耗尽步数预算的尝试从 27 次降至 5 次，平均长度从 33.3 步降至 16.4 步。
  * *基础设施的主张有测量支撑。* 1,000 个新环境的启动时间为 328.4 秒（移动端）、88.9 秒（计算机）和 94.2 秒（浏览器）；重置中位数为 165.0、37.2 和 6.0 秒；因环境故障而重跑的尝试占 1.2%、1.9% 和 0.0%（表 5）。与逐步历史相比，按窗口历史使前缀缓存命中率翻倍（42.5% 到 85.9%），每条轨迹的训练 token 减少 84.7%，更新时间从 2166.4 秒降至 810.9 秒，代价是 rollout 速度降低 18.9%（表 6）。
* **比标题弱或更窄的地方。**
  * *"10B 以下最优"只在两个任务分布外基准上成立。* 在从未训练过的环境中，MAI-Gym-9B 在 AndroidWorld（75.9 对 80.2）和 MobileGym（46.5 对 52.7）上落后于 UI-Venus-2-9B；在计算机环境分布外基准上远低于前沿模型，例如 OSWorld 2.0 为 3.7/11.3，而 Claude Opus 4.8 为 20.3/54.8，MyPCBench 为 15.2 对 62.0（笔记作者对表 4 的解读）。
  * *任务分布外其实是同一环境内。* 5,000 个训练任务是在 MobileWorld 和 OSWorld 环境中合成的，所以两个主要基准与训练共享应用、文件和界面布局。正文说基准任务从未出现在训练中，但没有描述对合成任务与基准任务做近似重复检查（笔记作者的观察）。
  * *基线来源不一。* 大多数基线数字来自各自使用自己 harness 的已发表报告和排行榜，而 MAI-Gym-9B 运行在它的训练 harness 中。论文本身的前提是仅改 harness 就会改变分数，所以几分之差的跨模型差距难以归因（笔记作者的推断）。
  * *单次运行。* 每种训练配置（联合、专家、任务规模实验、SAO）看起来都只运行了一次，没有随机种子或方差，SAO 的比较是从曲线上读出的。合并比较只覆盖三种权重。
  * *迁移不完整。* RL 之后克隆与真实应用的差距从 7.7 个点扩大到 25.0 个点，所以克隆上的收益高估了真实应用上的收益。真实应用测试只有一个应用中的 52 个任务。
  * *诊断闭环没有多轮检验。* 论文描述并使用了失败驱动的合成，但说明尚未评估"诊断、合成、再训练"的多轮重复。

# Q9 贡献

* 一个开放平台：通过每种配置一个 harness，统一移动端、计算机和 Web 上的 GUI 智能体评测、数据收集和在线 RL，集成十个基准，并做了 20,000 实例的规模测试。
* 面向大规模 GUI RL 的系统技术：容器原生的 Android 与快照重置、带预热池的异步实例供应、把基础设施故障挡在奖励之外的故障隔离、对 KV 缓存友好且复用为训练样本的按窗口历史、策略自适应任务采样，以及基于逐 token KL 的训练与 rollout 一致性闸门。
* 覆盖任务全部四个组成部分的合成流水线：可重置的真实应用克隆和新造应用、基于人物与场景的跨应用世界，以及先定需求、只有通过"初始-完成-重置"执行测试和多模型轨迹审查才被接受的验证器。
* MAI-Gym-9B：一次联合 RL 得到的单一 9B 移动端与计算机策略，并公开权重、49 个应用和 2,000 个已验证任务。
* 证据表明：联合 RL 优于专家合并；固定 rollout 预算下任务数量重要；克隆训练能部分迁移到物理手机上的真实应用。

# Q10 下一步

* **作者提出的。** 评估多轮"诊断-合成-再训练"；通过 Web 适配器把合成技能用于新应用；在共享接口上比较更多 RL 算法。
* **缩小克隆与真实之间的差距（笔记作者建议）。** 衡量克隆的哪些差异（布局、延迟、弹窗、登录状态）造成差距扩大，并在任务选择中混入少量真实应用评测。
* **在两个训练环境之外训练（笔记作者建议）。** 既然 RL 收益在训练环境内最大，可以在类似 AndroidWorld 或 macOS 的环境中合成世界，检验与 UI-Venus-2-9B 的环境分布外差距是否缩小。
* **报告方差和同 harness 基线（笔记作者建议）。** 用 MAI-Gym 自己的 harness 重跑同规模基线（UI-Venus-2-9B、SCALECUA-Qwen3.5-9B），平台让这件事很便宜；并为联合与合并的比较报告多个随机种子。
* **与"代码即动作"结合（笔记作者的关联）。** 同一团队的 [OpenGCUA](../papers/2610.22200.md) 发现，对冻结的前沿模型，覆盖 GUI 和 shell 的程序优于批量 GUI+CLI 动作。MAI-Gym-9B 使用批量动作，因此在 MAI-Gym 中训练一个会写程序的小策略，可以检验这一发现在 RL 之后是否仍然成立。

# 相关

* [GUI 与计算机使用智能体](../topics/gui-computer-use-agents.md) - 在移动端、计算机和 Web 上评测并用 RL 训练 GUI 智能体的单一平台，以及用它训练的 9B 联合移动端与计算机策略。
* [智能体环境](../topics/agent-environments.md) - 把可重置的模拟应用（真实应用克隆和新造应用）、基于人物设定的跨应用世界和经执行测试的验证器用作 RL 环境，并测量从克隆到真实的迁移。
* [智能体微调](../topics/agent-fine-tuning.md) - 跨领域联合在线 GRPO 与专家合并的对比、策略自适应任务采样、按窗口打包，以及训练与 rollout 一致性的 KL 闸门。
* [OSWorld](../concepts/osworld.md) - OSWorld-Verified（361 个任务）是任务分布外的主要基准，得 76.2%；OSWorld 2.0（108 个任务）是环境分布外基准，得 3.7/11.3；公开的 2,000 个任务中有一半在 OSWorld 环境中合成。
* [AndroidWorld](../concepts/androidworld.md) - 环境分布外基准（116 个任务），MAI-Gym-9B 得 75.9%，低于 UI-Venus-2-9B 的 80.2%。
* [MobileWorld](../concepts/mobileworld.md) - 其仅 GUI 划分（117 个任务）是移动端的主要基准，得 78.4%；一半合成训练任务在其环境中生成。
* [WebArena](../concepts/webarena.md) - 平台集成的三个 Web 基准之一（812 个任务，30 步上限）；MAI-Gym-9B 没有在其上评测。
* [GRPO](../concepts/grpo.md) - 主要 RL 配方（组大小 8、逐 token 损失、KL 损失 1e-3），配合策略自适应预算，减少奖励全相同的组浪费的 rollout；并与 SAO 比较。
* [上下文压缩](../concepts/context-compaction.md) - 按窗口历史在窗口边界把较早截图换成占位符以复用 KV 缓存，同样的窗口又作为训练样本。
* [Agent-World](../concepts/agent-world.md) - 作为让环境与智能体共同演化的方法、以及 RL 环境合成工作被引用。
* [EnvScaler](../concepts/envscaler.md) - 作为支撑工具使用 RL 进展的可扩展、可验证环境的例子被引用。
* [OpenGCUA](../papers/2610.22200.md) - 同一团队在冻结前沿模型上的 harness 研究，用代码执行代替批量 GUI+CLI 动作。
* [MAI-UI](../papers/2512.22047.md) - 同一团队较早的基础 GUI 智能体，也是 MobileWorld 基准的来源。
* [UI-Mate](../papers/2608.15930.md) - 作为以环境为依据的训练改进 GUI 智能体训练闭环的配方之一被引用。
* [SoftwareGym](../papers/2610.12611.md) - 同样在合成软件上训练 Qwen3.5-9B 的计算机使用能力，但用的是在经 GUI 测试的桌面应用上做 SFT，而不是在线 RL；它的 OSWorld 划分和指标不同，数字不可直接比较（笔记作者的关联）。
