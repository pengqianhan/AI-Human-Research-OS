# Q1 问题定义

* **输入（X）：** 散落在各独立仓库中、已完成的 Lean 形式化项目，内容是有名的数学结果，由人、AI 或二者合作写成，各自锁定不同的 Lean 与 Mathlib 版本；以及源源不断的 Lean/Mathlib 新版本。
* **输出（Y）：** 一个持续可构建的档案库。每个收录项目都能在当前共享的 Lean/Mathlib 环境下编译，并通过内核、linter 与准入检查；每个项目保留署名与来源，其结果可被后续工作查找、检查和导入。
* **核心问题：** AI 让产出证明变得便宜，于是检查以及*保持可复用*成为瓶颈。Mathlib 因严格的人工审核大致线性增长，且缺少大量研究级内容；与此同时，独立的形式化仓库会随 Lean 与 Mathlib 的变化而失效。问题在于：在机械检查和人类监督之下，AI 智能体能否承担发现、导入、升级修复、优化和审阅等工作，让一个大型形式化档案库保持可用。

# Q2 问题新颖性

部分新颖。维护型形式化档案库早已存在：Isabelle 的 Archive of Formal Proofs（AFP）把投稿的形式化与审阅、持续维护结合起来；在 Lean 生态中，Mathlib 把一切整合进统一 API，Tau Ceti 以更严格的性能门槛整合投稿，Palomar Registry 则登记彼此独立的仓库。新的是维护*模式*：各项目作为独立、署名的开发保留，但放在一起构建；而大部分周期性劳动——寻找合格项目、导入、每次升级后修复、精简证明、审阅命题——交给智能体。这篇论文是运行记录而非对照实验。它对智能体研究的意义在于：这是少见的长期部署案例，智能体的工作持续受到硬验证器（Lean 内核）和较软的 LLM 命题忠实度审阅的双重检查。

# Q3 科学假设

如果一个档案库同时具备硬正确性判据（Lean 内核）、严格的机械准入规则、针对命题忠实度的 LLM 审阅，以及负责发现、修复和优化的定时智能体任务，那么由智能体协助的维护就能：（a）在每次依赖升级后恢复数百个独立编写项目的兼容性；（b）在不破坏库的前提下缩小并加速它；（c）形成一个后续研究形式化真正会复用的档案库。论文用自身的运行记录而非专门设计的检验实验来支持这些主张。

# Q4 相关工作与关键人物

* **档案库与共享库。** AFP（Isabelle）；Mathlib；Reservoir（Lean 包索引）；Rocq Platform；Software Heritage；以及 Lean 生态中的 Tau Ceti 与 Palomar Registry，论文表 9 从投稿、维护、验收和文档策略几方面做了对比。
* **发现、形式化与复用。** TheoremSearch 和 TheoremGraph（跨非形式与形式来源检索和连接命题）；LeanDojo 与 LeanAgent（用于构造证明的检索与学习）；项目级基准；半自主形式化；以及 **LeanEval 结构审计**，这是论文关于复用的外部证据。
* **修复与审阅。** 证明兼容性研究、证明迁移、APRIL（基于编译器反馈的证明修复）；命题忠实度评估方法；专家对生成数学的评估，强调除了补齐证明缺口，还需要恰当的定义、忠实的命题和好用的库设计。
* **动因。** OpenAI 的《Ten Advances in Mathematics and Theoretical Computer Science》与《Finite Time Blowup for Navier–Stokes》在发布长篇 AI 生成论证时附带了 Lean 形式化；其中 Navier–Stokes/Euler 的开发现已收录进档案库。
* **关键人物。** 唯一作者 Vasily Ilin。他致谢 Justin Asher 为 Lean Pool 的共同创建者（初始发现工具与 CI），以及 Austin Letson 贡献的证明精简。可能的批评者：Mathlib 维护者（可能反对不经人工审阅就收录代码），以及 Tau Ceti 与 AFP 社区。

# Q5 关键解法思路

把*正确性*（完全交给内核和机械检查）与*维护劳动*（主要交给智能体）分开，人类负责准入决策与监督。

* **准入规则。**
  * 不得有 `sorry` 或 `admit`，除 `Classical.choice`、`propext`、`Quot.sound` 外不得引入公理。
  * 不得使用 `set_option`、未检查的声明、linter 豁免、整体导入 Mathlib，或绕过资源限制的机制。
  * 许可证须为 Apache-2.0 或 MIT。
  * 每个项目须有一张卡片，写明作者、上游来源、证明来源（人写、AI 写或混合），以及配有非形式陈述的主要结果。
  * 开放问题放在单独的挑战板上，其解答要与登记的命题核对。
* **CI：** 全库构建、警告检查、Mathlib 的环境与风格 linter、档案库特有检查（卡片、署名、公理、证明与文件大小、绕过尝试），以及编译后环境审计。性能分析只是建议性的，不作为合并门槛（与 Tau Ceti 不同）。
* **定时智能体任务**（提示词加一个主机运行器，放在单独的自动化仓库中）：近期与早期项目发现 → 带署名的导入 PR；审阅并修复待合并 PR；项目优化；处理维护者问题；向 Lean Zulip 频道发布公告。
* **依赖升级** 作为单独的工作流运行：检测新版本，在新版本下探测每个项目，把每个失败项目分派给一个修复智能体，汇总补丁，构建合并后的档案库，并开出草稿 PR。
* **LLM 数学审阅：** 检查忠实度、新颖性、重要性、来源和代码质量。后期版本把大改动拆成若干源码片段，并记录哪些范围真正给模型看过。
* **展示站点与检索：** 每个项目的依赖图把每条非形式主张连到其 Lean 命题，另有语义搜索（Octo），读者可以在导入前找到结果并核对其假设。

# Q8 证据质量

* **有支持：**
  * *兼容性可以大规模恢复。* 升级造成的破坏很大：历次升级中编译失败的项目分别为 59 个中 44 个、91 个中 58 个、143 个中 100 个、145 个中 19 个、148 个中 3 个、191 个中 97 个。在迁移到稳定版 Lean 时，97 个修复任务中 95 个成功，最终被接受的迁移通过了合并构建和全部仓库检查。每次被接受的升级改动 4,676-25,583 行。
  * *全库精简有效。* 被接受的改动最多删掉 54,965 行（降低繁饰成本，构建快 5.8%）和 45,217 行（全库压缩，快 3.3%）。
  * *确有复用。* 在 LeanEval 结构审计中，Lean Pool 是被匹配最多的外部仓库。
* **弱于标题所示：**
  * *更短不一定更快。* 贡献者的证明精简删掉 12,515 行，干净构建却*慢了* 5.4%（21.83 → 23.01 分钟），不过内存用得更少。每对前后测量都只是共享虚拟机上的单次运行，且虚拟机同时在跑后台任务。
  * *修复并非完全自主。* 两个失败的修复任务（图的基本群、不完备性定理）以及遗留的警告和 API 断裂，是靠进一步的智能体辅助整合解决的。这次整合*加强了辅助假设*（可测性、σ-有限性、极大性）。论文指出，构建成功并不证明每条声明在升级前后等价——定理所陈述的内容可能被悄悄改变。
  * *LLM 审阅的证据薄弱。* 普查只统计结论和 PR 结果，不统计审阅是否正确。同一 PR 的报告对只有 69 组，其中 37 组一致（约 54%，读者计算），同一修订版本的报告对为 0。该服务在观察日之前已被手动停用。记录的价格为：285 份按 API 计费的报告共 308.52 美元，仅 6 份按 Codex 配额计的报告共 752.38 美元（均为等价 API 估价，非发票）。
  * *智能体劳动量未被测量。* 任务定义列出了职责，但论文说明它们不能确定历史上每项贡献由哪个模型完成。人工劳动和资金成本都没有记录，因此维护中人与智能体的分工比例未知。
  * *共享构建的代价。* 档案库比 Mathlib 更大、构建更慢：源码 323 万行对 233 万行，构建 60.28 分钟对 37.44 分钟，内存 20.03 GiB 对 7.35 GiB。
* **写作说明：** 人写部分只有一页，作者称其余部分几乎完全由 AI 生成。AI 使用声明称，所报数字均由保留的源记录重新计算，并通过源哈希校验与重建表格验证。本笔记按原文报告引用这些数字，未独立核实。

# Q9 贡献

* 一个运行中的公开档案库，展示了形式化数学的"项目独立、共同构建"模式：在内核加 linter 的准入门槛下，由智能体负责发现、修复、优化和审阅。
* 一份诚实的运行记录，说明智能体维护能做到和做不到什么：大规模升级修复可行，但需要后续整合；证明精简可能拖慢构建；LLM 审阅缺乏准确性标注，且已暂停。
* 保留来源信息的项目卡片（证明由人、AI 或混合写成），以及把非形式主张连到形式命题的展示层——这是"主张—产物可追溯"的一个具体模板。
* 一个愿景：大多数新的数学论文应附带一个持续维护的形式化，其导入关系与引用关系相对应。

# Q10 下一步

* **为审阅者打标签：** 请数学家对一批 LLM 审阅结论（尤其是命题忠实度方面的标记）评分，得到精确率和召回率，而不是只统计合并结果。
* **命题漂移检查：** 当升级修复改动了假设时，自动比对定理命题，把任何变弱之处交给人确认。这一点很重要，因为论文表明修复可能悄悄改变所证明的内容。
* **记录智能体工作量：** 记录每个任务所用模型、token 数、耗时和人工介入，让"由智能体维护档案库"变成可量化的主张。
* **把性能列为合并门槛：** 证明精简曾拖慢构建，Tau Ceti 的强制性能检查可以直接解决这一问题。
* **与研究可验证性的联系（读者构想）：** 在[研究可验证性](../topics/research-verifiability.md)主题所追踪的"主张—证据"谱系中，Lean Pool 位于形式数学一端。内核消除了证明层面的疑问，剩下的薄弱点是*形式命题是否与非形式主张相符*——该主题中那些 LLM 评审审计正试图为经验性主张弥补的也是同一缺口。
* **与本仓库的契合（读者笔记）：** 升级工作流（全部探测 → 把每个失败分派给修复智能体 → 合并构建 → 草稿 PR）是一个可复用的模式，可用来让本仓库的技能和脚本在依赖升级后保持可用。
