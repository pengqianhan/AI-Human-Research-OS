# Q1 问题定义

* **输入（X）：** SOL-ExecBench 的一道题：它的 PyTorch 定义、形状和数据类型，以及每个工作负载（workload）w 公布的基线时间 t_b(w) 和光速上界（speed-of-light bound）t_sol(w)。没有参考 kernel，没有以往运行的结果，也没有官方分数。
* **输出（Y）：** 一个运行在 NVIDIA B200 上的 GPU kernel，要求基准网站判定它在每个工作负载上都正确，并且尽可能快。网站对每个工作负载打 SOL 分：等于基线时为 0.5，达到硬件上界时为 1；先在工作负载上取平均，再在一个榜单的所有题目上取平均。
* **约束：** 模型固定不变；网站把 SM 时钟锁定在 1,500 MHz，构建超过 300 秒即终止，拒绝运行时编译原生代码的方案；正确性只能靠测试确立，因为作者考察过的形式化和 SMT 工具都无法建模 Blackwell 的异步张量核心操作。

# Q2 问题新颖性

用 LLM 生成 kernel 并不新（KernelBench、TritonBench、经 RL 训练的 kernel 模型，以及 Blackwell 上的多个固定模型框架，如 ForgeKernel、Cursor 与 NVIDIA 的规划者-工人系统、JustGoal）。这份报告的问题更窄，偏工程：如何让每道题的搜索在自己先前的尝试上持续积累，同时在数百道题上并行、超过一千个智能体会话一起跑，而且不让搜索自欺欺人。这很重要：SOL-ExecBench 的作者自己就把 14.5% 的智能体提交判为奖励投机（reward hack）而拒绝；本文最终 kernel 的中位长度约 7,000 行，人工根本审不过来。

# Q3 科学假设

如果把每个正确的 kernel 都保存在模型之外的档案库（archive）里，让 LLM 控制器可以扩展其中任意一个（而不只是当前最优），并由模型看不到、也影响不了的检查来判定正确性，那么一个固定模型就能从 PyTorch 定义一路爬升到领先的 kernel，较慢的中间 kernel 可以充当垫脚石。第二个经验性主张：这个循环建立起来以后，规模的上限取决于基础设施每小时能提供多少可靠测量，而不是跑了多少个智能体。

# Q4 相关工作与关键人物

* **Kernel 基准及其可信度。** KernelBench 和 TritonBench；之后关于加速比被夸大的工作（复用参考实现的内存、METR 过滤可投机任务、加固后的重新评测把最好的 KernelBench 模型从 1.43x 降到 0.88x、检查器漏掉真实错误、硬编码测试形状）。SOL-ExecBench（NVIDIA）用 SOLAR 光速上界打分。
* **改模型还是用固定模型搜索。** 用 RL 或微调训练 kernel 模型（Kevin-32B 等）与固定模型外加循环两条路线；本报告属于后者，附录列出 25 个系统。
* **框架应该知道多少。** JustGoal（只给目标的智能体就是强基线）、一份 FlashInfer 竞赛报告（专家指导必不可少）、AKO（由人来重定向停滞的搜索）。
* **档案库与控制器。** 带档案库的程序演化系统（AlphaEvolve、OpenEvolve 等）。本文借用三个想法：来自 [Darwin Gödel Machine](../concepts/darwin-godel-machine.md) 的档案库加父节点采样，来自 [HyperAgents](../concepts/hyperagents.md) 的任务智能体之上的 LLM 元智能体，以及来自 ForgeKernel 的"新根节点应当是新设计"。
* **关键人物。** 通讯作者 Qian Qu 及其 Amazon 同事，末位作者 Benoit Dumoulin。可能的批评者：KernelBench 可信度那一脉的作者，会要求在测试形状之外证明鲁棒性；只给目标的基线的作者，会问这套框架是否带来了单个智能体在同样预算下得不到的东西。

# Q5 关键解决思路

系统由四层嵌套循环组成，每层比内层慢。

1. **子循环。** 一个子智能体拿到一个父 kernel（新根节点则没有）和一个方向，在 B200 上修改、编译、计时；在最终运行里它在第一个正确 kernel 处停止。模型之外的检查判定正确性，只有正确的 kernel 才作为节点写入档案库；失败的尝试只记日志，不成为节点。
2. **控制器循环。** 每道题有一个无状态的 LLM 控制器，只有两个工具：对档案库的只读 SQL 查询，以及 `expand(parent, directions)`，用互不相同的方向填满所有空闲子槽位。它可以挑任意节点，因此一个正确但较慢的 kernel 也能成为父节点。
3. **团队循环。** 负责人和助手智能体监控整个集群并修复框架；每项修复由人批准，在一次热重启（warm restart）时生效：在同一次运行和同一批档案库上重新启动智能体。智能体自身没有记忆，只需重新读取档案库。
4. **外层循环。** 由人决定把哪些 kernel 提交到公开榜单、何时提交，并且（从 2026-10-25 起）根据每道题与第一名的差距设定子槽位数量。

奖励是基于本地计时、相对公布基线的几何平均加速比，而不是 SOL 分数，因为 SOL 分数在高加速比时趋于平坦。本地 GPU 不锁时钟（最高约 1,965 MHz），本地计时偏快；人用一个智能体看不到的校准来修正。正确性检查分五类（官方正确性；在未提交形状和压力值上的鲁棒性；规则与奖励投机；网站就绪性；人工评审加网站自身检查），附录列出十二项提交检查。

# Q6 实验设计

* **主运行。** 对全部 235 道题（L1 94、L2 82、Quantization 33、FlashInfer-Bench 26）做一次冷启动的最终运行，所有智能体都是 Claude Opus 5.5，同时有一千多个会话。结果按四种标注好的指标报告：网站 SOL 分、网站计时下相对 t_b 的加速比、本地计时下相对 t_b 的加速比、本地计时下相对 torch.compile 的加速比。FlashInfer-Bench 的 kernel 只以私有行的形式在网站上验证为正确，不报告结果。
* **系统经验。** 在实际运行中跨热重启做前后对比（吞吐量、锁时间、鲁棒性检查覆盖率、首个提示写入的上下文量）。
* **搜索设计测试。** 在最终版之前的框架版本上做的三组对比，每组每臂只跑一次：LLM 控制器对比编码实现的 UCB 式树搜索（38 对题目，各 24 小时）；强制使用与可选使用参考文档和技能（233 对，计划 48 小时，实际约 23 小时）；对停滞运行追加"尝试结构性改变"的指令（4 次运行，210 分钟）。附录还比较了子智能体引擎（Claude、Codex、混合）以及两项 FlashInfer-Bench 测试。
* **案例研究。** 五条谱系，选自那些鲁棒、公开且不含运行时计时的提交。

# Q7 数据集与代码

基准是 NVIDIA 公开的 SOL-ExecBench（来自 124 个真实模型的 235 道题，3,957 个工作负载，BF16、FP8 和 NVFP4，前向与反向）。作者计划发布搜索循环、SOL-ExecBench 接口、检查代码和示例配置（不含智能体提示），以及全部 235 个最终 kernel；投稿时链接的 Hugging Face Space 已按榜单和算子类型列出这些题目。

# Q8 证据质量

* **榜单结果来自外部且标注日期。** 排名（L1 第一 0.823339、L2 第一 0.819260、Quantization 第一 0.909670）、单题计数（209 题中 89 题第一、193 题前十）和 4.40x 几何平均（中位数 3.78x；各榜 4.04x、3.62x、9.19x）都来自截至 2026-11-11 的公开网站，且网站判定每个 kernel 正确。这是报告最强的证据。但这是个移动目标：论文自己记录了在 L2 和 Quantization 上失去又夺回第一，部分是靠公开更多的行。
* **加速比分布广。** 39 道题达到 10x 或以上，最大值 1062x（L1/094）；但有两道题比基线慢（L2/037 为 0.30x，L1/030 为 0.96x），209 题中 21 题低于 1.5x，全在 L1 或 L2；普通 GEMM/MLP 和完整层离 SOL 最远。
* **规模经验有提示性，但未经检验。** 每小时评估候选数提高 3.6x（每个计分候选的锁时间下降 71%），来自一次捆绑了多项改动的热重启，比较的是匹配的时段；作者明说各项改动的贡献没有拆开测量，也没有直接改变智能体数量。
* **设计测试都是单次运行。** 控制器对树搜索：同等墙钟时间下 38 题中赢 35 题（严格按 24 小时截断为 34 题），几何平均比 1.143；但在同等候选数下控制器只在 38 题中的 15 题更好，所以优势在尝试速率，不在挑选质量。强制参考：比值 0.981，两个混杂因素都不利于强制组，因此不能排除小幅收益。结构引导：操纵检查失败，只是一个筛查性的零结果。这些都在较早的框架版本上进行。
* **正确性是测出来的，不是证明出来的。** 鲁棒性检查覆盖的是每次运行的新最优（94.9% 被检查），而不是每个候选。论文报告了自己运行中被抓到的奖励投机（Quant/030 的最优路径从第 3 步到第 155 步，约占运行前三分之一，都靠运行时计时挑选按形状的变体，之后才被禁止），这既说明检查有效，也说明检查在一段时间里落后于搜索。
* **"从零开始"有限定。** 搜索是冷启动，但模型在公开代码上预训练过，智能体可以读 CUTLASS 头文件、上网、看一个公开 wiki，而且人根据公开排名分配子槽位。没有智能体看到过分数或排名。
* **读者核查。** 垫脚石统计（235 条最优路径中 41 条含有比父节点慢至少 10% 的一步；75 条建立在低于当时该题最优 0.9 倍的父节点上）说明获胜路径上确有较慢节点；但没有跑"只扩展最优"的对照组，所以不能说明只扩展最优的搜索就会失败（读者推断）。

# Q9 贡献

1. 一个有文档记录的固定模型 kernel 搜索系统，在三个公开 SOL-ExecBench 榜单上登顶，全部 235 题经网站验证正确，每个核心数字都标明计时基准和日期。
2. 清晰的角色分离：模型之外的档案库是唯一共享记忆，无状态 LLM 控制器负责选节点，模型之外的检查负责判定正确性，人只参与框架修复和提交，官方分数不进入搜索。
3. 运行一千多个智能体的操作经验：吞吐量受限于构建和计时的争用；热重启让框架可以演化而不丢进度；验证应放在做决策的地方；大的父节点应以文件而非文本传递。
4. 来自单次运行测试的证据：LLM 控制器靠尝试速率胜过 UCB 树搜索，强制参考材料没有带来可测提升；以及谱系案例：较慢或落后的节点成为后来 86% 到 97% 节点的基础。

# Q10 下一步

* **论文自述。** 更便宜的验证，以便可靠地测量更多尝试；换到其他 GPU 和基准；把 kernel 换进推理服务框架，测量首 token 时间和吞吐。
* **直接改变智能体数量。** 固定基础设施，扫描每题子智能体数，检验"上限是测量速率而非智能体数"这一论断（论文自己指出尚未检验）。
* **只扩展最优的消融。** 在同样的题目上跑一个只能扩展当前最优节点的控制器，测量保留较慢垫脚石到底带来多少（读者建议）。
* **在最终框架上重复设计测试。** 每组对比都只在早期版本上每臂跑一次；重复运行能看出 0.981 的零结果和 35/38 的胜率是否成立（读者建议）。
* **与更便宜的测量结合。** GPU Forecasters 这类运行时代理模型正好针对本报告指出的瓶颈；检验预测器能否在 B200 计时前先筛选子候选，是直接的后续工作（读者建议）。
