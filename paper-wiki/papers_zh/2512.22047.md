> 论文:**MAI-UI Technical Report: Real-World Centric Foundation GUI Agents**
> 论文链接:<https://arxiv.org/abs/2512.22047>
> 机构:阿里巴巴通义实验室(Tongyi Lab, Alibaba Group)

# Q1 问题定义

* **输入 `X`**:对于 grounding 任务,是一张 GUI 截图加一条自然语言指令;对于导航任务,是一个 POMDP 观测流(指令 + 一张或多张截图),带有此前动作/观测的历史记录,运行在真实 Android 设备或模拟器上。
* **输出 `Y`**:对于 grounding,是定位目标 UI 元素的坐标点;对于导航,是从一个动作空间中每步输出一个动作,该空间涵盖标准 GUI 操作(点击、滑动、输入、拖拽、系统按键)以及论文引入的两个扩展动作——`ask_user`(向用户请求澄清)和 `mcp_call`(调用外部 MCP 工具而非操作 UI)。
* **核心问题**:当今的 GUI agent 是为端到端执行而优化的,但在实际部署中这一假设常常不成立:用户指令往往含糊而非完全指定,纯 UI 操作序列冗长且容易出错,还会把 agent 限制在 UI 可达的任务范围内;agent 要么只能在设备端运行(能力受限),要么只能作为云服务(隐私/成本/延迟受限),二者之间没有原生的切换机制;在静态轨迹上训练的 agent 会过拟合特定界面,对现实世界的动态性(界面随版本变化、意外弹窗等)保持脆弱。
* **范围**:一个基础 GUI agent 家族(2B、8B、32B、235B-A22B,基于 Qwen3-VL 构建)加上一套设备-云协同系统和一套自我进化的训练流水线;在 GUI grounding、离线/在线移动导航,以及一个专门测试 agent-用户交互和 MCP 工具使用能力的新的真实场景导向基准(MobileWorld)上评测。

# Q2 问题的新颖性

论文将自身定位为针对以下四个此前工作大多未充分解决、面向真实部署的缺口:(1)agent-用户交互——大多数系统按端到端方式执行,不会主动提出澄清问题或为敏感操作征求同意;(2)纯 UI 操作——仅依赖 GUI 操作会放大逐步误差,并把 agent 限制在 UI 可达的任务上,而 MCP 工具调用可以把冗长脆弱的操作序列压缩成少数 API 调用,并触及此前 UI 不可达的任务(例如,从手机操作一个 GitHub 仓库);(3)缺乏原生设备-云协同能力——agent 通常要么是轻量级的设备端模型,要么只能作为云服务,这迫使用户在隐私/成本与能力之间做取舍,而非按需路由;(4)对动态环境的脆弱性,源自在静态、预先收集的轨迹上训练。MAI-UI 声称的新颖之处在于用一套统一的方法论同时解决这四个问题,而非逐一击破。

# Q3 科学假设

如果一个基础 GUI agent 的动作空间被扩展为原生包含 agent-用户澄清动作和 MCP 工具调用动作(通过一个混合拒绝采样轨迹、人工标注轨迹和自主 rollout 轨迹的自我进化数据流水线来训练),如果一个设备-云协同系统根据检测到的轨迹偏离和数据敏感度,在设备端监控/agent 与更高能力的云端 agent 之间路由执行,并且模型在可扩展的动态 GUI 环境中进一步接受在线强化学习训练,那么得到的 agent 将在每个模型规模上都取得最先进的 grounding 和移动导航准确率,在需要澄清或工具使用的真实场景任务上大幅超越端到端基线,并且设备-云系统相较于纯云端或朴素切换方案,会在提升设备端表现的同时降低云端调用并保护隐私。

# Q5 核心解法

1. **扩展的动作空间。** 在标准 GUI 动作(点击、长按、输入、滑动、拖拽、系统按键、等待、结束、回答)之外,MAI-UI 加入了 `ask_user`(为指定不足的指令请求澄清)和 `mcp_call`(调用指定名称的 MCP 工具并传入参数),使 agent 每步都可以在 UI 操作、用户互动和工具使用之间做选择。
2. **自我进化的 SFT 数据流水线。** 导航任务指令来自 App 使用手册、专家设计任务和经过筛选的开源数据;任务经过扩展(L1:参数变化,L2:对象替换)后,通过人工标注(在 Android 模拟器上)和基于模型的 rollout 两条途径生成执行轨迹;一个 MLLM-as-judge 对轨迹做端到端有效性判断,并额外挖掘失败轨迹中"最长正确前缀"以复用。迭代拒绝采样让微调与 rollout 交替进行,使模型与训练语料共同演化,明确地缩小 pass@1 与 pass@N 之间的差距,同时抬高 pass@N 上限。agent-用户交互和 MCP 增强轨迹的构造方式是刻意省略关键任务信息,并将 `ask_user` 查询路由给一个以隐藏缺失上下文为条件的合成 LLM 用户 agent。
3. **可扩展动态环境中的在线强化学习。** 一个容器化、RL 原生的 GUI 环境(基于 Docker 封装的 root 化 AVD、35+ 个已集成的真实应用、标准的 `reset`/`step`/`get_observation`/`evaluate`/`close` 原语),由一个中心化的环境管理器协调,仅用 10 台阿里云 ECS 服务器就支持最多 512 个并发实例。训练采用定制版 GRPO(组大小 16,DAPO 式非对称 clip-higher,ε_low=0.2/ε_high=0.3,不含 KL 惩罚,加入动作重复惩罚,以及每任务 8 条轨迹的经验回放缓冲区),运行在基于 verl、支持异步且混合并行(张量+流水线+上下文并行)的 rollout 框架之上——这是因为轨迹长度可达数百万 token。任务按当前策略的成功率被动态划分为四个难度档(前沿/探索/接近精通/巩固),以驱动自动课程学习,并由一个混合规则式与 MLLM-as-judge 的验证器(与人工标注 83% 一致)为确定性任务和复杂任务打分。
4. **原生设备-云协同(DCC)。** 一个本地 Agent(设备端)兼任 GUI 执行者和轨迹监控者,检查执行失败、无进展的重复动作或指令偏离;一旦检测到偏离*且*上下文中不含隐私敏感数据,就通过一个本地统一轨迹记忆将任务连同一段自动生成的错误摘要移交给能力更高的云端 Agent,该记忆使任一模型都能从任意状态无歧义地续接。一个独立的本地隐私检测模块可以在检测到敏感内容(如密码输入)时直接阻止云端切换,即使检测到偏离,也保持在设备端执行。
5. **全谱系模型规模。** 以 Qwen3-VL 为骨干,提供 2B/8B/32B/235B-A22B 四档,经过四个训练阶段(grounding/感知 SFT → 导航 SFT → grounding RL → 在线导航 RL),使同一套方法论既能服务高效的设备端部署,也能服务高能力的云端服务。

# Q6 实验设计

在三类基准上与同期强基线(可比规模)对比评测。**Grounding**(五个基准):ScreenSpot-Pro 在 32B 上达到 67.9%(加 zoom-in 为 73.5%),相较最强基线 GTA1-32B 提升 4.1 个百分点;UI-Vision 达到 47.1%(加 zoom-in 为 49.2%),相较 UI-Venus-Ground-72B 提升 12.4 个百分点;MMBench-GUI L2 达到 91.3%,相较此前最佳(GTA1)提升 7.9 个百分点;OSWorld-G 达到 67.6%(加 zoom-in 为 70.9%);ScreenSpot-V2 达到 96.5%。**离线导航**:GUI Odyssey 在 32B 上成功率 83.4%,创下新的 SOTA;在 Android Control 高层指令上表现具竞争力但未达 SOTA。**在线导航**:AndroidWorld(116 个任务,20 个 App,实时模拟器)——235B-A22B 达到 76.7%,超过 UI-TARS-2(73.3%)和 Gemini-2.5-Pro(69.7%);32B/8B/2B 分别达到 73.3%/70.7%/49.1%,各自在其参数规模上均为最佳(2B 相较最强的设备端基线 Ferret-UI Lite-3B 的 28.0%,提升 21.1 个百分点/相对提升 75.4%)。**MobileWorld**(201 个真实场景任务):235B-A22B 整体达到 41.7%,相较最强端到端基线(Doubao-1.5-UI-TARS,20.9%)提升 20.8 个百分点,与使用 GPT-5 或 Gemini-3-Pro 作为规划器的智能体框架(43.8%-51.7%)相比也具竞争力(但严格来说不完全可比);在专门测试用户交互(45 个任务)和 MCP(40 个任务)的子集上,235B-A22B 分别得到 51.1% 和 37.5%,相较此前最佳端到端分数提升 18.7 和 32.1 个百分点。**消融实验**:在线 RL 在各规模上相较纯 SFT 提升 3.5 至 6.0 个百分点;定制 GRPO(课程学习 + 重复惩罚 + 经验回放)在 AndroidWorld/8B 上相较标准 GRPO 额外提升 4.2 个百分点;交互预算从 15 步扩展到 50 步累计提升 1.7 至 6.0 个百分点;并行环境数从 32 扩展到 512 使 AndroidWorld/8B 从 65.5% 提升到 70.7%;DCC 相较纯设备端模型带来 33.4% 的相对提升,相较等云调用频率的随机切换基线提升 7.7 个百分点,同时将云调用减少 42.7%,并使超过 40% 的 AndroidWorld 任务完全在设备端完成;移除监控器在切换时给出的错误摘要会造成 6.9 个百分点的损失。

# Q7 数据与代码

训练数据混合了开源数据集(JEDI、OS-Atlas)和自采集数据,后者来自容器化虚拟操作系统探索(MLLM 引导的动作发现,通过无障碍树或 OmniParser V2 定位)。在公开基准上评测:ScreenSpot-Pro、UI-Vision、MMBench-GUI L2、OSWorld-G(-Refine)、ScreenSpot-V2、Android Control、GUI Odyssey、AndroidWorld,以及论文自建的 **MobileWorld** 基准(200+ 个任务,15+/20 个模仿商用 App——如 Temu/Amazon、Microsoft Teams/Slack、X/Twitter——的开源应用)。代码发布于 github.com/Tongyi-MAI/MAI-UI(据 `hf papers info` 有 2,132 个 GitHub star);所属组织为 AlibabaTongyiLab/TongyiLab。检索到的文本中未明确说明是否会发布自我进化训练数据本身(区别于代码和评测工具)。

# Q9 主要贡献

1. **MAI-UI**,一个 2B/8B/32B/235B-A22B 规模的基础 GUI agent 家族(Qwen3-VL 骨干),统一了 GUI grounding 与移动导航,并加入两个原生新动作——用于澄清的 `ask_user` 和用于外部工具使用的 `mcp_call`——通过一个使模型与轨迹语料共同演化的自我进化数据流水线训练。
2. 一套**原生设备-云协同系统**(设备端监控 + 高能力云端 agent + 共享轨迹记忆 + 本地隐私门控),使设备端表现相对提升 33%,将云调用减少超过 40%,并通过在检测到轨迹偏离时仍能因敏感内容而阻止云端切换,证明了其隐私保护能力。
3. 一套面向 GUI agent 的规模化**在线 RL 框架**(最多 512 个并行容器化环境,运行在 10 台云服务器上,异步 rollout,面向百万 token 轨迹的混合张量/流水线/上下文并行),配有自动四档难度课程学习和混合规则式/MLLM-judge 验证器。
4. 在 GUI grounding(五个基准)、离线(GUI Odyssey)与在线(AndroidWorld,76.7%)移动导航,以及论文自建的真实场景导向基准 **MobileWorld** 上取得新的 SOTA,且在从 2B 到 235B-A22B 的每个评测规模上均成立。

# Q10 下一步

本笔记从检索到的文本中无法解答的开放问题:设备-云监控器的偏离检测阈值,在唯一报告的一次消融实验之外,如何在错误切换(成本/延迟)与漏切换(任务失败)之间取舍;当 agent 在训练中未见过某个 MCP 工具时,推理阶段如何确定工具的可用性/选择;以及 MobileWorld 的真实性在多大程度上能从其 15-20 个自托管开源应用泛化到 agent 从未见过的任意商用 App。**与本仓库的关联**:MobileWorld 明确设置的 agent-用户交互和 MCP 工具使用子集,以及"原生 `ask_user` 动作加合成用户训练流水线能切实改善澄清行为"这一发现,与任何构建或评测"agent 何时该问、何时该做"这一决策能力的项目直接相关——值得在两条线索都被完整阅读后,与本知识库的模拟用户评测和 agent 环境相关主题做对比。
