# Q1 问题定义

* **输入 (X)：** 一个真实世界任务及其上下文（输入、环境、约束、验收标准），以及一个可复用单元库：工具、仓库组件、证明方法、源文档、多智能体模式、文件或 harness 控制操作。
* **输出 (Y)：** 一个针对该任务的 harness，构造成由被激活原语组成的图，它产出任务的产物（工具调用序列、代码仓库、Lean 证明、答案、完成的线上操作）并通过任务自身的验收检查；以及为后续任务而加入库中、经过验证的新单元。
* **约束：** 修订轮数有固定预算；构建或测试失败不能被模型判断推翻；事先建好的库在任务进行中不变，任务内部产生的东西只能经由单独的验证路径进入库。

# Q2 问题新颖性

部分新。工具学习、检索与记忆、技能与代码库、多智能体框架、工作流搜索和 harness 优化器，都让资源更容易被够到。本文的主张是：它们都把"应用资源的能力"留给了调用方（或一个整体式智能体），于是每个 harness 都要重建这种能力。它的回答是在每个资源里放一个常驻 LLM（resident LLM），这推广了可复用组件、时间扩展的选项（options）和契约式设计的思想。八个原语家族并不是本文新提出的：每个都是同一团队的配套研究（Tool Primitives arXiv:2609.01736、Code Primitives arXiv:2610.09079、Math Primitives arXiv:2610.09401、Knowledge Primitives arXiv:2610.02150、Agent Primitives arXiv:2602.03695、Dev-Primitives arXiv:2610.07832、Navigation Primitives arXiv:2609.33326、Harness Primitives arXiv:2609.38912）。本文新的是统一它们的单一定义、重述的理论、跨家族分析和 heelo.dev 评测。

# Q3 科学假设

如果每个可复用资源都带着自己的 LLM，在上下文中应用它、验证自己这一步，并把要求发给依赖它的原语，而 harness 只激活任务需要的原语、只修订失败所牵连的原语，那么智能体能完成的真实任务会多于那些由自己应用资源的前沿 harness，而且成本随任务需求增长，而不是随库的规模增长。

# Q5 关键解决思路

**智能体原生原语（agent-native primitive）。** 一个原语由资源 *a*、一个常驻 LLM 和一个供 harness 发现它的接口 *d* 组成。用自然语言请求在上下文中调用它时，LLM 应用该资源，返回结果以及发给其他原语的消息（该结果对它们提出的要求，或它们需要的信息）。一个基座模型可以作为库中所有原语的常驻 LLM。原语还可以评估自己是否相关并提出用法，并在返回前运行资源自带的验证（测试、schema）。若领域有精确的程序，就用代码代替 LLM。

**HEELO 的三个机制。** (1) *库选择与组合*：通过检索或读取所有接口找到候选，读取它们的相关性评估，构造一张只含少数被激活原语的图，边上传递结果与消息。(2) *基于证据的执行与改进*：按轮运行该图，执行能执行的部分（构建、测试、编译器），验证结果，指出失败牵连的原语，并只修订这些原语，最多 *B* 轮。(3) *验证与发布*：在任务之间，只在领域验证通过后才接纳新的或改进的原语（挖掘得到、从已验证运行中收获、或由失败提出）。

**八个家族。** Tool Primitives（25,519 个工具各对应一个原语，其中 16,464 个封装真实 API；框架 HEART）、Code Primitives（1,424 个带测试的组件；LEGO）、Math Primitives（82 个从 Putnam 2000-2014 构建、Lean 编译通过的方法契约；自我推荐式选择）、Knowledge Primitives（每个权威来源一个源模型；SourceLearn）、Agent Primitives（Review、Voting and Selection、Planning and Execution 三种潜空间算子，在同一 LLM 上共享 KV 缓存）、Dev-Primitives（每个仓库文件一个，发送定向消息；HERMES）、Navigation Primitives（按未解决需求路由的领地工作者；ANTMAN）和 Harness Primitives（经验证的控制操作，在执行者开始前组合成 harness；STITCH）。

**理论（转述自配套研究）。** 若每个原语只为解决一个未解决需求而被激活，激活数量受任务需求约束，与库的规模无关。在加性模型下，逐任务组合优于最佳固定 harness，当且仅当其选择损失小于一个可计算的差距。任何对相似度检索短名单的重排器都受该短名单召回率的上限约束，而对整个库做评估可以避免这一上限。

# Q6 实验设计

* **各家族基准，共二十多个。** ToolBench、NESTFUL、τ²-bench、ACEBench、BFCLv4 和 50 个整理的真实工具任务；LEGO-REPO（作者自建的 522 个仓库重建任务）以及 RepoZero、RepoGenesis 和 RepoCraft；Lean 4 中的 120 道 Putnam 2015-2025 题和 60 道 IMO ProofBench 题；MultiDoc2Dial、NarrativeQA、SWE-QA、APIBench 和 [AppWorld](../concepts/appworld.md)；八个用于多智能体系统的数学、代码和问答基准；SWE-bench Verified、Terminal-Bench 4.0（66 个任务）、DevOps-Gym 和 SWE Refactor Bench；HotpotQA、2WikiMultiHopQA、MuSiQue、RepoProbe-Python、SWE-QA-Pro、[GAIA](../concepts/gaia.md)-Text-103 以及 32K-512K token 的受控空间；Harness Primitives 使用 100 个 SWE-bench Verified 和 45 个 Terminal-Bench 2.0 任务的样本。
* **基线。** 各家族配套研究中、在相同底座上的基线，包括 Codex、Claude Code、OpenHands、[mini-SWE-agent](../concepts/mini-swe-agent.md)、SWE-agent、Aider、DFSDT、RAPTOR、HippoRAG 2、LatentMAS、MAS-GPT、LongAgent、Chain of Agents、MemoHarness 和 Meta-Harness，以及移除或替换原语的对照。
* **跨家族分析（第 5 节）。** 预算匹配对照、原语字段消融、通信消融（KV 缓存重新编号、Dev-Primitive 消息）、激活与修订消融，以及模型放置扫描，均取自配套研究。
* **heelo.dev（第 6 节）。** 46 个任务覆盖四个线上闭环（分发、获客、个人助理、市场验证）中的 26 项能力；Claude Code 搭配 Claude Opus 5.5、Codex 搭配 GPT-6.1 Sol，均为 medium 推理强度，分别单独运行和通过 [MCP](../concepts/model-context-protocol.md) 服务器接入 HEELO；多数任务每组跑三次；分发和助理闭环的答案由 Claude Sonnet 5.5 盲评，并由人工复核其评分。

# Q8 证据质量

* **有支持的结论。**
  * *在 Terminal-Bench 4.0 上大幅领先 Codex。* 在 66 个任务的五次运行中，HERMES 搭配 GPT-5.6 Sol 在 max 强度下解出 55.5%（Codex 为 37.3%），在 medium 强度下 51.8%（Codex 为 33.0%）；GPT-5.6 Terra 提升约 26 分。
  * *逐任务组合 harness 有帮助。* 以 GPT-5.6 Luna 为执行者，STITCH 把 mini-SWE-agent 种子的 Pass@1 在 100 个 SWE-bench Verified 任务上从 73.0% 提到 80.5%，在 45 个 Terminal-Bench 2.0 任务上从 60.0% 提到 72.2%，高于对所有任务使用最佳单一原语（76.0%）和随机组合器（73.3%），组合成本为一次执行者尝试的 2.7% 到 4.3%。
  * *收益在于"应用"而非"获取"资源。* 在预算匹配的对照中，对原始 schema 自我修正参数只达到 34.2% 的 ToolBench 通过率，而 Tool Primitives 为 75.1%；把同样检索到的组件作为只读上下文给调用方，仓库交付分为 0.3544，而 Code Primitives 为 0.5134。
  * *通道与修订很重要。* 若共享 KV 缓存不做 RoPE 重新编号，R1/Llama-70B 上组合的多智能体系统在 HumanEval+ 上从 85.3% 跌到 31.1%；去掉诊断反馈后，HERMES 在 Terminal-Bench 4.0 上从 51.8% 降到 41.2%。
  * *激活随需求变化。* 干扰项使空间扩大 16 倍时，活跃的 Navigation Primitives 只增加 1.23 倍，而 LongAgent 和 Chain of Agents 约增加 15 倍。
* **比标题弱或范围更窄的地方。**
  * *HEELO 作为一个整体系统并没有在研究基准上评测。* 每个家族都是独立的系统（HEART、LEGO、HERMES、STITCH、ANTMAN 等），在各自的研究中评测；附录 E 只规定了跨家族组合的评测协议，没有结果。统一框架是八个系统共享的描述，重述的命题在各研究的假设（例如加性收益模型）下成立（读者对附录 E 和第 3.5 节的理解）。
  * *标题对比挑的是较弱的前沿 harness。* 与最强基线 Claude Code 搭配 Claude Opus 5 相比，HERMES 在 max 强度下只提升 1.2 分（51.8% 到 53.0%），medium 下 1.5 分；18.2 分是相对 Codex 而言。HERMES 在 Terminal-Bench 4.0 上的 token 与成本约为 Codex 的两倍（例如 max 强度下每次评测从 2.5k 到 4.7k 美元），Claude Sonnet 5 是特别提到的例外。
  * *若干基线范围较窄。* Tool Primitives 在 ToolBench 上的 75.1% 比相同 Qwen3-8B 底座上的 DFSDT 高 19.3 分，但只比 Claude-4.6-Sonnet 加 DFSDT 高 1.7 分。Code Primitives 的 0.5134 是在作者自建的 LEGO-REPO 基准上、相对执行反馈（0.3180）测得的。SWE-bench Verified 已接近上限（HERMES 搭配 Sol 为 97.0%，mini-SWE-agent 为 96.2%）。
  * *harness 研究样本小。* STITCH 在 SWE-bench Verified 上领先 Codex 的 1.5 分相当于 200 次尝试中的 3 次（读者算术），而且原语是在同一基准上不相交的开发任务上开发的。
  * *heelo.dev 的设置偏向接入 HEELO 的一组。* 单独运行的智能体拿不到凭证、不能操作任何账户，所以两者在助理闭环上的 0% 是由设置决定的，12 项零分能力中多数是操作账户。当某次运行暴露原语缺陷时，原语被修复后任务重跑，只报告修复后的运行。任务来自作者自己的产品，一位作者隶属于该产品，评分由 LLM 完成并经人工复核。"每完成一个任务"的时间与成本是用总量除以完成数，因此对完成更多的一组有利；按单次运行看，接入后的智能体通常读取更多 token（助理闭环运行的中位数为 160,701 对 19,456）（读者根据第 6.3-6.4 节的观察）。

# Q9 贡献

* 一个单一定义（资源 + 常驻 LLM + 接口 + 消息），把八个可复用、能自我应用的单元家族联系起来。
* HEELO 对逐任务组合、基于证据只修订受牵连原语、以及经验证才扩充库的描述。
* 跨家族分析：把收益定位在原语内部对资源的应用、原语之间的通道，以及由需求驱动的激活和由证据驱动的修订。
* heelo.dev：一个通过 MCP 把真实世界操作作为原语开放的线上平台，并附 46 个任务的端到端评测。

# Q10 下一步

* **执行附录 E 的协议（来自论文）。** 需要两个以上家族的任务、资产与预算匹配的对照组、以及组合分布下各家族验证器的误通过率，才能把 HEELO 作为一个系统来检验。
* **公平的线上比较（读者建议）。** 给单独运行的智能体相同的凭证和 API 访问，并在评测前冻结原语，使 heelo.dev 的结果衡量的是应用能力而不是账户访问。
* **对比最强 harness（读者建议）。** 报告每个家族相对最强同底座 harness（Terminal-Bench 4.0 上为 Claude Code 搭配 Opus 5）的提升，并加入算力匹配的版本。
* **漂移下的库维护。** 论文把 API schema、文档和依赖漂移列为压力测试；经验证的原语多久会过时、重新验证要花多少，决定了一个 25,519 个工具的库能否持续可用。
* **按角色分配模型。** 强模型在诊断环节最有用、小模型可以在原语内部工作的发现，与 AgentBaton 这类按轮次的交接相呼应（读者关联）。
