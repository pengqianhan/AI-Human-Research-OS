# Q1 问题定义

* **输入（X）：** 被评测的*构建模型*（build model），运行在固定的构建 harness（[OpenCode](../concepts/opencode.md) 1.17.0）里。空容器中只放两份文件：一份*开发文档*，逐条款（clause）规定一个编码智能体 harness 应有的行为；一份*契约骨架*（contract skeleton），由 [mini-swe-agent](../concepts/mini-swe-agent.md) 精简而来（五个 Python 文件、约七十行，外加安装脚本、入口脚本和项目配置），只声明三个不可更改的接口：CLI、无头（headless）入口，以及供自动评测驱动的 API。
* **输出（Y）：** 一个完整的*候选 harness*。模型提交且契约检查通过（能编译安装、所有必需命令都在、没有残留占位桩、三个接口齐全）时即被冻结。一个典型候选约有 30 个 Python 文件、16,000 行代码，其中约 99.6% 由构建模型写成。
* **评什么：** 冻结后的 harness 在每个测试用例各自的容器里运行，由一个*按脚本回复的模拟模型*（mock model）端到端驱动，共 328 个用例。每个用例的效果从四个通道读取：发给模型的请求、磁盘上的文件、进程退出码、命令输出。构建模型的能力按通过率排名，取三次独立构建的平均。
* **约束：** 除模型网关外无网络；每次构建两小时墙钟时间、最多三次提交；用 OpenCode 每次只推进一轮的 `opencode run` 加 `--continue` 续接，最多 24 轮，上下文用到 80% 时自动压缩；每个测试用例限时 900 秒。

# Q2 问题新颖性

部分新。论文把已有工作分成三类，认为没有一类在逐条款地判定 harness 自身行为是否符合规范：

* **评测现有 harness 的基准。** Claw-SWE-Bench 发现换 harness 会让分数变动 27.4 分，换模型是 29.4 分；Harness-Bench 主张能力应按"模型-harness 配置"报告。
* **评测 harness 某一项能力的基准。** 跨指令载体的规则遵循（Harness-IF）、技能检索（Skill-Use）、组件生命周期（CordisBench）、安全（Permission Denied、HarnessRisk、HarnessSafe），以及能否跟上不断变化的 harness（EvoHarnessBench）。
* **评测从现有 harness 出发生成或修改 harness 的基准**（HarnessDev、Evo-Bench、HarnessOpt-Bench）。它们用下游任务上的提升来衡量；有后续论文指出这与多花测试时搜索的收益分不开，而且分数还取决于驱动它的模型。

与仓库级生成（Commit0、NL2Repo-Bench、RepoZero、[ProgramBench](../concepts/programbench.md)、DeepSWE）相比，论文的论点是：那些基准是重建已发布的软件，并通过固定接口用单元测试判定；而 harness 的一个功能可以有许多种实现方式，harness 自己也完成不了下游任务。论文还认为 harness 出现时间短、更新快，构建它比重建一个可能已在训练数据里的成熟库更依赖泛化。本 wiki 中最接近的是 [AgentSWE](../papers/2610.13361.md)：它同样冻结由编码智能体构建的智能体，但用真实运行时模型和评分细则（rubric）在下游用例上打分。

# Q3 科学假设

论文没有明确陈述假设，下面是读者根据设计归纳的版本。如果只通过 harness 外部可观察的行为来规定它，并用按脚本回复的模拟模型代替真实模型来驱动，那么它的规范符合度就能被确定性地打分，并与任何模型的下游能力分开；这个分数能在"构建 harness"这项能力上区分前沿模型。第二个论断是事后从源码分析得出的：代码量相同时，拆成更多模块的 harness 符合度更低。

# Q5 关键解决思路

**只描述行为的规范。** 开发文档分三步写成。第一步，从十二个 harness 的用户文档中爬取候选功能，并补全调用形式、参数含义和边界行为。第二步，把功能清单写成条款，每条有语法、含义和预期行为，且其效果必须在四个通道之一上可见。各章覆盖：交付物与入口脚本、内置工具、命令与子命令、五种权限模式和五种角色模式及拒绝规则、全局参数、会话内命令、持久记忆、约定文件、跨章节一致性规则、封闭的退出码集合，以及评测 API。第三步，两条消歧规则：含义相同的命令合并（Claude Code 的 `/compact` 与 Cursor 的 `/summarize` 统一为 `/compact`）；同名不同义的概念拆开（"plan"在 Claude Code 中是只读权限模式，而 Aider 把提出修改与执行修改分给 architect 和 editor 两个角色，于是文档把只读归入权限、把提出与执行归入角色）。除骨架的三个接口外，不约束任何实现方式。

**测试用例分三种来源轮流生成。** 每个用例必须锚定在某条条款上，并且能区分不同实现。当前方法的产出下降时就换下一种：

1. *公开 issue 挖掘。* 取 Claude Code（9,868）、OpenCode（5,438）、Gemini CLI（4,831）、Kimi Code（946）全部 21,083 个非 PR 的 issue，按与文档的相关度排序，从头开始人工审阅，直到审阅成本超过产出；按所报告的现象聚类，同一条款上效果过近的簇只保留一个；只有能写成确定性断言且尚未被覆盖的候选才保留。前提假设是：构建模型会重犯成熟 harness 多年来暴露过的缺陷。
2. *跨 harness 对比。* 把一个候选 harness 和一个成熟 harness（Kimi Code、Qwen Code）都按文档的功能分组切分，逐模块列出差异；只有能从某条条款的目的推导出来的差异才成为用例。
3. *单变量扩展。* 从一个已知能区分实现的用例出发，每次只改场景中的一个变量、断言不变：达成效果所用的工具；输入形式（检查路径逃逸时：指向文件的符号链接、指向目录的、多级的、相对路径的）；承载典型错误的参数（把 0 当作缺省）；结果出现的位置（stdout、stderr、错误文本）。与种子太接近的候选丢弃，保留下来的成为新种子。

**为"不得发生"类断言设阳性对照（positive control）。** 例如"用读取工具读一个指向工作区外的符号链接，外部文件内容不得出现在发给模型的请求里"——如果读取工具什么都读不了，这个用例同样会通过。阳性对照与用例共享场景和初始文件（fixture），只改输入或访问路径，并断言一个"只要观测机制正常就必然发生"的结果。共三类：*通道*（读普通文件，内容确实进入请求）、*同形*（用 bash 工具读同一个符号链接——该条款不约束 bash——确认它解析到工作区外且可读）、*反向*（指向工作区内的符号链接仍能读到，排除"一律拒绝符号链接"的实现）。只有用例本身及所有控制它的对照都通过才算通过；对照本身不计分。328 个用例中有 130 个受对照约束（114 个受一个、15 个受两个、1 个受三个）；覆盖面最广的对照约束六个用例。

**每个阶段固定一个部件。** 构建阶段用 OpenCode，而不是 Claude Code 或 Codex CLI，因为厂商 harness 与自家模型一起开发；评测阶段用模拟模型，因为真实模型会带来每次运行的波动。

# Q6 实验设计

* **模型。** 来自十一家厂商的十九个模型：Claude Opus 4.6、4.7、4.8、5；GPT-5.5、GPT-5.6-sol、GPT-6 Astra；Qwen3.8 Max 0902；Kimi K3；GLM 5.2、5.3；DeepSeek V4 Pro、V4.1 Flash；Hy3、Hy4 preview；Doubao Seed 2.1 Pro；MiMo-V2.6-Flash；Grok 4.7；Step 5 Preview。每个模型构建三次，共 57 个计分 harness，全部在一台 48 线程、128 GB 内存的服务器上运行。
* **测试集。** 328 个用例分为九个互不相交的类别：会话状态 84、文件操作 75、权限 61、无头模式 40、直接驱动 33、交互终端 20、"其他"15（交付物检查 7、启动 7、扩展发现 1）。
* **分析。** 分类别通过率；每类的强弱差（最强与最弱模型之差），以及用例中"地板"（无人通过）、"天花板"（全部通过）与具有区分度的用例数；前两名在普通场景与边界场景上的对比；在至少 20 个用例的六个主要类别间的排名变化和两两相关；57 个 harness 上的 KR-20 内部一致性；以及对每个计分 harness 源码的分析（代码行数、模块数、每模块行数、最大模块占比），包括模型间方差占比和留一模型检验下的偏相关。
* **没有做的。** 没有参考 harness（人写的，或十二个真实 harness 之一）在测试集上的分数，无法说明文档允许的上限；没有检验通过率能否预测搭配真实模型时的实际效用；没有统计阳性对照推翻了多少次通过；没有构建-评测-修复的迭代循环。

# Q8 证据质量

* **有支撑的结论。**
  * *测试集能区分模型且未饱和。* 通过率从 53.05 ± 0.25（GPT-6 Astra），经 46.65 ± 1.80（Opus 5）、45.83 ± 0.14（Qwen3.8 Max），一直到 27.44 ± 0.43（Hy3），均值 38.30（表 2）。328 个用例中 256 个有区分度，56 个所有 harness 都失败，16 个所有 harness 都通过。57 个 harness 上的 KR-20 为 0.913。
  * *各类别揭示的东西不同。* 权限类区分度最高：平均 43.7%，强弱差 50.8 分，61 个用例中 51 个有区分度。文件操作平均相近（39.6%），强弱差只有 20.9 分。交互终端接近饱和（平均 79.9%，20 个用例中 7 个全部通过）。GPT-6 Astra 领先六个主要类别中的四个，Grok 4.7 领先文件操作，Qwen3.8 Max 领先交互终端。
  * *排名会变，但能力大体是一维的。* 同一模型在不同类别间的排名最多相差十六位（Grok 4.7 文件操作第一、会话状态第十一；Opus 4.6 直接驱动第三、权限第十九），但十五对类别相关系数全为正（均值 +0.521）。
  * *前两名的差别在边界情况。* 普通场景上 Opus 5 领先 GPT-6 Astra（80.68% 对 72.46%）；边界场景上 GPT-6 Astra 领先（48.97% 对 37.02%）。
  * *实现规模由模型决定。* 代码行数的方差有 95.9% 来自模型之间；同一模型三次构建的变异系数平均 12.7%，而十九个模型均值之间为 60.1%。各模型平均规模从 1,271 行（GPT-5.5）到 16,681 行（Qwen3.8 Max）。在所有构建上，代码行数与通过率的相关为 0.614。
  * *代码量相同时，模块越多分数越低。* 控制代码行数后，模块数与通过率的偏相关为 −0.423（留一模型检验下在 −0.484 到 −0.309 之间），每模块行数为 +0.504（0.312 到 0.649）。
* **比标题更弱或更窄的地方。**
  * *"失败集中在横切功能如何拆分到各模块"超出了所展示的分析。* 证据是 19 个模型 57 次构建上的相关性，而模块数的方差有 87.9% 来自模型之间，所以这主要是在比较模型；模型的整体能力可能同时决定模块化程度和通过率。正文没有把失败的用例归因到模块边界，"专用模块"的关键词判定规则虽有定义，却没有报告用到它的结果。这一关系也不单调（读者据表 4 观察）：Opus 5（33.3 个模块）和 Qwen3.8 Max（40.0 个）分列第二、第三，而 GPT-5.5 把 78% 的代码放在一个模块里，排第十三。
  * *符合规范不等于好用。* 测试集用脚本化模型检查行为是否符合合并后的文档。harness 服务真实模型的能力（提示构造质量、面对真实输出时的上下文管理）没有被衡量，也没有用 57 个 harness 做下游运行来检验排名。
  * *中段排名在构建噪声之内。* 三次构建的标准差最高达 3.29（MiMo-V2.6-Flash、Step 5 Preview），而相邻模型最少只差 0.30（GPT-5.6-sol 43.80、Grok 4.7 43.50）；只有排名的首尾分得清（读者观察）。
  * *何时停手会影响分数。* 契约检查只查形式不查行为，提交早的模型冻结的是修改较少的 harness；作者称其分数是下界。两小时墙钟限制也让分数与服务商延迟挂钩（读者注）。论文没有报告多少次构建是主动提交结束、多少次是超时结束。
  * *测试集部分是在模型构建的 harness 上挑出来的。* 跨 harness 对比用的是某个候选 harness，扩展的种子是已证明有区分度的用例，用例是否有区分度要在评测后才确定。正文没说用了哪些模型的 harness，因此无法排除对排名的选择效应（读者担忧）。作者自己列为局限的相关变体问题也会抬高 KR-20。
  * *56 个地板用例未经审查。* 无人通过的用例可能是真难、文档不清或用例本身有错；没有参考 harness 就无法区分。
  * *构建 harness 是固定选择。* 选 OpenCode 避免了厂商主场优势，但它对排名的影响没有检验；[Learn2Play Bench](../papers/2610.08215.md) 在另一类任务上发现同一底座下 OpenCode 不如 Claude Code 和 Codex（读者交叉引用）。

# Q9 贡献

* 一个从规范出发构建 harness 的确定性基准：从十二个 harness 合并出的纯行为条款、只含接口的骨架、在四个通道上读取的模拟模型黑盒驱动。
* 一套针对禁止性要求的阳性对照设计（通道、同形、反向三类），防止"这件事不得发生"的断言因为功能根本没运行而通过；适用于任何对负面要求的黑盒测试。
* 一套从公开 issue、跨实现差异和带距离检查的单变量扩展中生成测试用例的方法。
* 十九个模型的排名、分类别结果，以及对全部 57 个计分 harness 的源码分析。

# Q10 下一步

* **作者提出的。** 一个迭代的构建-评测-修复协议（当前只衡量单次构建）；处理扩展变体之间的相关失败。
* **给分数定锚（读者建议）。** 用十二个真实 harness 之一或一份人写的文档实现跑一遍测试集，并据此审查 56 个地板用例。
* **与下游使用对照（读者建议）。** 让 57 个 harness 搭配真实模型跑一个编码基准，检验符合度排名能否预测任务成功率——这正是 Doc2Harness 与 AgentSWE 这类基准之间缺的那一环。
* **归因失败（读者建议）。** 把失败用例映射到所涉及的模块，让模块化结论建立在用例级证据而不是模型间相关性上；在 Claude Code 和 Codex CLI 下重复构建，测量构建 harness 本身的影响。
* **与本仓库的关联（读者注）。** 阳性对照规则（每个"某物不存在"的检查，都要配一个"同样的观测在它存在时能看到它"的检查）可以直接用在本仓库那些断言某个禁止的文件、链接或字符串不出现的验证脚本上。

# 相关

* [AgentSWE](../papers/2610.13361.md) - 同样冻结编码智能体构建的智能体并通过基准自有的模型接口运行，但用真实运行时模型和评分细则在下游用例上打分，而不是用模拟模型检查条款符合度。
* [JIT-Agent](../papers/2608.25593.md) - 在统一的四模块协议下重新实现了 13 种 harness 设计，并训练模型按任务合成 harness；Doc2Harness 衡量的则是通用模型能否实现一份合并后的 harness 规范。
* [Learn2Play Bench](../papers/2610.08215.md) - 把 OpenCode 作为九个底座模型的公共 harness，并发现同一底座下厂商 harness 胜过它。
* [ProgramGym](../papers/2610.13395.md) - 另一个"依规范重建"的场景，通过对照参考程序的黑盒测试打分，而非对照书面文档。
