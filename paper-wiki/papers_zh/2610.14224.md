# Q1 问题定义

* **输入（X）：** 一串逐个到来的任务 q₁, …, q_N，没有答案、验证器或分数；一个冻结的执行模型；一个公共的起始 harness H₀，由 K = 8 个可编辑文件组成（系统提示词、护栏、记忆、工具使用指引、技能、脚本、子智能体，以及在工具循环内部运行的中间件插件）；以及重跑当前任务的预算。
* **输出（Y）：** 每个任务在适配后的 harness 下产出的一份交付物，外加一个更新后的*改进 harness*（由被采纳的 harness 和经验教训组成的库），带到下一个任务。
* **约束：** 已完成的任务不再重放；每个任务都从 H₀ 重新开始，而不是继承上一个任务的 harness；编辑者永远看不到评审结论、评分细则或分数；模型权重和改进流程本身保持不变。

# Q2 问题新颖性

部分新颖。离线 harness 搜索（Meta-Harness、AHE，以及论文中 27 种方法对比表里的其他方法）在部署前针对训练任务做优化；测试时方法要么按任务改进 harness（Recursive Harness Self-Improvement、Harness Scaling），要么在无标签批次之间把一个 harness 往下传（TTHE），有时借助代理标签或延迟标签。论文的主张在于组合：不用标签、逐个任务地同时改进执行 harness 和改进它的那套流程，并配一项测试时扩展研究。理由是部署中的任务没有验证器；而把高度定制的 harness 带到下一个任务，会在任务分布变化时引入噪声，真正可复用的是"如何诊断并修好一个弱点"的经验。

# Q3 科学假设

1. 把一个拟议的修改放到同一任务上运行，与未修改的参考运行比较轨迹和交付物，所得证据足以在没有任何正确性标签的情况下选择 harness 改动。
2. 在这件事上投入更多测试时预算（并行组合更多候选，或串联更多步骤），交付物会持续变好。
3. 从这个过程中提取的经验教训，连同它们产生的 harness 一起保存，能让之后的改进更好，包括在另一个基准上。

# Q4 相关工作与关键人物

* **递归自我改进。** 自奖励模型、STOP、达尔文哥德尔机（Darwin Gödel Machine）、Hyperagents（元层面流程可编辑）、MetaSkill-Evolve 和 MCE（产物与构建产物的技能共同演化）。
* **Harness 优化。** 提示词与工作流（DSPy、GEPA、ADAS、AFlow）；记忆与技能（ReasoningBank、Evo-Harness、HyperSkill）；离线优化整个 harness（[Meta-Harness](../concepts/meta-harness.md)、AHE、AI4AI、DarwinX、HarnessX、HSI）；离线加测试时（MemoHarness、Harness-R1、[JIT-Agent](../papers/2608.25593.md)、Recuris）；在线（RHI、Harness Scaling、TTHE、Adaptive Auto-Harness、Continual Harness、HCL）。并行递归借用了 RSA 的聚合原则，串行递归则是把 Self-Refine 用在 harness 上。
* **关键人物。** Google Cloud AI Research（Tomas Pfister、Chen-Yu Lee、Rujun Han、Yanfei Chen），第一作者 Ruiyao Xu（西北大学）。该团队也是基线之一 ReasoningBank 的作者，且有六位作者同时是 [RRSI](../papers/2609.24972.md) 的作者，RRSI 在其中两个相同基准上评测离线 harness 演化。可能的批评者：Meta-Harness 和 AHE 的作者（会要求算力对齐的比较），以及"Rethinking the evaluation of harness evolution"（即 Harness Scaling 基线）的作者。

# Q5 关键解决思路

**对比式一步：提议、探测、组合（Propose、Probe、Compose）。** 先用当前 harness 在任务上跑一次作为参考；参考运行展示的是 harness 的行为方式，而不是输出对不对。编辑者随后通过修改组件文件写出两个候选 harness：一个*跨领域不变（invariant）*候选，针对在各领域都会反复出现的缺陷（规划、工具使用、上下文管理、任务委派）；一个*领域特定*候选，针对本任务所在领域的知识、流程和约束。每个候选都在同一任务、同一模型和环境下运行，与参考运行的差异就是证据。组合者阅读参考运行、两个候选、它们的 diff 以及全部运行记录，然后合并有证据支持的改动、修订相互冲突的改动、采纳其中一个候选，或保留当前 harness，并把每个决定都绑定到一条具体观察上。组合后的 harness 再运行一次，产出交付物。

**两种追加投入的方式。** 预算为 k 时，*并行递归*收集 k 次参考运行，为每个范围各起草 k 个候选，再在整个候选池上进行 k 次独立的组合会话（只做一次种群更新，所以 k 决定宽度而非深度）。*串行递归*串联 k 步，每一步都从上一步的 harness 和迄今为止的全部证据出发。k > 1 时，由一个智能体式选择器对照请求和源文件比较匿名化的交付物并返回其中之一，它看不到哪个 harness 产出了哪份交付物。

**学会构建 harness。** 任务结束后，反思者审阅完整记录，只在有执行对比支持时才保留经验；被采纳的 harness 文件树和一份 `EXPERIENCE.md`（适用情境、经验、证据）成为库中的一条记录，并有索引。下一个任务仍从 H₀ 开始，但它的提议、探测和组合都可以读取并改造库中的记录。可执行组件以文件形式保存，不压缩成文字总结。

# Q6 实验设计

* **基准。** [WorkBuddy-Bench](../concepts/workbuddy-bench.md) 的 Code、Web、Office（测试半区分别为 40、35、25 个任务；综合验证器包括隐藏测试、文件检查，以及以 Gemini 3.5 Flash 为评审的 LLM 或 VLM 评审项）。[JobBench](../concepts/jobbench.md)（34 个测试任务；由 Claude Opus 4.8 按加权评分细则评审）。[Harvey LAB](../concepts/harvey-lab.md)（取自一项已发表 harness 优化研究的 100 个测试任务；按条目通过率"Partial"评分，由 Claude Sonnet 4.6 评审）。每种方法把测试任务当作一条流来处理；报告三条打乱顺序的流上的均值和标准差。
* **配置。** 执行模型为 Gemini 3.5 Flash 和 GLM-5，运行在 OpenCode 或 Codex 中（每个基准四种组合）；每次 rollout 上限 200 轮、3,600 秒。编辑者、组合者、反思者和选择者都是在 OpenCode 下以高推理强度运行的 Claude Opus 4.8；一个守卫会拒绝交出任何包含评审结论、评分细则或分数的工作目录。主表使用一步（k = 1）；"+ Recursion"为 k = 5 的并行递归。
* **基线。** 原始 harness；ReasoningBank（harness 不变，加上在无答案自评下蒸馏出的检索记忆）；Meta-Harness（在 WorkBuddy-Bench 和 JobBench 的训练半区、或 LAB 的 24 个开发任务上离线搜索，然后原样部署）；Harness Scaling（按任务、不看验证器的修订，不携带状态）。修订和反思都用 Opus 4.8。
* **分析。** 在 WorkBuddy-Bench Code 和 Office 上的并行与串行递归预算曲线；总 token 与性能的关系；对库、两个分范围编辑者和组合步骤的消融（k = 1）；库的效果（不借助证据直接改写、k = 1 与 k = 5 下构建的库、从 JobBench 迁移到 WorkBuddy-Bench、留一法重跑）；执行者与编辑者为同一模型（五个模型，k = 2）；附录中的组件移除、库的来源统计、跨模型迁移、工具出错率、与生产级 harness 的比较和失败分析。

# Q8 证据质量

* **有支撑的结论。**
  * *一步就在所有配置中有效。* WorkBuddy-Bench 平均分从 72.4、74.5、64.2、64.4 升到 77.5、77.5、75.7、75.3（Gemini/OpenCode、Gemini/Codex、GLM-5/OpenCode、GLM-5/Codex）；JobBench 提升 1.2 到 4.5 分；LAB Partial 提升 2.0 到 11.8 分。在全部四种组合中，它在 WorkBuddy-Bench 平均分和 JobBench 分数上都高于所有基线；在 LAB 上四种中有三种如此（Gemini 在 Codex 下，Meta-Harness 以 76.5 对 75.6 领先）。Harness Scaling 在十二个基准-配置组合中有七个低于原始 harness。
  * *追加预算持续有回报。* k = 5 的并行递归在一步的基础上，WorkBuddy-Bench 再加 2.9 到 3.9 分，JobBench 再加 3.0 到 4.2 分，LAB 再加 2.6 到 6.7 分。在 WorkBuddy-Bench Code 和 Office 上，两种递归形式从 k = 1 到 5 都单调上升（并行：76.5 到 80.8，79.5 到 83.4），而 Harness Scaling 在 k = 2 到 3 之间出现回退。
  * *每个组件都有贡献。* 在 Gemini/OpenCode、k = 1 下，去掉库在 WorkBuddy-Bench 和 JobBench 上分别损失 3.1 和 1.8 分，把两个分范围编辑者换成两个通用编辑者损失 2.9 和 3.7 分，跳过组合损失 1.6 和 1.9 分。
  * *带来提升的是探测，而不只是更强的编辑者。* 让编辑者在没有参考运行、探测和库的情况下直接改写原始 harness，WorkBuddy-Bench Code 从 73.4 降到 63.2，Web 从 69.9 降到 65.0。
  * *经验有一定的迁移性。* k = 5 下构建的库无需额外探测就能支撑 0.9、4.4、5.1 分的一步提升（Code、Web、Office），JobBench 的库让 WorkBuddy-Bench 提升 0.6、0.5、2.9 分。
  * *不需要更强的编辑者。* 执行者与编辑者为同一模型时（OpenCode，k = 2），从 GLM-5 到 Claude Opus 5 的五个模型在每个基准上都有提升，例如 GLM-5 在 LAB 上提升 13.7 分。
  * *工具出错更少。* 一步在三个基准上都降低了工具出错率，JobBench 降幅最大（14.4% 降到 9.1%），同时 JobBench 和 LAB 上的调用次数反而增加。
* **比标题弱或更窄的地方。**
  * *选择者与评审共用模型。* Opus 4.8 负责编辑、组合和选择，同时也是 JobBench 的评审；WorkBuddy-Bench 的评审项用 Gemini 3.5 Flash，而它也是执行模型之一；LAB 由 Claude Sonnet 4.6 评审。守卫隐藏了细则和分数，但如果选择者偏好的正是同一模型家族作为评审时偏好的东西，JobBench 分数就会在工作质量没有变好的情况下上升（读者观察）。论文没有报告人工评分或跨家族评审。
  * *主表没有对齐算力。* 一步就已经在任务上运行四次（参考、两个探测、组合后的 harness），k = 5 的并行递归要运行二十次再加上编辑会话，而原始 harness 只运行一次。回应这一点的 token 比较（Harness² 位于帕累托前沿）只在图中给出，其数值未读取。附录 C 规定了一个使用同一选择者的 Best-of-k 基线，但在已读的正文和表格中没有出现任何 Best-of-k 数字，因此 k = 5 的提升中有多少来自"在更多次运行中挑选"、而非来自 harness 修改，并未得到展示。
  * *相对噪声而言边际较小。* 标准差最高达 4.5 分，若干一步提升落在一个标准差以内（Gemini/Codex 在 JobBench 上，33.9 ± 2.6 到 35.3 ± 3.5；Gemini/OpenCode 在 LAB 上，79.9 到 81.9）。没有报告显著性检验。
  * *主结果用的是更强的编辑者。* 主表中是 Opus 4.8 为更弱的执行者改进 harness；同模型研究（k = 2）把提升画在图里，正文只给出了其中几项。
  * *跨任务学习是测试最少的一层。* 库在一条流内部的作用只由一项消融衡量（k = 1，一种配置）。留一法重跑（WorkBuddy-Bench 77.5 到 79.4，JobBench 36.0 到 37.7）可以读到后续任务的记录，且重复了执行，作者自己也说明这是离线分析，而不是在线收益。
  * *选择可能挑中更差的输出。* 失败分析显示，选择者曾在 95 分和 55 分的输出之间选了 55 分；一个 LAB 案例因覆盖面变窄从 54 分降到 26 分；错误前提也可能扩散到所有候选中。

# Q9 贡献

* 给出"递归式智能体 harness 构建"的定义，把被改进的执行 harness 和负责改进的改进 harness 分开，只有后者跨任务携带。
* 一种不需要标签的改进步骤：用当前任务的配对重跑作为证据，把提议分成跨领域和领域特定两个范围，并给出并行与串行两种扩展方式。
* 在三个由评审打分的专业基准上，相对离线搜索、检索记忆和逐任务修订都取得提升，并附测试时扩展研究和消融，表明分范围编辑者和探测确有作用。
* 一个具体的八组件、一组件一文件的 harness 布局（包括一个在工具循环内部强制执行行为的中间件插件），以及"诊断出的失败对应修改哪个组件"的实例。

# Q10 下一步

* **作者提出的方向。** 库的管理（合并重叠组件、修订过时经验、改进检索），以及按任务难度分配探索预算、在探测不再带来新证据时停止的自适应递归；更好地平衡覆盖面与精确度的选择，挑战共同前提的探测，以及用重复运行区分修改效果与随机波动。
* **单独隔离选择的作用（读者建议）。** 在执行次数对齐的条件下报告使用同一选择者的 Best-of-k，以及组合后 harness 在选择之前那一次运行的分数。
* **评审与选择者解耦（读者建议）。** 用另一模型家族的评审重新给 JobBench 打分，或请人工给部分样本评分，并用与评审不同家族的选择者再做一遍。
* **在更长的流上测量库（读者建议）。** 画出每个任务的提升随其在流中位置的变化，看靠后的任务是否比靠前的受益更多，这正是留一法测不出的在线效应。
* **与本项目的契合（读者笔记）。** "跨领域不变 / 领域特定"的划分对应本仓库自己的分层：跨项目规则放在根目录的智能体指令和技能里，领域知识放在项目文件里。"先探测再组合"的做法（保留一项改动之前，把修改后的设置与未修改的参考在同一任务上并排运行）是修订本仓库智能体指令时值得采用的低成本检查。

# 相关

* [智能体 harness 工程](../topics/agent-harness-engineering.md) - 在线、无标签地逐任务改进由八个文件组成的 harness，只保留配对重跑支持的改动。
* [递归自我改进](../topics/recursive-self-improvement.md) - 既更新执行 harness，也更新改进 harness（被采纳的 harness 与经验教训组成的库）；编辑模型、其提示词和决策规则保持不变。
* [智能体测试时扩展](../topics/agent-test-time-scaling.md) - 把单个任务的算力花在 harness 候选及其执行证据上（并行宽度或串行深度），报告从 k = 1 到 5 的单调提升。
* [Meta-Harness](../concepts/meta-harness.md) - 在训练半区上搜索后原样部署的离线基线；在 Gemini 于 Codex 下的 LAB 上最好，其余情况都低于 Harness² 的一步，且总算力更多。
* [LLM-as-a-judge](../concepts/llm-as-a-judge.md) - JobBench 和 LAB 完全由评审打分，WorkBuddy-Bench 部分如此；JobBench 的评审与编辑者、选择者是同一个模型。
* [JobBench](../concepts/jobbench.md) - 34 个测试任务；一步提升 1.2 到 4.5 分，并行递归再加 3.0 到 4.2 分。
* [Harvey LAB](../concepts/harvey-lab.md) - 100 个测试任务，按条目通过率评分；GLM-5 在 OpenCode 下一步提升 11.8 分。
* [WorkBuddy-Bench](../concepts/workbuddy-bench.md) - Code、Web、Office 的测试半区；预算、消融、库和组件研究的主要基准。
* [RRSI](../papers/2609.24972.md) - 同一团队：针对演化集过拟合加以正则化的离线 harness 演化，在 JobBench 和 Harvey LAB 上评测；Harness² 通过逐任务改进、只迁移经验来回避演化集。
* [AgentSWE](../papers/2610.13361.md) - 发现通用编码智能体在小开发集上做的 harness 优化大多无法迁移；Harness² 把每项修改都限定在它被测试过的那个任务上。
* [JIT-Agent](../papers/2608.25593.md) - 同样在测试时按任务适配 harness，但用的是训练出的 harness 合成模型，而不是带探测的冻结编辑者。
* [MemoHarness](../papers/2607.14159.md) - 把离线 harness 搜索与双层经验库和逐案例适配结合；Harness² 从空库开始，不使用任何标签。
* [Mid-Harness](../papers/2609.39982.md) - 另一种在固定任务上花测试时算力的方式：在循环内部对动作采样和验证，而不是修改外围的 harness。
* [AREX-2](../papers/2609.38288.md) - 通过训练模型来扩展单个任务内的改进轮数；Harness² 用冻结的执行者做到这一点。
