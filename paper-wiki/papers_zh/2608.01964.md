> 论文：**LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks**
> 论文链接：<https://arxiv.org/abs/2608.01964>
> 机构：DreamX Team，阿里巴巴集团

# Q1 问题定义

* **输入 `X`**：一个长时程任务和一个计算机环境(桌面虚拟机、终端,或混合 GUI/CLI 工作空间)、一个选定的底座模型,以及一个执行后端(Claude Code、Codex CLI、OpenClaw 或 Hermes Agent)。
* **输出 `Y`**：一条经过审计的任务完成轨迹,最终落在四种管理者决策之一——完成(done)、受阻(blocked)、需要询问(ask),或轮次预算耗尽——由一个外部维护的任务状态驱动(需求、制品、事实三类记录,每条都标记为已完成/待定/受阻/不可信,并附有支持性审计证据)。
* **核心问题**：现有 agent harness 把任务执行、任务状态跟踪、完成度自我评估都放在同一个不断增长的上下文里,导致状态越来越难以追踪,而 agent 对"是否完成"可能出错的自我判断又会被记录下来,成为后续决策的前提。
* **范围**：这是一个 harness 层面的干预。模型权重和各后端原生的 agent 循环(单个 episode 内的规划与工具使用)都保持不变;改变的只是外围的角色结构和状态持久化契约。

# Q2 问题的新颖性

长时程 agent 执行及其被命名的失败模式——误差累积与目标漂移、上下文腐化(context rot)、任务状态丢失——都是既有的关注点(论文引用 METR 的发现:先进 agent 的任务完成时限大约每七个月翻一番)。现有的 harness,例如 Claude Code、Codex CLI、OpenClaw,已经支持规划、任务分解、工具使用,以及用于执行或复核的隔离上下文子 agent。本文的新意在于诊断出这些 harness 长时程失败背后的两个具体结构性耦合——(i) 任务执行与任务状态管理共享同一个不断增长的上下文;(ii) 任务执行与完成度评估仍由同一个 agent 耦合完成——并通过把角色彻底拆分为三个(管理者、执行者、审计者)来同时修复这两个问题,其中只读的审计者从不采信执行者自身的完成度声明,并通过一个轻量级 `AgentAdapter` 包裹在既有后端之外,保留其原生 agent 循环。

# Q3 科学假设

如果把任务状态维护成一份完全独立于任务执行之外的显式记录,只由一个独立的、只读的审计者直接对照环境核验过的事实来推进(而绝不采信执行者自我报告的完成度声明),并且每个子任务都在一个全新的、有预算上限的上下文中执行、其原始轨迹在结束后被丢弃,那么长时程任务完成的可靠性就能在不同底座模型、不同执行后端、不同交互领域(GUI、CLI、混合)之间获得一致的提升,而不需要在模型层面引入新能力。论文并不主张 MEA 本身能提升单步任务求解能力——论文明确发现该框架无法弥补 agent 本身缺失的某项能力(例如视觉感知或算法设计)——它只主张 MEA 能提升既有的单步能力被转化为完成长时程任务的可靠程度。

# Q4 相关工作与关键人物

* **长时程能力趋势**：METR 的发现——先进 agent 的任务完成时限大约每七个月翻一番;前沿编码 agent(Codex、Claude Code)已经能在单个项目上持续工作数小时。
* **借用自既有工作的命名失败模式**：误差累积与目标漂移、上下文腐化、任务状态丢失。
* **被扩展而非被替代的既有 harness**：Claude Code、Codex CLI、OpenClaw、Hermes Agent——LongHorizon-Harness 通过 `AgentAdapter` 包裹而非重新实现它们原生的类 ReAct 循环。
* **Agent-as-judge / LLM-as-judge 相关文献**为设计一个独立的、只读的审计者角色提供了动机。
* **作者/机构**：Hailang Huang、Shun Zou、Yong Wang、Shidong Yang、Yiming Hu、Fei Wei、XiangXiang Chu——DreamX Team,阿里巴巴集团。

# Q5 核心解法

一个 Manage-Execute-Audit(管理—执行—审计,MEA)循环,单个任务最多运行 `N_max=25` 轮：

1. **管理者(Manager)**：持有持久化的任务状态,且完全没有环境访问权限——不能观察应用状态、不能查看工作空间内容、不能调用 GUI 或 CLI 工具、不能修改环境。它读取原始任务、当前任务状态,以及所有已积累的审计报告,据此更新任务状态并做出控制决策(执行 / 完成 / 受阻 / 询问)。当决定继续执行时,它给出一份有边界的子任务契约——目标、验收标准、边界约束、相关的既有证据——并按所需的主要环境转换类型路由给 GUI 或 CLI 执行者。
2. **执行者(Executor)**：唯一被允许有意修改环境的角色。它在一个全新的、有预算上限的 episode(1800 秒)中执行契约,该 episode 只包含当前轮次提供的信息——不含早前轮次的原始交互轨迹。在这个 episode 内部,它可以多次循环规划、环境交互、观察和修正;episode 结束后,只有它的执行报告(一份自我报告的摘要,并非完成的证明)会被转发,原始轨迹和内部推理都被丢弃。GUI 执行者获得截图、点击、滚动、输入等能力,CLI 执行者获得 shell 执行、文件编辑、测试等能力——这是一种按角色划定的能力边界。执行者通过统一的 `AgentAdapter` 接口实例化:给定一份契约、角色专属的环境接口和一个执行预算,适配器把 Claude Code、Codex CLI 或 OpenClaw 等既有后端作为一个有边界的 episode 启动;harness 不替代后端内部的执行流程,只控制提供的上下文、可用工具、环境权限、执行预算,以及最终返回的报告。
3. **审计者(Auditor)**：只读,预算 300 秒。它接收原始任务、任务状态、契约、契约引用的既有审计报告,以及执行者报告——但从不接收执行者的原始交互轨迹或内部推理。它独立检查执行后的环境(GUI 审计者通过观察式交互检查应用与屏幕状态;CLI 审计者用非修改性的命令和检查工具查看文件、元数据、日志、进程、测试、工作空间状态),产出的审计报告包含三部分内容:第一,依据契约的验收标准评估出的完成状态(完成/未完成/受阻);第二,通过检查工作空间修改、制品有效性与来源、相关删除约束得到的完整性状态(干净/可疑/违规)——harness 会在整个审计过程中监控与任务相关的工作空间和制品状态,审计者自身造成的任何环境改动都会被记为完整性违规,相应的报告不能支持"已完成"这一记录;第三,记录检查所支持的任务状态更新,包括已核验的事实、支持性证据、仍存在的缺口。审计者可以提议对需求、制品、事实记录做出改动,但由管理者决定这些发现如何被纳入下一步的任务状态——因此执行者报告始终只是一份未经核验的执行摘要,而审计报告才是可能推进持久化任务状态的、有环境依据的证据。

关键设计选择是:执行者报告被明确当作"一份未经核验的执行摘要",只有审计者独立核验过的报告才能推进持久化的任务状态记录——这正是阻止一个看似合理但实际错误的完成度声明扩散到后续决策中的机制。

# Q6 实验设计

在相同底座模型、相同 Claude Code 执行后端的匹配对比(基线 vs. MEA)条件下,评估三个基准:**WeaveBench**(114 个跨 8 个领域的混合 GUI+CLI 任务;PassRate 定义为得分不低于 0.8 的任务比例,Overall 为全部任务的平均分;由 Claude Opus 4.7 担任轨迹感知型评判者)、**OSWorld 2.0**(108 个桌面工作流任务,人类完成时间中位数约 1.6 小时,使用官方 Docker 虚拟机基础设施;Binary Accuracy 为最终得分恰为 1 的任务比例,Partial Accuracy 为平均得分——LongHorizon-Harness 独特地使用了混合 GUI+CLI 工具池,而官方基线仅使用 GUI 工具),以及 **Terminal-Bench 2.1**(纯命令行任务,通过 Harbor/Docker 评测,每个任务独立运行三次取平均,单次试验超时 5 小时)。主要底座模型为 Qwen 3.7-Plus,并在 OSWorld 2.0 的一个 34 任务子集上用 Claude Opus 4.7 检验泛化性。管理者和审计者各预算 300 秒,执行者预算 1800 秒,`N_max=25` 轮。论文按角色(管理者/执行者/审计者)在每个基准上报告了 token 消耗占比的拆解。四组配对案例研究展示了同一任务下基线与 MEA 的轨迹对比——从卡顿交互中恢复、审计看似完成实则不合格的结果、保留修复前证据、从已核验进度继续——并给出前后对比得分。

主要匹配结果:WeaveBench PassRate 从 51.8% 提升到 80.7%(Qwen 3.7-Plus,Claude Code 后端);Terminal-Bench 2.1 从 69.7% 提升到 77.2%(同一配置);OSWorld 2.0 二值完成率从 2.8% 提升到 8.3%,部分得分从 21.5% 提升到 35.2%(Qwen 3.7-Plus);OSWorld 2.0 的 34 任务子集上,二值完成率从 20.0% 提升到 34.3%,部分得分从 55.8% 提升到 66.9%(Claude Opus 4.7)。

# Q8 证据质量

核心对比是匹配的——相同底座模型、相同 Claude Code 执行后端,只隔离出 MEA 这一层包装——覆盖三个各自独立来源的官方基准,跨越混合 GUI+CLI、桌面、纯命令行三类领域,且在每一组匹配对比中都取得一致的提升,这为"提升来自 MEA 机制本身而非仅仅是底座模型强度"提供了较有说服力的证据。论文对成本和适用边界也相当坦诚:token 消耗在 WeaveBench/OSWorld 上上升了 2.3–3.6 倍,但在 Terminal-Bench 上反而下降了 24%(并非固定倍数),且提升集中在进度可以被表示为可验证环境状态的任务上,在瓶颈是单一模型能力(而非长时程执行可靠性)的任务上收益会缩小甚至转负——审计无法补足模型本身不具备的能力。需要注意的地方:WeaveBench 与官方报告数字的对比中,本文的运行使用了任务虚拟机内的 root 权限,而官方结果使用普通用户账户,因此这部分跨配置的行被明确标注为参考点而非匹配对比;OSWorld 2.0 的官方基线只使用 GUI 工具,而 LongHorizon-Harness 使用混合 GUI+CLI 工具池,因此 OSWorld 上的部分提升可能来自额外的工具访问权限,而非 MEA 结构本身——论文没有报告一个纯 GUI 的 MEA 消融来把这两个因素分开;WeaveBench 的评判者(Claude Opus 4.7)与审计者角色都依赖 LLM-as-judge 式的核验,因此二者都继承了这一评判范式本身可能带有的盲点。

# Q9 主要贡献

1. 把长时程 agent 执行重新表述为一个任务状态管理问题:状态在执行之外被显式维护,只由独立核验过的事实推进,并被用来决定下一个子任务。
2. 设计了 Manage-Execute-Audit 循环,包含三个角色分离的组件——持有状态、不接触环境的管理者;修改环境、在全新上下文中运行的执行者;只读、独立核验的审计者——外加一个轻量级 `AgentAdapter`,使得跨后端(Claude Code、Codex CLI、OpenClaw、Hermes Agent)、跨模型(Qwen、Claude、GPT)的互换成为可能。
3. 在 WeaveBench、OSWorld 2.0、Terminal-Bench 2.1 上做匹配对比实证验证,展示了在混合、桌面、纯命令行三类领域以及两个底座模型上的一致提升,并给出按角色的 token 成本拆解和四组定性案例研究,具体展示了恢复机制的运作方式。

# Q10 下一步

* 论文自身的分析呈现的是适用边界,而非一份正式的局限性小节:MEA 的收益集中在瓶颈是长时程执行可靠性的任务上,而非瓶颈在于单一模型能力(视觉感知、数学推理、编码、算法设计)的任务上——独立审计"无法补足模型本身不具备的能力"。成本并非固定倍数,而是依赖任务和模型:较弱的模型(Qwen)会把更多 token 花在重复执行和恢复上(10.7M → 34.3M token/任务),而较强的模型(Opus)所需的审计—重规划轮次更少,其成本反而下降(16.5M → 11.1M)。
* 自然的后续工作:通过一个纯 GUI 的 MEA 消融来分离 OSWorld 2.0 的提升究竟来自混合 GUI+CLI 工具池还是 MEA 结构本身;在匹配的(非 root)权限下重新运行 WeaveBench 对比,得到一行真正可比的数字;研究在真值本身模糊的任务上(具身视觉精度、时间性的视频证据、允许多种合理解读的任务语义——论文自己指出的剩余失败集中区域)审计者的判断质量本身是否会下降。
* **与本仓库的关联**：管理者/执行者/审计者的角色分离——审计者从不采信执行者的自我报告,任务状态只从独立核验过的事实推进——与本仓库自身的证据优先原则("仓库证据优先于摘要和交接快照")高度相关,值得对照检视本仓库当前对委派或多步 agent 工作的核验方式。
