# Q1 问题定义

* **输入（X）：** 一条描述游戏的用户指令、当前游戏版本 $G_t$（代码与素材）、上一轮的反馈，以及用户在试玩过程中可选提供的显式文字偏好。
* **输出（Y）：** 每一轮产出一个修订后的可玩候选版本 $C_t$，外加审阅者（Reviewer）关于保留哪个版本的选择，以及供下一轮使用的结构化反馈记录。循环轮数可配置，模型参数保持不变。
* **核心问题：** 编码智能体已经能做出可运行的游戏，但程序正确并不保证玩起来有趣。难度、机制、呈现和反馈决定一款游戏值不值得玩；论文要回答的是：如何把这种体验、乃至某位玩家的个人口味，变成"构建—试玩—审阅"反复循环的明确目标。

# Q2 问题新颖性

部分新颖。迭代式的智能体游戏开发已经存在：Harness-of-Harness（多日开发并带独立评估）、VibeGame（带自我进化对抗智能体团队的提示到游戏开发）、AVR-Agent（根据音视频录制进行修订）、用 GUI 智能体测试游戏的持续生成方法，以及同期工作 [RSIGame](../papers/2609.39045.md)，它根据评估反馈递归改进游戏。GameDevBench、GameCraft-Bench、GameXpert-Bench 等基准对生成、修复与优化进行评分。论文声称的不同在于目标：不只是功能正确或基准分数，而是玩家体验——通过大量低成本、由代码驱动的试玩来衡量——以及对单个玩家推断出的或明确表达的偏好的适配。

# Q3 科学假设

1. **用代码玩比用截图玩更适合测试。** 如果试玩者（Player）编写可复用的策略，通过游戏的程序化接口作用于暴露出来的状态，而不是根据截图逐步选择动作，那么试玩会频繁、多样且可复现，足以暴露难度和失败点（3.2 节；图 4 只作示意，没有与 GUI 试玩者做对比测量）。
2. **以体验为导向的审阅能逐轮改进游戏。** 如果审阅者结合轨迹统计、针对具体游戏的评分细则和视觉证据，并且每轮只保留更好的版本，游戏质量会逐轮上升并超过迭代式基线（GameCraft-Bench、GameASG-Bench）。
3. **偏好反馈能把游戏引向某位玩家。** 如果把推断的和显式的偏好记录下来交给设计者（Designer），修订就会朝着预期体验移动（专家评分的用户研究）。

# Q4 相关工作与关键人物

* **软件之外的编码智能体。** 视频方向的 Code2Video、VideoAgent、VideoCoCo；具身控制与奖励设计方向的 Code as Policies、ProgPrompt、Voyager 和 Eureka——它们启发了把可执行策略作为试玩者的载体。
* **用编码智能体开发游戏。** MetaGPT、ChatDev、GameGPT、AutoUE、OpenGame、AVR-Agent、Harness-of-Harness 和 RSIGame；基准 GameDevBench、GameCraft-Bench、GameXpert-Bench、GameASG-Bench。
* **反馈精炼与偏好对齐。** Self-Refine、Reflexion、AFlow、EvoMAC、Darwin Gödel Machine；RLHF、DPO 和 VideoDPO；体验驱动的程序化内容生成（Yannakakis 与 Togelius），以及面向赛道的体验驱动强化学习。本文修订的是游戏产物，而不是模型权重。
* **关键人物。** 四位作者均署名港大 MMLab 和香港大学，其中三位还署名 Shenzhen Loop Area Institute；文中有共同一作和通讯作者标记，但从获取的 HTML 中无法还原对应关系（Xihui Liu 列于最后）。RSIGame、Harness-of-Harness 和 GameASG-Bench 的作者是最直接的批评者；体验驱动内容生成方向的研究者也会质疑以游玩时长和策略成功率作为乐趣的代理指标。

# Q5 关键解法思想

* **设计者（Designer）。** 把需求简述和上一轮反馈展开为计划 $P_t = (h_t, \Delta_t, A_t, X_t)$：关于要做哪种体验改进及其理由的假设、具体改动及需保留的优点、以场景/玩家输入/可观察结果表述的验收目标，以及素材需求。
* **构建者（Builder）。** 按游戏机制和视觉方向选择工具，先做出可玩草稿（必要时用占位符），由框架生成所需素材，再整合进去，并在游戏场景中检查素材与碰撞、动画、交互区域的配合。
* **代码原生的试玩者（Coding-native Player）。** 读取游戏的状态模式、合法动作和测试目标，编写一个"观察状态—选择动作—重复直到回合结束或预算耗尽"的策略。策略在策略风格、技能水平、探索程度和风险偏好上各不相同；回放以并行或重复的执行任务运行，记录状态、动作、事件、进度、耗时和终止结果。每一步动作都无需调用语言模型；执行失败时会修订策略代码。
* **以体验为导向的审阅者（Experience-oriented Reviewer）。** 使用（1）共享信号：不同技能水平策略的成功率（目标是合适的难度，而非最高成功率），以及结合进度解读的游玩时长，以区分丰富多样的长时间游玩和卡关；（2）针对具体游戏的评分细则，从共享维度（操控响应、内容丰富度、节奏、视觉一致性、对探索或重玩的支持）实例化而来，例如赛车游戏看转向、视觉小说看对话连贯；（3）抽样截图和录像，审阅时看不到源代码，也不知道版本先后。它写出一份偏好记录，说明期望的体验、支持证据、每条偏好是推断的还是用户明确提出的，以及优先级。
* **版本保留。** 审阅者在匿名化证据上比较候选版本与当前保留版本，给出 A/B 偏好、平局或"无法判断"，并附理由和证据路径；框架保留被偏好的产物，把反馈交给设计者。

# Q6 实验设计

* **GameCraft-Bench。** 在由 Harness-of-Harness（Yan 等，2026）选出的 45 个任务上做三轮精炼，按五个游戏类别（动作、时机、策略、模拟、冒险）和总分以 0-100 打分。对比对象：Codex + GPT-5.5（high）、OpenCode + DeepSeek-V4-Pro、Pi + MiniMax-M3 的原始结果和 Harness-of-Harness 第 1-3 轮结果，以及本框架所用模型 GPT-6 Astra（high）的基线。
* **GameASG-Bench。** 47 个浏览器游戏任务。L1 检查源代码；L2 在浏览器中运行游戏，分三个优先级（P0 启动与测试接口，P1 必需玩法，P2 扩展功能）。任务成功要求有效交付、完成评估、通过全部 L1 检查以及所有适用的 L2 P0/P1 检查。基线数据直接取自 GameASG-Bench 论文的表 3。
* **定性开发轨迹。** 一款动作游戏、一款视觉小说和一款三角色"Meme Arena"对战游戏的早期、中期、后期版本（V1-V3），以及三款展示游戏（MOBA、赛车、视觉小说）。
* **试玩者探索。** 在一个 FPS 测试场景中，48 次策略回放的访问热力图，旁边是三条示意性的 GUI 式路线。
* **用户研究。** 在三轮偏好引导的修订中，由专家对操控、可玩性、深度和美术按 1-10 分评分，并记录平均游玩时长。

# Q8 证据质量

* **有支持的部分。**
  * *同一模型的游戏在 GameCraft-Bench 上逐轮变好。* 总分从第 1 轮的 72.70 升至 75.35 和 77.89，GPT-6 Astra 基线为 71.26（+6.63），Harness-of-Harness 最佳条目（Codex + GPT-5.5 第 3 轮）为 71.52（+6.37）。五个类别从第 1 轮到第 3 轮全部提升；动作类提升最多（67.96 到 77.62），但第 1、2 轮仍低于基线的动作分 73.33。
  * *在 GameASG-Bench 上相对 Codex CLI 下的同一模型大幅提升。* 任务成功 25/47（53.2%），而 GPT-6 Astra（high）配 Codex CLI 为 9/47（19.1%），提高 34.1 个百分点；L2 平均通过率（93.4%）和 P2 扩展功能通过率（93.9%）为表中最高。
  * *用代码试玩能覆盖关卡。* 48 次策略回放覆盖了 FPS 场景 97.1% 的网格，包括 11 个室内空间；作者说明这只展示覆盖率，并不是相对 GUI 试玩的测得加速。
* **较弱或比标题更窄的部分。**
  * *在 GameASG-Bench 任务成功率上并非最佳。* GPT-6 Astra（ultra）配 Codex CLI 通过 26/47（55.3%）；本方法在 L1（98.3 对 99.6）、P0（99.0 对 100.0）、P1（92.2 对 92.7）上也不是列最高。贡献列表中"在两个基准上总分最高"的说法只对 GameCraft-Bench 和 L2 平均通过率成立。摘要中的"34.1% 提升"是百分点差；引言中的"from 9.47 to 25/47"看起来指的是 9/47。
  * *基线对比中模型与框架相互混杂。* Harness-of-Harness 只用 GPT-5.5、DeepSeek-V4-Pro 和 MiniMax-M3 运行过，从未用 GPT-6 Astra，因此领先它 6.37 分同时包含框架和模型的差异。GameCraft-Bench 上 GPT-6 Astra 基线所用的框架未说明，GameASG-Bench 的基线是从另一篇论文照搬而非重跑。
  * *没有算力匹配，也没有消融。* 本框架用三轮"设计—构建—试玩—审阅"对比单次或配置不同的基线，且未报告成本。没有实验去掉代码原生试玩者、游戏专属评分细则、视觉证据或偏好记录，因此无法说明哪个组件带来了提升。
  * *用户研究很单薄。* 表 3 每轮只给出一个整数分（例如可玩性 1、4、7）和平均游玩时长（1.50、4.87、12.41 分钟），没有专家人数、玩家人数或游戏数量，没有方差，也没有对照条件。摘要称其为用户研究，表格称其为专家评分。
  * *子集与评估方式。* GameCraft-Bench 结果只覆盖 140 个任务中的 45 个，且该子集由另一篇论文选定；论文没有描述 GameCraft-Bench 的评分流程，也没有报告重复运行，因此运行间波动未知。

# Q9 贡献

* 一个以玩家体验为修订目标的四角色框架：每轮有明确的设计假设和验收目标；试玩者编写并运行策略，而不是根据截图行动；审阅者结合轨迹统计、游戏专属评分细则和视觉证据；以匿名 A/B 比较决定版本保留。
* 一份区分"观察到的行为、推断的偏好、用户明确要求"的偏好记录，使同一个循环既能用于一般性质量提升，也能为单个玩家定制。
* 在 GameCraft-Bench（45 任务子集）和 GameASG-Bench 上相对同一基础模型的大幅提升，以及定性版本轨迹和专家评分的定制化研究。

# Q10 下一步

* **作者提出的。** 把功能原型推进为产品级游戏，并评估对单个玩家的持续适配；对试玩者而言，与基于 GUI 的试玩做一次受控对比，匹配预算和可观察信息，并计入策略构建、修复、执行和审阅的成本。
* **匹配条件的对比（读者建议）。** 用 GPT-6 Astra 在相同轮数和 token 预算下运行 Harness-of-Harness 和 RSIGame，并逐一消融审阅者的各项输入，以区分框架本身、模型和额外算力各自的贡献。
* **代理指标是否对齐。** 审阅者奖励来自合成策略的"合适成功率"和更长、更多样的游玩时长，构建者据此修订。这究竟追踪的是人的乐趣，还是在教构建者把游戏做得更长，需要一项给出样本量、对版本先后做盲化的人类研究来检验，类似 RSIGame 的自由试玩检查。
* **接口能暴露什么。** 代码策略只能测试游戏程序化接口所暴露的内容；屏幕上可见、但不在状态模式中的缺陷只能通过抽样画面传到审阅者。测量每个通道各能发现多少缺陷，可以说明视觉审阅是否足够。
* **超越小游戏。** 所有结果都针对智能体几轮内就能做完的游戏；代码原生试玩能否扩展到大型引擎项目（如 AutoUE 所用的 Unreal）或长线成长内容，尚未检验。
