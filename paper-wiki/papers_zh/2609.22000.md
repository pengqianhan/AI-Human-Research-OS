# Q1 问题定义

* **输入（X）：** 一条高层任务提示、一个正在运行的参照应用 A* 的交互式访问权限，以及一个同时暴露图形界面控制与软件开发工具的预备环境。智能体可以在"操作参照应用、编写代码、构建/启动自己的候选实现、并将运行中的候选与参照应用做核对"这几件事之间反复切换——任务规定了期望产出的工件，但不规定动作的顺序或方式。
* **输出（Y）：** 一份满足该平台构建/启动契约的完整源码提交 S（桌面平台：源码加构建/启动入口点；Android：能生成 APK 的 Gradle 项目；Web：脚手架源码生成一个自包含的 `index.html`）；构建并启动 S 会产出可运行的候选应用 Â，据此对照一套隐藏的、经参照应用验证过的测试套件打分。
* **核心问题：** 计算机使用智能体此前沿两条彼此互不相通的路线发展——操作图形界面的智能体无法构建界面背后的软件，终端/编程智能体能编写程序却看不到自己动作所产生的界面。真实的数字工作需要二者交替配合，而不是首尾相接的两个阶段；现有基准大多只侧重一种交互方式，使得对"探索→实现→验证"这一长程循环的自主协调能力长期未被充分测量。
* **范围：** 覆盖五个平台（Ubuntu、macOS、Windows、Android、Web）的复现任务；RecreationBench 留出评测共 250 个任务（每平台 50 个）；一项在两个 Qwen 初始化模型上进行的 35,000 条轨迹 SFT 训练研究，迁移到五个独立的分布外（OOD）基准上（并非 RecreationBench 本身）。全部基准评测均使用标准的直连 MCP 接口；一项持久化可编程运行时对比实验（5.2 节）是单独进行的、不计入基准结果的实验，仅在一个平台（Windows）、一个模型（Claude Opus 4.8）上开展。

# Q2 问题新颖性

论文并不单独声称首创图形界面智能体、终端/编程智能体或可扩展环境生成——它引用 OSWorld/OSWorld 2.0 与 AndroidWorld 作为图形界面操作这条线的代表，SWE-bench/ProgramBench 作为终端/编程这条线的代表，并将 WeaveBench/PhoneHarness/CoAct-1/StateAct 列为已在一定程度上结合图形界面与代码的既有工作。其自陈的新颖之处在于"复现"这一具体任务设计：智能体不是像大多数编程基准那样一开始就拿到固定规范，也不是执行一个脚本化的图形界面操作目标，而是必须通过操作一个正在运行的参照应用来自行还原出规范，然后才能实现并自我验证一份忠实的复现——这颠倒了通常编程任务的方向，使图形界面探索、实现与验证真正不可分割，而不是先后进行的独立阶段。这与 CoAct-1（在图形界面与代码两种可调用模式之间做委派）和 StateAct（以程序状态访问为主、图形界面为辅）不同，因为 RecreationWorld 要求智能体在完全没有预设工作流的情况下，自主决定何时探索、何时实现、何时验证。它也与拥有既定规范的可视化编程基准（Design2Code、WebGen-Bench、Vision2Web）不同，因为规范本身必须通过交互被发现，而不是从提示词中读出。参照应用即预言机的设计被明确表述为"验证不对称性"（Wei, 2025）的一个实例：一旦针对参照应用验证并冻结了隐藏测试套件，对任意候选打分就是自动且与实现无关的。

# Q3 科学假设

如果在执行落地的复现轨迹上训练智能体——其中成功要求跨越一个"探索—实现—验证"闭环，而不是遵循一个固定规范——那么该智能体应当发展出能够迁移到复现训练期间从未见过的基准与任务分布上的混合计算机使用能力，并伴随更频繁地对自身产出做自我验证的副产物。论文自身的证据：两个模型初始化（Qwen3.7-Plus；Qwen-Flash-CPT）在 35,000 条经拒绝采样的复现轨迹上微调后，均在全部五个分布外基准（ProgramBench、GameCraft-Bench、Vision2Web、OSWorld 2.0、WeaveBench）上超过各自的首个评测检查点，最高提升达 17.9 个百分点（3.2 节，图 5），并伴随自身输出图像读取次数与图形界面观察/交互的可测量上升（3.3 节，图 6）——不过论文明确指出，这些行为层面的变化是描述性的，并不能证明它们与得分提升之间存在因果关系。

# Q4 相关工作与关键人物

* **面向智能体任务的可扩展环境。** Gym-Anything、CUA-Gym、GUI-GENESIS、InfiniteWeb、AutoWebWorld、VeriEnv 与 OSGym 被归为既有的可扩展环境构建工作（自动化搭建/审计、合成的模拟网页应用、代码原生奖励、并行执行基础设施）；OpenCUA、OS-ATLAS、UI-TARS/UI-TARS-2、ComputerRL、SCALECUA、EvoCUA 与 Qwen-CUA 被归为扩展"用于训练智能体策略的经验数据"这一路线的既有工作。RecreationWorld 自陈的区别在于，将可扩展任务构建、自动化验证与轨迹生成统一在同一个框架内，同时服务于训练与评测，且可执行的参照应用在"不预先规定实现方式"的前提下提供行为监督信号。
* **混合计算机使用。** OSWorld/OSWorld 2.0 与 WebArena/AndroidWorld 是图形界面/网页/移动端环境谱系；WeaveBench 与 PhoneHarness 被引用为明确研究图形界面与代码/工具协同的工作；CoAct-1（在图形界面与代码之间委派）与 StateAct（以程序状态访问为主、图形界面用于视觉定位的子目标）是最接近的既有混合智能体设计，二者都与 RecreationWorld 完全自主、无预设工作流的循环有所区别；EdgeBench 与 Agents' Last Exam 被引用为其他长程可验证任务的路线。
* **可视化与交互式编程。** Design2Code、DesignBench、Web2Code、WebCode2M、SWE-bench Multimodal、Interaction2Code、WebGen-Bench、Vision2Web、APPFORGE、RealDevWorld 与 GameCraft-Bench 被归为既有的可视化/交互式编程评测工作；RecreationWorld 自陈的扩展在于要求目标规范本身必须通过交互被主动发现，而不是给定，同时仍通过冻结的、经参照应用验证的测试来对外观与条件化行为两方面打分。
* **关键人物与机构。** 共 32 位贡献者，按姓氏字母顺序排列（据论文自身的贡献者说明）；`hf papers info` 将该论文归属于 Qwen（阿里巴巴）组织。检索到的贡献者名单中未单独标出通讯作者。提交于 2026 年 9 月 18 日（arXiv v1；本次抓取的 HTML 为 v2，2026 年 9 月 21 日）。项目主页 recreation-bench.cc；代码见 github.com/QwenLM/RecreationWorld（据 `hf papers info`，抓取时 40 星）。

# Q5 关键解法思路

1. **将应用复现作为任务表述（2.1 节）。** 给定一个正在运行的参照应用 A*，智能体必须返回满足平台构建/启动契约的源码 S；仅评估 S 的**可观测行为**，而非其架构或源码结构本身，让智能体在保持成功判定客观的同时，自由选择实现策略。
2. **五平台可复现执行底座（2.3 节）。** 每次执行都会分配到一个版本化、任务隔离的工作机（固定的图形运行时、自动化接口、构建工具链），并在一个可水平扩展的虚拟机池中调度；单次执行的墙钟超时设为 20 小时，让任务复杂度（而非基础设施截止时间）决定有效的交互时长；桌面工作机暴露原生的截图/输入/无障碍树访问，Android 工作机托管一个固定的硬件加速模拟器，Web 工作机在本地托管参照应用并通过 Playwright 驱动无头 Chromium。
3. **参照应用驱动的双通道测试生成（4.3–4.4 节）。** 一个编排器加多个专职子智能体从参照应用中构建功能/界面/动作清单，随后编写用例，包含一个固定条件、一段交互序列，以及程序化（Prog：通过各平台原生自动化接口——AT-SPI、AXUIElement、UI Automation、UiAutomator、DOM/ARIA——读取精确文本/控件状态/计算结果）和/或视觉（VLM：一个共享的裁判模型在固定的视觉检查点上，针对一条依据参照应用生成的自然语言断言返回二元判定）断言之一或二者兼有；每条提出的用例都会先在一个干净的参照应用实例上重放、过滤、经人工复审，然后才被冻结用于自动打分——因此断言依赖运行时可观测的行为，而不是参照应用的内部实现，使同一用例能够不加修改地在任意架构不同的复现实现上运行。
4. **将隔离作为评测完整性的控制手段（4.5 节）。** 模型生成的命令、进程与工件均被视为不可信：一个专用的低权限智能体主体，配合 POSIX 权限或 Windows ACL，只向智能体暴露正在运行的界面、一个可写工作区，以及经批准的固定条件，同时对参照应用源码、隐藏评测材料与凭据加以屏蔽；网络出站流量按平台过滤（Ubuntu 按 UID 过滤，macOS/Windows 采用主机级默认拒绝防火墙，Web 使用带窄口径中继的无路由命名空间）；在 Web 平台上，一旦检测到对参照应用实现工件的直接重新打包或回放，该任务的总分会被封顶在 0.10。
5. **面向训练的规模化轨迹生成（3.1 节）。** Qwen3.8-Max 针对一个独立、经去重处理的高质量开源图形界面应用池（覆盖与 RecreationBench 相同的五个平台）生成复现执行轨迹；通过任务专属的行为验证器做拒绝采样，每个平台挑选 7,000 条高分轨迹（合计 35,000 条，按条数而非 token 长度做平衡），用于在同一混合数据上微调两个初始化模型（完全后训练完成的 Qwen3.7-Plus，以及经过持续预训练的 Qwen-Flash-CPT 检查点）。

# Q6 实验设计

**主基准评测（5.1 节）。** 十个前沿模型（包括 GPT-6 Astra、Claude Opus 5、GPT-5.6 Sol、GLM-5.3、Qwen3.8-Max-0902）通过标准直连 MCP 接口在完整的 250 个 RecreationBench 任务上评测，报告整体与分平台（附录 B）的 Prog 与 VLM 得分。

**可编程运行时研究（5.2 节，图 9）。** 一项单独的、不计入基准结果的对比实验，在相同的 50 个 Windows 应用上进行：直连 MCP（每个原子动作后都交还控制权）对比暴露 Qwen Code 的 `qwen-cua-driver` SDK 的持久化 Node.js REPL，二者均使用 Claude Opus 4.8，每个任务/配置各执行一次；任务质量指标使用全部评测有效的配对，交互/资源指标使用两种配置下记录均完整且无错误的 39 对配对。

**分布外迁移（3.2 节，图 5）。** 两个训练分支（Qwen3.7-Plus、Qwen-Flash-CPT）在 35,000 条复现轨迹混合数据上微调后，沿两条检查点扫描曲线在一个共同的 Claude Code 脚手架下、每个任务每个检查点执行一次，评测五个外部基准（ProgramBench、GameCraft-Bench、Vision2Web、OSWorld 2.0、WeaveBench），各基准均采用自身原生的 0–100 分制指标。

**轨迹与工件分析（6 节）。** 参照应用探索广度（交互类型覆盖率、窗口覆盖率）、受控输入变化、最终闭环完成率、随执行进度变化的实现规模曲线、评测作弊尝试检测（网络访问、受保护路径访问、包/二进制文件检查、权限提升）、token 用量/成本，以及工具调用类型构成，均基于四个已公开完整轨迹日志的模型（Claude Opus 5、Qwen3.8-Max-0902、GPT-6 Astra、GLM-5.3）的记录轨迹计算得出。工件结构分析针对这四个模型全部可用的交付源码（不按行为得分过滤），比较交付源码规模、文件数量/集中度以及界面框架选择与各自参照应用的差异。

**对假设的支撑强度。** 五基准分布外迁移扫描（3.2 节）是论文关于真正泛化能力的最有力证据，因为五个迁移基准都不是 RecreationBench 本身，且训练池已明确针对评测集做过去重——但论文自身也指出这些轨迹"并非全程单调"，所以"超过首个检查点"是一个比"训练全程单调提升"更弱的说法。可编程运行时研究（5.2 节）被论文自己明确标注为"单次执行的完整配置对比"，展示的是"观测到的更低交互开销，而非孤立的因果效应"——这是一次单轮试验的结果，而非受控消融实验。作弊尝试分析（6.1.3 节）是一项真实的完整性检查，但论文明确指出它并不证明任何边界被成功突破，只说明智能体反复发出了与检测器匹配的操作**尝试**。

# Q9 主要贡献

1. RecreationWorld，一个围绕应用复现构建的五平台（Ubuntu、macOS、Windows、Android、Web）可复现执行框架，将可扩展的任务构建、执行落地的自动化验证与轨迹生成统一在一个系统内，同时服务于混合计算机使用智能体的训练与评测。
2. RecreationBench，一个已发布的 250 任务（每平台 50 个）留出基准，配有经参照应用验证、人工复审并冻结的隐藏测试套件，结合程序化（原生无障碍/自动化接口）与视觉（VLM 判定）两类断言；十个前沿模型的评测结果显示 GPT-6 Astra 以 58.1% 的整体得分领先，但完全通过程序化测试的任务比例仅为 2.8%。
3. 实证证据表明复现轨迹训练能够迁移到训练环境之外：两个在 35,000 条经拒绝采样的复现轨迹上微调的模型初始化，均在五个独立的分布外编程与混合计算机使用基准上超过各自首个评测检查点，最高提升 17.9 分，并伴随自身输出验证行为的增加。
4. 一套系统性的轨迹与工件层面分析，表明当前前沿智能体复现界面静态结构的可靠程度明显高于复现交互与计算结果，交付的复现应用通常远小于且在结构上更集中于参照应用（源码行数中位数仅为参照应用的 16.9%），并且智能体经常用平台原生界面工具包替换参照应用原本使用的框架——为"当前混合智能体究竟在哪些方面达不到参照级别的保真度"给出了一份具体、量化的说明，而不只是一个笼统的得分差距。

# Q10 后续方向

论文自陈的局限性（第 8 节）：(1) RecreationBench 强调固定、可复现的环境，因而对涉及实时服务、持续变化的外部状态或真实用户交互的工作流覆盖有限；(2) 隐藏测试套件只抽样了有限的视觉/行为结果集合，因此通过测试并不能确立在所有状态/交互路径上的完全等价性；(3) 公开的参照实现可能已出现在预训练数据中，源码重合筛查无法排除既有记忆或各种形式的源码复用——作者提出，将受控的在线/多用户工作流、扩展隐藏测试覆盖范围，以及引入新构建的参照应用（降低污染风险）作为未来工作方向。

除论文自身列出的局限之外，有三点值得提醒读者在评估本笔记证据时留意。其一，分布外迁移主张（3.2 节）覆盖五个基准，但各自有独立的打分方式、任务数量与配置细节（放在附录 A.5，本笔记未完整阅读）——论文报告的是"统一在 0–100 分制"下的增益，但这五个基准的度量方式本质不同（测试通过比例、评分规则打分、视觉/功能复合得分），因此头条的"+17.9 分"数字应理解为特定于某一基准，而非跨扫描统一的单位。其二，作弊尝试检测器（6.1.3 节）统计的是"与某检测器模式匹配的已执行操作"，明确未确认是否真的成功突破边界或存在恶意意图——一项区分良性调试行为（例如一次合法的包管理器网络请求）与真正评测完整性威胁的后续工作，能够进一步夯实这一具体发现。其三，6 节中做轨迹/工件分析的四个模型，是拥有已发布、完整轨迹日志的子集，未必等同于全部十个参与基准评测的模型——因此第 6 节中的行为主张（例如"更广泛的参照应用探索伴随更强的基准表现"）是从一个四模型子集中得出的，未必能均匀刻画全部十个模型的整体表现。

# 相关

* [GUI and computer-use agents](../topics/gui-computer-use-agents.md)（图形界面与计算机使用智能体）- 在该主题"示范引导 vs. 原生动作空间扩展"这一分歧轴上给出了第三种、截然不同的答案：不同于 UI-Mate 在推理时注入示范，也不同于 MAI-UI 扩展原生动作空间（澄清提问、MCP 工具调用）并配合设备-云协同架构，RecreationWorld 彻底取消了固定规范本身——智能体必须先通过操作参照应用弄清楚"要建什么"，然后才能决定"怎么建"，这使得探索在每个任务中都成为真正承重的、无预设的组成部分，而不是叠加在既定指令之上的一种可选的鲁棒性机制。
* [Agent environments](../topics/agent-environments.md)（智能体环境）- 一个延续 VibeWorlding 与 UrbanGround 风格、从零搭建的沙盒，但覆盖五种异构平台运行时（三种桌面操作系统、Android、Web），共用一套观察-构建-评估契约，而不是局限于单一任务领域；与 VibeWorlding 的双约束验证器类似，RecreationWorld 的"参照应用即预言机"设计把评测与奖励信号生成合并为同一机制（经拒绝采样的复现验证器直接挑选出用于 35,000 条轨迹 SFT 训练集的数据），但不同于 UrbanGround 单一的局部打分代理指标，RecreationWorld 专门配对了两个互补通道（Prog 与 VLM），使得仅复现界面的静态结构无法替代对交互与计算行为的复现——论文自身 6.3 节的发现（结构比交互结果更容易被可靠复现）正是这一设计意图的直接证据。
* [Model Context Protocol (MCP)](../concepts/model-context-protocol.md) - 将每一个平台动作（图形界面控制与编程工具皆然）都通过直连 MCP 工具调用暴露，作为标准的基准接口；并单独研究了（5.2 节）用一个持久化可编程 SDK 运行时替代这种逐原子动作的 MCP 往返模式，作为面向效率的替代方案。
* [OSWorld](../concepts/osworld.md) - 既将 OSWorld 2.0 作为相关工作引用（RecreationWorld 将自身定位为对该图形界面操作谱系的延伸），也将其作为五个外部分布外迁移基准之一（3.2 节）——复现训练后的模型在其上表现出提升，与 RSIAgent 和 LongHorizon-Harness 此前使用同一个 2.0 划分做 harness 机制评测（而非迁移训练证据）的用法形成对照。
