> 论文:**MemOS: A Memory OS for AI System**
> 论文链接:<https://arxiv.org/abs/2507.03724>
> 机构:MemTensor(上海)科技有限公司,联合同济大学、浙江大学、中科大、北京大学、人民大学、北京航空航天大学、上海交通大学等多家学术机构

# Q1 问题定义

* **输入 `X`**:一个 LLM 系统持续产生的用户交互流、任务上下文和累积知识——横跨参数权重、推理时的瞬时状态(KV-cache、隐藏状态),以及外部检索或用户提供的文本。
* **输出 `Y`**:针对某次查询,一份被调度组合进模型推理的明文(plaintext)、激活(activation)、参数(parameter)三类记忆,以及每个记忆单元的系统级生命周期状态(生成/激活/合并/归档/过期)。
* **核心问题**:LLM 缺乏把记忆当作可控资源来管理的统一方式。参数记忆更新代价高、不透明;RAG 本质上是一种无状态的"检索-拼接"补丁,没有生命周期跟踪、版本管理或权限模型;二者都没有把记忆当作可以跨用户、跨任务、跨平台调度的资源——因此系统难以维持长上下文一致性、吸收演化中的知识、实现持久的个性化,或跨部署环境迁移记忆。
* **范围**:提出一套系统架构(三层、四大核心模块)以及 MemCube——一种统一的记忆单元抽象,并对由此实现的系统(MemOS-1031)做端到端评测,对比记忆系统基线;不涉及对底层 LLM 预训练本身的修改。

# Q2 问题的新颖性

面向 LLM 的显式记忆管理是一个活跃方向(各类 RAG 变体、知识编辑、KV-cache 优化、Mem0、Zep 等 agent 记忆工具),但本文认为这些工作停留在工具或机制层面——在一个本质上仍是隐式的记忆底座上叠加插入/更新/删除操作——缺乏系统级的资源模型。本文把这一领域的发展框定为四个阶段(记忆的定义与探索 → 类人记忆发展 → 工具化记忆管理 → 系统化记忆治理),并将 MemOS 定位为第一个在明文、激活、参数三类记忆上统一引入操作系统式资源抽象(调度、生命周期、权限、迁移)的工作,而不是把每种记忆类型当作独立机制分别处理。

# Q3 科学假设

如果把明文、激活、参数三类记忆封装进一个共同的可调度单元(MemCube),该单元带有用于身份识别、治理和行为使用的共享元数据,并由一个三层系统(接口层、操作层、基础设施层)管理其完整生命周期与跨类型转换,那么由此得到的系统在维持长上下文一致性、个性化和知识一致性方面,会优于基于 RAG 或单一机制的记忆工具,同时仍能满足生产部署所需的效率和鲁棒性。

# Q4 相关工作与关键人物

* 延伸了作者自己此前的工作 Memory 3(全文引用为 [1]),后者首次提出在参数存储与外部检索之间引入一层显式记忆,把外部知识编码为稀疏 KV 对注入注意力机制;MemOS 把这一思路推广为一个由操作系统统一管理的、覆盖明文/激活/参数三类记忆的完整系统。
* 直接与 MIRIX(六个专用记忆组件)、Mem0(基于槽位的抽取/更新记忆,参见 [Mem0](../papers/2504.19413.md))、Zep(时间感知知识图谱记忆)、Memobase、Supermemory(动态知识图谱)以及 MemU(多模态摘要为记忆文件)做基准对比——所有方法都在同一个 GPT-4o-mini 底座上重新实现以保证公平性。
* 其操作系统类比取材于经典操作系统的资源管理(调度器、文件系统、访问控制列表),并引用 vLLM 的 PagedAttention 作为已有的、受操作系统启发的 KV-cache 管理实例。
* 与知识编辑方向(ROME、MEMIT、基于 LoRA 的适配器)相关,本文将其归类为参数记忆机制,MemOS 可以将其与明文、激活记忆一并调度,而非与之直接竞争。
* **作者/机构**:由 Zhiyu Li 和 Feiyu Xiong 领衔的 39 人团队,署名 MemTensor(上海)科技有限公司,以及同济大学、浙江大学、中科大、北京大学、人民大学、北京航空航天大学、上海交通大学、上海高等算法研究院等九家学术机构;原始提交于 2025-07-04,本笔记检索的 v4 版本经过大幅扩充,提交于 2025-12-03。

# Q5 核心解法

**三类记忆,一种单元。** MemOS 区分明文记忆(外部检索/注入的文本、结构化图谱、提示词模板——可编辑、可追溯)、激活记忆(推理时的 KV-cache、隐藏状态、注意力权重——短期且隐式激活),以及参数记忆(编码在模型权重中的知识,可通过 LoRA/适配器模块化扩展)。任意类型的每个记忆单元都被封装进一个 MemCube:一个 Memory Payload(语义内容)加上分为三组的 Metadata——描述性标识(时间戳、来源签名、语义类型)、治理属性(访问控制、TTL/衰减规则、优先级、合规标签)、行为使用指标(访问频率/近因性、上下文指纹、版本链)。行为指标驱动"策略感知调度"(Policy-Aware Scheduling),并支持三种明确定义的跨类型转换:高频明文可预编译为激活向量;稳定的明文/激活内容可蒸馏为参数模块("能力插件");冷或过时的参数可退回到明文存储。

**三层架构。** 接口层的 MemReader 把自然语言请求解析为结构化的 MemoryCall(任务意图、时间范围、记忆类型、访问意图),对外暴露一套 Memory API(Provenance、Update、LogQuery)以及用于串联操作的流水线机制(检索 → 增补 → 更新 → 归档)。操作层是控制中枢:MemOperator 构建标签/图谱/层级索引以支持检索,MemScheduler 依据任务意图和上下文选择并排序应调用哪些记忆类型,MemLifecycle 跟踪每个单元经历的五个状态(生成、激活、合并、归档、过期)。基础设施层负责存储与治理:MemGovernance 执行访问控制与审计日志,MemVault 管理多个仓库,MemLoader/MemDumper 处理导入导出与跨平台同步,MemStore 提供跨 agent 的发布-订阅式共享(例如,某领域专家发布一份付费的"记忆插件")。本文还给出了从经典操作系统概念到 MemOS 组件的逐项映射(调度器 → MemScheduler,文件系统 → MemVault,系统调用 → Memory API,设备驱动 → MemLoader/Dumper,包管理器 → MemStore,访问控制列表 → MemGovernance),用以论证该设计把操作系统的资源管理原则推广到了记忆领域。

# Q6 实验设计

所有端到端对比都在同一个 GPT-4o-mini 底座上进行(涵盖 MIRIX、Mem0、Zep、Memobase、Supermemory、MemU 以及 MemOS-1031),硬件为 80GB H800 GPU,每个方法都调至各自在验证集上的最优配置——在固定底座的同时,允许每个系统运行在各自的最优工作点。

* **长上下文/多会话(LoCoMo、LongMemEval)**:衡量跨任务类别(单跳、多跳、时间推理、开放域)的 LLM 评判分数,以及 F1 和上下文 token 开销。
* **个性化(PreFEval、PersonaMem)**:PreFEval 在注入 0 轮和 10 轮无关对话的情况下测试个性化响应率,并跟踪错误类型(偏好未察觉、幻觉、不一致、无帮助响应);PersonaMem 报告对推断出的用户画像/偏好做四选一的准确率。
* **组件消融**:LoCoMo 上的 chunk 大小/Top-K 扫描;在负载下(10/40/100 QPS)的检索鲁棒性,衡量增/查操作的 P99/P90/平均延迟与成功率;另有一项关于基于 KV 的激活记忆加速的独立研究(检索到的正文部分未给出具体数字)。

这一设计通过固定底座,让质量/延迟/token 开销上的差异可以归因于记忆架构本身而非底层 LLM,从而直接检验本文的假设。

# Q7 数据与代码

使用的基准:LoCoMo、LongMemEval、PreFEval、PersonaMem(均为第三方基准,本文只是引用而非提出)。代码开源于 [github.com/MemTensor/MemOS](https://github.com/MemTensor/MemOS),该仓库回链至本篇 arXiv 论文以及一篇姊妹短文(arXiv:2505.22101);评测表格中发布的系统称为 MemOS-1031。

# Q8 证据质量

在四个基准、六到七个基线上,MemOS-1031 几乎在每一项报告指标上都取得最好或接近最好的成绩:LoCoMo 总体 LLM 评判分 75.80(次优 Memobase 为 72.01),总体 F1 为 45.27;LongMemEval 总体 77.8(次优 Memobase 为 72.4);PreFEval 在 0 轮和 10 轮无关对话下的个性化响应率分别为 77.2 和 71.9(次优 Mem0 为 65.9/63.7),且偏好未察觉错误率最低;PersonaMem 准确率 61.2(次优 Memobase 为 58.9)。检索鲁棒性数据显示 MemOS-1031 在高达 100 QPS 下仍保持 100% 成功率,而多个基线(MemU、Memobase、Zep)在 40 QPS 以下就出现成功率或延迟的明显恶化。这些是跨多个独立基准的一致、大幅度领先,比单一基准上的胜出更有说服力。但仍有若干局限限制了证据的推广范围:所有对比都基于同一个底座(GPT-4o-mini)和同一套硬件配置,尚不清楚这一排名在更强或不同规模的模型下是否成立;消融研究(chunk 大小/Top-K、KV 加速)在检索到的正文中只有定性描述,没有给出具体数字表格;并且——正如同时提出系统与其自有命名 checkpoint(MemOS-1031)的架构论文通常存在的问题——检索到的材料并未说明各基线的配置由谁调优,以及调优投入在各系统间是否对等。

# Q9 主要贡献

1. MemCube:一种统一封装(Memory Payload + 三段式 Metadata),让明文、激活、参数三类记忆可以通过同一接口被调度、版本化,并相互转换,而不是作为三套独立机制。
2. 一套操作系统风格的三层系统架构(接口层/操作层/基础设施层),配有命名模块(MemReader、MemScheduler、MemLifecycle、MemOperator、MemGovernance、MemVault、MemStore、MemLoader/Dumper),把可控性、可塑性、可演化性明确地作为设计支柱,而不是隐含的涌现属性。
3. 一次实证验证(MemOS-1031),表明该架构在长上下文问答、个性化、偏好理解四个基准上均优于六个记忆系统基线,同时在并发负载下保持更低延迟和更高成功率。

# Q10 下一步

* 论文自身提出的方向:面向跨 LLM/跨应用记忆共享的记忆交换协议(Memory Interchange Protocol, MIP),定义信任与兼容规则;能从使用反馈中自我优化和重构、无需人工维护的自演化 MemBlock;以及支持资产级记忆交易的去中心化"记忆市场"。
* 检索到的材料未能解答的问题:MemOS 的优势随底座模型强度或规模变化会如何演变;当明文/激活 → 参数的蒸馏遇到后续需要撤回的记忆(参数 → 明文)时,冲突该如何解决;以及本文在四个应用场景中提出的、跨多用户多 agent 边界的记忆共享(货币化、权限控制)该如何被审计或防止泄露。
* **与本仓库的关联**:MemCube 为每个记忆单元维护的生命周期状态 + 溯源 + 版本链,是本知识库在 [Agent memory](../topics/agent-memory.md) 主题下已经关注的"可审计状态"问题的一个具体实例——值得对照 Mem0 更简单的 ADD/UPDATE/DELETE/NOOP 工具调用式设计,以及 Zep 的时序知识图谱路线,看这套额外的治理机制在实证上换来了什么、代价是多少复杂度。
