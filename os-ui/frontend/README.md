# os-ui/frontend

This is the user interface of the Research OS: the pages you see in the
desktop client ([os-ui/client](../client/README.md)) and, during development,
in a browser. It is a Vite + React + TypeScript + Tailwind app. It does not
produce data by itself; it reads `public/state.json`, which is generated by
`os-ui/generator/`.

The frontend polls `state.json` every five seconds. If the file is missing, it
shows an empty state with the generator command. If fields are missing, it shows
honest empty values instead of inventing repository state.

## What you see

Since 2026-11-22 the app uses the layout of mockup C, "document first"
([os-ui/mockups/step1/c-document.html](../mockups/step1/c-document.html), chosen by the Human Owner on
2026-11-21; the decision is the "Layout" row in [HANDOFF.md](../../HANDOFF.md)
Decisions):

- **Left navigation**: Home, Projects, Paper wiki, Skills, Plugins, a Quick
  access list of the registered projects, and at the bottom the snapshot
  status (with Regenerate in the desktop client), Settings, and Collapse,
  which shrinks the bar to icons.
- **Home**: the root-agent conversation as a prompt bar that opens in place,
  one card per project, and a closed **Workspace status** section with Active
  Work, Recent Activity, Governance, and the policy chips.
- **A project's workspace**: its conversation on the left (collapsible to a
  thin strip) and its views on the right: Overview, then Idea, Code, Skeleton,
  Assets, Paper. Idea is the bundled `idea-view` plugin's page (the project's
  `idea_graph.md` drawn as a graph of questions, hypotheses, experiments,
  results, and claims), Code the bundled `code-view` plugin's (the project's
  `Code/` files and Git changes), Skeleton the bundled `skeleton-view`
  plugin's (the project's `paper_skeleton.md`, claims and evidence first),
  Assets the bundled `assets-view` plugin's (the project's `Figs/`,
  `Baselines/`, `Code/results/`, and the datasets `Code/README.md` lists), and
  Paper the bundled `paper-view` plugin's (the project's `paper/main.pdf`,
  drawn with a vendored PDF.js), all in the desktop client only.
- **Paper wiki**, **Skills**, **Plugins**, and **Settings** pages.

The app remembers, in the browser's local storage, whether the sidebar and the
conversation panes are collapsed and which page and project were open. The
older desktop-OS shell (draggable windows and a dock) is still in
`src/desktop/` but no longer shown; see "Going back" below.

## Run

First generate `state.json`:

```bash
cd os-ui/generator
uv run python generate.py
```

Then start the frontend:

```bash
cd os-ui/frontend
npm install
npm run dev
```

The dev server usually opens at `http://localhost:5173/`. `./os-ui/start.sh`
does both steps and also copies `paper-wiki/` in for the Paper wiki page.

Build:

```bash
cd os-ui/frontend
npm run build
```

The build output goes to `dist/`, which is gitignored.

Tests (the endpoints in `server/`, with a real os-harness turn with its fake
Claude CLI and a real Vite dev server, and the renderer's pure modules in
`src/`, such as the plugin pages and the saved layout; Node 22.18+ for its
TypeScript support). `npm test` runs every `server/**/*.test.ts` and
`src/**/*.test.ts`:

```bash
cd os-ui/frontend
npm test
```

A test file that has not finished after 10 minutes fails with its name
(`--test-timeout=600000`; the slowest, `server/codeGit.test.ts`, takes under
a minute on CI, and its own per-test allowances add up to under 9 minutes).
On Windows, `server/testGuard.ts` (preloaded with `--import`, here and in
`os-ui/client`'s `npm test`) also prints `# [test-guard]` lines when a file's
process stays up 5 s after its tests are done, or is still running a minute
before that limit: the event loop's resources, child processes, unfinished
tests, and the git on PATH. `OS_UI_TEST_GUARD=1` turns those lines on
elsewhere.

The layout itself is tested end to end in the desktop client
(`os-ui/client/e2e/app.test.ts`, `npm run test:e2e` there).

## Common Edits

### Change a colour, a font, or a shadow

Every colour lives once, as a variable at the top of `src/index.css`, for
example `--accent: #1e5a56;` (the teal of selected items, links, and the focus
ring) or `--bg: #f3eee5;` (the page background). Change the value there and
every page follows. Each variable has a comment saying where it shows.

- `tailwind.config.js` only gives those variables short names for the page
  code (`bg-card`, `text-muted`, `bg-accent`, ...). You do not need to touch it
  to change a colour; only to add a new one.
- The second block of variables (`--panel`, `--ink-soft`, `--grid`,
  `--verify`, `--stale`) are older names kept for existing components and
  point at the new colours. Leave them as they are.
- Fonts are the `--serif`, `--sans`, and `--mono` lists in the same place.
  They name fonts already on the computer, so the app downloads none.
- The brand monograms in the Papers popover (`components/PaperSources.tsx`)
  keep each paper source's own colour on purpose; they are not theme colours.

### Change a piece of text

Fixed text lives in the page or component that shows it. Search the `src/`
folder for the words you see on screen; the file that contains them is the one
to edit. The most visited ones:

- Page titles and the line under them: the `PageHeader` call at the top of
  each file in `src/pages/` (for example `title="Home"` and `lede="..."`).
- The left navigation labels: `src/shell/Sidebar.tsx`, except a plugin's
  page (Paper wiki), whose label is its panel's `title` in
  `plugins/<id>/plugin.json`.
- The root agent's and a project agent's opening text and example requests:
  `src/lib/agentCopy.ts`.
- The Plugins page: an enabled plugin's card shows its manifest's `name` and
  `description`; the plugins not yet available are the `PLANNED` list in
  `src/pages/PluginsPage.tsx`.
- The workspace's tab row (`workspaceTabs` in `src/shell/layoutState.ts`) and
  the ask bar: `src/pages/WorkspacePage.tsx`; the selection message and the
  reference text: `src/plugins/select.ts`.
- The Code view's page: `plugins/code-view/site/`; the Paper view's:
  `plugins/paper-view/site/`; the Skeleton view's:
  `plugins/skeleton-view/site/`; the Assets view's: `plugins/assets-view/site/`
  (its folder walk in `walk.ts`, its picture queue in `queue.ts`, its SVG
  check in `svg.ts`); the Idea view's: `plugins/idea-view/site/` (its
  map's layout in `layout.ts`) (each one's
  words in `logic.ts`). Each is
  static files and a TypeScript entry, checked by `npm run typecheck`, tested
  by `npm test`, and bundled by the desktop client's `scripts/build.mjs`; what
  they share (text-only DOM helpers, the read channel's URLs and reading a
  response, the selection limits) is `plugins/site-kit.ts`, and the Markdown
  reader (blocks, inline tokens, a skeleton's claims and Snapshot) is
  `plugins/md-kit.ts`. Its tests read frozen copies of two skeletons in
  `plugins/fixtures/`, the Assets view's frozen copies of nanochat_cpu's
  and the template's asset folders, and the Idea view's two idea files (its
  README says what each is). The Paper view's PDF.js is vendored in
  `plugins/paper-view/site/vendor/`, never an npm package: its README says
  how to update it, and `npm test` checks the files against it.

Dynamic repository content from `state.json` stays as source data, not
rewritten in the frontend.

### Other changes

- Skill install command construction: edit `src/lib/skills.ts`. The
  per-location enable/disable toggle lives in `src/components/SkillInstalls.tsx`
  and posts to `/api/skill/toggle` (`server/skillToggle.ts`).
- `state.json` shape: update `src/types.ts`, `os-ui/DESIGN.md`, and the
  generator together.
- Endpoints: the app's own are listed in `TRUNK_MOUNTS` in `server/api.ts`.
  A bundled plugin's endpoints are named in its `plugins/<id>/plugin.json`
  (`contributes.handlers`, served at `/api/<id>/<handler>`), and their code is
  listed in `server/pluginHandlers.ts`; the tests fail if the two disagree.
  `DESKTOP_ONLY_HANDLERS` there (the Code view's `code-view/git`) are declared
  but never mounted on the dev server.
  The registry (`server/registry.ts`) joins both lists. `api-plugin.ts`
  serves the result on the dev server's one origin; the desktop client
  serves the same registry split by origin, the trunk's endpoints on
  `app://research-os` and each plugin's on `app://<id>`
  (`os-ui/client/src/main/protocol.ts`), so there is no second list to keep
  in step. `server/registry.test.ts` and `server/api.test.ts` pin the
  resulting prefixes and token flags; update them with any endpoint change.
  The client ships each `plugins/<id>/plugin.json` (and a `site/` folder
  beside it, if any) in its package, so on the server and in the client a new
  bundled plugin needs only its folder, its id in `plugins/bundled.ts`, and
  its handlers.
- Plugin pages in the app: the renderer compiles every bundled
  `plugins/<id>/plugin.json` in (`src/plugins/registry.ts`, in
  `plugins/bundled.ts` order) and parses it with the same parser as the
  server; a manifest that does not parse is left out with a console error.
  `src/plugins/pages.ts` turns the manifests into pages: a home panel with
  `"placement": "nav"` becomes a left-navigation item after Projects, which
  opens `src/pages/PluginScreen.tsx` (the band with the plugin's name and
  description, then the page in a frame), and every loaded plugin gets a
  card on the Plugins page with one chip per page. The frame loads
  `app://<id>/<entry>` in the desktop client and `./<site.workspace>/<entry>`
  in a browser (Paper wiki: `./paper-wiki/viz.html`, the cache copy
  `start.sh` makes); a plugin without `site.workspace` says it opens in the
  desktop app. The manifest has no icon, so `pluginIcon` in `registry.ts`
  holds one per bundled plugin (the puzzle piece otherwise).
  `src/plugins/pages.test.ts` pins Paper wiki's label and both frame URLs
  against the real `plugins/` folder.
- What the layout remembers: `src/shell/layoutState.ts` (one `localStorage`
  key, `osui.layout.v1`; clearing it returns to Home with everything open).
  A plugin's page is remembered by its key, `<plugin>/<page>`; a saved page
  whose plugin is not loaded opens Home, and a layout saved as `wiki` before
  2026-11-22 opens `paper-wiki/viewer`.

### Going back to the desktop-OS shell

`src/App.tsx` renders `<Shell>`. Rendering `<Desktop state={status.state} />`
from `./desktop/Desktop` there instead brings back the windows and the dock;
the comment in that file says so. A later change deletes `src/desktop/`.

## English-first Policy

The UI is currently English-first. Do not add a language switch or i18n layer
yet. Chinese support can be added later when the OS is stable enough to justify
the maintenance cost.

`os-ui/README_zh.md` keeps the Chinese overview for reference. Runtime UI,
generator messages, and current docs should remain English unless a later task
explicitly opens Chinese localization work.
